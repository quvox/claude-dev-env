# 00-requests/ — 要求定義

日本語で書く。

**この層が決めること**: なぜやるのか。何をやりたいか・何を達成したいか、「完成」の姿、
受け入れシナリオ、用語、記録した決定。
**この層が決めないこと**: システムの振る舞い(01)、構造(02)、実装(03)。
**技術の名前を出すことだけは条件つきで許される** — 下の `decisions/` の指針を見ること。

**この層は人間のものである。** AI はここのどのファイルにも差分を提案してよいが、
**00 への意味のある変更はすべて人間の同意を要する**。とくに `request.md` は人間自身の言葉で
書かれており、**AI が「整えるため」に書き直してはならない**。

## ファイル構成

```
docs/00-requests/
├── request.md            # 必須。中心となる要求文書(人間の言葉)
├── <topic>.md            # 任意。要求ごとに追加してよい(画像・HTML は examples/ に置いて参照する)
├── acceptances.md        # 必須。受け入れシナリオ
├── terminology.md        # 必須。プロジェクト用語集
├── decisions/
│   ├── index.md          # 生成物。手書きしない
│   └── <category>.md     # 要求カテゴリごとの決定事項
└── examples/             # 任意。具体例・サンプル。フロントマター不要、版管理対象外
```

## request.md

- 必須の見出しは**雛形にある見出しすべて** — 背景と目的 / 対象ユーザー / **やること** /
  **やらないこと** / 完成イメージ / 制約・前提 / 未解決事項。(`/verify-docs` の C 検査が見るのは
  「空でない未解決事項が検証済み記録を止める」ことだけなので、**見出しの欠落は黙って通り抜ける**。
  だから見出しそのものを必須にしてある。)
- **「やらないこと」を決して空にしてはならない。** 除外の一覧が空だと範囲が無限になり、
  下流のすべての検査が働かなくなる。本当に除外するものが無いなら、**そう書き、その理由を書く**。
- 各要求に `RQ-<category>-nn` の ID を与える。`<category>` は要求のかたまりを表す短いケバブ語
  (`auth` / `billing` / `ops` …)である。
- **矛盾する要求は上書きである。** 新しい要求が既存の文と共存できないなら、古い文を書き直す
  (**両方を残さない** — 取り下げられた意図は git の中に生きている)。

## acceptances.md

- 利用者の言葉で書くシナリオ。ID は `AC-nn`。
- 各シナリオ: 対応要求(`RQ-*`)/ 前提 / 操作 / 期待される結果。**技術用語を使わない**
  (これを EARS にするのは 01 の仕事である)。「やらないこと」を理由に**意図的に試験しない**
  シナリオは、その理由とともに雛形の「対象外とするシナリオ」節に置く。
- これらは 01 のユースケース(`UC-nn`)の種である。**形式化する `UC` を持たない `AC-nn` は
  01 の穴である。**
- 「やらないこと」に挙がっている操作を成功シナリオとして書いてはならない
  (矛盾として検出される)。

## terminology.md

- 用語 / 定義 / **含む例 / 含まない例** / 英語表記(識別子で使う語)/ 別名と禁止表記。
- **含む例・含まない例は、足す用語・明確化する用語のすべてで必須である。この規則はこのファイルが
  所有する**(他所からは引用すること。書き写してはならない)。定義の1文だけでは、
  **全員が合意しながら別の外延を思い浮かべる**ことができてしまう — 含む例2つと含まない例1つが、
  それを固定する。既存の行は、タスクがその用語に触れたときに埋める。
  **検査は `/verify-docs` A0 の `all` モードだけ**、重大度「中」で、PASS を止めない:
  雛形には「新しく書いた行」と「古い行」を区別するものが無いので、増分で走らせると
  古い行を毎回すべて報告することになる。
- 雛形の「判断に迷いやすい区別」の表は任意である — 区別するものが無いときは「なし」と書く。
- **すべての層がこのプロジェクト用語集に従う。** 新しい用語が要るときは、まずここへ足すことを提案する。
- **定義が揺れたままの用語を残さない** — 揺れは 03 まで伝わり、実装の不一致になる。

## decisions/ — 決定台帳

要求カテゴリごとに1ファイル。ID は `D0-<category>-nn`。**分割の引き金はサイズではない**
(`.claude/directions/core.md` §6): 1つのカテゴリの中のサブトピックが**別々の作業指示の対象になった**ときに
`<category>-<subtopic>.md` へ切る。切るときに要るのは、切る候補と、新しいファイル名と、
**いま現在そのパスを参照している文書**(`source:` frontmatter と本文の両方)である。
そして**決して番号を振り直さない**: `D0-<category>-nn` はカテゴリに属していてファイル名には
属さないので、移した項目は ID を保つ(条項 ID と同じ不動性である)。

すべての項目は、下の3区分のちょうど1つに必ず分類される。
**この分類こそが、無人での運転を可能にしているものである。**

| 区分 | 意味 | AI の扱い |
|---|---|---|
| **決定** | 人間が理由と見直す条件つきで決めた | 見直す条件が偽であるあいだは従う。変えるのは 00 起点の変更タスクである |
| **委任** | AI が決めてよい。**委任範囲**と**制約(ガードレール)**が必須 | 範囲の中で自分で決める(これが既定)。決めたことを `D0-*` の ID つきで、書いた場所に記録する |
| **要確認** | まだ誰も決めていない。**論点**と**誰がいつまでに**が必須 | **決して自分で決めない。** 仕事がそこへ届いたら決定シートに載せる |

- **キットの標準委任(`DS-01`〜`DS-08`)は既に有効であり、ここには書かない**
  (`.claude/directions/delegation.md` §2 — それはキットの規範であって、このプロジェクトの
  台帳ではない)。このファイルは、プロジェクトがそれを**狭めるか取り消す**場所である:
  DS-ID を名指した `決定` が、その瞬間から標準の範囲に勝つ(向こうの §4)。
  **標準の集合を `decisions/` へ書き写してはならない** — 委任の複製は必ずずれ、
  プロジェクト側のファイルは**キットの更新を黙って追わなくなる**。
- **指針(検査なし。執行者は読み手 — 原則11)。決定が技術の名前を出してよいのは、その技術を
  選んだこと自体が人間の判断だったときである。** そのとき 00 が持つのは**何を選んだか、
  そして何がそれによって禁じられたか**である。どう使うか — 設定値、関数名、順序、ファイル名、
  行番号 — は 02 / 03 のものである。区分ごとの読み方の試験:
  - **決定**: 「技術の名前を消しても、内容の欄はまだ何かを意味しているか?」
    何も残らないなら、その項目は決定の在るべき場所に機構を記録している(実測: `iptables` の
    項目は名前を消すと空になった — 本当の決定「ホストではなくコンテナ内で制御」は、
    理由の欄にしか座っていなかった)。
  - **委任**: **制約(ガードレール)は技術の名前を出してよい**(「`flock` は使わない」は
    本物のガードレールである)。**委任範囲がそれで閉じてはならない** — 次の項目を見ること。
  - **要確認**: 対象外である。論点は、答えられるようになるために必要なものを何でも名指す。
- **指針(同上)。委任範囲が手段を並べるときは、一覧を開いたままにする。**
  「実装手段(`flock` / `mkdir` / `ln -s` **/ その他**)」や「…**など**」は委任の広さを述べて
  いる。**開きの語を落とすと、その一覧は「許された選択肢の閉じた集合」と読める** —
  それは委任することの逆である。
- **委任範囲か制約を欠いた委任の項目は、重大度「高」の所見である**(範囲の無い委任は白紙小切手)。
- **新しい決定・触れた決定は必ず `見直す条件` を持つ。** これは前提を考え直さなければならなく
  なる**観測可能な条件**であって、予定された見直し日ではない。本当に恒久のときは
  `なし(恒久である理由)` と書く — 裸の `なし` では足りない。既存の台帳を一気に埋め戻しては
  ならない。タスクがその決定に届いたとき、あるいはそれを変えたときに、古い項目を埋める。
  **条件が成立しても決定が黙って無効になることはない**: その項目が古くなり、
  00 起点の変更か、続行するという人間の明示的な決定を要する状態になる。
- **要確認は検証を止めない**(宣言された停止点である)。ただし仕事がそこへ届いたら、
  決定シートに載る。
- 要確認に答えが出たら、**決定**へ移し、理由を書く(MINOR の変更)。
- **タスクの `sheet.md` の回答はここへ着地する**: 概念の明確化の回答は `terminology.md` の行に
  なり(含む例つきで)、判断を決着させたところは**決定**または**委任**の項目になる。
  **`分割可否` を確認する節はシートに無い** — 01 を書く AI が決めて、01 の要件の行に
  開示する(`.claude/directions/01-requirements.md` の「分割可否」)。ここではない。
- 繰り返し出てくる問いは、次の決定シートで**委任**にすることを提案する —
  **ただし、それが既に `DS-*` に覆われていないかを先に確かめること**。覆われていたなら、
  それはそもそも問うてはならなかったものである。

## Frontmatter(`examples/` 以外のすべてのファイル)

`id` はファイル名と一致させる(01 に同じ名前のファイルが在るときは、`id` が層を名乗る —
`.claude/directions/core.md` §6)。`source` は 00 の外を決して指さない(ここが最上層である)。
`request.md` は `source: []` を持ち、層の中での派生は起点を並べる
(`acceptances.md` / `terminology.md` → `request.md`。雛形が示すとおり)。
実物の frontmatter のコメントは**行まるごとだけ** — 値の後ろのインラインコメントは、
このキットのパーサに**値の一部として読まれる**(`.claude/directions/core.md` §6)。

```yaml
---
id: request
version: 1.0.0
updated: 2026-08-01
source: []
summary: <1行>
keywords: [認証, MFA]
# verified: verify 系フローだけが書く
---
```

## 終える前の自己点検

- `request.md` の「やること」の各項目は `RQ-*` の ID を持っているか?
- 「やらないこと」は空でないか?
- 「やらないこと」と矛盾する `AC-nn` は無いか?
- `decisions/` のすべての項目は 決定 / 委任 / 要確認 のどれかになっていて、
  すべての委任に範囲とガードレールが、すべての要確認に論点と期限が在るか?
- プロジェクト用語集に無い語を使っていないか?
- 参照している `examples/` のファイルは実在するか?
- **他所の事実(00 は最上流なので、写しうるのはコードと下の層の事実である)を写していないか?** 持ち主でない文書は、写さずに参照する(形と例外の正は `conventions.md` §4)。値そのものを本文に出したいなら機械の欄に入れる。
