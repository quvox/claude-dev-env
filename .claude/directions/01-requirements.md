# 01-requirements/ — 要件定義

日本語で書く。

**この層が決めること**: 何を満たすか — システムが満たすべきこと、ユースケース、
システムと環境への要件。
**この層が決めないこと**: なぜやるのか(00)、どう作るか・モジュール分割(02)、実装(03)。
**技術の選択は 02 のものである。ただしそれを選んだこと自体が人間の判断だったときは 00 のもの**
(`.claude/directions/00-requests.md` の `decisions/`)。どちらにせよ 01 のものではない。
`system.md` だけが唯一の例外である(下の「system.md」の節)。

`source` は必ず 00-requests を指す(`functional.md`: 少なくとも `request.md` と関係する
`decisions/*.md`。`usecases.md`: `acceptances.md`。各ファイルの集合は雛形が示す)。
同じ層の中の参照(`usecases.md` が `functional.md` を挙げる)を足してよいが、
**00 の起点を置き換えることは決してない。**
**00 に無いものを 01 へ持ち込んではならない。**「やらないこと」から 01 へ紛れ込んだものが
無いことを、毎回確かめる。

## 01 と 02/03 の境目 — **この境目はこのファイルが所有する**

**実測された失敗は、01 が下へずり落ちることである**: 要件が、それを実現する機構の言葉で
書かれてしまう。**代償は二重に払う。** 文書は、要件を持っている当人にはレビューできなくなり、
そして — **01 に書かれた機構は*要件*なので** — **実現の細部のすべてが人間の同意を要するように
なる**。それは、まさに AI がやるべきだった仕事である。

試験は2つある。どちらも安く、互いに一致する:

| テスト | 問い | 01 でない例 → 行き先 |
|---|---|---|
| **置き換えテスト** | **実現方式を丸ごと別のものに差し替えても、この文はまだ真であってほしいか。** 差し替えると偽になる/意味を失うなら、書いているのは要件ではなく機構 | 「WHEN キューへの投入が3回失敗したら」→ 再試行回数も、キューであることも機構。**02**(方式)と **03**(実際の回数) |
| **観測者テスト** | **システムの内側を見ずに、この文が満たされたか確かめられるか。** 内側を見ないと確かめられないなら 01 ではない | 「IF 接続プールが枯渇したら」→ 外からは見えない。外から見えるのは「待たされる/断られる/何が表示される」のほう。**02/03** |

**これは問う基準の条件1とまったく同じ境目である**(`.claude/directions/delegation.md` §1):
外から見えるか。**それは偶然ではない** — **01 は外から見えるものを持ち、外から見えるものこそが
人間に問うてよいものである。** 1本の線が両方を決めており、その線の向こう側はすべて `DS-*` の
領分である: 決めて、02/03 に書いて、なぜそうしたかを開示する(向こうの §3)。

**これが意味しないこと。** 01 が以前より曖昧になるのではない — 曖昧語は禁止のままである
(CLAUDE.md §7、CS8)。**具体性が「外から観測できるもの」の側へ移る**という意味である:
「3回再試行する」は機構、「30秒以内に成功するか、失敗を利用者に伝える」は要件であり、
**後者のほうが*より*試験しやすい。**

**周期は上限ではなく、決して上限に書き換えてはならない。** 「30 秒ごとにポーリングする」は
「30 秒以内に反映する」に**ならない**: 最悪の遅延は周期を**超える**ので、この書き換えは 01 を
02 と矛盾させる(上の回数の書き換えが成り立つのは、回数には最後の試行が在るからである。
実測 — この形がそのまま出荷され、差し戻された)。**システムが実際に保証する上限を書く**
(02 がそれを満たせるか確かめたうえで)か、**数字を持たない観測可能なもの**を書いて
(「次に起動するコンテナから使える状態になる」)、周期は 02 に任せる。

**要件として述べるべき値が本当に無いとき**(再試行が何回かは外の誰も気にせず、
回復することだけを気にする): **問うてはならず、要件を発明してもならない。**
`DS-04` の下で決め、それを所有する層に書き、そこに理由を開示する
(`.claude/directions/delegation.md` §2〜§3)。**外の誰にも見えない値は、抜け落ちた要件ではない**
— **決められるのを待っている実現方法**である。

**検査は `CS18` である**(`check-ssot.py` — 仕様ドキュメントの一括検査):
`functional*.md` / `usecases.md` / `non-functional.md` の中の下層の ID
(`MODULE-*` / `MOD-*` / `PLAN-*` / `CTR-*`)や、コードの識別子・ファイルパスが違反になる。
**捕まえるのは露骨な場合だけ**であり、本当の規則は上の2つの試験で、その執行者は読み手である
(原則11)。`system.md` は対象外である — 技術を名指すことがその目的そのものだからである。

## ファイル構成

```
docs/01-requirements/
├── functional.md         # 機能要件      FR-<domain>-nn
├── non-functional.md     # 非機能要件    NFR-<category>-nn
├── usecases.md           # ユースケース  UC-nn
├── system.md             # システム・言語・開発環境・ツールの要件  SR-nn
└── decisions/
    ├── index.md          # 生成物。手書きしない
    └── <type>.md         # 要件種別ごとの決定事項  D1-<type>-nn
```

`functional.md` は、**2つの業務ドメインが別々の作業指示の対象になったら**業務ドメインで
分割する(`functional-<domain>.md`)。**引き金はサイズではない**(CLAUDE.md §7) —
クロージャはパスの集合なので、1本のままだと 01 を触るどの作業指示も交わり、並走できない
(`orchestration.md` §3.4)。分割の基準は業務の構造である —
技術的な分割は 02 の仕事であり、ここで起きてはならない。

## functional.md

- 要件ごとに: ID / 内容 / **分割可否** / **受け入れ基準(EARS)** / 対応する 00 の `RQ-*`・`AC-*`。
- **各受け入れ基準は自分の ID を持つ** — `FR-<domain>-nn-#`(`#` の欄が番地になっている)。
  02 の網羅表と 03 のテスト表はこの**条項 ID**を鍵にしており、それによって
  **要件が部分的にしか満たされていないことが、見えないままではなく数えられる**ようになる。
- **条項 ID は、一度割り当てたら決して動かない**(この規則はこのファイルが所有する。
  **消えた条項 ID は `check-ssot.py` CS26 が見る** — 基準の版(最後の `/verify-docs` の green の
  鮮度スタンプのコミット。無ければ `HEAD`)と比べて、**要件の見出しが残っているのに条項 ID だけが
  消えた形**を違反にする。**git を引けない場所では「判定不能」と印字して違反を出さない**ので、
  そこと、要件まるごとの移行(下)は `/verify-docs` の独立レビューが見張る)。
  02・03・`pendings.md`・`residual.md` が外から参照しており、**番号を振り直した参照はそれでも解決してしまう**
  — 別の条項を指すだけである — ので、**壊れ方は静かである**(参照の側のどの検査も解決に
  成功してしまう。鳴るのは上の CS26 だけである)。
  - **条項 ID は受け入れ基準の表の1列目に置く。**
  - **穴を埋めるために番号を振り直してはならず、退役した番号を別の条項に再利用してもならない。**
    7つの条項の4番目を消したら、残るのは 1, 2, 3, 5, 6, 7 の6つである。
  - **条項の退役は明示的な削除である**: 編集の `種別` 欄に `delete` と書く(**消えるのは条項であって行ではない** —
    行は `delete` の印を持ったまま残す。番号を振り直さない — 条項 ID は不動である。CLAUDE.md §7)。**ただ消えただけの条項は
    この規則の違反である**(番号の振り直しは、失われたことを隠す)。
  - 要件まるごとの番号の振り直しは**移行**であって編集ではない:
    **同じ `/build` のクロージャが、参照しているすべての行を書き直さなければならない**
    (番号を動かす作業とその参照の書き換えは1タスクである)。`/verify-docs` A2 は 02 側を読む。
    **`pendings.md`・`residual.md` 側には検査が無いので指針である — 執行者は読み手**(CLAUDE.md 原則11 の仕掛け)。
- **要件が「利用者に何かを伝える」と約束するとき、受け入れ基準が文面を持つ**
  (配置は持たない — それは UX 文書のもの。`.claude/directions/ux.md`「01(要件)との紐付け」)。
  「削除した資源を種別つきで1行ずつ表示する」は条項である。画面のどこに出るかは条項ではない。
  **01 の側から UX 文書への参照は書かない**(紐付けは ux 側からの片方向 — 同節)。
- **★ `分割可否` — この要件は一部だけ満たされてよいか?** 値はちょうど2つ:
  - `不可分` — 部分的な状態は、何も無いより悪い(権限、金、データ整合、監査証跡)。
    **そういう要件に `部分` の条項が在ることは、例外なく PASS を止める。**
  - `段階可(理由)` — 部分的な状態が正当な途中の状態である。**理由は必須**であり、
    理由の無い `段階可` は重大度「高」の所見である(ガードレールの無い委任と同じ形)。
  - **すべての要件がこれを述べる。未記載は既定ではなく違反である**(`check-ssot.py` CS24)。
    「書かなければ `不可分` とみなす」という既定を置くと、**「決めなかった」と「不可分と決めた」が
    区別できなくなる** — 02 が正当に `部分` と書きたい場面で完成判定が止まり、止まった側は
    原因を辿れない(このキットが繰り返し述べる「沈黙と不在は区別できない」と同じ形である)。
  - **非機能要件もこれを持つ**(条項に分けないので、要件1つにつき1つ)。性能目標は
    たいてい `段階可`、法令要件は `不可分` である。
  - どこで決まるか: **この判断は 01 が所有する。人間には問わず、01 を書く AI が決めて開示する。**
    **02 で決してはならない**(仕事をする層に「どこまでやるか」を選ばせることになる)。
    **決定シートには載せない** — シートに何を載せてよいかの正は
    `.claude/directions/delegation.md` §1 であり、**その例外(上流と衝突するときなど)は
    向こうが所有する。ここで先取りしない。**
  - **開示先は要件の行そのものである。** 値は `functional.md` / `non-functional.md` の当の要件が
    持ち(未記載は違反 — `check-ssot.py` CS24)、`段階可` は同じ行に理由を持つ(上)。
    **要件の行の外に台帳を置かない** — 値と理由が要件から離れると、その要件を読む者が
    「どこまで満たせば足りるか」を要件から読み取れなくなる
    (`delegation.md` §3 が求める構築記録への写しは、台帳ではない)。
- **EARS**: `WHEN <契機> the system SHALL <振る舞い>` / `IF <条件> THEN the system SHALL …` /
  `WHILE <状態> …` / `WHERE <文脈> …`。日本語でよいが、この構造は保つ。
- **正常系だけを覆う受け入れ基準は未完成である**(`check-ssot.py` CS25 が見る。
  **見るのは機能要件だけである** — 非機能要件は条項に分けないので `種別` の欄を持つ表が無く、
  機械が数えられるものが無い。そちらは下の「終える前の自己点検」が受け持つ)。
  すべての要件は**境界値**と**異常系**を述べなければならない: 上限を超えたら何が起きるか、
  空のときどうなるか、外部依存が落ちているときどうなるか。
  **この穴だけは下流が捕まえられない** — 02 のカバレッジ表も 03 のテスト表も
  「01 の条項に対して行が在るか」しか見ないので、**条項そのものが無い穴は全層を素通りする。**
  **足すときは末尾に新しい番号で足す** — 途中に挿し込んで番号を振り直すことは、上の
  「条項 ID は不動である」の違反であり、**そちらは `check-ssot.py` CS26 が見る**(この検査が、
  別の検査が違反として鳴らす向きに押してはならない — 末尾に足せば両方を満たす)。
  **正当に省くときは、その要件の中に `境界値なし(<理由>)` / `異常系なし(<理由>)` と書く**
  (下の「外の誰にも区別できない結果しか持たない…」がその理由になる)。
  **`なし(該当なし)` のような空の文句は理由として数えない** — 逃げ道は必ず濫用される。
  **ただし機械が見るのは形だけである** ★ — 打ち消しの決まり文句かどうかは判定できても、
  **その理由が本当に理由になっているかは判定できない**(`ああああ` は通る)。
  そこは**指針であり、執行者は読み手である** — `delegation.md` §3 が
  「理由が本当に理由になっているか」を検査を持てないものに分類しているのと同じ扱いである。
  **`種別` の欄は語と完全に一致して読まれる** — `境界値なし` と書いて条項の代わりにすることは
  できない。**基準の欄が空の条項も、条項として数えない。**
  **境界値の条項を退役させた**(`種別` を `delete` にした)ときは、代わりの条項を末尾に足すか、
  上の `なし(<理由>)` を書く。**退役だけしてそのままにはできない。**
  **機構としてではなく、観測できる結果として書く**(上の2つの試験):
  条項は「何が見えるか・データはどう残るか」であって、「どう検知して何回試すか」ではない。
  **外の誰にも区別できない結果しか持たない境界値や異常系は、そもそもここに属さない** —
  それは `DS-02` / `DS-04`(`.claude/directions/delegation.md` §2)であり、02/03 で決めて開示する
  (向こうの §3)。そういう行で 01 を膨らませることが、この層の境目が止めようとしている
  ずり落ちそのものであり、**AI が下せた決定を人間が下さねばならないものに変えてしまう。**
- 曖昧語と程度の語は禁止 — 語彙とその正は CLAUDE.md §7 である(CS8 が見る)。
  数・条件・例を書く。
- **AI が決めた既定は「今回決めた既定(開示)」の節に置く**(雛形が持っている)。標準委任
  (`.claude/directions/delegation.md` §2)で決めたもののうち、**外から観測される値・振る舞い**
  だけがここに来る — 条項として書いたものには、その条項 ID を添える。形は同 §3 の1行
  (`[DS-nn]` / 決めたこと / 理由 / 見直す条件。すべて必須)であり、**節を空にしない**
  (決めた既定が無かったのなら「判断なし: <理由>」。`check-ssot.py` CS19 が見る)。
  **ここへ手段を降ろさない** — リトライ回数・例外型・キューは 02/03 のものである(上の2つの試験)。

## non-functional.md

**6つのカテゴリすべてに節を置く。** 該当しないものを消してはならない —
代わりに「適用外(理由)」と書く(**節の欠落は穴を見えなくする**):

性能 / 可用性・信頼性 / セキュリティ / 運用・保守性 / 拡張性 / 法令・コンプライアンス。

すべての要件は**測定可能**でなければならず(「速い」ではなく「p95 で 300ms 以内」)、
**どう測るかを述べなければならない — 観測点として述べるのであって、その観測を行う実装として
ではない**。「3種のプロセス環境を取得して当該変数が無いことを確認する」は測定方法である。
「`<module>` の単体テストが `unset X` を含むことを固定している」は 03 の領分であり、
**どのテストが在るかを名指すと、テストが1本増えるたびに 01 が古くなる。**
**どのテストがどの条項を覆うかは `03-impl/tests/` に属する。**
本当に観測点を持たない要件のときは、測定方法の欄に「測らない」とその理由を書く —
これは「適用外(理由)」と**同じではない**。後者はカテゴリまるごとを落とすが、
ここでは要件は立ったままで、その測定だけが不可能だと宣言されている。

**各要件は「対応する上流」を持つ。** `RQ-*` / `request.md` の制約・前提 / `D0-*` のどれかを引く
— 機能要件が 00 の項目を引くのと同じ理由である。どの人間の期待から来た値かが辿れないと、
**値を変えたときに何が損なわれるかを誰も確かめられず**、雛形の例示値がそのまま
「追跡可能な誤仕様」として下流へ運ばれる。どれも引けない要件は、上流を持たない発明である —
00 へ戻して立てるか、`DS-04` の下で決めて開示する(`.claude/directions/delegation.md` §2.1)。

**法令・コンプライアンスだけは列が違う**: `ID / 根拠法令・契約 / 適用条件 / 必須統制 /
検証方法 / 対応する上流 / 分割可否`(雛形が示す)。法的要件は数値の目標値を持たないことが多く、
**法令名だけでは実装もテストもできない** — 何を根拠に、どこまで適用され、実装が何を満たし、
どう確かめるかを分けて書く。`検証方法` が他分類の `測定方法` に当たる。
該当が1件も無いときだけ、表を消して「適用外(理由)」と書く。

## usecases.md

- `UC-nn`: アクター / 目的 / 事前条件 / 事後条件 / **基本フロー** / **代替・例外フロー** /
  関連する要件。
- 各 UC に、それが 00 のどの `AC-nn` を形式化しているかを書く。
  **対応する UC を持たない `AC-nn` は穴である**(正当な理由が在るならそれを書く)。
- **すべての機能要件は、どれかの UC のフローに現れなければならない。** 現れないものは理由つきで
  「シナリオ外要件」の節に並べる。**そこへ列挙が要るのは機能要件だけである** —
  どの UC にも現れない非機能要件は普通のことであり、並べる必要は無い(雛形の NFR の行は
  任意の例示であり、`/verify-docs` A1 は機能要件だけを見る)。
- **UC は E2E シナリオの唯一の上流である**(02 がそこから `E2E-nn` を導く)。
- 利用者の道筋を持たないシステム(純粋なライブラリなど)では、「ユースケースなし(理由)」と書く。

## system.md

システム・インフラ・言語・開発環境・道具立てに対する**要件**(`SR-nn`)。

- 「何が要るか」がここに入る。**正確なコマンドと版を固定するのは 02 の仕事である**
  (`02-design/environments.md`)。ここに入るのは要件と制約である:
  「オンプレで動くこと」「Python 3.12 以上」「CI で 10 分以内にテストが終わること」など。
- 交渉不可能な技術的制約は、専用の「必須制約(交渉不可能)」節に置く(雛形どおりの見出し)。
- **`system.md` を書くときは外部依存表が必須である**(雛形が持っている): 外部システム1つにつき
  1行で、ID の欄が `EXTERNAL-<system>` を持つ。その欄が、`relations` の
  `callers` / `callees` の `EXTERNAL-*` の値が一致すべき正である
  (`relations.md` §3 / §5 — 同じ ID であって、対応づけではない)。
  指針 — この表を突き合わせるスクリプトは無い。`check-relations.py` は `EXTERNAL-` の接頭辞
  しか見ていない。
- **`SR-nn` の ID は決して振り直さない** — 02 がその行を参照しているので、振り直すと参照が壊れる
  (条項 ID が不動なのと同じ理由)。指針 — **この振り直しの禁止**を覆う検査は無く、読み手が守る(`充足` のほうは `/verify-docs` A2 が見る)。
  SR の採番は雛形の帯方式である(1節につき10番の帯を1つ)。
- 未決の項目を消してはならない — 「未定(02設計で決める)」と明示的に書く。
- **`分割可否` は `SR-*` には適用されず、条項 ID も付かない。** これらは技術的な前提と制約で
  あって、システムが満たす振る舞いではないので、「一部だけ満たされた」に意味が無い:
  交渉不可能な隔離境界を半分だけ守るのは途中の状態ではなく、**破れている**。
  したがって、このファイルの自己点検にある「機能要件・非機能要件」という言い方は、
  **省略形ではなく、これで全部**である。02 の網羅表は `SR-*` の行を要件単位で持ち、
  その `充足` の欄は**2値**である — `満たす` / `破れている(課題票 ID)`。
  **「一部だけ」が無いことは、充足を判定しない理由にはならない** — 不可分な制約こそ2値で
  判定できる。**`破れている` が1件でも在れば完了定義を満たさない**(`CLAUDE.md` §3。
  語彙の正は `.claude/directions/02-design.md` の要件カバレッジの表である)。

## decisions/ — 要件レベルの決定

要件種別ごとに1ファイル。ID は `D1-<type>-nn`。3つの区分(決定 / 委任 / 要確認)と扱い方は
00 とまったく同じである(`.claude/directions/00-requests.md` の decisions/ の節を見ること)。

00 と 01 のどちらに置くか: **要求の意味を決めるものはすべて 00 に属する**。
**要件を固定する判断 — 詳細さの水準、境界値、非機能の目標値 — は 01 に属する。**
迷ったら 00 へ上げる(CLAUDE.md 原則3)。
