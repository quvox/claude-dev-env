# 02-design/ — 基本設計書

日本語で書く。

**この層が決めること**: どう作るか — アーキテクチャ、**モジュール分割**、契約(スキーマ・API)、
**設計が想定する連携**、具体的な開発環境、ログ戦略、テスト戦略、そして **UI の有無の宣言**。
**この層が決めないこと**: なぜやるのか(00)、何を満たすか(01)、実際のコード(03)、
UI/UX の中身 — 画面の配置・遷移・項目と状態・デザインの基調は `docs/ux/` が正である
(`.claude/directions/ux.md`。下の「UI 設計」)。

**モジュール分割はこの層の出力である**(01 が決めてはならず、03 はそれに従う)。

## ファイル構成

```
docs/02-design/
├── architecture.md       # システムアーキテクチャ、インフラ構成の設計
├── system.md             # モジュール分割定義、要件カバレッジ表、分割の根拠(この3つは動かせない)
│                         # テスト戦略と UI の有無の宣言もここに書く(切り出す契機は下記。サイズではない)
├── relations.md          # 想定機能連携一覧  PLAN-<feature-slug>   ★02⇄03比較の一方の当事者
├── contracts/
│   ├── index.md          # 生成物。手書きしない
│   └── <name>.md         # スキーマ定義・API定義  CTR-<name>(分割方法は任せる。サブディレクトリ可)
├── environments.md       # 開発環境・開発ツールの基本設計(実コマンドはここが正)
└── logging.md            # ログ戦略、ログ仕様
```

`system.md` から切り出すのは、**テスト戦略が、それだけを対象にする作業指示の
対象になったとき**である — テスト戦略を `testing.md` へ。残りはその場に
置く。**引き金はサイズではない**(CLAUDE.md §7)。
(かつては UI 設計を `ui.md` へ切り出せたが、UI/UX の中身は `docs/ux/` へ移った —
`.claude/directions/ux.md`。`ui.md` を持つプロジェクトの移し方は
`.claude/migrations/2026-08-28-docs-ux.md`。)
**3つの節は決して `system.md` を離れられない**: モジュール分割定義、要件カバレッジ表、
分割の根拠 — スクリプトがそのパスを literal で解決しているためである
(`check-relations.py` / `callgraph-check.py` の `DESIGN_SYSTEM`、および `check-ssot.py` の
CS19)。**動かすと、機械検査は所見ではなく誤報になる。** 他の切り方を選ぶ前に
`grep -rn "02-design/<file>" .claude/scripts/` を走らせ、当たったものはすべて動かせないものとして
扱うこと。
何が移っても ID は `DSN-<area>-nn` の名前を保つので、
03 の `design:` 参照はファイル境界を越えてそのまま解決する — 張り直しが要るのは `source:` と、
パスを名指している本文である。

各設計判断に `DSN-<area>-nn` の ID を与える。**すべての設計判断は、その理由と、却下した代替案を
述べる**(理由の無い設計判断は、誰にも変えられない負債になる)。制約によって選択肢が1つしか
なかったときは「代替案なし: <理由>」が正当な値である — 欄を埋めるために偽の代替案を書くのは、
空の一覧を避けるために所見をこしらえるのと同じ欠陥である(CLAUDE.md §3)。

**`architecture.md` の「設計判断」と `system.md` の「分割の根拠」は決して空にならない** —
`CS19` が一括検査(`check-ssot.py docs`)でそれを強制する。そして
**どちらかのファイルに触れた者は、そこに既に在る判断を読み直し、1つずつ 継続/更新/削除 の印を付ける**
(`/build` §2 は自分のクロージャの中で、`/verify-docs` の C 検査はリポジトリ全体で —
`.claude/directions/delegation.md` §3.1 がその規則を所有する)。
「判断なし: <理由>」は正当な答えである。**空白の節は正当ではない** — それを
「判断が無かった」と区別するものが何も無いからである。
**この層は「なぜこの構造なのか」に答える場所である**: 03 はどう実現したかを述べ、
ここはなぜその構造がそれを許すのかを述べる。

## system.md

### モジュール分割定義(必須の表)

| モジュールID | 責務 | 対応要件 | 依存 | 詳細設計 | relations の接頭辞 |
|---|---|---|---|---|---|
| `MOD-auth` | 認証とセッション管理 | FR-auth-01..05 | MOD-db | あり(`auth.md`) | `MODULE-auth-*` |

- **大きすぎるモジュールは 03 を膨らませる。** 1つのモジュールが 03-impl で 15 本の relations を
  超えるなら、**モジュールの切り方そのもの**を考え直す(`relations-query.py` がこの本数を数える)。
  **これは「設計書を分けろ」ではない** — 部品の分け方そのものの見直しであり、
  下の「モジュールの詳細を切り出すか」の節とは別の話である。

- 依存の列は**非巡回**でなければならず、relations が宣言するモジュール間の辺をすべて覆わねば
  ならない — どちらかを破った状態は `check-relations.py` と `/verify-impl` が落とす。

### モジュールの詳細を切り出すか — 判断であって、しきい値ではない ★

1つのモジュールの詳細は、`02-design/<module>.md` へ切り出してよい(`source: system.md`)。
**切る引き金となる数字は無い。** バイト数の上限も、relations の本数のしきい値も、この判断には
使わない(2026-08-22 の人間の裁定。**絶対的な基準は無い**)。

**判断するのは人間だけではない。AI も検討する。** そのモジュールをクロージャに含むタスクの中で、
`/build` が詳細を書き足したときに一度考える — 気づいた人間が言うのを待たない。

見るのは2つである:

1. **切る線がモジュールの境界と一致しているか。** モジュールの途中で切らない。
   一致しないなら、それは分割ではなく**モジュールの切り方の見直し**の話である
   (モジュール分割定義の表の直後の行)。
2. **切ると並走できるようになるか。** クロージャは**パスの集合**なので、2つの作業指示が
   `system.md` を共有しているかぎり非交差は証明できず、直列にしか流せない
   (`orchestration.md` §3.4)。**切ることで初めて同時に流せるようになるなら、切る理由が在る。**

**迷ったら、いま並走させたい仕事が実際に在るかで決める** — 無いなら切らない。
切ることには費用が在り(`source:` と本文のパス参照の張り直し、索引の追随)、
その費用は並走で取り返すものだからである。
**切ったなら、切った理由を切り出した先のファイルの冒頭に1行残す**(`source: system.md` の隣。
次に見る者が、線を引き直してよいかを判断できるようにするため)。
**「分割の根拠」の節には書かない** — あそこは**モジュールの切り方**の根拠(`DSN-<area>-nn` を持つ
設計判断)であって、ファイルの切り方の根拠ではない。同じ節に2つを混ぜると、後から読む者は
その1行がどちらの話かを区別できない。

### ★ 要件カバレッジ — 条項単位で、`充足` 欄つき(この規則はこのファイルが所有する)

カバレッジ表の鍵は**01 の受け入れ基準 ID**(`FR-<domain>-nn-#`)であって、要件ではない。
要件を鍵にすると、3つの条項のうち1つを実現した設計と、3つとも実現した設計が**文面上まったく
同じ**になり、部分的な充足が見ることも検査することもできなくなる。
非機能要件は条項に分けないので、要件1つにつき1行のままである。

| 列 | 規則 |
|---|---|
| `充足` | **決して空欄にしない。** `FR-*` / `NFR-*` の行は**ちょうど4値**: `完全` / `部分(P-nnn)` / `適用外(理由)` / `-`。**`SR-*` の行は2値**: `満たす` / `破れている(課題票 ID)` — 交渉不可能な制約に「一部だけ」は無いので2値であり、**`破れている` が1件でも在れば完了定義を満たさない**(`CLAUDE.md` §3) |
| `部分(P-nnn)` | **棚上げの ID が必須である。** その項目が実在し、`関連` にこの条項 ID を名指し、「どうなったら解消が必要か」が空でないこと |
| `適用外(理由)` | その要件がここに**適用されない**ときだけ。`根拠` 欄が、そう述べている上流の ID を引く(`SR-*` / `decisions/` の項目 / 「やらないこと」)。**先送りは 適用外 ではない** — 「次期にやる」は `部分(P-nnn)` である。先送りをここに書くと、02 が 01 の要求から黙って自分を免除することになる(原則3) |
| `-` | その行は**主担当のモジュールではない**(`根拠` が主担当の行を指す)。**`SR-*` の行はこの値を取らない** — 2値のどちらかを必ず書く。SR の行では、モジュールの列はその前提が制約するモジュールを名乗る(システム全体を縛るなら `-`)— 「主担当」は 充足 についてだけの話であって、この列の話ではない |
| `根拠` | `完全` は DSN-ID を引くか、`-(設計判断を要さない)` と書き下す — **裸の `-` は書かない**(充足の `-` と衝突する)。`部分` は何が実現されていないかを述べる。`満たす` は**その前提を実現している設計判断(DSN-ID)か環境の記述**を引く — **`SR-nn` 自身を引いてはならない**(自分を根拠に引く行は「その制約が存在する」以上のことを何も言わない)。`破れている` は課題票の ID を引く |
| `割り当てモジュール`(非機能要件の行) | **1つのモジュールだけで破れるか?** で決める — 03 がテスト対応表の置き場を決めるのと同じ判定基準である(`03-impl.md`「tests/」)。破れるならそのモジュールを書く。破れないなら `-(システム横断)` と書き、`根拠` に「試験は e2e が担当」と述べる。**`-(システム横断)` の行がその要件の主担当の1行であり**、`充足` はその行に書く |

**1つの条項の主担当モジュールはちょうど1つ**であり、`充足` は**その行にだけ**書く。
他の行は `-` を持つ。条項が満たされているかどうか**そのもの**が主担当行の値である —
集約の規則は存在しない。「このモジュールの分担はどれだけ完全か」を一貫して判定することが
できないからである。これはテスト戦略が契約に対して既に使っている仕掛けと同じものである
(1契約につき主担当モジュールがちょうど1つ)。同じ言い回しで揃えること。
**主担当行が0行または2行以上なのは所見である。**

**行き場の無い条項**も、**対応要件の無いモジュール**も、どちらも所見である。

**何が検査され、何が指針にすぎないか**(**検査されていない規則が最初に壊れる** —
delegation.md §3.1 の仕掛けを、ここに当てたもの):

| 規則 | 検査主体 |
|---|---|
| 01 の条項に、02 カバレッジ行と 03 テスト行がある | AI: 条項を動かしたタスクでは `/build` §5(タスク内整合確認の一部)、検証の周では `/verify-docs` A2(カバレッジ)と `/verify-tests`(テスト表)。**専用の機械検査は無い** |
| 充足が語彙どおりで空欄なし(`FR`/`NFR` は4値、`SR` は2値)/ **`破れている` が0件** / 主担当行がちょうど1行 / `部分(P-nnn)` の実在と解消条件 / `適用外` の上流根拠 | AI: `/verify-docs` check A2(各違反は高)。**機械検査は無い** — 崩れは次の `/verify-docs` まで見えない(`分割可否` はこの表の語彙ではないが、**その判定の当否は A2 が読む** — 値と記載の有無は `01-requirements.md` が所有し `check-ssot.py` CS24 が見る。所見の行き先は `origin_layer: 01` の課題票だけである)|
| `根拠` 列の書き方(`完全`→DSN 引用、裸の `-` 禁止)/ SR 行の規約 | 指針。執行者は読み手(原則11) |

### テスト戦略

**3つの水準すべて**(unit / integration / E2E)に方針を書く。使わない水準は
「適用外(理由)」と印を付ける。

- 水準ごとに: 道具立て / 実行環境 / データ / いつ走るか。
- **結合テストの対象**: モジュール間の**すべての契約**に、それを保持する主担当モジュールを
  ちょうど1つ割り当てる(**主担当の無い契約は所見である**)。
- **E2E シナリオ一覧**(`E2E-nn`): 01 の `UC-nn` から導く。すべての UC は覆われているか、
  「適用外(理由)」として並んでいるかのどちらかである。
  **上流の UC を持たない E2E シナリオを発明してはならない。**
  **退役したシナリオを行ごと消してはならない** — `種別` の列に `delete` と書いて行を残す
  (01 の条項と同じ規則である。ID を振り直すと、03 の「廃止(…)」の行が上流を失う)。
- **全体で確かめる条項の選定**(`対象条項 ID` の列): 次のどれかに当たる条項は、
  **必ずどれかの E2E シナリオが持つ** — ① 2つ以上のモジュールにまたがる、
  ② 外部システムとの境界で起きる(停止・遅延・失敗を含む)、
  ③ 失敗が利用者に見えて重大である(認可の失敗、取り違え、消失)。
  **すべての条項を E2E に載せるのではない**: 条項ごとの網羅は
  `03-impl/tests/<module-slug>.md` が持ち、ここが持つのは**統合の境界でしか確かめられないもの**
  だけである。当たらないシナリオの列は `-` である。
- **`E2E-nn` は `system.md`(切り出し後は `testing.md`)にしか存在しない** —
  02 の他のどのファイルにも定義も言及も置かない(`check-ssot.py` CS22 が強制する)。
  02 の中では、e2e の鮮度スタンプの失効判定はその2ファイルと `environments.md`(実行コマンドの
  置き場)を読む — 依存集合の全体は `stamps.py deps verify-tests:e2e` であって、この一文では
  ない(inspection-16 D3)。**他所に書かれた `E2E-nn` は黙って網から外れる。**
- **`testing.md` へ切り出したなら、`flow-config.local.json` にそう宣言する** —
  `"e2e_scripts_in": "testing"`。宣言すると `system.md` が e2e / qa の失効判定から外れ、
  モジュール分割の散文を直しただけで E2E suite 全件と探索的ブラウザQAが失効する過大近似が
  消える(`flows.md` §2。inspection-20 V-4)。**宣言は「切り出し済みである」という主張なので、
  `system.md` に `E2E-nn` が1つでも残っていたら `check-ssot.py` CS23 が違反にする** —
  偽の宣言は、台本の在るファイルを黙って網の外へ出すからである。
  **切り出していないなら宣言しない**(未宣言は安全側の `"system"`。`testing.md` を作る前に
  宣言しても、`stamps.py` も CS23 も宣言ごと無視する)。

### UI 設計 — 中身の正は `docs/ux/` である

**この節が持つのは UI の有無の宣言だけである。** UI が無いなら「UIなし(理由)」と書く
(qa 試験区分を外す宣言の上流でもある — `flows.md` §2)。UI が在るなら `docs/ux/` を指す
1行だけを書く — 画面一覧(`SCR-nn` の台帳)・画面遷移・各画面の項目と状態・デザインの基調は
すべて `docs/ux/` が持つ(`.claude/directions/ux.md`)。**02 に画面の記述を書き足すことは、
必ずずれる重複である。**
`policy.md` と `flows.md` の初版は、02 を書く作業指示が一緒に作る(`ux.md`「場面1」)。

**約束を担う文面は 01 のものである** — どの文が受け入れ基準かの試験
(この文が無かったら、満たされない要件が在るか?)は `ux.md`「01(要件)との紐付け」が
所有する。E2E の台本(`E2E-nn`)は従来どおりこの層(テスト戦略)のものである。

## relations.md — 想定機能連携一覧 ★

`03-impl/relations/` の相方であり、**設計が想定する連携**である。ID は
`PLAN-<feature-slug>`(スラグは実装側の `MODULE-<feature-slug>` と一致させる)。
語彙は `.claude/directions/relations.md` とまったく共有する
(`kind` / `sync` / 呼び出し元 / 呼び出す先 / 契約)。

| PLAN-ID | モジュール | kind | sync | 呼び出し元 | 呼び出す先 | 契約 | 対応要件 | 概要 |
|---|---|---|---|---|---|---|---|---|
| `PLAN-auth-login` | MOD-auth | rest-api | sync | USER-enduser, PLAN-front-login-form | PLAN-auth-session-create, EXTERNAL-idp | CTR-api-login | FR-auth-01 | 資格情報を検証しトークンを発行 |

- 実装の前は、**これが唯一の連携情報である**。実装の後は、`03-impl/relations/` が事実であり、
  こちらが意図である。
- 雛形の `PLAN` ごとの詳細ブロック(「連携の詳細(設計上の期待)」)は**任意である —
  正は表のほうである**(`/verify-impl` の検査 E は表しか読まない)。
  1行では期待を担えないときにブロックを書く。
- まだ実装が無い `PLAN-*` は、雛形の「未実装として認識しているもの」節に、追跡先
  (`docs/issues/NNN` かタスク)つきで置く — `/verify-impl` の検査 E がそれを読んで、
  「設計済み・未実装」と「実装漏れ」を区別する。
- **02 ⇄ 03 の差こそが、抜けと見落としを検出する手段である**
  (`/verify-impl` の検査 E。詳細は `.claude/directions/relations.md` §7)。
- 覆うべきもの: 要件に関係するエントリポイントである関数と、モジュール境界を越える呼び出し。
  内部の private なヘルパは書かない(03 の粒度に合わせる)。

## contracts/

スキーマと API の定義。ID は `CTR-<name>` であり、**同じ ID を `03-impl/contracts/` でも使う**
(ID が同一であることが、02⇄03 の契約検査を機械的にしている)。

### ★ REST API の契約は OpenAPI 3.1 で書く

**API を表や散文に書き直してはならない。** 理由:

- **機械的に検査できる。** 02 と 03 のあいだのパス・メソッド・ステータスコードの差が自動で出て、
  コールグラフのエントリポイントと突き合わせられる(`check-contracts.py`)。
- **言い回しのぶれが消える。** 「必須」と "required" と「〇」が混ざらなくなる。
- **既存の資産につながる。** コード生成・モックサーバ・API Gateway への取り込みがそのまま動く。

書き方は2通りある。どちらかを frontmatter の `openapi:` に書く:

| 値 | 意味 |
|---|---|
| `inline` | 文書内の ` ```yaml openapi ` ブロックが契約の本体である |
| `<path>` | リポジトリ内の既存の OpenAPI ファイルが本体である。**02 と 03 が同じファイルを指してよい** |

規則:

- **エラー応答の無い OpenAPI は未完成である。** 正常系だけの `responses` は所見である。
- 振る舞いがそれに依存するなら、`x-idempotent` / `x-ordering` / `x-concurrency` を明示する。
  **書かないことは「依存しない」を意味する。**
- パスパラメータは OpenAPI の `{id}` 記法を使う。それがコールグラフの `path_key` と揃うものである。
- **OpenAPI で表現できることを散文で重複させない。** 散文が担うのは OpenAPI で表現できないもの
  だけである: 設計判断と却下した代替案 / 順序性と冪等性の**理由** / 権限設計の根拠。
- 実装の断片を書かない。

### REST でない契約

データスキーマ、イベント、永続化(`kind: data-schema` / `event` / `storage`、
どれにも当てはまらないものに `other` — **この5値の語彙はこの節が所有する**。
`kind:` を持つ3本の雛形(`02-contract.md` / `02-contract-nonrest.md` / `03-contract.md`)は
手控えとして並べてよいが、値を増減するのはこの節である)は OpenAPI の守備範囲の外なので、従来どおり表で書く。
**型・必須かどうか・既定値・制約・エラーの場合は、それでも必須である。**
JSON Schema で表現できるものは `components/schemas` の形にしてよい。
**雛形は `.claude/templates/02-contract-nonrest.md`** である — REST 用の
`.claude/templates/02-contract.md` は本文が OpenAPI 専用で、この5項目を書く欄を持たない。

**2つ以上の機能が使うキューのメッセージ、イベント、共有テーブル/ファイル、その他の資源の形式は、
契約でなければならない。** この 02 の契約が意図された形式を所有し、その 03 の相方が実装された
形式を所有し、生産する側と消費する側の `MODULE-*` はすべて `contracts:` に同じ `CTR-*` を並べる。
**各モジュールの散文にスキーマを複製してはならない。** 資源名による結合と、機能1つのときの
免除は `callgraphs.md` §5.11 が所有する。

ファイルの分け方は任せる(REST API とデータスキーマを分ける、ドメインで分ける、…)。
サブディレクトリを作ってよい。

## environments.md

開発環境と道具立ての設計。**ここに書かれたコマンドの文字列が正であり**、
すべてのスキルがこの文字列をそのまま使う。**見出し構造を変えてはならない**
(スキルが見出しを名前で参照している)。

必須の節:

- **セットアップ手順**
- **lint・テストコマンド** — セットアップ / lint / 単体テストと結合テスト / E2E テスト / ビルドを、
  **正確な文字列**として、水準ごとに書き下す。既存のリポジトリでは、
  **実際に実行して確認した文字列**を書く。
- **コンテナ・実行環境** — Docker / compose の使い方、ポート、依存するサービス。
- **ブラウザQAの宛先 allowlist** — E2E と `/browser-qa` のブラウザが到達してよい宛先を
  **正確に**書く。**スキームとホスト/CIDR の両方を書く** — 突き合わせはスキームまで見るので、
  `http` だけを書くと WebSocket を使う画面のライブ表示に入れない
  (`.claude/directions/orchestration.md` §1.1.2 の表)。
  **床**は `localhost` / `127.0.0.1` / `[::1]`(**角括弧付きは宣言側の綴りである。
  強制側の `EXCLUDE` へそのまま貼らない** —
  綴りは `.claude/directions/orchestration.md` の「1.1.2 ブラウザQAの口は MCP で足す」 が正)。そこに、**このプロジェクトのブラウザQAが到達
  しなければならない宛先だけ**を足す(docker network の CIDR と compose のサービス名、
  同じ構内や VPN の私設アドレスなど)。**天井は「公開インターネットへ出る宛先を1つも書かない」
  である** — 広い書き方は公開の住所を巻き込むので(`172.*` は公開の `172.217.*` を巻き込む)、
  範囲を正確に書いて巻き込んでいないことを示す。**床を超えて足した行には、なぜその宛先へ
  到達する必要があるのかを1行添える** — 添えられないなら、それは足してよい宛先ではない。
  **その値についてはここが唯一の正である。宣言は、強制する側が数え上げられる形で書く。**
  それを強制する機構(chrome-devtools MCP の `--allowedUrlPattern`、Chrome の
  `--host-resolver-rules`、Playwright の `launchOptions.args`)と、そこに書ける範囲の形は
  `.claude/directions/orchestration.md` の「1.1.2 ブラウザQAの口は MCP で足す」が正である。
  (要旨: 強制側は CIDR を解さないので、境界の判る範囲で宣言する)
  **外部へ出る宛先を書いてはならない** — 委任の既定が「外部ネットワークに出ない」だからである
  (`delegation.md` DS-01)。UI を持たないプロジェクトは一行「適用外(UI 無し)」。
  この節は**ブラウザ検証の実行条件**も所有する — アプリの起動コマンド、アプリの URL、
  E2E のシードとリセットのコマンド。`/browser-qa` が読むのはこの文書を含めて4つだけであり
  (`reading.md`)、ここに無ければそのレーンは立ち上げられないか、読む量の上限を破るかの
  どちらかになる。`03-impl/tests/e2e.md` の「テスト環境」と**同じ値を持つ行は逐語で一致させる**
  (起動・シード・リセットの3つ。どちらの表も相手に無い行を持ってよい)。
- **CI** — 何がいつ走るか。
- **未定**の項目を消してはならない — 「未定(いつ決めるか)」と書く。

**コールグラフ抽出設定** — 節そのものは残す。使わないプロジェクトは「適用外(理由)」を1行書く。
このプロジェクトが何を絞ったか、想定される Tier は何かを記録する。ローカルの配列は和として
併合されるので、`internal_roots` を `callgraph-config.local.json` で絞ることはできない —
当面は、ローカルの `excludes` に兄弟パッケージ等を並べて絞る(足すと縮むだけ — `tools-readme.md`
§6 と同じ形)。恒久的な直し方はスクリプトの変更であり、それは汎用的な直しなので
`/kit-improve` の2つの縛り(CLAUDE.md §3)を満たせばいつでも直してよい。
**見出しでこの節を読むものは他に無い。** 絞ったことが記録された決定として残るために在る。
