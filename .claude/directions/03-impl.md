# 03-impl/ — 現実装の仕様ドキュメント(実装層)

日本語で書く。

**この層は何か**: **実装の鏡像**である。このリポジトリのコード・インフラ定義・開発ツールが
**いま実際に何をしているか**を記述する。
**願望・計画・意図したが実装されていないものを、ここに書いてはならない。**

**どう作られるか**: **コードから、下流から上流へ向かって生成する**(上から書き下ろさない)。
`/relations` か `/retrofit` がそれを行う。上流が想定する連携は `02-design/relations.md` に属し、
**比較できるようにするためにこそ**両者は分けてある。

**不変則**: コード ⇄ 03-impl は正確に一致する。食い違いを見つけたとき、
**黙ってどちらかに寄せてはならない。** これが CLAUDE.md 原則2 であり、
**その詳細はこのファイルが所有する**。詳細とは、効いている語が「黙って」であって、
**「食い違いのたびに問え」ではない**ということである。振り分ける:

| 差異の種類 | 扱い |
|---|---|
| **事実の差異** — パス、シグネチャ、呼び出し先の有無、テストの実在 | **コードが正。直して報告に載せる**(**黙って寄せない = ここで果たされる**)。読めば決まるので問わない。直す場所 — `/build` 中: クロージャ内なら当該 SSOT 文書を直接、クロージャ外なら原則8の記録先の振り分け。フロー外: `/verify-impl` の自動修正、または `/relations --apply`(人間の明示要請) |
| **意図の差異** — 02 の期待と実装が違い、**どちらも正でありうる** | **自分で決めない。** 事実を両側書いて決定シートへ。矛盾なので問う基準を満たす(`.claude/directions/delegation.md` §1) |

実装のほうが正しいことが多いが、要件や設計のほうが正しいこともある —
**2行目が在るのはそのためであり、人間に届くのはその行だけである**(キューか質問シートを通って)。
`/verify-impl` §2 の表はこの振り分けを運用の形にしたものである。両者の歩調を合わせること。

境界の場合: **コードには在るが 02 の `PLAN-*` に無い呼び出し**は、03 にとっては事実の差異であり
(コードが勝つ。記録する)、**同時に** 02 に対する意図の差異でもある。
`/verify-impl` の検査 E が 02 側を拾う。タスクを伴わない `/relations --apply` では検査 E は
走らないので、**その run の報告で、欠けている `PLAN-*` を名指す** — 設計の違反が黙って
「記録された事実」になるのを防ぐためである。

### 原則2 の例外(ブートストラップ中に限る)

ブートストラップ(`/relations --apply --bootstrap` / `/retrofit`)の最中は、
**既存の文書**とコードの矛盾を、コードを正として書き起こしてよい —
**ただし矛盾するすべての箇所を、報告に全件列挙することを条件とする。**

**なぜこの例外が在るか**: ブートストラップは 00〜03 の全体を1回の下降で生成するので、
食い違いのたびに止まると、**どちらの側もまだ検証されていないうちに**何百もの問いを人間へ
出すことになる。
**なぜ列挙が代償であって、儀礼ではないか**: 列挙が無ければ、これは規則が禁じている
「黙って寄せる」**そのもの**である。「コードを正として採り、それが含意する箇所はこれで全部である」と
「黙って片側を選んだ」を分けているのは、その一覧だけである。
**空の一覧は主張である**(「矛盾は見つからなかった」)。**暗黙のまま省いてよい欄ではない。**

**ブートストラップの外では、原則2 に例外は無い** — ブートストラップ自身が書いたものも含めて
である(その時点からそれは文書であり、しかもまだ検証されていない)。

## ★ 実装がまだ無いとき(グリーンフィールド)— 鏡ではなく、これから作るものの記述

グリーンフィールドでは、`/build` の文書の段が 03 で鏡に映すものがまだ何も無い。
**そのとき 03 が担うのは、実装者が着手するために要るものだけであり、残りはコードを待つ。**
難しいからではなく、**それ以上を書くと情報が失われるから**である:

1. **定義により上書きされる。** `/build` §4 のタスク内整合確認が、03 の文書を
   **実際に作られたもの**に対して決着させ(`impl` / `callers` / `callees` / `contracts` /
   `tests` と本文)、`/verify-impl` がツール側の生成物をコードから作り直す。
   **実装前にコードの鏡として書いたものは、そこで置き換えられる。**
2. **03 にしか無い意図は、黙って消える。** 03 はコードから再生成されるので、
   他のどこにも生きていない意図は**作られたもので置き換えられ、突き合わせる相手が何も残らない**
   — 差異が検出不能になる。**意図は上流に属する**: アルゴリズムの要求は 01 の受け入れ基準へ、
   想定される連携は `02-design/relations.md` の `PLAN-*` へ、契約は `02-design/contracts/` へ。
   実装前の 03 は**そこから導いた、これから作るものの記述**であり、置き換えられてよい。原本が上流に生き残って
   いるからである。**02 を薄くして詳細を 03 に書くのが、いちばん高くつく**:
   02 ⇄ 03 の比較(`relations.md` §7、`/verify-impl` の検査 E)が、比べる相手の側を失う。

| 成果物 | 実装が無い時点で書くか |
|---|---|
| `relations/MODULE-*.md` | **書く。ただし実装者が要る分だけ**(節ごとの範囲は `.claude/directions/relations.md` §4.1)。**機械的上限: 1本 4,000 バイト** — 超えていたら削る(判断ベースの上限は破れ、数えられる上限は守られた、が実測。`wc -c` で検査可能)。**この上限は列の題のとおり「実装が無い時点」のもの** — 実装済みモジュールを §4 の整合確認が settle した後の本文には当たらない。**必須の連携先の小節(`relations.md` §4 の「連携先と連携内容」)を削ってまで収めない — 衝突したら必須の小節が勝ち、そのぶんの超過は違反ではない** ★。**この免除は記録に依存しない** — 必須の内容が入りきらないという事実だけが根拠であり、消えうる記録(`残務` の行)を条件にしない。併せて、収まらないことは 02 のモジュール分割を見直す信号なので、出口は `conventions.md` §1 と同じ**「02 の分割を見直す提案」**である — それを報告に出し、`residual.md` の `残務` に1行残し、`doc-health.py --rotate` を打つ(`issues-pendings.md` §1 の4 と §2.1 (2)。**課題票にはしない** — 振る舞いの誤りでも完了定義の阻害でもない) |
| `features.md` | **書く**(境界の定義。人間が合意する唯一の場所であり、コードからは決まらない) |
| `tests/<module-slug>.md` `tests/e2e.md` | **行だけ書く**(01 の受け入れ基準と 02 の `E2E-nn` から。状態は全行 `未検証(テスト未実装)`)。手順・フィクスチャ・期待値は実装後。**実装前の `strategy.md` は「フィクスチャ・ヘルパの流儀」「命名と配置の規約」「カバレッジの扱い」の節を持てない**(実装後の内容。`/build` §4 が実物から足す) |
| `contracts/` | **ID とスタブだけ**(`CTR-*` を 02 と同一IDで置き、02 の OpenAPI を正として指す)。**実装前の OpenAPI をコピーしない**(二重管理になる) |
| `environments/` `infra/` | **書かない**(まだ存在しない仕組みと構成)。実コマンドの正は `02-design/environments.md` |
| `callgraphs/` `feature-graph.md` | **絶対に書かない**。ツールだけが書く生成物(再生成は `/verify-impl` と `/relations` — 誰が書くかの正は `principles.md` §1) |
| `index.md` | **この時点では書かない**(書く対象がまだ無い)。実装後の扱いは下の Files が正 |

**そこで浮いた労力は 00〜02 へ回す** — どんな道具にも決して再生成できない事実が在るのは、
そちらだからである:

| 層 | 実装後には作り直せないもの |
|---|---|
| 00 | 目的・**やらないこと**・受け入れシナリオ `AC-*`・決定と委任 `D0-*` |
| 01 | EARS の受け入れ基準(**境界値と異常系を含む**)・`UC-*`・`SR-*` |
| 02 | モジュール分割定義 `MOD-*`・契約 OpenAPI `CTR-*`・**`PLAN-*`(想定連携)**・E2E シナリオ一覧・`environments.md` の実コマンド |

**00〜02 の穴はコードから検出できないので本番まで生き延びる。薄い 03 は同じタスクの中で道具が
埋める。** その非対称性こそが、労力を上流へ回す理由のすべてである。

明示しておく価値のある帰結が2つある:

- `impl:` は、これから作る**つもりの**パスとシンボルを持つ。ディスク上にはまだ存在せず、
  それが `building` の過渡である(`flows.md` §3)— verify 系フローは、構築が出口を出るまで
  そのクロージャを除外する。**欄が完成して見えるように、それらしいシンボル名を発明しては
  ならない。** `/build` §4 が、作られた結果に対してそれを訂正する。
- **02 の `PLAN-*` に無い連携を、自分が 03 に書こうとしているなら、起点は 02 である**(原則3)。
  **同じ下降の中で、先に `PLAN-*` を足す。**

│   ├── strategy.md       # レベル別の実行方法・絞り込み実行・データ管理・流儀
│   ├── <module-slug>.md  # モジュールごとの 受け入れ基準⇄テスト対応表
│   └── e2e.md            # E2Eシナリオ⇄テスト対応表
├── environments/         # 開発環境の制御・ツールの実装仕様(docker の使い方など「仕組み」)

    ├── dev/
    └── prod/

これらのファイルを通じて、意味の最低線は `CLAUDE.md` §1 が所有する:
外から観測できるエラーと境界、境界をまたぐ契約と共有形式、状態と整合の不変条件、
決定の根拠と見直す条件、検証と切り戻しの条件は、**SSOT から見つけられなければならない。**
「(コードを参照)」を使ってよいのは、残りの導ける機構に対してだけであり、
**その最低線を免除することは決してない。**

`environments/` と `infra/` のどちらに置くか: **仕組みは environments/、具体的な設定値は infra/**。
例えば「compose がどうサービスを起動するか」→ environments/、
「dev 環境の VPC / サブネット / インスタンス種別」→ infra/dev/。

## callgraphs/ ★

**ここに書くのは道具だけである。AI は1文字も書かない。** 版も検証済み記録も持たない純粋な
導出物であり、**実装が変わらない限り1バイトも変わらない**。鮮度は保存せず、
`build-callgraphs.py --out <解決値> --check` で検査する
(出力先は常に SSOT である — `callgraphs.md` §3.1)。
**これは機能間連携仕様書ではない** — 関係だけを持つので、そのままでは決して仕様にならない。
唯一の正は `.claude/directions/callgraphs.md` である。ここに書き写さないこと(所有の重複を避ける)。

## features.md / feature-graph.md ★

**機能表 `features.md` は「何を1つの機能と数えるか」だけを述べる1枚の表**であり、
relations と 1:1 である(行の ID が、文字どおりファイル名 `relations/<ID>.md` である)。
**AI が起草し、人間が合意する** — この層で境界が決まる唯一の場所である。

`feature-graph.md` は**生成物**であり、その表とコールグラフから機械的に導かれる。
その不変則は「**実装か機能表が変わらない限り1バイトも変わらない**」であり、callgraphs/ とは
異なる(実装が同一でも機能表を変えれば変わる。それが callgraphs/ の中に住んでいない理由である)。

どちらも自分の版も検証済み記録も持たない。`features.md` は relations の層とともに
`03-impl/index.md` が代表する(原則6)。`feature-graph.md` は生成物であり、callgraphs/ と同じく
検証の対象の外に在る。唯一の正は `.claude/directions/features.md` である。
ここに書き写さないこと(所有の重複を避ける)。

## relations/ ★

**この層でいちばん重要なもの。** 粒度・命名・frontmatter・本文の構造・機械検査は、
`.claude/directions/relations.md` だけが所有する。ここに書き写さないこと(所有の重複を避ける)。

## contracts/

**実際に実装されている**契約(API、データ形式、イベント、永続化スキーマ)。

- **内容は実装と正確に一致する。** 実際の検証、実際の既定値、実際のエラー応答を書く。
- ID は `CTR-<name>` であり、**`02-design/contracts/` のものと同一である**
  (ID を共有する理由と粒度の規則は `relations.md` §5 が所有する)。
- 差を見つけたとき、「実装が正しい」と決めてかからない — 報告する
  (設計が正しく実装が不具合であることもある。原則2)。

### ★ REST API の契約は OpenAPI 3.1 で書く

書式の規則は `.claude/directions/02-design.md` の contracts の節とまったく同じである。
03 側に固有なのは次の点である:

- **リポジトリに OpenAPI のファイルが既に在るなら、`openapi: <path>` でそれを指す。**
  複製して2つを保守してはならない(必ずずれる)。生成されたファイルでよい
  (FastAPI の `/openapi.json` のダンプなど)。
- **実装シンボルを `x-impl` に書く**(`callgraphs` のシンボル ID と同じ記法。区切りは `::`)。
  それによって `check-contracts.py` が「コールグラフのエントリポイント ⇄ 契約」を機械的に
  突き合わせられる — 実装されているのに契約に無い API と、契約に在るのに実装が無い API が
  表に出る。
- 本文の表が持つのは、**検証がどこで行われるかのような、コードの位置に紐づいた事実**だけである。
  **OpenAPI が担えるものを重複させてはならない。**

### ★ 非 REST の契約が HTTP の経路を持つなら `endpoints:` で名指す

WebSocket の升格点や Server-Sent Events は、**HTTP の経路として登録されているのに、契約は
正しく非 REST の側に在る**(`kind: event` など)。この経路を OpenAPI へ足すのは誤りである。

だが `check-contracts.py` の CT4 は、コードの経路を突き合わせる先として OpenAPI しか
持っていなかったので、**そういう経路は「契約が無い」と重大度「高」で出続けた** —
OpenAPI へ足せば規範に反し、足さなければ所見が消えない、どちらへも行けない所見である
(実測 2026-09-01)。**直しようの無い所見は、やがて一覧ごと読まれなくなる。**

そこで、非 REST の契約は自分が覆う経路を frontmatter で名指す:

```yaml
kind: event
endpoints: [GET /ws]
```

- **1行スカラーで書く**(frontmatter の解析器は1行しか読まない)。区切りは**コンマ `,`**
  (全角の読点 `、` も受ける)。角括弧は在っても無くてもよい。
- 項目は `METHOD /path`。**メソッドを省くとそのパスのどのメソッドにも当たる**
  (`endpoints: [/healthz]`)。
- **前方一致はしない。** `/ws` は `/wsx` を覆わない。
- `kind: rest-api` の契約には書かない — そちらの経路は OpenAPI の `paths` が所有する。

| ファイル | 中身 | 雛形 |
|---|---|---|
| `strategy.md` | レベル別の実行方法、**絞り込んで実行する方法**、データの準備と後始末、フィクスチャの流儀、命名と配置、不安定テスト、カバレッジ | `.claude/templates/03-tests-strategy.md` |
| `<module-slug>.md` | **02 の分割定義の1モジュールに1ファイル**。受け入れ基準⇄テスト、契約の結合テスト、`MODULE-*`⇄テスト | `.claude/templates/03-tests-module.md` |
| `e2e.md` | E2Eシナリオ⇄テスト、テスト環境(通過する機能は写さず `relations-query.py --downstream` でその場導出 — 雛形が正) | `.claude/templates/03-tests-e2e.md` |
| `index.md` | **全体が生成物**(`build-index.py`)。**規範上の手保守部分は無い** | (なし) |

規則:

- **テストはここに書くのであって、relations には書かない。** `relations/MODULE-*.md` が持って
  よいのは `tests:` の欄(参照)だけであり、**内容・手順・フィクスチャ・期待値の正はこちら側である**
  (`.claude/directions/features.md` §0.1、`relations.md` §4)。
- コマンドは `02-design/environments.md` の**正確な文字列**と一致させる。
- **`tests/` 配下のすべてのファイルは `id` に `tests-` の接頭辞を持つ**:
  `tests-<module-slug>` / `tests-e2e` / `tests-strategy`。付けないと `tests/cli.md` と
  `contracts/cli.md` が1つの層の中で `id: cli` として衝突し、`id` は `docs/` 全体で一意である
  (`conventions.md` §1 — 契約が 02 と 03 で1つの `id` を共有するのが意図的な例外であり、
  テスト仕様はそれではない)。接頭辞は、いま衝突しているかどうかにかかわらず
  **ディレクトリの全ファイル**に付ける: たまたま衝突する名前にだけ当てた規則は、
  1つのディレクトリを2つの書式で書かれた状態にする。
- **状態の列に許される値は、この節が定める一覧のどれかである**: `実装済み` /
  `未検証(テスト未実装)` / `テスト対象外(理由)`、および次の項が定める `廃止(<理由>)`。
  **決して空欄にしない。** `build-index.py` が `tests/index.md` の進捗の数字のために数えるのは
  前の3語だけなので(退役した行を進捗に入れないため。次の項)、独自の言い回しを発明すると
  集計が壊れる。
  (「テスト対象外」= その行のテストを作る予定が無い。02 の網羅表は「その要件が適用されない」に
  「適用外」という別の語を使う — **この2つが同じ語になることは、設計上決して無い。**)
- **上流の条項やシナリオが退役した行は、`廃止` の値を取る。それだけである:**
  `廃止(<移設先 or 廃止の根拠>)`。上流は退役した条項を
  `| FR-<domain>-nn-# | delete | … |` の行として保ち(条項 ID は不動である —
  `01-requirements.md`)、退役したシナリオを `| E2E-nn | delete | … |` として保つので、
  こちら側も行を保つ。セルは**`廃止` の語で始まり**、条項がどこへ行ったか
  (`廃止(FR-agent-07 受け入れ基準1c へ移設)`)か、なぜ無くなったか
  (`廃止(D0-core-32 で不要と決めた)`)を名指す。`build-index.py` は上の3語しか数えないので、
  退役した行は**意図的に進捗の数字の外に在る** — もう存在しない要件は、実装済みでも未検証でも
  ない。**それに `テスト対象外(理由)` を書いてはならない**: その値は「この行のテストは作らない」を
  意味しており、退役した行で埋めると、背後に要件がまったく無い行でその値を膨らませることになる。
- 01 の**受け入れ基準の条項**(`FR-<domain>-nn-#`。主担当モジュールがこのモジュールであるもの —
  それを決めるのは 02 の網羅表である)ごとに行を作り、02 のすべての `E2E-nn` に行を作る。
  **一覧に無いシナリオのテストを決して作らない。**
- **すべての `NFR-<cat>-nn` も、ちょうど1つの「NFR ⇄ テスト対応」の表に行を持つ**:
  モジュール固有の NFR はそのモジュールの `tests/<module-slug>.md` に、
  **システムを跨ぐ NFR は `e2e.md`** に(分け方: 1つのモジュールだけで破れるか?)。
  **1つの NFR につき居場所は1つ** — `/verify-tests` はこれらの表の和を突き合わせるので、
  重複した行は何も強めず、欠けた行は違反である。行は、その NFR をどのテストが担うかと、
  3語の状態を述べる。**測定値をここに書くことは決して無い**
  (測るのは `strategy.md` のカバレッジの扱いのコマンド、またはテストそのもの)。
- `<module-slug>.md` の `MODULE-*` ⇄ テストの表は、`relations/` の `tests:` の欄と一致していな
  ければならない。一覧は
  `python3 .claude/scripts/relations-query.py --list --module MOD-<slug>` で取る。
- **「未検証(テスト未実装)」の行は重大度「高」で報告されるが、PASS を止めない唯一の分類である**
  (規則は `/verify-tests` が所有する)。この層がそれに対して負うもの:
  そういう行を全件、そのファイルの「未検証(テスト未実装)の全件」節に集め、
  **未検証でなくなる条件**を添える — 「解消の条件」であって、「いつやるか」ではない。
  予定は計画であり、SSOT はいまの姿だけを記述する(CLAUDE.md §1)。雛形はかつて「閉じる予定」を
  求めており、それが両者を正面から衝突させ、所見として報告された。
  **黙って残してはならない。**
- 用語の注意: ここでいう「未検証」は**テストが実装されていない**ことを意味しており、
  文書が未検証である(検証済み記録を持たない)のとは別の概念である。両方が現れる場所では、
  区別するために「未検証(テスト未実装)」と書く。

## environments/

開発環境をどう**制御しているか**: Docker / compose の使い方、Makefile とスクリプトが何をするか、
依存サービスの起動順、シードの仕組み、ローカルで認証をどう迂回するか、など。
**実在するファイルを引くこと**: パスは必須である。`:line` を足すのは、その行そのものを引いて
いるときだけにし、**行番号よりも安定した目印**(サービス名、make のターゲット、節)を選ぶ —
行番号は編集のたびに腐り、自己点検はファイルの実在しか確かめない。
(原則11 の `path:line` の規則は**報告**のためのものであり、報告は一度しか読まれない。
そちらは変わらない。)

**開発環境を作るために在るものは機能ではないので、relations ではなくここに入る**
(その試験と除外の一覧は `.claude/directions/features.md` §0.1 が所有する — ここには書き写さない)。
**実行する正確なコマンドの正は `02-design/environments.md` である。**
ここは仕組みを記述する場所である。

## infra/

環境ごとの具体的な構成。`local/` `dev/` `prod/`(必要に応じて足す)。

- 図(Mermaid)、資源の一覧、ネットワーク、権限、秘密情報の在り処(**値は決して書かない**)、
  デプロイ手順、環境変数の一覧と既定値。
- IaC が在る場合は、必ずその定義ファイルへのパス参照を含める(IaC が正であり、こちらは索引である)。
- 雛形はさらに**4つの運用の節**を持つ(運用ランブック・バックアップ/リストアなど —
  `.claude/templates/03-infra.md`。`docs/README.md` が読み手にそれらを約束している)。
  **運用手順は運用上の事実であって計画ではない** — その層の判断こそが、
  それらがこの SSOT の文書に属する理由である。

## Frontmatter

`relations/` 以外の 03 の文書:

```yaml
---
id: tests
version: 1.0.0
updated: 2026-08-01
source:
  - docs/02-design/system.md
summary: <1行>
keywords: [テスト, E2E]
# verified: /verify-impl が層代表(index.md)に書く
---
```

`tests/<module-slug>.md` はさらに `scope: MOD-<slug>` を持つ — `build-index.py` が
`tests/index.md` の 対象 の列のためにそれを読む。この鍵が取る形はちょうど3つである:
`MOD-<slug>`、`全体`(`tests/strategy.md`)、`E2E`(`tests/e2e.md`)。雛形が示すとおりである。

`relations/MODULE-*.md` の frontmatter は独自のスキーマを使う
(`.claude/directions/relations.md` §3)。それらは `version` も `verified` も持たない。
**`03-impl/index.md` が層全体を代表して版と検証済み記録を持つ** —
relations の1本ずつに版を打つと、変更のたびに集合全体が無効になり、手順として成立しなくなる。
だから**層はまとめて検証される**。個々の relations の正しさは `check-relations.py` と、
コードとの突き合わせ(検査 B)が保証する。

**検証済み記録の検査において、クロージャの `MODULE-*` の行は `docs/03-impl/index.md` が代表する**
— 検証済み記録を読む検査(`/verify-docs` §0、`/verify-impl` §3)は、MODULE の行を層代表へ
解決するのであって、MODULE のファイル自身に検証済み記録を要求することは決してない。
**`index.md` がまだ層代表の frontmatter を持たないあいだ**(グリーンフィールド — 初回の `/build` §4 が
それを作る)、層代表の行に対する検証済み記録の要求は免除される(発行は `/verify-impl` §3)。

## 終える前の自己点検

**この一覧はコードが存在する場合に当てるものである** — `/relations`・`/retrofit`・`/verify-impl`
の一覧である。**実装より前に書かれた 03 に決して当ててはならない**
(`/build` の途中、グリーンフィールド): 同期すべきコールグラフも、欠けうるエントリポイントも
まだ存在しない。その時点で何を書くかは、上の「実装がまだ無いとき」の節である。

- `build-callgraphs.py --out <解決値> --check` は「最新」と言うか(コールグラフはコードと
  同期しているか)?
- `callgraph-check.py` に重大度「高」が残っていないか(FT / CG 検査)?
- `check-relations.py` は通るか(対称性、impl のパスの実在、ID の実在、重複なし)?
- 02 の分割定義のすべてのモジュールが、少なくとも1本の `MODULE-*` を持っているか?
- 各 `MODULE-*` の `module:` は分割定義に実在するか? 分割定義に無いモジュールの relations は
  無いか?
- `contracts/` のすべての `CTR-*` が `02-design/contracts/` にも在るか(片側だけなら所見)?
- `tests/` の表に空欄は無いか(すべての状態が `tests/` の節が許す値のどれかか — `廃止(…)` を
  含む)? 02 の分割定義のすべてのモジュールが `tests/<module-slug>.md` を持っているか?
- コードに在るすべてのエントリポイント(ルーティング、ハンドラ、イベント購読、CLI サブコマンド、
  cmd の分岐)が relations に現れているか? **1つでも欠けていれば 03 は未完成である。**
- `environments/` と `infra/` のパス参照は、実在するファイルを指しているか?
- **上の層に在る事実を写していないか?** 持ち主でない文書は、写さずに参照する(形と例外の正は `conventions.md` §4)。値そのものを本文に出したいなら機械の欄に入れる。
  **03 では持ち主がコードであることが多い** — コードを読めば分かる値は、散文に書かずに機械の欄へ入れる(原則2)。
