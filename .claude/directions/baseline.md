# 基本要件(BR-nn)— 誰も頼まなくても成果物が備えていなければならないもの

日本語で書く。
**このファイルが基本要件の唯一の正である。** 項目は ID で引用すること。
**項目の内容を他所に書き写してはならない** — 複製は、歩調を合わせる場所が2つになることである。

## 0. なぜ在るか

原則4 は「上流が持たないものを作らない」で始まる。その1文だけを読むと、
**述べられていない性質が、誰のものでもなくなる**:
**人間は要求に「最後の管理者を削除できないこと」と書かない。**
それは願望ではなく、**「アカウント管理機能」が既に意味しているもの**だからである。
**§2 が並べている性質のどれについても同じである。**
(ここに例を数え上げない — 数え上げれば、項目を足すたびにこの行が伸びる。§1 の7)

2026-08-19 の人間の指摘: 「sysdev および sysdev-multi で作られるシステムに、しょうもない考慮漏れが
多すぎる。あえて説明されるまでもなく考慮するようにして欲しい。」
**その抜けはすべてこの1種類だった** — 難しい判断を間違えたのではなく、
**どの層も所有するよう告げられていなかったために、どの層も所有していなかった性質**である。

**この一覧を1語で要約しない** ★。「安全性の一覧」と呼んだ日から、**攻撃者以外から守る項目が
一覧の外に見えるようになる** — 失ったものを戻せることは、誰の攻撃も受けずに失われる。
**この一覧を束ねているのは「何から守るか」ではなく、性質の種類のほうである**:
**人間が要求に書かないのに、その機能を作ると言った時点で含まれているもの。**
何から守るかは項目ごとに違い、**次に足す項目が何から守るかは、いま決まっていない。**
だから、この一覧が何の一覧かを他所で書くときも、守る相手を数え上げない(§5)。

**基本要件は、委任でも願望でもない。成果物が備えていなければならない性質であり、
それについての上流の沈黙は何の情報も持たない。** それを*どう*満たすか(値、文面、閾値、機構)は
依然として標準委任の判断であり、依然として開示行を負う(`delegation.md` §3)。
**満たすか*どうか*は、あなたが決めることではなく、決してシートの項目にならない** —
「入力検証を入れてよいですか」と問うことが、このファイルが置き換えた失敗そのものである。

## 1. どう縛るか

1. **適用はクロージャに対して判定する。** システム全体ではなく、そのタスクが触る範囲に
   §2 の適用条件が当たるかを見る。当たった項目を持ち込んだタスクが、その項目の持ち主である。
2. **該当したら、事実の在る層へ降ろす**(原則3)。**どこへ降ろすかは項目ごとに違い、
   §2 の「既定の落とし先」の欄が正である** — 契約に現れるものは 02 の契約、実現方法だけの
   ものは `MODULE-*.md` の「実装上の判断」、運用の手順は `03-impl/infra/` の表、というように。
   **落とし先の種類を、ここで数え上げない** ★ — 数え上げれば、それに収まらない項目を足すたびに
   この行が古くなる(実測: `BR-11` を足した回に「4つ目の落とし先」という特例をここへ書いた)。
   **どの項目にも掛かる規則は、次の1つだけである**:
   **外から観測できることは、既定の落とし先が何であれ、必ず 01 の受け入れ基準(EARS)にも書く。**
   そこへ書けば `/verify-docs` A2 が 02 のカバレッジ行を、`/verify-tests` がテスト表の実在を
   要求するので、**「書いたが検証されない基本要件」が構造的に作れなくなる** —
   **この連鎖が付くのは 01 だけである。** 01 の外(02 の契約、`MODULE-*.md`、`infra/` の表)に
   しか書かなかった基本要件は、誰も検証しない。
   **§2 の欄は「既定」であって網羅ではない** ★ — 欄が 01 を挙げていない項目でも、
   外から観測できる部分が在れば 01 にも書く。**この規則が欄に上乗せされる。**
3. **非該当は理由つきで書く。** 「該当なし」だけの行は未判定と区別できない(`CS19` と同じ理由)。
   **同じ理由が複数の項目に掛かるなら、共通理由として一度だけ書いてよい** ★ —
   `## 基本要件の点検` に `- R1: BR-03 / BR-06 — <理由>` の形の行を置き、各項目の理由の欄には
   `R1` とだけ書く。**共通理由は、それが覆う項目を全部名指しする** — `check-buildrecord.py`
   BRC5 が、指した項目がそこに挙がっているかを見る(名指しが、**項目ごとに適用条件を見た**
   ことの形の証拠である)。
   **減るのは理由の本文だけであって、判定ではない** — 判定行は全項目ぶん要り、適用条件は
   項目ごとに見る。**「依存の更新だから全部非該当」のような、適用条件を見ていない一括の
   非該当は認めない。**
4. **記録先は構築記録の `## 基本要件の点検`**(書式は `.claude/templates/build-record.md`、
   節の規則は `build-record.md` §1)。**見る者は3つ在り、見るものが違う** ★:
   - **`check-buildrecord.py` BRC5**(F1 の出口)— **判定行が在るか**、該当なら落とし先まで
     書いてあるか。**判定が正しいかは見ない。**
   - **F3(`/verify-impl`)の「主張の突き合わせ」** — **判定そのもの**を、再生成した
     コールグラフとコードが実際に示すものに照らす。**誤った `非該当` はそこで所見になる。**
     これが無かった間、「`BR-02` 非該当: 外から値を受け取らない」と1行書けば、
     入力の検証はそのタスクから**永久に消えていた。**
     **ただし F3 が読むのは、その run の対象集合に掛かるクロージャの記録だけである** —
     `verified` になった過去の記録は、この目には入らない。
   - **`check-baseline-verdicts.py`(計器)— 全状態の記録を読む3つ目の目** ★。
     `非該当` の行ごとに、**その記録が宣言したクロージャのファイルの中身**を
     その BR の適用条件の証拠(`baseline-evidence.json`)で走査し、証拠が在れば疑いとして
     名指す(**照らすのはその記録の `commit:` 時点の中身**である — いまの作業ツリーに
     照らすと、後から同じファイルへ機能が増えただけで疑いが立つ)。
     **上の2つの隙間 — 過去の `verified` の記録 — がこれの持ち場である。**
     計器なので何も拒まず、**疑いは裁定ではない**(裁定は F3 か人間)。
     **持ち場と、打つ時期は別である** ★ — この計器は**2度打つ**。
     1度目は**記録を書いた直後**(`/build` §5 の構築記録ゲートの隣)で、そこは**持ち場ではなく、
     いちばん安く直せる場所**である — 判定した文脈がまだ手元に在るので、誤った `非該当` を
     その場で書き直せる。2度目は **F3 の run ごとに1回、全記録に対して**である
     (`/verify-impl` §1)。**説明が過去の記録を強調しているのは持ち場の話であって、
     1度目を要らないと言っているのではない** — 1度目を外すと、誤った `非該当` に気づくのが
     後続の工程になり、そのときには判定した文脈が失われている。
     **疑いの数と一緒に「検査できなかった行」も必ず印字する** — 1件を指して終わる検査は、
     その隣を見落としたことを黙るからである(実測: 同型の再発9度のうち2度が
     「直したつもりで隣を見落とした」型であった)。
     **足したばかりの項目は、この目に映らない** ★ — 過去の記録にはその項目の判定行が無く、
     **行が無ければ `非該当` も無く、疑いも立たない。** それは疑いの数にも「検査できなかった行」
     にも現れないので、**計器は「記録に判定行が無い BR」を BR ごとに数えて印字する**
     (§4.3「足した項目は、過去に対して盲目である」)。
5. **この一覧は網羅ではない。** 抜けに気づいた瞬間が足す時である(§4)。
   一覧に無いことは「考えなくてよい」を意味しない。
6. **UI が無いことは免除ではない。** **満たす手段は成果物の作りで決まる** — 画面・CLI・API・
   スケジュール起動のどれで提供してもよく、**どれを採ったかを書く**。画面が無ければ、意思確認は CLI の
   問い返しや API の引数として現れる。**「UI 無し」で落とせるのは、その操作自体が存在しない
   ときだけである。** 手段に条件が付く項目は、その条件を §3 の小節が書く。
7. **§0 と §1 には、どの項目にも掛かることだけを書く** ★。ある項目にだけ掛かることは、
   **§2 の行と §3 の小節が持つ。** 特例をここへ書くと、次に項目を足す者が、その特例が
   自分にも掛かるのかを判じるために §0〜§1 を読み直し、書き直すことになる —
   **1項目 = 2箇所という §4 の値段が、そこで崩れる。**

`check-buildrecord.py` BRC5 も `check-baseline-verdicts.py` も、**このファイル全体**から
`| BR-nn |` で始まる行を集める。**だから §2 の外に、その形の行を書いてはならない** —

## 3. 各項目

**該当した行の小節だけを読む。** 非該当と判定した項目の小節は読まなくてよい(§2 の適用条件で
判定できる粒度に書いてある)。
**これは判定する側(`/build`)の話である** ★ — **`/verify-impl` には掛からない。**
あちらの仕事はまさに**誤った `非該当` を見つけること**なので、疑った項目の小節は読む
(§1 の4)。

### 3.1 BR-01 自己ロックアウトの禁止

- 拒否するもの: **自分自身の削除・自分の管理権限の剥奪・自分の無効化**、および
  **その権限を持つ最後の1件**の削除・降格・無効化・ロック。
- **判定はサーバ側(操作を実行する点)で行う。** 画面でボタンを隠すのは実装ではない。
- **同時実行で 0 人になる経路を塞ぐ。** 二人の管理者が同時に相手を降格させると、逐次では
  起きない状態が起きる。件数の確認と更新を同じトランザクションに入れるか、
  「管理者が1件以上」を DB の制約として持つ。
- 拒否は**理由の分かる応答**で返す(利用者は自分の操作がなぜ通らないのか分からない)。
- 検証: 「最後の1人でその操作をすると拒否される」を自動テストで持つ。これは受け入れ基準であって、
  テストの有無は DS-01 の委任ではない。

### 3.2 BR-02 入力の検証

- 全項目について **必須/任意・型・長さの上下限・文字種・値域・形式** を決めて書く。
  決める場所は 01 の受け入れ基準(利用者に見える拒否)か 02 の契約(型と制約)。
- **判定はサーバ側で行う。** クライアント側の検証は利便であって、サーバ側の判定の代わりにならない。
- **allowlist で書く。** 「許す形」を書く。禁止文字の列挙は、必ず書き漏らす。
- 拒否は**項目ごとに理由をつけて返す**。最初の1件で打ち切ると、利用者は往復を強いられる。
- **長さ上限のない自由入力を作らない。** 上限は保存側(桁数・カラム長)と一致させる。
- 検証: 境界値(最小・最大・最大+1)と、空文字・空白のみ・不正な文字種のテスト。

### 3.3 BR-03 識別子の文字種と正規化

- **拒否する**: 空文字、空白のみ、前後の空白、制御文字、NUL、改行、タブ。
  前後の空白は「黙って落とす」か「拒否する」かを**決めて書く**(黙って落とすと、
  利用者が入れたものと保存されたものが違う)。
- **正規化と同一視の規則を書く**: Unicode 正規化形(NFC 等)と大文字小文字の扱い。
  重複判定に使う正規形を決めないと、**見た目が同じ別人**を作れる。
- **使える文字集合を allowlist で、長さの上下限とともに書く。**
- **予約語と衝突する形を決める**: `admin` `root` `api` `me` `new` などの経路名、
  システムが使う形(UUID・連番)との衝突。
- 落とし先は 02 の契約(型と制約)。利用者に見える拒否文言は 01 の受け入れ基準。

### 3.4 BR-04 システム境界での検証

- 境界とは: API の受信と応答、キュー、ファイル取込、**外部サービスの応答**、
  保存されている JSON/YAML、環境変数、Webhook。
- **入ってくるものはスキーマで検証してから使う。** 「自分が書いたデータだから正しい」は、
  前の版が書いたかもしれないという事実を無視している。
- **外部サービスの応答も検証する。** 相手の障害や仕様変更が、自分の内部状態を壊してはならない。
- **未知のフィールドの扱い(拒否か無視か)を決めて書く。** 決めないと版が上がるたびに挙動が変わる。
- **出す側も契約に一致することを確かめる**(REST は OpenAPI 3.1 — `.claude/directions/core.md` §6)。
- 検証の失敗は握りつぶさず、分類された失敗として扱う(DS-02 のガードレール)。

### 3.5 BR-05 破壊的操作の意思確認

- 対象: 削除、パスワード・メールアドレス・権限・公開範囲の変更、一括操作、外部への送信、
  取り消せない状態遷移。
- **確認には「何が起きるか」と「対象の名前と件数」を書く。** 「本当によろしいですか?」だけは
  確認ではない — 利用者は自分が何を消そうとしているのかを見ていない。
- **取り消せないものは、取り消せないと書く。**
- **危険度の高いもの**(アカウント削除・全件削除・権限の剥奪)は、**再認証**または
  **対象名の入力**を要求する。
- **確認 UI はサーバ側の権限判定の代わりにならない。** 破壊的操作を GET で起こさない。
- **回復手段の有無を書く**(取り消し猶予・ゴミ箱・監査記録からの復元)。無いなら「無い」と書く。
  無いことを書かないと、後から「在るはず」と誤解される。

### 3.6 BR-06 乱数と秘密の生成

- 対象: トークン、セッション ID、再設定リンク、招待コード、初期パスワード、API キー、
  ソルト、nonce — **推測されると困る値のすべて**。
- **暗号論的乱数生成器のみ**: Python `secrets`、Node.js `crypto.randomBytes` / `webcrypto`、
  ブラウザ `crypto.getRandomValues`、Go `crypto/rand`、Java `SecureRandom`。
  **使わない**: `random`(Python)、`Math.random()`、`math/rand`(Go)、時刻やカウンタからの導出。
- **エントロピーは 128bit 以上。** 文字数ではなくビット数で書く。
- 生成した秘密は**ログに出さない**(DS-03 のガードレール)。**有効期限と使い切りの規則**を決める。
- **例外はテスト用データの生成だけ**である。再現性のために種を固定するのは DS-01 のガードレール
  そのものであり、この項目に反しない。**ただし本番経路と同じ関数を使うなら、乱数源を
  差し替えられる形にする** — テストのために本番の生成器を弱めてはならない。

### 3.7 BR-07 操作の認可

- **「誰であるか」ではなく「その対象に対してその操作をしてよいか」である。** 認証を通った利用者が、
  **他人の識別子を指定して他人のものを読む・書く**経路がこの項目の相手である。
- **識別子を受け取らない経路も相手である** ★ — 一覧・検索・書き出しは、**問合せそのものを
  主体で絞る。** 全件を取ってから絞る形にすると、絞り忘れた1経路が全件を返す。
- **判定はサーバ側(操作を実行する点)で行う。** 一覧に出さないこと・画面でボタンを隠すことは
  実装ではない(`BR-01` と同じ形である)。**識別子を推測されれば通る**からである。
- **毎回判定する。** 入口で1度だけ確かめて後は信じる形にしない — 経路が増えたときに、
  新しい経路だけが素通りする。
- **失敗したときの応答は、対象の存在を漏らさない形で定める。** 「権限がありません」と
  「見つかりません」を撃ち分けると、**存在の有無そのものが漏れる。** どちらに寄せるかは
  01 の受け入れ基準に書く(外から観測できることだからである)。
- 検証: 「他人の識別子を指定すると拒否される」「一覧に他人のものが混ざらない」を自動テストで持つ。
  これは受け入れ基準であって、**そのテストを置くかどうかは `DS-01` の委任ではない**
  (`BR-01` と同じ形である)。

### 3.8 BR-08 出力時のエスケープ

- 出す先とは: 画面(HTML)、テンプレート、URL とその引数、JSON、CSV、メール本文、ログ、
  SQL、シェルの引数、ファイル名 — **プロセスの外へ値を出すすべての経路**である。
- **出す瞬間に、出す先の規則で変換する。** 入口で1度だけ変換して保存する形にしない —
  保存した値がどの先へ出るかは保存の時点では決まっておらず、**二重に変換された表示と
  変換されないままの表示が同時に生まれる。**
- **入力の検証は代わりにならない** ★ — 自由記述の本文は、許した文字集合の中に断片を持てる。
  `BR-02` を通った値がそのまま危険である。だからこの項目が別に在る。
- **HTML は出す場所ごとに規則が違う**(要素の中身・属性値・`<script>` の中・`style`・
  `href` のスキーム)。テンプレートの自動変換を切って生のまま出す箇所は、
  **どこで切ったかとその理由**を `MODULE-*.md` の「実装上の判断」に書く。
- **SQL はプレースホルダで値を渡す。** シェルは引数の配列で渡し、文字列を繋げて命令を作らない。
  ファイル名として使う値は、区切り文字と `..` を許さない。
- 検証: 代表的な仕込み文字列(`<script>`、引用符、改行、`../`)を入れたときに、
  **出す側で無害化されている**ことを自動テストで持つ。これは受け入れ基準であって、
  そのテストを置くかどうかは `DS-01` の委任ではない。

### 3.9 BR-09 認証試行の抑止

- 対象: ログイン、パスワード再設定、確認コードの検証、招待コードの引き換え、資格情報による
  API の認証 — **秘密を突き合わせるすべての経路**。
  **`BR-01` は逆向きの項目である**(締め出しの行き過ぎを防ぐ)ので、これの代わりにならない。
- **回数と間隔に上限を置く。** 数える単位は**利用者の識別子と発信元の両方**である —
  片方だけでは、1つの識別子への総当たりか、多数の識別子への総当たりのどちらかが素通りする。
- **上限に達したときの振る舞いを決めて書く**(遅らせる・一定時間受け付けない・追加の確認を求める)。
  **必ず時間で解ける形にする** — 永久に受け付けない形は、`BR-01` が禁じた締め出しそのものである。
- **応答から、その識別子が実在するかを漏らさない**(`BR-07` と同じ形である)。
  失敗の文面と所要時間を、実在と不在で撃ち分けない。
- **失敗した試行を記録する**(いつ・誰の識別子へ・どこから)。**秘密そのものは書かない**
  (`BR-06` と同じ形である)。
- 検証: 「上限を超えた試行が拒否される」「上限が時間で解ける」を自動テストで持つ。
  これは受け入れ基準であって、そのテストを置くかどうかは `DS-01` の委任ではない。

### 3.10 BR-10 サイト外からの要求の拒否

- 対象: **認証済みの利用者の権限で状態を変える経路**(フォームの送信、`POST` / `PUT` /
  `DELETE`、資格情報の変更、決済、権限の変更)。読むだけの経路は対象ではない。
- **その要求が自分のサイトから出たことを、サーバ側で確かめる。** 手段は成果物の作りで決まる
  (1回だけ有効な値を仕込んで突き合わせる / 発信元の宣言を見る / 資格情報が別のサイトからの
  要求に付かない設定にする)。**どれを採ったかを書く** — 決めないと経路ごとに別の手段が混ざり、
  混ざったことに誰も気づかない。
- **`BR-05` の確認画面は代わりにならない** ★ — 確認を押す操作そのものを、外から踏ませられる。
- **`BR-07` とも重ならない**: あちらは「その主体にその権利が在るか」、
  こちらは「その要求が本人の意思で出たか」である。**両方が要る。**
- **画面が無いことは免除ではない**(§1 の6 と同じ形である)。ブラウザから呼ばれる経路が
  1本でも在れば該当する。呼ばれないなら、**呼ばれないことを理由として書いて** 非該当にする。
- 検証: 「別の発信元からの状態変更の要求が拒否される」を自動テストで持つ。

### 3.11 BR-11 バックアップとリストア

- 対象: **失われるとサービスを続けられない値** — 顧客のデータ、利用者の設定、系の設定。
  **対象でない保存先**: 失っても作り直せるものだけを置くもの(キャッシュ、導出した索引、
  一時ファイル)。**同じ保存先に守るべき値が同居するなら、その保存先は対象である。**
  **後から証明に使う記録は対象である** ★ — 監査記録、操作の履歴、課金の明細。
  失っても系は動き続けるが、**「誰が何をしたか」を後から示せなくなり、それは作り直せない。**
  観測のためだけのログ(デバッグの出力、アクセスの統計)は対象でない。
  **見分けるのは保持の目的であって、ログという名前ではない。**
  **機構が既に在っても、保存する対象を増やしたタスクは 該当 である** — 増えた対象が
  バックアップに入っていることまでが、そのタスクの仕事である。
- **バックアップとリストアは2つで1組である。** バックアップだけを作ったものは、
  戻せることを一度も確かめていない複製であり、**在るように見えるだけ**である。
- **戻せることを確かめる。** 「取れた」で終わる確認は、この項目を満たさない。
  **バックアップ → 空の保存先へリストア → 中身が一致する**、までを1本の自動テストにする。
  **機構が外部サービスの機能である**(管理された DB の時点復旧など)ために自動テストに
  載せられないことがある。**手動の実測で代えることは `DS-01` の対象外なので、そこは
  決定シートに載せて人間が決める**(`delegation.md` §2 — 委任の対象外は問う基準の例外である)。
  代えると決まったら、**実測した日付を `03-impl/infra/` の表の
  「リストア手順(実測済みか)」の欄に書く。空欄は満たしていない。**
- **何が入り、何が入らないかを書く。** 書かないと、後から足した保存先だけが黙って外れる。
  **書く場所は同じ表である** ★ — 雛形に「入らないもの」の欄は無いので、
  **入らない保存先も `対象` の欄に1行として立て、残る3欄を1つも空けない** —
  「取得方法・頻度」に `適用外(理由)`、残る2欄に `—` と書く
  (**語はキットの定型に揃える。** 雛形のコメントの `適用外(理由)` は表まるごとの話、
  こちらは行1つの話で、**どちらの話かは `対象` の欄が在るかで決まる**)。空欄のままにしない
  (「見ていない」と「見た上で外した」が同じ見た目になる。**空欄を「満たしていない」と
  読む規則が上に在る**ので、対象外の行の空欄は誤った赤にもなる)。**欄を足さないのは意図である** — 表の形は配布先の既存の文書と
  揃っており、欄を1つ足すことは、その全部を古くすることである。
- **操作の手段は画面に限らない** ★ — 画面・CLI・API・スケジュール起動のどれでもよく、
  どれが適するかは成果物の作りで決まる。**「画面が無い」は免除にならない**(§1 の6)。
  **ただしスケジュール起動が手段になりうるのはバックアップだけである** — リストアは必要に
  なった日に人が起こすものなので、**人が起こせる経路**(画面・CLI・API のどれか)を
  必ず1つ持つ。**この項目に反するのは、バックアップの手段が1つも無いことと、
  リストアに人が起こせる経路が無いことの2つである。**
- **手段の選択は問う基準に掛ける**(`delegation.md` §1)。手で行う運用手順が増えるので条件1に
  当たることが多く、条件2まで当たるなら決定シートに載せる。当たらないなら決めて開示行を残す
  (`delegation.md` §3)。**頻度と保持期間は `DS-04` の判断である** — 単位を付けて値と根拠を
  書き、外から見える値になったものは 01 の受け入れ基準へ書き足す。
  **「決められない」は問う理由にならない**(`delegation.md` §1)— 先に上流と契約とコードを引く。
  **問うてよいのは どう満たすか だけであり、満たすか どうか は決して問わない**(§0)。
- **管理者向けの手順を残す。** 落とし先は `docs/03-impl/infra/<環境>/` の
  「バックアップ・リストア」の表である(雛形は `.claude/templates/03-infra.md`。
  **環境が3つ在れば表も3つ在る**)。**採った手段は「取得方法・頻度」と
  「リストア手順(実測済みか)」の欄に、そこから手段が読み取れる形で書く。**
  リストアの手順には、**途中で止める必要が在るか**と**どこまで戻るか**(直近の
  バックアップより後の変更は失われる)まで書く。
  **手順の無い機能は、必要になった日に読む者が居ない機能である。**
- **この表は、他の落とし先と違って、全タスクが共有する** ★ — 環境ごとに1つしか無く、
  永続化に触るすべてのタスクが同じ表を書き換える。**それでも先送りの口は作らない**
  (該当した基本要件をいま満たすことは、後回しにできない)。**書けない見え方は2つ在り、
  片方は先送りではなく、もう片方は並走の問題である**:
  - **`infra/` をまだ書かない段階**(`03-impl.md` — 実装が無い時点では書かない)。
    **ここには先送りは無い** — 運用の手順は運用上の事実であって、**その事実がまだ存在しない**。
    落とし先は 01 の受け入れ基準だけでよい。
    **この免除が効く境目は「実装が在るか」であって、「着手時に `infra/` が在ったか」では
    決してない** ★ — **保存先を実際に作るコードを書くタスクは、この免除の外に在る。**
    そのタスクが `infra/<環境>/` を作り、表を埋める。**`infra/` が無かったことは理由に
    ならない** — 無ければ、そのタスクが作る。
    (この免除の中に居られるのは、**文書だけで終わるタスク** — 01 と 02 を書き、
    保存先をまだ1つも作らないもの — である。)
    雛形(`.claude/templates/03-infra.md`)は**書き方を示すだけである** —
    「適用外なら『適用外(理由)』と1行書く(空欄のままにしない)」。
    **執行するのは雛形ではない** ★ — 該当した行の落とし先が実体を指しているかを見る
    BRC5 と、`/build` の出口の点検(先送り禁止のうち「該当の行が実際に作られていること」)
    である。**雛形が禁じているのは空欄であって、書き忘れではない。**
  - **表は在るが、別の走っているタスクの範囲に在る。** これは**クロージャの排他の問題**で
    あって、基本要件の問題ではない。**その表は、この項目が該当したタスクのクロージャに入る** —
    入れられないなら、その2つのタスクは並走できない(**1つのクロージャにつき書き手は1人**。
    範囲の排他は、そのキットの並走の規則が持つ)。**順序を決めるのであって、落とし先を諦めるのではない。**
- **実行できる者を書く。** 役割によって可否が変わるなら `BR-07` の持ち場である。
  **運用者だけが叩く経路のように、利用者ごとの違いが無くて `BR-07` が非該当になるときは、
  この項目が持つ** — 譲った先が非該当になると、誰の持ち場でもなくなる(§0)。
  **書くのは 01 の受け入れ基準である**(誰が実行できるかは外から観測できる)。
- **隣の項目に譲るもの** ★:
  - リストアが読み込むバックアップの検証は **`BR-04`**(保存されたデータは境界である)。
  - リストアは戻せない上書きなので、**その操作の意思確認**は **`BR-05`**。
    **`BR-05` が問う回復手段として「`BR-11` のリストア」とだけ書いてはならない** —
    1回の操作を取り消すことと、保存先ごと巻き戻すことは別物である。
  - バックアップを守る鍵や、取り出しに使う一時的な符牒は **`BR-06`**。
- 検証: 「バックアップから戻すと、取った時点の中身と一致する」を自動テストで持つ。
  これは受け入れ基準であって、そのテストを置くかどうかは `DS-01` の委任ではない。
  **手動の実測で代える道は、上の3番目の箇条が正である**(ここには書き写さない)。

### 3.12 BR-12 成果物の版の名乗り

- 対象: **人か別の系が起動する成果物** — CLI、常駐するサービス、**ブラウザで動く画面(web アプリ)**、その他のアプリ、配布するライブラリ。
  **対象でないもの**: そのリポジトリの中でしか動かない補助のスクリプト、テスト、
  一度きりの移行のスクリプト。**見分けるのは「外へ渡るか」であって、実行できるかどうかではない** —
  外へ渡らないものは、どの版が動いているかを尋ねる相手が居ない。
- **既に在る成果物が版を名乗れないことを、この項目が自分で拾うことはしない** ★ —
  遡って効かせる道は §4.3 が持つ。**この項目が捕まえるのは、起動の入口に触れたタスクである** —
  引数を1つ足す、下位コマンドを増やす、起動時の出力を変える、のどれもが入口である。
  **入口に触れておきながら、その成果物に版を名乗らせないことはできない。**
  **名乗れるようにするための仕事は一度で終わる** — 以後のタスクは、
  **上の適用条件のどれにも当たらないかぎり** 非該当 である(版の値やその出し方を動かすタスクは、何度目であっても 該当 である)。
- **名乗る手段は成果物の作りで決まる**(§1 の6)。CLI は `-v` と `--version`、常駐する
  サービスは版を返す経路か起動時の記録、ライブラリは公開する属性。
  **ブラウザで動く画面は、画面から辿れる1箇所**(情報の画面・脚の行など)**か、
  配信された資産の中の決まった場所**(`meta` の欄など)。**どちらか一方でよいが、
  どこに在るかを書く** — 書かなければ、支援を求められた者が探す場所を持たない。
  **どれを採ったかを書く。**
  **人が読める形で出す** — 呼び出した者が、返ってきた文字列だけで版を読み取れること。
- **別々に配られるものは、別々の成果物である** ★ — ブラウザで動く画面とそれが呼ぶサービスが
  別に配られるなら、**版も別に持ち、別に名乗る**(同じ番号を強いない)。
  **片方だけが名乗れる状態は、この項目を満たさない** — 動いている組み合わせが判らなければ、
  どちらの版の話をしているのかが決まらない。
- **値の形は `major.minor.revision` の3つ組である。**
  **どの変更でどの桁が動くかは `flows.md` §9 が正であり、ここには書き写さない** —
  規則を成果物ごとに決め直さない(読む側は、成果物ごとに規則を確かめない)。
  3つ組から外れる印(先行版の符牒、ビルドの識別子)を足すなら、
  **3つ組が先頭に在り、それだけでも読める形にする。**
- **値の持ち主は1箇所である** ★ — 版の値を置く場所を1つ決め、名乗る経路はそこから読む。
  **このキットが用意している持ち主は `flows.md` §9 のリリース台帳である**
  (**その届く範囲と、届かないときに誰が決めるかは、そこが正である。ここには書き写さない**)。
  **手で2箇所に書かない**(`conventions.md` §4)。組み立てのときに埋め込むなら、
  **埋め込みの元がその1箇所である**。そして**埋め込みに失敗したときに何を名乗るかまで決める** —
  空の文字列や `unknown` を黙って出す成果物は、**版を名乗れない成果物と同じである。**
- **いつ上げるかは、この項目の持ち場ではない** ★ — **持ち主は `flows.md` §9(リリース)である。**
  この項目が縛るのは**名乗れること・形・持ち主が1つであること**の3つだけであり、
  **契機と桁の決め方はそこが正である。ここに書き写さない。**
- **隣の項目に譲るもの** ★:
  - 版を返す経路を**誰が呼べるか**が役割によって変わるなら、それは **`BR-07`** である。
  - 版の文字列を画面・ログ・応答へ出すときの逃がしは **`BR-08`**。
- 検証: 「その成果物に版を尋ねると、`major.minor.revision` の形の値が返る」を自動テストで持つ(尋ね方は上で選んだ手段そのものである — CLI なら引数、サービスなら経路、画面なら表示か資産の中の決まった場所)。
  これは受け入れ基準であって、そのテストを置くかどうかは `DS-01` の委任ではない。
  **手で1回確かめて終わりにしない** — 版の出し方は、組み立ての仕方を変えた日に黙って壊れる。

### 3.13 BR-13 画面を使える手段の確保

- **この項目が縛るのは3つである**: **キーボードだけで完了できること**(押す・選ぶ・閉じる・
  送るのすべてに、指す道具を使わない道が在る)、**支援する道具に読める名前と状態を持つこと**
  (項目に名前が在り、いまどの状態か — 選ばれている・無効・読み込み中・誤りが在る — が
  値として読めること)、**色や大きさだけに頼らず見分けられること**(色を落としても意味が残り、
  文字と背景の差が十分に在ること)。
- **満たす水準は、この製品が決めて書く。** このファイルは水準を定めない ★ —
  **どの外部の基準に、どの段階まで従うか**を決めるのは、製品ごとの判断である。
  決めた水準は 01 の受け入れ基準に書く(外から観測できる)。**決めていない状態で
  該当の判定を書くことはできない** — 「配慮する」とだけ書いた行は、何も約束していない。
- **満たさない範囲が在るなら、範囲と理由を書く。** 「対応しない」だけの行は未判定と
  区別できない(§1 の3 と同じ形である)。
- **画面の外の手段は免除にならない** ★ — 同じことが CLI や API でもできるからといって、
  画面の側を落とせない。画面を出すと決めたのは成果物の側であり、**その画面しか知らない
  利用者が居る。**
- **既に在る画面が満たしていないことを、この項目が自分で拾うことはしない**(`BR-12` と
  同じ形である)。**この項目が捕まえるのは、画面を作った / 変えたタスクである。**
  遡って効かせる道は §4.3 が持つ。
- **隣の項目に譲るもの** ★:
  - 画面でボタンを隠すことは判定の実装にならない、は **`BR-01`** と **`BR-07`** である。
    **この項目は「操作できるか」であって、「操作してよいか」ではない。**
  - 誤りの文面を出すときの逃がしは **`BR-08`**。
  - 破壊的な操作の確認そのものは **`BR-05`** で、**この項目はその確認を
    キーボードだけで通せるか**を見る。
- 検証: 「その画面の主要な操作が、指す道具を使わずに最後まで通る」を自動テストで持つ。
  これは受け入れ基準であって、そのテストを置くかどうかは `DS-01` の委任ではない。
  **道具で測れる部分と、人が見るほかない部分が在る** — 測れない部分は探索的な画面確認
  (`qa` 試験区分)の観点として残し、**どちらで見たかを書く。**

## 4. 項目の足しかた

**足すのはキットの編集である**ので `/kit-improve` が手順を持つ(`.claude/directions/core.md` §3 の2つの縛りが効く)。

**この節は、足すときに掛かる費用を全部並べたものである** ★ — 数えていない費用は、
足す当日に発見されて、その日の作業を膨らませる(実測: `BR-11` を足した回は、
§2 と §3 の2箇所で済むはずが16ファイルになった)。

### 4.1 足してよいもの

- 上流が黙っていても満たさねばならず、**特定の製品ではなく、その種の機能に共通して**言えること。
- 特定プロジェクトの事情は基本要件ではない — `docs/00-requests/decisions/` の `決定` に書く
  (プロジェクトの `決定` のほうが強い)。
- **何から守る項目かは問わない** ★。この一覧は守る相手で束ねていない(§0)。
  「安全性ではないから基本要件ではない」は、足さない理由にならない。

### 4.2 足すときに手で書くもの — この3つで全部である

1. **§2 の表に1行。** ID は現在の最大値 + 1。**欠番は埋めない**(過去のタスクの点検表が
   その ID を指している)。**§2 の外にこの形の行を書かない**(§2 の冒頭)。
2. **§3 に1小節。** その項目にだけ掛かることは、**すべてここに書く** — §0 と §1 へ
   特例を書かない(§1 の7)。
3. **`baseline-evidence.json` に証拠パターン。** これは 2026-08-28 に計器
   (`check-baseline-verdicts.py`)が生まれてから掛かるようになった費用である。
   **パターンを書けないなら、書けないと決めてよい** — 計器はそれを「パターンを持たない BR」
   として毎回印字する。**黙って空にしない。** 適用条件の一部しか表せないときは、
   **表せない部分を注記に書く**(その部分は疑いにも取りこぼしにも現れないので、
   書かなければ穴の在り処が誰にも残らない)。

**手で書くのはこの3つだけだが、機械が作り直すものが1つ在る** ★ —
`.claude/kit-manifest.json`(配布物の内容の台帳)である。**手で書かない。**
`python3 .claude/scripts/kit-manifest.py update` が作り直し、作業場の `make check` が
鮮度を見る。数え忘れると、`make check` に落ちて初めて見つかる。

**この値段は、キットの1つぶんである** ★ — **この仕組みを持つキットが複数在りうる。**
実測: `BR-11` を足した回に触った16ファイルは、8ファイル × 2キットである。
**どのキットへ入れるかと、その配り方は、このファイルの持ち分ではない** —
**キットを作る側の手順が持つ**(配布物であるこのファイルは、本流の運用を語らない)。

**条件つきで掛かるものが2つ在る**(**当たらなければ払わない**):

- **新しい概念語を作るなら、`glossary.md` に行を足す**(`conventions.md` §3.2 —
  表に無い概念を名付けたなら、規範用語集に足してから規範に書く)。**1行とは限らない** ★ —
  その語が**既に別のものを指している日本語**に当たるなら、`glossary.md` の
  「同じ比喩が2つ以上のものに当たる語」の節にも1行が要る(どの意味で使ったかを
  読み手に分かる形で書かせる節である)。**その節の番号をここに書かない** ★ —
  **この一覧を持つキットどうしで番号が違う**ので、焼き込めばどちらか一方で必ず外れる。**行数を先に決めない** —
  いくつ要るかは、その語が既存の語とぶつかるかで決まる。
  **作らずに済むなら作らない** — 既にある平の言葉で書くほうが安い。`BR-11` はそう判断した。
- **§2 の「既定の落とし先」は、雛形に受け皿が既に在る先から選ぶ。** 無い先を選ぶなら
  `.claude/templates/` も手で書くことになり、**それは配布先の既存の文書を全部古くする**
  (§3.11 の「欄を足さないのは意図である」と同じ理由)。

**§0・§1・他のファイルを触ることになったら、それは項目のせいではなく、そこに書いてあった
一般の言明が狭すぎたということである** ★ — **そのときは、言明のほうを、次の項目でも
壊れない形に直す**(§5)。項目のための特例を足して回らない。特例は、次の項目を足す者が
払う費用になる。

### 4.3 足した項目は、過去に対して盲目である

**これは欠陥ではなく、そういう仕組みである。** §1 の4 の見る者が新しい項目をどう扱うかは、
それぞれ違う:

- **`check-buildrecord.py` BRC5** は、**そのタスクの記録1本**に対して、§2 の全項目の判定行を
  要求する。だから**足した後に出口を通る記録は、新しい項目も必ず判定する** — 足す前に着手した
  タスクでも同じである(出口で判定行が無ければ落ちる)。
  **`--all` は全記録を一度に見る使い方であり、項目を足した直後は当然に赤くなる。**
  その赤は「過去へ遡って埋めよ」ではない(下)。
- **F3(`/verify-impl`)** は、その run の対象集合に掛かる記録しか読まない。
- **計器(`check-baseline-verdicts.py`)** は、記録に**在る行**だけを見る。新しい項目の行は
  過去の記録に無いので、**その項目については過去の記録を1件も見ていない。**
  疑いが出ないのは「疑わしくない」からではなく、**見ていない**からである。
  **計器はこれを「記録に判定行が無い BR」として BR ごとに数えて印字する**(§1 の4)。

**遡って埋め直さない。** 足した項目は、その版以降のタスクにだけ効く。**既に `verified` に
なった構築記録は書き換えない** — 記録は、そのタスクが何を判断したかの記録であって、
いまの規範に対する適合表ではない。**遡って効かせる必要が出たときは、記録ではなく成果物に
当てる**: `/retrofit` の一括点検(既存システム全体に §2 を当てる唯一の機会)か、
`docs/issues/` の起票である。**規範に項目を足すことは、タスクを開かない。**

### 4.4 廃止するとき

- **§2 の行を消す。** これで機械の一覧から消える(§2 の冒頭 — 機械はファイル全体を読むので、
  **消した行を §3 や §4 へ移して残さない**)。
- §3 の小節には「廃止 <YYYY-MM-DD> — 理由」を残す。**ID は再利用しない。**
- `baseline-evidence.json` のパターンも消す(残すと、居ない BR のパターンを計器が抱える)。

## 5. この一覧を、他所でどう語ってよいか

**このファイルは2つのものの唯一の正である** ★ — **項目**と、**基本要件という種類そのもの**
(何の一覧か / どう縛るか / 落とし先 / 誰が判定を見るか / 足しかた)。
冒頭の「項目の内容を他所に書き写してはならない」は、**後者にも同じく掛かる。**

**なぜこれを明文にしたか。** 項目を足すたびに書き換える羽目になっていたのは、項目の一覧では
なかった — **一覧を言い直している写しのほう**だった。実測(2026-08-19 以降、項目が増えた4回):
機械は §2 の表を実行時に読むので**スクリプトも雛形も1行も変わらない**のに、
**この一覧を「安全性の性質」と要約していた** `CLAUDE.md` / `flows.md` / `glossary.md` /
`introduction.html` と、**判定を見る者を数えていた** `principles.md` / `reading.md` /
`CLAUDE.md` が、そのつど古くなった(見る者の数は 2026-08-23 と 2026-08-28 に
**2度動いている**)。**同型の直し忘れが、項目を足した直近3回すべてで独立検査に拾われた。**

**だから、他所に書いてよいのは次の2つだけである**:

- **このファイルへの指し**(「基本要件は `baseline.md` が正である」)。
- **その文書の仕事に必要な、この一覧の中身を数えない言い方** — 規範用語集の
  「上流が黙っていても免除されない性質(`BR-01`〜)。その機能の意味に既に含まれているもの」が、
  そのまま使える形である。

**書いてはならないのは、数え上げ — この一覧の中身を数えて並べること — である** ★:

- **何から守る一覧かの列挙**(「安全性の」「安全性と、失っても戻せることの」)。
  次の項目が第三のものから守った日に、**全部が同時に古くなる。**
- **落とし先の列挙**(「01 と 02 と `MODULE-*.md` の3つ」)。§2 の欄が正である。
- **項目の数**(「7項目」「11項目」)と、**個別の項目の中身の言い直し**。
  「`BR-01`〜」のように**一覧全体を1つの名前で指す書き方**は、数え上げではない —
  これは使ってよい。
- **判定を見る者の、数と分担**(「見る者は2つ」「3つ」「BRC5 は行の有無、F3 は当否」)。
  §1 の4 が正である。

**禁じているのは言い直しであって、名指しではない** ★ — スキルや `build-record.md` が
**自分の手順として**「この道具をこの回数だけ走らせる」「この節を読む」と書くのは、
指しであって数え上げではない。**書いてはならないのは、その道具どうしが何を分担しているかを
そこで説明し直すこと**である。分担が変わった日に古くなるのは、後者だけだからである。

**この規則は、機械では守りきれない。** `check-kit-refs.py` (e) が見るのは
「§2 の外に `| BR-nn |` 行が無いこと」だけであり、**散文の中の数え上げは見つけられない。**
だから、**項目を足す作業の独立確認では、この節を明示的に当てる** — 「一覧を言い直している
写しが、キットのどこかに増えていないか」を、独立に検査する側の観点に必ず入れる。
