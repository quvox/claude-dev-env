# docs/build-records/<slug>.md — 構築記録

日本語で書く。骨格は `.claude/templates/build-record.md` であり、
**このファイルはその周りの規則を所有する。**
**構築記録ゲート**は `check-buildrecord.py`(ID の一覧は `--list`。規範に書き写さないこと)。

構築記録は、**検証を先送りする側が払う頭金である**(flows.md §1)。
1タスク = 1ファイル = 数十行。**仕事はちょうど3つ**である:

1. **検証の優先度づけの入力** — verify 系フローは、すべてを掃くのではなく `awaiting-verify` の
   記録のクロージャと重要な変更のフラグを読む。critical なクロージャは常に独立レビューに含まれる。
2. **`/clear` を跨ぐ再開点** — 記録とそれが名指すファイルだけで、どの段からでもタスクを再開
   できなければならない。これは廃止されたタスクメモの後継であり、その最も高くついた規則を
   受け継いでいる: **目に見える成果物が1つ仕上がった瞬間に進捗メモの1行を書く。決して最後に
   まとめて書かない** — 文脈はタスクの途中で死にうるのであり、**その瞬間に記録が持っていない
   ものは失われる。**
3. **F4 が失敗したときの犯人探しの範囲を絞ること** — 壊れたテストは、履歴全体ではなく、
   **最後の green 鮮度スタンプ以降の構築記録**と突き合わせる。

## 1. 機械が読むもの。そして決して動かしてはならないもの

- `check-buildrecord.py` は frontmatter(`slug` / `state` / `critical` / `origin` / 時刻)、
  `## 影響範囲(closure)`、`## 主張`、`## 基本要件の点検`、
  そして **`## 直さなかった指摘(独立レビュー・探索的QA)`** を読む ★(2026-09-15。
  inspection-28 A-6 — **節が在ること**と、**各行が理由を持つこと**を見る。
  1件も無いなら「なし」の1行を書く。**既に `verified` で閉じた記録には求めない** —
  この節は 2026-09-15 に足したもので、それより前の記録は持っていないからである)。
- **クロージャの1行は、パス1つで始まる。** 書式は次の3つで、**どれも同じ読み方をする道具が
  3本ある**(`check-buildrecord.py` / `stamps.py` / `check-baseline-verdicts.py`):

  ```markdown
  - src/x.py                 普通の名前
  - .github/workflows/ci.yml 先頭が `.` のものもそのまま書ける
  - `src/my app/auth.py`     空白を含む名前はバッククォートで囲む
  ```

  注釈を付けるならパスの後ろへ置く(`- src/x.py — 追記`)。
  **上のどれとしても読めない行は、黙って捨てられずに違反になる**(BRC6)★ —
  捨てられると、その1本だけが検証の範囲からも `critical` の機械判定からも消えるのに、
  他の行が在るぶん「クロージャが空」の検査は通ってしまう(2026-09-13)。
  リポジトリの外を指す形(`../` と絶対パス)は書けない。
- **クロージャは作業コミットと突き合わせる** ★(2026-09-23)— `commit:` が名指すコミットで
  変わったファイルが1本でもクロージャに無ければ、`check-buildrecord.py` が落とす(BRC8。
  履歴・課題票・索引・台帳のような帳簿は数えない)。クロージャは人が書いて人が読むので、
  抜けは書いた本人にも読んだ側にも見えず、**抜けたファイルは検証の範囲から黙って消える**
  (実測: 1周で3回 — E2E の台本の抜けと、別の画面の台本との取り違え)。
  **見るのは `commit:` の1コミット(マージなら第一親との差分)だけである** — 作業が複数の
  コミットに分かれたなら、それより前のコミットの分は書く側が `git log` で拾う(機械は下限を
  引き上げるだけである)。改名は新しい名前を書く。**大きく書き換えた改名は git が
  削除+追加と見るので、そのときは旧名も書く**(消したファイルも触ったファイルである)。
  **この作業が書いたのではないファイルが同じコミットに入ったとき**(人間が着手前に置いた要望や
  資料。**最初のコミットでは着手前から在ったものが全部入る**)は、クロージャに書かない —
  クロージャは「触った」という主張なので、書けば偽になる。代わりに
  `## 作業コミットに入れた入力` に `- <パス> — <この作業が書いていない理由>` と申告する
  (2026-09-23)。**申告は書いて残す行為なので、書き忘れ(BRC8 が止める抜け)の隠し場所には
  ならない。** それでも理由は機械に確かめられないので、**申告できる場所を機械で絞る**:
  そのコミットで**新しく入った**ファイル(書き換え・削除・改名は作業が触ったのだから申告できない)
  で、**`docs/` の下の、SSOT の4階層と `docs/ux/` の外の、文書か画像**(.md / .txt / .pdf / 画像の
  拡張子)だけである — コード・テスト・設定・SSOT は、`docs/` の下に在っても申告では外せない
  (外せると、BRC8 からも、クロージャだけを見る BRC2 からも消える)。
  理由の無い行・理由が雛形のままの行・クロージャと重なる行も BRC8 が落とす。
  **着手前から在ったコードが作業コミットに入るのは、git 管理を始める最初のコミットを作業に
  兼ねたときである** — 申告では扱えないので、作業の前に人間が最初のコミットを作る
  (`/setup` は `git init` だけでコミットしない。最初のコミットの中身は人間が決める)。
- `check-debt.py` はすべての記録の `state:` と `updated:`、および `docs/sheets/` のファイルを読む。
- verify 系フローは `state:`(`building` のクロージャは判定から除外される — flows.md §3)、
  クロージャ、主張、`critical:`、**そして `## 基本要件の点検`** を読む
  (**誰がその節の何を見るかは `baseline.md` §1 の4 が正である。ここでは言い直さない。**)。
  **例外が1つ在る** — `check-baseline-verdicts.py` は何も拒まない**計器**なので
  「判定から除外する」対象を持たず、`building` を含む**全状態**の記録を意図的に読む。
  除外の規則は verify 系フロー自身の判定にだけ掛かる。

`state` はちょうど3値を取る: `building`(F1 が走行中、または中断)→
`awaiting-verify`(F1 は終わったが、verify 系フローがまだ確認していない)→ `verified`。
**`verified` への扉は `stamps.py promote` だけである**(inspection-14)。
そして判定は**その記録自身のコミット時点**で行う: フローごとに、そのフローの全体スタンプと
この記録の `commit` のあいだで動いた依存を取り、**そのすべてが green(全体または部分)に
覆われているときに限って**記録を進める — だから**記録より*前*に記録された鮮度スタンプでも
昇格させうる**(`flows.md` §2)。
**`verified` への遷移を手で書き換えるスキルは1つも無い** — `awaiting-verify` → `verified` の扉は
`stamps.py promote` の専有である(`building` → `awaiting-verify` は `/build` §5 が自分で書く)。
対象がそのクロージャを決して覆わないフロー(00/01 だけのクロージャは F3 の範囲に入らない)は、
構造的に覆われている: そのフローの依存を1つも動かしていない記録は、その鮮度スタンプに止められない。
**1つだけ、すべての記録を止めるものが在る**: **green の全体スタンプをまだ1度も持たないフロー** —
何も無いところから区間は計算できないので、すべてのフローが最初の green を持つまで `promote` は
待つ(fail-closed)。`updated` は state の変化のたび、進捗メモの1行のたびに動く —
`check-debt.py` はそこから `building` の滞留を測る。
`origin:` は `derived` か `human-report` であり、着手時に証拠から一度だけ決める
(課題票の `found_in: 人間の指摘`、feedbacks の項目、人間自身の要望)。
これが決めるのは**1つだけ**である: エラー処理 / テスト / ログ / 設定を**そもそも問うてよいか**
(`delegation.md` §5)。

**フローが記録を削除することは決してない。** 終わった(`verified`)記録は履歴の材料である。
古い `verified` の記録を刈るのは、人間が明示的に求めたときだけである。
タスクを越えて恒久的に残すべきものは、従来どおりの場所へ行く: 履歴(1タスク1ファイル。
F1 が出口で書く)、決定、feedbacks、03-impl。

## 2. 主張(`## 主張`)

**各主張は、後のフローが確かめられる形でなければならない**: テストや lint の主張は、
コマンドとその最終出力行を逐語で引く(裸の ✓ は散文である)。
**「確かめられる」と「反証される」は違う** ★ — 逐語の引用はどちらにも要るが、
**後から実際に反証する者が居るかは主張ごとに違う**(下の表)。
**外部挙動の変化は3つの値のどれか1つである** ★ — `なし` / `あり(後方互換。…)` / `あり(互換を壊す。…)`。
**この3値は成果物の版の桁を決める**(`flows.md` §9)ので、**自由な言い回しで書かない** — `check-buildrecord.py` BRC4 が値を読む。
**どれを選ぶかの基準**: 呼ぶ側・使う側が**何も直さずにそのまま動き続けるか**。動き続けるなら `後方互換`、直さないと壊れるなら `互換を壊す`、外から見て何も変わっていないなら `なし` である。
critical への接触 あり/なし を、重要な変更のフラグ(`critical:`)と一致させて述べる(BRC2 がパスと突き合わせる)。
**後の verify 系フローが反証した主張は、原則2 が事実の差異を扱うのと同じに扱う**:
現実が勝ち、その矛盾はこの記録を名指してキューへ載る。

**誰が何を反証するかは、その手段で反証できるかで決まる** ★:

| 主張 | 反証する者 | 手段 |
|---|---|---|
| 外部挙動の変化 / critical 接触 | **F3**(`/verify-impl`) | 再生成したコールグラフとコード |
| **`## 基本要件の点検` の 該当 / 非該当** | **F3** | 同上(`baseline.md` §1 の4) |
| 触ったテスト green | **F4**(`/verify-tests`) | **実際に走らせた結果** |
| 資格情報の混入検査(実施 / 未設定) | **F4**(`/verify-tests`) | 基盤を使うなら `f4-unit` が `strict` の下で呼ぶ `secret_scan` ステップ、直に走らせる構成なら `environments.md` のその行のコマンド(どちらでも、未設定なら unit が green にならない) |
| テストの環境の版がビルドと一致(一致 / 不一致 / 未確認 / 未宣言) | **F4**(`/verify-tests`) | 自分の run の前に同じ確かめ方で一致を見る(`delegation.md` §2.4。版の固定を宣言したプロジェクトでは、不一致も未確認も unit / integration / e2e が green にならない。未宣言のプロジェクトでは報告に書くだけで合否に掛からない) |
| lint / build green | **誰も直接には反証しない** ★ | F4 の試験一式が落ちることで**間接的に**露見するだけ。**指針であり、執行者は読み手である** |

**反証しないものに宛先を書かない** ★ — 「誰かが見ている」と読めてしまうからである。
F4 が走らせるのは unit / integration / e2e / qa の4つだけで、**lint も build も試験区分に無い。**
**ただし義務そのものは弱まらない** ★ — `lint / build` を green にすることは
**F1 の先送り禁止のままである**(`flows.md` §6 の1項目目)。宛先が無いのは、
**それを後から反証する者**だけである。

**F3 にテストの主張を持たせない。** グラフからもコードからも判定できないので、
**黙って飛ばされる死んだ行になるか、F4 の最も高い仕事を重複して払うか**のどちらかにしかならない。

## 3. シート(`docs/sheets/<slug>.md`)と転記

決定シートの書式と問う基準は変わっていない(`.claude/templates/sheet.md`、
`delegation.md` §1。機械の検査は `check-sheet.py`)。変わったのは置き場と一生である:

- **問いの前段は構築記録の `## 質問キュー(出口のシートの種)` である**: 下降の途中で
  問う基準を通った論点は、下降を止めずにその節へ1行ずつ溜める(`/build` §2)。出口はその節を
  読み、空でなければ1枚のシートにし、空なら「お伺いする事項なし」と述べる(`/build` §5)—
  **「お伺いする事項なし」の根拠がディスク上に在る**のはこのためである。
  回答を `## 決定シート(回答済み)` へ転記したら、対応する行はキューから消す。
- 決定シート(F1)は `docs/sheets/<slug>.md` に在る。無人の検証フローの質問シートは
  `docs/sheets/questions-<YYYY-MM-DD>.md`(1日1枚 — フローが追記する)。
- **転記してから削除する**: 回答(ファイルからのもの、または日付つきで逐語引用したチャットの
  回答)を構築記録の `## 決定シート(回答済み)` へ転記し — **ブロックごとに結末の行を1つ**:
  回答 / 推奨を承認 / 既定を承認 / 棚上げ — シートのファイルを削除する。
  **ディスクに残っているシートは未回答の問いを意味し**、`check-debt.py` はそれをそう数える —
  **存在した瞬間から、猶予期間なしに**である。「まだ新しい」は答えではないからである。
- **AI が「★あなたの記入」の欄に書くことは決してない。** 逐語引用の捏造は検査の偽造である。
- 「すべて推奨どおり」がすべてのブロックを決着させる。中身が「曖昧さなし」の開示行1つだけの
  シートは、答えそのものが要らない(`check-sheet.py` が免除する)—
  「問いなし(開示のみ)」と記録してから削除する。

**この節が引用される、シートを書く側の規則**(inspection-17 M-4 まで雛形のコメントにしか
存在していなかった — `delegation.md` §1、`/build` §1、`sheet.md`、`/relations` の参照は
ここを指していたので、**ここが束縛する場所である**):

- **根拠の三方向**: 論点の根拠は決して空でない — **上流・同層・下流のそれぞれから1つずつ引く**
  (上流 = それを許す/禁じる条項、同層 = 既存の決定か先例、下流 = その選択が着地する実装や
  テスト)。**三方向が*食い違うこと*自体が論点である**(`delegation.md` §1)。
  三方向を読まずに書かれた論点は、「問う前に導出せよ」の違反として削除する。
- **概念の明確化は最大7件**であり、問う基準の2条件を迂回してよい唯一の節である。
  **まず削る。** 削り方は `delegation.md` §1 が所有する2つである:
  上流が既に答えているものは事実である(決して問わない)。
  実装者が決めてよいものは委任である(決して問わない)。
- **過去の回答の走査**: 論点を立てる前に、既存の決定(`00-requests/decisions/`)、
  構築記録のすべての `決定シート(回答済み)` の転記、そして履歴を grep する —
  **既に答えが在るものを二度問うことは決してない。**
- チャットの回答の転記行(逐語 + 日付)が「返答済み」の証拠である — SH4 の3つ目の合格経路。
  その場合、シートの 記入完了 の欄は空のままでよい。

## 4. 進捗メモと申し送り

**進捗メモは再開点である**: 目に見える成果物が1つ仕上がるごとに1行、
行使した `[DS-nn]` の委任1つにつき1行(**理由と見直す条件を同じ行に** — `delegation.md` §3。
SSOT への開示行は段2/段4 でそれを所有する文書に書き、**記録側の行は、中断したタスクが
それでもそれを見つけられるための道である**)。
**申し送り**が担うのは、このタスクの文脈より長生きするが、タスクそのものではないものである:
並走タスクへの警告、走らなかった独立レビュー、まだ保留されている人間の判断。
残っている仕事を述べるときは、**検査の出力から引用する**(`check-buildrecord.py <slug>`、
`stamps.py check`)。散文で描写しない — **散文は古くなり、検査は古くならない。**
