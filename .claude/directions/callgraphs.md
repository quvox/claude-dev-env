# 03-impl/callgraphs/ — 機械が導けるものだけ

日本語で書く。

## 0. これは何であって、何でないか

`docs/03-impl/callgraphs/` を書くのは**道具だけである**。**AI は1文字も書かない。**

| | callgraphs/ | relations/(機能間連携仕様書) |
|---|---|---|
| 誰が書くか | **道具だけ** | **AI**(コールグラフとコードを読んで) |
| 単位 | **関数とエンドポイント**(コードの構造そのまま) | **機能**(契機とモジュール境界で切る) |
| 中身 | 呼び出し関係、シグネチャ、エンドポイント定義 | 目的、処理の流れ、連携の詳細、異常系、実装上の判断 |
| 判断 | **いっさい無い**(解決できないものは未解決として並べる) | 粒度・畳み込み・どちらが正か以外のすべての判断を行う |
| 決定性 | **実装が変わらない限り1バイトも変わらない** | 人間の読みが意味を変えたときだけ変わる |
| 版 / 検証済み記録 | **無い**(純粋な導出物) | 層を代表して `03-impl/index.md` が持つ |

**コールグラフは仕様ではない。** 関係だけを持つので、そのままでは決して連携の仕様にならない。
**コールグラフのすべての関数をそれぞれ仕様にすることも、同じく誤りである。**

## 1. なぜ分けてあるか

**機械にできることと、AI にしかできないことの境界を、成果物として固定するため**である。

- **中間の成果物が残る**: 実装が変わっていなければコールグラフも変わっていないので、
  AI は毎回コードを読み直す必要が無く、**差分だけを読めばよい**。
  それが「検証のたびにコードを漁って文脈を燃やす」という元の問題への答えである。
- **AI の主張が検査可能になる**: relations が「A は B を呼ぶ」と言ったとき、
  コールグラフの対応する経路と機械的に突き合わせられる(§6)。逆に、
  コールグラフに在って relations に無い連携は**取りこぼしである**。
- **道具の限界が見えるようになる**: REST の呼び出し元のように機械が決められないものは、
  **「未解決」として明示的に並ぶ**ので、**空白が「連携が無い」と誤読されることが決してない。**

## 2. 双方向の流れ

```
既存コード:  コード ──ツール──► callgraphs/ ──AI(コード精読)──► relations/
新規開発:    relations/ ──AI──► 実装 ──ツール──► callgraphs/
                   ▲                                      │
                   └── 不整合 → 実装を直す or relations を更新 ◄┘
```

**機能間連携仕様書は実装と仕様ドキュメントの接点であり、機械生成と AI の作業の混成である。**
グリーンフィールドでは実装が無いので、先にコールグラフを作ることはできない。
relations を先に書き、それに対して実装し、それから
**結果からコールグラフを作って relations と照合する。**

## 3. ファイルの配置

```
docs/03-impl/callgraphs/
├── index.md        # 生成物。言語ごとの Tier・抽出器バージョン・件数・未解決数
├── python.md       # 言語ごとに1ファイル
├── go.md
├── typescript.md
├── rust.md
├── shell.md        # bash/zsh(正規表現抽出。Tier 3)
├── make.md         # Makefile のターゲット(同)
├── infra.md        # API Gateway / ALB のパス転送設定 と API 以外のイベント源
├── boundaries.md   # 言語・プロセスを跨ぐ辺の候補(ツールでは確定できないもの)
└── resources.md    # 資源(テーブル/バケット/キュー/トピック)を誰が触るか
```

**言語ごとのファイルが持つのは、コードから導かれた情報だけである。**
抽出器の版のような道具側の事実は `index.md` **にだけ**入る —
さもないと**道具を上げただけで全ファイルに差分が出て**、
「コールグラフの変化だけをレビューする」が働かなくなる。

### 3.1 どこに生成するか — 常に SSOT

コールグラフは**いまのコードから導かれる**ので、置き場は1つである:
`docs/03-impl/callgraphs/`。フローの模型では段階の側が存在しない —
`/build` は自分のクロージャの中で SSOT を直接書き、**過渡の区間を治めるのは構築記録の state**
(`flows.md` §3)であって、2つ目の出力先ではない。

**誰がいつ再生成するか**:

| 状況 | 生成先 | 誰が書くか |
|---|---|---|
| `/verify-impl`(周期・デプロイ前) | `docs/03-impl/callgraphs/` | `build-callgraphs.py`。**F3 だけが定常の再生成点である** |
| `/relations`(**どのモードでも** — 検査モードを含む) | 同上 | 同上。再生成は判断を伴わずにコードを書き写すので、書き手の閉一覧(原則1)はこれを例外として持つ(`principles.md` §1)。**もう1つのツール生成領域 `feature-graph.md` も同じ扱いだが、書くのは `cluster-features.py` であり、この表の対象外である**(`features.md` §6.1) |
| `/build` | **再生成しない**(先送り禁止の対象外)。触ったモジュールの `relations/` は AI が settle するが、ツール生成領域は F3 に委ねる — 古さは鮮度スタンプの失効として見える | — |

**これを安くしているのが決定性(§4)である**: 変わっていないモジュールは同じバイト列に
再生成されるので、**全体を再生成しても実効的な差分はコードの差分が含意するものそのものになる。**

**出力先を自分で決して決めない。** 解決させて渡す:

```bash
CG_SSOT=$(python3 .claude/scripts/resolve-callgraph-out.py --ssot)
python3 .claude/scripts/build-callgraphs.py --out "$CG_SSOT"
python3 .claude/scripts/build-callgraphs.py --out "$CG_SSOT" --check
```

`--out` は**書込みと `--check` の両方**に効く(書いた場所と違う場所を検査すれば、
報告は嘘になる)。`callgraphs/` のファイルは**コードの代理として立つ道具の出力**である
(CLAUDE.md 原則10)。**手で書かず、検査を通すために編集せず、再生成する。**

## 4. 決定性(この仕組みの前提)

**実装に変化が無ければ、callgraphs/ の中身は1バイトも変わらない。**
**生成の注記は中身ではない。** それは `<!-- BEGIN NOTE: <tool> -->` と
`<!-- END NOTE: <tool> -->` のあいだに在り、**鮮度の比較はその領域を取り除いたファイルで行う** —
さもないと**注記の言い回しを変えただけで、全プロジェクトの全生成物が古い印になる**のに、
実際には何も変わっていない(実測: 1文字で7ファイル)。
**frontmatter は中身である**: その件数はコードとともに動くので、比較に残る。
(`<!-- BEGIN GENERATED: <tool> -->` は逆の仕事をする別の目印である —
手で保守するファイルへ差し込む機械の欄を囲む。**所有する道具は2つに増えた** ★:
索引を書く `build-index.py` と、**事実の機械の欄を書く `build-facts.py`**(2026-08-27。
そちらは `id=<事実の id>` を印に持つ — `conventions.md` §4)。
**道具名は印に書く。どちらの区画かは、その名前で決まる。**)

これを保つ規則:

1. **すべての一覧を辞書順に固定する。** 照合順序は Unicode のコードポイント順である
   (ロケールに依存しない)。ファイル、シンボル、callees、callers、エンドポイント、未解決の項目 —
   **例外は無い。**
2. **行番号を決して書かない。** 番地は `path::symbol` だけである。
   これが「コメントを1行足しただけで至るところに差分が出る」を防いでいる。
   飛ぶには grep / LSP で足りる。
3. **時刻・絶対パス・ホスト名・実行ごとに変わる ID を決して書かない。**
4. 抽出器の版は `index.md` にだけ入る(§3)。
5. 鮮度は**保存せず、検査する**: `build-callgraphs.py --out "$CG_OUT" --check` が
   「いま再生成したら差分が出るか」に答える(`--out` は常に付ける — §3.1)。
   差分が出るならコールグラフは古い。**時刻を持たずに鮮度を保証しているのがこれである。**

## 5. 中身の規則

### 5.1 シンボル ID

`<リポジトリ相対のパス>::<修飾名>`。修飾は**言語によらず `.` で繋ぐ**。

| 言語 | 例 |
|---|---|
| Python | `src/api/auth.py::LoginService.handle` |
| Go | `internal/auth/login.go::Service.Login`(レシーバはポインタ有無を区別しない) |
| TypeScript | `web/src/api.ts::login` / `web/src/App.tsx::App.handleSubmit` |
| Rust | `api/src/routes.rs::build` / `core/src/store.rs::Repo.find_all`(`impl` のメソッドは `<型名>.<メソッド名>`。`#[cfg(test)]` の項目は記号にしない) |

**無名関数とコールバックが独自のシンボルになることは決してない。** その内側の呼び出しは、
**それを囲む最も近い名前つきのシンボルに帰属させる。** それがグラフを安定させ、
relations の「内部ヘルパは畳み込む」という粒度の規則と一致する。

### 5.2 エンドポイント ID

`<METHOD> <パステンプレート>`(例: `POST /v1/auth/login`)。

パスパラメータは言語と基盤で書き方が違う(`{id}` / `:id` / `<int:id>` / `*`)ので、
**照合用の正規化した鍵**を別に持つ: パラメータの区間をすべて `{}` に畳む
(`/v1/users/{user_id}/posts` → `/v1/users/{}/posts`)。表示は元の表記のままにする。
これが無いと、FastAPI のルートを ALB のパス転送規則と突き合わせられない。

### 5.3 同梱された第三者ライブラリは解析しない(全言語)

**Python・Go・TypeScript・Rust で同じ方針である。** リポジトリに同梱された第三者ライブラリが、
コールグラフにも relations にも入ることは決してない。理由:

- **それは我々の実装ではない。** 03-impl は「このシステムが何をするか」の鏡像であり、
  依存の内部は対象外である。
- **名前衝突を量産する。** 実データでは、Lambda レイヤに同梱された urllib3 などが
  シンボルの **46%** を占め、`get` / `read` / `copy` のような一般的な名前で
  大量の偽の `ambiguous` を生んでいた。
- **差分レビューが働かなくなる。** 依存を更新しただけでコールグラフ全体が変わる。

検出は2段であり、**名前に依存しない**:

| 段 | 仕組み | 例 |
|---|---|---|
| 名前 | `excludes`(パス部分一致) | `node_modules/` `vendor/` `site-packages/` `.venv/` `bower_components/` `third_party/` … |
| **メタデータ** | `vendor_markers` — このディレクトリ**直下**に目印が在れば、**そのディレクトリ自身**を丸ごと除外 | `*.dist-info` `*.egg-info` `pyvenv.cfg`(Python) / `modules.txt`(Go の vendor) |

メタデータによる検出がなぜ要るか: 同梱先は**独自の名前**を持ちうる(実データでは
`pip install -t` が `pymodules/` を宛先にしていた)。**名前の一覧は決して追いつかない**が、
`*.dist-info` のような**配布のメタデータ**は名前が何であれ付いてくる。

**`excludes` に属する既知のディレクトリ名(`node_modules` など)を `vendor_markers` に入れては
ならない。** `vendor_markers` に当たると、**当たった項目自身ではなくその親**がまるごと除外される —
だから `node_modules` のようなディレクトリ名を登録すると、**それを含むアプリケーションの
ソースディレクトリが消える**(npm / pnpm では `node_modules/` はソースの兄弟であり、
`node_modules/` を含むディレクトリ自体は同梱物ではない)。既知のディレクトリ名は `excludes` の
仕事であり、そこでは部分一致がどの入れ子の深さでも正しく働く。
実害の記録: 2言語のグラフが、黙って同梱の除外を失っていた。

**決して黙って除外しない。** 除外したディレクトリは必ず `callgraphs/index.md` の
「解析対象から外したもの」の表と、実行時の報告に現れる。
**自分のコードが誤って除外されていないかを人間が確かめるのは、そこである。**

### 5.4 外部への呼び出し

`internal_roots`(設定で名指したリポジトリ内のコード領域)の**外**への呼び出しは、
関数表に書かない(標準ライブラリの呼び出しで埋まった表は読めない)。ただし:

- HTTP クライアントの呼び出しとキューへの publish は**境界辺の候補**なので、
  `boundaries.md` が拾う。
- 外部呼び出しの総数だけが `index.md` に入る。

### 5.5 未解決の呼び出し(決して黙って落とさない)

解決できなかった呼び出し式は**すべて**並べる。分類:

| 分類 | 例 |
|---|---|
| `dynamic` | `handlers[name]()` — 辞書・配列からの動的ディスパッチ |
| `higher-order` | 関数を引数で受け取って呼ぶ |
| `reflection` | `getattr` / `reflect` / `eval` |
| `ambiguous` | 同名候補が複数(**候補を全部書く**) |
| `boundary` | プロセス・言語を跨ぐ(REST / キュー / RPC) |

**空白は「呼び出しが無い」を意味する。「解決できなかった」は必ず未解決の表へ入る。**
**その区別がいったん崩れると、コールグラフ全体が信用できなくなる。**

### 5.6 レシーバの出自を先に決める(Tier 2 の要点)

**同名照合は最後の手段である。** レシーバの出自を先に確定しないと、標準ライブラリの呼び出しが
同名の内部シンボルに当たり、偽の `ambiguous` を量産する。
実データ(2,000シンボル)では、これを飛ばすと**未解決の項目の 94% が偽物**になり、
信号が埋もれた。抽出器はこの順で解決する:

| 順 | 判定 | 例 | 結果 |
|---|---|---|---|
| 1 | import 由来で外部と分かる | `zlib.decompress` / `copy.copy` / `os.environ.get` | **外部**(照合しない) |
| 2 | `self` / `super()` / クラス属性 | `self.validate()` / `super().handle()` / `self.repo.save()` | 内部として精密に解決 |
| 3 | 変数の型が分かる | `x = SomeClass()` / `def f(x: SomeClass)` / `with open() as f` / モジュール直下の生成と別名 | 内部として解決、または外部と確定 |
| 4 | **組み込み型のメソッド名** | `.get` `.items` `.read` `.append` `.encode` … | **外部**(照合しない) |
| 5 | それ以外 | `client.list_users()` | 同名照合。曖昧なら**候補を全部出す** |

**規則5 が照合してよいシンボルの種類は、呼び出しの形で絞る** ★ — レシーバを置く呼び出し
(`x.Name()`)で **`Name` という名前がパッケージ直下の関数に束縛されることが言語上ありえない**
なら、そこで**関数を候補に混ぜてはならない**。Go がそれである: `x.Name` の `Name` は
`x` の型の**メソッドかフィールド**であって、パッケージ直下の関数ではない — 関数を呼ぶ
修飾された形 `pkg.Func()` は import 表を持つ規則1 が必ず先に返すからである。
**Python はこれに当たらない** — `mod.func()` のモジュール属性は関数そのものなので、
あちらは関数を候補に残す。
混ぜたときに何が起きるかは実測されている(2026-08-31): Go の `cmd.Run()`(`*exec.Cmd` の
メソッド)が製品の `func Run(...)` へ確度**「確定」**で解決され、**その1本から偽の到達辺が
111本生えて** `callgraph-check.py` の CG4 が重大度「高」を111件出した。
**確定辺は機能表の「棄却した候補辺」では抑止できない**(棄却が効くのは確度「候補」の辺だけ)
ので、この状態は実装整合フローを構造的に green にできなくする。
**取りこぼしは在る。規則4 とまったく同じ取引である** ★ — フィールドが**関数値**を持ち、
そこにパッケージ直下の関数が**代入されている**ことは在る(`table["x"].Run()`)。
それは名前の束縛ではなく**値の流れ**であり、名前で当てにいけば当たり外れが偶然になるので、
受け手の型が分からないその形からは辺を引かない。偽の確定辺は1本で到達集合を丸ごと汚すのに対し、
こちらは静かな偽陰性1本なので、この取引を採っている。**扱いは規則4 の代償と同じであり、
下の「規則4 の代償を理解すること」の段落がこの2つをまとめて引き受ける。**

**規則4 の代償を理解すること**: 内部のクラスが `get` や `read` という名前のメソッドを持っていても、
レシーバの型が分からない呼び出しからは**辺がまったく引かれない**。
偽陽性が取りこぼしを桁違いに上回るので、この取引を採っている。

**これと規則5 の取引は静かな偽陰性であり、`.claude/directions/features.md` §5
(「在るは狭く、無いは広く」)に対する意図的な例外である — 例外はこの2つで全部であり、
ほかに無い。その上に立つ主張に何を払わせるかは、あちらの §5.1 に在る** —
「無い」(「到達不能」「孤立」「連携なし」)を網羅として報告する前に、それを読むこと。

**同梱された第三者ライブラリは必ず `excludes` に入れる。** Lambda レイヤの `pymodules/` のような
ディレクトリが混ざると、シンボル数が膨らみ、名前衝突が爆発する。
それは `callgraphs/index.md` の「シンボルが集中しているディレクトリ」の表で見つかる。

### 5.7 内部分岐を1つの機能単位として扱う

`lambda_handler` が内部で分岐するとき — 例えば
`if cmd == "CREATE": ... elif cmd == "BULKCREATE": ...` — **分岐ごとに合成シンボル
`<関数名>#<値>` を作る。** 要点は、名目上の関数ごとではなく*実効的な*機能の実装ごとに1単位に
することであり、これによって relations の `impl:` が分岐を直接指せる
(`app.py::lambda_handler#CREATE`)。

- 辺はディスパッチャ本体から各分岐へ引く。分岐の先の呼び出しはその分岐に属する。
- 分岐の前後の共通処理(認可の確認など)はディスパッチャ本体に残る。
- 検出する変数名は設定の `dispatch_variables` から来る
  (既定: `cmd` / `command` / `action` …)。`match cmd: case "X":` と
  `if cmd in ["A","B"]:` も拾う(後者は `#A|B` として)。
- 入口の関数名は `entrypoint_functions` から来る(既定: `lambda_handler` / `handler`)。
- **ガード節を分岐と読ませないための宣言が在る** ★(2026-08-25。ct_matchsupport の課題票 243)。
  `cmd in <集合>` という綴りは、**機能の分岐**でも**要求を弾く前段**でも同じ形になる:

  ```python
  # 前段(実在しない入口を1つ作る)                  # 本物のハンドラ(VIP だけ別扱い)
  if route == APPLICANT and cmd in IDENTIFIED \      if tenant == "vip" and cmd in ("A","B"):
          and not p.get("applicationDataId"):            return vip_batch(p)
      return err(...)                              if cmd == "A": return ordinary_a(p)
  elif cmd == "CHECK_PAYMENT": ...                 if cmd == "B": return ordinary_b(p)
  ```

  **どちらも「追加条件つき」で「値が細かい分岐にも在る」。形では区別できない** —
  自動で落とす規則を書くと、右の**本物の入口が消える**(2026-08-25 の独立検査が反例で示した)。
  **「本文がその場で返すだけなら入口でない」も採れない** — 本物の分岐も `return handler(p)` の
  1文だけであることが普通である。
  **区別しているのは「その分岐が機能か」という意味であり、それは人間の合意事項である**
  (`features.md` — 機能表の行は人間のもの)。だから**機械は決めず、宣言を強制する**:

  ```jsonc
  // .claude/scripts/callgraph-config.local.json
  // ★ `languages` の中は**キーごとに置き換わる**(和にならない。`cgx/base.py` の併合)。
  //    和になるのは最上位の 6 キー(excludes / *_markers / *_roots)だけである。
  "languages": {"python": {"dispatch_guards": [
    "backend/.../app.py::lambda_handler#CHECK_PAYMENT|PAY_BY_CONVENI|PAY_BY_CREDIT_CARD"
  ]}}
  ```

  **貼るのは FT2 の指摘の「根拠」欄が出す*ハンドラのID*である** ★ —
  `ハンドラ: backend/…/app.py::lambda_handler#A|B|C` の値のほうであって、
  **「対象」欄の `dispatch A|B|C @ backend/…/app.py::lambda_handler` ではない**(形が違うので
  当たらない)。**値は辞書順に並ぶ** — `#B|A` と書いても当たらない。
  **宣言した分岐の本文はディスパッチャ本体に残る**ので、ガードの中の呼び出し(エラー応答など)は
  辺として消えない。

  **効くのは「値」の単位である** ★ — 同じ値の分岐は先に1つへ畳まれているので、`#A` を宣言すると
  `if tenant == "vip" and cmd == "A"` と `if cmd == "A"` の**両方**が落ちる。
  **だから、値が本物の分岐と同じガードを宣言してはならない。そしてその必要も無い**:
  値が同じなら入口は1つに畳まれ、**偽の入口はそもそも生まれず**、ガードの中の呼び出しは
  その機能に帰属して正しい。**宣言してよいのは、FT2 が偽物として指摘した値だけ**である
  (その値は機能表に行を持たない)。

  **落とした宣言と、効かなかった宣言は、生成物の「解析対象から外したもの」の表に出る** ★ —
  綴り違い(パス・関数名・値の順序)や、コードから消えたガードを**黙って見逃さない**ため
  である。**表に「効かなかった宣言」が並んでいたら、宣言を直すか消す。**
  `entrypoint_functions` の外の関数へ書いた宣言は FT2 には現れないので、
  **この表がその唯一の目である。**
  **放っておくと止まるのは F3 である**: 機能表にその行が無いので FT2 が重大度「高」を出し続け、
  鮮度スタンプが green にならず、デプロイゲートが閉じない。**機能表に行を足す道は勧めない** —
  行は人間の合意事項であり、ガード節に機能の身分を与えることになる。

### 5.8 Tier(どこまで信じてよいか)

抽出の精度は環境に依存するので、**その run がどの Tier を使ったかを必ず印字する。**

| Tier | 手段 | 保証 |
|---|---|---|
| 2 | tree-sitter / `ast` による構文解析 + 名前解決 | 同名衝突は `ambiguous` として候補列挙。**既定** |
| 3 | 正規表現 | 定義とエンドポイントのみ。**呼び出し関係は不完全**と明記される |

**Tier 3 の結果を「網羅した」と決して報告してはならない。** Tier は `index.md` と各ファイルの
frontmatter に現れる。relations を書く AI は、**主張の強さを Tier に合わせて調整する。**

**型解決による Tier 1 は意図的に持たない。** 言語のツールチェーンによる型解決は名前衝突による
偽の辺を消せるが、**この仕組みの目的に対して投資対効果が最も悪い**:

- 目的は**モジュール境界での連携の理解**であって、関数単位の完全なコールグラフではない。
- **偽陽性のほうが偽陰性より良い**(`.claude/directions/features.md` §5)。Go(2,839辺)での実測で、
  Tier 1 が消した偽の辺は30本 — **この基準では消す価値が無い**。足した本物の辺139本のうち、
  境界を越えたものはごくわずかだった。
- **対象プロジェクトがビルドでき型検査できることを前提にする**ので、CI とコンテナで失敗する。
  **精度が環境で変わる仕組みは、検査の再現性を壊す。**
- 曖昧さは**候補を全部出す**ことで扱う(§5.5)。候補辺は機能表のクラスタリングの到達性の計算に
  数えられるので、**Tier 1 が無くても境界は失われない**(`features.md` §5)。

名前衝突で使い物にならないリポジトリに当たったら、Tier 1 を足す前に
**`excludes` / `vendor_markers` の設定漏れを疑う**(実際にそれが原因だった)。

### 5.9 道具立ての準備 — 規範は3つ。操作は `tools-readme.md`

**コマンド、何がどこに入るか、Tier の表は `.claude/tools-readme.md` §1、
困ったときの対処はその §6 が持つ**(運用の入口。原則10)。ここには書き写さない。
*この*ファイルに属するのは、抽出そのものが守るべき3つの規則である:

- **キットは、対象プロジェクトの環境にもホストにも何も入れない。** 道具の依存は
  **キット専用の venv(`.claude/.venv`)**に閉じ込め、`.claude/.venv` / `.claude/.tools` は
  git の外に置く。理由: 道具の都合がプロジェクトの依存やホストを変えると、
  **誰の都合が何を壊したのか分からなくなる。**
- **対象プロジェクトがビルドでき型検査できることを決して前提にしない**
  (理由と、Tier 1 を持たない理由は §5.8。ここには書き写さない)。
- **必須依存が無いとき、道具は起動時に直し方を1行言って止まる** — **決して黙って精度を落とさない。**
  `tree-sitter` / `PyYAML` は `go` / `typescript` / `rust` / `infra` に*必須*であり、正規表現の縮退経路は持たない。
  **コードの半分が見えないグラフで verify の run を完走させることは、このキットが他の
  すべての場所で拒んでいる fail-open だからである**(inspection-17 判断1)。
  ある言語を解析しない選択は、`callgraph-config.local.json` の明示的な `enabled: false` である。
  設計として縮退するのは shell / make だけであり(正規表現のみ、Tier 3、外部依存なし)、
  **その Tier は常に報告される。**

### 5.9.1 解析しないもの — テストと開発ツール

**本番実行系から到達しないものは解析しない**(試験は `features.md` §0.1)。
`test_markers` / `include_tests` と、**同じ仕組み**である
`tooling_markers` / `include_tooling` が落とす。

| キー | 落とすもの | 既定 |
|---|---|---|
| `test_markers` | テスト本体・フィクスチャ | `test_` `_test.` `.test.` `.spec.` `/tests/` `/test/` `/__tests__/` `/e2e/` |
| `tooling_markers` | Makefile・CI 定義・compose・devcontainer | `Makefile` `.github/` `.gitlab-ci` `.circleci/` `.devcontainer/` `compose.yaml` `docker-compose.` ほか |

- **目印そのものの形が、照合の仕方を決める**(`base.is_test()`。**リポジトリ相対のパス**に対して)。
  だから**目印の書き方で規則を選ぶ**:

  | 目印の形 | 照合 | 例 |
  |---|---|---|
  | **前後が `/`** | **ディレクトリセグメント**(直下にも当たる) | `/tests/` `/test/` `/e2e/` |
  | それ以外で `/` か `.` を含む | **部分文字列** | `_test.` `.spec.` `.github/` `compose.yaml` |
  | どちらも含まない(裸) | **basename の接頭辞だけ** | `test_` `Makefile` |

  **どちらの書き方も、逆向きの実害から来ている**:

  - **裸の目印が部分一致したことで、本番のコードが落ちた** — `test_` が
    `src/contest_handler.py` と `src/latest_report.py` に当たった
    (`KIT-marker-substring-false-positives`)。**接尾辞**として当てたい目印は、
    だから区切りを持たねばならない: `spec` ではなく `_spec.` と書く。
  - `/tests/` が素朴な部分一致だったことで、**リポジトリ自身の最上位のディレクトリを取り逃した** —
    `tests/conftest.py` が解析に残り、恒久的な FT2 の偽陽性になった
    (`KIT-leading-slash-dir-markers`)。`/foo/` の目印はいま `/` + パスに対して照合されるので、
    `foo/…` にも `…/foo/…` にも当たり、それでも `bar_foo/…` には当たらない。
- **先頭の `/` は「ディレクトリ名まるごと」を意味するのであって、「リポジトリの根に錨を打つ」では
  ない。** だからディレクトリの目印は**両端**にスラッシュを付けて書く(`/e2e/`)。
  片側だけだと部分一致である: `.github/` は根にしか現れないディレクトリには正しく、
  `/e2e` は `src/foo/e2e_helpers.ts` にも当たる部分文字列になってしまう。
- **`scripts/` `tools/` `bin/` を既定に入れてはならない。** 本番のコードがそこに置かれることが
  あり、それを落とすと **FT2 の取りこぼし検出そのものが黙って働かなくなる。**
  プロジェクト固有の項目は `callgraph-config.local.json` の `tooling_markers` へ入れる
  (**配列は和として併合される**)。
- **落としたものを言わずに済ませてはならない。** 言語ごとの件数が `callgraphs/index.md` の
  「解析対象から外したもの」に入る。**黙って落とすことが「網羅した」という誤読を招く。**
- `include_tooling: true` にすると昔の収集の挙動に戻る
  (**FT2 の恒久的な偽陽性つきで**)。

### 5.10 boundaries.md — 道具が決められない辺

**道具に REST の呼び出し元は特定できない。** それが機械の限界であり、AI が埋める境界である。
それでも機械にできる範囲で**候補**は出す:

| 種別 | 出し方 | 確度 |
|---|---|---|
| http | HTTP クライアント呼び出しの URL リテラルを、エンドポイントの正規化キーと突合 | 一致すれば `候補`、変数組み立てなら `未解決` |
| iac | API Gateway / ALB のパス転送 → 転送先(Lambda / ターゲットグループ / サービス)→ ハンドラのシンボル | 設定から辿れれば `確実` |
| iac | **API 以外のイベント源**(SQS/SNS/ストリーム/定時/S3/EventBridge/Cognito)→ ハンドラのシンボル | 設定から辿れれば `確実` |
| queue | publish 側の名前リテラルと、**そのキュー/トピックで起動されるハンドラ**を突合 | 一致すれば `候補`(非同期なので到達は断定しない) |

そして常に、**呼び出し元を特定できなかったエンドポイントの一覧**を出す —
その一覧が、文字どおり AI へ渡された宿題である。
**イベント源を読まない限り、キュー・ストリーム・定時起動で駆動される機能はその一覧に永久に
残る**(既知の入口を持たないので機能表にも決して届かず、その先はすべて「到達不能」になる)。

### 5.11 resources.md — 呼び出し辺としては存在しない連携

**サーバレス / イベント駆動のシステムでは、連携のかなりの割合が、原理的に呼び出し辺として
存在しえない。** A がテーブルへ書き、B がそれを読む。呼び出しは1つも無いのに、
**B は A の形式に依存している。** この結合はコールグラフにも boundaries にも現れないので、
**CG4 の取りこぼし検出の網はそこに一切触れない。** `resources.md` が資源の側からそれを埋める。

**資源結合を relations のどこに書くか — この節がその規則を所有する。**
**決して `callees` には書かない**: それは呼び出しではなく、そこに書くと対称性の検査と CG3 が壊れる。
書く場所は**本文**である: 書く側は「戻り値・副作用」の下に(書き込むテーブル・バケット・
キュー・トピックを名指す)、読む側は「連携先と連携内容」の下に(資源を名指し、その契約を指す)。
CG7 が見られるのは、**本文に資源名が現れているかどうかだけ**である(§6)。

**2つ以上の機能が共有する資源の形式は、SSOT をちょうど1つ持つ: `CTR-*` の契約**であり、
`kind` は `storage` / `data-schema` / `event` のうち適切なものにする。
生産する側と消費する側の MODULE 文書は、どちらも `contracts:` に同じ ID を並べる。
散文は資源と目的を名指すが、**欄・型・必須かどうか・既定値・順序・互換の規則を書き直さない。**
02 と 03 の契約の対と、両側の参照は**同じタスクで作る。**
1機能に閉じた形式は、その MODULE 文書に留めてよい。
`resources.md` は**どの資源名を誰が触るか**についての、機械が導いた SSOT のままである。
**手書きのスキーマ登録簿になることは決してない。**

**資源の識別子は「触られている名前」でよい。** リテラルでも、環境変数の名前でも、
定数の名前でもよい。**実名へ解決できるならする**が、
**できないときに捨ててはならない** — 同じ環境変数を読む2つのモジュールは、
その先の実体が何であれ結合している。それが「偽陽性のほうが偽陰性より良い」
(`features.md` §5)のもとで正しい振る舞いである。

| 表記 | 意味 |
|---|---|
| `{}` | 変数で組み立てられた区間(`"caseDataTbl" + os.environ["HASHSALT"]` → `caseDataTbl`)。**先頭と末尾の `{}` は落とす** — 落とさないと同じテーブルが `orders` と `orders{}` に割れて結合が消える |
| `$VAR` | 実資源に解決できなかった環境変数 |
| `#Logical` | 実名の分からないインフラ資源・定数 |

アクセスの種別は操作の名前から決める(`get` / `query` / `scan` → 読み、
`put` / `delete` / `publish` → 書き)。決着している判断が2つ:

- **環境変数を読むこと自体は `unknown` である。** それは資源がどう使われるかについて何も言わない。
- **`permission`(IAM 由来)は結合として数えない。** それは使用の証拠ではなく、
  **許されていることの上限**である。`Resource: '*'` はどの資源も特定しないので使わない —
  **件数だけを報告する。**

**濾し落としたものの件数を必ず報告する。** 実資源へ解決できなかった環境変数のうち、
名前が `resources.env_patterns` に当たらないものは資源として扱わない —
その濾過が無いと、全モジュールが読む変数(`DEPLOY_ENV` のような)が
「全機能が触る資源」になって信号を埋める。**除外した件数と上位の名前は必ず `resources.md` に
現れる**ので、実在する資源は設定へ足すこと。

**TypeScript は資源参照を出さない**(意図的である)。フロントエンドはデータストアを直接
触らず REST の境界を通るので、そこは `http` の boundaries が覆う。

## 6. 機能表・relations との照合(`callgraph-check.py`)

**機能間の関係は `cluster-features.py` と同じ実装で導く**(二度実装することは決してない)。
入口は**機能表**が定義し、機能ごとに到達集合を計算し、機能を跨ぐ辺を出す。
アルゴリズムとその一意性は `.claude/directions/features.md` と
`callgraph-design.md` §8.3 に在る。

```
入口: roots(F) = 機能表 F 行の「入口」をシンボルに解決したもの
到達: s ∈ reach(F) ⟺ roots(F) から s への経路があり、中間ノードが1つも他機能の入口でない
辺  : F → G ⟺ reach(F) の中から roots(G) を呼んでいる (u,v) が在る
```

**機能表が無いときは、relations の `impl:` を入口とみなして走る**(導入の途中で検査が止まらない
ようにするため)。その場合 FT2〜FT5 は検査されず、**そう言う。**

**どの検査 ID が存在するかを述べるのは道具であって、規範ではない** —
`callgraph-check.py --list` が、検査器自身が使う唯一の `CHECKS` の対応表からそれを印字する。
**「CG1〜CGn」のような範囲をどこにも書かない**: CG5 は FT2 に吸収されて欠番なので、
**どの範囲もどちらかの向きに誤りになる**(18箇所が `CG1〜CG7` と `CG1〜CG6` に割れていた)。
「FT/CG 検査」と書くか、意味する ID を個別に名指す。
**下の表は各検査が*何を意味するか*を所有し、*何が存在するか*は道具が所有する。**

**下の表は意味と既定の対処を一緒に持つ。** 分けると必ずずれる —
CG4 の意味は「取りこぼし」であり、その対処は「`callees` に追記する」であって、
**同じ主張を言い換えただけである。** フローごとに変わるのは**修正がどこに着地するかだけ**である:
**`/build` §4 は自分のクロージャの文書とコードを直し、`/verify-impl` は SSOT をリポジトリ全体で
直す。** スキルはその1行を持ち、この表を引く。

| ID | 検査 | 不一致が意味すること | 既定の対処 |
|---|---|---|---|
| FT1 | 機能表の全入口が callgraph に実在し、重複が無い。**ただし抽出器が無い言語の入口**(`::` の前のファイルの拡張子を、シンボルを出す抽出器のどれも設定で名乗っていない、かつそのファイルが実在するもの。**今回出たシンボルからは決めない**。テスト・開発ツールの目印に当たるもの・重複は除く。実装は `cgx/base.py` の `unextracted_symbol`)**は FT1 にせず、「未検査」として件数を出す** — callgraph に無くて当然のものを「実在しない」と言うと、その言語を含むプロジェクトでは以降の検査が永久に走らない。その機能の辺・到達は辿っていないので、`feature-graph.md` にも未検査として名指し、その機能が `impl` で所有するシンボルの CG2 にも但し書きを付ける(`check-contracts.py` の CT6 も `x-impl` に同じ判定を使う。CG1 の `impl` の飛ばし方は従来のまま — 判定はこれと同じではない) | 機能表が古い / 表記の誤り。**これが落ちたら以降は検査しない**(誤ったクラスタで指摘を出す方が有害) | 入口の表記を実態に合わせる(機能表は SSOT — 直すのはクロージャに持つ /build か、事実の差異として /verify-impl)。**再生成待ちの区間の中の FT1 は §6.1 を見る** |
| FT2 | callgraph の全エントリポイントが、いずれかの機能の入口である。**ただしテストと開発ツール(`test_markers` / `tooling_markers`)由来の入口は数えない** — 機能表に載せてはならないものを取りこぼしと呼ぶと、規範上どうやっても消せない指摘になる(`features.md` §0.1。実装は `cgx/features.py` の `missing_entrypoints`) | **★機能の取りこぼし**(旧 CG5) | 機能表に行を足し、relations を1本足す。**ただし、その入口が抽出の作った偽物(ガード節)なら行を足さない** — `dispatch_guards` に宣言して落とす(§5.7) |
| FT3 | 機能表の機能ID と `relations/MODULE-*.md` が 1:1 | 片方だけ存在 = 未記述または孤児 | 片方だけ作った/消した。両方揃える |
| FT4 | 機能表の `所属` が 02 のモジュール分割定義に実在する | 分割定義との乖離 | `所属` を直すか、02 起点の変更として挙げる |
| FT5 | **入口を網羅宣言したファイル**(同じファイルのシンボルIDを2件以上入口に並べた統合行 — `features.md` §2 — で、かつ未宣言のシンボルがどれも機能から到達しないもの)に、機能表が知らないシンボルが無い | **★入口の取りこぼし**。FT2 が見られるのは endpoints だけなので、**画面ハンドラのようにエンドポイントを持たない入口**は落ちても FT2 に掛からず、`feature-graph.md` の「どの入口からも到達しない関数」に静かに積まれる(実測: Vue 画面1枚の入口が 23 のまま実装が 37 になり、14 件が未到達に化けていた) | 機能表のその行に入口を足す(**再生成待ちの区間の中は §6.1**)。実装側の死にコードだったなら消す |
| CG1 | `impl:` の全シンボルが callgraph に実在する | relations が古い / シンボル名の誤り | 表記の誤りなら relations を直す。実装が違うならどちらが正かを判断する |
| CG2 | どの入口からも到達しないシンボル | 到達不能コード候補(**削ってよいかは決めない**)。入口の登録漏れも疑う | **入口の登録漏れを先に疑う**。違えば §7 の最後の箇条(事実はコードで決着させ、問う基準で振り分ける)に従う — **判断できなかったこと自体は問う理由ではない** |
| CG3 | `A.callees ∋ B` に対応する辺が存在する | **relations が実在しない連携を主張している** | **実装漏れの疑い**。まず実装を確認する |
| CG4 | 機械が出した辺 `A→B` が `A.callees` に宣言されている | **★取りこぼし**。この仕組みの目玉 | `callees` に追記する。意図しない依存なら実装を直す |
| CG4(確度が「候補」) | 同上(名前衝突の候補で繋がった辺) | 実在しないことがある | **コードを読んで採否を決め、理由を残す**(棄却も可)。採るなら `callees` へ、棄却なら機能表の「棄却した候補辺・確認済みの境界辺」節へ — レポート限りの棄却は次回また候補として戻る |

**「低(断定できない)」の CG3 は、道具が未解決の呼び出しの向こうを見られなかったことしか
意味しない。** コードを読み、判断し、根拠を本文に書く。
**呼び出しの有無は事実なので、コードが決着させ、あなたはそれを報告する**(原則2)。
コードが決着させられないところ — 両側の*意図*が衝突するところ — でだけ、両方を記録して
問う基準で振り分ける。**決して自分でどちらかに寄せず、
「判断できなかった」を問う理由として決して扱わない**(§7 の最後の箇条が正である)。

**確度の扱い**(`features.md` §5 の「在るは狭く、無いは広く」の帰結):

- CG3 は、`候補` の辺で繋がっているときは**報告しない**(候補も宣言を支えている)。
- CG4 は確度 `確定` で「高」、`候補` で「中」である。候補辺は名前衝突だけで繋がっていることが
  ありうるので、**AI がコードを読み、採否を決め、理由を記録する。**
  **根拠に Tier 3 の言語(または言語を決められないシンボル)が絡む辺は「参考」へ落ちる —
  辺ごとであって、リポジトリごとでは決してない**: shell / make は常に Tier 3 なので、
  リポジトリ全体で落とすと、**精密に解析された言語についても CG4 が至るところで恒久的に黙る**
  (inspection-17 判断2)。
- CG2 と FT2 は候補辺を数に入れて判定する(**「無い」の主張は最も広い基準を使う**)。
- **FT5 はその同じ「無い」に乗っている**ので、Tier 3(正規表現で抽出された)言語のシンボルが
  絡むと「中」へ落ちる(`features.md` §5.1 — そこでは「到達しない」こと自体が取りこぼしで
  ありうる)。その適用範囲は、**実測された欠陥を捕まえる最も狭いもの**に意図的にしてある:
  **入口を統合したファイルに限り、かつ未宣言のシンボルがどれも到達不能な場合に限る。**
  どちらかの条件を広げると、**ハンドラの隣に座っている死にヘルパがすべて「取りこぼし」になる** —
  このプロジェクトでの実測で偽陽性15件であり、**検査そのものが仕事を止めるものになってしまう。**
- **CG7 は `callees` を見ない** — 資源結合は呼び出しではない。その規則と書く場所は **§5.11** に在る
  (ここには書き写さない)。
  広く共有された資源は所見から除外する — 全機能の半数より多くが触り、**かつ8機能以上が触る**もの
  (`ubiquitous_min` の既定。`callgraph-config.json` の `resources` の節で上書きできる。
  両方の条件が要る)— **件数だけを報告する。**

**境界辺(REST やキューを跨ぐもの)はコールグラフでは決められない**ので、
`boundaries.md` の候補と照合する。候補も存在しないなら **「AI の主張・根拠要」**として並べ、
**コードを読んで自分で確認する** — どの行が HTTP を呼び、どの行がメッセージを積むのか —
そしてその `path:line` を relations の本文に書く。
**根拠は事実なので調べるものであり、決して人間に出すものではない**
(`.claude/directions/delegation.md` §1)。何も見つからなければその主張は根拠を欠く:
**理由とともに辺を落とすのであって、上へ上げるのではない。**
**確認したことは機能表の「棄却した候補辺・確認済みの境界辺」の節に記録する** —
さもないと同じ辺が次の run でまた争われる。

**どちらが正かを決める検査は無い。** 検査は事実の食い違いを表に出すだけである(CLAUDE.md 原則2)。

### 6.1 フローの模型における `cluster-features.py` — この節がその規則を所有する

`cluster-features.py` は機能表を SSOT から読む。フローの模型では、`/build` がその表を直接編集し
(自分のクロージャ)、**グラフを再生成しない** — だから構築の出口と**次の再生成**の
あいだ、`--check` は正当に「古い」と報告し、退役・改名した入口の行は **FT1 として終了コード1 に
なる — 仕様であって欠陥ではない。** **及第ラインがこの区間を正当にしている**:
その古さは、失効した `verify-impl` の鮮度スタンプが表示しているものそのものである。
**区間を閉じるのは、`/verify-impl` §1 の再生成か、それより先に走った `/relations` である** ★ —
`/relations` は**どのモードでも**ツール生成領域を再生成するので(原則1)、
区間の終わりを `/verify-impl` に固定して書いてはならない。
**区間の途中の終了コード1 は「まだ再生成されていない」と読み**、古いグラフから何も決めず、
FT / CG の所見を裁定する前に再生成させる(F3、または `/relations`)。

**グリーンフィールドの最初の構築**: 機能表はまだ空の雛形なので、`cluster-features.py` は
終了コード2(「機能表が空である」)になる — **想定どおりである。**
表に行が入った後の最初の再生成(`/verify-impl`、または先に走った `/relations`)が、
最初のグラフを作る。

**この節を引く側は、決して書き写さない**: `/build` §4、`/verify-impl` §1、
`/relations` の検査モード。

### グリーンフィールドでの扱い

実装の前にはコールグラフが無い。`callgraph-check.py` は:

- コールグラフが無い → 「実装前のため未検査」と報告して正常に終わる(エラーではない)
- relations は在るが実装がまだ無い機能(`/build` の途中、または 02 で宣言された未実装)は
  CG1 / FT1 の所見として表に出る — **`building` のクロージャの中では、それは正当な過渡であり**
  (`flows.md` §3)、エラーではない
- 実装の後は、素の run(モードのオプションは無い)がすべての検査を回す。見つかった不整合を解決すること —
  **実装を直すか relations を更新するかで** — が `/verify-impl` の中核の仕事であり、
  `/build` §4 が先に自分のクロージャを決着させる

## 7. 決してしてはならないこと

- **callgraphs/ を手で編集すること。** 次の再生成で消える。直すなら、抽出器かコードを直す。
- **callgraphs/ を relations の代わりに使うこと。** 関数表は仕様ではない。
- **未解決の項目を空のままにすること。** 「解決できなかった」と「呼び出しが無い」を
  決して混同してはならない。
- **Tier 3 の結果について「網羅した」と言うこと。**
- **コールグラフに無いというだけで relations の記述を消すこと。** 動的呼び出しかもしれず、
  外部への参照かもしれず、道具が対応していないだけかもしれない。**コードを読んで決着させる** —
  呼び出しの有無は**事実**である。コードが決着させられないところでは、両側を記録して
  問う基準で振り分ける(`.claude/directions/delegation.md` §1):
  **「判断できなかった」は、それだけでは問う理由にならない。**
