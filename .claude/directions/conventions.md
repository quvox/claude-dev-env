## 1. すべての文書に共通すること

- Markdown + YAML frontmatter(`id`/`version`/`updated`/`source`/`summary`/`keywords`。
  `verified` は verify 系フローだけが書く)。**`id` は `docs/` 全体で一意**である —
  同じファイル名が層をまたいで現れるとき、`id` が層を名乗る(`01-system` / `02-system`)ので、
  層をまたぐ grep が両者を見分けられる。**意図的な例外: 契約は1つの `id` を共有する** —
  `02-design/contracts/` と `03-impl/contracts/` で同じ `id` を持ち、それが `CTR-*` の
  突き合わせ鍵になる(`check-contracts.py` が frontmatter の `id` から作る)。層はパスが名乗る。
  各層の `index.md` も同じ例外である(雛形が `id: index` を持ち、生成された索引は frontmatter を
  そもそも持たない — 層はパスが名乗る)。**UX 文書(`docs/ux/`)も意図的な例外である** —
  frontmatter は `id` / `updated` / `summary` だけを持ち、`version` と `verified` を持たない
  (あの置き場は検証連鎖の外に居て、鮮度は文書の検証済み記録ではなく qa 試験区分の
  鮮度スタンプが持つ — `.claude/directions/ux.md`)。**1つの層の中では、同じ理由で `id` が種別を名乗る** —
  `03-impl/tests/` の下のファイルはすべて `tests-` を頭に付け(`tests-cli`・`tests-e2e`)、
  `03-impl/contracts/cli.md`(`03-impl.md` の tests 規則がこの接頭辞を所有する)と衝突しない。
  **frontmatter のコメントは行まるごとだけ** — 値の後ろに `# コメント` を書くと、パーサによって
  解釈が3通りに割れる。
- **曖昧語と程度の語は全層で禁止**(「適切に」「正しく」「高速に」「ほぼ」「長めに」「十分に」…)。
  数・条件・具体例を書く。(CS8 が見る。**00-requests の本文 — 人間の言葉 — は機械検査の対象外**)
- 受け入れ基準は **EARS**(WHEN / IF…THEN / WHILE / WHERE + SHALL)で書く。
  各条項は動かない ID `FR-<domain>-nn-#` を持つ。
- **REST API の契約は OpenAPI 3.1** で書く。表でも散文でもない。REST でない契約は、型・必須か
  どうか・既定値・エラーを持つ表にする。
- 図は Mermaid。**文書を分ける引き金は並走の単位であって、バイト数ではない。分割を強いる
  バイト数の上限は持たない。**(**書きすぎを抑える上限は別物で、そちらは生きている** —
  `03-impl.md` の `relations/MODULE-*.md` 1本 4,000 バイトは、既定では超えたら**削る**上限であって、
  分割の引き金ではない。バイトが減る上限と、バイトが減らない上限は、別の道具である。
  **掛かるのは実装が無い時点の本文だけで**、実装済みモジュールの整合確認が済んだ後の本文には
  当たらない — 範囲の正は `03-impl.md` である。**削れないとき(必須の小節と衝突したとき)に
  どちらを優先するかも、同じ節が定める** — ここには写さない。)
  クロージャは**パスの集合**なので、2つの作業指示が1つのファイルを共有している
  かぎり非交差は証明できず、直列にしか流せない(`orchestration.md` §3.4)。だから問うのは
  「大きいか」ではなく「**そこが別々の作業指示の対象になったか**」である。
  **その問いは層ごとに形を持つ**:
  **01 の `functional.md` は業務ドメインで切る**(`01-requirements.md`)— 作業指示は業務の単位で
  来るので、ドメインがそのまま並走の単位になる。
  **02 のモジュール詳細は、切るならモジュール単位で切る**(`02-design.md` が正)— このキットでは
  クロージャがモジュール単位で立つので、**モジュールが並走の単位そのもの**である。
  **ただし 01 と違って、これは命令ではなく判断である**: 切る引き金となる数字は無く、
  **既定は「切らない」**である。切る理由になるのは「切ることで初めて並走できるようになる」
  ときだけで、**いま並走させたい仕事が無いなら切らない**(切る費用は参照の張り直しであり、
  それは並走で取り返すものだからである)。**判断するのは人間だけではなく、AI も検討する。**

  (大きすぎるかどうかの判定は relations 15 本 — `02-design.md`。**これはモジュールの切り方の
  見直しであって、設計書を分ける引き金ではない**)。

## 2. SSOT に何を書くか(`.claude/directions/core.md` §1)

**厳密さは逆ピラミッドで配分する**: 00〜01 は試験可能であることを求められ、02 は境界・契約・決定を
記録し、03 は**コードだけからは意味が安定しない/自明でない**実装上の事実を記録する。
SSOT は**人間が読める仕様と決定の記録**であり、コードは完全な実行可能記述である。
両者は補い合うものであって、代わりになるものではない。

SSOT は、実装の細部から意図を再構成させることなく、保守する人に次を見つけさせなければならない:
(a) 外から観測できる正常・異常・境界の振る舞い、(b) 所有の境界と、境界をまたぐ契約・共有資源の形式、
(c) 破れると金・データ・権限・監査可能性を失う状態遷移と不変条件、(d) その境界や制約がなぜ在るのか、
いつ見直すのか、(e) 検証の手順、受け入れの証拠、切り戻しの条件。
**コードに機構が在っても、これらは書く。** 関数ごとの流れ、内部の分岐、ファイル一覧、
道具が導ける構文は、**重複して書かない**。それ以外の文が SSOT に属するのは、
**何かを制約する / 変えるのが高くつく / 所有の境界をまたぐ / 検証に要る**のいずれかのときだけである。
残りは実装者の自由であり、既に委任されている(原則4)。

- **新しく書き足す文は、表の綴りで書く。** これだけが常に掛かる。

**機械検査は括弧の幅も語のあいだの空白も見ていない** — 見分けるには地の文とコード例を

### 3.1 「純粋な英語」も「純粋な日本語」も成立しない

**到達点は異言語の語がゼロになることではなく、残る異言語の語がすべてこの節に載っていることである。**
ここに無い混在は違反である。
**地の文の判定から外すものを「引用島」と呼ぶ。** 言語の判定(LA1・LA2)はここを見ない:

- コードフェンスとインラインコード
- frontmatter と HTML コメント
- `「」`『』の引用
- パス・URL・ファイル名・長オプションとその値
- 識別子(`DS-01` `BR-01` `CS8` `F1`〜`F4` …)・`原則n`・`§n`
- frontmatter の値(`building` / `awaiting-verify` / `verified`)と、スクリプトが出力する語
  (`green` / `red` / `PASS` / `FAIL` / `OK` / `NG`)
- 雛形の差し込み記号(`<...>`)

**引用島が免除するのは「地の文かどうか」だけである** — 使ってはならない表記の扱いは §3.3 が正である。

**英語のファイルに残る日本語** — 訳してはならない:

- **`原則n`** — `check-kit-refs.py` がキット全文に当てる ID である
- frontmatter の `description`(スキル一覧に日本語で出る)
- 出力の雛形の中身(報告様式の行など)
- 台帳・記録・`docs/` に書き込む literal 文字列(`## 基本要件の点検` など)
- **人間に見せてはいけない言い回しの例示**(`delegation.md` §1.1 の規則2 が挙げるもの)—
  引用なので原文のまま
- 規範用語集の日本語側

**日本語のファイルに残る英語** — 訳してはならない:

- パス・ファイル名・コマンド・オプション・終了コード
- 識別子と ID(`DS-01` `BR-01` `FR-<domain>-nn` `CS8` `MODULE-*` `PLAN-*` `CTR-*` `F1`〜`F4`)
- コードフェンスとインラインコードの中身
- frontmatter のキー名と `state:` の値(`building` / `awaiting-verify` / `verified`)
- スクリプトが実際に出力する語(`green` / `red` / `PASS` / `FAIL` / `OK` / `NG`)—
  **出力と規範の表記を割らない**
- 規範用語集の英語側
- `run` — **一回の実行**。★ **何を1回と数えるかは、書くその場で示す**
  (例: 「`/verify-tests unit` の1 run」「F2 の1 run」)。**示さずに裸で書かない** —
  個別のテスト1件を指すこともあれば検証の一巡を指すこともあり、日本語の「実行」と併存して
  揺れていたのがこの項の理由である。**「ラン」とは書かない。**

**一覧の全文は `.claude/directions/glossary.md` §10 が持つ**(ここには書き写さない)。

### 3.2 語の正は規範用語集である

**概念に当たる語は `.claude/directions/glossary.md` のとおりに書く。** 表に無い概念を名付けたなら、
**規範用語集に足してから**規範に書く。日本語と English の両側を同時に埋める — 片側だけ増やすと、
もう一方の言語のファイルで各人が訳を作ることになり、それが `gate` で起きたことである。

### 3.3 これは機械が見る

**言語規約が文章にしかなければ fail-open である**(inspection-14 の同型)。実際、この規約は
2026-08-21 まで文章にしか存在せず、**英語と定めたファイル群の 44% が日本語だった** —
規約は書かれた瞬間から守られていなかった。

`check-language.py` が `make check` の中で見る: ファイル区分と言語の一致、§3.1 の引用島の除外、
規範用語集の「使ってはならない表記」が現れていないこと。
**移行の途中は「移行済みファイルの一覧」に載ったものだけを見る。**

**引用島が免除するのは「地の文かどうか」だけであり、使ってはならない表記は引用島の中でも
使ってはならない。** 例外は1つだけで、**その行に `LA3-ok` と書いてある行**は LA3 の対象から外れる
(検査スクリプト自身が禁止表記を材料として持つ行のためのものである。ファイル単位の免除は持たない —
ファイルごと外すと、そのファイルの他の行も一緒に素通りする)。 ★ 禁止表記が最も害を為すのは、バッククォートに入った**スクリプトが実際に
印字する文面**や雛形の中である — そこは人間がそのまま読む。島を剥がして検査すると、まさにその
場所だけが抜ける(2026-08-21 の実測: `roles/work.md` が人間に見せる1行を含む15か所が
「0件」を通り抜けていた)。

**`.py` と `.json` については禁止表記だけを見る。** ★ 地の文の判定はこの2種類に対してだけ
誤検知が捕捉を上回る — ライブラリ名の並び、docstring 内のコード例、JSON の鍵の名前が、
どれも「英語の地の文」に見える。**鳴り続ける検査は信用を失い、やがて外される。**
コメントを日本語で書くことは規範として残り、そこは読み手が守る(原則11)。
**禁止表記のほうは見る** — 実測で、`flow-config.json` の `_comment` に古い表記が生き残っていた。

## 4. 同じ事実を2か所に手で書かない ★

**2026-08-27 に入れた。** 2026-08-26 の実測: 1つの検証の周が直した15件は**全件が
「別の場所に正しい値があるのに、その写しが古くなっていた」**であり、
**1つの事実が12本の文書の46か所に手で書かれていた。**
**写しは必ずずれる。** 検査が毎周それを直しているのは、ずれが生まれないようにしていないからである。
形は3つで、それで全部である。

### 4.1 すべての事実に持ち主を1つ決める

**持ち主とは、その事実を手で書いてよい唯一の場所である。**
**層の規則がそのまま持ち主の規則である**(原則3): 目的・範囲は 00、振る舞いは 01、
構造・契約は 02、実装の細部は 03。
**そして実装の細部のうち、コードを読めば分かるものはコードが持ち主である**(原則2 の言い換え
にすぎない — 「コード ⇄ 03-impl は正確に一致する」)。

**新しい決まりはここではなく、次の 4.2 と 4.3 である。**

### 4.2 持ち主でない文書は、写さずに参照する

**形はこれ1つである**(この形だけを機械が見る — `build-facts.py check`):

```markdown
<!-- いま(写し) -->
`.gitignore` には状態の置き場所を除外する行を1行だけ追記する(既にあれば何もしない)。

<!-- あと(参照 + 要旨1行) -->
`.gitignore` への追記の内容は `docs/03-impl/contracts/conf.md` の「除外の追記」が正である。
(要旨: 除外の行と、その中の設定ファイルを戻す行を、無いものだけ足す)
```

- **`` `<リポジトリ相対パス>` の「<節見出し>」が正である。`` が参照の形である。**
  機械が見るのは2つ — **パスが実在すること**と、**その節見出しがそのファイルに在ること**。
- **要旨は1行までとする。1行とは「参照の直後に置く括弧書き1文、60字以内」である。**
  **2行以上を許すと写しに戻り、0行にすると読み手が必ず別のファイルを開くことになる。**
  **60字を超えたものは `build-facts.py check` が数えて出す**(拒まない)—
  **あれは「写しへ戻り始めた」ことに気づくための計器である。**

### 4.3 本文に値を出したいときは、機械の欄に入れる

**機械の欄とは、手で保守する文書の中の、道具が丸ごと書く区画である。手書き禁止。**
印は既存の書式と同じで、**終端にも道具名を書く**(`callgraphs.md` §4。生成の注記を囲む
`BEGIN NOTE` とは別物である — あちらは生成物の中の注記、こちらは手書き文書の中の生成区画):

```markdown
<!-- BEGIN GENERATED: build-facts.py id=<事実の id> -->
33本
<!-- END GENERATED: build-facts.py -->
```

- **`id=` が要るのは、1つの文書に2つ以上の区画を置く道具だけである** ★ —
  `build-facts.py` がそれで、どの事実を出す区画かが決まらなければ埋めようがない。
  **1文書に1区画しか置かない道具は、道具名だけでよい**(`build-index.py` の索引がそれである)。
- **終端は2つの形が在る。** 新しく書くときは道具名を書く(`<!-- END GENERATED: <道具名> -->`)。
  **道具名を持たない旧終端 `<!-- END GENERATED -->` も読める** — 雛形 `templates/03-index.md` が
  配っているのはその形であり、**失効の判定も一括検査も両方を受ける**
  (`stamps.py` の `_GENERATED`・`check-ssot.py` の `blank_generated`)。
- **中身の宣言はプロジェクトの `docs/facts.json` に置く**(1件1欄: `id` / `type` / `args` /
  `format`)。**抽出器は組み込みの4つだけで、任意のコマンドは決して実行しない** —
  宣言を書ける者が任意のコマンドを走らせられるなら、それは宣言ではなく別のコードである。
  **一覧と書式の正は `.claude/scripts/build-facts.py` の説明文である**(ここには写さない)。
- **埋めるのは `build-facts.py update`、確かめるのは `build-facts.py check`** であり、
  **F2 と F3 は検査の先頭でそれを走らせ、差分ゼロを合格の条件にする**
  (`/verify-docs` §1・`/verify-impl` §1)。**走らせ忘れは起きない** — 手順の先頭に在る。

### 4.4 機械の欄は、他の検査を失効させない

**機械の欄の中身だけが動いた変更は、鮮度スタンプを失効させない**(`flows.md` §2)。
生成器が実装から書き写しただけの区画が動いても、**手書きの部分は動いていない**ので、
読み比べる検査の結論は古くならない。
**ただし除外はパス単位では書けない** ★ — 機械の欄は手で保守する文書の**中に**在るので、
ファイルごと除外すると**同じ文書の手書きの部分の変更まで失効しなくなる**(穴である)。
だから判定は**区画単位**であり、管理欄(`updated:` 行・`verified:` ブロック・`version:` 行)と
同じ仕組みに乗っている(`stamps.py` の `machine_owned_only`)。
**区画そのものが増えた・消えた・`id` が変わったのは中身の変更である** — 道具の持ち場が
動いたということだからである。
**同じ理由で、機械の欄の中身は仕様ドキュメントの一括検査の対象からも外れる**
(`check-ssot.py` が中身を空行に置き換えて読む。手で編集してはならない場所で違反を出しても、
直せる者が居ない)。

### 4.5 何を機械の欄にし、何を参照にするか

**値そのものを本文に出したいなら機械の欄、そうでなければ参照である。**
**迷ったら参照にする** — 参照は宣言を1つも増やさず、ずれようがない。
**そして、どちらでもなく「写す」を選ぶことはもう無い。**
