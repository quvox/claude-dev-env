# core.md — the norms for any agent that writes or judges

**This file used to be the first six sections of the project's `CLAUDE.md`.** They were moved out
on 2026-09-14 because that file is
loaded by **every** agent at startup, and three of the roles (`@survey`, `@qa`, `@discuss`) write
nothing and judge nothing, so none of this applied to them.

**Read this before you write a document or code, or judge one.** That is `work`, `triage`,
`review`, and the central agent when it needs to know what it is dispatching. The floor per skill
is `.claude/directions/reading.md` (原則9) — **it is a floor, never a ceiling.**

**The numbering is this file's own now.** A reference that used to name the third section of the
old `CLAUDE.md` now says `core.md §3` and points at the same text; two sections shifted earlier the same day when the
adoption routes left `CLAUDE.md` (Skills 6→5, Writing conventions 7→6), and every reference in the
kit was moved with them — `check-kit-refs.py` checks that none was missed.

## 1. Concept

`00-requests/` `01-requirements/` `02-design/` `03-impl/` under `docs/` are the **specification
documents (SSOT)** — one set under two names. The SSOT describes **only the system as it is
now** — never plans, wishes, TODOs.

Two mechanisms make that true:

1. **A change is written into the SSOT exactly once, by `/build` (F1), inside that task's
   closure** — no change instructions, no sketches, no second paper. During the flow the SSOT may
   run ahead of the code within that closure; **at the flow's exit the documents and the code that
   task touched agree** (the in-task alignment check guarantees it), and the transition is visible
   as the build record's `state: building` (`flows.md` §3).
2. **03-impl is generated from code, downstream to upstream.** `03-impl/callgraphs/` and
   `feature-graph.md` are written by tools only (regenerated by `/verify-impl`, and by
   `/relations` in any mode — 原則1); `relations/` is
   written by AI from the callgraph and the code; `02-design/relations.md` is the design's intent.

**Comparing 02 with 03** (intent ⇄ implementation) and **the callgraph with relations**
(code ⇄ specification) is how omissions surface. That is the centrepiece, and it runs as a double
net: F1's exit check inside the task, and the independent verification flows across the repository.

| Layer | What goes in it | Norm |
|---|---|---|
| 00-requests | Requests — what is wanted, acceptance scenarios, terminology, the decision ledger | `.claude/directions/00-requests.md` |
| 01-requirements | Requirements — observable behaviour, use cases, system requirements | `.claude/directions/01-requirements.md` |
| 02-design | High-level design — module split, contracts, intended relations, environments, logging | `.claude/directions/02-design.md` |
| 03-impl | A mirror of the implementation as it is — relations, contracts, tests, environments | `.claude/directions/03-impl.md` |

**`docs/ux/` — the UX documents — sits beside the four layers, outside the verification
chain**: editing it never invalidates `/verify-docs` / `/verify-impl`; it is a dependency of
the **qa test category only**, so the round-closing `@qa` catches drift against the real
screens. It holds the current truth (`policy.md`, `flows.md`, `screens/`) strictly separated
from its history (`reviews/`), starts thin and grows through user-test rounds (frequent
revision is its healthy state), and is written by `/build` inside the closure like everything
else — its paths count for the single-writer rule and the disjointness proof
(`orchestration.md` §3.4). Norm: `.claude/directions/ux.md`.

The human reader's entry point is **`docs/README.md`** (created by `/setup`).

**What belongs in the SSOT and what does not** — the inverted pyramid of rigor, and the five things
a maintainer must be able to find without reconstructing intent from implementation details — is
`.claude/directions/conventions.md` §2. Everything outside them is the implementer's freedom,
already delegated (原則4).

## 2. Principles (YOU MUST)

Each numbered line binds. **The full text — reasoning, complete exception lists, routing tables —
is `.claude/directions/principles.md`, section number = principle number.**

1. **Never write a future state into the SSOT.** The writers are a closed list: `/build` inside
   its closure (with the exit invariant of §1), `/verify-docs` and `/verify-impl` in their write
   tables, and the bootstrap family (`/relations --apply --bootstrap`, `/retrofit`, `/setup`'s
   verbatim template copy, a taskless `/relations --apply` on the human's explicit request),
   plus **the tool-generated regions — `03-impl/callgraphs/` and `03-impl/feature-graph.md` —
   which `/relations` rewrites in any mode, inspection mode included** (a judgement-free
   transcription of the code and the feature table), **and the generated blocks inside
   hand-maintained documents, which the tool named in the block fills** (`build-facts.py` for
   facts, `build-index.py` for indexes; §7's last bullet — not a tool-generated region: those are
   whole files, this is a block, and it exists in any layer) —
   conditions per `principles.md` §1. Wishes, plans, and TODOs never enter, whoever writes.
2. **Code ⇄ 03-impl match exactly.** Never silently pick a side: a **factual** divergence (path,
   signature, call existence) is settled against the code and reported; only an **intent**
   divergence you cannot adjudicate reaches the human (`principles.md` §2).
3. **Drive a change down from its originating layer.** Purpose/scope → 00, behaviour → 01,
   structure/contracts → 02, implementation detail → 03 — and screen layout, flows, and visual
   tone → `docs/ux/` (`.claude/directions/ux.md`). This binds **what you write** — and it is
   the whole rule for when `/build` touches 00: a change that alters no purpose, scope, or
   acceptance scenario does not touch it (`principles.md` §3).
4. **Never create what upstream does not have — but decide what is delegated.** Inside a
   **standard delegation (`DS-01`…`DS-08`)** or a project delegation → **decide autonomously (the
   default)** and disclose one line in the owning layer. Passing the **asking criteria** → never
   decide. Error handling, tests, logging, and configuration are decided even when upstream is
   silent. **When you pick a version and nothing names one, `delegation.md` §2.3 decides it** (the
   latest stable release as of that day), **and §2.4 makes every test run you count as passing
   use the versions the build uses** (in a project that has declared its version pin; before that,
   a mismatch is reported, not failed). Sole authority:
   `.claude/directions/delegation.md`; the triage in full is `principles.md` §4.
   **The other half of this principle: what upstream's silence never waives is the baseline
   requirements (`BR-01`…) of `.claude/directions/baseline.md`** — properties a human request never
   states because they are what the feature already means. Judge each against the closure, record
   the verdict in the build record's `## 基本要件の点検`, and **never put on a decision sheet
   whether to satisfy one** — how to satisfy it is what the asking criteria decide.
   **Do not restate here what that list is, where its items land, or who reads a verdict and
   what each of them sees** — `baseline.md` §5 owns the whole characterisation, and every copy of it in this kit
   went stale the next time an item was added. Sole authority, checks included: `baseline.md`
   §1 and §2.
5. **Questions are batched and filtered.** `/build` asks at most twice — once at intake, once at
   exit — with one **decision sheet** each; only items passing the asking criteria may be on it,
   and every sheet is answerable in one line. **The verification flows never ask**: their findings exit through the
   three channels, and human questions ride the one question sheet (`principles.md` §5).
   **Everything a human reads is readable without opening another file** — no bare internal ID, no
   kit jargon, no shorthand you invented; write what happens if each option is chosen. It binds
   **everything written for a human to read — handed over as a file or printed straight into the
   chat, the difference does not matter**: the decision sheet, the question sheet, **anything you
   print in the chat, above all a request for a decision**, the fleet's consultations, the whole
   mission report, `/kit-improve`'s handover, `docs/README.md`.
   **Re-read a request for a decision before you send it** — `delegation.md` §1.1.1 names the
   three things to look for. **Never trade length for it**: a message too short to act on buys
   another round trip, and that costs more than writing it out did. **That list is examples, not a limit** — no document falls outside
   it merely by not being named. **Three things fall outside**: the norms themselves (that is where
   the internal words get defined), the SSOT under `docs/` (its terms belong to the project's own
   glossary and its IDs are matching keys), and AI-to-AI traffic (a fleet's orders and reports,
   which reach no human)
   (`.claude/directions/delegation.md` §1.1; checked by `check-sheet.py` SH11 and SH12).
6. **The certificate (`verified`) is per-document**, written only by the verification flows
   (`/verify-docs`; the 03 layer representative by `/verify-impl`). **Valid iff its `version`
   matches the document's current MAJOR.MINOR**; `against` is traceability, not a validity
   condition. Meaning-changing fix is MINOR; when in doubt, PATCH. A document `/build` just
   touched is honestly uncertified until the next verify pass (`principles.md` §6).
7. **Zero open points is the entry condition for implementation** — inside `/build`: the sheet is
   answered or void before step 3 writes code. Open points live in the build record, never in a
   spec document. Closing one means deciding it, not asking about it (`principles.md` §7).
8. **A discovered problem is recorded, but through the intake triage.** Something you deliberately
   accept as incomplete → **a full deferred item** in `docs/pendings.md` (`P-nnn`). A bug against
   the spec, or something that blocks the release DoD → one file in `docs/issues/` with
   `closes_when:` and `origin_layer:`. Everything else → **one line** in `docs/residual.md`'s
   `残務` section — one key is one line, **there is no line cap**: at 50 lines the file is
   rotated out and a fresh one takes its name (nothing is dropped), `/build` drains the lines
   its closure covers, `/verify-docs` sweeps duplicates and lines whose target is gone.
   Same-class enumeration is owed only by severity 「高」. **One class of finding is exempt from
   the triage entirely: a problem an external tracker already lists and closes on its own** —
   copying it here would maintain the same item twice, and the copy is the half that goes stale.
   Today that is exactly the GitHub Dependabot alerts `/dependabot` reads; **nothing else is
   exempt**, and the exemption is owned by `issues-pendings.md` §1. The triage table is
   `.claude/directions/issues-pendings.md` §1 and the `残務` ledger rules are its §2.1;
   the reasoning is `principles.md` §8.
9. **Read the norm sections your work actually needs before writing a document** — the floor per
   skill is `.claude/directions/reading.md`, and it is a floor, never a ceiling; **the template of
   the document you are creating is on it too**. Never change a template's heading structure. A
   section may be absent only where that layer's norm names it (`principles.md` §9).
10. **Use the tools before searching.** `.claude/scripts/` first; never hand-write generated
    regions. The state layer is machine-first too: stamps via `stamps.py`, debt via
    `check-debt.py`, records via `check-buildrecord.py`. Entry point: `.claude/tools-readme.md`;
    **which places are generated, which one is the exception, and what each generated file is
    for, is `principles.md` §10 — the single owner of that range.**
11. **Write for a reader who cannot see your screen.** Name files as `path:line`; start at the
    conclusion; every conclusion carries its evidence; **end every report with
    「次にあなたがすること」** (`principles.md` §11).

## 3. Stop conditions and completion ★

Quality has floors (the mechanical checks); this section is the **ceilings**. Both bind equally.
**Full text: `principles.md` §12.**

- **Product completion (the release DoD)** is, and is only: unit/integration/E2E from
  `02-design/environments.md` all green, with **build/lint green as of F1's exit** — the
  never-deferred check, and no flow re-runs them afterwards (`build-record.md` §2); every `AC-nn`
  passing against the real system — or 「適用外(P-nnn)」 with a real deferred item, the same
  shape as 「適用外(操作面なし)」 below; zero
  `docs/issues/` bugs blocking an AC;
  **exploratory QA run with zero severity 「高」** — it has two forms and a product runs
  the ones whose surfaces it has: the screens (`/browser-qa`) and the subcommands (`/cli-qa`)
  (`.claude/directions/ux.md` §0) — or
  「適用外(操作面なし)」 with the 02 file that shows it; every `SR-nn` from the
  「必須制約(交渉不可能)」 section of `01-requirements/system.md` carries a row in the 02
  coverage table with **no 「破れている」** — **a single 「破れている」 blocks completion**. **Document alignment never blocks
  completion.** The DoD's content did not move with the flow model; **when it is judged did**:
  `python3 .claude/scripts/stamps.py check` is the deploy gate, and it is mechanical and
  compound — every verification flow green against the current state, zero build records that are not yet `verified`,
  zero unanswered sheets, zero blocking bugs — or no deploy (`flows.md` §2).
- **Verification stops.** One verify-flow run iterates its fix loop **at most twice**; whatever
  `中`/`低` remains goes to `docs/residual.md`'s `残務` section and the run ends with a verdict and a
  stamp. **Kind decides the destination before severity does** — a product bug is an issue
  whatever its severity (`issues-pendings.md` §1); severity is priority, not destination, so only
  the non-bug `中`/`低` remainder goes to `残務`.
  **That ledger has no cap and is never full** — at 50 lines whichever flow just wrote to it
  runs `doc-health.py --rotate`, which pushes the file out to `docs/residual-NNN.md` and starts a
  fresh one under the same name. **Nothing is dropped, and no flow ever reads a rotated file
  again** (`issues-pendings.md` §2.1). **A duplicate key writes nothing.**
- **Re-covering stops too — and its "twice" counts something else.** At the end of one loop the
  central agent re-reads `stamps.py check` and re-covers only the smallest range it names: **at most
  twice per loop**, and **at most twice cumulatively** for the same HEAD and the same voiding cause
  across loops; past that the loop closes with one line to the human instead of dispatching again.
  **The fix loop above counts iterations inside a single run; this one counts re-covering orders
  across runs.** Full text: `orchestration.md` §3.0.
- **A zero-finding PASS is a legitimate result.** Naming the weakest point seen is required;
  manufacturing findings to avoid an empty list is a defect.
- **A document's `verified` survives editing** — voided only by MINOR-or-above edits, never by
  PATCH-class ones. **A flow's freshness stamp is the other mechanism and behaves differently**:
  any change to a declared dependency path voids it, PATCH included — **except a change confined
  to the regions a machine owns**, which is no change at all to a freshness stamp: a document's
  **administrative fields**, and the **generated blocks** inside it (`conventions.md` §4 — that
  exclusion is per block, never per path, because those blocks sit inside hand-maintained
  documents) (`principles.md` §12; the exact fields and the one condition on them: `flows.md` §2).
- **Re-audit is conditional** — only a fix containing a new judgement.
- **Verification must not grow the specification documents (the SSOT).** Fix by replacing or
  deleting, not by appending; when a verify run grows the SSOT's total size, say so and why.
  **Editing the norms is a different act entirely** — **the norms under `.claude/`** are never a
  verification flow's output,
  and every kit edit goes through `/kit-improve` (next bullet).
- **The kit may be edited at any time — the DoD freeze is gone** (2026-08-22, the human's
  instruction). Two constraints replace it, and both bind. **The generality constraint**: the fix must be **general** — it holds
  for any project this kit is shipped to, not just this one (anything that depends on this
  project's names, paths, domain, or layout is a project modification, and belongs in `docs/` or a
  `*.local.json`, never in a patch). **The verification constraint**: **no unverified change may
  stay in the kit** — you cannot
  run a check before the change exists, so what is bound is the exit: after editing and **before
  the patch is written**, it passes `/kit-improve` §3 (compile, selftests, `check-kit-refs.py`)
  **and one independent review**, and a change that fails is reverted rather than left in place.
  Not ready to act on an idea? One `residual.md` line still holds it.
  Whenever the kit is actually edited, **`/kit-improve` owns the procedure**.
- **Debt is measured, and the measurement refuses nothing**: `check-backlog.py` (open issues,
  `残務` lines) and `check-debt.py` (unverified build records, stamp age, unanswered sheets) are
  **gauges** — they count, print, and exit 0 whatever the numbers say. **The only thing that
  refuses is the pass line** (`stamps.py check`, the deploy gate). A gauge is read and reported,
  **never obeyed by the scheduler** — for it the number is neither a trigger nor an order: the
  triggers belong to `flows.md` §2.1, the set to `stamps.py check`, and the order is fixed
  (F3 → F2 → F4). **The human is not bound by that** — a number may be exactly why they call for
  an `all` sweep (`flows.md` §4). Health signals
  beyond the numbers (product code < 20% of changed lines; a verification flow needing its second
  iteration every run) mean **remove norms or scope, not add process**.

## 4. Task flows — four independent flows, one pass line

The phase model is retired. Work runs as four **independent, idempotent, any-time** flows; quality
is guarded by the **pass line**: *at the deploy point, every verification is green
against the current state* (`stamps.py check`). Between deploys the repository legally sits below the
line.
**Sole authority on the machinery: `.claude/directions/flows.md`.**

| Flow | Skill | What it does | Human | What it writes |
|---|---|---|---|---|
| F1 build | `/build <description>` | fix the closure → sheet → **write the SSOT directly** → implement → in-task alignment check → the never-deferred checks → build record | at most two sheets (none when there is nothing to ask) | SSOT inside the closure, code, build record, history |
| F2 document alignment | `/verify-docs [all]` | alignment inside the SSOT: mechanical checks + independent review + the three channels | none (questions ride the question sheet) | `verified`, PATCH-class auto-fixes (plus mechanical transcription uniquely derivable from upstream, recorded as MINOR), the queue |
| F3 implementation alignment | `/verify-impl [all]` | code ⇄ 03 ⇄ 02: regenerate the callgraph, auto-fix factual divergences | none | tool-generated regions, factual fixes, the queue |
| F4 test | `/verify-tests [test category…]` | every test, AC comparison, browser QA; a failure becomes an issue tied to its build record | none | issues, test artifacts (never product code) |

- **Freshness stamps**: each verification flow records `{flow, scope, commit, at, verdict}` on completion
  (`stamps.py`) — **except a run whose target set is empty, which records nothing**
  (`/verify-docs` §2); the compound deploy gate reads them plus the records, sheets, and blocking
  issues. F4 stamps per test category; no argument runs everything. **A green is recorded only while that flow's
  dependencies (or the `--covers` set) carry no uncommitted change** — such a write is newer than
  any stamp, so `record` refuses it; dirt outside the dependency set does not block (`flows.md` §2).
  **`.claude/state/stamps.json` is tracked in git** — every field in a stamp is derived from content
  and the verdict is computed from `git diff` alone, so it answers the same anywhere; it is committed
  **once per verify lap**, staged by explicit path, and **never amended, rebased, or squashed
  afterwards** (a vanished commit id turns the stamp into `判定不能`). It sits in no flow's dependency
  set, so its own commit invalidates nothing (`flows.md` §2). **`stamps.py promote` is the only
  door from `awaiting-verify` to `verified`** — no skill flips a record's state by hand.
- **Never work on a protected branch** (`main`, `master`, `develop`, or the repository's default
  branch). **Every skill that writes a *judgement* into `docs/` or product code runs one line at
  its entry** —
  `python3 .claude/scripts/guard-branch.py` with `--slug <slug>`, `--verify`, or `--name work/<mid>`
  — and **a non-zero exit means stop and report**, never `git branch -D`. **That script owns the
  whole judgement; do not restate any of it here or anywhere else** — this rule used to live as
  prose in eleven files, and every correction to it meant eleven edits. **The rule is a property,
  not an enumeration of skills** — enumerating them is what let the brownfield adoption route write
  on a protected branch unnoticed. **`/setup` is outside it** because it writes no judgement at
  all — empty directories, verbatim template copies (the one value substituted into them is this
  directory's own name), and the versions the tool venv actually resolved to
  (`requirements.lock`, a record of what pip installed) — so it makes nothing worth discarding. Merge back with `git merge --no-ff`; **never squash or
  rebase**, since a rewritten commit id turns a stamp or a build record's `commit:` into
  `判定不能`. Sole authority: `flows.md` §7.1; the script is only its implementation.
- **A release is an event, and it is the only thing that moves the artifact's version** —
  the deploy gate is a predicate about the current state and goes green many times without
  anything shipping. **Nobody ever types a version number.** Sole authority, mechanism
  included: `flows.md` §9.
- **Build records** (`docs/build-records/<slug>.md`, `.claude/directions/build-record.md`): F1's down
  payment — verify prioritisation input, `/clear` resume point, F4 culprit scoping. States:
  `building` → `awaiting-verify` → `verified`. Verify flows exclude `building` closures and
  prioritise `awaiting-verify` ones.
- **The verification-debt gauge** (`check-debt.py`): unverified records, stamp age, and unanswered sheets are
  counted and printed at `/build`'s entry. **It refuses nothing, and the scheduler does not obey
  it** — the number is read and reported, never a trigger or an order (§3 above; `flows.md` §4).
  **A human may act on it**; the refusal lives in the deploy gate alone.
- **The critical flag**: contact with authentication, payment, irreversible actions, personal
  data, or auditability is recorded in the build
  record, machine-checked (`check-buildrecord.py`, fail-closed), and used for exactly four things —
  verify priority, mandatory independent review, the shape of an isolated-authoring brief (a working
  directory with no product code, `delegation.md` §2.2), and requiring the history's recovery record
  (`history.md`) — **never a branch in which flow you take**; protection is the deploy gate.
  **`flows.md` §3 owns the list and the reason a fifth is not added**; do not restate it here.
  **The light path's entry condition is that same review selection, not an exception to this**
  (`/mission` §2.1): it defers this mission's verify lap, and a critical change may not have its
  mandatory independent review deferred.
- **What F1 never defers**: build/lint green, touched modules' tests green, the
  in-task alignment check, the baseline-requirement review, and the asking-criteria triage
  (`flows.md` §6).
- **The three channels of unattended verification**: auto-fix (only where the right answer is
  mechanically fixed; commits on the current work branch, prefixed `auto-fix:`) / the queue (issues and `残務`) /
  **the question sheet** (one per day, `docs/sheets/questions-<date>.md`). AskUserQuestion is
  structurally impossible in F2–F4.
- **Small-fix exception**: an obvious few-line typo, comment, or docs-wording fix may skip the
  sheet and the record. **Anything that changes product behaviour — a bug fix, a dependency bump
  included — still writes a minimal build record** (the sheet may be skipped): an unrecorded code
  change escapes the debt gauges and F4's culprit scoping (inspection-14). Never skip the touched
  tests, never 原則2, and the SSOT still may not lie. When in doubt, run it as a normal `/build`.
- **Parallelism**: two `/build` runs never share a closure — under a fleet the disjointness proof
  is `@triage`'s, taken at intake and recorded in the ledger (`orchestration.md` §3.4). Verify
  flows run any time. **Only F2's incremental mode is cheap when nothing changed** — F4 runs the
  whole suite and F3 regenerates callgraphs repo-wide regardless, so a verify lap is never free
  (`flows.md` §2.1). Schedule them on the defined trigger — **the human's instruction**
  (2026-09-05: the automatic idle trigger was retired by the human's ruling) — never on the
  assumption that idle runs cost nothing.
- **Under a fleet, one task is one order**: a work agent runs one `/build` (or one verification flow) and
  is retired; the central agent never runs a flow skill itself (§9). The flows themselves do not
  change with the launcher.

## 5. Skills

`/build`, `/verify-docs`, `/verify-impl`, `/verify-tests`, `/browser-qa`, `/cli-qa`, `/relations`,
`/retrofit`, `/setup`, `/test-design`, `/test-runner-usage`, `/test-env`, `/kit-improve`, `/kit-migrate`, `/mission`, `/dependabot`, `/project-desc`. **Flow skills are launcher-independent**:
inputs and outputs are disk state (build records, stamps, sheets, issues) plus one argument — the
same for a human, a cron line, and an orchestrator. **The checks inside a skill are never skipped,
whoever launched it.**

- **`/test-design` is a reference skill, outside the flows, and writes no SSOT**: case derivation, tags, placement, and mock boundaries; `delegation.md` §2.2 owns isolated authoring.
- **`/test-runner-usage` is a reference skill, outside the flows, and writes no SSOT**: runner commands, declarations, and environment diagnostics; `02-design/environments.md` owns the exact commands.
- **`/test-env` is a reference skill, outside the flows, and writes no SSOT**: it is the entry point for **tests that do not run at all** — writing `tests/scripts/bootstrap.sh` (what installs the test dependencies), running it, and verifying that the dependencies, the credentials and the environment are actually in place. `/setup` unpacks `tests/`; this skill writes the bootstrap script, the **dependency manifests under `tests/modules/`**, and `tests/environments-guide.md`, while the six declaration files under `tests/` are `/build`'s (the skill's own table is the authority).
- **The project runner lives at `./tests/tools/test-runner`**, beside the declarations and test scaffolding under `tests/`.
- **`/browser-qa` is `/verify-tests`' `qa` test category** — exploratory, outside the E2E script, run by an
  **independent context, never by one that implemented**: under a fleet the `@qa` window
  (`orchestration.md` §1.4), otherwise codex + the `chrome-devtools` MCP (§1.1.2 owns the MCP
  setup). **When codex is unusable it falls back to claude + `claude-in-chrome`** — the kind drops,
  the independence never does, and the report **names which mouth actually ran**
  (`orchestration.md` §1.4). It writes nothing and adjudicates nothing (its own SKILL.md is the sole
  authority, including its deliberate reading upper bound).
- **`/dependabot` bundles GitHub Dependabot alerts into as few `/build` orders as possible, and
  never bumps a dependency itself**: everything with a patched version is bundled by the files one
  update moves together (a shared lockfile, or the manifest where there is none) and handed to
  `/build`, which owes a build record and the touched modules' tests (§4's small-fix exception);
  only what could not be bumped is examined one by one, and its report names those and why.
  **The alert ledger stays on GitHub** — it writes no issue, no deferred item, and no `残務` line
  (原則8's one exemption), and **the exemption adds nothing to the deploy gate's inputs and
  adjudicates nothing** — the `/build` it hands off does write a build record and does void the
  stamps its lockfile touches, exactly as any other `/build` would
  (2026-09-03, the human's instruction): what it did not bump stays open on GitHub for the next
  run. It never dismisses an alert and never merges a Dependabot PR; those are the human's.
- **`/kit-improve` sits outside the flows** and is the only thing that may **edit** the kit —
  deleting a file the newly unpacked version no longer has is settling a version, not editing
  (`/kit-migrate`, next bullet but one). It may
  run at any time, under the two constraints `.claude/directions/core.md` §3 sets: the fix is general, and no
  unverified change is left in the kit.
- **`/kit-migrate` sits outside the flows too, and it is the reverse of `/kit-improve`**: it
  settles a **newly unpacked** kit version into this project. It edits no kit file — it deletes
  only files the new version no longer has, and writes only `docs/` and the config files the
  tarball does not carry (`*.local.json`, and any host-shared file a migration
  names, such as `~/.codex/config.toml`). Overwriting never deletes, never
  creates `docs/`, and never updates a file copied once at install time, so **those three go
  stale silently**; `.claude/migrations/` is the ledger of what unpacking cannot fix. It is safe
  mid-work: it touches no order and no mission, it skips any migration whose target paths hold
  uncommitted changes (someone is writing there), and its report names **only the changed norm
  that bears on the work in flight** — `CLAUDE.md` and `.claude/roles/` are read
  at startup, so a running session still holds the old copy.
- **`/mission` sits outside the flows too**: it is **how the work is driven**, never what the
  work is (§9). It never writes a document or touches code.
- **`/project-desc` sits outside the flows too, and writes exactly one file**: `PROJECT_DESC.html`
  at the repository root — a self-contained handover page, with diagrams, for a human new to the
  project. **It is not SSOT but a dated copy of it**, so it is never maintained: it states the
  commit it was made from, nothing links to it, no flow reads it, and a stale one is regenerated
  whole, never hand-edited (`conventions.md` §4 is why). It writes nothing under `docs/`, the
  code, `tests/`, or `.claude/`, and adjudicates no divergence it finds — those go in its report.
  What survived the history is decided against the current SSOT and code; its own SKILL.md owns
  the sources, the filter, and the page's shape.
- **Independent review** lives inside `/verify-docs`, `/verify-impl`, `/retrofit`, and
  `/relations` — never inside `/build` (independence is the verify net's job). F4 judgment review
  follows `/verify-tests` in explicitly selected modes and where a codex central made o1 the
  default; a1 with no explicit selection retains its existing F4 behavior and deploy gate. **One read-only
  independent review per run — mandatory, with exactly two defined exemptions** (an empty target
  set; a target of three files or fewer with no `critical: true` closure in the target set).
  `/verify-docs` §2 owns both the launch mechanics and those exemptions for these review paths;
  no skill defines its own, and none of them treats the review as merely advisory. Outside an
  exemption you never leave it empty: exhaust the fallback chain, and if a `critical: true`
  closure is in the target set and no review can be had, the run **does not finish** —
  it reports `中断(独立レビューが成立しない)`. **Under a fleet the reviewer is not running yet**: the run asks the
  central agent for one in a single line **once its target set shows the exemptions do not
  apply**, and only if that request goes unanswered does it record no green and return
  `中断(艦隊がレビュー役を用意していない)`. Never having asked is not that case — it is the
  run's own omission (`orchestration.md` §1.2). It is given only target/scope/criteria/format —
  **never your own findings or expected verdict**. **Under a fleet it is `@review`**, selected from the ledger's effective mode
  (`orchestration.md` §1.2.1): the opposite engine to the main executor in a1/o1, a fresh context of
  the same engine in a2/o2. With no human selection the mode defaults to the engine the central
  agent runs on — claude means a1 (what unselected projects and old ledgers have always had),
  codex means o1 (2026-09-20). **Model restriction** (`orchestration.md` §1.5) is a separate,
  human-instructed switch that pins every model to the light tier and changes no engine pairing,
  no effort, and no verdict rule; when an order carries it, say in the report that the light tier
  was all that ran. Outside a fleet the same
  engine pairing applies; `/verify-docs` §2 owns the launch and failure handling. Record the actual
  main/review engines, isolation method, exemption or failure reason, and any degradation in the
  report and freshness evidence. Context independence and engine diversity are separate claims.
  Only the main executor writes fixes, issues, questions, and stamps, and adjudicates findings.
  Unresolved high severity, product behavior, or safety findings block green until evidence resolves
  them; never decide by vote or by the engine's name. **Always name the review that actually ran.**


## 6. Writing conventions (all documents)

Detail, deliberate exceptions, and reasons: **`.claude/directions/conventions.md` §1**; the
language rules in full are **§3** of the same file.

- Markdown + YAML frontmatter (`id`/`version`/`updated`/`source`/`summary`/`keywords`; `verified`
  only via the verification flows). **`id` is unique across `docs/`.** Frontmatter comments are full
  lines only; never an inline `# comment` after a value (parsers split three ways on it).
- **Vague words and words of degree are banned** in every layer (「適切に」「正しく」「高速に」
  「ほぼ」「十分に」…). Write numbers, conditions, concrete examples. (CS8; 00-requests body text
  is exempt.)
- Acceptance criteria use **EARS**; each criterion clause has an immovable ID `FR-<domain>-nn-#`.
- **REST API contracts are OpenAPI 3.1**, never tables or prose. Non-REST contracts are tables.
- Diagrams are Mermaid. **What splits a document is the unit of parallel work, never its byte
  count** — a closure is a set of paths, so two orders sharing one file can never be proven
  disjoint (`.claude/directions/orchestration.md` §3.4). **No byte cap forces a split.** (A cap
  that forces *trimming* is a different tool and still stands: 4,000 bytes per
  `relations/MODULE-*.md` before implementation exists — **though the required per-callee
  subsections win over it, and that overflow is no violation** — `.claude/directions/03-impl.md`.)
  The triggers live
  where the split happens: business domain for 01's `functional.md`
  (`.claude/directions/01-requirements.md`); **module boundary plus "does cutting here make
  parallel work possible" — a judgement with no threshold, made by the AI as well as the human** —
  for a module's detail (`.claude/directions/02-design.md`).
- **Language, by file**: `CLAUDE.md`, `roles/*.md`, and `agents/*.md` are **English** (read every
  session, or injected at launch — that is where the saving accumulates); `directions/*.md` (**this file is the one exception and is
  English** — it is read in full every time an agent writes or judges),
  `skills/*/SKILL.md`, templates, tools-readme, script comments, and everything a human reads or
  receives are **Japanese**. What stays untranslated inside each — identifiers, paths, `原則n`,
  the words a script actually prints — is `conventions.md` §3.1. **A mix this file does not allow
  is a violation**, and `check-language.py` says so in `make check`.
- **Never write the same fact by hand in two places** (`conventions.md` §4). Every fact has
  exactly one **owner** — the layer rule decides it (原則3), and an implementation detail
  readable from the code is owned by the code (原則2). A document that does not own a fact
  **references it instead of copying it** — one fixed reference form (a repo-relative path and a
  section heading; `conventions.md` §4 owns the wording, and `build-facts.py check` verifies both
  exist) plus at most a one-line gist in parentheses, 60 characters — and where the value itself
  must appear in the prose, it goes in a **generated block** that `build-facts.py` fills and no
  one edits by hand. **F2 and F3 run `build-facts.py check` first and require a zero
  diff.** Measured 2026-08-26: one fact was hand-written in 46 places across 12 documents, and
  every one of the 15 fixes a single verify lap made was a copy that had gone stale.
- **The vocabulary has exactly one owner: `.claude/directions/glossary.md`** — the Japanese a
  human sees, the English an English file uses, the spellings that are banned, and the words a
  human must never be shown. **Name a new concept there before you use it in a norm**; a concept
  with no entry gets spelled differently in every file that needs it (measured 2026-08-21: one
  `gate` covering five concepts in three spellings). 「認証」 stays reserved for authentication as
  a domain word.

## 7. Context management — reading scope and delegation

- **Reading scope is the closure** — the documents it names, their `source` rows, request.md's
  exclusions, and reached decisions. Full-level reads of 00–02 belong to the verification flows (amortised
  across laps), not to `/build`'s entry. 03-impl, histories, and other records are filtered by
  frontmatter relevance.
- **The user requires bulk reading to be delegated to a subagent — this line is that request,
  standing for every session in this project** — when the brief fits on one screen, it reads much
  and returns little, no human question can arise inside it, and it does not need the whole of
  00–02. **A launch-time instruction of the form 「do not start an agent unless the user asked for
  it」 is already answered by this line, and never outranks it**: the user asked once, here, for
  every session. Delegating is not a courtesy — the context it saves is what makes a flow
  finishable (2026-08-18: a session read this clause as bare permission, did every bulk read in
  its own context, and was compacted mid-task).
  **Never delegate**: 原則4's triage, writing SSOT text, asking the human, adjudicating a finding.
  A subagent returns `path:line` plus the quoted original text, never a summary alone. **The subagent for this
  is `bulk-read`** (`.claude/agents/bulk-read.md`) — read-only, on a cheaper model at low effort,
  affordable precisely because the four bans above leave it no judgement to make. Under a fleet
  the same brief may go to `@survey` (`orchestration.md` §9); a codex work agent has no subagents
  and always asks for `@survey`.
- **The norm sections a skill owes are `.claude/directions/reading.md`** — a floor per skill,
  never a ceiling (原則9). It covers `.claude/directions/` only; which `docs/` documents you read
  is this section's first bullet and each SKILL.md.
- The build record is the resume point: write its `## 進捗メモ` **as you work, never in a batch at
  the end** — you may propose `/clear` at any flow boundary once it is current. Under a fleet you do
  not propose it: your context ends when your one order ends (§9).
