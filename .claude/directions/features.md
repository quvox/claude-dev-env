# 03-impl/features.md — 機能表(境界の定義)

日本語で書く。

## 0. これは何であって、何でないか

**機能表は、「システムにどんな機能が在り、それぞれの入口はどのシンボルか」だけを述べる1枚の表で
ある。** 中身(目的・処理の流れ・連携の詳細)は持たない — それは `relations/MODULE-*.md` に属する。

| | features.md | callgraphs/ | relations/ |
|---|---|---|---|
| 誰が書くか | **AI が起案し、人間が合意する** | 道具だけ | AI |
| 単位 | 機能(= 入口1つ) | 関数とエンドポイント | 機能 |
| 中身 | ID・入口・所属・種別・概要 | 呼び出し関係 | 目的・流れ・連携・異常系 |
| なぜ機械に書けないか | **境界がどこに在るかは設計判断である** | — | コードの意味を記述するものだから |

**機能表は relations と 1:1 である。** 行の ID が、文字どおりファイル名 `relations/<ID>.md` である
(`relations.md` §2)。1:1 が対応づけではなく **ID の同一性**であるため、
突き合わせは1回の集合演算で済む。

## 0.1 ★ 機能表に載せないもの — 試験は「本番実行系から到達するか」である

> **入口が機能表に属するのは、本番で走っている実行系から到達できるときである。**
> **開発者の手元か CI でしか走らないものは、機能ではない。**

**「サービスに必要か」で判定してはならない**(**曖昧な言い回しである** —
lint はサービスの品質に必要だ、と論じることができてしまう)。
**「本番実行系から到達するか」**なら、コードを読んだ全員が同じ答えに至る。

| 対象 | 機能表 / relations | 行き先 |
|---|---|---|
| REST エンドポイント、イベント/キュー/ストリームのハンドラ | **載せる** | — |
| **定時ジョブ・運用バッチ・cron** | **載せる** | 本番実行系である。開発ツールではない |
| **本番で動く管理用 CLI / admin コマンド** | **載せる** | 運用者もサービスの利用者である |
| テスト本体・フィクスチャ・モック・テストヘルパ | **載せない** | `03-impl/tests/`(`03-impl.md` の tests 節) |
| Makefile、setup/build/lint スクリプト、コード生成 | **載せない** | `02-design/environments.md`(コマンドが正)+ `03-impl/environments/`(仕組み) |
| CI 定義(`.github/workflows/` 等)、compose、devcontainer | **載せない** | 同上 |
| E2E のシード投入・リセット | **載せない** | 同上。**E2E で使うからテストではなく開発環境である** |
| 一度きりの移行スクリプト | **載せない** | `03-impl/environments/`。実行済みなら `docs/histories/` |

### 機械が強制するものと、人間が強制するものを混同しない

機械が落とせるのは、**パスで目印に当たるものだけ**である
(`test_markers` / `tooling_markers`。`callgraphs.md` §5.9.1)。

- **目印に当たる** → `build-callgraphs.py` が収集の時点で落とす。手で機能表に書いても、
  その入口はコールグラフに無いので、**FT1 が重大度「高」で捕まえる**(そして代わりの行き先を出す)。
- **当たらない**(`scripts/` `tools/` `bin/` の下の開発者専用コードなど)→ **検査は無い。**
  人間と AI が上の試験を当てる。**これは指針であって規範ではない。**

**人間の判断は機械へ移せる。** 目印が区別できないものを見つけたら、そのプロジェクトの
`callgraph-config.local.json` の `tooling_markers` へ足す(配列は和として併合される)。
そうすれば同じ判断を二度としない — **同じ判断を2回したら設定へ移す**が、この仕組みの習慣である。

## 1. なぜ機能表が要るか

**「モジュール境界での呼び出し単位の関係性」は、境界さえ固定すれば機械的に作れる。**
境界が無ければ作れない。**それが、AI にコードベース全体を読ませていた理由**であり、
機能表はまさにその1つだけを人間の合意として固定する。

固定されると、そこから先は機械の仕事になる(`cluster-features.py`):

```
callgraph × 機能表 ──► ① 各機能に属する関数の集合
                      ② 複数機能から到達される共有関数(= 境界の実体)
                      ③ 機能間の辺と、その代表呼び出し箇所
                      ④ どの入口からも到達しない関数
                      ⑤ 資源(テーブル・バケット・キュー)を介した結合(§7)
```

**③ は文字どおり `relations` の `callees:` である**ので、
**AI が最も誤りやすい部分が機械で埋まる。** AI の仕事は「連携を見つける」から
「機械が出した辺を確認するか棄却し、それを記述する」へ移る。

## 2. 粒度 — 入口1つ = 機能1つ(これが既定)

**入口1つが機能1つである。** それが機械に決定できる唯一の粒度であり、
`relations.md` §1 の「分岐ごとに1仕様ドキュメント」と同じ規則である。

| 入口の種類 | 1機能になる単位 |
|---|---|
| REST | エンドポイント1つ(`POST /v1/orders`) |
| Lambda / イベント / スケジュール | ハンドラ1つ |
| 内部分岐 | 合成シンボル1つ(`app.py::lambda_handler#CREATE`)。ディスパッチャ本体も1機能 |
| 共通基盤(§4) | 昇格させた関数1つ |

おおよその規模: REST 中心のシステムでは「エンドポイント数 = 機能数」。
**数が多いことは問題ではない** — 1つあたりの文章が短くなるだけで、合計は同じである。
**機能を大きくすると、境界がその内側に埋もれる。**

### 統合は人間がすること

複数の入口を1つの機能に併合してよい。**そのときだけ、1行の `入口` の欄が複数の値を持つ。**
**機械が自分で併合することは決してない。** 機械が出すのは**統合候補**(関数集合が大きく重なる
機能の対)である。決定は、人間が機能表へ書くことで決着する。

**逆 — 1つの入口を2つの機能に割ること — は禁止である。** 入口より細かいものは機械的に追跡できない。
割りたいならそれは内部分岐である: `#分岐値` の合成シンボルとして入口を足す。

**統合した行は黙って古くなるので、検査がそれを見張る**(FT5。`callgraphs.md` §6)。
1つのファイルから複数のシンボル ID を並べた行で、そのファイルの未宣言のシンボルがどれも到達
不能なとき、その行はそのファイルの**網羅宣言**である: 中のすべてのシンボルが入口である。
その後、実装がハンドラを足し、誰も行を足さず — そしてそれはエンドポイントではないので —
**FT2 は決してそれを見ない**。代わりに `feature-graph.md` の「どの入口からも到達しない関数」に
積まれる。実測: Vue の画面1枚の入口が 23 のままで実装は 37 に達し、
**欠けた14件のハンドラを見つけたのは人間の独立レビューであって、機械ではなかった。**

## 3. 書式

`docs/03-impl/features.md`。雛形は `.claude/templates/03-features.md`。

```markdown
| 機能ID | 種別 | 入口 | 所属 | 概要 |
|---|---|---|---|---|
| MODULE-order-create | rest-api | POST /v1/orders | MOD-order | 注文を登録する |
| MODULE-order-get | rest-api | GET /v1/orders/{id} | MOD-order | 注文を1件返す |
| MODULE-store-query | function-call | src/db/store.py::Store.query | MOD-db | 注文表を検索する |
```

| 列 | 規則 |
|---|---|
| `機能ID` | `MODULE-<feature-slug>`。**`relations/<機能ID>.md` のファイル名と同一**。`<feature-slug>` = `<module-slug>-<feature>` |
| `種別` | `relations` の `kind` と同一語彙(6値の正は `.claude/directions/relations.md` §3 — ここに写さない) |
| `入口` | エンドポイントID(`POST /v1/orders`、`dispatch CREATE @ app.py::lambda_handler`)または シンボルID(`path::symbol`)。**まずエンドポイントIDとして照合し、無ければシンボルIDとして照合する**(書式では判別しない — cmd 分岐のエンドポイントIDは `::` を含む)。複数は `, ` 区切りで**1行**に書く(統合したときだけ) |
| `所属` | 02 のモジュール分割定義にある `MOD-<slug>` |
| `概要` | 1行80字以内 |

frontmatter は `id: features` / `updated` / `summary` / `keywords` だけである。
**`version` も `verified` も持たない**(下記)。

1枚の表の下に、雛形は記録の節を3つ持つ — 「統合した機能」「昇格させた共通基盤機能」
「棄却した候補辺・確認済みの境界辺」。ここに人間の統合(§2)と昇格(§4)の決定、
および CG4 候補の棄却と境界辺の確認(`callgraphs.md` §6)が保たれるので、
**棄却した候補が次の run で未決のまま戻ってくることがない。**
これらが記録するのは判断だけであり、**境界そのものは表に在る。**

- **入口はコールグラフに実在しなければならない**(検査 FT1)。表記は `callgraphs/` の
  シンボル ID かエンドポイント ID と**1文字も違わず**一致させる。さもないと突き合わせが
  そもそも起きない。
- 行の並びは `所属` → `機能ID` の辞書順に固定する(差分レビューのため)。
- **セルの中の `|` は `\|` でエスケープする。** 入口 ID は `|` を含みうる
  (`dispatch ALL|GROUP @ app.py::lambda_handler`)。
- **版も検証済み記録も持たない。** relations の層とともに `03-impl/index.md` が代表する
  (機能表と relations は常に一緒に変わるので、別々の版を持つと必ずずれる)。

## 4. 共通基盤機能 — 境界はファンインで見つかる

**2つ以上の機能から到達できる関数は、どれか1機能の内部ヘルパではありえない。**
畳み込むと、同じ処理が複数の relations に二度現れる。**それが「モジュール境界」の機械的な定義で
ある。**

```
ファンイン(s) = s に到達できる機能の数
ファンイン(s) ≥ 2  ⟺  s は境界の実体
```

`propose-features.py` が**共通基盤候補**をファンインの降順で並べる。
人間がそのどれかを `function-call` の行として機能表へ足すと、次のクラスタリングが
**その関数を根に昇格させ**、経路はそこで切れ、呼んでいた機能は `callees` の辺を1本得る。

**この反復は収束する。** 根への昇格は経路を切るだけであり、新しい到達性を作ることは決してない。
最短の道は、上流(入口)から下へ向かって定義し、**ファンインの高いものから先に昇格させる**ことである。

**ファンインが高いことは昇格を義務づけない。** 言語標準に近い薄いユーティリティ(型変換、整形)は
畳み込んだままでよい。**判断は人間のもの**であり、機械が出すのは候補と件数だけである。

## 5. ★ 主張の向きによって、使う辺の集合を変える

コールグラフには**確定辺**(名前解決に成功した辺)と**候補辺**(`ambiguous` の候補から展開した辺)が
在る。**両者を混ぜてはならない — しかしどちらも捨ててはならない。** 規則:

| 判定 | 使う辺集合 | 理由 |
|---|---|---|
| 機能間に辺が**在る**と言う | 確定辺のみ → 確度`確定`。候補辺を入れて初めて出るものは確度`候補` | 主張には根拠が要る |
| 関数が**共有**である(= 境界) | 確定辺 ∪ 候補辺 | 境界の**見落とし**が最悪の結果 |
| 関数が**どこからも到達しない** | 確定辺 ∪ 候補辺 | 「到達不能」は最も危険な断定 |
| 機能が**孤立**している | 確定辺 ∪ 候補辺 | 同上 |
| 機能が資源を**触る**(⑤ 資源結合) | 確定辺 ∪ 候補辺 | 「共有」の主張なので広く(`callgraphs.md` §5.11) |

一般化すると: **在るという主張は狭く、無いという主張は広く。**
偽陽性は確度の印つきで生き残り、人間が棄却できる。**偽陰性は誰の目にも触れない。**
機能表とクラスタリングは、後者を出さないことを優先する。

候補辺が使われるのは**クラスタリングの到達性の計算の中だけ**であり、
確定辺と同じ配列に出力されることは決してない。

### 5.1 この規則を意図的に破っている2箇所 — 「無い」を信じる前にこれを知る

**`callgraphs.md` §5.6 の規則4 は、意図的に静かな偽陰性を作る。** 組み込み型のメソッド名
(`.get` `.items` `.read` `.append` `.encode` …)への呼び出しで、レシーバの型が決められなかった
ものは外部として扱われ、**辺がまったく引かれない** — 候補としてすら引かれない。
そこでの偽陽性が取りこぼしを桁違いに上回るのでこの取引を採っており、その正当化はあの節に在る。

**その帰結はここ、原則の側に属する。** ここが「無い」を主張する場所だからである:
**「到達不能」「孤立」「連携なし」は、まさにこの理由で誤りでありうる**のに、
出力にはどこがそうなのかを示す印が無い。規則が2つ従う:

- モジュールが組み込みのような名前のメソッドを持つとき、**「無い」を網羅として報告しては
  ならない。** どの主張が規則4 に乗っているかを言い、人間に見てもらう。
- **モジュール境界を越えるかもしれないものは、規則4 に落とさせるのではなく候補として残す** —
  候補は見えて棄却できるが、落としたものは見えない。

**偽陰性の2つ目の系統的な源は Tier 3 の抽出である**(`callgraphs.md` §5.8):
正規表現で読まれた言語は**構造上**呼び出し関係が不完全なので、そのシンボルに対する
「無い」の主張はすべて規則4 と同じ但し書きを負う。`cluster-features.py` はこれを伝播させる:
④ の表は Tier 3 の言語のシンボルに「Tier 3(取りこぼしの可能性)」の印を付け、
1件でも在ればその節に警告が出る — **人間が見るまで、それらの行は「未確認」として扱い、
決して削除候補として扱わない**(shell / make の多いプロジェクトで効いてくる)。

**この2つが、この向きの意図的な例外のすべてである。** それ以外で偽陰性を生むものは、
取引ではなく欠陥である。

## 6. クラスタリングの結果はどこへ行くか

クラスタリングの結果は **(コールグラフ, 機能表) の純粋関数**である
(`callgraph-design.md` §8.3.1)。一意に定まるので導出物として保てる —
ただし**境界の情報だけを保つ**。

| 出力 | 置き場所 | なぜ |
|---|---|---|
| ② 共有関数(ファンイン) | `docs/03-impl/feature-graph.md` | 境界の実体そのもの。次に昇格させる行の候補として人間が繰り返し見る |
| ③ 機能間の辺 + 呼び出し箇所 | 〃 | **これが「モジュール境界での呼び出し単位の関係性」= この仕組みの目的そのもの**。差分レビューの対象として最も価値が高い |
| ④ どの入口からも到達しない関数 | 〃 | 小さく、それ自体が指摘 |
| ⑤ 同じ資源を触るのに呼び出し辺が無い機能 | 〃 | **呼び出し辺として原理的に存在しない連携**。③ が拾えない領域(`callgraphs.md` §5.11) |
| ① 各機能の関数集合 | **`--format json` のみ** | 全関数×所属で callgraph と同じ桁の量。かつ relations の `impl:` に写るので実質的に重複 |

`feature-graph.md` の規則:

- **`callgraphs/` の中に置かない。** callgraphs/ の不変則は「**実装**が変わらない限り1バイトも
  変わらない」だが、この結果は**実装が同一でも機能表が変われば変わる**。
  不変則の違うものを同じディレクトリに置くと、「コールグラフの変化だけをレビューする」が壊れる。
- **この文書の不変則は「実装か機能表が変わらない限り1バイトも変わらない」である。**
  鮮度は保存せず、`cluster-features.py --check` で検査する(callgraphs と同じ考え方)。
- **生成物である。決して手で編集しない。** 版も検証済み記録も持たない。
- **これは仕様ではない。** relations の代わりに使ってはならない(`callgraphs.md` §7 と同じ誤り)。
  **その警告を必ず先頭に印字する。**

**「これは relations の `callees:` の重複ではないのか」への答え**: そのとおりであり、
**それがこの仕組みである。** この系は意図的に2つの表現を保ち — 02⇄03 と コールグラフ⇄relations —
機械的に差分を取って抜けを検出する。導出物(機械の主張)と宣言(AI の主張)が共存するのは、
CG3 / CG4 がその隙間を見せられるようにするためである。
**一方をもう一方に合わせて手で書き換えることは禁止である**(それは差分を消すことである)。

## 6.1 機能表は SSOT である — 書き手の閉じた一覧は原則1 が持つ

機能表は SSOT の一部なので、他のすべての 03 の文書と同じ体制で動く:
**誰が書いてよいかの正は原則1 の閉じた一覧である**(`principles.md` §1。ここには写さない —
写せば正が2つになる)。日々の変更を担うのは**クロージャがそれを含む `/build`** であり、
直接編集する(機能を足せば行が増え、改名すれば行を書き換え、廃止すれば行を消す)。そして F1 の出口の整合確認と `/verify-impl` の FT / CG 検査が、
それをコードに対して正直に保つ。編集から**次の再生成**(`/verify-impl`、または先に走った
`/relations`)までのあいだ、**グラフは正当に古い**(その区間の意味は `callgraphs.md` §6.1 が
所有する)。

| 変更 | 書き方 |
|---|---|
| 機能を足す | 新しい機能IDの行を足し、`relations/MODULE-*.md` を1本足す(FT3 が 1:1 を見る) |
| 機能を変更する | 同じ機能IDの行を書き換える |
| 機能を廃止する | 行を消し、対の `MODULE-*.md` も消す(片方だけは FT3 が落とす) |

`feature-graph.md` は道具の出力(`cluster-features.py`)であり、決して手で編集しない —
**ツール生成領域**なので、`/verify-impl` と `/relations`(**どのモードでも** — 検査モードを含む)
が再生成する(`principles.md` §1)。

## 7. 機械と人間の分担(この仕組みの要点)

**人間が触るのは行2だけであり、それも1回だけである** — `/relations` §3A で、
分割定義と機能表を一緒に載せた1枚のシートで。ここに在る他のすべての判断は AI のものであり、
決めて開示する(境界が問う基準を通る唯一のものである理由は
`.claude/directions/delegation.md` §1 に在る)。
**行2を、繰り返し問うてよい許可としても、このファイルの他のことを問うてよい許可としても、
決して読んではならない。**

| # | 誰 | すること |
|---|---|---|
| 1 | 機械 | `propose-features.py` — 入口一覧とファンインから、機能候補・共通基盤候補を出す |
| 2 | **AI → 人間** | **AI が機能表を起案し、人間が合意する。ここだけが判断** |
| 3 | 機械 | `cluster-features.py` — ①〜⑤を出し、②③④⑤を `feature-graph.md` に書く。`callees` の材料が確定する |
| 4 | AI | relations 本文を書く(目的・流れ・連携内容・異常系)。機械が出した辺を**棄却してもよいが、理由を書く**。⑤ の資源結合を `callees` に書かない(置き場は `callgraphs.md` §5.11) |
| 5 | 機械 | `callgraph-check.py` — 宣言(relations)⇄ クラスタリング結果 の差分 |

## 8. 決してしてはならないこと

- **機械に機能表を書かせて決着させること。** 機械の役目は候補を出すところで終わる。
  **境界は設計判断である。**
- **1つの入口を複数の機能に割ること。** 追跡できなくなる。分岐なら、合成シンボルとして入口を足す。
- **入口の表記をコールグラフとずらしたままにすること。** 突き合わせが黙って外れる。
- **`feature-graph.md` を手で編集すること、または relations の代わりに使うこと。**
  それは生成物である(§6)。
- **① (各機能の関数集合)を `docs/` に書くこと。** コールグラフと同じ桁の量であり、
  `impl:` と重複する(§6)。
- **候補辺を確定辺として出力すること。** 確度を落とすことと辺を捨てることは別物である(§5)。
- **資源結合を `callees` に書くこと。** それは呼び出しではないので、対称性の検査と CG3 が壊れる
  (`callgraphs.md` §5.11)。
- **テストコードや開発ツールを機能として入れること。** 本番実行系から到達しないものは機能ではない
  (§0.1)。
- **機能表に無い入口を relations に書くこと、またはその逆。**
  1:1 がいったん壊れると、**すべての検査が無意味になる。**
- **原則1 の書き手の閉じた一覧の外で機能表を書き換えること。** 表は SSOT である —
  §6.1 のとおり、誰が書いてよいかの正は `principles.md` §1 だけが持つ(ここには写さない)。
  `/build` がそれを書けるのは自分のクロージャの中だけである。
