# flows.md — 4つのタスクフローと及第ライン

日本語で書く。**CLAUDE.md §4 が束縛する1行を持ち、このファイルが機構の全体を持つ。**
違う読み方をされうるとき、**何が束縛するかは CLAUDE.md が決め、それが何を意味するかはこの
ファイルが決める。** この模型の背後にある設計の記録(実測、裁定、廃止されたフェーズモデル)は
本流のリポジトリに在り、このキットには入っていない。

## 1. 模型を1段落で

すべての仕事は、**独立・冪等・いつでも走れる4つのフロー**のどれか1本として走る:
F1 構築(`/build`)、F2 文書整合(`/verify-docs`)、F3 実装整合(`/verify-impl`)、
F4 試験(`/verify-tests`)。品質を守るのは、廃止されたフェーズモデルが持っていた段どうしの直列の検査ではなく、
**及第ライン**である:

> **デプロイ/リリースを判断する瞬間、すべての検証が現在の状態に対して green である。**
> 途中では、個々のフローが green である必要は無い。

リリースの完了定義(CLAUDE.md §3)は変わっていない。動いたのは検証の*時点*だけである —
「タスクごと」から「デプロイの時点で。あいだはラインを下回っていてよい」へ。それを安全にしているのが
§2〜§6 の機構の集合であり、**どれか1つを外すと契約は成り立たない。**

検査は二重の網である:

| 網 | 範囲 | 独立性 | いつ |
|---|---|---|---|
| タスク内整合確認(F1 の段4) | そのタスクの文書とコード | 同じ文脈(自己点検) | 毎タスク、その出口で |
| verify 系 F2/F3/F4 | 増分は最終 green 鮮度スタンプ以降の差分、全数はリポジトリ全体 | 独立した文脈 | 増分は人間の指示(§2.1)、全数は人間の明示か人間が仕掛けた固定時刻、デプロイ前は必須 |

1つ目の網は「いま作ったずれ」をその場で殺す。2つ目は、自己点検には見えないものと、
タスクを跨ぐすべてのずれを捕まえる。**実装前の紙の検査は存在しない** —
2026-08-19 の裁定が、critical の例外も置かずにそれを廃した:
AI が両方をやる以上、**コードを見るのは紙を検査するより高くつかない**のであり、
verify 系フローを通らずにデプロイされるものは何も無い。

## 2. 鮮度スタンプとデプロイゲート(`stamps.py`)

各 verify 系フローは、完走時に `{flow, scope, commit, at, verdict}` を記録する:

```bash
python3 .claude/scripts/stamps.py record verify-docs green
python3 .claude/scripts/stamps.py record verify-tests green --scope unit --scope e2e ...
python3 .claude/scripts/stamps.py record verify-impl green --covers docs/02-design/x.md  # 部分
python3 .claude/scripts/stamps.py deps         # 依存集合(この出力が正)
python3 .claude/scripts/stamps.py check        # デプロイゲート
```

**依存集合は (flow, scope) ごとに `stamps.py` の `DEPENDS` が持ち、`stamps.py deps` が印字する。
この文書はその中身を書き写さない** — 2箇所に書けば必ず食い違う。要点だけ: **許可リストである**。
**この失効判定が、verify 系を2本同時に走らせない本当の理由でもある**(verify は書くので、
重ねると互いの green を失効させ合う — 艦隊運用の直列の規則は `orchestration.md` §3.4)。
宣言されたパスが動いたときだけ鮮度スタンプは失効し、**宣言されていないものは何が動いても失効させ
ない**(その正しさは失効判定ではなくテストが動かして確かめる)。コードの置き場だけはプロジェクト
ごとに違うので `flow-config(.local).json` の `code_roots` が正であり、
**未宣言ならデプロイゲートは red**。
**試験区分(`scope`)ごとのコードの置き場は `scope_roots` に別に宣言でき、宣言するとその試験区分は自分の
置き場に掛からない変更では失効しなくなる — 未宣言の試験区分は広いほうへ倒す**(qa は `ui_roots`、
それ以外は `code_roots` 全体。過大近似・安全側。red にはしない。inspection-21 V-9)。
**`ui_roots`(UI に関わるコードの置き場)は qa の既定として残る** — 宣言すると
バックエンドだけの変更で探索的ブラウザQAは失効しなくなる(inspection-17 判断5)。
**試験区分の中は当面 suite 丸ごとのままである** — どの試験がどのパスを覆うかを機械で言えない間は、
減らせるのは「無関係な試験区分まで一律に失効する」ぶんだけである。

**宣言していないことの代償は、見えるようにしてある** ★(2026-08-22 の人間の指示)。
過大近似は安全側だが、余分な失効を毎回払う。`stamps.py check` と `deps` は、
**置き場の宣言が無いせいで広く倒れている試験区分をそう言う** — 「失効 — 覆えていない依存 N 件」
だけでは、その N が実際の依存なのか宣言漏れのぶんなのかを人間も AI も区別できない
(実測: コードの置き場を1つ宣言しただけのプロジェクトで、Dockerfile 1本の変更が
unit・integration・e2e・qa の4つの試験区分すべてを同時に失効させていた)。**判定は変えていない。**
**注記の在り処は2つで、それで全部である** ★ — 内訳と直し方は `stamps.py check` と `deps` が、
件数だけは `check-debt.py` が出す(§4)。**どちらも宣言を義務にしない** —
`scope_roots` / `ui_roots` は狭く誤ると穴になるので、正は下の `code_excludes` と同じ
「迷ったら書かない」である(inspection-23 C-8)。

**`code_excludes` — 置き場の中に在るが検証の入力ではないもの** ★(同じ日の指示)。
コードの置き場に混ざったメモ・固定データ・同梱バイナリのように、どの検証も読まないパスは
`flow-config(.local).json` の `code_excludes` に宣言でき、宣言したものは動いても失効させない。
**既定は空 = 今までどおり**(書かなければ何も変わらない)。
**狭く誤ると穴になる** — 検証が実際に読むものを書くと、変えても失効せず古い green のまま
出荷できる。`ui_roots` と同じ但し書きが掛かる: **迷ったら書かない。**
**どの置き場より真に狭い項目だけを受け付ける。** 落ちるのは3種類である — 置き場の**外**
(文書側の依存を黙って外す口になる)、置き場の**親**、そして**どれかの置き場と等しいもの**
(後の2つは、その置き場ごと失効判定を殺す)。**置き場そのものを外したいなら、
`code_excludes` ではなく `code_roots` からその項目を消すのが正しい形である。**
置き場が**ファイル**のときは、その下に在るものは存在しえないので容れ物に数えない。
宣言は鮮度スタンプへ焼き込むので、**変えた時点で失効する**(`code_roots` と同型。D8)。

**失効の例外は2つで、補強が1つ在る**(inspection-16 D2・D8 と 2026-08-27)。
**2つの例外はどちらも「機械が持つ領域だけが動いた」という同じ形をしており、判定は同じ関数
(`stamps.py` の `machine_owned_only`)に乗っている。**

**例外(1) 管理欄だけの変更は失効を作らない** —
frontmatter の `updated:` 行・`verified:` ブロック・`version:` 行だけが
動いた docs の変更は依存の変更と数えない(F2 の検証済み記録の書込みが F3 を毎周失効させる構造を
消すため)。

**この管理欄に `version:` 行そのものが入るのは、2026-08-25 の人間の裁定である** ★ —
inspection-16 D2 は例外を「MAJOR.MINOR が動かない `version:`」= PATCH の繰り上げまでで
切っていた。**その線をここで引き直している。** 理由が次の段落である。

**失効を決めるのは中身であって、版の札ではない。** 本文と、管理欄以外の frontmatter が
動いていないなら、`version:` が MINOR へ、あるいは MAJOR へ繰り上がっていても
失効させない。(**「動いていない」を判定するとき、frontmatter の行の区切り方の違い —
改行コードなど — は見ない** ★。そこまでバイトで比べると、改行コードが違うだけの環境で
毎回失効することになる。本文はバイトで比べる。)「MINOR = 意味が動いた」は**中身についての宣言**であって、中身が動いていない
ならその宣言は偽であり、事実と自己申告が食い違うときに採るのは事実である(原則2)。
**中身が動いていれば版が据え置きでも失効するので、これは穴ではない。**

**この緩和が掛かるのは、変更の前と後の両方が「正しい形の `version:` を
ちょうど1行」持つときだけである** — 版の行が消えた・値が壊れた・行が重複した側では、版を
本文と同じに扱うので、その変更はそのまま失効させる。**そうしないと、`version:` を消す/壊す
変更が管理欄扱いになり、壊れた版が古い green を延命させる。**

**これを外していたあいだに何が起きていたか**(2026-08-25 の実測): 検証済み記録を
打ち直すだけの run が本文無変更のまま MINOR を上げ、**その1本だけで相手フローの鮮度スタンプが
死んでいた** — しかも上流の版が上がると下流の `verified.against` の行が動き、そこでまた版が
上がる連鎖になっていた(20文書を打ち直した run で、本文が動いたのは4文書だけである)。
**連鎖の源を断つのは原則6 側である**(検証済み記録を打ち直すだけの run は `version:` を動かさない)—
こちらは、それでも上がってしまった版を失効の理由にしない、という受け側の手当てである。

**例外(2) 機械の欄の中身だけの変更も失効を作らない** ★(2026-08-27)。
`<!-- BEGIN GENERATED: <道具名> … -->` から `<!-- END GENERATED: <道具名> -->` までの**中身**が
動いても、**手書きの部分は動いていない**ので、読み比べる検査の結論は古くならない
(書式と趣旨の正は `conventions.md` §4)。
**この除外はパス単位では書けない** ★ — 機械の欄は手で保守する文書の**中に**在るので、
下の `EXCLUDES` でファイルごと外すと**同じ文書の手書きの部分の変更まで失効しなくなる**。
だから判定は**区画単位**であり、管理欄と同じ仕組み(`stamps.py` の `machine_owned_only`)に
乗っている。**印そのものは比較に残す** — 区画が増えた・消えた・`id` が変わったのは中身の
変更である(道具の持ち場が動いたということだからである)。
**剥ぐのは道具名を問わない** — `build-facts.py` が埋める事実の欄も、`build-index.py` が
埋める索引の欄も、同じく機械が持つ区画だからである。

補強のほうは
**`code_roots` の宣言は記録時の値が鮮度スタンプへ焼き込まれ、現在の宣言と違えば失効**になる —
**設定ファイルはどのフローの依存集合にも入っていないので、それが動いても差分は失効を作らない**。
**焼き込みだけが「見る範囲を変えたら見直す」を機械で守る。**

**許可リストからの除外は2件である** ★ — **根拠は1つだけで、それは
「見ないと宣言した場所は、動いても検証結果を古くしない」= 分担の宣言そのものである。**
この根拠に当たらない除外規則は書かない。除外された領域は `--covers` でも覆えない
(覆う対象が無いため)。

1. **F2 は 03-impl のうちツール生成領域(`callgraphs/` と `feature-graph.md`)の中身を
   検査しない**と分担で宣言している(`/verify-docs` §1)ので、そこが動いても F2 は失効しない。
   数えていたころは、F3 がコードの変更を機械的に転記しただけの run でも F2 が失効し、
   毎周の覆い直しを払っていた(inspection-20 V-2)。
2. **F2 は残務(`docs/residual.md`)を検査の対象にしない** ★(2026-08-27)。
   残務は 3チャネルの「キュー」の出口であり、**F2 自身も、他の検証フローも、そこへ所見を
   1行足す**。依存に数えていたので、**残務へ1行書いた run が F2 を失効させ、同じ検証の周の
   中で F2 をもう1本払っていた**(2026-08-26 の実測: 1つの検証の周で検査が6本回り、
   6本目が回った直接の原因が残務への1行だった)。**残務の中身を見る者が居なくなるわけではない** —
   行の形と件数は `check-backlog.py` と `doc-health.py` が見る(§4)。

**この2件目は「所見の書き出しが、その所見を出した検査自身を失効させる」形を消すためのもので
あって、残務の内容を軽く扱ってよいという意味ではない。**

**E2E 台本の置き場は宣言できる。** ★ `flow-config(.local).json` の `e2e_scripts_in` に
`"testing"` と書けるのは、**`E2E-nn` を `docs/02-design/testing.md` へ切り出した
プロジェクトだけ**である。そのとき e2e / qa の依存から `system.md` が外れ、代わりに
`testing.md` が入る — モジュール分割定義の散文を直しただけの `/build` で、最も高価な
E2E suite 全件と探索的ブラウザQAが失効する過大近似が消える(inspection-20 V-4)。
**未宣言・不正値は `"system"` へ倒す**(過大近似・安全側)。**`testing.md` がまだ無いのに
`"testing"` と宣言しても無視して `"system"` として扱う** — 誤宣言で、台本の在る `system.md` が
依存から静かに落ちるのを防ぐためである。**中身の側は `check-ssot.py` CS23 が見る**:
`"testing"` と宣言したのに `system.md` に `E2E-nn` が残っていたら違反である
(`stamps.py` はファイルの存在までしか見られないので、この2つで宣言の裏を取る)。
**CS23 も同じ倒し方をする** — `testing.md` が無いあいだは宣言ごと無視するので、
正しく安全側へ倒れている構成が違反になることはない。この宣言も `code_roots` と同じく鮮度スタンプへ
焼き込まれ、変えれば失効する(**欄を持たない古い鮮度スタンプも既定値 `"system"` として比べる** —
飛ばすと宣言を変えた瞬間だけ fail-open になる)。

**`code_roots` には、振る舞いを運ぶ設定ファイルも入れる。** ★ 許可リストに載らないものは
何が動いても失効させないので、**`docker-compose.yml`・CI の定義・マイグレーション・
起動スクリプトのように、動かすと製品の振る舞いが変わるものを宣言から落とすと、
それらの変更はどのフローも再検証しないまま出荷できる**(除外リストを止めた 2026-08-20 の裁定は
同梱物と生成物についてのものであって、振る舞いを運ぶ設定を外に置いてよいという意味ではない)。
**判断の基準は1つである**: そのファイルを変えると製品の振る舞いかテストの結果が変わりうるなら、
それはコードの置き場に属する。

**`code_roots` を最初に宣言するのは、lint/テストの実際のコマンドを 02 に書くのと同じ1回である**
(`/build` §3 の入口条件・`/retrofit` §6 手順2' — その時点でコードの置き場は実在している)。
**ただし「1回」は書き始めのことであって、書いたあと放っておいてよいという意味ではない** ★ —
`/build` は毎回、そのタスクが触るコードのパスが宣言済みの接頭辞の下に在るかを見て、無ければ足す
(inspection-23 B-1。許可リストなので、宣言から漏れたパスは何が動いても失効を作らない)。
**足せば宣言が変わり、その宣言を焼き込んだ鮮度スタンプが失効する** — 見る範囲を変えたら見直す、である。**未宣言は
verify では動かせない red** である: 何度回しても `未宣言` が返るだけで、`promote` も全件保留に
なる。**回して閉じない red を回し続けないために、この1つは verify の対象ではなく設定の欠落として
扱う**(中央エージェント側の扱いは `orchestration.md` §3.0 の4)。

**記録は、そのフローの依存が空になってから。** 失効判定は未コミット・未追跡も見るので(`stamps.py` の
`changed_since`)、書いたものをコミットする前に打った green は**書いた瞬間に失効している**。
`stamps.py record` は依存(部分記録なら覆い)に未コミットの変更が在るとき **green を拒む**
(red はいつでも記録できる — red は green の主張ではない)。ゆえに各フローの並びは
**書く → コミットする → `record` → `promote`** である。試験成果物のような検証の産物は
`code_roots` の外に置くか `.gitignore` に入れる — さもないと自分の産物で自分の鮮度スタンプを殺す。

**鮮度スタンプは git で共有する。** ★ `.claude/state/stamps.json` は追跡し、コミットする。
記録の中身は `{フロー, scope, コミット, 時刻, 判定}` であり、**どれも中身から決まる値で、
判定の手続きも `git diff` と `git status` だけである** — つまり最初から「どこでも確かめられる形」を
している。それを git の外に置けば、**検証が通った状態からコードが変わっていないかを、
その1か所でしか確かめられなくなる。** 打つのは1周につき1回で、並びはこうなる:

  **書く → コミットする(作業)→ `record` → 1周の終わりに1回、鮮度スタンプをコミットする**

- **記録のたびにコミットしない。** 1周の中では `record` が何度も走る(F4 は試験区分ごと、
  終わりには覆い直しもある)ので、まとめて1つのコミットにする。
- **`.claude/state/` はどのフローの依存集合にも入っていない**(`stamps.py deps` で確かめられる)
  ので、このコミットは鮮度スタンプを失効させない。**`code_roots` にリポジトリの根を丸ごと
  宣言した場合だけは例外である** — そこは `deps` の印字がそう言うので、推測せず読む。
- **記録したあとに、その作業のコミットを `git commit --amend` / rebase / squash してはならない。**
  ★ 焼き込んだコミットが履歴から消えると、`check` はその鮮度スタンプを **`判定不能`** と言う
  (`stamps.py`)。同じ理由で、作業ブランチを保護ブランチへ入れるときも**マージである**
  (§7.1)。
- **1周が途中で中断されたら、鮮度スタンプは未コミットのまま残る**(消えはしないが共有されない)。
  **次の周の頭で拾ってコミットする** — 周の頭は `check-debt.py --demote` を運ぶ段なので、そこで一緒に打つ。
- **コミットは明示のパスで stage し、コミットにもそのパスを名指す** ★
  (`git add -A` を使わない。`git commit -m "…" -- <パス>`)。拾う前の鮮度スタンプが、
  次の `/build` のコミットへ黙って相乗りするのを防ぐ。**艦隊運用ではこれが混入も防ぐ**:
  登録場所は同じ作業ツリーの全員が共有するので、パスを名指さないコミットは
  **並走している別のタスクの書きかけを、自分の名で刻む**(`orchestration.md` §3.4.2)。
  **新しく作ったファイルは先に `git add` する** ★ — 未追跡のまま `-- <パス>` で指すと
  git は `pathspec … did not match any file(s) known to git` で失敗する(実測)。
  **ディレクトリを指したときも、その中の未追跡ファイルは黙って入らない。**
- **メッセージは必ず `-m` で渡す** ★ — この節が命じるコミットは、どれも人が端末に付かない
  実行で打たれうる。`-m` を省くと git はエディタを開こうとし、**そこで止まる**
  (この節の「コミットする」はすべてこの形である。§7 の増分の検証の周・全数の周も同じ)。
- **明示のパスで stage する以上、共有すると決めたものには打ち手が要る** ★
  (`.claude/.gitignore` の先頭のコメント):
  **`.claude/scripts/*.local.json` は、それを書いたフローが同じコミットに入れる**
  (`code_roots` を書くのは `/build` の入口条件 — 上の §2)。
  **`.claude/settings.local.json` も同じく、書いた者が入れる。**
  **`.claude/missions/` は中央エージェントがミッションを閉じるときに入れる**
  (`/mission` §5。**途中の台帳は作業ツリーに在れば足りる** — 台帳が越えさせるのは
  `/clear` とセッションの死であって、それはコミットしなくても越えられる)。**「共有する」と書いてあるだけで誰も stage しないなら、
  未追跡のまま残る。**

**部分再検証**: 範囲を絞って回した run は `record … --covers <path>` で記録する。判定は
全体スタンプと部分スタンプの**併合**で行い、green は **「動いた依存パス1本ごとに、その最後の変更
以後にそこを覆う green が在る」**ときにだけ成立する。覆えないパスが1本でも残れば失効であり、
**見ていない範囲を green と言うことはできない**。`check` は red のとき**回すべき最小の範囲**と、
それを記録する `record --covers …` を印字する — 「全部やり直し」は既定ではない。

**覆い切った部分は、基準点を進めて畳む** ★(2026-08-25)。**green の** `record --covers` の結果、
併合の判定が green になったなら、`record` はその場で**基準点(latest と last_green)をその
commit へ進め、部分スタンプを捨てる**。併合が green だということは、基準点以降に動いた依存が
1本残らず覆われているということであり、それは**その commit に対する green そのもの**だから
である。**主張は1バイトも広がらない** — 既に出ている判定を正規化しているだけで、基準点が無い・
latest が red・依存に未コミットが在る・宣言(`code_roots` 等)が記録時と違う、のいずれでも
判定は green にならないので、畳みも起きない。

**`red --covers` は決して畳まない。畳まないかわりに、直近の判定(latest)を red へ進める** ★。
部分を回して red だった、も記録できる。そのとき併合の判定は**追記前の全体 green**を基準に出るので
green になりうるが、そこで畳むと red の記録が最終 green の基準点に入り、下の「素の red は最終
green の基準点を消さない」を破って、以後 `promote` が red を green の基準として読む。
**畳むのは green の記録だけである。** そして**進めないほうも穴である** — latest を以前の green の
まま置くと、基準点以降の依存変更が0件のとき `check` がそのフローを green と読み、**red だと
分かっている範囲を抱えたままデプロイゲートが開く**。latest は「直近の判定」であり、デプロイゲートは
それを見る。**`red --covers` は latest だけを動かし、最終 green の基準点も部分スタンプも
消さない** — 素の red とそこは同じである。

**畳まないと閉じない。** 進めなければ基準点は最後の「全部回した green」に据え置かれ、
**覆う義務のあるパスの集合が単調に増え続ける** — 覆いの条件は「そのパスの最後の書き手で
あること」なので(上の「その最後の変更以後に」)、集合が育つほど、誰かが1本触るたびに
どれかの覆いが死ぬ。**F2 と F3 は互いの依存(`docs/02-design/` と `docs/03-impl/`)へ本文を
書く**ので、交互に回すと義務が積み上がって閉じなくなる。実測(2026-08-23、7周):
F3 の1周が F2 の依存を毎回 3〜10 本、F2 の1周が F3 の依存を毎回 1〜3 本動かしており、
**7周まわしてもデプロイゲートは閉じなかった**。この相互の書込み自体は正当である
(互いに相手が検証した中身を動かしている)ので、除外では消せない — 消せるのは、
**覆い終えた区間を基準点に畳まずに持ち越していた**ぶんだけである。

**素の red は「最終 green の基準点」を消さない**(inspection-17 判断4)。鮮度スタンプは直近の判定
(latest)と最終 green(last_green)を別々に持ち、素の red は latest だけを動かす — 部分スタンプ
も捨てない。増分の範囲(「最終 green 鮮度スタンプ以降の差分」)はどのフローでも last_green 基準で
あり、**red を記録した次の run が全数化することはない**。デプロイゲートは latest を見るので
red のまま出荷はできない。red の解消は、`check` が印字する「最終 green 以降に動いた依存」を
増分で回してから**素の green** で閉じる(`--covers` では latest が red のままデプロイゲートが開かない。
未変更部は last_green が保証している)。**critical: true の記録が検証待ちのあいだ、F2/F3 の
green は `--lens <実際に走った独立レビューの名前>` を添えないと `record` が拒む** —
CLAUDE.md §6 の「critical は独立レビュー必須」の機械接続で、防ぐのは忘れと依頼の不達である
(inspection-17 判断9)。**この要求の範囲は run に合わせる** ★: `--covers` で覆いを申告した
run は、**その覆いにクロージャが掛かる critical 記録だけ**を見る(掛からなければ `--lens` は要らない)。
覆いを持たない run は依存集合まるごとを主張するので、critical 記録が1件でも在れば要求される。
**免除の粒度と機械の粒度を揃えるためである**(`/verify-docs` §2 は 3ファイル以下・critical 非含有の
run に独立レビューを起こすなと指示しており、揃っていないと「指示どおりに走ると記録できない」
run が生まれ、実在しない独立レビュー名の申告を誘う。inspection-19 V-2)。

**デプロイゲートは機械的で、かつ複合である**(`stamps.py check`、inspection-14):
green には次のすべてが要る — すべての鮮度スタンプ(F2、F3、`flow-config.json` の `f4_scopes` の
**全 F4 試験区分**)が現在の状態に対して green であること。
**`building` または `awaiting-verify` の構築記録が0件**(前者はまだ作業が終わっていないもの、
後者は作業は終わったが検証がまだ確認していないもの)。
**`docs/sheets/` のファイルが0件**(未回答の人間への問いを抱えたまま出荷しない)。
**`type: bug` かつ `severity: 高` の課題票が0件**(完了定義の3項目目の機械近似)。
**「かつ」である** ★ — `severity: 中` の bug も、bug でない `severity: 高` も、これは止めない。
or にすると及第ラインが不具合ゼロに戻ってしまう(及第ライン =「不具合ゼロではない」—
`glossary.md` §3)。
「現在の状態に対して」は、その (flow, scope) の宣言された依存の外に落ちる変更をすべて許容する。
それ以外は red であり、欠けている駒を作らねばならない —
**いつでもよい。決まった時刻を待つ義務は決して無い。** F4 は試験区分ごとに記録する。
引数なしの `/verify-tests` はすべてを走らせ、全試験区分を記録する(裁定 D'-4)。
UI を持たないプロジェクトは `flow-config.local.json` で `f4_scopes` から `qa` を外し、
その理由を `docs/pendings.md` の棚上げの項目(`P-nnn`)として記録する(`check` は集合が狭められているときに注記を印字する)。
**ただし 02 の宣言の行が先である** ★ — この2筆は `02-design/environments.md` の
「ブラウザQAの宛先」の節が負う1行の**写し**であり、**写しが単独で立つことはない**
(`conventions.md` §1)。02 にその行が無いあいだは外せず、F4 は `qa` を red のまま報告して
その行を書く課題票を起こす(`/verify-tests` §1)。

**どのパスがどの鮮度スタンプを無効にするかは、印字させるのであって推測しない。** `stamps.py deps` は
(flow, scope) ごとの依存集合をそのまま出す。**この文書に表を写さない**(§2 冒頭の理由)。
推測が高く付いた実測が2つある: 2026-08-20 の損失は 「F2 は 00〜02 だけ見る」と決めた
スケジューラが F2 の検証の周と `/build` を並走させ、その build が `docs/03-impl/tests/e2e.md` を
書いてその周を捨てさせた(**F2 は 03-impl にも依存する**)。逆向きの損失もある: 除外リスト時代は
検証の入力でないファイル(同梱物・生成物)の差分で全試験区分が失効し、無関係な再検証を強いた
— だから依存集合は許可リストである。**帰結はこの文書で数えず `deps` で数える**。それでも1つだけ
言っておく価値があるのは、**どのフローも自分と他人の鮮度スタンプを殺しうる**ことである: F2 と F3 は
どちらも 02 と 03-impl に依存し、どちらもそこへ書く。F4 も 「`docs/issues/` しか書かないから
誰も殺さない」ではない — 課題票を起こせば `docs/issues/index.md`(F2 の依存)が動き、
テスト自体の欠陥を直せばテストコード(F3 と F4 全試験区分の依存)が動く。**だから 1周の終わりには
必ず `stamps.py check` を読む**(§2.1)。

**`stamps.py promote` が `awaiting-verify` から `verified` への唯一の扉であり**、
判定は**その記録自身のコミット時点**で行う: フローごとに、全体スタンプとそのコミットのあいだで
動いた依存を取り、**そのそれぞれが green(全体または部分)に覆われているときに限って**昇格させる。
**green の全体スタンプをまだ1度も持たないフローは、すべての記録を止める** —
免除ではなく fail-closed である。あるフローの依存を1つも動かしていない記録は、そのフローの
古い鮮度スタンプに止められない — 上のデプロイゲートは依然として*現在の*状態に対する green を要求
するので、免除しているのではなく、二重に数えるのをやめているだけである。
`is_ancestor(record, stamp)` は区間を空にするので、**前の規則はこの規則の特別な場合である。**
**`verified` への遷移を手で書き換えるスキルは1つも無い** — `awaiting-verify` → `verified` の扉は
`stamps.py promote` の専有である(`building` → `awaiting-verify` は `/build` §5 が自分で書く)。
各 verify 系フローは自分の鮮度スタンプを記録した後に
`promote` を走らせ、何が動いたかを報告する。

文書ごとの `verified`(検証済み記録)は変わっていない(原則6)— 書き手がいま F2(および 03 層の
代表については F3)になっただけである。既存の「MINOR が検証済み記録を無効にする」機構は、
**F1 が触った文書に対する「作ったばかりで、まだ検証していない」の正直な表示**としても働く。

### 2.1 増分と全数 — 起動契機は条件で決まる

**引数の有無が二つの別物を選ぶ。** 混ぜて運用したのが 2026-08-20 の損失である(全数 `all` を1日6回
出し、うち1周は未配車の要望3件を抱えたまま回して丸ごと無駄になった)。

| | 何を見るか | 起動契機(条件) |
|---|---|---|
| **増分** — `/verify-impl` `/verify-docs`(引数なし)、`/verify-tests <試験区分。複数並べてよい>` | 自分の最終 green 鮮度スタンプ以降の差分。F3 は `relations-query.py --impact` の到達で閉じ、F2 は `source` の下流と失効した検証済み記録を足す(各 SKILL.md §0 が正)。F4 は名指した試験区分の suite を丸ごと | **人間の指示** ★(2026-09-05 に自動の契機(真の idle — 書込み0本・未配車0件・修繕キュー空で自動発火)を廃した — 人間の裁定。検証は人間が指定したタイミングで回す)。**実行は走行中の書込み作業指示が0本になってから**(書込みを抱えたまま回した周は二重払い — 下の ★)。計器は起動契機を作らない — 拒むものがもう無いので、「閉じたデプロイゲート」という契機も存在しない |
| **全数** — `/verify-impl all` `/verify-docs all`、`/verify-tests`(引数なし=全試験区分) | SSOT 全体・全モジュール・全試験区分。**F2 はここでしか、用語の例が埋まっているかの点検と、決定の見直す条件の発火を見ない**(`verify-docs/SKILL.md` §1 の A0) | **人間の明示指示**、または **要望台帳を読まない固定時刻のスケジュール**(cron・定時)。要望の到着とは独立に起こる |

**F4 に増分は無い。あるのは試験区分別の記録だけである。** ★ 名指した試験区分は suite を丸ごと走らせる
ので、**試験区分を複数の作業指示に割っても走る試験は引数なしと同一**である(差分駆動が無い)。
そしてデプロイゲートは `f4_scopes` の**全試験区分**の green を要求し、
**その試験区分の置き場のコードが動けばその試験区分が失効する**(`scope_roots` を宣言していない試験区分は広いほうへ倒す —
qa は `ui_roots`、それ以外は `code_roots` 全体で判定するので、コードが動けば同時に失効する)。
ゆえに **F4 の1周とは「`stamps.py check` が green でないと言った試験区分を1本にまとめて回すこと」**である —
コード変更の直後はそれが全試験区分に一致する。**green の試験区分は回し直さない**(次項のフロー選別と
同じ規則の試験区分粒度 — 02 の散文だけが動いた後の unit/integration が典型)。逆に、red の試験区分を
残したまま周を「完了」とは呼べない — 全試験区分が揃う瞬間が来ず、`promote` も止まったままになる。
**試験区分を分けて出しても走る量は減らない** — 分けて得られるのは報告と失敗の切り分けだけであり、
その代償は次の ★ が言う増幅である(スケジューラ側の形は `orchestration.md` §3.0 の4)。
**そして red の試験区分は分けない** ★ — 分けると、後の試験区分の自動修正のコミットが
先の試験区分の打ちたての green をコード依存で失効させ、周の終わりに suite 丸ごとの再実行を
払うことになる(inspection-20 V-3)。**全試験区分が red なら引数なしで1本、一部だけが red なら
その red の試験区分を並べて1本**である(`/verify-tests` は試験区分を複数受ける — inspection-23 B-6)。
どちらの1本も、全修正のコミットの後に走らせた試験区分をまとめて記録するので、この増幅が起きない。
**green の試験区分は並べない**(上の「green の試験区分は回し直さない」がそのまま掛かる)。
報告が40行 / 2,000バイトに収まらないときだけ、
失敗した試験区分の詳細をファイルに落としてパスで示す。

**1周に出すのは、`stamps.py check` が green でないと言ったフローだけである。** ★ 00/01 だけが
動いた後に F3 と F4 を回しても、失効していないものを回し直すだけで何も閉じない。「何もすることが
無い run は安い」は **F2 の増分にしか当てはまらない** — F4 は suite を丸ごと走らせ、F3 は
コールグラフを全リポジトリぶん再生成する。**回すフローは推測せず `check` の出力で決める。**

**1周の終わりに `check` をもう一度読む。** ★ F2 と F3 は互いの依存へ書くので(§2)、1周の中で
先に回した側の鮮度スタンプが後の側の書込みで失効する。そこで **`check` が名指した「回すべき最小の
範囲」だけを覆い直し、`record --covers …` で記録する** — フローを丸ごともう1本払うのは既定では
ない(範囲は `check` の印字が正 — **検査したのちに**、印字された `record --covers` 行で記録する。
コマンド行は記録の形であって、検査の代わりではない)。

**軽量経路で次へ回された検査も、この増分の周が拾う** ★(2026-08-27)。4つの条件を満たす
要望1件を検証の周なしで閉じる経路(`/mission` §2.1)は、**受け皿を新設しない** — 先送りは
台帳の負債計器の欄に1行残り、**次に人間が指示した増分の周が同じ範囲を覆う**(指示が無ければ
覆われないままである — その間もデプロイゲートが fail-closed に受け止め、未検証のまま出荷される
経路は無い)。
**「次のミッションの頭で必ず1周回す」という決まりは作らない** — 人間の指示なしに
verify を差し込むことになり、上の表の起動契機(人間の指示)に正面から反する(2026-08-20 の損失そのもの)。
**先送りのあいだデプロイゲートが red であることは変えない** — 出荷が要るなら先に周を回す。

**全数を要求するものは1つも無い。** 鮮度スタンプの記録項目は `{flow, scope, commit, at, verdict}`
で、**増分と全数を区別する欄が無い**(`stamps.py` の `record`)。ゆえに増分が作った green は
`check-debt.py` と `stamps.py check` に対して全数の green と同じに効く。
**デプロイゲート(`stamps.py check`)の red を「`all` を回せ」と読んではならない** ★ —
あれが名指すのは**回すべき最小の範囲**であり(§2)、自動配車はそこを増分で回す。
**`check-debt.py` の数字はここに関与しない** — あれは計器なので読んで報告するだけである(§4)。
**全数を出すのは人間の契機である**(§2.1)。

**ただし「全数を最後に回した日」だけは別に記録する。** 全数を回した run は
`record … --full` を添える(**F2/F3 の `all` のみ。F4 に全数の印は無い** — F4 は毎回が suite
丸ごと=全数であり、全数でしか回らない検査も無いので、印は情報を持たない。inspection-16 D1)。
この印は**デプロイゲートにも失効判定にも効かない**が、
`stamps.py check` と `check-debt.py` が1行で出す。理由は上の表の右上に在る:
**用語の例が埋まっているかの点検と、決定の見直す条件の発火は、全数でしか回らない**ので、印が無いと「一度も全数を回さない
まま green」に誰も気づけない。**この印が「一度も無い」または古いことは、人間が全数を出す契機で
ある**(スケジューラの契機にはならない — それが (b) の意味である)。

**書込みが続いている間に回した1周は二重払いである**: 次の書込みコミットがその鮮度スタンプを失効させる
(§2 の依存集合 — `stamps.py deps`)。だから指示が無いあいだは溜める(指示された周は別である —
書込みが閉じ次第、未配車の要望より先に回す)。溜めた分を払うのは人間が指示した周であって、**計器の数字ではない** — §4 の計器は
何も拒まないので、「デプロイゲートが閉じたから1周出す」という契機はもう存在しない。**どのフローを回すかを
決めるのは `stamps.py check` であって、計器の数字ではない**(計器が出す鮮度スタンプの古さは記録日からの
日数であり、失効を見ていない — §4)。数字が悪いことは要望を止める理由にもならない。
**指示が無いまま要望が続くあいだ検証が溜まりうる**のはこの設計が受け入れた帰結であり、それを止めるのは
デプロイゲート(§2)である — 溜めたまま**出荷はできない**。

## 3. SSOT の過渡状態と critical フラグ

F1 の段2〜段5 のあいだ、SSOT は**そのタスクのクロージャの中で**実装より先行する。
原則1 の中心(SSOT に願望・TODO・将来の計画を書かない)は手つかずである。
「未来の状態は一瞬たりとも存在しない」に代わるのは、次の不変則である:

> **F1 の出口で、そのタスクが触った文書と実装は一致している**(段4と、段5からの小さなループが
> それを保証する)。過渡は構築記録の `state: building` として見え、
> **verify 系フローは `building` の記録のクロージャを判定から除外する**(過渡は不整合ではない)。
> **その除外は verify のエージェントが何を判定するかについての話であって、`stamps.py` について
> の話では決してない。** 失効判定はパスの差分だけを読み、クロージャのことを何も知らない(§2):
> だから `building` のクロージャの後のコミットは、同じ周で記録された鮮度スタンプを**黙って殺す**。
> `building` は `flow-config.json` の `max_building_hours` より長く生き延びてはならない:
> それを過ぎると `check-debt.py --demote` が `awaiting-verify` へ強制的に戻し、次の周の網へ返す(打たれるのは次に人間が指示した周の頭である — 指示が無いあいだは滞留したまま、デプロイゲートが red で受け止める) —
> **穴が、検出可能な不整合に変わる。**
> **作業ツリーに未コミットの変更が在るあいだ `--demote` は飛ばす**: 降格した記録は再開の探索の
> 届く範囲から出る(`/build <slug>` — `orchestration.md` §3.2.1)ので、
> **コミット済みの仕事だけが網へ戻る。** 書きかけの仕事は `/build` として再開するのであって、
> 決して verify の対象としてではない。

**critical フラグ**(構築記録の `critical: true|false`)は、**廃止されたリスク・レーン**
(タスクをリスク別の系統に分けていた旧模型)の後継である:
認証・決済・不可逆・個人情報・監査への接触を記録し、`critical-config.json` のパスパターンに
対して機械検査し(`check-buildrecord.py` BRC2、fail-closed)、**ちょうど2つのことにだけ使う** —
検証の優先度と、そのクロージャを独立レビューに必ず含めること。
**手順を分岐させることは決してない**: 保護はデプロイゲート(§2)に集約されている。
**effort も分岐させない** ★(2026-09-04)。それまでは「critical なクロージャでは F1 の主ウィンドウの
effort が上がりうる」としていたが、廃した。**旗が確からしさを買う手段は独立レビューの必須化であり**
(上の2つの用途の1つ)、その上に深さを重ねるのは同じものへの二重払いである。
しかも上げる先の F1 は**最も長いウィンドウ**なので(設計と実装を1本で担う)、
待ち時間の代償が最も大きいところで払うことになる。
それ以外は何も変わらない。

## 4. 検証負債の計器(`check-debt.py`)

検証を先送りするのは借金であり、これはその**明細書**である — **与信枠ではない。**
このスクリプトは数えて印字し、**数字が何であれ終了コード0で終わる**。
設定すべき値は無く、タスクを拒む条件も無い。画面に出すもの
(2026-08-20 の裁定。人間の指示「上限は削除で」):

- `awaiting-verify` の構築記録 — 何件と、その名前。含むもの:
  `flow-config.json` の `max_building_hours` を過ぎて滞留した `building` と、
  `state` が読めない記録(**壊れた記録は数える。逃がさない**)。
  **`max_building_hours` は拒否の値ではない**: 過渡と停滞を分ける定義であり、`--demote` の契機である。
- 最終 green 鮮度スタンプのうち最も古いもの — F2、F3、**各** F4 試験区分 — を日数で
  (green が無いものは名前で出す)。**これは記録日からの日数であって、いま green かどうかの
  判定では決してない** — 失効の正は `stamps.py check` である。**どのフローを回すかも
  `check` を読んで決める**(記録日の古さでは決まらない。**回す順は固定である** —
  §7 の F3 → F2 → F4)
- **全数(`all`)の最終実行からの日数**(`record --full` の印。§2.1)。「一度も無い」もそのまま出る
- `docs/sheets/` に残っているシート — **ディスクに残っているシートは未回答の問いである**
  (2026-08-19 の裁定)。答えるとは、構築記録へ転記してファイルを消すことだからである。
  **古さの条件は無い**: 在るか、無いかである。
- **試験区分の置き場の宣言漏れ** — `scope_roots` / `ui_roots` を宣言していないために
  広いほうへ倒れている試験区分の**件数**(§2 の「宣言していないことの代償」の、計器の側の1行。
  内訳と直し方は `stamps.py check` が出す)。**宣言する行為は、どの手順の義務でもない** ★ —
  狭く誤ると穴になるので正は「迷ったら書かない」であり、
  **義務にすればその反対を全作業に配ることになる**(inspection-23 C-8)。
  **`code_roots` は別である**: あちらは許可リストの本体で、未宣言ならデプロイゲートが red に
  なり、`/build` が毎回見直して足す(§2)

**このキットの中で拒むのはデプロイゲートだけである** — デプロイの時点の `stamps.py check`(§2)。
それが何を要求するかを決めているのが**及第ライン**である(`glossary.md` §3: 及第ラインは
*水準*、デプロイゲートはその水準を機械で当てる*機構*。**計器は何も拒まない** — `glossary.md` §8)。
**拒む場所が1つなら、何かが拒まれたときに見る場所も1つ**であり、
**数字を上げて拒否を消すことがもうできない。** では数字は何の*ため*に在るかというと、
**読んで報告するため**である ★(2026-08-25 — vpnsys-op から渡ったパッチの主張を入れた)。
`/build` の入口で読み、周の報告に写す。**自動配車はそれに従わない**:
**起動契機を持つのは §2.1 だけ**であり、増分でどのフローと試験区分を回すかを決めるのは
`stamps.py check` の出力だけ、**回す順は固定である**(§7 の F3 → F2 → F4)。
**人間は縛られない** — 全数を最後に回した日が古いことは、人間が全数を出す契機である
(§2.1 のその段)。
**読みの悪い計器は、1周を飛ばしてよい許可では決してない — そして自動配車にとっては
1周を回す契機でもない。**

## 5. 無人検証の3チャネル — 夜に問いは出ない

F2〜F4 は無人で走る。所見の出口はちょうど3つであり、
それが AskUserQuestion をそこで構造的に不可能にしているものである:

| チャネル | 条件 | 例 |
|---|---|---|
| 自動修正 | 正しい直し方が機械的に定まる: ツール生成領域 / 原則2 の事実の差異(コードが勝つ)/ PATCH級の形 | 壊れた参照、写し取ったシグネチャの誤字 |
| キュー | 判断が要る、または製品の不具合である | 意図の差異、テストの失敗 → `closes_when:` つきで `docs/issues/` へ。整合の抜け → `residual.md` の `残務` 1行(従来どおり原則8の記録先の振り分けを通す) |
| 質問シート | 問う基準を満たす(`delegation.md` §1) | 仕様の読みが本当に割れる |

**質問シートの書き方の正は `delegation.md` §1.1 であり、人間に判断を求める文なので
同 §1.1.1 の読み直しを通す** ★。**この経路でこそ最も効く** — 無人で走るフローに追加で問い返せる人は
居ないので、**書かれたままでは答えられない論点は、その周まるごと失われる**
(同 §1.1)。

質問シートは **1日1枚**の `docs/sheets/questions-<YYYY-MM-DD>.md` である
(`.claude/templates/sheet.md` の論点ブロックの書式。フローは追記するのであって、
同じ日に2枚目を作らない)。verify 系フローの自動修正は **`auto-fix:` を頭に付けた専用のコミット**として
**現在の作業ブランチ**へ入り(裁定 D'-2 — **自動修正のために別ブランチもマージ作業も作らない**。
作業ブランチそのものは §7.1 が既に用意している)、**検証の周の報告**(40行 / 2,000バイト
以内)がそれらを並べる。誰にも答えられない項目は飛ばす。**ただし決して黙って飛ばさない**:
原則8の記録先の振り分けを通して `残務` 1行(または環境の課題票)を残す —
**1つの不明が周を止めることは決してなく、消えることも決してない。**
**回答の着地は次の `/build` が所有する**(どの run でも、着手時に):
回答は逐語 + 日付で、SSOT の外の宛先にだけ転記される — 名指された構築記録か、
名指された課題票の `## 経緯` — そしてシートは削除される(§4)。
**名指すのはシート側の仕事である**: 質問シートの各論点ブロックは 転記先 の行を持つので
(`.claude/templates/sheet.md`)、転記する `/build` が宛先を推測することは決してない。
**中身が SSOT に属する回答**(決定、仕様の解釈)は、着手時にそこへ書かれない
(それはどのクロージャにも属さない SSOT への書込みになる — 原則1):
逐語の回答 + 日付は **`docs/histories/<YYYY-MM-DD>-answer-<論点>.md` 1本**へ入り
(`.claude/templates/answer.md` — 回答の逐語はキューのどちらの形にも収まらない: `残務` の行は
1行しかなく、課題票の本文は不具合の形をしている)、**それを指すのは `docs/issues/` の課題票
1件(`type: modify`)である** — `closes_when:` は「その回答が SSOT に反映されたとき」。
そのクロージャを所有する `/build --repair` がその課題票を読んで着地させる(inspection-17 判断8)。
**残務の1行にしてはならない** ★(inspection-19 D-17 の裁定 2026-08-21。**理由は 2026-08-25 に
入れ替わった**): `残務` はローテーションで押し出され、**押し出されたファイルはどのフローも
二度と読まない**ので、**唯一のポインタをそこに置くと、人間の回答が黙って読まれなくなる** —
この節の「消えることも決してない」と正面から衝突する。課題票はローテーションしない。
**`/build` が来る見込みが無いとき** — 要望を全部さばき、キューが空 — 回答済みでディスクに
残っているシートには持ち主がおらず、**デプロイゲートは永久に red のままになる。** だから回収は
それ自体が配車できる作業指示である: **人間が1行「シートに回答した」と言い、スケジューラ
(または単独運用の人間)が `/build <そのシートのパス>` を走らせる** —
転記だけの run(`/build` §0)であり、回答を着地させ、キューの修繕を起票し、シートを削除して
止まる(inspection-17 判断8)。

## 6. F1 の先送り禁止 — 決して後回しにしないもの

「構築フローは検査をスキップする」にも、決して後回しにしない項目が在る。`/build` のどの run でも決して後回しにしない:

1. build / lint が通ること(壊れた状態を鮮度スタンプのあいだで受け渡さない)
2. **このタスクが触ったモジュールのテスト**が green であること(全件は F4 に譲る。
   自分が壊したぶんは譲らない)
3. **タスク内整合確認**(F1 の段4)— 飛ばすと二重の網(§1)が1枚目を失う
4. 基本要件 BR-nn の判定(`baseline.md` — 後回しにしてよい項目は1つも無い)
5. 問う基準の振り分け(人間に属するものを、黙って夜へ流さない)

## 7. 運用の型

**艦隊(このキットの既定)** — 常駐する中央エージェントが、デプロイゲートをスケジューラの入力に変え、
人間に残る仕事を「要望を投げる・シートに答える・検証の周を指示する」だけにする(CLAUDE.md §9。ループは
`orchestration.md` §3.0 が所有する)。1タスク = 1作業指示 = 1本の `/build`。
スケジューラは**人間の指示を受けて**、**増分**の verify 作業指示を出し —
**`stamps.py check` が green でないと言ったフローに限り、周の終わりに `check` を読み直す** —
**全数の周を決して決めず、自動で周を差し込むことも決してない**(§2.1。2026-09-05 に
自動の契機を廃した)。指示が無いあいだ、隙間の時間には何も走らない。

**単独運用(掲示板なし — `orchestration.md` §10)** — 運用の手間は人間に残る:

```
構築  /build を直接起動(並走は端末を分けて。クロージャが重なる仕事は並走させない)
検証  **人間が指定したタイミングで**回す ★(2026-09-05 に「夜の cron」の型を廃した — 対話で
      指示しても、人間が自分で cron を仕掛けてもよい。指示が無いあいだは何も走らない)。
      まず python3 .claude/scripts/check-debt.py --demote
        (滞留した building を次の周の網へ戻す — 降格の実行者はこの行である)。
        次に stamps.py check を読み、**green でないフローだけ**を、/build を1本も走らせない
        1周として直列で回す(F3 → F2 → F4 の順。F3 が先: 03-impl をコードへ合わせてから
        00〜03 の整合を見る方が手戻りが少ない。F2 と F3 は 02 と 03-impl を双方が書くので
        互いに相手を殺しうる ——「一方向だから安全」ではない。F4 は check が green でないと
        言った試験区分を1本にまとめて回す)。
        1周の終わりに stamps.py check をもう一度読み、名指された最小範囲だけを覆い直して
        record --covers で記録する(1周につき最大2回 — 単独運用ではこの上限の正は CLAUDE.md §3 である。
        艦隊運用では `orchestration.md` §3.0 が同じ数字を持つ)。
        **同じ HEAD・同じ失効原因の覆い直しは、周を跨いでも累積2回まで**である —
        超えたら持ち越さず、何が閉じないかを1行残して人間へ渡す(CLAUDE.md §3)。
        最後に git add .claude/state/stamps.json &&
        git commit -m "verify: record freshness stamps" -- .claude/state/stamps.json で**この周の鮮度スタンプを
        1回だけコミットする**(§2。中断したら次の周の頭で拾う)。**メッセージは必ず -m で渡す** ★ —
        省くと git はエディタを開こうとし、**端末に人が居ない実行はそこで止まる**
全数   /verify-impl all → /verify-docs all → /verify-tests(引数なし)を**固定時刻で**1周
        (§2.1 の「全数」の行。順が F3 → F2 なのは増分の周と同じ理由 — 03-impl をコードへ
        合わせてから 00〜03 の整合を見るほうが手戻りが少なく、逆順だと F3-all の書込みが直前の
        F2-all 鮮度スタンプを毎回失効させる(inspection-17 V-7)。
        **時刻と間隔を決めるのは人間であり、キットは頻度を持たない**)。
        全数でしか回らない検査が在るのでこの1周が要る。記録には --full を添える
        (F2/F3 のみ — F4 は印を持たない。§2.1)。**この周も1周なので、終わりに
        git add .claude/state/stamps.json && git commit -m "verify: record freshness stamps" -- .claude/state/stamps.json
        で鮮度スタンプを1回コミットする**(§2。上と同じく **-m を省かない**)。
        最後に回った日は check-debt.py が出す
朝    ① 検証の周の報告を読む ② docs/sheets/questions-*.md に回答 ③ キューを /build --repair で消化
デプロイ前  python3 .claude/scripts/stamps.py check(複合のデプロイゲート)— red なら verify 系を
        手動起動して green を作ってから(決まった時刻を待つ義務はない)。red が (b) の awaiting-verify だけなら
        python3 .claude/scripts/stamps.py promote を打ち、書き換わった記録をコミットする —
        鮮度スタンプは揃っていて遷移だけが残る形はこれで閉じる
```

周を出すのは人間である — 指定の形は問わない(対話の1行でも、人間が仕掛けた cron でも)。
回してよいのは、**`stamps.py check` が green でないと言った**増分のフローである(§2.1)。
**green のフローを安心のために回し直すことは決してない**し、
「何もすることが無い run は安い」が真なのは F2 の増分についてだけである。
**全数(`all`)は増分の周のついでではない**: それは §2.1 の人間の明示の周であり、
書込みが続いているあいだにそれを回すのが、あの節が名指した二重払いの誤りである。

フローのスキルは**どちらの運用の型でもまったく同一である**: 入力と出力はディスクの状態
(構築記録、鮮度スタンプ、シート、課題票)と引数1つであり、報告の様式は起こした側で変わらない。
その**起動元からの独立性は設計上の制約であって、便宜ではない** —
**人間が見ているときにだけ働く段を、決して足さないこと。**

### 7.1 保護ブランチでは作業しない ★

**保護ブランチとは、`main` / `master` / `develop` の3つの名前と、そのリポジトリの既定ブランチである**
(4つ目は名前が何であってもよい。下の求め方)。**この語はこのキットの「本流」とは別物である** —
「本流」はキットの配布元のリポジトリを指す(`principles.md`・`/kit-improve`)。

**書込みを始める前に、現在のブランチを見る。保護ブランチに居たら、作業ブランチを作って移動してから
書く。既に作業ブランチなら、そのまま書く。**

- **見るのは**: `git branch --show-current`(現在のブランチ)★。
  **`git rev-parse --abbrev-ref HEAD` を使わない** — あれは**コミットが1本も無い枝**
  (`git init` の直後)で `fatal` を吐くので、**グリーンフィールドの最初の `/build` が
  入口で死ぬ**(`/setup` は `git init` してコミットしない)。`--show-current` は
  その状態でも名前を返し、detached では空を返す。
  既定ブランチは **すべてのリモートの `HEAD`** を見て集める(`git symbolic-ref --short
  refs/remotes/<リモート>/HEAD`)★ — **最初に当たった1つで打ち切らない**。リモートは名前順に
  出るので、`origin` より前に並ぶもの(`archive` / `backup` / フォーク元)が在ると、
  **そちらの既定枝が答えになり、本流の既定枝が丸ごと外れる。** 保護は緩めるより広げるほうが
  安全なので、全部を保護の側に足す。**取れた名前が実在するかまで確かめる** — あの命令は
  **指す先が消えていても終了コード 0 で名前を返す**(既定枝が改名された後の古いクローン)。
  `git config --get init.defaultBranch` は最後に見るが、**これで「特定できた」とは数えない**
  — あれは `git init` のときに読まれる設定であって、そのリポジトリの枝名の記録ではない。
  **どれも取れなければ上の3つの名前だけで判定し、そう言う**(それ以上は推測しない。
  **黙って緩まない**)。
  **比べる前に、取れた名前の先頭の `origin/` を取り除く** ★ — 1つ目のコマンドは
  `origin/trunk` のようにリモート追跡の名前を返すのに、現在のブランチは `trunk` である。
  取り除かずに比べると**必ず一致せず、守ろうとした4つ目の枝をそのまま見逃す**
  (下の「判定するのは誰か」が名指す全員が、この1手を踏む)。
- **作業ブランチの名前は `work/<YYYY-MM-DD>-<slug>`** である。艦隊運用ではミッション ID が
  ちょうどこの形なのでそれを使い(`orchestration.md` §7)、単独運用ではそのタスクの slug を使う
  (`/build` が必ず持っている — 構築記録が `docs/build-records/<slug>.md` だからである)。
  **検査フロー(F2・F3・F4)が自分で切るときは `work/<YYYY-MM-DD>-verify` である** ★ —
  あれらは slug を持たないので、**名前を発明させない**(艦隊運用では中央エージェントが先に
  移しているので、この形が使われるのは単独運用で無人に起きたときだけである)。
  **同じ名前のブランチが既に在るときの扱いは、2つに分かれる** ★ — この名前は日付までしか
  区別しないので、**人間が保護ブランチへ戻したあとの2回目は、いつも前回の枝に当たる**
  (単独運用では増分の周・全数の周・手動の起動が同じ日に重なりうる。この §7 の単独運用の枠)。
  **判定せずにそのまま移ると、前回以後に保護ブランチへ入った変更を含まない古い基点を
  検証することになる** — 記録した鮮度スタンプと修正が現在の保護ブランチを表さず、
  **「検証は全部合格した」のに不具合のある成果物が通りうる。**
  **比べる相手は、いま自分が立っている保護ブランチ(`HEAD`)である** ★ — この判定に来るのは
  保護ブランチに居るときだけであり、保護ブランチは最大4つ在りうる。名前を選ぶと、
  **判定した相手と `git branch -d` が見る相手(あれは `HEAD` を見る)がずれる**。
  `HEAD` は必ず解決するので、**名前が解決できずに終了コード 128 が返る経路も同時に消える**
  (`--is-ancestor` の `128` は「取り込み前」ではなく**誤り**である。混同すると、
  古い基点へ黙って落ちる)。
  - **取り込み済みなら、削除して作り直す** — 前の周は終わっている。
    判定は `git merge-base --is-ancestor <その枝> HEAD` が真(終了コード `0`)であること。
    削除は `git branch -d`(取り込み済みの枝しか消さない)であり、**`-D` を使わない。**
    **削除が失敗したら、そこで止まって報告する** ★ — 別の作業ツリーがその枝を使っている
    などの、こちらの知らない事情が在る。**git は `-D` を勧めてくるが、それは書きかけを消す。**
  - **取り込み前なら、そのまま移る。それが中断からの再開である**(`/clear` のあとの再開が
    これである)。**消してはならない** — 前の周の書きかけがそこに在る。
    **ただし、移ったあとに保護ブランチを取り込んで基点を追いつかせる** ★
    (`git merge --no-ff <いま出てきた保護ブランチ>`。**移ったあとは `HEAD` が保護ブランチでは
    ないので、名前を覚えておく**)。**「取り込まれていない」ことと「基点が新しい」ことは
    別の質問である** — `--is-ancestor` が答えるのは前者だけであり、中断した枝ほど長く
    放置されるので、**いちばん古い枝がいちばん確実にこちら側へ落ちる。**
    **移れなかったとき・取り込めなかったときは、そこで止まって報告する** ★ —
    前の周の書きかけが在るのだから、`git switch` が未コミットの変更で撥ねられることも、
    このマージが衝突することも、**例外ではなく既定の場合である。**
    無人の3チャネル(§5)はどれも git の失敗を受け止めない。**衝突を残したまま検証を
    始めてはならない** — 印の残ったファイルを仕様として読むことになる。
    (削除側にも同じ出口が在る。**片側にだけ出口が在る状態にしない。**)
  - **`HEAD` と比べることの裏側** ★: 保護ブランチが複数在るとき、**`main` へ取り込まれた枝を
    `develop` の上で判定すると「取り込み前」に見える**。そのまま上の手順に従うと `develop` を
    取り込むことになる。**判定は、いま立っている枝に対する答えでしかない。**
  - **人間が squash で戻した枝は「取り込み前」に見える** — フローは squash を使わないが、
    人間や PR の側は止められない(戻すのは単独運用では人間である。下)。
    そのときは中身が入っているのに `--is-ancestor` が偽になり、**機械には区別が付かない。**
    前の周が済んでいると分かっているなら、その枝は消して作り直す。
  - **既に作業ブランチに居るなら、この判定は走らない**(上の「既に作業ブランチなら、そのまま
    書く」)。**それが正しい** — 単独運用の1周は F3 → F2 → F4 を直列に回すので、
    2本目と3本目は1本目が切った枝を共有する。**1つの周は1つの基点の上に載る。**
- **判定するのは誰か。** 艦隊運用では中央エージェントが主である(`orchestration.md` §2.1)。
  加えて、**判断を含む文字を `docs/` かコードへ書くスキルは、すべて入口で判定する** ★ —
  取りこぼしを捕まえるためである。
  **ここをスキルの名前で列挙しない** — 以前はそう書いていて、**列挙が現実に追いつかなかった。**
  既存プロジェクトへの導入経路(`/relations --apply` と `/retrofit`)は列挙の外に居たまま、
  文書を大量に生成し古い文書を削除していた。**気に入らなかったときに枝ごと捨てられない。**
  性質で書けば、これから増えるスキルも最初から覆われる。
  **「判断を含む」が線である** — `/setup` は `docs/` の下へ書くが、**判断を要する文字を
  1つも書かない**と自分で宣言しており(空のディレクトリ、雛形の逐語複写、機械が導く索引、
  雛形の中で機械が決まる1語 = このディレクトリの名前、道具の venv、そして pip が実際に解決した
  版の記録 `requirements.lock` だけ)、
  **捨てたくなるものを何も作らないので判定を持たない。** 導入で最初に枝が切られるのは
  `/relations --apply` の入口である。
  (**`/kit-improve` も外である** — あれが書くのはキットであって `docs/` でもコードでもない。
  **外す判断をここに書いておく** — 書かないと、次に読む人が「列挙をやめたのに漏れている」と
  読む。**ただし、あれが枝の扱いを持っているという意味ではない** ★ — 実際に持っていない。
  キットの改造を捨てたくなる場面は在るので、**ここは開いた問いである。**)
  **挙動は運用の型で変えない**(§7 の末尾の宣言のとおり): どちらの型でも、
  **保護ブランチに居たら作って移動する。** 艦隊運用では中央エージェントが先に移しているので、
  フロー側の判定は普通は発火しない。
- **判定の実装は `.claude/scripts/guard-branch.py` である** ★ — 上の全部
  (既定ブランチの求め方 / `origin/` の除去 / 同じ名前の枝の2分岐 / `HEAD` と比べること /
  止まって報告する条件)を1本が持つ。**入口はこれを走らせるだけでよい:**

  ```sh
  python3 .claude/scripts/guard-branch.py --slug <そのタスクの slug>   # /build
  python3 .claude/scripts/guard-branch.py --verify                     # F2・F3・F4
  python3 .claude/scripts/guard-branch.py --name work/<mid>            # 艦隊の中央エージェント
  ```

  **終了コードが `0` でなければ、そこで止まって報告する。** 意味は2つに分かれる ★:

  - **`1` = こちらの知らない事情が在る**(人間を呼ぶ)— 別の作業ツリーがその枝を使っている /
    前の周の書きかけが衝突した / **中断したマージや未解決の衝突が残っている** /
    どの枝にも居ない(detached)/ 作業ツリーの外に居る。
    **`git branch -D` を打って先へ進んではならない。**
  - **`2` = 呼び手の誤り**(直せば済む)— 移る先が `work/…` で始まらない / 移る先が保護ブランチ /
    **git が枝名として受け取らない名前**(`x..y`、`x.lock`、空白入り。**可否は git 自身に聞く** —
    自前の文字種の制限を置くと、**このキットが認めている日本語の slug を撥ねる**)。
    **`2` を `1` に化けさせない** — `1` は人間を呼ぶ合図なので、直せる誤字で無人の周が止まる。

  **止めたことが次の呼び出しで消えないようにする** ★ — 追いつかせるマージが衝突したら
  **木を元に戻してから止まり**、戻せなかったならそう言う。加えて**入口で中断した操作を見る**
  ので、別の理由で残った衝突も同じところで捕まる。
  **この節が規範の正であり、スクリプトはその実装である** — 食い違ったらこちらが正しい。
  **判定の中身をここ以外の散文へ書き写さない** — 以前は11のファイルに散らばっており、
  1つ直すたびに全部を1つずつ直していた(実測で2度起きた)。
- **保護ブランチへ戻すのはマージである** — `git merge --no-ff`。
  **squash も rebase も使わない**: どちらも元のコミットを作り直すので、**鮮度スタンプと構築記録が
  焼き込んだコミットが履歴から消え、判定は `判定不能` になる**(§2)。
  マージが衝突したら、中央エージェントは自分で解かない(`orchestration.md` §2.1)。
  **戻すのは誰か**: 艦隊運用では中央エージェントが、ミッションの完了のときに戻す
  (`orchestration.md` §2.1・`/mission` §5)。**単独運用では人間が戻す** —
  フローは決して戻さない(いつが「終わり」かを知っているのは人間だけである)。
- **この規則を見る機械の検査は無い。** 規範の文だけが守らせる。

## 8. 報告の様式(すべてのフロー共通)

原則11 のとおり: 結論から、根拠を添えて、「次にあなたがすること」で終える。
verify 系フローはさらに、報告の全体を 40行 / 2,000バイト以内に収め、次を並べる:
記録した鮮度スタンプ、`auto-fix:` のコミット、起票したキューの項目(課題票 / `残務`)、
質問シートに追記した項目、そして飛ばしたものとその理由。

## 9. リリース — 出した状態を1点として残す ★(2026-09-04)

**このキットは長いあいだ「出せる状態か」の判定しか持たず、「出した」という出来事を持たなかった。**
だから成果物の版(`baseline.md` の `BR-12`)を動かす契機がどこにも無く、版は最初の値のまま止まる。
この節がその1点を作る。

**リリースとは、デプロイゲートが green の状態を「外へ出した」と決めて記録することである。**
判定(`stamps.py check`)は状態についての述語であり、リリースは出来事である。
**green は何度も起きるが、リリースは出したときにだけ起きる。**

### 9.1 打つもの

```bash
python3 .claude/scripts/stamps.py release      # 版は機械が決める。人間は桁を指定しない
git add .claude/state/releases.json
git commit -m "release: <版>" -- .claude/state/releases.json
```

**台帳は `.claude/state/releases.json` である。** 置き場がここなのは、
**`.claude/state/` がどのフローの依存集合にも入っていないから**であり(§2)、
**版が動いても検証は1つも失効しない。** これは運用の心がけではなく、
**失効判定がそもそもそのパスを見ていない**という構造である。
**製品のコードに版を置くとこうはならない** — その1文字が F3 と F4 の全試験区分を失効させる。
**コミットの作法は鮮度スタンプと同じである**(パスを名指して1件だけ。`git add -A` を使わない)。

### 9.2 拒む条件は5つ。どれも fail-closed である

- **デプロイゲートが red** — 出せない状態を、出したことにしない。
- **未コミットの変更が在る** — 記録する版がどの木を指すのかが決まらない。
- **台帳が読めない** — 壊れた台帳を「まだ1度も出していない」と読むと、**次の1回が履歴を捨てて
  最初から書き直す。** 手で直すまで進まない。
- **台帳の先頭の版が3つ組でない** — 壊れた版の上に桁を積まない。
- **区間の構築記録に、3つの値のどれでもない宣言か、区間に置けない `commit:` が在る** —
  欠けている場合と、git が解決できない場合(HEAD から辿れない cherry-pick や revert)の両方である。
  **名指して拒む。** `commit:` が無い記録を黙って飛ばすと、**互換を壊す宣言を持っていても
  数から消える**(独立検査 2026-09-04 の実測)。

**構築記録が1件も無い区間でも、revision は動く** ★ — **出したという出来事そのものが記録**
であり、版はそれを指す。**ただし、前回のリリースから台帳の外が1バイトも動いていなければ
何も書かない** — 状態が同じなら出来事も同じである。
**「同じ commit なら書かない」と書いてはならない** ★ — 上の手順が台帳をコミットして
HEAD を進めるので、その形は**二度目以降に必ず素通りし、打ち直すたびに版が動く**
(独立検査 2026-09-04 の実測)。

### 9.3 桁は構築記録の宣言から決まる — 人間は関与しない ★

前回のリリースの commit から HEAD までに入った構築記録の `- 外部挙動の変化:` の値を集め、
**その最大値を採る**(値の意味は `build-record.md` §2 が正である):

| 区間に1件でも在れば | 動く桁 |
|---|---|
| `あり(互換を壊す。…)` | **major**(下の2桁は 0 になる) |
| `あり(後方互換。…)` | **minor**(revision は 0 になる) |
| どちらも無い | **revision** |

**最初のリリースだけは桁を計算しない** ★ — 区間の始点が無く、過去の構築記録はこの仕組みが
無かった頃の書式だからである。**遡って埋め直さない**(`baseline.md` §4.3 と同じ理由)。
**最初の版は `0.9.0` である。**

### 9.4 成果物が名乗る値は、この台帳から読む

```bash
python3 .claude/scripts/stamps.py release --current   # 版だけを印字する
```

**組み立てのときにこれを読んで埋め込む。** これが `BR-12` の「値の持ち主は1箇所」の実体である。
**埋め込みに失敗したときに何を名乗るかは、その成果物が決める**(同じく `BR-12`)。

### 9.5 承知で残る穴 — 塞げないので在り処を書く ★

- **名前を変えずに意味を変えた非互換は、機械には見えない。** 引数の意味を変えた、
  返す条件を変えた、という型である。**宣言する側が `互換を壊す` と書けば拾えるが、
  書き忘れれば major は動かない。**
- **宣言は作業した側の自己申告である。** critical の旗と同じ形であり、
  **反証するのは F3 である**(`build-record.md` §2 の表)。
- **遡って効かない。** この仕組みより前の構築記録は書き換えない。
- **台帳は1リポジトリに1つである。** **別々に配る成果物が2つ以上在るリポジトリでは足りない**
  — `BR-12` はそれぞれが別に名乗ることを求めるので、そのときの持ち主はプロジェクトが決める。
