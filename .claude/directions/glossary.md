# 規範用語集 — 規範と人間向け出力で使う唯一の表記

日本語で書く。**この表がキットの用語の正である。** 同じものを別の語で書いてはならない。
**この表を「規範用語集」と呼ぶ。** 配布先に作る `docs/00-requests/terminology.md`
(製品・業務の概念の外延を決める表)は「プロジェクト用語集」であり、**別の正である**。
裸の「用語集」は書かない — どちらを更新すべきかが読み手に決まらない。

**なぜ在るか**: 2026-08-21 の実測で、`gate` という1語が**5つの別概念**に当たり、しかも
`gate` 101 / `関門` 26 / `ゲート` 16 と**3通りに書かれて**いた。原因は `conventions.md` の
固定語彙に gate の項が無かったことである。**定義の無い語は、各ファイルで好きに書かれる。**

## 0. この表の使い方

- **規範を書くとき**: 概念に当たる語を、この表の「日本語」欄のとおりに書く。表に無い概念を
  名付けたなら、**その語をここに足してから**規範に書く(片側だけ増やさない)。
- **英語のファイル**(`CLAUDE.md` / `roles/` / `agents/`)を書くとき: 「English」欄のとおりに書く。
- **人間に宛てる文を書くとき**: 「人」欄に ★ が付いた語を**使ってはならない**。
  普通の言葉に開くか、その場で1行定義する(`delegation.md` §1.1 の規則2)。
  **その場の定義は、丸括弧で、同じ行の中に書く** — 機械(`check-sheet.py` SH12)がその形を見る。
- **「認証」はドメイン語(authentication)に予約されている。** 検証・照合・突き合わせの意味で
  使ってはならない(この予約だけは対になる語を持たないので、表ではなくここに書く)。
- **語を変えるとき**: 古い表記を「使ってはならない表記」欄に**必ず残す**。
  残さないと、検査は「揺れ」を検出できない(`templates/00-terminology.md` の「別名」「使ってはいけない言い方」の
  2欄と同じ設計)。

## 1. 欄の意味

| 欄 | 中身 |
|---|---|
| 日本語 | 規範(`directions/` `skills/` `templates/`)と人間向け出力で使う唯一の表記 |
| English | 英語のファイル(`CLAUDE.md` `roles/` `agents/`)で使う唯一の表記。`—` は英語側に語を持たないもの |
| 定義 | **何を指すか**を1〜2行。**なぜ在るかは書かない**(それは各規範の仕事) |
| どこを見るか | それを見るために開くもの — 走らせるコマンド、住んでいるファイル、値そのもの。`—` は**見に行く先が無い**(規範だけが正)ということ。**その規範の節が1つに定まるときは、`—` の後ろに丸括弧でその節を添える**(定まらないときは `—` だけ) |
| 使ってはならない表記 | 過去に混在した表記。**名指しで禁止する** |
| 人 | ★ = **人間に宛てる文に書いてはならない**(`delegation.md` §1.1) |

**機械が読む約束** ★: 「2. ゲート」から「8. 検査と計器」までの表は**すべてこの6欄**である。行の1列目が空でなく、
2列目以降が5つ並ぶ行が1項目である。`—` は「無し」を表す。
`check-language.py` は 5列目(LA3 の禁止表記)と、1・2・3列目(LA4 の表の健全性)を読む。
`check-sheet.py` SH12 は1・5・6列目を読む。
**§9 の3欄の表も機械が読む** ★ — `check-language.py` の LA5 が「書き方」の欄から
「裸の『X』を書かない」の行だけを拾う(§9 に但し書きが在る)。**この表の書き方を変えるときは §9 を読むこと。**
**列挙をスクリプトへ書き写さない** — 正が2つになる。

機械は語を**部分一致**で当てるので、欄の書き方に2つの約束がある:

1. **`/` で区切ると複数の語になる。** 「関門 / デプロイ関門」は2語である。
2. **丸括弧を含む項目は、機械が使わない**(人間向けの注記として扱う)。
   「影響範囲(単独で書かない)」のような**条件つきの禁止**は機械には判定できないので、
   括弧を付けることで対象から外している。**条件を付けずに禁止したい語だけを、括弧なしで書く。**

**日本語に語の切れ目は無いので、載せてよいのは「そのキットでしか使われない語」だけである。** ★
日常語(「ログ」「割り当て」「一括」「古い」)も、**他の語の一部になる語**も載せてはならない。
実測: 「ボード」を載せたところ、決定シートの論点「ダッシュボード」が落ちた(2026-08-21)。
**★を付けるかは「この語が製品の仕様ドキュメントに出うるか」で決める** — 出うるなら付けない。
同じ理由で外したもの — レポート / オーダー / リソース / エッジ / 証明書 / チケット / スコープ /
帳簿 / 期限切れ / メーター / 進捗率 / 工程 / 自動整形 / 連携仕様 / ディスパッチ / 内部整合 /
設計書(「基本設計書」= 02 層の
正式名の部分文字列である。「連携仕様」も「機能間連携仕様書」の部分文字列である。
「ディスパッチャ」はコールグラフ抽出の用語で配車とは別概念であり、「SSOT の内部整合」は
タスク内整合確認とは別のことを指す。「ペイン」は tmux のペインという別の実体である)。
**製品側の言葉になりうるものも、正式名の一部になる語も載せない。**

「条件1 / 条件2」も同じ理由で「人」欄を空にしてある(この2語は普通の日本語であり、
仕様の文に自然に現れる)。人間に見せてはならないのは**古い表記の「関門1 / 関門2」の側**であり、
そちらは5列目に載っている。
**同じ扱いのもの**: 「修繕」「レーン」「再監査」「台本」「受け入れシナリオ」「受け入れ基準」「鮮度確認」「完了定義」
「増分」「全数」「基本要件」「配車」。
どれもキットの語であると同時に製品側の文に自然に現れうる(大規模修繕 / スイムレーン /
増分バックアップ / 全数検査 / 配車アプリ /
外部の再監査 / 工程の完了定義 …)。**行そのものは表記を1つに保つために要るが、「人」欄を ★ にすると
SH12 の部分一致が製品の論点を落とす。**

| エラー | error | 検査が拒む理由になる違反。`check-relations.py` はこれを `警告` と分けて数える | `check-relations.py` の `### エラー N 件` | — | — |

## 9. 同じ比喩が2つ以上のものに当たる語 ★

**同じ語を使ってよいが、どの意味かが読み手に分かる形で書く。**
**書き方の欄が語ごとに違う** — 裸を禁じるもの(ゲート・仕様書)、文脈が1つに定まるときだけ裸を
許すもの(台帳・キュー・シート・口・版・周)、片方の意味だけ名指しを義務づけるもの(フェーズ)、片方の意味を別の語へ
寄せるもの(欠陥・区分・本流)、2義は裸でよいが第3の意味を禁じるもの(床)、**日本語の地の文では書かないもの**
(`scope`)が在る。
**表の「書き方」欄がその語の正である。**

**この表のうち機械が見張るのは「裸の『X』を書かない」の形の2語(ゲート・仕様書)だけである** ★ —
`check-language.py` の LA5 が、**許される複合語をこの表の書き方の欄から読んで**当てる
(だから書き方の欄には、許される形を「…」で必ず並べる)。
**残る10語は機械の外に在る。** 「文脈が1つに定まるときだけ」「②の意味では使わない」は、
書き手がどの意味で使ったかを知らないと判定できない。**条件つきの禁止を機械にやらせると誤検知が出て、
鳴り続ける検査は信用を失う。** 穴はここに在る — **その10語は読み手が守るしかない**(原則11)。

| 語 | 当たっているもの | 書き方 |
|---|---|---|
| ゲート | §2 のとおり2つだけ(デプロイゲート・構築記録ゲート) | **裸の「ゲート」を書かない** — 「デプロイゲート」「構築記録ゲート」のどちらかで書く |
| 本流 | ① キットの配布元のリポジトリ(`/kit-improve` がパッチを戻す先)/ ② git の主要な枝 | **②の意味では使わない。**そちらは「保護ブランチ」と書く(§3)。「本流」は①だけを指す |
| 口 | ① ブラウザを操作する手段(`chrome-devtools` MCP / `claude-in-chrome`)/ ② 通知を送る入口(`notify-slack.py` が持つ3つ)/ ③ 起動時に能力や規範を受け取る入口(スラッシュコマンド・起動引数。codex はどちらも持たないので、指示がパスで名指す) | 裸の「口」は、節か直前の語でどれか1つに定まるときだけ。定まらないなら直後の括弧で示す |

## 10. 訳さないもの

**識別子と、機械が literal で見ている語は、どちらの言語のファイルでも原文のまま書く。**

| 何 | 例 | なぜ |
|---|---|---|
| 検査ID・仕様ID | `DS-01` `BR-01` `CS8` `SH11` `BRC3` `FR-<domain>-nn` `CTR-*` `P-nnn` `AC-nn` | 機械が名指しで照合する。`check-kit-refs.py` (d) が実在を見る |
| 原則n | `原則4` `原則10` | `check-kit-refs.py` の `PRINCIPLE_RE` がキット全文に当てる。**英語のファイルでも `原則4` と書く** |
| フロー番号 | `F1` `F2` `F3` `F4` | 機械可読な短縮。人間に宛てる文では「構築フロー」等に開く(★) |
| 状態の値 | `building` `awaiting-verify` `verified` | frontmatter の値そのもの |
| `scope` を含む鍵と引数 | `f4_scopes` `scope_roots` `stamps.py --scope` / `build-callgraphs.py --scope` / frontmatter の `scope:` | **試験区分を指すのは前の3つだけ**で、地の文ではそう書く(§3)。呼出関係図の `--scope` は**パスの部分木**、試験の文書の `scope:` は**その文書が覆う対象**(`03-impl.md` の「Frontmatter」節)であり、どちらも試験区分ではない(§9) |
| frontmatter の鍵 | `severity:` `found_in:` `critical:` | 機械が鍵の名前で読む。**鍵は `severity:`、地の文では「重大度」と書く** |
| スクリプトの出力語 | `green` `red` `PASS` `FAIL` `OK` `NG` | **出力と規範の表記を割らない** |
| パス・コマンド・オプション・終了コード | `docs/sheets/` `stamps.py check` `--covers` `終了コード 2` | そのまま打つものだから |
| 文書の見出し | `## 影響範囲(closure)` `## 基本要件の点検` `## 機能一覧` `## 残務` | スクリプトが文字列で節を切り出している |
