# issues / pendings — 見つけた問題はどこへ行くか、そして記録先の振り分け

日本語で書く。
**これ専用のスキルは存在しない**: 問題を見つけたスキルが、**その場で**記録する。
別のスキルへ渡す瞬間こそが、所見が失われる瞬間である。

## 1. 記録先の振り分け — 記録することが仕事になるのを止めているもの

この振り分けが止めるために存在する、実測された失敗: **課題票は解消される速さの 2.4〜3.4 倍の
速さで生まれ**、その大半は製品の問題ではなく文書整合の雑務だった。
だから `docs/issues/` の**ファイル**は、**本当に追跡された行動を要するもの**に取っておく。
次の順に問い、**最初に Yes になったところで止まる**:

| # | 問い | Yes なら |
|---|---|---|
| 1 | いまのタスクの範囲の中で直すべきか? | このタスクで直す(構築記録の進捗メモに書く。新しい記録は作らない) |
| 2 | **不完全なまま意図的に受け入れる**ものか? | `docs/pendings.md` に完全な項目1件(§2) |
| 3 | 振る舞いが**仕様に対して誤っている**(不具合)、または**完了定義を阻害する**(`.claude/directions/core.md` §3 — `AC` か、リリースの完了定義の項目)か? | `docs/issues/` に1ファイル(§3) |
| 4 | それ以外 — 文書整合の抜け、言い回しのずれ、網羅表の穴、何も阻害しない技術的負債 | `residual.md` の「残務」節に**1行**(§2.1)。ファイルも重大度も追跡義務も作らない |

**振り分けに入る前に落ちるものが1つだけ在る** ★ — **`/dependabot` が読む GitHub の
Dependabot アラートである。それだけであり、他は1つも無い**(2026-09-03 の人間の指示)。
理由は、**外部の追跡システムが既にその一覧を持ち、直れば向こうで閉じるからである** —
写せば同じものを2箇所で管理することになり、**写した側が必ず古くなる**(`conventions.md` §4)。
**この理由は規則ではない** ★ — **他の追跡システム(Sentry・Jira・Code scanning・Snyk など)を
使っていることは、この例外に入る理由にならない。** 同じ理由が当てはまるように見えても、
**現地の判断でこの一覧を増やしてはならない。増やす経路は `/kit-improve` でこの節を
書き換えることだけである。**

**これは無視してよいという意味では決してない** — 向こうの一覧が台帳であり、直すものは
`/build` の作業指示になり、直せないものは向こうに open のまま残って、次の run でまた見られる
(`.claude/skills/dependabot/SKILL.md` §3)。

**この例外が覆うのは、アラートを一覧としてこちらへ写さないことだけである** ★ —
そのアラートとは独立に、**行3 の条件を実測で満たすことが分かった**場合
(`AC-nn` が実システムに対して落ちる / `SR-nn` が「破れている」)は、
**それは製品の不具合であって外部の一覧の写しではないので、今までどおり行3 を通る。**

**この例外はデプロイゲートが読むものを増やしも減らしもしない**(`flows.md` §2)。
**そこから先まで言わないこと** ★ — この例外を通ったアラートを `/build` が実際に上げれば、
構築記録が1本増え、触ったマニフェストとロックファイルが `code_roots` に在るぶん鮮度スタンプが
失効する。**それは普通の `/build` と同じであって、この例外によるものではない。**

**前置きは2つ在り、順序はこの順である** ★ — **まずこの例外**(写さないもの)、
**次に §1.1 の問い**(元からあった問題か)、**それから上の表**である。

**行3と行4が振り分けである。** **黙って直すことも、黙って無視することも許されない**(原則8)。
ただし行4は1行しか要らず、それは意図的である: **1行は記録であって、作業項目ではない。**
3と4のどちらか決められないときは **4を選ぶ** — 言い回しの抜けを追跡し損ねるのは取り返しがつくが、
課題票の一覧を溺れさせることは、4つのプロジェクトを止めた。

**この振り分けが決めるのは追跡するかどうかであって、後になってもまだ真かどうかでは決してない** —
それは §8 であり、**別の問いであり、答えも別である。**

**課題票を起こす前に `origin_layer:` を決着させる** — **修正が始まる層**であって、
それを見つけた層では決してない。「実装が仕様と違う」は 03。「その仕様が要求と違う」は 01 か 00。
**迷ったら上の層にする。** `/build` はこれをそのままタスクへ運ぶので、
**1つ低い値は、症状を下流で直して要件を決して変えない結果になる。**(検査: `CS20`。)

### 1.1 元からあった問題 — 基準コミットで再現するものは、直さずに次のミッションへ ★

**振り分けに入る前の2つ目の前置きである**(2026-08-27。1つ目は §1 の写さない例外)—
**問いが1つ在る**: **その問題は、いまのタスクが
作ったのか、元からそこに在ったのか。**

**物差しは基準コミットである** — いまのミッションが作業ブランチを切った元のコミットで、
台帳の frontmatter `基準コミット:` に在る(`orchestration.md` §7)。作業指示がその値を運ぶ
(同 §4)。

| 基準コミットで同じことが | それは | どうするか |
|---|---|---|
| **再現する** | **元からあった問題** | **このタスクでは直さない。** 上の表のとおりに記録し(行3なら課題票、行4なら残務の1行)、**次のミッションへ回す** |
| **再現しない** | **このタスクが作った問題** | **今までどおり直す**(上の表の行1) |

**確かめるのは、その問題を見つけた本人である** ★ — 実測した本人がいちばん安く答えられ、
**中央エージェントは `docs/` も製品コードも開けない**ので、中央が自分で確かめる形は元から
取れない(`orchestration.md` §2)。枝を切り直して実測するのは、環境の設定で破れる問題では
特に高くつくので**要求しない** — **確かめた方法(基準コミットの版で同じ手順を踏んだ、
その行がその版に既に在った、など)を報告の根拠に1行書く。**

**主観を1つも要さないのが、この物差しの値打ちである。** 「関係が深いか」「ついでに直せるか」を
考えさせない。2026-08-26 の事故は、頼まれた仕事が終わった後、**元からあった1つの穴を
18時間21分追いかけたもの**だった — **この判定だけで、1本目の修繕の前に止まっていた。**

**既定で走り続ける。止まらない。** 元からあった問題を見つけても、人間に「いま直すか」を
問うために手を止めることはしない(**問いは着手前に1回にまとめる**という原則5 と同じ向きである)。
出口は2つだけである:

- **報告に書く**(`orchestration.md` §5 の `元からあった問題:` の欄)。**元の依頼の完了を
  妨げる疑いが在るときだけ「妨げる疑い: 有り」とし、根拠を1行付ける。**
- **中央エージェントは、疑い 有り のものだけを台帳の `## 人間への問い` に1行載せる。**
  **人間の1行が来たときだけ**、同じミッションで直す(修繕の作業指示が出る)。来なければ
  既定のまま次のミッションへ回る。

**重大度「高」の不具合を次へ回すと、リリースミッションは閉じられない** ★ — デプロイゲートは
`type: bug` かつ `severity: 高` の課題票が0件であることを要求する(`flows.md` §2)。
だから**リリースミッションでその重さの課題票を起こしたなら、「妨げる疑い」は 有り である** —
出荷を塞ぐものは、定義上、頼まれた仕事の完了を妨げる。**これは新しい経路ではなく、
上の「妨げる疑い」の判定が機械的に決まる1つの場合である。**
**通常ミッションでは塞がない**(及第ラインを要求するのはデプロイ点であって、ミッションの
終わりではない — `flows.md` §1)。

**一律に課題票へ倒さない。** 元からあった問題も、記録先は上の表そのままである
(課題票に値するのは不具合と完了定義を阻害するものだけで、残りは残務の1行)。
**「元からあった」は追跡の要否を1段上げる理由にならない** — 一律に票を起こせば、
§1 が止めている「課題票が解消の 2.4〜3.4 倍の速さで生まれる」に戻る。

## 2. `docs/residual.md` と `docs/pendings.md` — 残務と、意図的な先送り

### 2.1 残務(振り分けの行4からの1行)— 台帳ではなく、境界のある作業集合

**置き場は `docs/residual.md` ただ1つである** ★(2026-08-25 の人間の裁定でここへ分けた。
それまでは `docs/pendings.md` の中の1節だった)。節は「## 残務(文書整合ほか)」の1つ、
項目1つにつき1行、**日付が先頭**:
`- <日付> <path:節> <一文で何が揃っていないか>`。ID も重大度も解消条件も無い。
**日付を先頭に置く形は荷重を負っている**: `doc-health.py` は残務の行をその形で見分ける。
**検証のあいだ、この一覧を読み直すものは1つも無い** — これが `/verify-docs` の所見へ
戻ってくることは決してあってはならない。

**なぜ1つのファイルに溜め続けないか。** 実測された失敗は「項目が記録されたこと」ではない。
**記録が無料で、削除が任意だったので、一覧は増える一方だった**ことである。
1行の記録は入るときは安く、**一覧が誰も読まない長さになった時点で、出るときには無価値**である。
だから重複が落ち、**仕事そのものがそれを消化し**、**長くなったらファイルごとローテーションする。**

**★ 2026-08-25 の裁定で、行数の上限(50行)と 90日の恒久受容を廃止した。**
それまでは、上限を超えた分と 90日誰も動かさなかった行が「恒久受容」として落ちていた。
**いまは落とさない — 代わりにローテーションする**(下の (2))。落とす側の穴のほうが
大きかったからである: 落とした行は報告に件数しか残らず、**増分でしか読み直さないフローは、
落とした所見の対象がその後変わらなければ二度と同じ場所を読まない。**
記録を捨てずに「1つのファイルが大きくなりすぎない」を満たす形が、ローテーションである。

**(1) 1鍵1行。書くのは1つのコマンドからである** ★(2026-09-12)。
鍵は **`path:節` とその1文を正規化したもの**(空白を畳み、末尾の 。 を落とす)。
**追記も削除もこのコマンドで行い、台帳を直に開いて書かない** ★ — **錠を取らない書き手が
1つでも居れば、その書き手が読んでから書き戻すまでのあいだに入った追記が消える。
追記だけを錠に入れても塞がらない**(2026-09-13):

```bash
python3 .claude/scripts/doc-health.py --append-residual="- <YYYY-MM-DD> <path:節> <一文>"
python3 .claude/scripts/doc-health.py --resolve-residual="<落とす行の逐語>" \
    --verdict="<直した | 不要と裁定(理由)>" --record=docs/histories/<履歴>.md
```

**鍵の重複はこのコマンドが見る。既に在るなら何も書かずに 0 を返す** — 新しい日付すら書かない。
**手で grep してから書く形はやめた** ★ — grep と書込みのあいだ、そして
**押し出し(`--rotate`)が複写してから元を空にするあいだ**に、書いた行が
**押し出し先にも新しい台帳にも残らずに消える**(2026-09-12 の検査 A2-6)。
退避は最初から錠を取っていたので、**錠を取らない書き手が居ることがそのまま穴だった。**
コマンドは退避と同じ錠を取り、読取りから書戻しまで他の更新を待たせる。
**1文が鍵の一部であるのは意図的である** — 同じ節の中の別々の問題は別々の2行であり、
それを1行に畳むのは黙って無視すること(原則8)になる。
**見るのは `docs/residual.md` だけである** ★ — ローテーションで押し出された
`docs/residual-NNN.md` はコマンドも見ない(2026-08-25 の裁定)。**だからローテーションをまたぐと、
同じ気付きがもう一度書かれうる。** それは承知の上の代価である —
押し出されたぶんまで毎回読むなら、ファイルを分けた意味が消える。

**(2) 50件でローテーションする。これは上限ではない**(語の定義は `glossary.md`)。
残務へ1行でも書いたら、**書き終わったところで**次を打つ:

```bash
python3 .claude/scripts/doc-health.py --rotate
```

行が 50 以上なら `docs/residual.md` の中身を `docs/residual-<3桁の連番>.md` へ**複写し、
そのうえで元を空にする**(見出しと書式の注記は元のファイルから引き継ぐので、書き手が見る形は
変わらない)。50 未満なら何もしない。**先に改名してはならない** ★ — 改名と新規作成のあいだで
落ちると `docs/residual.md` が消えたまま残り、打ち直しても戻らない(台帳の欠落は
fail-closed で拒まれるので、次の `/build` が入口で止まる)。この順なら、落ちても台帳は在り、
押し出しの写しが1本余分にできるだけである。
**打つのは書いたフロー自身である。** 掃き出し(下の (4))と違って権限の制限は無い —
**1行も落とさない操作だからである。**
**50 は厳密ではない。** まとめて書いて 50 を超えても構わない。超えていたらそのまま回す。
押し出されたファイルは消えず、人間はいつでも読める。**フローは読まない**(上の (1))。

**だから、消えては困るものを残務に置いてはならない** ★: 人間の回答の着地
(`docs/histories/<日付>-answer-<論点>.md`)への唯一のポインタは課題票である
(`type: modify`。`flows.md` §5。inspection-19 D-17)。**理由は 2026-08-25 に変わった** —
行が落ちるからではなく、**ローテーションで押し出された時点で、どのフローも二度と読まない**
からである。課題票はローテーションしない。

**(3) 仕事がこれを消化し、その消化は義務である。** `/build` の出口(§5)で、
`path` が閉じるタスクのクロージャに在る残務の行すべてに**判定が付く** —
直した / 不要と裁定(理由) / 持ち越す(理由) — そして**削除されるのは最初の2つだけである**。
判定はそのタスクの履歴ファイルに記録する。**覆われているのに判定の無い行は `/build` の出口の欠陥である。**
**見るのは `docs/residual.md` だけである**(押し出されたファイルには判定を付けない)。
**強制されるのは判定であって、作業ではない**: 履歴に「持ち越す(理由)」と書けば通る。
**警告にすぎない消化は、誰も引かない消化である** — それが、そもそも一覧が伸びた原因である。
(これは `.claude/directions/core.md` §3 の「文書整合は完了を決して阻害しない」と矛盾しない:
あちらはリリースの完了定義についての文であり、こちらは F1 の出口の規律である。)
これは読取を増やさない: **それらの文書は既に開いている。**
**パスの一致だけで削除してはならない** — 同じファイルの別の節に在る、触れていない問題は、
直ってもいなければ判定もされておらず、それを消すのは原則8 が禁じる黙った無視そのものである。

**(4) 掃除は機械が回し、決して黙って起きない。**
`python3 .claude/scripts/doc-health.py --as-of=<YYYY-MM-DD>` は、落ちることになるものを並べる。
**落ちるのは2種類だけである** — 同じ鍵の重複と、`path` がもう存在しない行 — そして
**生成ファイルを含め、何も書かない**。`--sweep --record=<履歴ファイル>` を足すと落とす。
**`--record` は必須であり、`docs/residual.md` が書き換えられる前に書かれる**ので、
**途中で中断した run が「台帳から消えていてどこにも記録されていない行」を残すことはできない。**
`--sweep` を付けて走らせるのは `/verify-docs` だけであり、検証の段で行い、その後に再生成する
(掃くのを最後にすると、生成された作業一覧が古いまま残る)。

**キットの版を上げたときの失効は、`/kit-migrate` が持つ** ★(2026-08-25)。
**キットを名指した残務の行だけ**を、新しい版の現物に照らして1行ずつ判定し、
**解消されているものを `--resolve-residual` で落とす**(消した行は同じコマンドが履歴へ逐語で残す。
台帳を直に開いて消さない — §2.1 の「1鍵1行」と同じ錠を通す)(手順の正は
`.claude/skills/kit-migrate/SKILL.md` の段5)。**掃き出し(上の (4))とは別物である** —
あちらは日付と重複で落とす一括の操作で、権限は `/verify-docs` だけが持つ。こちらは
**版が上がったという事実に対する1行ごとの判定**であり、製品の残務には触らない。
**これを誰も持たないと、直っているキットの欠陥が「まだ在る」という顔で残り続ける。**

**満杯という状態は無くなった** ★ — **どのフローもいつでも残務へ書ける。**
2026-08-25 の裁定より前は、節が50行で満杯のとき `/verify-docs` 以外のフロー
(`/verify-impl`・`/verify-tests`・`/relations`)は所見を書かずに落とし、
**満杯そのものが「`/verify-docs` を先に回す契機」**だった。**その2つとも廃止した** —
落とす先が無くなったので、落とす理由も、先に回してもらう理由も無い。
(製品の不具合はもともとこの経路に乗らない — 課題票には上限が無い。§1。)

**落ちた行の一覧は `docs/histories/` へ写す。** 決して `docs/reverification.md` へは写さない —
あのファイルは毎回まるごと再生成されるので、そこへ残した記録は次の生成で消える。
`doc-health.py` は「今日」という概念を意図的に持たない(同じ入力に対して生成物がバイト単位で
同一でなければならない)。だから日付は `--as-of` として入り、**生成しないこの1経路だけ**で使う
(いまの `--as-of` が決めるのは履歴に書く実行日だけで、**どの行が落ちるかには効かない**)。

**変わらないこと**: 残務は依然として1行であり、ID も重大度も `closes_when:` も追跡義務も持たない。
**完了を決して阻害せず**(`.claude/directions/core.md` §3)、**古いというだけで課題票へ格上げされることも決してない。**

**旧い版から上げたとき**(2026-08-25 より前の版でこのキットを使っていたプロジェクト)★ —
上書き展開は `docs/` を作らないので、**この1回だけ手で移す**:

```bash
cp -n .claude/templates/residual.md docs/residual.md
# docs/pendings.md の「## 残務(文書整合ほか)」節の行を、そのまま docs/residual.md の
# 同じ見出しの下へ移し、pendings.md からその節を削る。**1行も捨てない。**
python3 .claude/scripts/check-backlog.py   # 残務の件数が、移す前と同じであること
```

**途中で止めたことは機械が見つける。** `docs/residual.md` が無いか、`docs/pendings.md` に
`## 残務` の節が残っているあいだ、`check-backlog.py` と `doc-health.py` は
**「残務0行」と読まずに終了コード 2 で拒む** — `cp` だけして行を移し忘れると、
既存の行はどの道具からも見えないまま「0行」で通ってしまうからである。

### 2.2 意図的な先送り(振り分けの行2)

**能動的に「不完全なままでよい」と決めたもの**だけについて、項目1つにつき節を1つ:

```markdown
## P-003 MFA のバックアップコードは未実装
- 決めた日 / 決めた人(人間 / AI(D0-xx の委任内))
- 何が不完全か / なぜ今は OK か
- どうなったら解消が必要か: <非空。これが空の棚上げは棚上げではない>
- 関連: FR-auth-05-3 / MODULE-auth-mfa-verify / issues: なし
```

`P-nnn` は3桁の昇順連番で、**欠番は埋めず、削除済みの番号も再利用しない**(課題票の `NNN` と同じ
規則)。**番号は自分で数えず、機械に払い出させる** ★(2026-09-05。それまでは手で
`grep` して最大値+1 を採っていたが、台帳自身は解消時に消えるので削除済み番号を再発行しうるうえ、
並走した2本が同じ番号を採る穴が在った):

```bash
python3 .claude/scripts/doc-health.py --next-pending-id   # 錠の下で払い出す。印字された番号を使う
```

払い出しは実物(台帳・履歴・02 のカバレッジ表)と控え(`.claude/state/ids.json`)の両方を見て
単調に増えるので、**実物が全部消えた番号も再発行しない**。**控えは git で共有する**(鮮度スタンプの
`stamps.json` と同じ扱い — 変わったらコミットに含める。共有しない複製では「消えた番号を
再発行しない」が実物の走査だけに弱まる)。重複がそれでも入ったときは
`check-ssot.py` の CS27(採番の一意)が捕まえる。
番号が別の棚上げを指すようになると、`部分` の根拠が静かに入れ替わる。

その項目が 02 のカバレッジ表の `部分` を裏づけているとき、`関連` は**条項 ID** を名指さねばならず、
「どうなったら解消が必要か」は空であってはならない(`/verify-docs` A2 が確かめる。欠けたら「高」)。
一生: タスクになったとき、または仕様として決着したときに削除する(そのときは 01/02 へ
「適用外(理由)」を書く)。`pendings.md` は仕様ドキュメントではない
(version も verified も持たず、決して `source` にならない)。

## 3. `docs/issues/` — 追跡する問題(不具合と完了定義の阻害だけ)

`docs/issues/NNN-<TYPE>-<slug>.md`。`NNN` は昇順で、**決して再利用しない**。
**番号は `python3 .claude/scripts/doc-health.py --next-issue-id` で払い出す** ★(2026-09-05。
§2.2 の `P-nnn` と同じ理由 — 手で数えると、削除済みの再発行と、並走した2本の同番が起きる)。
`TYPE`: `bug`(仕様に対して振る舞いが誤っている)/ `modify`(仕様どおりだが変えねばならず、
かつ完了定義を阻害する。**人間の回答がまだ SSOT に反映されていない**ものもここに入る —
決めたことが仕様に書かれていない状態は完了定義を塞ぐ。`flows.md` §5)/
`future`(後で必要 — **控えめに使う**。「後で」の大半は残務の1行である)。

```markdown
---
id: 007-bug-login-lockout-counter
type: bug
severity: 高
origin_layer: 03
found: 2026-08-01
found_in: /verify-impl(02⇄03比較)
related: FR-auth-02, MODULE-auth-login
closes_when: ロックアウトカウンタが成功ログインでリセットされ、FR-auth-02-3 のテストが green
pattern: success-path-state-reset-missing
pattern_survey: grep -rn "attempts" src/auth/ で走査 — 同型2件(login_attempts / mfa_attempts。2026-08-01)
summary: ロックアウトのカウンタが成功ログイン後にリセットされない
---
```

(この例は重大度「高」なので、本物の `pattern:` **と** `pattern_survey:` を持っている —
§3.1 の対である。中/低 の課題票は `pattern: なし` と書き、走査は省く。)

- **`closes_when:` は必須である** — その課題票が閉じる、外から観測できる条件。
  **それを述べられない課題票は、課題票ではなく残務の1行である。**
- **`found_in:` が、格上げされたタスクが何を問えるかを決める。** これは `/build` の着手時に
  構築記録の `origin:` へ写される — 人間の指摘 は `origin: human-report` になり、
  AI が見つけたもの(verify 系・実装中・QA・機械検査)はすべて `derived` になる。
  **その1欄が、エラー処理 / テスト / ログ / 設定を問えるかどうかを決めている**
  (**唯一の正: `.claude/directions/delegation.md` §5**)ので、
  **修正がどこへ着地するかではなく、実際に誰が見つけたかを書く。**
  条件が満たされたらファイルを削除する(履歴は `docs/histories/` と git に生き残る)。
- 本文の見出しは `.claude/templates/issue.md` が所有する
  (事象 / 影響 / 原因の見当 / 正はどちらか / 対処案 / 経緯)。
- 一生: `/build <issue-id>` が格上げする(ファイルは `/build` の出口が消すまで残る)。
  誤検知だったときは理由を追記して削除する。
- **範囲の中に `severity: 高` の不具合が残っているあいだ、「文書は完全」と報告してはならない。**

### 3.0 `severity` — この表が唯一の正である

**目の前の1件だけから決められること。** **頻度は意図的に入力にしない**:
下の同型の走査を負うのは「高」だけなので、**「同型が何件あるか」が「高」にするものでもあると、
循環する** — その循環こそが、この値が感覚で選ばれていた理由である。

| 値 | 条件(いずれか1つで足りる) |
|---|---|
| **高** | `AC-nn` が実システムに対して落ちる / データ・権限・金・監査証跡が損なわれる / 回復に再リリース・データ移行・外部への連絡が要る |
| **中** | 受け入れ基準の条項に対して振る舞いが誤っているが、上の「高」の条件のどれにも当たらない |
| **中** | 仕様どおりに動いてはいるが、外の誰かが気づく本物の問題である(状況に合わない文言、無駄に遅い経路、紛らわしい状態) |
| **低** | 外側は何も変わらない: 言い回し、参照、表の穴、何も阻害しない技術的負債 |

**複数の条件に当たるときは、最も高いものが勝つ。** 根拠は本文の 影響 の節に書く
(`templates/issue.md`)。この値は CS12 と、下の §3.1 と、verify 系フローの裁定義務が読む
(`.claude/directions/core.md` §5 が「高」の所見の裁定を必須にしている)ので、
**決して読み手の印象に委ねられない。**

### 3.1 同型の走査 — 重大度「高」のときだけ

**「高」**の不具合の最初の1件で、直す前に: 型を1文で名指し、ファイルの集合を道具で導き
(`check-ssot.py`、`relations-query.py --impact`、grep — **決して記憶からではない**)、
件数を数え、その両方を課題票の frontmatter に記録する(`pattern:` + `pattern_survey:`。
CS12 は、型を宣言しながら走査を持たない「高」を落とす)。**いま何件直すかは人間が決める** —
**機械的に列挙し、承知のうえで切る。** 残した分は同じ `pattern:` を持つ課題票になる。

**中/低 では列挙は不要であり、要求してもならない** — 出会ったものを直して(または残務の行を
1本落として)先へ進む。**毎回新しい型を発明することが、列挙が無限になった経路である。**

## 4. `docs/feedbacks/` — 知見(問題の記録ではない)

やり取りから学んだこと: 人間が提案を覆したこと(理由が示されなかったときは質問をちょうど1つする)、
自明でない罠と教訓。知見1つにつき1ファイル、`docs/feedbacks/NNN-<slug>.md`:
状況 / 提案 / 決定と理由 / 次にどう活かすか。仕様ドキュメントではない。
**何かを提案する前に、ファイル名を走査し、当たったものだけを読む。**

## 5. タスクが存在しないときの決定シートの項目

構築記録も**質問シートも持たない** run(`/relations`・`/retrofit` — verify 系フローはこれに
当たらない。あちらの人間への問いは質問シートに乗る。`flows.md` §5)が挙げた項目は、
**1項目につき `docs/issues/` の1件**として起票する。これは §1 の振り分けの表に対する
**1つ目の明示的な例外**である(§5.1・§5.2 と同じく、表とその問いの順序が決して変わらないよう、
表の外に並べてある): **答えの無い人間の判断は、その報告とともに死ぬ**(実測: 12項目のうち6件が
失われた)ので、追跡の仕組みを持つ唯一の記録に留める。`closes_when:` は
「人間が回答し、回答が反映されたとき」に、その項目を足したものである。
例外: 人間が**変えない**と決めた項目には課題票を作らない — 根拠は `docs/histories/` へ。
起票の前に `docs/issues/index.md` を走査し、**本当に同一の項目が在れば、複製を作らずにその
経緯へ追記する。**

**鮮度の所見をここへ起票することは決してない**(§8)— この規則に番号を振らないのは、
§1 の振り分けを広げるのではなく、**この節を狭めている**からである。その主題は**既に存在する記録**
であり、所見はその記録へ戻る。**課題票について起票された課題票は、この一覧を答えようのないものに
する唯一の形である。**

## 5.1 中断の残余 — タスクを打ち切るとき

**2つ目の明示的な例外**(置き場の理由は §5 と同じ): タスクを放棄するとき
(`/build` の「中断したとき」の手順。**入口は2つで、実装の途中で人間がやめると決めたときと、
出口で整合が取れなかったときである** — 後者は実装が終わった後にしか起きない)、
残余は **`type: modify` の `docs/issues/` 1件**として
起票する。構築記録とそのシートは打ち切りとともに削除されるので、原本が消える —
**課題票の本文へ引用する**: 何が半分できていたか、何を戻すか終わらせるか、
そしてどこにもまだ反映されていない、到達した決定・回答済みのシート項目のすべて。
`closes_when:` = 「全項目が後続タスクで反映されるか、破棄と裁定されたとき」。
学んだことの振り分け: 調べた事実とタスクを跨ぐ前提はこの課題票の本文へ。
`docs/feedbacks/` へ行くのは教訓と罠だけである(§4 の定義 — **事実は知見ではない**)。

## 5.2 タスクの衝突で待たされた変更要求 — `/build` の経路

**3つ目の明示的な例外**(置き場の規則は同じ): `/build` が、新しい変更要求が進行中のタスクと
重なっていることを見つけ、人間が「そちらを先に終わらせて」と答えたとき、
待たされた要求は **`docs/issues/` の1件**として起票する(`type: modify` か `future` —
手順は `/build` §1)。それは不具合でも完了定義の阻害でもないが、
**課題票は再開の仕組みを持つ唯一の記録である**(`/build <issue-ID>`、`related:` にクロージャの種)—
残務の1行はそれを担えない。`closes_when:` = 「`/build <issue-ID>` で後続タスクに昇格して
反映されるか、取り下げと裁定されたとき」。

## 6. 索引の再生成

`docs/issues/index.md` と `docs/feedbacks/index.md` を決して手で書かない:
`python3 .claude/scripts/build-index.py`。`pendings.md` に索引は無い。

## 7. histories/ はどこで規定されているか

`docs/histories/` は自分の規範ファイルを持たない: **書式の正は `.claude/templates/history.md`**
であり、書くのは `/build` の出口である(および原則1 の書き手 — `/verify-docs`、
タスクを伴わない `/relations --apply`、`/retrofit` — がそれぞれ自分の項目を残す)。

## 8. 鮮度 — その記録はまだ真か(唯一の正)

**記録は、それが書かれた日における事実である。** §1 の振り分けは追跡する価値が在るかを決めるが、
**その中の何ひとつとして、後になってもまだ真かどうかを決めていない。** その隙間は実在する:
棚上げは 02 のカバレッジ表の `部分` を裏づけており(§2.2)、
他のタスクの副産物として直された不具合の課題票は、依然として完了定義の阻害として読める
(`.claude/directions/core.md` §3)。**どちらも、どの検査も捕まえない偽の主張である。**

**これが直す非対称**: AI の `DS-*` と人間の `決定` はどちらも 見直す条件 を持ち、
どちらも条件成立の検査を持つ(`/verify-docs` の C 検査 と A0)。
**棚上げの 解消条件 と課題票の `closes_when:` は同じ形をしているのに、その検査を持っていなかった。**

### 作業一覧は判定ではない

`doc-health.py` が「鮮度確認の候補(棚上げ・課題票)」の節を `docs/reverification.md` へ生成する:
すべての棚上げと課題票を、**記録日**(決めた日 / `found:` — 最終確認日の欄は存在せず、
`found:` を上書きしてそれを偽装することも決してない)、条件の逐語、`関連` とともに並べる。
残務は件数と最古の日付だけとして現れ、**決して行としては現れない**(§2.1 は生きている:
検証はあの一覧を読み直さない)。生成ファイルは「今日」という概念を使わないので、
集計の傾向は**そのファイル自身の git 履歴**から読む — `.claude/directions/core.md` §3 の「課題票の純増」は
そこから来る。

**機械は 解消条件 を判定できない。** 作業一覧は AI が読むべきものを並べるだけで、
**決して判定を書かない。** 判定するのは2箇所であり、**それで全部である**:

| いつ | 何を | 規範 |
|---|---|---|
| `/verify-docs` A2 | クロージャが既に開いている `部分(P-nnn)` の棚上げ | `/verify-docs` A2 |
| `/build` §1 | `pendings.md` 全文と `issues/index.md`(毎タスク開く) | `/build` §1 |

**どちらも、既に起きている読取を広げているだけである。どちらも新しい読取を足していない。**
定期的な棚卸しのスキルは存在せず、作ってはならない(このファイルの前文:
既にそこに居るスキルが記録する)。**課題票の本文が開かれるのは格上げのときだけである**
(`/build` §0)— だから課題票については作業一覧の**最古の記録日**が信号であり、
1件読むことにするのは**人間の一手であって、予定された義務ではない。**

### 判定不能は失敗ではなく、期待される答えである

大半の `closes_when:` は判定に実システムを要する — 重大度「高」は、`AC-nn` が実システムに対して
落ちることとして*定義*されている(§3.0)。**既に範囲に入っている**文書とコードから判定し、
それ以外は 判定不能 と書く(A0 が `決定` の検査に与えているのと同じ逃げ道である)。
**判定不能 を無くそうとすると、これは実行を伴う棚卸しに変わる** — それは考えうる最も重い手順で
あり、**手順を足すのではなく減らせという `.claude/directions/core.md` §3 の指示が禁じているもの**である。

### 鮮度の所見はどこへ行くか — 決して新しい記録にはしない

**これが、この仕組みが自分自身を養うのを止めている唯一の規則である。**
条件が成立したことは新しく発見された問題ではない。**人間の結末を要する、既存の記録である。** だから:

- **条件が成立した棚上げ** → 報告する(verify 系フローの報告、またはタスクなら構築記録の申し送り)。
  人間が決着させる: それがこのタスクの仕事になる(§1 の行1)、新しいタスクになる、
  または 01/02 が「適用外(理由)」を得て項目が削除される(§2.2 の一生)。
  **人間の結末を得ないまま置かれたものは、黙って無効になるのではなく、古いままである** —
  A0 と同じ言い回しであり、意図的である。
- **`closes_when:` が既に満たされて見える課題票** → その課題票の 経緯 に日付つきで1行追記し、
  報告する。**削除するかは人間が決める**(§3 の一生)— **自分の読みだけで決して消さない。**
- **決して新しい `docs/issues/` の項目として起票せず、決して残務の1行にもしない。**
  §5(タスクを伴わない run の項目は1件ずつ課題票になる)は**鮮度の所見には適用されない** —
  課題票について起票された課題票は「どれが未反映か」を答えようのないものにし、
  このファイルが小さく保つために存在している一覧を膨らませる。

**ここに関所は1つも無い。** 鮮度は `/verify-docs` を止めず、出口の条件でもなく、
リリースの完了定義の一部でもない。
