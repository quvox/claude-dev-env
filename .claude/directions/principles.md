# 原則 — `.claude/directions/core.md` §2 と §3 の全文

日本語で書く。**`core.md` §2 は各原則の束縛する1行を持ち、このファイルは理由・例外の一覧・
振り分けの表を持つ。** 2つで1つの規範であって、2つの規範では決してない。
`core.md` §2 の行とこのファイルの節が違う読み方をされうるとき、**詳細の正はこのファイル、
何が束縛するかの正は `core.md` §2** である。

**目の前の判断が実際に触れている節を読む。ファイルを読むのではない。**

**同じ規定を2か所に書かない。写しではなく参照を置く。** ★ 規範(`.claude/` の下)では、
1つの規定の正はただ1つの節が持つ。他の節・スキル・雛形・道具の一覧は、その節を参照する —
**写しを置いてよいのは、参照先がその場で要る実際の値を持たないときだけである**
(絶対パス・識別子・そのまま打つコマンド行が差し込み記号のままで、参照先を開いても値が
得られない場合)。**そのときも写すのは値だけであり、手順と条件は参照へ送る。**
参照先が値を運んでいないなら、**まず参照先に値を運ばせる**(写しを増やすのではない)。
理由: 参照は腐らないが、写しは片方だけ直されて腐る — 2026-08-23 の検証で、雛形・スキル・
道具の一覧に置かれた5つの写しが、どれも正と食い違っていた(人間への問いの経路が正反対、
報告の手順が実行できない、起動行の引用が壊れている、`green` を記録できる条件が逆、
導入の手順が消してはならない設定の行を消せと言う)。
**キットに同梱されない導入手順(`install-notes.txt`)は、この基準の外に在る** —
人間が導入の場でそのまま打つ行を運ぶ文書である。

## 1. 未来の状態を SSOT に書かない。

**未来の状態を SSOT に書かない。** 中心はこのキットが生まれた日から変わっていない —
願望・計画・TODO は決して入らない。SSOT は**いまの姿だけ**を記述する。
フローの導入で変わったのは*誰がいつ書くか*である。書き手は閉じた一覧である:

- **`/build`、そのクロージャの中で。** フローの最中、SSOT はそのクロージャの中に限って
  コードより先行してよい(境界のある、機械から見える過渡である: 構築記録の `state: building`。
  verify 系フローはそのクロージャを除外する — `flows.md` §3)。「未来の状態は一瞬たりとも
  存在しない」に代わる不変則は、**F1 の出口で、そのタスクが触った文書とコードが一致している**
  ことである(F1 の段4と、段5からの小さなループがそれを保証する。構築記録ゲートは
  `check-buildrecord.py`)。`building` の記録は上限を越えて生き延びてはならない —
  `check-debt.py --demote` が滞留したものを verify の網へ戻す。
- **`/verify-docs` と `/verify-impl`、それぞれの書込み表の範囲で**(PATCH級と機械的に導ける修正、
  ツール生成領域、`verified`、版、履歴、索引)。
- **ブートストラップの一族**: 構築が進行していないときの `/relations --apply --bootstrap` と
  `/retrofit`。**構築を伴わない `/relations --apply` を人間が明示的に要求したとき**
  (コード ⇄ 03-impl の復元。履歴に1件残す)。`/setup` の雛形の逐語複製(判断ゼロ)。
- **ツール生成領域は、`/relations` のどのモードでも書く(検査モードを含む)**:
  `docs/03-impl/callgraphs/` と `docs/03-impl/feature-graph.md` はその場で再生成される —
  再生成はコードと機能表を書き写すだけで判断を持たない(`relations/SKILL.md` §0。
  変わっていない入力は同じバイト列に再生成される)。
  **ツール生成領域として認めるのは、この2つのファイルだけである** — 状態の層(`stamps.py`)と
  仕様ドキュメントの一括検査(`check-ssot.py`)も、同じ2つを1組として扱う。
- **機械の欄**(`<!-- BEGIN GENERATED: <道具名> … -->` 〜 `<!-- END GENERATED: <道具名> -->`)を
  **印に名前が書かれたその道具**が埋めるとき ★(2026-08-27)。いまその道具は2つである —
  事実を出す `build-facts.py` と、索引を書く `build-index.py`。
  **失効の判定と一括検査が区画を剥ぐときも、道具名は問わない**(`flows.md` §2・`check-ssot.py`)。
  **これはツール生成領域ではない** — 上の2つは**ファイルまるごと**が機械のものだが、こちらは
  **手で保守する文書の中の区画**である(層を問わない)。書き写すだけで判断を持たない点は同じで、
  **同じ入力なら同じバイト列が出る。** **手書き禁止であり、埋め直しは F2 と F3 の検査の
  先頭で走る**(`conventions.md` §4)。**未来の状態は、ここにも入らない** — 出るのは
  いまのコードといまの上の層から読み取った値だけである。
  **原則10 が言う「生成領域」はこれより広い**(索引や `reverification.md` を含む)—
  **広いほうの残りを `/relations` の検査モードが書くことは無い**(書き手はこの条の上の行が持つ)。
  **判断を含む 03-impl のファイルは、`--apply` と上の verify 系フローのものである。**

**これ以外は SSOT を書かない** — `/verify-tests` も書かない(課題票と試験成果物を書く。
03-impl/tests の所見はキューへ回り、`/verify-impl` が決着させる)。質問シートの転記も書かない:
回答の転記先は SSOT の外に限られ(構築記録、課題票の `## 経緯`)、**中身が SSOT に属する回答は
キューに載る修繕**になり、そのクロージャを持つ `/build --repair` が着地させる(`flows.md` §5)。

## 2. コード ⇄ 03-impl は正確に一致する。

**コード ⇄ 03-impl は正確に一致する。** 食い違ったとき、**黙ってどちらかに寄せてはならない**:
**事実の差異**(パス、シグネチャ、呼び出しの有無)はコードに合わせて直し、報告する。
**自分で裁定できない意図の差異だけ**が人間に届く — キューか質問シートを通って届くのであって、
フローの途中の質問としてではない。振り分けの表: `.claude/directions/03-impl.md`。
ブートストラップの例外(既存文書よりコードが勝つ)は、**矛盾する箇所を全件列挙すること**を
条件とする。定期的な強制は `/verify-impl`、クロージャの中では F1 のタスク内整合確認が強制する。

**コードが持ち主である値は、散文に書き写さずに機械の欄へ入れる** ★(2026-08-27) —
`conventions.md` §4 がその形を持つ。**これはこの原則の言い換えであって、新しい要求ではない**:
コードを読めば分かる値を人が写せば、その写しは実装が動いた瞬間に嘘になり、
**この原則が求める「正確に一致する」を保つ費用を、検査が毎周払うことになる**
(2026-08-26 の実測: 1つの周が直した15件は全件がその型で、1つの事実が46か所に写されていた)。

## 3. 変更はそれが生まれた層から降ろす。

**変更はそれが生まれた層から降ろす。** 目的・範囲 → 00、振る舞い → 01、構造・契約 → 02、
実装の細部 → 03、そして**画面の見え方・操作の流れ・デザインの基調 → `docs/ux/`**
(UX 文書 — 検証連鎖の外に居る置き場で、正は `.claude/directions/ux.md`)。これは**何を書くか**を束縛する規則であり、「`/build` はいつ 00 を書き直すか」に
そのまま答えている: **目的・範囲・受け入れシナリオのどれかが実際に変わるときだけ**である
(裁定 D'-7。運用の形は `/build` §1 の起点の表)。既存の文が正しい層に在るかの棚卸しは
**`/retrofit` で一度だけ**行う — 繰り返す検査ではない(機械の見張りである CS18 / CS20 は
一括検査に残る。気づいた置き違いは原則8の振り分けを通す)。

## 4. 上流が持たないものを作らない — ただし委任されたものは決める。

**上流が持たないものを作らない — ただし委任されたものは決める。** 曖昧さや欠落に出会ったら
振り分ける: **標準委任(`DS-01`〜`DS-08`)**またはプロジェクトの委任の中 → **自分で決める
(これが既定)**、そして所有する層に1行**開示する**: `[DS-nn] 決めたこと — 理由: … /
見直す条件: …`。**問う基準**(外から見える **かつ** 後から戻しにくい、または例外)を満たす
→ **決して決めない**。決定シート(F1)か質問シート(F2〜F4)へ載せる。
**エラー処理・テスト・ログ・設定は、上流が黙っていても決める** — 要求と受け入れシナリオ・受け入れ基準から導き、
外から見えるものは 01 の受け入れ基準に `[DS-nn]` として書き、**決してシートに載せない**
(`delegation.md` §2.1。`check-sheet.py` SH10 が載せたものを落とす)。
反転は1つだけ: **人間**がシステムを動かして提起したタスク(`origin: human-report`)は、
提起された領域について問うてよい(`delegation.md` §5)。
**版を選ぶときに指定が無ければ、どの版にするかは `delegation.md` §2.3 が決める**
(その時点の最新の安定版。条件はここで言い直さない)。
**テストはビルドと同じ版の環境で走らせる** — `delegation.md` §2.4(同上。版の固定を宣言していない
プロジェクトでは、合否に掛けず報告だけにする)。
範囲・条件・書式の唯一の正: **`.claude/directions/delegation.md`**。

**この原則の鏡像 — 基本要件(`BR-nn`)。**「上流が持たない」は、範囲を発明しない理由である。
**その機能が既に含意している性質を欠いたまま出荷してよい理由には決してならない。**
閉じていて、しかし増えていくその一覧が **`.claude/directions/baseline.md`**(唯一の正)である:
各項目をタスクのクロージャに照らして判定し、該当したものは**その事実を所有する層**に書き
(外から見えるものは 01 の受け入れ基準)、判定を — **該当も非該当も理由つきで** — 構築記録の
`## 基本要件の点検` に記録する。**その判定を誰がどう見るかは `baseline.md` §1 の4 が正であり、
ここでは数え上げない**(`baseline.md` §5 — この一覧を言い直した写しは、項目が増えるたびに
古くなった)。
該当した行が実際に作られたかは先送り禁止の点検が見る。**基本要件は決してシートの項目にならない**:
問う基準が決めるのは「どう満たすか」であって、「満たすかどうか」ではない。

## 5. 問いは束ねて絞る。

**問いは束ねて絞る。** `/build` が問うのは最大2回である: 着手時に1回(1枚のシート。
問いゼロのシートは人間の登場そのものが無いことを意味する)と、出口で1回 —
出口は**予見できなかったもの**で、**かつ**問う基準を満たすものに限る。着手時の機械的な曖昧さ
(slug の重複、対象候補が2つ以上)はその場で聞く。**verify 系フローは決して問わない**:
F2〜F4 は所見をすべて3チャネルへ流し(`flows.md` §5)、問う基準を満たすものは1枚の質問シートに
乗る — **1日1枚**で、人間は自分の速度で答え、**存在した瞬間から未回答の問いとして数えられる**
(`check-debt.py`。猶予期間は無い — 答えるとは、転記してファイルを消すことである)。
**どのシートも1行で答えられる。**

**答える前に調べさせる問いは、問うたのではなく転送しただけである。**
**人間に読ませるために書き、人間へ渡すものはすべて** — 決定シート、質問シート、チャット、
艦隊運用のエージェントからの相談、**ミッション報告の全体**、`/kit-improve` の**引き渡し文**、
`docs/README.md` — **別のファイルを開かずに読める**必要がある。
**この列挙は例示であって、限定ではない**(掛からないのは3つ — 規範そのもの、`docs/` の SSOT、
そして AI から AI への通信である。内訳は `delegation.md` §1.1)。要件は4つ:
裸の内部識別子を書かない、キット内部の言い回しを使わない、その場でこしらえた略語を使わない、
選択肢は記号ではなく起きることで書く。4つの規則と理由を持つ唯一の正:
`.claude/directions/delegation.md` §1.1。**4つのうち2つは機械が見る** —
`check-sheet.py` SH11(説明の無い識別子)と SH12(キット内部の言い回し。禁じる語は
`.claude/directions/glossary.md` から読む)— 残り2つは書く側が守る。

## 6. 検証済み記録(`verified`)は文書ごとに付く。

**検証済み記録(`verified`)は文書ごとに付く。** 仕様ドキュメントは `version`
(MAJOR.MINOR.PATCH)を持ち、`verified` を書くのは verify 系フローだけである —
`/verify-docs` は自分の範囲の文書に、`/verify-impl` は 03 層の代表に書く。
**検証済み記録が有効なのは、その `version` が文書の現在の MAJOR.MINOR と一致するときだけである。**
`against`(検証時点の上流の版)は**追跡可能性のために記録されるが、有効性の条件ではない** —
上流が動いたとき、下流の文書は**再検証候補**になる(`/verify-docs` が報告する作業一覧)のであって、
自動的に無効になるのではない。**意味を変える修正は MINOR、迷ったら PATCH。**
**版を上げるのは、その版が指す中身が動いたときだけである** ★ — 検証済み記録を打ち直すだけの
run、`against` の行が上流の版に追随しただけの run は、`version:` を動かさない。有効性の条件は
「`verified` の版が現在の MAJOR.MINOR と一致すること」であって、打ち直しのたびに繰り上げること
ではない。中身が動いていないのに MINOR を上げると、それは**偽の「意味が動いた」宣言**であり、
下流の `against` の行を連鎖して動かして、鮮度スタンプを無意味に失効させる(実測 2026-08-25:
20文書を打ち直した run で中身が動いたのは4文書だけだったのに、版の繰り上げが別のフローの
鮮度スタンプを殺していた。受け側の手当ては `flows.md` §2)。
**「その版が指す中身」は、まとめて検証する代表では自分のバイト列ではない** — 下の例外に在る
`docs/03-impl/index.md` は 03 層をまとめて検証するので、`relations/` や `features.md` が動けば
索引自身が1バイトも動かなくても版を上げる(そうしないと、層が動いたのに層の検証済み記録が
有効なまま残る)。**代表以外の文書では、指す中身はその文書自身である。**
`/build` が書き直したばかりの文書は未検証である(MINOR の繰り上げが古い検証済み記録を無効に
した)— これは「作ったが、まだ検証していない」の正直な表示であって、欠陥ではない。
例外: `relations/MODULE-*.md` と `features.md` は `03-impl/index.md` によってまとめて検証される。

## 7. 未決点ゼロが実装の開始条件である。

**未決点ゼロが実装の開始条件である** — 境界はいま `/build` の中に在る: 着手時のシートに
未回答の項目が在るあいだ、段3(コードを書く段)は始まらない。フローの途中で見つかった
問う基準を満たすものは**出口へ回す**のであって、推測で回避してはならない。
未決点は構築記録の中に生き、**仕様ドキュメントの中には決して置かない**。
未決点を閉じるとは、それを決めること(原則4)であって、それについて問うことではない。

## 8. 見つけた問題は記録する。ただし記録先の振り分けを通す。

**見つけた問題は記録する。ただし記録先の振り分けを通す。** 範囲の外の問題を黙って直しては
ならず、記録することが仕事になってもならない:

**振り分けに入る前に落ちるものが1つだけ在る** ★ — **外部の追跡システムが既にその一覧を持ち、
直れば向こうで閉じる問題は、こちらへ写さない。**「記録しない」のではない: **記録は向こうに在り、
写せば同じものを2箇所で管理することになって、写した側が必ず古くなる**(`conventions.md` §4)。
だから**これは黙った無視ではない** — 向こうの一覧が台帳であり、直すものはこちらの仕事になり、
直せないものは向こうに open のまま残って次の run でまた見られる。
**該当するのは `/dependabot` が読む GitHub の Dependabot アラートだけであり、
他のどんな問題もこの例外に入らない。例外の正は `issues-pendings.md` §1 が持つ**
(範囲も、増やす経路も、覆う先がどこで止まるかも、あちらが決める。ここに写さない)。

- **仕様に対して振る舞いが誤っている(不具合)、または完了定義(`.claude/directions/core.md` §3)を阻害する**
  → `docs/issues/` に1件1ファイル。`closes_when:`(閉じる条件)と `origin_layer:`(修正が
  始まる層。迷ったら上の層)を書く。`/verify-tests` はさらに、最後の green 鮮度スタンプ以降の
  構築記録に1件ずつ紐付ける。
- **それ以外**(文書整合の抜け、言い回し、網羅表の穴、何も阻害しない技術的負債)
  → `docs/residual.md` の `残務` 節に**1行**。ファイルも重大度も追跡義務も作らない。
  **この節に行数の上限は無い**: 1鍵(`path:節` + その1文)が1行、**50行以上になったら
  書いたフローがファイルをローテーションする**(`doc-health.py --rotate`。1行も落ちない。
  押し出されたファイルはどのフローも読まない)、`/build` は自分のクロージャが覆う行を
  判定を付けて消化し、`/verify-docs` は検証の run のたびに掃き出す
  — **落ちるのは同じ鍵の重複と、対象が実在しない行だけである**(落とした行は
  `docs/histories/` に記録する)。記録が無料で削除が任意だったこと、それだけが、
  この一覧が誰も読まない長さまで伸びた理由である(仕組みの正は `issues-pendings.md` §2.1。
  ここに書いたことが `残務` に何かを阻害させることは無い)。
- **同型の走査(`pattern:` / `pattern_survey:`)が必須なのは重大度「高」の課題票だけである。**
  それ以外は、出会ったものを直して先へ進む。

意図的な先送りは、それでも `pendings.md` の完全な項目を得る(**そちらは `残務` とは
別のファイルである**)。書式:
`.claude/directions/issues-pendings.md`。

## 9. 文書を書く前に、その仕事が実際に必要とする規範の節を読む。

**文書を書く前に、その仕事が実際に必要とする規範の節を読む。** スキルごとの最小集合は
`.claude/directions/reading.md` である。それは**床であって天井ではない** —
自分の判断が並んでいる節の外へ出た瞬間に、そのファイルの該当する節を開いて読む。
**多く読むことは決して違反ではない。読んでいない節から決めることが違反である。**
どの `docs/` の文書を読むかは別の問いであり、各 SKILL.md と `CLAUDE.md` §1 が持つ。
**作る文書・作り直す文書の `.claude/templates/` のファイルも、同じ床の上に在る** —
`reading.md` が雛形を並べていないのは、各層の規範が自分の雛形を名指しているからである。
**雛形の見出し構造を変えてはならない**(スキルとスクリプトが見出しを名前で参照している)。
節をまるごと欠いてよいのは、**その層の規範がそう名指している場合だけ**である(現在は
`tests/strategy.md` の実装後の3節。正: `.claude/directions/03-impl.md`)。
`relations` の埋まっていない見出しは残すのであって、決して削除しない(`relations.md` §4.1)。

## 10. 探す前に道具を使う。

**探す前に道具を使う。** まず `.claude/scripts/`。**生成領域を手で書かない。**

**「生成領域」の範囲の正はこの §10 である** ★。生成領域は2つの形を持ち、**どちらも手書き禁止**である:

- **ファイルまるごとが機械のもの**: `docs/03-impl/callgraphs/` と `docs/03-impl/feature-graph.md`
  (この2つだけを「**ツール生成領域**」と呼ぶ。§1)、各層の索引 `index.md`(`build-index.py`)、
  `docs/reverification.md` と `docs/histories/index.md`(`doc-health.py`。下の段落が理由を書く)。
- **手で保守する文書の中の区画**: 「**機械の欄**」
  (`<!-- BEGIN GENERATED: <道具名> … -->` 〜 `<!-- END GENERATED: <道具名> -->`)。
  埋めるのは印に名前が書かれたその道具である(§1、`conventions.md` §4)。

**例外は1つだけである** — `docs/03-impl/index.md` の手で保つ節
(`.claude/directions/03-impl.md`)。**他の節・他のスキルに在る列挙はすべて例であって、
範囲の宣言ではない** — 数えるときはここへ戻る。

構築で最もよく手を伸ばす4本:
`relations-query.py --impact <path>`、`check-ssot.py docs`、`check-buildrecord.py`、
`check-debt.py`。検証では: `build-callgraphs.py`、`cluster-features.py`、
`callgraph-check.py`、`stamps.py`。運用の入口: **`.claude/tools-readme.md`**。
`docs/reverification.md` と `docs/histories/index.md` も同様に `doc-health.py` が生成する:
前者は上流が動いた文書を、無効にすることなく可視化する。後者は文書ID・仕様IDから履歴への、
安定した逆引きである。`reverification.md` はさらに、**記録した条件を誰も読み返していない**
棚上げと課題票を並べる(鮮度確認の候補。それぞれの記録日つき)。
**これは作業一覧であって判定ではない** — 解消条件を機械が判定することはできない。
判定するのは `/verify-docs` A2 と `/build` §1 が、既に行っている読取の中で行う。
条件が成立したものが新しい課題票や `残務` の行になることは無い
(唯一の正: `.claude/directions/issues-pendings.md` §8)。

## 11. 自分の画面が見えない読み手に向けて書く。

**自分の画面が見えない読み手に向けて書く。** ファイルは `path:line` で名指す。
**このキットが定義した ID だけを使い、初出でその ID が何かを言う**(`KIT-*` は教訓のラベルで
あり、ケバブケースの ID そのものが教訓を述べている。台帳は存在せず、必要でもない)。
結論から始める。世辞は書かない。**どの結論もその根拠を伴う。**
**すべての報告を「次にあなたがすること」で終える**(正確なコマンド、または必要な決定、
または「無し(こちらで続けます)」)。人間が理由を言わずに提案を覆したときは、
**学習のために質問をちょうど1つ**して、`docs/feedbacks/` に記録する。

## 12. 停止条件と完了(`.claude/directions/core.md` §3)

品質には床(機械検査)が在る。この節は**天井**である。**両者は等しく束縛する。**
**停止条件を伴わずに床だけを定める規則は、このキットの欠陥である。**

- **製品の完了(リリースの完了定義)は、次によってのみ定義される**:
  1. `02-design/environments.md` の `unit` / `integration` / `E2E` のコマンドが全部 green、
     **`build` / `lint` は構築フロー(F1)の出口の時点で** green(先送り禁止の1項目目。
     `flows.md` §6)— **作った後にこの2つを確かめるフローは無い** ★: 試験フロー(F4)が
     走らせるのは4つの試験区分だけで、`build` も `lint` も試験区分に無い(`build-record.md` §2)。
     **資格情報の混入検査(`secret_scan`)は `unit` の green の中に入っている** ★ —
     テスト基盤を使うなら `f4-unit` が `strict` の下でそれを呼ぶので、**コマンドが未設定なら
     unit は green にならない**(`tests/gates.yml` の F4 の節)。**基盤を使わず言語のテスト命令を
     直に走らせる構成でも、`unit` の green には同じ検査の1回の成功が要る**(`/verify-tests` §3)。
     構築の組は未設定でも通るので、**出荷を止めるのはここだけである**、
  2. `00-requests/acceptances.md` の `AC-nn` が全件、実システムに対して通る(**または `適用外(P-nnn)`** — その環境をこのリリースでは用意しないと人間が決め、棚上げの項目が実在するとき。4項目目の「または `適用外(操作面なし)`」と同じ形である。`/verify-tests` §1)、
  3. `docs/issues/` に AC を阻害する不具合が1件も無い、
  4. **探索的QAを走らせて重大度「高」の所見が0件** — **実体は操作面の種類ごとに2つ在り、
     持っている分だけ走る**(画面は `/browser-qa`、サブコマンドは `/cli-qa`。
     `.claude/directions/ux.md` §0)— または 「適用外(該当する面が無い)」を、
     それを示す 02 のファイルとともに宣言してある。**ブラウザやコマンドを動かせないことは
     そのどちらでもない**: それは環境の不備であり、人間へ回る(`/browser-qa` §0・`/cli-qa` §0)。
  5. `01-requirements/system.md` の `## 必須制約(交渉不可能)` の節が持つ `SR-nn` が、02 の要件カバレッジ表に**行を持ち**、
     **1件も「破れている」になっていない** — 交渉不可能と宣言した制約が完成を止めないなら、
     「必須制約(交渉不可能)」という節名は何も意味していない。

- **覆い直しにも上限があり、その「2」は別のものを数える。** 1周の終わりに中央エージェントは
  `stamps.py check` をもう一度読み、名指された最小範囲だけを覆い直す — **1周につき最大2回**、
  **同じ HEAD・同じ失効原因なら周をまたいで累積2回まで**。超えたら配車し直さず、
  何が閉じないかを1行残して人間へ渡す。**上の修正ループの「最大2回」は1本の run の内側の反復を、
  こちらは run をまたぐ覆い直しの本数を数える。** 全文は `orchestration.md` §3.0。

  **文書整合(検証済みの網羅、`residual.md` の `残務`)は完了を決して阻害しない** — それは後から
  付いてくる。フローの導入が動かしたのは*いつこれを判定するか*であって、*何を判定するか*では
  ない: デプロイゲート(`stamps.py check`)は全 verify 系フローが**現在の状態に対して** green で
  あることを要求し、完了定義の項目はそれらのフローが実行するものそのものである。
  **完了定義を判定することは常に正当な仕事である。** 結果は表で報告する。
- **検証は止まる。** verify 系フローの1回の run は、修正のループを**最大2回**する
  (スキルの中で強制されている)。2回目の後に残った `中`/`低` は `docs/residual.md` の `残務` へ回り
  (行数の上限は無く、同じ鍵は何も書かない — **満杯という状態が無いので、どのフローもいつでも
  書ける。行数が判定を保留させることも、所見を課題票へ格上げすることも無い。50行以上に
  なったら、書いたフローがファイルをローテーションするだけである**。`issues-pendings.md` §2.1)、
  run は判定と鮮度スタンプを残して終わる(**対象が0件の run を除く** —
  独立レビューも鮮度スタンプも起きない。`/verify-docs` §2)。**green を止められるのは阻害する所見だけである**
  (虚偽を述べている文書、どちらが正でもありうる未解決の矛盾、`callgraph-check.py` の重大度 高)。
  **回答に駆動された修正の run**(質問シートを適用する run)は、回答が変えたものとその下流に
  自分を限定し、**その差分から生まれた論点についてだけ**シートの項目を足してよい —
  それ以外は原則8の振り分けを通るので、ループは構造的に収束する。
- **所見ゼロの PASS は正当な結果である。** 見た中で最も弱い点を名指すことは必須である。
  空の一覧を避けるために所見をこしらえるのは欠陥である。
- **文書の検証済み記録(`verified`)は編集を生き延びる。ただし鮮度スタンプは別の仕組みであり、生き延び方が違う。** ★ green の鮮度スタンプを無効にするのは鮮度スタンプの仕組みだけである —
  `stamps.py` はパスを**その (flow, scope) が宣言した依存**(許可リスト: `stamps.py deps`)と
  突き合わせるので、**宣言された依存への変更は PATCH であっても無効にし**、
  宣言されていないものへの変更は何も無効にしない(意味の等級を機械は付けられない)。
  **例外は2つで、どちらも「機械が持つ領域だけが動いた」という同じ形をしている** ★ —
  **(1) 管理欄だけに収まる変更は、鮮度スタンプにとって変更ではない**
  (frontmatter の `updated:` 行・`verified:` ブロック、および両側が正しい形の `version:` を
  ちょうど1行持つときのその `version:` 行)。**(2) 機械の欄の中身だけの変更も、同じく変更では
  ない**(2026-08-27。手で保守する文書の中の、道具が丸ごと書く区画 — `conventions.md` §4。
  **除外はパス単位では書けないので区画単位である**)。**中身が動いていないなら、版の札が繰り上がって
  いても失効させない** — 「MINOR = 意味が動いた」は中身についての宣言であって、中身が動いて
  いなければ偽だからである(原則2)。欄の一覧と、版の札に掛かる唯一の条件は `flows.md` §2 が正。
  無効になるのは**動いたパスだけ**である: それらを検証し直して `record --covers …` で記録する —
  green は全体の鮮度スタンプとその部分の記録から組み立て直され、**誰も覆わなかったパスは鮮度スタンプを
  古いままにする**。**green を記録できるのは、そのフローの依存(部分記録なら覆い)に未コミットの変更が無いときだけである** —
  未コミットの書込みはどの鮮度スタンプよりも後なので、`record` がそれを拒む。
  **依存の外の汚れは拒まない**(`flows.md` §2)。
  **検証済み記録**を無効にするのは MINOR 以上の編集だけであり、PATCH級の修正
  (言い回し、参照の張り直し、古くなった文の削除)は無効にしない。
- **再監査は条件付きである。** **新しい判断を含む修正**の後は、検証し直す。
  名指した出典に対して逐語で確認できる修正には再監査は要らない — 代わりに確認したことを記録する。
- **検証は仕様ドキュメント(SSOT)を太らせてはならない。** 但し書きを足すのではなく、
  置き換えるか削除して直す。検証の run が SSOT の総バイト数を増やしたなら、そのことと理由を言う。
  **規範への追記は、これとは全く別の話である** ★ — `.claude/` の下の規範は verify 系フローの
  出力先ではなく、変えるときは必ず `/kit-improve` が手順を持つ(次項)。**混同してはならない**:
  SSOT に向けた禁止を規範に当てると規範の改善が止まり、規範に向けた手順を SSOT に当てると
  クロージャの外の書込みが通ってしまう(原則1)。
- **キットはいつでも直してよい。完了定義による凍結は廃止した**(2026-08-22 の人間の指示)。
  代わりに**縛りが2つ**在り、**どちらも満たさなければ、その直しはキットに残らない。
  確かめる時点は別である**(汎用の縛りは触れる前、検証の縛りは書き出す前)。
  (番号で呼ばない — `条件1 / 条件2` は「人間に問うてよいか」の予約語である。`glossary.md` §2):
  **汎用の縛り — 汎用的であること** — このキットを配る**どのプロジェクトでも成り立つ**直しであること。
  このプロジェクトの名前・パス・業務・構成に依存するものは、キットの改善ではなく
  **プロジェクト固有の改造**であり、`docs/` か `*.local.json` に属する(`/kit-improve` §4 の
  分類 **[その他]** がそれを名指す)。
  **検証の縛り — 検証を通していない変更を残さないこと** — 直した後、**パッチを書き出す前に**通す
  (編集より先に検査は走らせられないので、縛るのは順序ではなく出口である)。下限は
  `/kit-improve` §3 が持つ(コンパイル・selftest・`check-kit-refs.py`)、加えて**独立の検査を
  1本**通す(艦隊なら中央へ要求して起こしてもらう `@review`、単体なら codex か文脈の空いた
  サブエージェント。`orchestration.md` §1.2)。
  **通らなかった変更は戻す。**
  いま手を付けないと決めたなら、案は今までどおり `residual.md` の1行へ回してよい。
  **キットを実際に編集するときは、必ず `/kit-improve` が手順を持つ**
  — 最初に `kit-patch.py status`、最後に `.claude/improvements/patches/` へパッチを出し、
  **そのパッチはただちに本流のリポジトリへ移す**(1改善 = 1パッチ。プロジェクト側は複製も
  メモも残さない)。**パッチを生まなかった編集と、プロジェクトから出なかったパッチは、
  次の配布で失われる。**
- **負債の計器と健全性の信号。** `check-backlog.py`(未クローズの課題票 / `残務` の行数)と
  `check-debt.py`(未検証の構築記録 / 鮮度スタンプの古さ / 未回答のシート)は `/build` の入口で
  読まれ、**何も拒まない**: 数えて印字し、数字が何であれ終了コード0で終わる。
  **設定すべき値は無く、上げるべきものも無い** — **「もう見ないことにする」という決定を、
  数字を書き換えて下すことはもうできない。数字がもう何も決めていないからである。**
  拒むのは及第ラインだけである(デプロイの時点の `stamps.py check`)。**計器の数字は、
  自動配車にとっては読んで報告するだけのものであり、次に何を回すかを決めない** ★ —
  起動契機は `flows.md` §2.1 が、回すフローの集合は `stamps.py check` が持ち、回す順は固定で
  ある。**人間はそれに縛られない**: 数字を読んで全数を出すのは人間の契機である
  (`flows.md` §4)。数字の外の健全性の信号(製品コードが変更行の
  20%未満、verify 系フローが毎回2回目を必要とする)は、**手順を足すのではなく規範か範囲を
  減らせ**という意味である(`residual.md` の1行を通すか、上の2条件を満たすなら
  そのまま `/kit-improve` で直す)。
