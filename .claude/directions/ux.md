# ux.md — docs/ux/(UX 文書)

日本語で書く。

**この層が決めること**: UI/UX — **利用者が製品に触れるところ(「操作面」)ごとに、
そこで何が達成されていないといけないか**。そして画面については配置方針、項目と状態、
画面遷移と操作の流れ、デザインの基調(トーン・色・余白・文字サイズの段階・部品の流儀)、
コマンドについては呼び出しの形と出力の見え方、そしてその経緯。

**操作面は2種類ある** ★ — **画面**(`SCR-nn`)と**コマンドのサブコマンド**(`CMD-nn`)である。
**この層は画面だけのものではない**(2026-09-15 の人間の裁定で広げた)— コマンドしか持たない
製品にも、「どのサブコマンドで何が達成されていないといけないか」の置き場が要る。
**この文書で「画面」とだけ書いてある規則は画面だけに掛かり、「操作面」と書いてあるものは
両方に掛かる。**
**この層が決めないこと**: 何を約束するか(01 — 受け入れ基準)、モジュール構造・契約(02)、
実際のコード(03)。

## 0. この層の性質 — 検証連鎖の外、qa 試験区分の中 ★

**UI/UX の記述は、最初は薄く、試行錯誤とユーザテストを経て徐々に仕上がる。**
最初から正解がある前提の仕組みは間違いであり、**周回ごとの追記・改訂は正常な姿であって
不備ではない**(2026-08-28 の人間の裁定)。だからこの層は他の層と扱いが違う:

- **文書検証(`/verify-docs`)と実装整合検証(`/verify-impl`)の依存の外に在る。**
  `stamps.py` の依存集合は許可リストで、`docs/ux/` はそこに載っていない —
  UX 文書だけを直しても、00〜03 のどの鮮度スタンプも失効しない。
  ちょっとした UI 修正が大規模な検証作業を発生させないための線である。
- **qa 試験区分の依存には入っている**(`stamps.py deps verify-tests:qa`)。
  UX 文書を直せば qa が失効し、qa 試験区分の run(**探索的QA** — ユーザテストの周回の
  中なら周回末の `@qa`)が実物と突き合わせて戻す。
  **qa 試験区分の実体は2つある** ★ — 画面を触る**探索的ブラウザQA**
  (`.claude/skills/browser-qa/SKILL.md`)と、サブコマンドを叩く**探索的CLI QA**
  (`.claude/skills/cli-qa/SKILL.md`)である。**持っている操作面の分だけ走る**
  (2026-09-15 の人間の裁定で足した)。**qa 試験区分が丸ごと適用外になるのは、人が直接操作する
  面が1つも無いとき**(他のプログラムから呼ばれるだけの部品など)**だけである** —
  「画面が無い」はブラウザQAが適用外になる理由であって、qa 試験区分が消える理由ではない。
  **これが無いと、実画面と食い違う内容へ書き換えてもどの検査も鳴らずに出荷できてしまう。**
- **純粋な UX 文書の編集には、決定シートも `/verify-docs` も独立レビュー(`@review`)も
  付けない。** 付くのは周回あたり `@qa` 1回だけである。文書同士を突き合わせるためだけの
  新しいレビュー工程を作らない(過剰 verify への逆戻り)。
- **検証連鎖の外に置くことと、単一書き手の外に置くことは別である。**
  `docs/ux/` のパスはクロージャに含め、並走判定にも数える(`orchestration.md` §3.4。
  例外は `reviews/` 配下 — 同 §3.4 とこのファイルの「ユーザテストの周回」)。
- **今の姿だけを書く**(原則1 と同じ規律)。書き手も同じく `/build` がクロージャの中で書く。

**承知の上の代金が2つある**(判断が分かれたら人間へ): UX 文書と実画面のずれを文書検証の
強制力では捕まえない(受け皿は qa の失効 + `@qa` の突き合わせ + 下の機械検査 —
UI/UX では文書が数日古いことの実害が小さい、として払う)。01 との紐付けは部分的なので、
条項 ID の grep で列挙されるのは紐付けを書いた画面だけである(受け皿は周回末の `@qa` と
人間のユーザテスト)。

## ファイル構成

```
docs/ux/
├── policy.md                    # 基調: トーン、色・余白・文字サイズの段階、部品の流儀
├── flows.md                     # 冒頭に台帳2本(画面一覧 = SCR-nn / コマンド一覧 = CMD-nn)
│                                #   + 主要な操作の流れ
├── screens/SCR-nn-<画面>.md     # 画面ごと: 達成条件、見え方の基準、配置方針、項目、状態
├── commands/CMD-nn-<コマンド>.md # サブコマンドごと: 達成条件、呼び出しの形、出力と終了コード
└── reviews/NN.md                # ユーザテスト第N回の指摘と処置(経緯の台帳)。00.md は初期設計の
                                 #   判断の置き場(移行したプロジェクトでは移行の記録もここ)
```

- **台帳は `flows.md` の中の2本の表である** — 画面 ID は「**画面一覧**」の節、
  コマンド ID は「**コマンド一覧**」の節(02 から引っ越した — かつては `02-design/system.md` の
  UI 設計が定義場所だった)。**持っている面の分だけ置けばよい**: 画面しか無い製品に
  コマンド一覧は要らず、コマンドしか無い製品に画面一覧は要らない。
- ファイル名にも ID を入れる(`screens/SCR-01-ログイン.md` / `commands/CMD-01-deploy.md`)—
  画面名やサブコマンド名を変えても ID は不動なので、`flows.md`・`reviews/` からの参照が切れない。
- 雛形: `.claude/templates/ux-policy.md` / `ux-flows.md` / `ux-screen.md` /
  `ux-command.md` / `ux-review.md`。
- **frontmatter は `id` / `updated` / `summary` だけ持つ**(意図的な例外 — 例外の一覧の正は
  `conventions.md` §1 で、そこに載せてある): `version` と `verified` を持たない — この層の鮮度は
  文書の検証済み記録ではなく qa 試験区分の鮮度スタンプが持ち、`source` の再検証の網の
  外に居る(冒頭の「この層の性質」)。

## 状態と経緯を分ける(この層の SSOT 規則)★

**「現在どうなっているか」(状態)と「なぜそうなったか」(経緯)を同じ置き場に混ぜない**
(2026-08-28 の人間の裁定「当然A」。01 が `functional.md` と `decisions/` を分けている流儀)。

- **経緯(判断とその理由)の置き場は `reviews/` だけである。** `screens/` には持たせない。
- `screens/` の行から経緯へは**参照だけ** — 書式は「`reviews/NN.md` の指摘 <n>」
  (下の機械検査がこの形を読む)。
- 逆に `reviews/` の処置欄は「何をしたか1行 + 直した `screens/` の箇所への参照」に留め、
  **画面の現状の記述を持たない** — 持てば現状を記述する2つ目の場所が生まれ、ずれたとき
  どちらが正か判らなくなる(この層は文書検証の外なので、機械は捕まえない)。
- `screens/` は `policy.md` の値(余白の段階など)を再掲しない。参照する。
- **`reviews/` は歴史の記録である。** 後の画面の削除・改名で処置欄の参照先が消えるのは
  許容する — 遡って直さず、検査も掛けない。

`reviews/` が要である: 「第3回で6人中5人が設定を見つけられなかった → ナビ直下に移した」という
経緯が残るので、後から来た者が「なぜこの配置か」を辿れ、一度捨てた案に戻ることも防げる。
`screens/` の記述は指摘を処置したときに直す — 事前に完成させる必要がない。

## 設計の前に調べる — 業務の流れと、操作の頻度 ★

**操作面の配置と道順は、調べてから決める。** 操作面を**新しく作るとき**と、
**既存の面の配置・道順を作り直すとき**は、**1バイトも書く前に**次の3つを調べる。
**掛かるのは「何をどこに置くか」を決め直すときだけである** — 項目名の変更、文言の直し、
値の調整、達成条件の表だけの更新、見え方の基準だけの更新には掛からない。

| 調べること | どこを見るか | 調べないと何が起きるか |
|---|---|---|
| **1 この製品は何のために在るか** | 00 の `request.md` の目的と対象利用者。**読むのはこの調べのあいだだけで、`docs/ux/` の本文に 00 の語や ID を持ち込まない**(この層の文書が参照してよい上流は 01 の条項 ID だけであり、それは下の「00/01 が変わったときの橋」が変わらず持つ) | 目的に要らない操作が主導線に並び、目的の操作が奥に沈む |
| **2 利用者の業務の流れ — だれが、どの順で、どれくらいの頻度で行うか** | 00 の受け入れシナリオ、01 の UC、既存の面の `reviews/`、人間が挙げた不満 | 面の並びが業務の順と食い違い、1つの仕事が面をまたいで散る |
| **3 先例 — 同じ種類の製品が、この操作をどこに置いているか** | 既存の実装、同種の製品の通例 | その分野の利用者が知っている場所に物が無い |

**調べた結果は `reviews/` へ書く** — 状態ではなく**判断の理由**だからである
(上の「状態と経緯を分ける」)。`screens/` / `commands/` には書かない。書き方は3つで固定する:

- 書くのは**調べたこと**であって、決めたことではない。決めたことは配置として
  `screens/` / `commands/` に現れる。
- **自分が触る操作面ごとに1つの節を足す。** 見出しは `## 調査: <面の ID>`(面をまたぐ
  作り直しなら `## 調査: <何の作り直しか>`)で、末尾に日付を置く。
  ユーザテストの周回の中なら**その周回の `NN.md`** へ、周回の外(新規作成・作り直し)なら
  **`00.md`** へ足す。
- **足すだけで、他の作業指示が書いた節には触らない** — 「ユーザテストの周回」の
  「各作業指示は自分の担当する指摘の行しか触らない」と同じ規律である。
  `reviews/` は並走判定の交わりに数えないので、**この規律が唯一の網である。**

**頻度は配置の根拠である** ★ — 上の 2 で数えた頻度を、導線の重みにする:

- **だれにとっての頻度かを書く。** 同じ操作でも、担当者には毎日・管理者には年1回ということが
  普通に在る。**先にその面がだれのものかを決め、その人の頻度で並べる。**
- **その人が毎日・毎回行う操作が、いちばん短い道順を取る。**
- **滅多に行わない操作は、日々使う面の中に混ぜない** — 年に数回の設定、ログアウト、
  管理者しか行わない登録などである。別の面へ出すか、その面の端へ寄せる。
  **「置ける場所が在ったから置いた」は配置の理由ではない。**
- **頻度が唯一の根拠になるわけではない** ★ — **危険な操作・緊急の操作・取り返しのつかない
  操作**は、頻度が低くても短い道順を要ることが在る。**頻度に勝てるのはこの3つだけ**であり、
  勝たせたならその理由を `reviews/` に書く。
- **`flows.md` の操作の流れには、だれがどれくらいの頻度で行うかを併記する** —
  頻度の書かれていない流れは、後から誰も配置の当否を判定できない。

**階層を1段増やすたびに、その段を通る回数だけ代金が要る。** 面を束ねる段は、
**なぜ束ねるのかを言えるときにだけ**置く(束ねないと選べない、権限で分かれる、
危険な操作を隔てる、など)。**言えないなら置かない。**

**これを止める機械検査は無い**(この層は検証連鎖の外に在る — §0)。受け皿は周回末の `@qa` と
人間である。**だから、調べずに決めたことは黙って出荷される。**

## 達成条件 — この操作面で何が達成されていないといけないか ★

**操作面ごとのファイル(`screens/` と `commands/`)は「達成条件」の表を持つ。** 1行が1つの達成で、
**その画面に立った利用者 / そのサブコマンドを打った利用者が、何を終えられなければならないか**を書く。
雛形は `.claude/templates/ux-screen.md` と `.claude/templates/ux-command.md`。

**なぜ要るか。** 01 の条項は**製品ぜんたいの約束**であり、下の「01(要件)との紐付け」が
定めるとおり、画面からの参照は**部分的で、何も止めない**。だから **「この画面で何ができないと
いけないか」を全部言える場所が、どこにも無かった** — 画面の項目と状態は書かれているのに、
その画面が在る理由は誰も数えられない、という形である(2026-09-15 の人間の裁定)。
**この表がその1つの置き場である。**

| 欄 | 書くこと | 空にできない理由 |
|---|---|---|
| **達成 ID** | `SCR-nn-A#` / `CMD-nn-A#`(面の ID + 連番)。**一度振ったら動かさない** | テスト・指摘・課題票から名指しで引く鍵になる |
| **何が達成されるか** | **製品の内側を見ずに確かめられる1文**(01 の観測者テストと同じ線)。例「下書きを保存して、開き直すと同じ内容が出る」「取り違えた設定を渡すと、どこが誤りかが読める文で出て、終了コードが 0 でない」 | 無ければ、その面が在る理由が書かれないまま残る |
| **実現する条項** | `FR-<domain>-nn-#` を列挙。**無いなら「上流に規定が無い」と書く** | 「書き忘れ」と「そもそも要件が無い」を区別する |
| **確かめる手段** | `<テスト識別子>` / `E2E-nn` / `探索的QA` / `未検証(<理由>)` | ここが試験の仕組みとの唯一の接続点である |

- **達成条件は条項の言い換えではなく、条項をこの画面へ割り当てたものである。**
  境目の試験は下の「01(要件)との紐付け」のものをそのまま使う —
  **この文が無かったら、満たされない要件が在るか?** 在るならそれは 01 のもの(受け入れ基準)で
  あり、この表はその条項 ID を引くだけである。**条項の文面を複写しない。**
- **1つの条項が複数の面に現れてよい**(1つの約束を画面とコマンドの両方で果たすことは普通に在る)。
  逆に**1つの達成が複数の条項を引いてもよい。** 表は網羅表ではない — 条項ごとの網羅は
  03 のテスト表が持つ(`03-impl.md`)。
- **達成 ID の退役は明示的に行う**(条項 ID と同じ規律): 行は残し、`何が達成されるか` の欄の
  頭に「退役: 」と書く。**番号を振り直さない** — 振り直した参照は別の達成を指したまま
  解決してしまい、壊れ方が静かになる。
  **「退役: 」の行は、達成を試す対象から外す** ★(2026-09-15。inspection-28 C-9)—
  外さないと、**正しく廃止した操作が「達成できない」として毎回不具合に挙がる。**
  **外した番号は報告に並べる**(黙って飛ばすと、見落としと区別が付かない)。
  **廃止したものが本当に消えているかを確かめたいなら、それは現役の条項と達成として書く** —
  退役の行に確かめさせるのではない。
- **対応表を 03 側に作らない** ★ — `確かめる手段` の欄がその役をすべて負う。
  03(`docs/03-impl/tests/`)は文書検証と実装整合検証の依存の中に在るので、
  そこへ画面ごとの表を足すと、**UI を1行直すたびに重い再検証が起きる**。
  この層が §0 でわざわざ検証連鎖の外に置かれている軽さは、そこで死ぬ。

**承知の上の代金(3つめ)** — **達成条件の表が無い面を、機械は止めない。**
遡って全部に書かせないという裁定(2026-09-15)を守るためで、**新しく作る面のファイルは
雛形が表を持つので必ず入り、既存の面は触ったときに埋まる**(下の「場面2」)。
**代わりに、表を持たない面は `check-ux.py` が注記として件数と ID を印字する** —
違反にはしないが、黙って消えもしない(空欄と不在を区別する、というこの層の流儀と同じ)。
受け皿は周回末の `@qa` と人間である。

## 見え方の基準 — 画面写真を「人が決めた期待値」として持つ ★

**画面ごとのファイルは、その画面の見え方の基準になる画像を指す行を持つ。**

```
- 見え方の基準: tests/visual/baselines/SCR-01/初期.png, tests/visual/baselines/SCR-01/エラー.png
- 見え方の基準: 未取得
```

**なぜ要るか。** テストが撮った画面写真は `artifacts/<run-id>/` に落ちる — あそこは
**出力**の置き場で、実行ごとに作り直され、git に入らない(`flows.md` §2)。だから
**改修のあとに「実際に見た目が変わったのはどの画面か」を機械で言えなかった。**
残っているのは作業指示の報告に添えた1枚だけで、それは**その1回の証拠**であって
画面ごとの台帳ではない(`/build` §4)。

- **置き場は `tests/visual/baselines/<画面 ID>/<状態>.png`** — **`tests/` の中、つまり入力**で
  あり、git で追跡する。判断軸はこのキットが既に持っているもの1つである:
  **入力か出力か**(`test-design` の `references/golden.md`「git 管理する」)。
  保存済みの期待値(golden)が**見た目は出力でも役割は「人がレビューして決めた期待値」**
  だから git に入るのと、まったく同じ理由でここに入る。
- **更新できるのは人間が明示したときだけである**(golden の更新権限と同じ — `delegation.md` の
  `DS-01`)。**AI が黙って基準を上書きできるなら、壊れた画面がそのまま次の基準になる。**
- **差が出たときに残す3枚**(基準・今回・差分)は出力なので
  `artifacts/<run-id>/visual/<画面 ID>/` へ出す。**この一覧が「今回どの画面の見え方が
  変わったか」の答えである。**
- **コマンドの面(`CMD-nn`)はこの行を持たない** ★ — コマンドの「見え方」は出力の文字列で
  あり、それを固定する仕組みは**保存済みの期待値(golden)として既に在る**
  (`test-design` の `references/golden.md`。`--help`・`--json`・エラー文言・`--version`)。
  同じことを2つの仕組みで持つと、必ず片方だけが直る。
- **撮る道具はこのキットが配らない。** 撮影はテストの側の機能であり
  (`test-design` の `references/evidence-wiring.md`)、何を使うかはプロジェクトで違う。
  **キットが決めるのは置き場・更新の権限・差分の出し方だけ**であり、実際のコマンドの正は
  `02-design/environments.md` である。

**★ 差分は合否を左右しない**(2026-09-14 の人間の裁定)。**画面写真の一致判定で試験を
落とさない** — 文字の描き方やフォントのわずかな違いで簡単にぶれるものを合否に噛ませると、
本当の不具合ではない赤が増え、やがて誰も赤を見なくなる。**差分は「人が見るべき所見」として
出すだけ**である:

- 比較を**落ちない形で配線する**(どう配線するかはテストの道具しだい。正は
  `02-design/environments.md` のコマンドの側)。差分が在っても試験区分は red にならない。
- **差が出た画面の一覧を、`/build` はそのタスクの報告に載せ、`@qa` は所見の材料にする。**
  どちらも**裁定はしない** — 意図した変更か退行かを決めるのは依頼元と人間である。
- **「止めるか止めないか」を設定で選べるようにしない。** 選べると、赤の意味が
  プロジェクトごとに変わり、読み手が毎回確かめなければならなくなる。

## 01(要件)との紐付け — 片方向・部分的・非ブロッキング

それ以上に強く紐付けない(検証連鎖に入れた瞬間、冒頭の「この層の性質」の軽さが死ぬ)。
**非ブロッキングとは「紐付けの無さ・部分さは何も止めない」ことである** — 書いた参照が
壊れていること(実在しない・退役済みの条項を引くこと)は別の話で、そちらは `check-ux.py` が
止める(下の「機械検査」)。

- **ux 側(`screens/` / `commands/` / `flows.md`)にだけ** ★(2026-09-15 に `commands/` を
  足した。inspection-28 C-4)、01 の条項 ID(`FR-<domain>-nn-#`)を
  「この画面/流れが実現する条項」として書く。**01 側には ux への参照を書かない** —
  画面の追加・改名のたびに 01 の鮮度スタンプが失効することになる。
- **`policy.md` は紐付け無しが普通である。** 余白やトーンに対応する要件は存在しない。
  全項目への紐付けを義務にしない(義務にすれば「最初から完成させる」重さが戻る)。
- **条項の文面を複写しない。ID で参照するだけ** — 条項が持つのは*何を伝えるか*、
  UX 文書が持つのは*どこに・どう出すか*(01 の「受け入れ基準が文面を持つ。配置は持たない」
  と対応する — `01-requirements.md`)。
- **01 との境目の試験**(02 の UI 設計の節から引っ越した): **この文が無かったら、満たされない
  要件が在るか?** 在るなら 01 のもの(受け入れ基準)。画面の項目・配置・状態の名前に
  すぎないならこの層のもの。**両方に書くのは、必ずずれる重複である。**
- **紐付けの有無を「どの指摘が 00/01 行きか」の選別基準にしない。** 選別は指摘を読んだ者の
  判断であり、紐付けは判断の基準ではなく、**判断した後の作業を有界にする道具**である
  (条項 ID を `screens/` と `flows.md` で grep すれば、見直すべき画面が列挙される —
  ただし列挙されるのは紐付けを書いた画面だけ。冒頭の「この層の性質」の2つ目の代金)。

## 機械検査 — `check-ux.py` ★

`python3 .claude/scripts/check-ux.py`。grep 級の実在検査を1本に束ねたもので、
**この6つを見る**(対象は `screens/` と `commands/` と `flows.md` だけ。`reviews/` は
歴史の記録なので対象外 — 古い条項・消えた面への言及は誤りではない):

1. **条項参照**(UX1) — 引いている条項 ID が `01-requirements/functional*.md` に**実在し、
   かつ `種別` が `delete`(退役)でない**こと。ID は不動でも行は `delete` 印付きで残るので
   (`01-requirements.md`)、「実在するか」だけでは退役を検出できない。
2. **画面ファイル**(UX2) — 3つの向きで見る: (a) 画面一覧(「画面一覧」の見出しの下の
   台帳の表 — 検査もその節だけを台帳として読み、**見出しが無ければ違反**である。
   **コードブロックの中の `#` は見出しとして読まない** — フェンス(``` と ~~~)の中と、
   4スペース以上字下げした行。そうしないと、例に書いた見出しらしき行で節が閉じ、
   その後ろの実在する台帳の行が丸ごと落ちる。**表の行にはこの判定は掛からない** —
   箇条書きの下に置いた台帳も読む)の行のうち
   **`未実装` の印を持たない行**は、対応する `screens/SCR-nn-*.md` が実在すること
   (印を持つ行は対象外 — 台帳には未実装の画面を載せてよく、画面ファイルはその画面を
   最初に実装する `/build` が作る。下の「場面1」。**印は、いずれかの欄にちょうど `未実装`
   とだけ書く** — 語を含むだけの文は印にならない)。(b) `screens/` の各ファイルの `SCR-nn` が
   台帳に載っていること。(c) `flows.md` の本文(操作の流れ・遷移図)に出る `SCR-nn` が
   台帳に載っていること — 台帳が唯一の定義場所である。
   **「画面一覧」の見出しが要るのは、画面を持つプロジェクトだけである** ★ —
   `screens/` にファイルが在るか、本文に `SCR-nn` が出るときにだけ見出しの不在を違反にする
   (コマンドしか持たない製品の `flows.md` に画面一覧は要らない)。
3. **指摘番号**(UX3) — 「`reviews/NN.md` の指摘 <n>」の参照先(ファイルと指摘の行)が
   実在すること。
4. **達成条件の欄**(UX4) — `screens/` と `commands/` の「達成条件」の表が**在るなら**、
   その各行の**4つの欄がどれも空でない**こと(上の「達成条件」)。
   **表が無いこと自体は違反ではない** — 遡って書かせない裁定(2026-09-15)を守るためで、
   **表を持たない面は違反ではなく注記として件数と ID を印字する**(終了コードを変えない)。
   `達成 ID` の形(`SCR-nn-A#` / `CMD-nn-A#`)と、その面の ID が**そのファイル自身の
   面の ID と一致する**ことも見る — 別の面の番号を書いた行は、どこからも引けない行だからである。
   **見出しは「達成条件」ちょうどにする** ★ — 「達成条件(この画面)」のように補足を付けると
   節として読まれず、**表が在るのに検査されないまま通り、しかも「まだ書かれていない」と
   注記される**(空欄と不在を区別するというこの層の流儀の、ちょうど逆が出る)。
   だから**惜しい見出しは違反である**。
5. **見え方の基準**(UX5) — `- 見え方の基準:` の行が**在るなら**、そこが指す画像ファイルが
   実在すること(上の「見え方の基準」)。**`未取得` は正当な値であり違反ではない。**
   **行そのものが無いことも違反ではない**(UX4 と同じ理由)— 表と同じく注記で見えるようにする。
   **山かっこだけの雛形のまま(`<...>`)は未記入として違反である** — 雛形を写しただけの
   ファイルが検査を通ると、書いたことと書かなかったことが区別できなくなる。
   **`commands/` にこの行を書くことは違反である**(コマンドの面は見え方の基準を持たない —
   上の節)。書けても何も鳴らないなら、「同じことを2つの仕組みで持たない」という上の節の
   決めごとを、検査が一度も守らせないことになる。
6. **コマンドファイル**(UX6) — UX2 のコマンド版で、見るのは同じ3つの向きである:
   (a) コマンド一覧(「コマンド一覧」の見出しの下の台帳の表)の行のうち `未実装` の印を
   持たない行は、対応する `commands/CMD-nn-*.md` が実在すること、(b) `commands/` の各ファイルの
   `CMD-nn` が台帳に載っていること、(c) `flows.md` の本文に出る `CMD-nn` が台帳に載っていること。
   **「コマンド一覧」の見出しが要るのは、コマンドの面を持つプロジェクトだけである**
   (画面しか持たない製品には要らない — UX2 (a) と同じ形の条件である)。
   **見出しが在るのに面の ID の行が1つも無いことも違反である**(UX2 も同じ) — 台帳として
   読まれるのは**1列目が面の ID のセルである行だけ**なので、サブコマンド名を1列目にした表を
   書くと、台帳が空のまま3つの向きが全部素通りする。

**解析について、この検査が守ること2つ** ★ — どちらも「正しく書いた行が落ちる」形の事故を
消すためである: **セルの中のエスケープしたパイプ(`\|`)は欄の区切りではない**
(`| 出力を `a \| b` へ渡せる |` は1つの欄である)。**HTML コメント(`<!-- -->`)の中は読まない**
(配っている雛形は書き方も例もコメントで渡す流儀なので、例に表の行を1つ書いた瞬間に
実データとして読まれてしまう)。

**(c) の本文走査はコードブロックの中も見る** — 遷移図(mermaid)は必ずフェンスの中に書くので、
そこの `SCR-nn` を台帳と突き合わせないと網に穴が開く。**フェンスに入れれば台帳の外の ID を
書けるようになるわけではない**(台帳に無い面を例として書きたいなら、台帳に `未実装` の行を
足すか、その ID を書かない)。**UX6 (c) も同じである。**

**この検査自身の自己検査は `check-ux.py --selftest` である**(壊した事例で各検査が落ちる
ことを示す。`make check` が `test-state-scripts.py` ごしに走らせるので、検査を直して
自己検査が追随していなければそこで止まる)。

**違反は非0終了(ブロッキング)である。走る時機は2つ**: `/build` のタスク内整合確認
(クロージャに `docs/ux/` が入るとき — `/build` §4)と、`/verify-tests` が qa 試験区分を
走らせる前(周回末)。`docs/ux/` が無いプロジェクトでは何も見ずに 0 を返す。

## ワークフロー — 3つの場面

既存の回り方(ミッション → `@triage` → `/build` の作業指示、`@qa`)に載せる。専用の手続きは無い。

### 場面1: 新規作成

- **`policy.md` と `flows.md` の初版は、02 を書く作業指示が一緒に作る。** 初版は薄くてよい —
  基調と主要な操作の流れだけ。02 の操作面の節は `docs/ux/` を指すだけになる(`02-design.md`)。
  **`policy.md` は画面のためのものである** — コマンドしか持たない製品では薄いままでよく、
  「画面を使える手段(BR-13)」の節だけが意味を持つ(端末の対話画面を持つときである)。
- **台帳には未実装の面を載せてよい — その行のいずれかの欄(目的の欄など)にちょうど `未実装` と
  だけ書く**(`check-ux.py` UX2 / UX6 がその行のファイル不在を許す。最初に実装する `/build` が
  ファイルを作り、印を消す)。
- **`screens/<画面>.md` と `commands/<コマンド>.md` は、その面を最初に実装する `/build` が作る。**
  設計段階で完成させない。実装ができた時点の姿を現在の正として書き、初期の判断の理由は
  `reviews/00.md` へ。
  **達成条件の表もこのときに書く**(上の「達成条件」)— 雛形が表を持っているので、
  作れば入る。実装した面が何を終えさせるのかは、実装した時点で判っているはずである。

### 場面2: 実装中のついで変更

- 面を触る `/build` は、**同じ作業指示の中で** `screens/` / `commands/` の該当行を直す
  (`/build` §2)。
  **達成が増えた・減った・言い方が変わったなら、達成条件の表も同じ場で直す。**
  **表がまだ無い既存の面を触ったなら、そこで作る**(これが裁定3「触った面から埋める」の
  実体である — 遡って全部を埋める作業指示は起こさない)。
  文書コスト数行、00〜03 の検証失効ゼロ(qa だけが失効する。戻すのは qa 試験区分の run で、
  ユーザテストの周回の中なら周回末の `@qa` がまとめて戻す)。
- 見た目・操作感の調整は「修正 → ビルド → 人間の確認」の反復で回す(`/build` §3 —
  反復のあいだ文書は書かず、着地したときに1回だけ書く)。

### 場面3: ユーザテストの周回 — 1周 = 1ミッション

入口(書き取り)と出口(`@qa`)が対で、台帳が周回単位で閉じる。五月雨に届く指摘は
「作業指示が増える」形で吸収する — **範囲の事前固定はしない。**

1. **入口**: 指摘を**全部** `reviews/NN.md` に書き取る作業指示を1本。選別しない。
2. `@triage` が処置を束ねる。大半は「コード修正 + `screens/`/`policy.md` の数行」で、画面や
   機能のまとまりごとに作業指示へ切る。**ついでの API 調整が混ざる指摘は、その作業指示の
   クロージャに 02 の契約なり 01 の条項なりを含めるだけ** — そこだけ通常の検証が走る
   (失効はフロー×試験区分の単位で、再検証には全数が走るものもある —
   「触った範囲に限って安くなる」わけではない)。
3. **要件級の少数は、通常のミッションへ切り出す**(下の「00/01 が変わったときの橋」の起点A)。
   選別は機械の基準ではなく判断で行う。`@triage` は「どう切るか」を決める役で「何を作るか」は
   決めないので、**要件級の候補として人間へ提示し、切り出すかは人間が決める。**
4. **周回中の並走**: `reviews/NN.md` は全作業指示が処置欄へ1行ずつ書くので、並走判定の交わりに
   数えない(`orchestration.md` §3.4)。代わりの規則 — **各作業指示は自分の担当する指摘の
   行しか触らない**(場面1の `reviews/00.md` への追記も同じ扱い)。
5. **出口**: `@qa` を1本(既存の qa 試験区分)。**この出口のために起こした `@qa`** の時点で
   周回の受付は締める — それ以後に届いた指摘は次の周回(`reviews/<NN+1>.md`)へ送る。
   **「出口のために」を落とさないこと** ★ — `@qa` は qa が走る作業指示ごとに先に起こされる
   ようになった(`orchestration.md` §1.4)ので、**周回の途中のコード変更で出た
   引数なしの `/verify-tests`** でも1本立つ。それを締切と読むと、周回はまだ受付中なのに
   閉じてしまう。
6. `reviews/NN.md` の処置欄が全件埋まり、qa が green で周回が閉じる。
   **周回は昇格した指摘(手順3)を待たずに閉じてよい** — 待たせると要件変更1件が
   周回全体を人質に取る。

## 00/01 が変わったときの橋

**この層が知っている上流は 01 の条項 ID だけである**(00 を直接参照しない)。00 の変更が UX に
効くときは、ほとんどの場合 01 の条項の増減・改訂を伴うので、橋は 01 の1本で足りる。
**条項が変わらない 00 だけの変更**(対象利用者や成功像の言い直しなど)には橋は発火しない —
その場合の UX への影響を見るかは、変更を束ねる `@triage` と人間の判断に委ねる(機械の網は無い)。
00〜03 の側は既存の検証連鎖がそのまま面倒を見る — 新規なのはこの橋だけである。

起点は2通りで、途中から合流する: **起点A(下から昇格)** — `reviews/NN.md` の指摘が要件級 →
処置欄に「昇格: ミッション <mid> へ」と1行書き、通常のミッションに切り出す。
**起点B(外から)** — 要求・要件の変更要望を最初から通常のミッションとして受ける。

1. `@triage` が束ね、`/build` の作業指示を1本。クロージャは縦1本(00 の該当要求 / 01 の該当条項 /
   02 の網羅表・契約 / 03 のテスト表 / 実装コード)。条項の編集は 01 の既存規則のまま。
2. その作業指示の中で画面のコードを触ったなら `screens/` も直し、新しい条項 ID を紐付けに足す
   (場面2の規則がそのまま掛かるだけ)。
3. 失効と再検証は既存のまま(`docs/ux/` は文書検証・実装整合検証の依存の外なのでそれらは
   失効しない。`screens/` を直したぶん qa は失効するが、デプロイ前の `@qa` が戻す)。
4. **閉じ際に橋を1回渡す**: 改訂・退役させた条項 ID を `screens/`・`commands/`・`flows.md` で
   grep する(`/build` §4)。引っかかるのは、手順2で触らなかったのに古い条項を参照している面。
   `reviews/` は対象外(歴史の記録の中の古い ID は誤りではなく、含めると偽陽性が
   不要な後続作業を積む)。
5. 引っかかった画面ぶんの後続の作業指示を同じミッションに積む(中身は場面2と同じ軽さ。
   画面の廃止ならファイルごと削除)。
6. **直し忘れの網は退役だけ二段である**: 手順4〜5 をサボっても、退役した条項への参照は
   `check-ux.py` の UX1 が後から拾う。**改訂**は ID が有効なまま残るので二段目が無く、
   閉じ際の grep(手順4)が唯一の網である。

## 終える前の自己点検

- 操作面を新しく作った / 配置と道順を作り直したなら、**先に調べたか**、そして調べたことを
  `reviews/` に書いたか(「設計の前に調べる」の3つ)?
- 滅多に行わない操作を、日々使う面の中に混ぜていないか。`flows.md` の操作の流れに
  だれが・どれくらいの頻度で行うかを併記したか?
- `screens/` / `commands/` に判断の理由を書いていないか(経緯は `reviews/` だけ)?
  `reviews/` の処置欄に画面の現状の記述を持ち込んでいないか?
- `policy.md` の値を `screens/` に再掲していないか?
- 01 の条項の文面を複写していないか(ID 参照だけか)?
- 触った面の「達成条件」の表を書いたか(4欄とも埋めたか。条項が無いなら
  「上流に規定が無い」と書いたか)?
- 見え方が変わる直しをしたなら、差が出た画面の一覧を報告に載せたか
  (**基準画像を自分で上書きしていないか** — 更新は人間の明示指示だけである)?
- `check-ux.py` は green か(クロージャに `docs/ux/` が入るとき)?
  **注記として出た「まだ書かれていない面」は、自分が触った面か?** 触ったなら埋める。
- 01 に属する約束(この文が無かったら、満たされない要件が在るか?)をこの層に書いていないか?
