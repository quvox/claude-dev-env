## 何が変わったか

2026-09-04 に、**「出した」という出来事**が規範に入った(正は `.claude/directions/flows.md` §9)。
それまでこのキットが持っていたのは「**出せる状態か**」の判定(デプロイゲート)だけで、
出来事を残す場所が無かった。そのため、成果物が名乗る版(`baseline.md` の `BR-12`)を
動かす契機がどこにも無く、版は最初の値のまま止まっていた。

入ったものは3つである。

- **リリース台帳** `.claude/state/releases.json`。1リリース1件。
  **置き場がここなのは、どの検証フローの依存にも入っていないからである** —
  版が動いても鮮度スタンプは1つも失効しない。
- **`stamps.py release`**。版の桁を**構築記録の宣言から機械が決める**。人間は桁を指定しない。
- **構築記録の `- 外部挙動の変化:` が3値になった** — `なし` / `あり(後方互換。…)` /
  `あり(互換を壊す。…)`。`check-buildrecord.py` BRC4 が**値を読む**ようになった。

## 何をするか

**判断が要るので、`/kit-migrate` はこれを自分で当てない。** 次の2つを人間が決める。

1. **いま外へ出しているものが在るか。** 在るなら、デプロイゲートが green の状態で1度打つ:

   ```bash
   python3 .claude/scripts/stamps.py check       # green であること
   python3 .claude/scripts/stamps.py release     # 最初のリリース = 0.9.0
   git add .claude/state/releases.json
   git commit -m "release: 0.9.0" -- .claude/state/releases.json
   ```

   **最初のリリースだけは桁を計算しない** — 区間の始点が無く、過去の構築記録はこの仕組みが
   無かった頃の書式だからである。**過去の記録を書き換えることはしない。**

2. **進行中の構築記録(`state: building`)が在るなら、その `- 外部挙動の変化:` の行を
   3値のどれかに直す。** 古い書式(`あり(…)` だけで後方互換か互換を壊すかを言わないもの)は、
   構築フローの出口で BRC4 に止められる。**既に `verified` になった記録は直さない。**

## 移らなかったときに何が起きるか

- **台帳が無い間、成果物は版を名乗れない** — `stamps.py release --current` が値を返さないので、
  組み立てが埋め込む元を持たない。`BR-12` を満たさない状態が続く。
- **進行中の記録を直さないと、その構築フローが出口で止まる**(BRC4)。
  止まるだけで壊れはしないが、そこで初めて気づくことになる。
