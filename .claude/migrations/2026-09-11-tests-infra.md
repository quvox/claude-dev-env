## 何が変わったか

この版から、規範・スキルの配布物1に加え、テスト基盤の初回導入用の配布物2
(`sysdev-multi-templates-<版>.tar.gz`)とバイナリ更新用の配布物3
(`sysdev-multi-runner-<版>.tar.gz`)が付く。宣言ファイル・環境スクリプト・実行の入口
`./tests/tools/test-runner` はプロジェクトの `tests/` に置き、実行結果は git 外の
`artifacts/` に置く(`.claude/directions/flows.md` §2)。

## 手順

**導入するかはプロジェクトの判断なので、/kit-migrate は自動で当てない。**
配布元 `sysdev-multi/install-notes.txt`(**このプロジェクトには同梱されない。配布元を持つ人に
頼んで渡してもらう**)の「テスト基盤を含む3つの配布物」と
「初回導入」が配布・展開の案内である。導入を選んだら:

1. 配布物2を用意し、プロジェクト直下で `tests/` だけを初回展開する。
   `tar -xzf <配布物2のtar> -C <プロジェクト> tests`。
   配布元で打つなら `make -C sysdev-multi deploy TO=<プロジェクト>` が同じ導入を行う。
   **既存の tests が在れば上書きせず、差分を見て取り込む範囲を判断する。**
2. 同梱の `gitignore-root` をルート `.gitignore` へ追記する。
   既に `artifacts/` 行が在れば追記しない。既存本文を保持し、末尾に改行を挟む。
   `deploy` は初回展開とこの追記を行う。
3. 対象プロジェクト直下で `./tests/tools/test-runner --print-schema` を実行し、
   ラッパと同梱バイナリが動作することを確認する。続けて
   `./tests/tools/test-runner setup`(何も書き換えず、埋まっていない設定を一覧にする)を
   実行し、出力を報告に貼る。**未解決が並ぶのは導入直後の正常な状態であり、
   このコマンドは終了コード 1 で終わる**(雛形の `adapters.yml` は全部コメントアウトで
   配られるため)— 失敗として扱わない。埋めるのは `/build` の仕事で、値を決めるのは
   判断だからここでは決めない。
   宣言ファイルのプロジェクト固有の値と `docs/02-design/environments.md` のコマンドは、
   実物を確認してから書く。以後、バイナリだけの更新は配布物3を使う。

## 入れないと決めたときは、そう書き残す ★

**このプロジェクトにテスト基盤を入れない、と決めることがある**(既に別の仕組みで回している、
製品の性質に合わない、など)。**そのときは記録する** — 記録が無いと、`/kit-migrate` は
「まだ決めていない」と区別できず、**版を上げるたびに同じ案内を出し続ける。**
本当に要る移行がその中に埋もれる。

`docs/pendings.md` に棚上げの項目(`P-nnn`)を1つ作り、**見出しか本文に
「テスト基盤: 入れない」の一句をそのまま含める**(この移行の `detect` がその字面を見る)。
決めた日・決めた人・なぜ今は要らないか・どうなったら入れるかを書く
(棚上げの書き方は `issues-pendings.md` §2.2)。

**入れたときは記録は要らない** — `tests/tools/` が在ることがそのまま記録である。

## 移らなかったときに何が起きるか

`docs/02-design/environments.md` の表に実行可能な test-runner 形のコマンドは書けず、
F4 は従来のプロジェクト固有のテストコマンドのまま動く。未導入でも既存の試験は壊れない。
