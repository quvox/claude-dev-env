## 何が変わったか

**単体・結合・E2E のテストは、出荷物を作るビルドと同じ版の環境で走らせる**決まりが入った
(`.claude/directions/delegation.md` §2.4)。同じ版とは、言語の処理系とツールチェーン、
実行基盤(コンテナの基底イメージ・OS)、製品の依存のライブラリの版が、ビルドが使うものと
一致していることである。手元にたまたま入っている版で通ったテストは、出荷物が動くことの証拠に
ならないからである。

**この決まりが合否に掛かるのは、プロジェクトが版の固定を宣言してからである**(2026-11-05 の
人間の指示)。宣言とは、`docs/02-design/environments.md` の「コンテナ・実行環境」の下に
**`### ビルドとテストの版の固定` の見出しが在ること**である。`environments.md` を雛形から
新しく作るプロジェクトは、雛形がこの見出しを持つので、初めから宣言済みである。**既存のプロジェクトにはこの見出しが無く、
この移行で足すまでは:**

- テストの合否は従来どおりに決まる。
- `/build` と `/verify-tests` と `/test-env` は、見比べられた版の不一致と、見比べられなかった
  項目を「未宣言(移行前)」として報告に書く。課題票は作らない。

## 手順

**足す前に、テストを同じ版で走らせる仕組みが本当に在るかを人間が判断する** — 見出しを足した
時点から、版が一致しない / 確かめられないテストの実行は合格にならない。仕組みがまだ無いのに
足すと、`unit` / `integration` / `e2e` の試験区分は、仕組みができるまで緑にならない。

1. ビルドが版をどこで固定しているかを調べる。たとえば次のようなファイルである:
   - 処理系とツールチェーン: `.node-version` / `.python-version` / `go.mod` /
     `rust-toolchain.toml`、またはビルドに使う Dockerfile の基底イメージ
   - 実行基盤: ビルドに使う Dockerfile、またはそのイメージのタグ・ダイジェスト
   - 製品の依存: ロックファイル(`package-lock.json` / `uv.lock` / `Cargo.lock` など)

   固定がどこにも無い項目があれば、まず固定を作るかどうかを決める(作るのは `/build` の
   タスクである)。版をどれにするかは `delegation.md` §2.3 である。
2. テストがその固定どおりの環境で走るかを確かめる。直近の `/verify-tests` か `/test-env` の
   報告の「版の一致: 未宣言」の行に、見比べた結果が出ている。
3. 走らせられる(または、緑にならない期間を受け入れる)と決めたら、
   `docs/02-design/environments.md` の `## コンテナ・実行環境` の表の下に、
   `.claude/templates/02-environments.md` の `### ビルドとテストの版の固定` の節を写す。
   表を埋められるなら埋める。埋められなければ `<>` のまま置いてよく、`/build` が埋める
   (そのあいだ、該当する試験区分は緑にならない)。
4. コミットする(この移行の `paths` だけを名指す)。

**見出しを足さないままにしてもよい。** そのときは「未宣言」の報告が続くだけで、合否は
変わらない。ただし、そのプロジェクトのテストの合格は、出荷物と同じ版で確かめたものとは
限らない。

## 移らなかったときに何が起きるか

- テストの合否は変わらない。報告と作業ごとの記録に「版の一致: 未宣言」の行が出続ける。
- 版のずれたテストの合格が、そのまま合格として残る(移行前と同じ状態である)。

**`docs/02-design/environments.md` を持たないプロジェクトには、この移行は掛からない**
(`detect` が先にファイルの実在を見る)。
