# コールグラフツール — 要件定義と設計

対象: `build-callgraphs.py`(新規) / `callgraph-check.py`(新規) / 既存2本の改修。
規範は `.claude/directions/callgraphs.md`。**このファイルは実装者向けの設計であり、
運用ルールを重複させない**(矛盾したら directions が正)。

## 1. 要件

### 1.1 機能要件

| ID | 要件 | 受け入れ基準 |
|---|---|---|
| FR-1 | コード群から関数表と呼び出し関係を導出し、`docs/03-impl/callgraphs/` に言語ごとのファイルとして出力する | Python / Go / TypeScript の各サンプルで、定義された関数がすべて表に現れ、同一言語内の呼び出しが辺として現れる |
| FR-2 | REST エンドポイントを導出する。**`FastAPI` / `Flask` / `Gin` / `Echo` / `chi` / `Express` / `Next.js`** のルート定義と、**AWS API Gateway / ALB のパス転送設定**を読む | 各フレームワークのサンプルで、メソッド・パス・ハンドラシンボルが対応付く。ALB のパス条件と転送先が対応付く |
| FR-3 | **REST の呼び出し元は特定しない**。特定できなかったエンドポイントを一覧で出す | `orphan_endpoints` に、対応する呼び出し元候補が無いエンドポイントが漏れなく出る |
| FR-4 | 言語・プロセスを跨ぐ辺の**候補**を出す(HTTP リテラル突合 / IaC のパス→転送先→ハンドラ / キューのトピック名突合)。確度を必ず付ける | `boundaries.md` の各行に `確実/候補/未解決` が付く。変数で組み立てた URL は `未解決` になる |
| FR-5 | 解決できなかった呼び出しを**すべて**分類して列挙する | 動的ディスパッチ・高階関数・リフレクション・同名衝突・境界越えが `unresolved` に出る。**空欄で落とさない** |
| FR-6 | **決定性**: 実装が変わらなければ出力が1バイトも変わらない | 同一コミットで2回実行して `diff` が空。コメント行の追加では差分が出ない(行番号を持たないため) |
| FR-7 | 鮮度検査 `--check`: 再生成したら差分が出るかを返す | 古ければ終了コード1と差分ファイル一覧を返す。ファイルは書き換えない |
| FR-8 | **Tier の明示**: どの精度で走ったかを出力に書く。降格したら理由も書く | `index.md` と各ファイルのフロントマターに `tier` が出る。降格時は `degraded_reason` が出る |
| FR-9 | callgraph と relations の整合検査(FT/CG。実装している ID は `callgraph-check.py --list`、意味は directions §6) | 各検査に対して、意図的に壊したフィクスチャで検出できる |
| FR-10 | 新規開発(実装前)を壊さない | callgraph が無ければ「実装前のため未検査」で正常終了。実装途中の不一致は `building` のクロージャの中では正当な遷移として扱う(`flows.md` §3) |

### 1.2 非機能要件

| ID | 要件 | 目標 |
|---|---|---|
| NFR-1 | 対応 OS | **Linux と macOS**。Windows は対象外 |
| NFR-2 | 実行時間 | 5万行規模のリポジトリで Tier2 全言語 60秒以内。`--lang` で絞れる |
| NFR-3 | 依存 | Python 3.11+ と `pip` で入るもの。**ホストの言語ツールチェーンを要求しない**。任意ツールが不在でも動く |
| NFR-4 | 失敗耐性 | 1ファイルのパース失敗で全体を止めない。失敗ファイルを列挙して続行する |
| NFR-5 | 安全性 | **対象コードを import / 実行しない**(FastAPI アプリを import してルートを取る方式は採らない)。静的解析のみ |
| NFR-6 | 可搬性 | 出力に絶対パス・ホスト名・タイムスタンプを含めない |
| NFR-7 | 拡張性 | 言語の追加が抽出器1ファイルの追加で済む(中間表現が契約) |

### 1.3 やらないこと

- 実行時トレースによる動的コールグラフ生成(静的解析のみ)
- 呼び出し回数・パフォーマンス情報
- コードの品質評価(それは `/codex-audit` の仕事)
- **どちらが正かの判断**(事実の不一致を出すだけ)
- Windows 対応

## 2. アーキテクチャ

```
                ┌──────────────── 抽出器(差し替え可能) ────────────────┐
コード ───────► │ python : ast + import 解決(Tier2)                    │
                │ go     : tree-sitter(Tier2)                          │
                │ ts/vue : tree-sitter(Tier2)                          │
IaC   ───────► │ infra  : hcl2json / CFN・SAM YAML / OpenAPI          │
                └──────────────────────┬───────────────────────────────┘
                                       │ 中間表現(callgraph-schema.json)
                        ┌──────────────┼──────────────┐
                        ▼              ▼              ▼
                  boundaries      出力器(emit)    callgraph-check
                  結合器           辞書順固定       FT/CG 検査
                        │              │              │
                        └──────────────▼              ▼
                          docs/03-impl/callgraphs/   指摘レポート
```

**中間表現(`callgraph-schema.json`)が契約**である。抽出手段を差し替えても、出力器と検査器は変わらない。

### 2.1.1 ツールの供給(どこに何を入れるか)

**判断: キットは対象プロジェクトの環境にもホストにも何も入れない。**

| 段 | 供給元 | 実体 |
|---|---|---|
| Tier2 | **キット専用 venv `.claude/.venv`** | `setup-tools.py` が `requirements.txt` から作る。実際のバージョンは `requirements.lock` に固定 |
| 任意ツール | **ホストの既存ツールチェーン**(Go) | `setup-tools.py --host-tools` が `.claude/.tools/` の中にだけ入れる(`GOBIN`)。**グローバル・sudo は使わない**。現在は `hcl2json` のみ |
| Tier3 | なし | 標準ライブラリの正規表現 |

理由:

- **プロジェクトの環境を汚さない。** ツールの依存とプロジェクトの依存が混ざると、
  どちらの都合で壊れたのか分からなくなる。`requirements.txt` / `pyproject.toml` に手を入れない。
- **対象プロジェクトのビルドや型検査を前提にしない。** 前提にすると CI やコンテナで落ち、
  精度が環境で変わって検査の再現性が壊れる(判断の記録は §6.1)。
- **依存ゼロでも動く**ことを既定に置く(Python 抽出器は標準 `ast` のみ)。
  「まず動く」→「必要なら精度を上げる」の順にする。

実装上の要点:

- `cgx/base.ensure_kit_venv()` がエントリスクリプトの冒頭で**自己再実行**する
  (`os.execv`)。`sys.prefix` と環境変数 `CGX_NO_REEXEC` で無限ループを防ぐ。
- `.claude/.gitignore` が `.venv/` と `.tools/` を除外する。
- venv が作れない環境(`python3-venv` 未導入など)は**ホスト側の作業**として報告し、
  Tier2 が要る言語を Tier3 に落とす。**勝手に apt/brew を叩かない。**

### 2.2 Tier の決定

```
--tier auto(既定):
  1. Tier2(tree-sitter / ast)。Python は標準 ast なので依存ゼロで常に成立する
  2. tree-sitter パーサが無い言語 → Tier3(正規表現。既存 entrypoint-patterns.json を流用)
     degraded_reason に落ちた理由を記録
```

**降格は必ず記録して報告する。** 黙って Tier2 に落ちると「取りこぼしなし」の主張が嘘になる。

### 2.3 抽出器ごとの方針

| 言語 | Tier2 | ルート抽出 |
|---|---|---|
| Python | 標準 `ast` + import 解決。**依存ゼロ**で、AST が正確なので精度は高い | `@app.get` / `@router.post` / `@app.route` デコレータ。`APIRouter(prefix=)` を辿ってプレフィックスを合成 |
| Go | `tree-sitter-go` + パッケージ内/跨パッケージの名前解決 | `r.GET("/p", h)` / `e.POST` / `chi.Route`。グループ(`r.Group("/v1")`)のプレフィックス合成 |
| TypeScript | `tree-sitter-typescript` | `Express` の `app.get`、`Next.js` の `app/**/route.ts` の `export function GET`、`pages/api/**` の `default export` |
| shell | **Tier 3 のみ**(正規表現)。関数定義(ネスト含む)・`case "$1"` のディスパッチ・リテラル `source` の跨ファイル解決。ヒアドキュメント本文とコメントは `base.scan_shell_line` で除去する | `case "${1:-help}" in` の各分岐を `dispatch <値> @ <file>::main`(`protocol: cli` — `case "$1"` が引数を捌いている証拠が在る)。**ディスパッチの無いスクリプトは1本=1入口で、`protocol: main`**(2026-08-25。種別を主張しない値。下の Go の行と同じ理由) |
| make | **Tier 3 のみ**(正規表現)。ターゲット・依存辺・`$(MAKE) x` 辺。レシピ行は shell の規則でコメントを落とす | ターゲットごとに1入口(`protocol: cli`) |
| Go(バイナリ入口) | 上の Go と同じ抽出器 | `package main` の `func main` を `dispatch main @ <file>::main`(`protocol: main`)。**配布されるバイナリの入口**。`func main` から分かるのは「実行ファイルの入口である」ことだけなので、`cli` とは言わない(種別を主張しない protocol。CG6 の突き合わせには使わない) |
| infra | — | Terraform(`hcl2json` または `python-hcl2`)、CFN/SAM YAML、OpenAPI |

**プレフィックス合成は必須**。`APIRouter(prefix="/v1")` や `r.Group("/api")` を無視すると、
ALB のパス転送設定と突き合わせられない。

### 2.4 IaC 抽出の具体

| 対象 | 読むもの | 出す `routing` 行 |
|---|---|---|
| API Gateway v1 | `aws_api_gateway_resource` + `_method` + `_integration` | method/path → lambda ARN |
| API Gateway v2 | `aws_apigatewayv2_route`(`route_key: "POST /login"`)+ `_integration` | 同上 |
| ALB | `aws_lb_listener_rule` の `condition{path_pattern,host_header}` + `action{target_group_arn}`、`aws_lb_target_group_attachment` | host+path → ターゲットグループ → サービス |
| SAM | `AWS::Serverless::Function` の `Events.Api` | method/path → 関数の `Handler` |
| OpenAPI | `paths` | method/path →(`operationId` があれば)ハンドラ手掛かり |

Lambda の `handler` 設定(`app.lambda_handler` 等)から言語側シンボルへ結ぶのが `boundaries.py` の仕事。

### 2.5 boundaries 結合の規則

| 種別 | 突合キー | 確度 |
|---|---|---|
| iac | `routing[].match.path_key` × `endpoints[].path_key`、または `target.handler_hint` × `symbols.id` | 一意に決まれば `確実`、複数候補なら `候補` |
| http | HTTP クライアント呼び出しの URL リテラルを正規化 → `endpoints[].path_key` | 一致すれば `候補`(実際に到達するかはツールでは分からない) |
| queue | publish のトピック名リテラル × subscribe のトピック名リテラル | 一致すれば `候補` |
| いずれも | URL/トピックが変数で組み立てられている | `未解決`(呼び出し元は AI が判断) |

`orphan_endpoints` = `boundaries` に1行も現れなかったエンドポイント。

### 3.2 `index.md`

言語ごとの Tier・**抽出器バージョン**・件数・降格理由・設定(`internal_roots` 等)。
**バージョンがここにしか出ないので、ツールを上げても言語ファイルに差分が出ない。**

### 3.3 決定性の実装規則

- 出力直前に全配列を `sorted(key=str)` でコードポイント順に整列する(ロケール非依存)。
- 辞書の反復順に依存しない。`json.dumps(..., sort_keys=True)`。
- 表のセル内のリスト(呼び出す先など)も整列し、区切りは `, ` に固定。
- 改行は LF、末尾に改行1つ。
- **単体テストで「2回実行して同一」「入力順を入れ替えても同一」を検査する。**

## 4. `callgraph-check.py` の設計

### 4.1 入力

- `docs/03-impl/callgraphs/*.md` ではなく、`build-callgraphs.py --format json` の**中間表現**
  (Markdown を再パースしない。表の書式変更で壊れるため)。既定はその場で生成し、
  `--from <json>` でキャッシュも使える。
- `docs/03-impl/features.md`(機能表 = 入口の定義)。**無ければ relations の `impl:` を入口とみなす**
  (導入途中で検査が止まらないようにするため。その場合 FT2〜FT5 は検査しない)。
- `docs/03-impl/relations/MODULE-*.md` のフロントマター(`impl` / `callees` / `kind` / `module`)。
  **重ねる層は無い**(タスクの変更指示を合成する `--to-be` は、変更指示の全廃とともに撤去した)。

### 4.2 アルゴリズム

**機能間の関係は §8.3(`cgx/features.py`)をそのまま使う。ここで再実装しない。**
同じ縮約を2箇所に持つと必ずずれる。この検査がやるのは、その結果と宣言の差を出すことだけ。

```
1. CG1 を先に走らせて owner: dict[symbol_id → MODULE-ID] を作る(impl の実在検査を兼ねる)
2. 入口を決める: 機能表があればそれ / 無ければ owner を機能ごとにまとめたもの
3. ft.cluster() → ③ 機能間の辺(確度つき) / ④ 未到達 / closure
   FT1 が落ちたら**ここで打ち切る**(誤ったクラスタで指摘を出す方が有害)
4. FT2: ft.missing_entrypoints()          ← 旧 CG5。機能表が唯一の入口一覧
   FT3: 機能表の機能ID ⇄ relations が 1:1
   FT4: 機能表の 所属 ⇄ 02 のモジュール分割定義
   FT5: ft.missing_consolidated_entrypoints() ← ④ のうち、入口を網羅宣言したファイルの分。
        FT2 は endpoints しか見られないので、画面ハンドラの取りこぼしはここでしか出ない
   CG2: ④ をそのまま
   CG3: 宣言 callees のうち ③ にも無いもの(確度 `候補` の辺で繋がっていれば指摘しない)
   CG4: ③ のうち callees に無いもの ← 取りこぼし。確定=高 / 候補=中
   CG6: kind: rest-api / event / tool の機能に対応するエントリポイントが無いもの
5. Tier に応じて重大度を調整: Tier3 では CG4 を「参考」に落とす(関係性が不完全なので
   取りこぼしの主張ができない)。**この調整を必ずレポートに書く。**
```

### 4.3 出力

`ReportFindings` 形式ではなく、他スクリプトと同じ日本語の表 + `--format json`。
各行に **どちらが正かは書かない**。`確度` と `根拠` を書く。

## 5. リスクと対処

| リスク | 影響 | 対処 |
|---|---|---|
| tree-sitter の Python バインディングは API 変更が多い | ツールが壊れる | バージョンを固定し、`base.py` に薄い適合層を置いて破壊的変更を1箇所に閉じる |
| 同名関数が多いリポジトリで Tier2 の解決が曖昧になる | `ambiguous` が大量に出る | 候補を全部出し、機能表クラスタリングの候補辺として算入する。まず `excludes`/`vendor_markers` の漏れを疑う |
| 動的ディスパッチが多いコードベース | 未解決が大量 | 未解決は「取りこぼしではなく、機械の限界の明示」。AI がそこを読む |
| 巨大リポジトリで出力が読めない大きさになる | 実用性が落ちる | 言語ファイルはモジュール別セクションに分ける。`--lang` / `--scope` で絞れる |
| フレームワークの書き方が想定と違う | ルートが取れない | 検出根拠を必ず出力し、**0件だったら「エントリポイントが無い」ではなく「パターン未対応の可能性」と報告する** |
| Markdown 表の書式変更で下流が壊れる | 検査が動かない | **下流は必ず中間 JSON を読む**。Markdown は人間用と割り切る |

Go 特有の知見(実データでしか出なかったもの):

1. **引数レシーバを高階呼び出しと誤判定していた。** `w.WriteHeader()` の `w` は関数引数なので
   「引数を呼んでいる」と誤って分類し、684件が化けた。**引数の型を型表に入れる**のが正解で、
   関数型の引数だけを高階の候補にする。
2. **ルート検出には「受け手がルータか」の判定が要る。** `Get`/`Delete`/`Handle` は
   リポジトリのメソッド名として普通に使われるので、`repo.Delete(ctx,id)` が経路として
   誤検出されていた(パスが空のエンドポイントが大量発生)。型名に `Router`/`Mux`/`Engine`/`Echo`
   を含むか、`Route`/`Group` のクロージャ引数であることを条件にした。
3. **`github.com/go-chi/chi/v5` のパッケージ名は `v5` ではない。** Go のバージョン接尾辞の慣習を
   知らないと import 解決が全部外れる。
4. **ハンドラはミドルウェアで包まれている。** `h.guard(roles, h.delete)` の形が普通で、
   呼び出しの引数を辿らないとハンドラの3割(43/131)が未特定のままだった。
   辿った経路は `source` に `(経由: h.guard)` として残し、監査できるようにした。
5. **tree-sitter の `struct_type` は `body` フィールドを持たない**(`field_declaration_list` の中)。
   ここを取り違えると構造体フィールドの型が全部引けず、`h.store.X` が軒並み ambiguous になる。
6. go.mod の相対パスは `.` になるので、隠しディレクトリ判定で捨ててはいけない。
   go.mod が読めない場合の保険として、import パスの**末尾一致**でも内部パッケージを引く。

Go は Python より名前解決が有利だった(未修飾呼び出しはパッケージスコープで確定、
`pkg.Func` は import で一意、レシーバ型が構文から分かる)。残る15件は
インターフェース越しの呼び出しなど、型推論なしには解けない正直な未解決である。

P5/P6 の知見(実データでしか出なかったもの):

1. **サーバレスでは REST のパスがコードに無い。** SAM の `Path` と `Handler`/`CodeUri` を読んで
   初めて「このパスはどのハンドラに届くか」が分かる。`CodeUri` + `Handler` から
   `<dir>/<module>.py::<func>` を組み立てると、**言語側のシンボルIDと完全に一致する**。
2. **CFN の短縮形(`!Ref` 等)を素通しする YAML ローダが要る。** 無いとテンプレートを1つも読めない。
3. **素の OpenAPI は「契約」であってインフラではない。** `x-amazon-apigateway-integration` を
   持つものだけを infra として扱う(持たないものは `check-contracts.py` の担当)。
4. **HTTP クライアントの受け手名は部分一致で見る。** `apiClient` のような命名が普通で、
   完全一致の白名簿(`api`/`client`/`http`)では境界の辺が**1本も取れなかった**。
5. **`export const api = { login: () => ... }` のオブジェクトリテラルが TS の主要な形。**
   ここを拾わないと API モジュールが丸ごと解析から落ちる。加えて、どのユニットにも属さない
   呼び出しを `<module>` に帰属させる保険を入れた(取りこぼすと境界の辺が消えるため)。
6. **アロー関数の本体が式1つのとき**(`const f = () => api.get("/x")`)、子ノードだけを見ると
   呼び出しを取りこぼす。走査に自ノードを含める必要がある。

**契約(OpenAPI)の検査 `check-contracts.py`**: 契約を OpenAPI で書く価値は「機械的に検査できる」点に
あり、検査しなければ表を YAML に書き換えただけになる。CT1〜CT6 を実装した。とくに
**CT4(コードにエンドポイントがあるが契約に無い / 契約にあるがコードに無い)**が、
コールグラフと契約を突き合わせる新しい検出面である。

### 6.1 P7(Tier1)を削除した判断 — 実装し、実測した上で捨てた

**Tier1(言語ツールチェーンによる型解決)は一度実装して実測し、その上で削除した。**
再び足したくなったときのために、判断の材料をここに残す。**同じ実装を繰り返さないこと。**

実測(`pos-system` / Go 297ファイル・5万行):

| | Tier2(tree-sitter) | Tier1(gocg / x/tools) |
|---|---|---|
| シンボル | 1493 | 1492 |
| 辺 | 2730 | **2839** |
| 未解決 | 15 | 391 |
| 実行時間 | 1.2s | **3.8s** |

辺を突き合わせた結果:

| | 件数 | 中身 |
|---|---|---|
| 共通 | 2700 | — |
| Tier1 だけ | 139 | 型解決で初めて分かった辺 |
| Tier2 だけ | 30 | 同名照合による**偽の辺**。`c.sdk.AdminRespondToAuthChallenge`(AWS SDK)を同名の内部メソッドと誤認、`r.From.IsZero()`(`time.Time`)を内部の `DateRange.IsZero` と誤認 |

**削除の理由**(いずれも「何のためにコールグラフを作るのか」に照らした判断):

1. **偽の辺を消すことに価値が無い。** この仕組みの基準は**偽陰性より偽陽性の方がマシ**
   (`.claude/directions/features.md` §5)。Tier1 の主な貢献は偽の辺 30本 の除去だが、
   これは 2839 辺の 1% であり、しかも**消す方向**の改善である。
2. **増えた 139 本のうち、モジュール境界を跨ぐものはごく一部。** 目的は境界の連携の把握であって
   関数レベルの完全性ではない。境界の辺は `boundaries`(IaC・HTTP リテラル)と機能表
   クラスタリングが担当しており、そちらの方が効く。
3. **対象プロジェクトのビルド・型検査が前提になる。** CI やコンテナで落ちる。
   **精度が環境で変わる仕組みは検査の再現性を壊す**ので、そもそも前提にできない
   = 「あっても使えないことがある」ものに複雑さを払っていた。
4. **実行時間が3倍。** 1% の精度のために。
5. **保守面が2重になる。** Tier1 と Tier2 で「解析の対象範囲」がずれる問題(ビルド設定 vs 設定の
   `excludes`)への対処、読まれなかったファイルの補完、降格経路 — これらは全部
   Tier1 があるから必要になっていた複雑さである。

**Tier1 の知見のうち、削除後も生きるもの**:

- **同名照合は最後の手段でなければならない**(§5.6 に規範化済み)。Tier2 の偽の辺 30本 は全部
  「受け手の型が分からないまま同名照合に落ちた」もの。**受け手の出所判定を強くする方が、
  Tier1 を足すより費用対効果が高い。**
- **インターフェース越しの呼び出しは「実装を探す」と解ける。** 実装が1つしか無ければ行き先は
  それしかない。これは**型解決なしでも近似できる**(構文からインターフェース名と実装の対応を取る)。
  必要になったらこの方向で Tier2 を強化する。
- **未解決の件数で優劣を比べてはいけない。** Tier2 は「当たってしまえば未解決に出ない」ので
  少なく見える。Tier1 の 391 件は正直な報告だった。**件数ではなく辺の正しさで比べること。**
- **ルート抽出は型解決の問題ではない。** chi/gin/echo のルート定義は構文パターンなので、
  仮に型解決を足しても Tier2 の結果を使うべきだった。

**再検討してよい条件**: 同名衝突が多くて `ambiguous` が実用にならないリポジトリに当たり、かつ
`excludes` / `vendor_markers` の設定漏れでないことを確認できたとき。その場合でも、
まず §5.6 の受け手の出所判定の強化と、上記のインターフェース近似を試すこと。

**P8 の判断保留**: `relations-coverage.py` は当初「廃止」と設計したが、**抽出器が無い言語
(Go/TypeScript/infra)の網羅性が検査できなくなる**ため、P4〜P6 が終わるまで残す。
`scan-entrypoints.py` も Tier3 のフォールバックとして残す。

**P3 を P4 より前に置く理由**: P2 まで終われば体系としては閉じるので、
先に配線して「言語が増えるだけ」の状態にしておく。P4 以降は文書の変更を伴わない。

### 6.2 P9 の実測(`ct_uemura` / Python 389ファイル・2492シンボル)

| 指標 | 値 |
|---|---|
| 機能候補(エントリポイント) | **77**(Lambda ハンドラ 16 + cmd 分岐 61) |
| 機能間の辺 | 61(確定 61 / 候補 0) |

**`tools/` の 908 件は誤検出ではない。** 機能表に載せた入口が Lambda と cmd 分岐だけなので、

P9 の知見(すべて実データでしか出なかった):

1. **入口の書式で種別を判別してはならない。** cmd 分岐のエンドポイントIDは
   `dispatch ADDGROUP @ app.py::lambda_handler` の形で `::` を含むので、
   「`::` があればシンボル」という判別は実データで即座に壊れた。
   **エンドポイントIDとして先に照合し、無ければシンボルとして照合する**(実在に当てる)。
2. **入口IDは `|` を含みうる。** `if cmd in ["ALL","GROUP"]` の合成シンボルは
   `dispatch ALL|GROUP @ ...` になる。機能表は Markdown 表なので、
   **書くときは `\|` に逃がし、読むときは逃がしを解いて `|` に戻す**必要がある。
3. **共通基盤候補は実リポジトリでは 300 件規模になる。** 一度に見るには多すぎるので、
   **ファンイン別の件数分布**を出して上流から片付けられるようにした。
   **閾値は提案の絞り込みにしか効かない**(クラスタリング結果は閾値に依存しない)ことを
   出力に明記する — さもないと「閾値を上げれば境界が減る」と誤読される。
4. **`<module>` 擬似シンボルを ④ に数えてはならない。** import 時に走るコードであり、
   機能から到達しないのが正常。数えると全モジュール分が系統的なノイズになる。
   ただし**黙って落とさず件数を明記する**。
5. **ルートを所有集合に入れ忘れると全ルートが ④ に落ちる。** 設計段階で見つけた
   (§8.3.1 の決定性を壊す実装ミス4種のうちの1つ)。単体で必ず検査すること。

**副産物: Python 抽出器の黙った偽陰性を1つ潰した。** `module_to_rel` が同名モジュールを
複数見つけると解決を諦めていたため、**Lambda を1関数1ディレクトリに置いて同名ドライバを
各所にコピーしている構成で、跨ファイルの辺が丸ごと落ちていた**(未解決にも出ない)。
フラットな `import drv_x` は Python では実行スクリプトのディレクトリが最優先なので、
**同一ディレクトリの候補を優先する**ようにした。実測: 辺 2128 → **2238(+110、消えた辺 0)**、
未解決 143 → 160(モジュールは解決したがシンボルが無い正直な報告)。

## 8. 機能表クラスタリング(P9) — 境界を先に決めて、境界の関係を機械で出す

規範は `.claude/directions/features.md`。**このファイルは実装者向けの設計であり、運用ルールを
重複させない**(矛盾したら directions が正)。

### 8.1 なぜこれを足すのか

`callgraph-check.py` の縮約(§4.2)は `relations` の `impl:` を所有関係として使う。つまり
**relations が書けていないと縮約が動かない**。しかし relations を書くのに必要な材料
(誰が誰を呼ぶか)こそが縮約の結果である。**鶏と卵**になっていた。

機能表はこの循環を切る。人間が決めるのは「入口の一覧」だけで、それ以降は機械が出す。
AI の仕事が「コードを読んで連携を見つける」から「機械が出した辺を確認・棄却して記述する」に
変わり、`callees:` の誤り(AI の主要な誤り)が構造的に消える。

### 8.2 要件

| ID | 要件 | 受け入れ基準 |
|---|---|---|
| FT-1 | 機能表と callgraph から、各機能に属する関数集合を出す | 全機能について、入口から確定辺で到達する関数が列挙される |
| FT-2 | **複数機能から到達される共有関数**をファンイン付きで出す | ファンイン降順で列挙され、各行に到達元の機能の並びが付く |
| FT-3 | 機能間の辺を、**代表呼び出し箇所**(from シンボル → to シンボル)付きで出す | 各辺に確度(`確定`/`候補`)と、根拠となる実際の呼び出しが付く |
| FT-4 | どの入口からも到達しない関数を出す | 判定は候補辺も入れた最も広い到達可能性で行う(directions §5) |
| FT-5 | 候補辺を確定辺と混ぜない | 出力の辺配列に確度列があり、候補辺だけで生じた辺が識別できる |
| FT-6 | 機能候補・共通基盤候補を提案する | 入口一覧とファンイン上位が、機能表に貼れる形式で出る |
| FT-7 | 決定性 | 同一の callgraph + 機能表で2回実行して JSON が同一 |
| FT-8 | ②③④ を `docs/03-impl/feature-graph.md` に出す。① は JSON のみ | 生成物の警告つきで出力。`--check` が鮮度を返す。`docs/` の他の場所は変更しない(directions §6) |

### 8.2.1 やらないこと

- 機能表を自動生成して確定させる(候補提示まで。境界は設計判断)
- ①(各機能の関数集合)を `docs/` に出力する(JSON のみ。callgraph と同じ桁の量で `impl:` と重複)
- どちらが正かの判断

### 8.3 `cluster-features.py` のアルゴリズム

```
入力: build-callgraphs.py --format json の中間表現 + docs/03-impl/features.md

0. 前処理
   roots(F) = 機能 F の入口を全部シンボルIDに解決する
              エンドポイントID → endpoints[].handler
              シンボルID       → そのまま
              解決できない     → FT1 違反。ここで停止する(誤ったクラスタを出すより止める)
   ★ roots(F) ∩ roots(G) ≠ ∅ (F≠G) → **即エラーで停止**。所有が一意でないと①〜④が定義できない
   ROOTS     = ∪ roots(F)
   E1(確定辺) = languages[].edges  ∪  boundaries[confidence=確実]
   E2(候補辺) = unresolved[reason=ambiguous].candidates を展開した辺
              ∪ boundaries[confidence=候補]
   ★ from が空の boundary 辺(iac の外部→ハンドラ)は**到達可能性に使わない**。
     それは入口であることの証拠であって機能間の辺ではない(FT2 の根拠としてだけ使う)

1. 到達 — **集合として定義する。DFS はこれを求める実装手段にすぎない**
   s ∈ reach(F, E) ⟺ ∃ r ∈ roots(F): r から s への E 上の経路が存在し、
                      その経路の**中間ノードが1つも ROOTS に属さない**
   ・s 自身が ROOTS に属するなら reach には入れない(2 の辺になる)
   ・自機能の別ルート(統合した機能)は中間ノードとして通ってよい
   → 訪問順に依存しない。E1 と E1∪E2 の2通りを計算する

2. 機能間の辺 — **これも集合として定義する**
   F → G の辺 ⟺ ∃(u,v) ∈ E : u ∈ roots(F) ∪ reach(F,E), v ∈ roots(G), F ≠ G
   ★ 呼び出し箇所 = **この条件を満たす (u,v) を全部**。「代表1本」を選んではならない
     (選ぶと DFS の訪問順に依存して決定性が壊れる)。出力は (u,v) の辞書順。
     表示だけ先頭 N 本 + 件数に畳む(N は設定、既定3)。**畳んだ件数は必ず出す**

3. 所有
   s ∈ roots(G)  → own(s) = {G}      ★ ルートは定義により自機能に属する
                                        (これが無いと全ルートが ④ に誤分類される)
   それ以外       → own(s) = { F | s ∈ reach(F, E1∪E2) }   ← 「共有」は広い方で判定する
   |own(s)| == 1  → 専有関数(その機能に畳み込む)
   |own(s)| >= 2  → **共有関数**。ファンイン = |own(s)|。これが境界の実体
   |own(s)| == 0  → どの入口からも到達しない(④)

4. 確度(辺ではなく**呼び出し箇所ごと**に決める。ここも集合演算で一意)
   (u,v) が (u,v) ∈ E1 かつ u ∈ roots(F) ∪ reach(F,E1) → その呼び出し箇所は `確定`
   それ以外                                            → `候補`
   辺 F→G の確度 = `確定` の呼び出し箇所が1本でもあれば `確定`、無ければ `候補`

5. 出力(全配列を辞書順に整列。辺は from → to → 呼び出し箇所 の順)
```

**なぜ打ち切るのか**: 打ち切らないと、機能 A が機能 B を経由して届く全部を A の連携として
主張してしまう。境界で切るからこそ `callees` に対応する。

**なぜ「共有」は広い辺集合で判定するのか**: 境界の見落としが最悪の結果だから(directions §5)。
共有関数が1つ見逃されると、それを呼ぶ全機能の記述に同じ処理が二重に現れ、しかもそれは
どの検査にも引っかからない。

### 8.3.1 一意性(これが成り立たないと検査が再現しない)

**クラスタリング結果は (callgraph 中間表現, 機能表) の純関数である。** 根拠:

| 量 | なぜ一意か |
|---|---|
| `roots(F)` | 機能表の入口 + `endpoints[].handler` の写像。前処理で重複を弾いてある |
| `E1` / `E2` | 中間表現の配列そのもの(callgraph 自体が決定的 — directions/callgraphs.md §4) |
| `reach(F,E)` | **経路の存在**で定義されており、探索順に言及していない |
| 機能間の辺 | 条件を満たす `(u,v)` の**全体集合**。「代表1本」を選ばないので選び方に依存しない |
| `own(s)` | `reach` から決まる。ルートは定義で固定 |
| 確度 | `(u,v) ∈ E1` と `u ∈ reach(F,E1)` の判定のみ。両方が一意 |

**決定性を壊す実装ミスは次の4つに限られる**(単体テストで潰す):

1. 呼び出し箇所を「DFS が最初に見つけた1本」にする → 順序依存
2. 入口の重複を弾かずに `own` を先着で決める → 入力順依存
3. `from` が空の boundary 辺を辿る → 空文字を節点として扱い、実装ごとに挙動が変わる
4. ルートを `reach` に入れ忘れたまま `own` を作る → 全ルートが ④(未到達)に落ちる

**検査**: 同一入力で2回実行して JSON が同一(FT-7)、かつ**機能表の行順・シンボルの入力順を
入れ替えても同一**であること。後者を入れないと 1・2 が素通りする。

なお一意なのは**クラスタリング結果**であって、`propose-features.py` の**提案**は別である
(閾値という調整可能なパラメータを持つ)。提案は機能表に写された時点で人間の判断に変わり、
そこから先は一意になる。

### 8.4 `propose-features.py` のアルゴリズム

機能表がまだ無い状態で走る。**入口だけで暫定クラスタリングして、次に足すべき行を出す。**

```
1. 機能候補 = endpoints[] 全件 + entrypoint 種別のシンボル(Lambda ハンドラ・cmd 分岐)
              → 機能表の行の形式(機能ID案・種別・入口・所属案・概要は空)で出力
   機能ID案  = MODULE-<ファイルまたはパスから導いた module-slug>-<feature>
              **これは案であって確定ではない**。人間が直す前提で出す
2. 暫定クラスタリング = 上記の入口だけを ROOTS として cluster-features のアルゴリズムを回す
3. 共通基盤候補 = ファンイン >= 閾値(既定 2)の関数を、ファンイン降順・同数は辞書順で列挙
              各行に 到達元の機能の並び を付ける
4. 統合候補 = 関数集合の重なり(Jaccard)が閾値(既定 0.8)以上の機能対
```

再実行、を繰り返すと**収束する**(ルートへの昇格は経路を切るだけで新しい到達を生まない)。

閾値は提案のためのものであり、規範ではない(`callgraph-config.json` の `features` 節)。

## 9. 共有データストア結合(P10) — 呼び出し辺として存在しない連携

規範は `.claude/directions/callgraphs.md` §5.11。**このファイルは実装者向けの設計であり、
運用ルールを重複させない**(矛盾したら directions が正)。

### 9.1 なぜこれを足すのか

サーバレス/イベント駆動では、連携の相当部分が**呼び出し辺として原理的に存在しない**。
A がテーブルに書き、B が読む。呼び出しは1本も無いが、B は A の書式に依存している。
この結合は callgraph にも boundaries にも出ないので、**CG4(取りこぼし検出)の網に
一切かからない** — この仕組みの目玉が丸ごと素通りする領域だった。

同時に、`Events` を Api/HttpApi に限定していたため、SQS/SNS/ストリーム/定時起動で動く機能は
**永久に「呼び出し元不明のエンドポイント」**のままだった。入口が分からなければ機能表にも
載らず、そこから先は全部「未到達」になる。P10 はこの2つを同じ材料(IaC + 資源名)で埋める。

### 9.2 要件

| ID | 要件 | 受け入れ基準 |
|---|---|---|
| RS-1 | 資源(テーブル・バケット・キュー・トピック・ストリーム・環境変数)の参照を、シンボル単位で出す | 各参照に アクセス種別 / 確度 / 根拠 が付く |
| RS-2 | **資源の識別子は「触り方の名前」でよい**。リテラル / 環境変数名 / 定数名のいずれでも、解決できたら実名に寄せる | 解決できない名前(`$VAR` / `#Logical`)でも結合のキーとして機能する |
| RS-3 | API 以外のイベントソース(Schedule/SQS/SNS/DynamoDB/Kinesis/S3/EventBridge/Cognito、`AWS::Events::Rule`、`EventSourceMapping`)をエントリポイントとして出す | ハンドラが実在すればエンドポイントになり、孤立エンドポイントから消える |
| RS-4 | `Environment.Variables` で `env:$VAR` を実資源に解決する | 解決したものは根拠に「どのテンプレートのどの関数か」が出る |
| RS-5 | IAM を**上界**として読む | `Resource: '*'` は識別子にならないので使わず、**件数を報告する** |
| RS-6 | queue の突合(publish ⇄ subscribe)を `boundaries` に出す(directions と schema にあって実装が無かった穴) | publish のリテラルと、そのキューで起動されるハンドラが `候補` で繋がる |
| RS-7 | 資源 → 触るシンボル を `docs/03-impl/callgraphs/resources.md` に出す | 資源とみなさなかった環境変数も件数付きで出る |
| RS-8 | 機能表があれば **資源 × 機能** に畳み、**呼び出し辺の無い機能対**を出す | `feature-graph.md` に資源ごとに1行。対の総数を必ず出す |
| RS-9 | 決定性 | 同一入力で2回実行して同一。資源名の端に `{}` が残らない |

### 9.2.1 やらないこと

- **SQL 文からのテーブル名抽出**(`FROM users`)。パーサが要るうえ、RDB は接続文字列側の
  結合(`env:$DATABASE_URL`)で十分に拾えることが多い。必要になったら足す。
- **TypeScript の資源参照**。フロントエンドはデータストアに直接触らず REST 境界を通るので、
  そこは `http` の boundaries が既に担当している。**入れると `process.env.VITE_*` が
  「全画面が触る資源」になって信号を潰す**。これは意図的な不採用であり、黙った欠落ではない。
- 実際に同じ物理資源かの判定(環境で変わる)。**どちらが正かの判断**。

### 9.3 資源の識別(この節が核心)

**資源キー = `<種別>:<正規化名>`。** 名前は次の順で決まる:

| 順 | 形 | 例 | 名前 |
|---|---|---|---|
| 1 | 文字列リテラル(連結・f-string を含む) | `"caseDataTbl" + os.environ["HASHSALT"]` | `caseDataTbl` |
| 2 | 定数参照 | Go の `dynamodb.TableUsers` | 定数表で `users` に解決。できなければ `#TableUsers` |
| 3 | 環境変数参照 | `os.environ["AUDIT_TABLE"]` | infra で `audit_log` に解決。できなければ `$AUDIT_TABLE` |
| 4 | インフラの論理ID | `!Ref UsersTable` | 宣言から実名。できなければ `#UsersTable` |

**解決できなくても捨てない。** 同じ環境変数名を読む2つのモジュールは、実体が何であれ結合して
いる。これが「偽陰性より偽陽性の方がマシ」(directions/features.md §5)に対する正しい振る舞い
であり、かつ最も安上がりでもある。

**非リテラル区間は `{}` に潰し、先頭と末尾の `{}` は落とす**(`base.path_key` と同じ考え方)。
端を落とすのは実データで必須だった: 実装が支配的に「リテラル名 + 環境ごとの接頭辞/接尾辞」の形を
取るので、片方が `orders`、もう片方が `orders{}` になると**同じテーブルが別資源に割れて結合が
丸ごと消える**。内側の `{}` は落とさない(`a{}b` と `ab` は別物)。

### 9.4 アクセス種別

`read` / `write` / `readwrite` / `unknown` / `permission`。**操作名の接頭辞**で決める
(`get`/`query`/`scan`/`list` → read、`put`/`update`/`delete`/`send`/`publish` → write)。
SDK もリポジトリ内のラッパも動詞は共通なので、**言語をまたいで同じ語彙で判定できる**。

2つの決めごと:

1. **環境変数を読んだこと自体は `unknown`。** その資源をどう使うかを何も言わないので、
   黙って `read` にしてはならない。使い方は操作の側で決まる。
2. **`permission`(IAM 由来)は結合に数えない。** 使っている証拠ではなく**使える上界**であり、
   混ぜると「権限があるだけ」の対が指摘に化ける。資源表には残す。

### 9.5 受け手の変数束縛(実データで必須だった)

`table = dynamodb.Table("caseDataTbl" + os.environ["HASHSALT"])` が**モジュール直下**にあり、
関数側は `table.query(...)` としか書かない — これが実データで支配的な形だった。よって:

- `X = <資源生成呼び出し>` を「変数 → 資源」の束縛として集める(ファイル単位 + ユニット単位)。
- **束縛そのものは資源参照として出さない。** 出すのは実際の操作の側である。
  生成を参照として数えると、ドライバモジュールの数だけ `<module>` 由来の参照が並び、
  どの機能にも属さない雑音になる。
- 生成の引数が環境変数なら、束縛の種別を `env` にして名前を `$VAR` にする。
  こうしないと `Table(os.environ["AUDIT_TABLE"])` は名前が取れず**丸ごと消える**。

Go は形が違う(資源名が定数表に集約され、呼び出し側には `dynamodb.TableUsers` しか現れない)ので、
**const 宣言を横断で集めた定数表**で解決する。ここを読まないと Go では1本も取れない。

### 9.6 結合の導出と、出力の粒度

資源 R について `touchers(R)` = R を触る機能集合(判定は最も広い到達可能性 = `closure`。
directions/features.md §5「『共有』の主張は広く」)。

```
呼び出し辺の無い対 = {(F,G) | F,G ∈ touchers(R), F≠G, 機能グラフに F→G も G→F も無い}
```

★ **出力は資源ごとに1行。機能対を並べてはならない。** 資源1つで O(n²) 行になり、実測では
どの資源も「辞書順で先頭の対」が並ぶだけの壁になった。読み手が要るのは
**誰が書式を決めていて、誰がそれに依存しているか**なので、列は
「書き込む機能」「読むだけの機能」にする。対の総数は必ず出し、全対は `--format json` に残す。

**広域共有資源**(機能の `ubiquitous_ratio` 以上 **かつ** `ubiquitous_min` 件以上が触るもの)は
指摘から外す — 全機能が触る資源に対の一覧を出しても読めない。**割合だけで判定してはならない**:
機能が3件のリポジトリでは「2機能 = 67%」が広域扱いになり、指摘が全部消える。

重大度は **書き込みが絡めば `中`**(片方の書式に他方が依存する)、読み取りだけなら `参考`。

### 9.7 検査 CG7

**資源結合を `callees` に書かない**規範は `.claude/directions/callgraphs.md` §5.11 が正
(ここでは再掲しない)。**実装上そこから従うこと**: 呼び出し辺として存在しないので、
機械が検査できるのは**「その資源の名前が機能間連携仕様書の本文に出ているか」**だけである。

| ID | 検査 | 不一致が意味すること |
|---|---|---|
| CG7 | 同じ資源を触る機能対に呼び出し辺が無いとき、各機能の relations 本文に資源名が出ているか | **記述漏れ**。書式を決めている機能の 副作用 に資源名が1度も出てこない |

- 名前が3文字未満のときは照合しない(本文照合の当たりが信用できない)。
- 重大度は書き込み側が漏れていれば `中`、読み取り側だけなら `参考`。
- 広域共有資源は対象外(§9.6)。

### 9.9 実データでしか出なかった知見

1. **`CodeUri: ../svc/x` は畳まないと当たらない。** SAM の普通の書き方だが、
   `infra/../svc/x/app.py::h` のままではシンボルIDに一致しない。`posixpath.normpath` が要る。
   これは P10 で足したイベント源だけでなく、既存のパス転送でも黙って外していた。
2. **環境変数の `!Ref` は資源とは限らない。** `DEPLOY_ENV: !Ref DeployEnv`(Parameter)が
   実データで普通に出る。**宣言された資源を指していると確認できたときだけ束縛を作る**。
   さもないと「全モジュールが触る資源」に化け、`env_patterns` の絞り込みも素通りする。
3. **同じハンドラを指す入口が複数になる。** Lambda ハンドラは「関数として入口」でもあり
   「定時起動の宛先」でもあるので、インフラを読んだ途端に同じハンドラが2つのエンドポイントで
   出てくる。`propose-features.py` は**ハンドラで畳む**必要がある(畳まないと入口が重複して
   FT1 が即座に止まる)。FT2 はハンドラで判定するので代表を1つ載せれば取りこぼさない。
4. **根拠に引数を書くと同じ操作が何行にも増える。** `table.query(KeyConditionExpression=…)` の
   引数違いで1関数から4行出た。**資源と操作が分かればよい**ので引数は畳む。
5. **IAM は実データでは `Resource: '*'` が普通。** 上界として使えないので、
   黙って落とさず件数だけ報告する形にした。IAM が効くのは資源を絞っているリポジトリだけである。
