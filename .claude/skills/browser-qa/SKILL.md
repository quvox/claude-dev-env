# 探索的ブラウザQA — 台本を離れるレーン

対象: $ARGUMENTS。人間に向けた出力(報告)はすべて日本語で書く。

**これは E2E ではない。** `/verify-tests` の e2e 試験区分は `environments.md` の E2E コマンドを走らせる — 02 の
`E2E-nn` に**書いてあるものが通ることの確認**である。このレーンは逆で、**書いていないところを触る**。
台本の外にしか無い不具合(壊れた戻り導線、二度押し、空・極端値、権限の抜け、読めない
エラー表示、リロード後の状態)は、シナリオ一覧を増やしても見つからない — 一覧に載った時点で
それは台本になり、e2e 試験区分の担当になるからである。

**書かない。裁定しない。** 製品コードも仕様ドキュメントも1バイトも変えない(直すのは依頼元の仕事)。
所見に重大度を付けるのはこのレーンの仕事だが、**採否を決めるのは依頼元**である。

## 0. 走らせる主体と、走らない場合 ★

**独立した文脈で走る。** 実装を書いた文脈がそのまま触っても、自分が想定した経路をなぞるだけになる
(独立レビューと同じ理屈 — CLAUDE.md §6)。

| 状況 | 誰が走らせるか |
|---|---|
| 艦隊(CLAUDE.md §9) | **`@qa`**。中央エージェントが起こしたウィンドウで(**qa が走る作業指示なら作業指示より先に起こされ、id が作業指示に書かれている**。その語の定義は `orchestration.md` §1.4 — 名指したものと引数なしの両方である。当てはまらないときは `/verify-tests` の要求を受けて起こす — `orchestration.md` §1.2・§1.4)、`.claude/roles/qa.md` が縛る(`orchestration.md` §1.4)。依頼元は対象・起動手順・触ってよい範囲・出力様式だけを渡す。**ウィンドウの kind は codex が既定**(両方がブラウザを操作できるなら codex。§1.2.1・§1.4)。**codex が使えないときは claude + `claude-in-chrome`**(`opus` / `high`。§1.4 の2つの縛りを起こす前に満たす) |
| 艦隊でない | **codex + `chrome-devtools` MCP**(`orchestration.md` §1.1.2)。対話モードで起こし、この SKILL.md をパスで名指して読ませる。**codex が使えないなら claude + `claude-in-chrome`**(同じく §1.4 の2つの縛りを満たしてから) |

**このレーンを走らせる codex のウィンドウは、艦隊でも単独でも砂箱なしで起こす** ★ —
起動行と理由は **`orchestration.md` §1.1.1「`@qa` だけは砂箱なしで起こす」が正である**
(要旨: 砂箱はシェル呼び出しごとに PID 名前空間を作り、§2 で立てたアプリを呼び出しの終わりに殺す)。
**単独運用ではその1行を人間が打つ**(`orchestration.md` §10)。
**このレーンが自分で起動行を選び直すことはできない** — 走り出したウィンドウのモードは
変えられない。砂箱付きで起こされてしまったなら、下の §2 でアプリが立たないことに当たり、
それはこの §0 が言う「環境の不備」である。

どちらでも、依頼元が渡すのは対象・起動手順・触ってよい範囲・出力様式だけで、
**自分の所見も期待する判定も渡さない**。

**どちらの口で走ったかを、報告の冒頭で必ず名乗る**(`chrome-devtools` MCP か `claude-in-chrome` か)。
**落ちるのは kind だけで、独立性は落ちない** — 実装を書いた文脈が走らせてはならないことは、
claude で走るときも同じである。

**「実行基盤が無い」は 適用外の理由にならない。** ブラウザを動かす口が無い(MCP 未設定、Chrome
不在、アプリを起動できない)なら、それは環境の不備である — **人間へ渡して止まる**。黙って飛ばすと
「やった」と区別が付かなくなる。**適用外にできるのはただ1つ**:

- **02-design に UI が無い**(画面を持たないプロジェクト・タスク)。このときだけ
  「探索的ブラウザQA: 適用外(UI 無し — `02-design/<根拠のファイル>`)」と根拠を名指して記録し、終わる。

## 1. 触る対象を決める(読むのは4つだけ)

**変更されたところと、その導線だけを触る。** 全画面を舐めるレーンではない(それは回帰であり、
台本の仕事である)。読むのはこの4つで足りる:

1. 最終 green 鮮度スタンプ以降の `docs/build-records/*.md` の 影響範囲(closure) — 何が変わったか
2. `docs/02-design/environments.md` — **アプリの起動コマンドと URL、E2E 用の
   シード・リセット手順**。触る先はここが名指す環境であり、**本番でも人間の常用環境でもない**
3. `docs/01-requirements/` の該当 `UC-nn` — その画面が**外から何を約束しているか**
4. `docs/ux/` の該当箇所 — `policy.md`(基調)と、触る画面の `screens/SCR-nn-*.md`・
   `flows.md` の該当する流れ。**UX 文書と実画面の突き合わせはこのレーンの仕事である**
   (あの層は文書検証の外に居るので、ずれを捕まえる独立の網はここだけ —
   `.claude/directions/ux.md` §0)。`docs/ux/` が無いプロジェクトではこの項は無い。

**これ以上は読まない。** 実装を読むと、実装が想定した経路をなぞってしまう。

## 2. 動かす

```bash
# environments.md の起動コマンドでアプリを立て、シードを入れる(コマンドの正はそちら)
# → 立ち上がらないなら、それは §0 の「環境の不備」である。ここで止めて人間へ渡す
```

**立てたアプリは、次のシェル呼び出しでも生きていなければならない** ★ — ブラウザは別のプロセス
であり、待ち受けを見つけられなければ**接続拒否**しか返さない。**待ち受けが消えていることは、
設定の誤りと見分けが付かない**(2026-09-04 に丸1回そう誤診した)。だから**立てた直後に、
別のシェル呼び出しから生きていることを1度だけ確かめる**(そのプロセスや `environments.md` の
URL への到達を見る手段はプロジェクトによる)。**消えていたなら、それは §0 の「環境の不備」で
あり、このレーンの手には無い** — 起こす側が渡した起動行の問題である(§0 の砂箱の段が
その正を名指している)。**「立て直せば次は残るかもしれない」で繰り返さない。**

**落ちたときは、落ちた実際のコマンドと出力を逐語で報告して止める。** どの形でも §0 の
「環境の不備」として渡し、qa は red のままにする。`read-only file system` のように書込みを
拒まれた形なら、その置き場を直すのも起こす側である(`orchestration.md` §1.1.1 の
「既定では `$HOME` へ書けない」)。**確かめるためのファイルを別に作らない**(このレーンが
書いてよいのは所見のファイルだけである — `.claude/roles/qa.md`)。**砂箱の書込み境界も
宛先の allowlist も、自分で緩めてやり直すことはしない。**

そのうえで **chrome-devtools MCP のツールで実際に触る**(`orchestration.md` §1.1.2 が設定の正)。
**claude で走っているなら `claude-in-chrome` の道具群で触る**(§1.4 のフォールバック)。そのときは
**先に触るブラウザを選ぶ**(`list_connected_browsers` → `select_browser`)— 人間が仕事に使って
いるプロファイルには触らない(`roles/qa.md`)。**モーダルを出す操作は避ける**(alert / confirm が
出るとそれ以降の操作が届かなくなる)。

**触ってよい宛先は、`environments.md` の「ブラウザQAの宛先 allowlist」が宣言したものだけである。**
codex 側では、**スキームを MCP サーバの起動引数が、宛先を Chrome の名前解決規則が**
分担して縛っている(§1.1.2)。**「二重に掛かっている」ではない** ★ — 宛先を縛る層は
名前解決規則ひとつだけなので、それを落とすと**宛先の縛りが全部消える**。**claude 側ではそれが自動では
掛からない** — 拡張のサイト単位の許可をその宣言した宛先だけに絞ってから触る(§1.4)。**外へ出ようと
して拒否されたら、それは
所見である** — 製品が外部へ出ているということなので、`environments.md` の allowlist に足すか、
製品を直すかを依頼元に返す。**自分で allowlist を緩めて確かめ直すことはしない。**

**★ allowlist から漏れた宛先は「拒否」ではなく「壊れている」として出る。** 内側の宛先が
到達できない形で失敗したら、**製品の不具合として起票する前に、症状から落ちた層を見分ける** —
症状と層の対応は
`.claude/directions/orchestration.md` の「1.1.2 ブラウザQAの口は MCP で足す」が正である。
(要旨: 症状の文字列で3層を見分ける表が在る)
**層が allowlist だったなら、それは製品の所見ではなく依頼元への報告である**
(2026-09-01 の実測では、この取り違えでブラウザQAが2日止まった)。

**Playwright を使ってもよい**(スクリプトで再現手順を固めたいとき、MCP のツールより速いとき)。
ただし**同じ allowlist を負う**: `launchOptions.args` に `orchestration.md` §1.1.2 (2) と同じ
`--host-resolver-rules` を渡す。**書いたスクリプトはセッションのスクラッチパッドに置き、追跡対象の木には
残さない**(このレーンは1バイトも書かない — 台本になるものは 02 の `E2E-nn` として依頼元が起こす)。

最低限これだけは踏む:

| 観点 | 触りかた |
|---|---|
| **戻り導線** | 変更した画面へ入って、ブラウザの戻る・リロード・直リンクで出入りする。状態が壊れないか |
| **二度押し・並行** | 送信ボタンを続けて押す。同じ操作を2タブで同時に行う |
| **境界の入力** | 空・空白のみ・極端に長い・想定外の文字種・ゼロ・負・上限+1 |
| **エラーの見え方** | わざと失敗させ、**画面に出る文言が利用者に意味を持つか**(スタックトレース・生の英語エラー・沈黙は所見) |
| **コンソールとネットワーク** | 操作の間じゅう、未処理例外・4xx/5xx・壊れた要求が出ていないか |
| **UX 文書との突き合わせ** | §1 の 4 で読んだ記述(配置方針・項目・状態・基調)と実画面が食い違っていないか。食い違いは所見(どちらが正かは裁定しない — 依頼元が決める。文書側が古いだけなら重大度は通常「低」) |

**破壊的な操作をしてよいのは、`environments.md` が E2E 用と定めた環境の中だけである。**
それ以外(本番、共有の検証環境、人間が使っているブラウザプロファイル)には触らない。

## 3. 返す

**重大度と再現手順が無い所見は所見ではない。** 1件ごとにこの形で:

```
### <一行の見出し>
- severity: 高 / 中 / 低
- 再現: 1. … 2. … 3. …(**そのまま踏める手順**。「適当に操作すると」は不可)
- 期待: <UC-nn / 受け入れ基準の条項 ID。無いなら「上流に規定が無い」と書く>
- 実際: <観測した事実。画面の文言・コンソール出力・ステータスコードは逐語>
- 証跡: <スクリーンショット等のパス>
```

- **重大度は `issues-pendings.md` §3.0 の表が唯一の正である**(この skill は別の定義を持たない)。
  ブラウザQAで実際に当たるのは「高」の条件のうち **`AC-nn` が落ちる / データ・権限・金・監査証跡が
  損なわれる / 回復に再リリース・データ移行・外部への連絡が要る**である。
  見た目の粗さは「低」。数を作らないこと。
- **上流に規定が無い所見は「規定が無い」と書いて出す** — 勝手に期待値を作らない(原則4 の
  問う基準に当たるなら、それは依頼元がシートに載せる)。
- **所見ゼロは正当な結果である。** そのときは **踏んだ観点の一覧と、最も弱いと感じた点**を書く。
  空を避けるために所見を作ることは欠陥である(CLAUDE.md §3)。
- 長い明細はディスクへ。艦隊なら報告本文は **40 行 / 2000 バイト**以内で、明細はパスで渡す。

**裁定は依頼元が行う** — 重大度「高」と振る舞いに関わるものは1件ずつ、残りは列挙のみ
(CLAUDE.md §6 と同じ扱い)。このレーンは採否を書かない。

## 4. このレーンの終わり方(依頼元が確認するもの)

qa 試験区分が green になるのは、次のどちらかが記録されたときである
(**この条件の正はこの節であり、`/verify-tests` §3 はここを参照する**):

- 探索的ブラウザQAを**実行し**、重大度「高」の所見が**ゼロ**になった(直した結果でよい)。
  **起票したかどうかによらない** — 課題票にしても所見は消えないので、この試験区分は green に
  ならない(CLAUDE.md §3 の完了定義の**探索的ブラウザQAの項**には「未起票の」という限定が無い)
- 「適用外(UI 無し — 根拠のファイル)」を記録した

**依頼元の控えに差が出た run も green にしない** ★ — `@qa` が所見のファイル以外へ書いたことに
なるので、**その run の所見は採らずに捨て、そのことを報告して red のまま閉じる**
(控えの正 — 何を打ち、何を除き、何が見えないか — は `orchestration.md` §1.1.1)。
**重大度「高」がゼロでも green にならない。**
**この run も、下の「最大2回」に数える** — 起こしたことに変わりはないので、
捨てた run を無制限に起こし直す口にしない。

**環境の不備で走らなかったときは、どちらでもない** — qa は red のまま。人間へ渡す。

**このレーンも止まる。** 1本の `/verify-tests` の run が同じ範囲へこのレーンを起こすのは
**最大2回**である(CLAUDE.md §3 の停止規則を、依頼元が qa 試験区分にも当てる)。
2回目の後に残った重大度「高」は、争わずに `docs/issues/` の1件として起票し、
qa を red のまま閉じる — **red は正当な結果であり、回し直しの理由ではない。**

## 5. 口の作り方は orchestration.md §1.1.2 が正である

**探索的ブラウザQA はデプロイゲートの一部である**(CLAUDE.md §3・§4)。MCP サーバの入れ方・宛先
allowlist・codex の信頼の設定は、このキットでは `.claude/directions/orchestration.md` §1.1.2 に
一元化してある(艦隊でも単独でも同じ口を使う)。**起こせない・止まったままなら、それは §0 の
「環境の不備」である** — 適用外にはできない。qa は red のまま、人間へ渡す(承認の是非は人間の
判断であり、AI が代わりに答えない)。
