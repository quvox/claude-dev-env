# 構築 — F1、構築フロー

入力: $ARGUMENTS
**やり取りも、作るファイルも、すべて日本語で書く。**

**目的**: 要求を、動くコードと真である SSOT に、1ウィンドウで変える。
このフローは verify 系フローが所有するものを**意図的に飛ばす** — E2E、テスト suite の全件、
ブラウザQA、独立レビュー、コールグラフの再生成、00〜02 の全件読み。
**決して飛ばしてはならないのは先送り禁止の5項目である**(`flows.md` §6)。
**このフローは起動元から独立している**: 入力は引数とディスクの状態(構築記録・鮮度スタンプ・シート・
課題票)であり、手順も報告も人間のときと中央エージェントのときで同じである。
**艦隊運用では**(CLAUDE.md §9)1本の `/build` が、1つの作業エージェントのウィンドウにおける
1つの作業指示である。違うのは**シートが人間へどう届くか**(§1)と**報告の上限**(§6)だけで、
下のすべての関所は同一に縛る。
**クロージャが重なる複数の要望をまとめて渡してよい**: 1クロージャ、1シート、1記録
(履歴では理由を `R-01`、`R-02` … に分ける)。

**このスキルが負う規範の節** — `.claude/directions/reading.md` の `/build` の行。それは**床**である:
多く読むことは決して違反ではない。**読んでいない節から決めることが違反である**(原則9)。

## 0. 着手 — 引数を解釈し、入口を通る

**最初に、保護ブランチで書かないことを確かめる** ★ — 走らせるのは1行である:

```sh
python3 .claude/scripts/guard-branch.py --slug <そのタスクの slug>
```

**終了コードが `0` でなければ、そこで止まって報告する**(`1` は、こちらの知らない事情が
在るという意味である。**`git branch -D` を打たない**)。判定の中身の正は
`.claude/directions/flows.md` §7.1 である。**ここには写さない。**

解釈は、最初に当たったものが勝つ:

- **引数のどこかに `--repair`** → 修繕モード: 対象はキューの項目である(課題票、`残務` の行、
  または引数や検証の周の報告が名指した verify の所見)。修繕モードは無人で走ってよい
  (**キューの項目が既に判断を担っている**)。**これはモードであって許可証ではない** —
  入口で仕事を拒むものは何も無いので、**通り抜けるべきものが存在しない**
  (上のブランチの確かめは仕事を拒まない — 移ってから同じ仕事を続けるだけである)。
- **`docs/issues/` の課題票 ID、またはその課題票のパスに一致**(艦隊の作業指示はパスで渡す —
  `orchestration.md` §4)→ その課題票を格上げする。本文を読む
  (**本文が読まれるのはここだけである**): `related:` がクロージャの種、
  `origin_layer:` が起点層の種になる(**種であって判定ではない** — §1 の表が決める。
  食い違ったら課題票の値を直し、そう述べる)。`closes_when:` が既に満たされているなら
  格上げしない — **報告する**(`issues-pendings.md` §8)。パスを記録の `issue:` に書く。
  課題票のファイルを消さない(成功したときに §5 が消す)。
- **`state: building` の `docs/build-records/<slug>.md` に一致** → 再開する。
  記録の 進捗メモ を読み、**終わっていない最初の段から再開する**。
  `docs/sheets/<slug>.md` がまだ在るなら、そのタスクは回答待ちである —
  そのパスをもう一度提示して止まる。
- **`docs/sheets/*.md` のパスに一致** → 転記だけの run(inspection-17 判断8):
  下の着手時の転記を行い(回答を着地させ、キューの修繕を起票し、シートを削除する)、止まる —
  **記録もシートもコードも作らない。** これは、これ以上 `/build` が来ないときの、
  回答済みのシートの回収である(`flows.md` §5)。**未回答**のシートはその場に残し、
  そう報告する。
- **小規模修正の例外**(CLAUDE.md §4): 明らかな数行の誤字・コメント・仕様ドキュメントの
  言い回しの修正は、**シートと構築記録を飛ばしてよい**。**製品の振る舞いを変えるものは
  すべて例外に当たらない** — 不具合の修正も依存の版上げも、シートは飛ばせても
  **最小の構築記録は必ず書く**(記録の無いコード変更は負債の計器と F4 の犯人の範囲から
  抜け落ちる — inspection-14)。触ったテストは飛ばさない。原則2 も飛ばさない。
  SSOT が嘘をついてよいわけでもない。**迷ったら通常の `/build` として回す。**
- **それ以外** → 自由文の要望。**引数が空** → `docs/issues/index.md`、`docs/pendings.md`、
  `docs/residual.md`、`building` の記録、そして未回答なら最新の質問シートを提示し、
  「どれに着手しますか、あるいは新しい変更内容を教えてください」と問うて止まる。
  **決して推測しない。**

そのうえで2つの計器を読む。**どちらもこのタスクを拒まない** —
旗を取らず、数字が何であれ終了コード0で終わる:

```bash
python3 .claude/scripts/check-backlog.py
python3 .claude/scripts/check-debt.py
```

**その数字を報告に載せて、先へ進む。** それはここで下す決定ではない:
**拒む場所は1つ、デプロイゲート(`stamps.py check`)だけ**であり、
このタスクの代わりに検証の周を回すという選択は、**このタスクを配車した側のもの**である。
どちらかが終了コード2 を返すのは別の話である — それは壊れた台帳か誤った引数であり、
**続ける前にあなたが直すもの**である(`flows.md` §4)。
**艦隊運用ではこの2本を、配車した中央エージェントが既に読んでいる — その二重読みは承知のうえで
残している**: フローのスキルがどちらの運用の型でもまったく同一であるという起動元からの独立性は、
設計上の制約であって便宜ではない(`flows.md` §7)。

**着手のついでに、残っている回答を転記する — ただし SSOT の外の宛先にだけ**:
回答済みの `docs/sheets/questions-*.md` か `docs/sheets/<slug>.md` が在るなら、
各回答を(逐語 + 日付で)名指された構築記録の 決定シート(回答済み) か、名指された課題票の
経緯 へ転記し、そのシートを削除する — **ディスクに残っているシートこそ、負債の計器が未回答の
問いとして数えているものである。**
**中身が SSOT に属する回答**(決定、仕様の解釈)は、ここから着地させない —
それはどのクロージャの外でもある SSOT への書込みになる(原則1):
引用 + 日付を `docs/histories/<YYYY-MM-DD>-answer-<論点>.md` 1本へ転記し
(`.claude/templates/answer.md`)、**それを指す課題票を1件起こす**
(`type: modify`、`closes_when:` は「その回答が SSOT に反映されたとき」)。
**残務の1行にはしない** — 残務はローテーションで押し出され、押し出されたファイルは
どのフローも読まないので、回答が黙って読まれなくなる(`flows.md` §5)。
そのクロージャを所有する `/build --repair` がそれを着地させる
(`flows.md` §5 — inspection-17 判断8)。

## 1. クロージャと1枚のシート(人間が登場する点。たいていは登場しない)

**クロージャ** = この仕事が触る 00〜03 の文書とコードのパスのすべて。
**考え始める前に、道具で確定させる。決して少しずつ広げない**(`relations.md` §6):

```bash
python3 .claude/scripts/relations-query.py --impact <path>   # 触りそうな実装から
python3 .claude/scripts/relations-query.py --requirement FR-<domain>-nn
python3 .claude/scripts/check-ssot.py docs                   # 一括検査の現状(母集団の凍結)
```

**凍結したものの出口** ★: **クロージャの中の違反だけを調査メモへ写し、外の違反には手を付けない**
— 外は文書整合(F2)のものである。**凍結は「先に在った違反を自分のせいにしない」ためであって、
掃除の指示ではない。**

読む範囲は**クロージャと、その行が名指すもの**である(`source` / requirements / contract /
test の行、request.md の「やらないこと」、到達した決定)— **決して 00〜02 の全部ではない。**
全件の読みは verify 系フローに在る。大量の読取は CLAUDE.md §8 に従って委任する。
**この1周の中で**: `docs/pendings.md` と `docs/issues/index.md` を見て、この変更が解消できる項目が
無いかを確かめ、開いたものの鮮度を判定する(`issues-pendings.md` §8)。

**起点層**を決める(これが段2 がどこまで上へ書くかを決める — 原則3):

| 判定基準 | 起点 |
|---|---|
| 目的・対象ユーザー・スコープ・受け入れシナリオが変わる | 00-requests |
| 事前に仕分けた判断が変わる(決定・委任・要確認の解決。技術の選択そのものを含む) | 00-requests(decisions/) |
| 目的は同じだが、振る舞い・受け入れ基準が変わる | 01-requirements |
| 振る舞いは同じだが、構造・分割・契約・選んだ技術の使い方が変わる | 02-design |
| 構造は同じで、実装詳細だけが変わる | 03-impl |

**目的・範囲・受け入れシナリオのどれも変えない変更は、00 に触れない** —
それが「要求の層をいつ書き直すのか」への答えのすべてである。
**「やらないこと」は必ず突き合わせる**: 衝突しているなら 00 が先に動かねばならず、
**意味のある 00 の編集はすべて人間の同意を要する**(シートの項目になる)。
**起点が曖昧なときは決めるのであって、問うのではない。** 上流の2つが別々の層を指しているときだけ
論点になる。**触らない層を明示的に判定する**(「01: 変更なし(理由)」を記録へ)。
他の `building` の記録のクロージャと重なる → **決して並走させない**。畳むかキューへ回す
(その要望を課題票として起票して報告する — 艦隊の粒度判定が当てるのと同じ規則である)。

**艦隊の下で並走している作業指示なら、確定したクロージャを作業指示が載せている①と②に
突き合わせる** ★ — **1バイトも書く前に、である。** ①は実装の交わり、②は文書と規範のパスの
交わりで、どちらも**配車のときに取った見込み**である(正は `orchestration.md` §3.4)。
**確定したクロージャがその外へ出ているものを1本でも含むなら、段2 へ進まずに止めて報告する** —
その対の非交差の証明は、いま古くなったからである。**書き始めてからでは遅い。**

**そのまま比べてはならない。比べる前に、両側の形を揃える** ★:

- **②と比べるのは**、確定したクロージャの中の**文書と規範のパスから、`orchestration.md`
  §3.4.1 の表の対象(共有生成物と `docs/ux/reviews/` 配下)を除いたもの**である。
  **共有生成物はどのタスクのクロージャにも入る**(段5 で索引を再生成し、機能表に自分の行を
  足すのは、この `/build` 自身である)ので、**除かずに比べると、並走している `/build` は
  1本残らずここで止まる**(一覧はここに写さない — 正は §3.4.1 の表である)。
- **①と比べるのは**、確定したクロージャの中の**コードのパスの全部**と、**そのパス1本ずつで
  `relations-query.py --impact` を打ち直して集めた** ID の集合である。
  **上でクロージャを決めるために打った1回の再掲ではない** — あれは「触りそうな実装」から
  打つものであって、確定した全パスから打ち直した集合ではない。**これは並走のために増える
  手であり、並走していない `/build` は打たない。**

(単独運用なら並走が無いので、この突き合わせも無い。)

**いま記録とシートを作る**(記録が先 — **回答が1つも返る前に中断しても、記録だけから再開できねば
ならない**):

```bash
mkdir -p docs/build-records docs/sheets
cp .claude/templates/build-record.md docs/build-records/<slug>.md   # state: building
cp .claude/templates/sheet.md        docs/sheets/<slug>.md
```

記録の frontmatter を埋める(`critical:` はクロージャのパスから — `critical-config.json` の
パターンが床であり、**あなたの判断はそれを上げることしかできない**。`origin:` は証拠から、一度だけ)。
そしてクロージャを埋める。**いま**、すべての基本要件 `BR-nn`(`baseline.md` §2)をクロージャに
照らして判定し、判定を `## 基本要件の点検` へ書く —
**該当した項目は段2 でそれを所有する層へ降ろす。満たすかどうかは決してシートに載せない**
(原則4。**どう満たすか**は問う基準が決める)。

シートは常在の規則に従って作る — **問う基準がすべての候補を濾し**(`delegation.md` §1)、
概念の明確化の節は `build-record.md` §3 に従って削り、**根拠の三方向は決して空でなく**、
エラー処理 / テスト / ログ / 設定は**導いて決めるのであって、決して問わない**
(`delegation.md` §2.1。`origin: human-report` の反転は §5)。提示の前に自己点検する:

```bash
python3 .claude/scripts/check-sheet.py <slug>    # SH4 は未回答なので落ちてよい。SH5/SH6/SH10/SH11/SH12 はあなたが直す
```

シートの**パスと件数**をチャットで提示する(**そのメッセージしか見ない読み手に向けて書く** —
`delegation.md` §1.1。**シートも、この提示の文も、人間に判断を求める文なので
`delegation.md` §1.1.1 の読み直しを通す** — 出す前に一度読み返す)。**艦隊運用では、提示するとは 20行のエージェントからの相談を自分のウィンドウに出すことである**
(加えて中央エージェントへ1行、自分のウィンドウ名で1回鳴らす)。**そして応答を終える** —
文脈は保たれ、人間は**そのウィンドウで**答え、その言葉であなたが起きる
(`orchestration.md` §6。中央エージェントは取り次がない)。
**問いがゼロのシートは人間を要さない**: 「問いなし(開示のみ)」と記録し、シートを削除し、
無人のまま続ける。そうでなければ待つ。回答が来たら(逐語 + 日付で)記録へ転記し、シートを削除する。

## 2. 文書を書く — SSOT に、直接

**これが設計という行為そのものである。** クロージャを**起点層から上から下へ、1回だけ**歩き
(00 → 01 → 02 → 03)、SSOT の文書をその場で編集する。
**変更指示書も、下書きも、別の紙も作らない** — 変更は、それを所有する文書に、ちょうど1回書かれる。
**SSOT はここで実装より先行する。その過渡は正当であり、目に見える**(`flows.md` §3)。

下降の規則:

- **変更が実際に触れる節だけを書く。** 作る文書の雛形を読む(原則9)。
  **雛形の見出し構造を決して変えない。**
- シートの回答と常在の委任を適用する。**行使した瞬間に、開示行をそれを所有する文書へ書き、
  1行を記録の 進捗メモ へ書く**(`[DS-nn] 決めたこと — 理由: … / 見直す条件: …`、
  `delegation.md` §3)。
- 該当した基本要件は、それを所有する層へ着地する(外から見えるものは 01 の受け入れ基準に EARS で)。
- 層ごとの必須: 00 — 回答を `decisions/` へ反映し、「やらないこと」との整合を保つ
  (矛盾は上書きする。**両方を残さない**)。01 — 境界値と異常系を持つ EARS の条項。
  **すべての要件に `分割可否`**(`段階可` は理由つき。問わずにここで決める — `01-requirements.md`)。
  UC のフローを更新する。02 — 連携が変わったら relations.md の `PLAN-*` を更新する。`CTR-*` を 03 と揃える。
  E2E シナリオ一覧を更新する。新しいモジュールは分割定義から始まる。
  **01 の条項を足した/変えたなら、要件カバレッジ表に対応する行を足し、主担当モジュールと
  充足 を書く**(`02-design.md`「★ 要件カバレッジ」)。
  **モジュールの詳細を書き足したなら、それを `02-design/<module>.md` へ切り出すかを一度考える**
  — しきい値は無く、見るのは「切る線がモジュールの境界と一致しているか」と「切ると並走できる
  ようになるか」の2つである(`02-design.md`「モジュールの詳細を切り出すか」)。
  **切らないと判断したことは書き残さない**(判断のたびに1行増やすと構築記録が埋まる)。
  ux — 画面のコードを触るなら、**同じ下降の中で** `docs/ux/` の該当箇所を直す(数行でよい。
  その画面の `screens/SCR-nn-<画面>.md` が無ければ、**このタスクが作る** — 事前に完成させる層では
  ない。現状は `screens/` へ、判断の理由は `reviews/` へ — `.claude/directions/ux.md`。
  `docs/ux/` のパスはクロージャに含める — 検証連鎖の外だが、単一書き手の外ではない。
  `orchestration.md` §3.4)。
  03 — **実装者が要るもののうち、コードが語らないものだけ**(処理の流れ・連携・実装上の判断)。
  鏡の側は段4 が作られた結果から決着させる。グリーンフィールドでは労力を 00〜02 へ回す —
  **そこの穴は本番まで生き延びるが、03 の当てずっぽうはどのみち段4 が上書きする**
  (`03-impl.md` 「★ 実装がまだ無いとき(グリーンフィールド)— 鏡ではなく、これから作るものの記述」)。
- **00 の必須ファイルがまだ無いとき(新規開発の1本目)**: **この層は人間のものである**
  (`00-requests.md`)。同じ問いに `/retrofit` §5 が既に答えており、ここでも規則は同一である —
  `request.md` の**骨子**を提案する(目的、利用者、やること、**やらないこと**)。
  **ファイルを書くのは人間であり、その人自身の言葉で書く。**
  `acceptances.md` / `terminology.md` は**候補のファイル**として生成し、人間がシートを通して直す。
  **AI が要求の文書を自分の言葉で書き上げることは決してない。** これは下降の途中の曖昧さでは
  なく起点そのものの不在なので、§1 と同じに扱う: 骨子と候補のパスを提示し、人間の執筆を待つ。
- **まだ `version` を上げず、`verified` に触れない** — 段4 が最終の文面を決着させ、§5 が刻む。
- 下降の途中の新しい曖昧さ: 委任のもとで決める(これが既定)。でなければ問う基準 —
  通ったものは記録の 質問キュー に溜めて出口へ回す。**決して下降を止めない。**
  範囲の外の問題は原則8 の記録先の振り分けを通し、**手を付けない。**

## 3. 実装する

入口条件: シートが回答済みか不在であること、**そして lint / テストのコマンドが実在すること** —
クロージャ(または、いま書いたばかりの SSOT)が、未定でないコマンドを持つ
`02-design/environments.md` を含んでいること。
無いコマンドは**事実として在る場所**から調べ(マニフェスト、CI の設定、Makefile、隣のテスト)、
`[DS-04]` の開示つきで 02 へ書く。本当に決められないもの(グリーンフィールドの実行系の選択)は
シートの項目になる — **検証できない実装は、完成させられない。**

**同じ1回で、コードとテストコードの置き場を宣言する** — `.claude/scripts/flow-config.local.json`
の `code_roots`(空か不在なら書く。**既にあるときは毎回見直し、このタスクが触るコードのパスが
宣言済みの接頭辞の下に無ければ足す** — 判断の基準は `flows.md` §2 の1文である:
そのファイルを変えると製品の振る舞いかテストの結果が変わりうるなら、それはコードの置き場に属する)。
**`scope_roots` と `ui_roots` はこの見直しの対象ではない** — 試験区分ごとの置き場は狭く書くと
穴になるので、正は「迷ったら書かない」である(`flows.md` §2)。
コマンドが実在する時点で置き場も実在して
おり、**未宣言のあいだ F3/F4 の鮮度スタンプはデプロイゲートで `未宣言` = red のまま、verify を何本
回しても動かない**(`flows.md` §2)。これは判断ではなく事実の転記なので、シートには載せない。
**足したときは、その宣言を焼き込んでいる鮮度スタンプが失効する**(`flows.md` §2)—
**それは望んだ動作である**: いままで許可リストの外に居た置き場が、次の周で初めて検証される。
**書いたら、この段のコミットに明示のパスで入れる**(`git add .claude/scripts/flow-config.local.json`)
— あの宣言は git で共有するものであり(`flows.md` §2)、手元にしか無ければ他の複製では
`未宣言` = red のままである。

そのうえで、タスク大の単位ごとにループを回す(1コミット、依存順):

1. **読む** — その単位が乗っているもの(受け入れ基準、02 の契約、そして既存ファイルに触れる前に
   `relations-query.py --impact <path>`)。
2. **実装する** — 書かれた仕様の中で。曖昧なとき: 委任 → 決めて、その場で開示する
   (所有する文書 + 記録の1行)。基本要件に触れた → **いま満たし**、非該当 だった判定の行を直す。
   問う基準を通るもの → キューへ入れて先へ進む。**フローを止めない。**
   **止まるのは、何も進められないときだけである。**
3. **確かめる**: lint と、**触ったモジュールのテスト** — 次の単位へ行く前に green にする。
   suite の全件・E2E・ブラウザQA は `/verify-tests` のものである。
   ここで走らせるのは、変更そのものが E2E のコードであるときだけである。
4. **記録する**: 仕上がった単位1つにつき 進捗メモ 1行。**その単位が触ったパスを名指して**コミットする(`flows.md` §2)。

**UI の試行錯誤 — 修正→ビルド→人間の確認 ★** 見た目・操作感の調整は、この段の中で
「直す → ビルド → 開発環境で人間がブラウザで見る → 人間が**この作業ウィンドウに**次の一言を打つ →
また直す」を何周でも回してよい(一言の届き方は `orchestration.md` §6 と同じで、中央エージェントは
中継しない)。**回っているあいだ文書は1文字も書かず、`/verify-tests` も回さない**(試験区分の
鮮度は失効したままでよい — デプロイゲートが見るのは出荷の瞬間である)。**着地したときに1回だけ**、
`screens/`(要るなら `policy.md`)を最終の現状に直し、`reviews/` の処置欄に1行書き、失効した
試験区分を green に戻して閉じる(qa を戻すのは qa 試験区分の run — ユーザテストの周回の中なら
周回末の `@qa` がまとめて戻す。`ux.md`「場面2」)。
N 周しても文書コストは最後の1回ぶんである — 試行錯誤の速度を文書に律速させない。

**ここでタスクを割ったり併合したりすることは決してない** —
大きすぎるということは 02 の分割が大きすぎるということである: **代わりにそれを報告する。**

## 4. タスク内整合確認 — このタスクの文書を、このタスクのコードに対して

**二重の網の1枚目である**(`flows.md` §1)。範囲: **まさにこのクロージャ** —
リポジトリ全体の版は `/verify-impl` の仕事であり、独立した文脈で行う。

1. 段2 が書いたものを、段3 が作ったものに対して読み直す。違うところを裁定する:
   **正当な実装上の判断だった** → 文書を直す(**設計の真実が追いついたのである**)。
   **逸脱だった** → コードを直す。裁定できないものは**構造上、問う基準を通る** — 出口のシートへ。
2. **触ったモジュールの 03 の鏡を、コードから決着させる**: `relations/MODULE-*.md` の
   frontmatter(`impl` / `callers` / `callees` / `contracts` / `tests`)を、コードを根拠として。
   コードが語れない散文の節(異常系・既知の制限・実装上の判断 — **既存の判断の行をすべて読み直し、
   継続/更新/削除 の印を付ける**、`delegation.md` §3.1)。足したテストについては
   `03-impl/tests/<module>.md`。
   **`callgraphs/` と `feature-graph.md` を再生成してはならない** —
   **`/build` は再生成しない側である** — 再生成するのは `/verify-impl` と `/relations` である
   (原則10 は依然としてそれらを手で書くことを
   禁じている。**古いことは鮮度スタンプで見えるが、手で書いて誤っていることは見えない**)。
3. 作られた連携が意図されたものと違い、その違いを設計が受け入れるべきものなら、
   `02-design/relations.md`(`PLAN-*`)を更新する。
4. **クロージャに `docs/ux/` が入っているなら**: `python3 .claude/scripts/check-ux.py` を回して
   green にする(条項参照・画面ファイル・指摘番号の実在 — `ux.md`「機械検査」。違反は非0終了)。
   **UI を触ったタスクは、閉じる前に自分でブラウザで該当画面を開き、スクリーンショットを報告に
   添える** — 独立ではないが即時であり、誰も見ないまま閉じることを無くす(独立の網は
   qa 試験区分 — ユーザテストの周回の中なら周回末の `@qa` — である。`ux.md` §0)。
5. **01 の条項を改訂・退役させたタスクは、その条項 ID を `docs/ux/screens/` と
   `docs/ux/flows.md` で grep する**(`ux.md`「00/01 が変わったときの橋」の手順4)。引っかかった
   画面(このタスクで触らなかったのに古い条項を参照しているもの)は直さずに報告へ載せる —
   後続の作業指示を積むのは起こした側である。`docs/ux/` が無ければこの手は無い。

## 5. 先送り禁止、そして記録を閉じる

先送り禁止の5項目(`flows.md` §6)のうち、**段4 の後に**回すのは次の3つである
(**確定した最終状態を検証しなければならない**)— 残る2つのうち「タスク内整合確認」は段4 そのもの、
「問う基準の振り分け」は下の §5-2 が担う:
build / lint、触ったモジュールのテスト、そしてすべての基本要件の 該当 の行が
**実際に作られていること**の確認(条項・契約・テスト、**および §2 の欄がそれ以外の落とし先を
挙げている項目では、その落とし先の実物**が在ること)。
**01 の条項が増えた/変わったタスクは、その条項が 02 の要件カバレッジ表と 03 のテスト対応表に
対応する行を持つことも確かめる**(行が無いことは空欄にならないので、確定した最終状態でしか捕まらない)。
これは先送り禁止の6つ目ではなく、**段4 のタスク内整合確認をこの位置で仕上げるもの**である
(`flows.md` §6 の5項目は増えない)。
先送り禁止の点検で入れた修正が段2 が記述した振る舞いを変えたなら、段4 へ戻る
(**この §5 の中で段4 へ戻れるのは、下の 2. の戻りと合わせて合計1回である**)。
**省略できる規則が1つだけ在る(inspection-16 D5): 段3 の最後に green だった build/lint+テストの
run 以降、`docs/` の外が1つも動いていないとき** — `git status --porcelain` と
`git diff --name-only <その実行時のHEAD>` に `docs/` 以外が1件も無い —
**build/lint+テストの回し直しを省略してよい**(段4 が文書だけで終わった典型)。
`docs/` 以外が1バイトでも動いたら全部やる。
**基本要件の点検とタスク内整合確認は、この省略の対象外である。**

そのうえで、この順で:

1. **文書に版を刻む**: 触った SSOT の文書ごとに `version` を1回上げる
   (意味が変わったなら MINOR、そうでなければ PATCH。`relations/` か `features.md` を変えた
   タスクは `docs/03-impl/index.md` の MINOR を上げる — それが層の版である)。
   **`verified` を決して書かない** — それは verify 系フローの署名であり、
   **その不在が「作ったが、まだ検証していない」の正直な表示である。**
2. **出口のシート。キューが空でないときだけ**: 溜まったもののうち問う基準を通るものすべてを、
   1枚のシートにする(`docs/sheets/<slug>.md`、ブロックの書式)。パスを提示する
   (艦隊運用では §1 と同じ、自分のウィンドウにエージェントからの相談を出す経路 — `orchestration.md` §6)。
   回答が来たら**起点層から下へ**適用し、転記し、シートを削除する。
   **その適用がこのタスクの SSOT かコードを動かしたなら、この §5 の 1.(文書に版を刻む)を
   やり直す** — 適用は 1. の後に文書を動かすので、**そのぶんの版が上がらない**。
   **適用がコードか 02/03 層を変えたなら、上の先送り禁止の3項目も回し直す。**
   **先送り禁止の3項目に回数の上限は無い** — 決して後回しにしない点検であり(`flows.md` §6)、
   **確定した最終状態に対して green でなければ出口を通れない**(**回数の上限が無いという意味であって、
   上の省略の規則 — 段3 の最後以降 `docs/` の外が1つも動いていないとき — はそのまま生きている**)。
   **回数で切るのは段4 への戻りだけである**: 上の戻りと合わせて**合計1回**。
   **使い切ってもまだ一致しないなら、このタスクはこの run では閉じられない** ★ —
   **出口を通らず、下の「中断したとき」の打ち切りへ進む**(`issues-pendings.md` §5.1)。
   `awaiting-verify` へ決して進めない — 進めれば、記録が「タスク内整合確認は済んだ」という
   **偽の主張**を持ったまま検証待ちに座る。**続きは課題票から始まる**
   (`/build <課題票の ID>`。課題票は再開の仕組みを持つ唯一の記録である — 同 §5.2)。
   **段4 を回数で切ってよいのは、切れたときに出口が閉じるからである** — 後回しにはしていない
   (`flows.md` §6)。
   **キューが空であること — それが設計された結末である** — は「お伺いする事項なし」と述べる。
3. **履歴**: `docs/histories/<YYYY-MM-DD>-<slug>.md` 1本(`.claude/templates/history.md`)—
   理由を `R-nn` として、更新した文書の表、何を実装したか、実行した移行(**無いなら明示的に
   「なし」**)、シートと開示から拾った 検討した代替案、副産物。
   **`critical: true` の記録は、移行が無くてもロールバック・復旧の表を埋める。**
   `origin: human-report` のタスクは 知見 の行を書く(`delegation.md` §5.1)。
4. **このタスクが閉じたものを解消する**: 起点になった課題票を削除する(履歴に記録する)。
   `path` がクロージャに在る `残務` の行を消化する — **1行ずつ判定し**
   (直した / 不要と裁定(理由) / 持ち越す(理由))、最初の2つを削除し、判定を履歴に記録する。
   **見るのは `docs/residual.md` だけである**(ローテーションで押し出された
   `docs/residual-NNN.md` には判定を付けない — `issues-pendings.md` §2.1)。
   **決してパスの一致だけで削除しない。** `python3 .claude/scripts/build-index.py` を走らせる。
5. **記録を閉じる**: **まず段1〜段4 が書いたものを、パスを名指して全部コミットする**(版の繰り上げ、履歴、
   再生成した索引、削除した課題票)— 記録の `commit:` は、**このタスクの仕事を実際に含む
   コミット**を名指さねばならず、**汚れたツリーはすべての verify の鮮度スタンプを無効に保つ**
   (`flows.md` §2)。そのうえで `## 主張` を埋め(コマンドと最終出力行を逐語で)、
   `commit:` を `git rev-parse HEAD` にし、`state: building` → `awaiting-verify` に切り替え、
   `updated` を更新する — **そして記録そのものをコミットする。**
   **打った後にそのコミットを `git commit --amend` / rebase / squash してはならない** —
   `commit:` が名指すコミットが履歴から消えると、この記録はどのコミットの仕事も指さなくなる
   (鮮度スタンプが `判定不能` になるのと同じ理由。`flows.md` §2)。
   そのうえで構築記録ゲート — fail-closed である。**迂回するのではなく、直して回し直す**:

```bash
python3 .claude/scripts/check-buildrecord.py <slug>
python3 .claude/scripts/check-baseline-verdicts.py <slug>   # 計器。拒まないが、読む
```

長い明細はパスとしてディスクに残す。`orchestration.md` §5)

```
## 構築完了: <slug>(state: awaiting-verify)
負債の計器(着手時に読んだ数字。拒まない): 課題票 N / 残務 N 行 / 未検証記録 N / 未回答シート N
### 書いた文書(SSOT 直接)
| 仕様ドキュメント | version 遷移 | 何を変えたか(1行) |
### 実装
| 対象 | 内容 | コミット |
### タスク内整合確認(§4)
| 差異 | 裁定(文書を直した / 実装を直した / シートへ) |
### 先送り禁止
| 項目 | コマンド | 最終行 |
### 今回 AI が決めたこと(開示。0件なら「なし」)
| DS/D-ID | 決めたこと | 理由 | 見直す条件 | 反映先 |
### 記録
構築記録: docs/build-records/<slug>.md / 履歴: docs/histories/<...>.md /
解消した課題票・残務: <一覧 / なし> / critical: <true|false>
### 検証の予約(このタスクは未検証である)
/verify-docs・/verify-impl・/verify-tests が green を返すまで、この変更はデプロイ不能
(stamps.py check)。次の verify 実行に含まれる。
### 次にあなたがすること
<シートの回答待ちならそのパス / 無ければ「無し(検証は人間が指示したときに回ります)」>
```

**打ち切りで終えた run はこの雛形を使わない** ★(下の「中断したとき」。`awaiting-verify` に
達していないので「構築完了」ではない)。**その run はこの形で報告する**:

```
## 構築打ち切り: <slug>(記録は削除した)
入口: 人間の決定 | 出口で整合が取れなかった(§5 の 2.)
起票した課題票: docs/issues/<ID>.md(`closes_when:` を1行で)
### 戻したもの

### 課題票へ引用したもの

### 削除したもの

### 次にあなたがすること
```

**艦隊運用では、この様式も §5 の欄の後ろに置く**(`orchestration.md` §5 の畳み方。
共通の欄の `状態:` は `中断` である)。

## 中断したとき

**一時停止**(`/clear`、セッションの死)には何も要らない: `state: building` と 進捗メモ が
再開点である。`max_building_hours` を過ぎれば `check-debt.py --demote` が次の周の網へ戻す —
**設計どおりである。**
**打ち切り**(**この記録では再開しない** — 続きは課題票から始める): 入口は2つで、
**人間がこのタスクをやめると決めたとき**と、**§5 の 2. で段4 への戻りを使い切っても
一致しなかったとき**である(2つ目では実装は終わっており、残っているのは一致しない箇所だけの
ことが多い — それでも巻き戻すのが、この形を選んだ代償である)。
半分できていたものと、戻すか終わらせるべきものを引用した
課題票を1件起票し(`closes_when:` 全項目が後続で反映されるか破棄と裁定されたとき)、
コードを戻し、そのうえで記録とそのシートを削除する。
**削除の前に確認を取るのは、1つ目の入口のときだけである** ★ — そこでは人間との対話が
既に始まっている。**2つ目の入口では確認を取らない**: この run は無人で走りうるので、
そこに人間を待つ段を置けば「起動元から独立している」を破る(`flows.md` §7)し、
`/build` が問えるのは着手時と出口の2回だけである(原則5)。**代わりに、戻した範囲と
削除したものを §6 の打ち切りの様式に列挙する** — 対話の代わりに記録で追えるようにする。
**半分だけ真である SSOT を決して残さない**: 段4 の不変則は打ち切りにも縛る —
**SSOT は、あなたが残すコードと一致していなければならない。**
だから整合を終わらせるか、文書をコードとともに戻すかのどちらかである。
