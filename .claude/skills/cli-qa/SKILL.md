# 探索的CLI QA — 台本を離れるレーン(コマンド側)

対象: $ARGUMENTS。人間に向けた出力(報告)はすべて日本語で書く。

**これは `.claude/skills/browser-qa/SKILL.md` の兄弟である** ★ — **同じ試験区分(qa)の、
もう一方の実体**であり、**触る先がブラウザの画面ではなくサブコマンドである**ことだけが違う
(2026-09-15 の人間の裁定で足した。`.claude/directions/ux.md` §0)。
**両方に共通する規則は、あちらが正である。このファイルはそれを写さない**:

| 何 | 正 |
|---|---|
| 書かない・裁定しない | `browser-qa/SKILL.md` の冒頭 |
| 独立した文脈で走ること、誰が起こすか | 同 §0 |
| 所見の形と重大度、所見ゼロの扱い、報告の長さ | 同 §3 |
| 試験区分が green になる条件、最大2回で止まること | 同 §4(**下の §4 が足す違いを除いて、そのまま掛かる**) |

**これは台本ではない。** `/verify-tests` の unit / integration / e2e の試験区分は
**書いてあるものが通ることの確認**である(CLI なら、保存済みの期待値による `--help` の固定や、
子プロセスを起こして終了コードを見るテスト)。このレーンは逆で、**書いていないところを叩く**。

## 0. 走らせる主体と、走らない場合 ★

**独立した文脈で走る**(理由は `browser-qa/SKILL.md` §0 と同じ — 実装を書いた文脈が叩いても、
自分が想定した呼び方をなぞるだけになる)。

| 状況 | 誰が走らせるか |
|---|---|
| 艦隊(`CLAUDE.md` §2) | **`@qa`**。中央エージェントが起こしたウィンドウで、`.claude/roles/qa.md` が縛る(`orchestration.md` §1.4) |
| 艦隊でない | 対話モードで起こし、この SKILL.md をパスで名指して読ませる |

**ブラウザの口(MCP)は要らない** ★ — このレーンが使うのはシェルだけである。
だから `browser-qa/SKILL.md` §0 が言う「MCP 未設定・Chrome 不在」は、**このレーンでは
環境の不備にならない**。**砂箱についても、このレーンは何も要求しない**:
あちらは立てたアプリが次のシェル呼び出しまで生きている必要があるので砂箱なしを要求するが、
**このレーンはコマンドを叩いて終わるので、砂箱の有無で成立が変わらない。**
(艦隊の codex は 2026-09-20 からどの役も砂箱なしで起きるので、艦隊ではこの違いは出ない —
`orchestration.md` §1.1.1。単独運用で砂箱付きのウィンドウを使うときだけ、
常駐するものを立てる製品があちらと同じ事情になる。)

**「実行基盤が無い」は 適用外の理由にならない。** 成果物をビルドできない・実行できないなら、
それは環境の不備である — **人間へ渡して止まる**。**適用外にできるのはただ1つ**:

- **人が直接打つサブコマンドが1つも無い**。このときだけ
  「探索的CLI QA: 適用外(コマンドの面なし — `02-design/<根拠のファイル>`)」と根拠を名指して
  記録し、終わる。

**★ 判定するのは「サブコマンドが実在するか」であって、「台帳が書かれているか」ではない。**
根拠は **02 の「操作面の宣言」**(`02-design.md`)であり、`docs/ux/flows.md` の「コマンド一覧」の
**有無ではない** — 台帳は遡って書き起こさないので(2026-09-15 の裁定。
`.claude/directions/ux.md`「達成条件」の代金)、**移行してきたプロジェクトでは、
サブコマンドが在るのに台帳がまだ無い状態が正常である**。
**台帳が無いあいだは、`docs/01-requirements/` の `UC-nn` と実物だけを頼りに走る**
(§1 の 4 がその場合は空になる)。**「台帳が無いから適用外」と読んではならない** —
そう読むと、このレーンは移行直後のプロジェクトで一度も走らない。

**★ 今回の変更がこの面に届いていないと確かめられたときは、起こさずに「対象0件」と書ける** ★
(2026-09-15。inspection-28 B-1。**画面の側と同じ規則である** — `browser-qa/SKILL.md` §0)。
**確かめられたとき、だけである。** 判定は `stamps.py deps verify-tests:qa` が返す置き場と、
今回の変更のパスの**交わり**で見る。**交わりが空でも、共通の処理を通ってサブコマンドに
届くことが在る** — 直接触ったファイルだけを見て「影響なし」と決めない。
**少しでも分からないなら、起こす。**
省いたときは、**判定に何を使い、なぜ届かないと言えるのかを報告に1行で書く。**

## 1. 叩く対象を決める(読むのは4つだけ)

**変更されたところと、その周辺だけを叩く。** 全サブコマンドを舐めるレーンではない
(それは回帰であり、台本の仕事である)。

1. 最終 green 鮮度スタンプ以降の `docs/build-records/*.md` の 影響範囲(closure) — 何が変わったか
2. `docs/02-design/environments.md` の**「CLI 検証の実行条件」の節** — 成果物のビルド、
   実行ファイルの場所、隔離した作業環境の作り方。叩く先はここが名指す環境であり、
   **人間の常用環境でも本番でもない**。**この節が無いなら、それは §0 の「環境の不備」である**
   (勝手に叩き方を決めない — 何を壊さないかが宣言されていないからである)
3. `docs/01-requirements/` の該当 `UC-nn` — そのコマンドが**外から何を約束しているか**
4. `docs/ux/commands/CMD-nn-*.md` と `flows.md` の該当する流れ —
   **達成条件・呼び出しの形・出力と終了コード。UX 文書と実物の突き合わせはこのレーンの仕事である**
   (あの層は文書検証の外に居るので、ずれを捕まえる独立の網はここだけ — `ux.md` §0)。
   **まだ書かれていないなら、この項は空である**(§0 の ★)— そのときは 3 の `UC-nn` と実物だけで
   走り、**「記述が無い」ことを報告に1行書く**(所見ではない。依頼元が台帳を起こす材料である)

**これ以上は読まない。** 実装を読むと、実装が想定した呼び方をなぞってしまう。

## 2. 叩く

**★ 自分の環境を壊さないことが、このレーンの最大の危険である。** ブラウザ側の「本番データを
触らない」に当たるのが、コマンド側では**「開発者自身の環境を壊さない」**であり、
**しかもこちらのほうが事故が起きやすい**(`test-design` の
`references/cli-variant.md`「テスト環境の隔離 の CLI 版」が理由と手口の正である)。

- **隔離した作業ディレクトリの中だけで叩く。** `$HOME` の設定ファイル、グローバルに入れた
  道具、共有の資格情報には触らない。**このプロジェクトで実際にどう隔離するかの正は、
  `environments.md` の「CLI 検証の実行条件」の節である**(上の `cli-variant.md` が持つのは
  「なぜ要るか」と一般的な手口であって、このプロジェクトのコマンドではない)。
- **叩く先がネットワークへ出るなら、宛先は `environments.md` の
  「ブラウザQAの宛先 allowlist」が宣言したものだけである**(節の名前はブラウザ由来だが、
  **宣言している値は探索的QAの両方のレーンが負う** — `02-design.md`)。
  外へ出ようとして拒まれたら、**それは所見である**(製品が外部へ出ているということなので、
  宣言に足すか製品を直すかを依頼元に返す)。**自分で緩めて確かめ直さない。**
- **確かめるためのファイルを追跡対象の木に作らない** — このレーンが書いてよいのは
  所見のファイルだけである(`.claude/roles/qa.md`)。
- **落ちたときは、打った実際のコマンドと出力を逐語で報告して止める。**

最低限これだけは踏む:

| 観点 | 叩きかた |
|---|---|
| **達成条件** | `commands/` の「達成条件」の表の行を、**実際に打って終えてみる**。終えられないものは所見である **ただし `何が達成されるか` の欄が「退役: 」で始まる行は試さない** ★(2026-09-15)— あれは正しく廃止した操作であり、終えられないのが正しい。**除いた番号は報告に並べる** |
| **引数の境界** | 必須を省く / 余計に渡す / 順序を変える / 同じオプションを2回 / 空文字 / 極端に長い値 / 想定外の文字種 |
| **入力の形** | 標準入力をパイプで渡す・渡さない、端末から実行・パイプの途中で実行(出力の形が変わる製品が在る) |
| **在りえない対象** | 存在しないパス、読めないパス、書けない先、空のファイル、壊れた設定 |
| **二度打ち・途中で止める** | 同じコマンドを続けて2回。長い処理を中断する。**中断のあとに何が残るか**(書きかけ・部分適用)を見る |
| **終了コード** | 成功は 0 か。失敗の種類ごとに区別が付くか。**`commands/` の「出力と終了コード」と食い違っていないか** |
| **エラーの読めかた** | わざと失敗させ、**出る文言が利用者に意味を持つか**(スタックトレース・生の英語エラー・沈黙は所見) |
| **`--help` と実物** | 説明されているオプションが実際に効くか。効かない・違う挙動をするものは所見である |
| **破壊的操作の意思確認(BR-05)** | 不可逆なことを起こすサブコマンドが、**何が起きるか・対象は何か**を示して確認を取るか |
| **版の名乗り(BR-12)** | 版を尋ねると `major.minor.revision` の形で返るか |
| **UX 文書との突き合わせ** | §1 の 4 で読んだ記述と実物が食い違っていないか。食い違いは所見(どちらが正かは裁定しない。文書側が古いだけなら重大度は通常「低」) |

**破壊的な操作をしてよいのは、`environments.md` が試験用と定めた隔離の中だけである。**

## 3. 返す

**`browser-qa/SKILL.md` §3 の形をそのまま使う**(重大度・再現手順・期待・実際・証跡)。
写さない — あちらが正である。**このレーンだけの違いは証跡の中身**で、
スクリーンショットの代わりに**打ったコマンドと、その標準出力・標準エラー・終了コードの逐語**を置く。

## 4. このレーンの終わり方

**`browser-qa/SKILL.md` §4 がそのまま掛かる**(重大度「高」がゼロで green、環境の不備なら red、
同じ範囲へ起こすのは最大2回)。**違いは適用外の理由だけである**:

- 「適用外(コマンドの面なし — 根拠)」を記録したときも green である(§0)。
- **★ 画面が無いことは、この試験区分が消える理由ではない**(2026-09-15 の裁定)。
  **qa 試験区分が丸ごと適用外になるのは、人が直接操作する面が1つも無いとき**
  (他のプログラムから呼ばれるだけの部品など)**だけである** —
  画面とコマンドの両方を持つ製品では**両方のレーンが走り、両方が green になって初めて
  qa が green になる。**
