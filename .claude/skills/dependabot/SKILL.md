# Dependabot アラートの仕分け — まとめて上げ、上がらなかったものだけを見る

対象: $ARGUMENTS。人間に向けた出力(報告)はすべて日本語で書く。

**このスキルの既定は「まとめて上げる」である。** アラートは数十件単位で上がるものであり、
**1件ずつ調べて1件ずつ直す形は、件数に比例して費用が伸びて必ず破綻する。** だから順序を逆にする:
**まず上げられるだけ上げる作業指示を作り、上げられなかったものだけを1件ずつ見る。**

**このスキルは依存を1バイトも更新しない。** 依存の更新は製品の振る舞いを変えるので、
**構築記録を伴う `/build` の仕事である**(CLAUDE.md §4 の小さな修正の例外は、依存の更新にも
最小の構築記録を要求している)。ここでやるのは**その手前**である。

**アラートを GitHub 上で閉じる(dismiss する)のも、このスキルの手には無い。** 「使っていない経路だから
無視する」は外から見える判断であり、後から戻すには再度の裁定が要る(`delegation.md` §1)。
**提案までを書き、押すのは人間である。**

## 0. 走る条件と、走らない場合 ★

**このスキルは追跡対象の木へ1バイトも書かないので、作業ブランチへ移らない** ★ —
`guard-branch.py` を打たない。読んで報告するだけの run が枝を作って切り替えるのは、
何も書かないのに git の状態だけを変える動きであり、適用外を返す前ですらそれが起きる。
**枝は、この後に走る `/build` が自分の入口で作る**(`flows.md` §7.1)。

**「GitHub 上のリポジトリか」は、道具の成否ではなくローカルの事実で決める** ★ —
`gh` の1つのコマンドが落ちる理由は、未ログイン・権限・通信・機能無効と何通りもあり、
**それを「GitHub 上に無い」と読むと、環境の不備を適用外と誤って報告する**:

```bash
command -v gh                       # 無ければ環境の不備(適用外ではない)
git remote -v | grep -i github.com  # **これが「GitHub 上か」の判定である**
gh auth status                      # どの資格情報で、どの権限で見ているか
```

| 症状 | 何が起きているか | 次の一手 |
|---|---|---|
| remote に `github.com` が無い | GitHub 上のリポジトリではない | **適用外**を宣言して終わる |
| `gh` が入っていない / 未ログイン | 環境の不備 | 人間へ渡して止まる |
| アラートの取得が `404` | 機能が無効か、権限が無くて存在も見えない | 環境の不備 — 有効化も権限も人間の手 |
| アラートの取得が `403` | 権限の不足 | 資格情報の**種別**を見る(下)。人間へ渡す |

**要る権限は資格情報の種別で違う。** 古い形式の個人トークンは `security_events`(公開リポジトリなら
`public_repo` でも読める)、細粒度のトークンはリポジトリ権限の `Dependabot alerts: read` である。
**環境変数の `GH_TOKEN` / `GITHUB_TOKEN` が在れば、`gh` が保存している資格情報より優先される** —
権限を足したのに何も変わらないときは、まずここを疑う。
**AI は自分の権限を広げない**(`gh auth refresh -s security_events` は人間が打つ)。

**適用外にできるのはただ1つ**: リポジトリが GitHub 上に無い。それ以外の「引けない」は
**すべて環境の不備**である — 黙って飛ばすと「アラートが無かった」と区別が付かなくなる。

## 1. 取り込む — 全件を、機械が読める形で1度に

```bash
# **置き場はこのセッションのスクラッチパッドである。`$$` を使わない** ★ —
# この節は分けて走らせたくなる作りなので、`$$` にすると2つ目のブロックが別の場所を見て
# 何も見つけられない(独立検査 2026-09-03)。**固定の名前にして、§1 の中では作り直さない。**
TMP="<このセッションのスクラッチパッド>/dependabot" && mkdir -p "$TMP/retry"

# **引数の形は `[severity] [--retry <番号,…> | --retry-report <パス>]` である。**
# **$ARGUMENTS を丸ごと写さない** ★ — **貼るのは、下の `set --` の1行だけ**である。
# **解析はここが行う。読み飛ばして空のまま先へ進んではならない** ★ — 空のまま進むと、
# 重大度の絞り込みも `--retry` も**黙って無視される**(独立検査 2026-09-03 に実測:
# 固定代入だけが書いてあったので、§4 の戻り口が一度も開かなかった)。
set -- $ARGUMENTS       # ← **ここだけが $ARGUMENTS に触れる。文字列として差し込まれるので、
                        #   シェル変数へ入れてから渡さない** — zsh は変数展開を語に割らないので、
                        #   丸ごと1語になって解析が全部外れる(2026-09-03 に3つのシェルで実測)
SEV_ARG=""; RETRY=""; RETRY_REPORT=""
while [ $# -gt 0 ]; do
  case "$1" in
    --retry)        [ -n "$2" ] || { echo "--retry に値が無い" >&2; exit 2; }
                    [ -z "$RETRY$RETRY_REPORT" ] || { echo "--retry と --retry-report は同時に渡せない" >&2; exit 2; }
                    RETRY="$2"; shift 2 ;;
    --retry-report) [ -n "$2" ] || { echo "--retry-report に値が無い" >&2; exit 2; }
                    [ -z "$RETRY$RETRY_REPORT" ] || { echo "--retry と --retry-report は同時に渡せない" >&2; exit 2; }
                    RETRY_REPORT="$2"; shift 2 ;;
    -*)             echo "知らない引数である: $1" >&2; exit 2 ;;
    *)              [ -z "$SEV_ARG" ] || { echo "重大度は1つだけである: $SEV_ARG と $1" >&2; exit 2; }
                    SEV_ARG="$1"; shift ;;
  esac
done

# **`--retry-report` は、前の run の報告から番号を読む。読む先は1行だけである** ★ —
# §5 の報告が出す `再取込: #<番号>,…` の行であり、**そこ以外から数字を拾わない**
# (本文の数字を拾うと、上げ終わったものを永久に戻し続ける)。
if [ -n "$RETRY_REPORT" ]; then
  [ -f "$RETRY_REPORT" ] || { echo "報告が読めない: $RETRY_REPORT" >&2; exit 2; }
  # **その行はちょうど1本でなければならない** — 2本在ったらどちらが正か決められない
  [ "$(grep -c '^再取込:' "$RETRY_REPORT")" = 1 ] \
    || { echo "報告の「再取込:」の行が1本ではない: $RETRY_REPORT" >&2; exit 2; }
  RAW=$(sed -n 's/^再取込: *//p' "$RETRY_REPORT")
  # **削る前に、生のまま書式を見る** ★ — 先に空白と # を消すと、**区切りの誤りが消えて
  # 別の番号に化ける**: 「再取込: #1 #2」(カンマ落ち)が 12 になり、#12 を取りに行く
  # (独立検査 2026-09-04 に3つのシェルで実測)。だから正規化は、書式が通った後だけ行う
  if [ "$RAW" = "なし" ]; then
    # **これは異常ではない** — 前の run で落ちたものが1件も無かった、という正当な結果である。
    # 戻す番号が無いだけなので、そのまま普通の run として続ける
    RETRY=""
  elif printf '%s' "$RAW" | grep -Eq '^#[0-9]+([[:space:]]*,[[:space:]]*#[0-9]+)*[[:space:]]*$'; then
    RETRY=$(printf '%s' "$RAW" | tr -d ' #')
  else
    echo "「再取込:」の行の書式が違う(「なし」か「#<番号>,#<番号>,…」): $RAW" >&2; exit 2
  fi
fi

case "$SEV_ARG" in
  critical) SEV='&severity=critical' ;;
  high)     SEV='&severity=critical,high' ;;
  medium)   SEV='&severity=critical,high,medium' ;;
  low|"")   SEV='' ;;
  *) echo "重大度は critical / high / medium / low のどれかである: $SEV_ARG" >&2; exit 2 ;;
esac
if [ -n "$RETRY" ] && ! printf '%s' "$RETRY" | grep -Eq '^[0-9]+(,[0-9]+)*$'; then
  echo "--retry は数字のカンマ区切りである: $RETRY" >&2; exit 2
fi

# **`--paginate` は1ページごとに別々の JSON 配列を吐く** ので、`--jq '.[]'` で1行1件にする。
# **途中のページが落ちたら止まる** — 部分的な一覧を全件だと思って仕分けないため、
# 成功したときだけ確定した名前へ移す
if gh api --paginate --jq '.[]' \
     "/repos/{owner}/{repo}/dependabot/alerts?state=open&per_page=100${SEV}" > "$TMP/alerts.part"
then mv "$TMP/alerts.part" "$TMP/alerts.jsonl"
else echo "取得に失敗した。HTTP の状態を報告して止まる" >&2; exit 1
fi

# **戻ってきた番号は、重大度の絞り込みとは別に、1件ずつ「丸ごと」取る** ★ —
# 絞り込みの外に在る番号も拾うためであり、§4 が使うのは生態系・マニフェスト・`scope`・勧告・
# `first_patched_version` であって、番号と名前だけでは何も調べられないからである。
# **1件でも取れなかったら止まる**(欠けた集合で仕分けない)
for n in $(printf '%s' "$RETRY" | tr ',' '\n' | sort -un); do
  # **alerts 側と同じ作法である** ★ — 落ちた応答(`{"message":"Not Found"}` など)を
  # 確定した名前に残さない。残すと、後から回した仕分けが `KeyError` で落ちる
  # (独立検査 2026-09-03 に実測)
  if gh api "/repos/{owner}/{repo}/dependabot/alerts/${n}" > "$TMP/retry/${n}.part"; then
    mv "$TMP/retry/${n}.part" "$TMP/retry/${n}.json"
  else
    rm -f "$TMP/retry/${n}.part"
    echo "戻ってきた番号 #${n} を取得できなかった。HTTP の状態を報告して止まる" >&2; exit 1
  fi
done

# 3つの集合と、どの集合にも入らないもの(既に閉じている番号)を、ここで確定させる
python3 - "$TMP" <<'PY'
import json, os, sys
tmp = sys.argv[1]

def row(a):
    d, v = a["dependency"], a["security_vulnerability"]
    return "\t".join([
        str(a["number"]), a["security_advisory"]["severity"],
        d["package"]["ecosystem"], d["package"]["name"],
        d.get("manifest_path") or "-", d.get("scope") or "-",
        (v.get("first_patched_version") or {}).get("identifier") or "パッチ未提供",
        a["security_advisory"].get("cve_id") or a["security_advisory"]["ghsa_id"],
    ])

retried, closed = {}, []
rdir = os.path.join(tmp, "retry")
for f in sorted(os.listdir(rdir)):
    a = json.load(open(os.path.join(rdir, f)))
    if a["state"] == "open":
        retried[a["number"]] = a
    else:
        closed.append(a)

bump, stuck = [], []
for line in open(os.path.join(tmp, "alerts.jsonl")):
    if not line.strip():
        continue
    a = json.loads(line)
    if a["number"] in retried:
        continue
    v = a["security_vulnerability"]
    if (v.get("first_patched_version") or {}).get("identifier"):
        bump.append(a)
    else:
        stuck.append(a)

for label, group in (("戻ってきたもの → 4", list(retried.values())),
                     ("上げられるもの → 2", bump),
                     ("上げられないもの → 4", stuck)):
    print("# " + label)
    for a in group:
        print(row(a))
print("# 対象外(--retry で渡されたが、既に閉じている)")
for a in closed:
    # **`state` を必ず出す** ★ — `fixed` と `dismissed` / `auto_dismissed` を混ぜてはならない
    print(a["number"], a["state"], a["dependency"]["package"]["name"])
PY

# 版上げの PR が既に立っていないか。**`gh pr list` は上限を持つので、`--paginate` で全部取る**
# (「大量に上がる」ことを前提にしたスキルが、固定の上限で黙って取りこぼしてはならない)
gh api --paginate '/repos/{owner}/{repo}/pulls?state=open&per_page=100' \
  --jq '.[] | select(.user.login == "dependabot[bot]") | [.number, .title] | @tsv'
```

**ここまでで、互いに重ならない3つの集合ができる** ★ — どのアラートも必ずどれか1つに入る:

| 集合 | 条件 | 行き先 |
|---|---|---|
| 戻ってきたもの | `--retry` で渡され、いま open | **§4**(版が在っても §2 へは入れない) |
| 上げられるもの | 上に入らない open で、`first_patched_version` が在る | **§2** |
| 上げられないもの | 上に入らない open で、`first_patched_version` が無い | **§4** |

**どの集合にも入らないものが2つ在り、どちらも黙って消えてはならない**:
`--retry` で渡されたが**既に閉じている**番号は「対象外(既に閉じている)」として報告に1行出す。
**`state` を必ず添えて、`fixed` と `dismissed` / `auto_dismissed` を区別する** ★ —
前者は向こうで直ったということだが、**後者は人間が握り潰しただけで、直っていない。**
混ぜると、直っていないものが「直った」として報告され、しかも open ではないので
次の run でも §4 に来ない — **このスキルが「台帳は GitHub 側」に賭けている当のものが静かに落ちる**
(独立検査 2026-09-03)。**取得できなかった番号は、仕分けそのものを止める** —
欠けた集合で束ねると、落ちた分が誰の仕事でもなくなる。

**`manifest_path` と `first_patched_version` が、次の2つの節の入力である。**
この2つを落とした一覧は役に立たない。
**取り込んだ出力はセッションのスクラッチパッドに置き、追跡対象の木には残さない。**

## 2. まとめて上げる — 束ねる単位は「同時に動くファイルの最小集合」★

**`first_patched_version` が在るものは、調べる前にまとめる。** 届いているかを1件ずつ確かめるのは、
**上げられなかったものだけの仕事である**(§3)— 上げてしまえば、その問いに答える必要が無い。

**ただし、`--retry` で戻ってきたものは、版が在ってもここへ入れない**(§1 の3つの集合)★ —
版が在るという理由だけでまた束ねると、**同じものが毎回束ねられては同じ理由で落ちる輪**になり、
§4 へ永久に届かない。`--retry` も `--retry-report` も渡されていない run では、この除外は空である。

束ねる鍵は、**その更新で同時に動くマニフェストとロックファイルの最小集合**である:

- ロックファイルが在る生態系(`package-lock.json`・`poetry.lock`・`go.sum`・`Cargo.lock` …)
  → **共有するロックファイルが鍵**。同じロックファイルを動かすものは、必ず同じ1本に入る。
- ロックファイルを持たない構成(Maven の `pom.xml`、lock を採らない pip など)
  → **マニフェストが鍵**。

**2本の `/build` が同じファイルを触ることはできない**(CLAUDE.md §4 の並走の規則)ので、
**この鍵を共有するものを分けてはならない。** 鍵が違うものは**別の作業指示の候補**である —
**「並走できる」とは書かない** ★: 版が設定文書や機械の欄に現れる構成では、鍵が違っても同じ
文書を2本が動かしうる。**並走の可否をこのスキルは決めない** — **艦隊運用なら**それは
非交差の証明であり `@triage` の仕事である(CLAUDE.md §4。**「艦隊運用なら」を落とさないこと** —
掲示板の無い運用では `@triage` が居ない)。**艦隊でないなら、作業指示を起こす側が行う。**このスキルは、各作業指示が動かすと見込むファイルの集合を添えて渡すところまでを行う。

**major を跨ぐ更新も、鍵が同じなら同じ1本に入れる。** 別の作業指示にはできない。代わりに、
**その1本の中で独立したコミットにし、コミットごとに試験を通す**よう作業指示に書く —
こうしないと「どれが壊したか」が答えようのないものになる。

## 3. 記録は増やさない — アラートの台帳は GitHub 側である ★

**このスキルは `docs/issues/` にも `docs/pendings.md` にも `docs/residual.md` にも1行も書かない。**
アラートは GitHub 上に一覧として在り、直れば向こうで閉じる。**それをこちらへ写すと、
同じものを2箇所で管理することになり、写した側は必ず古くなる**(`conventions.md` §4。
2026-09-03 の人間の指示)。

- **上げられたものの記録は、`/build` が書く構築記録1本である** — それは「GitHub が知っている
  警告」ではなく「こちらが実際に動かしたもの」の記録なので、写しではない(CLAUDE.md §4)。
- **上げられなかったもの**(パッチ未提供 / 上げると製品が壊れる)は、**GitHub 側に open のまま残る。
  それが台帳である。** こちらは §5 の報告で1行ずつ名指すだけで、ファイルを作らない。
- **このスキルは出荷してよいかの判定に一切関わらない** ★(2026-09-03 の人間の指示:
  「ひとまず、出荷判定とは全く別にしたい」)。**このスキル自身は**デプロイゲート
  (`stamps.py check`)の入力へ何も足さない。**そこから先まで言わないこと** ★ —
  ここで作ったものを `/build` が実行すれば、構築記録が1本増え、触ったマニフェストと
  ロックファイルが `code_roots` に在るぶん鮮度スタンプが失効する。
  **それは普通の `/build` と同じであって、この例外によるものではない**
  (だからリリースの直前に配ると、検証の周を1本余計に払う)。**重大度を裁定して人間に決めさせる段も作らない** — このスキルの目的は
  **人間が労力をかけずに脆弱性が減っていくこと**であり、判断を1つ増やすたびにその目的から遠ざかる。
- したがって、上げられなかったものについて報告に書くのは**事実の1行だけ**でよい:
  どのパッケージが、なぜ上がらなかったか(パッチ未提供 / 上げると壊れる)。
  **どう扱うかを人間に問わない**(次の run で自動的に §4 の対象になる)。

## 4. 上げられなかったものだけを、1件ずつ見る

ここへ来るのは、§1 の3つの集合のうち**「戻ってきたもの」と「上げられないもの」の2つ**である ★ —
束ねて上げる形は、
必ず一部が落ちる。**落ちた分の戻り口はここであり、依頼元は番号を次の run へ渡すことでそれを開く。**
渡す口が無ければ、落ちた分は毎回また束ねられて同じ理由で落ち、誰の仕事でもなくなって消える。

その2種類について、次を確かめる。**ここで初めて、届いているかを調べる:**

| 確かめること | どう確かめるか |
|---|---|
| 直接の依存か、推移的か | 依存ツリー(`npm ls <pkg>` `pip show` `go mod why` `cargo tree -i` 等) |
| 製品に載るか、開発時だけか | アラートの `scope` と、マニフェストのどの節に在るか |
| 脆弱な機能に届いているか | 勧告が名指す関数・機能をコードから grep する。**届いていないと言うなら、その grep を報告に逐語で書く** |
| 回避できるか | 呼び出し側で塞げるか、別の実装へ替えられるか |

**「たぶん使っていない」は事実ではない。** 確かめられないなら、確かめられなかったと書く。
**推移的な依存は、直接の依存を上げて解く**のが既定である。上書き(`overrides` / `resolutions` /
`replace` 等)へ倒すかは、**`delegation.md` §1 の2条件と例外に掛ける** — 外から見える変化が無く、
後続タスクの普通の変更で戻せるなら `/build` が決めて開示し、通ったときだけ人間へ出す。

## 5. 返す — 作業指示と、上がらなかったものの一覧

**成果物は、束ねた `/build` の作業指示である。** 1本ごとにこう書く:

```
/build <生態系> の依存をまとめて更新する(Dependabot アラート #<番号,…> — <n> 件)
- 上げるもの: <パッケージ> <現在の版> → <目標の版>(まとめて列挙。1行1件)
- 動かすと見込むファイル: <マニフェスト>[ と <ロックファイル>](並走の可否はこの集合で判定される)
- 破壊的変更の可能性: <major を跨ぐものだけ名指す。無ければ「無し」>
  major を跨ぐものは独立したコミットにし、コミットごとに試験を通す
- 完了の条件: **ロックファイルが在る構成**なら目標の版がロックファイルで解決していること。
  **無い構成**(Maven の `pom.xml` など)ならマニフェストと実際の依存ツリー
  (`mvn dependency:tree` 等)で目標の版が解決していること。加えて、
  触ったモジュールの試験が green・build/lint が green
- **落ちたときの手当て**: 解決や試験が落ちたら、**落ちた原因のパッケージだけを外して残りを通す。
  外したものは作業指示を分けず、報告に「上げられなかったもの」として名指して返す**
  (依頼元がそれを `/dependabot` の次の run の §4 に掛ける)
- **仕様ドキュメントは、通常1バイトも動かない** — 依存の版は設計の記述ではないからである。
  動くのは、その版が文書に事実として書かれている場合だけで、そこが機械の欄なら
  `python3 .claude/scripts/build-facts.py update` が作り直す(CLAUDE.md §7)。
  **版が上がっただけで設計を書き直さない。**
```

- **アラートが閉じたことを、この作業指示の完了条件にしない** ★ — Dependabot が走査するのは
  **既定ブランチ**であり、作業ブランチでマニフェストとロックファイルを直しても `state` は動かない。
  閉じたことの確認は**既定ブランチへ merge した後**であり、依頼元か人間が
  `gh api /repos/{owner}/{repo}/dependabot/alerts/<番号> --jq .state` で行う。
  これを完了条件に書くと、正しく直した `/build` が永久に終われなくなる。
- **Dependabot が既に PR を立てているものは、その PR 番号を作業指示に書く。** 中身を取り込むのは
  `/build` の仕事であり、**PR をそのまま merge する経路は使わない** — 構築記録も、触ったモジュールの
  試験も、`stamps.py` の失効も、そこを通らないからである。

報告そのものは短くてよい:

```
Dependabot アラート <n> 件(critical <a> / high <b> / medium <c> / low <d>)
まとめて上げる: 作業指示 <k> 本(鍵: <ロックファイル / マニフェスト>、各 <件数> 件)
上がらなかったもの <m> 件: #<番号> <パッケージ> — <理由(パッチ未提供 / 上げると壊れる)>・<届いているか>
再取込: #<番号>,#<番号>,…
```
**最後の行は機械が読む** ★ — `--retry-report` はこの1行だけから番号を拾う(§1)。
**上がらなかったものが0件なら、この行を `再取込: なし` と書く**(行ごと消さない —
消すと、次の run が「報告に行が無い」で止まる)。

- **1件も上がっていないのは正当な結果である。** そのときは、取得が返した件数が 0 だったことを
  書いて終わる(**確かめずに「無い」と書かない**)。
- 艦隊運用なら、報告本文は **40 行 / 2000 バイト**以内で、明細はパスで渡す
  (`orchestration.md` §5)。

## 6. 禁止

- 依存を自分で更新すること、Dependabot の PR を merge すること(§0・§5)。
- GitHub 上でアラートを dismiss すること、`gh auth refresh` で自分の権限を広げること(§0)。
- **アラートを `docs/issues/`・`docs/pendings.md`・`docs/residual.md` へ写すこと**(§3)。
- 上げられるものを1件ずつの作業指示に割ること、鍵を共有するものを2本以上に分けること(§2)。
- アラートが `fixed` になることを `/build` の完了条件にすること(§5)。
- 依存の版が上がったことを理由に仕様ドキュメントを書き直すこと(§5)。
- 上げられたものについて、届いているかを調べること — それは §4 だけの仕事である(§2)。
- `gh` の1つのコマンドが落ちたことを「適用外」と読むこと(§0)。
