# キットの改善 — ここでキットを直し、その差分を本流へ戻す

出力はすべて日本語で書く。

**このスキルの成果物は、本流まで運ばれた1本のパッチファイルである。**
キットを編集してそこで止まるのは、部分的な成功ではなく**このスキルの失敗である**:
プロジェクトの `.claude/` は展開されたコピーであり、**次の配布物がそれを上書きし、改善は失われる。**
キットは自分がどの配布物から来たかを記録している(`.claude/kit-manifest.json`)が、
**その後あなたが何を変えたかは一切記録していない** —
`kit-patch.py` の控えだけが、それを供給している。

**前提は、このプロジェクトが本流と歩調を合わせ続けることである。** 1改善 = 1パッチであり、
できたらすぐ本流のリポジトリの `inbox/` へ**移す**(複製ではない)。本流は別のホストに在ってよい。
**そのファイルをどう運ぶかは人間の領分であり、このスキルはそれを決して指定しない**
(転送のコマンドを決して名指さない — この環境が何を使っているか知りようがない)。
固定されているのは、**それが移動であること**である。だからプロジェクト側に複製は残らない。
**ここに留め置かれた改善は、次の配布物が消す改善である。**
キット自身の帳簿づけで人間の記憶に頼るものは1つも無い:
`kit-patch.py` が自分で控えを取り直し(§1)、パッチを書いたときに改善の作業跡を消す(§4)。

## 0. そもそもこのスキルは走ってよいのか?

**時期による制限は無い**(完了定義による凍結は 2026-08-22 に廃止した。`.claude/directions/core.md` §3)。
代わりに**縛りが2つ**在る(`.claude/directions/core.md` §3)。**確かめる時点が違う**:
**汎用の縛りはファイルに1バイトも触れる前に、検証の縛りはパッチを書き出す前に**確かめる。
(**番号で呼ばない** — `条件1 / 条件2` は「人間に問うてよいか」の予約語であり、
`glossary.md` §2 が、レベルの違うものに同じ語を当てることを禁じている。)

**汎用の縛り — その直しは汎用的か。** このキットを配る**どのプロジェクトでも成り立つ**ものだけが
キットに入る。判定は1問である: **別のプロジェクトへそのまま配って、同じように効くか。**
効かないなら、それはキットの改善ではなく**このプロジェクト固有の改造**であり、行き先は
`docs/` か `*.local.json` である(`conventions.md` §1)。
**紛れ込みは、パッチを書き出すときの分類 [その他] が名指す。だが、そこで気づくのは遅い** —
パッチを書いた後だからである。
迷う例と、その振り分け:

| 直そうとしているもの | 汎用的か | 行き先 |
|---|---|---|
| 検査スクリプトが正しい書き方を誤って落とす | **汎用的** | キット |
| 規範の節どうしが矛盾している / 手順が抜けている | **汎用的** | キット |
| このプロジェクトのモジュール名・ディレクトリ構成に合わせた閾値や除外 | 固有 | `*.local.json` |
| このプロジェクトの業務の都合で規範を緩めたい | 固有 | `docs/` の決定として記録する |

**検証の縛り — 検証を通していない変更を、キットに残さない。** 「あとで確かめる」を禁じる縛りだが、
**編集より先に検査を走らせることはできない**(検査する現物がまだ無い)。だからこの縛りが縛るのは
順序ではなく**出口**である: §2 で直したら、**§3 の自己検査と独立の検査を通すまでパッチを
書き出さない**(§4 へ進まない)。下限は §3(コンパイル・selftest・`check-kit-refs.py`)であり、
**それに加えて独立の検査を1本**通す — 艦隊運用なら `@review`、単体なら codex か、文脈の空いた
サブエージェント。**自分で読み返すことは独立の検査ではない**(書いた本人には、自分が置いた前提が見えない)。
**通らなかった変更は戻す** — 直したまま置いて「あとで見る」にしない。
検査に何を走らせ、独立の検査が何を言ったかは、§5 の報告に1行ずつ載せる。

**汎用の縛りを満たさないなら、キットを編集しない。検証の縛りを満たさないなら、その変更を戻す。**
今は手を付けないと決めたなら、案は `docs/residual.md` の1行として残す(書いたら `python3 .claude/scripts/doc-health.py --rotate` を打つ。`issues-pendings.md` §2.1 (2))—
**書かなかったという事実が記録である**(§2)。
**ファイルに触れる前に汎用の縛りをどう満たしたかを述べ、パッチを書く前に検証の縛りを
どう満たしたかを述べる。**

`docs/` がキットの変更の一部になることは決してない。
**製品の文書を運ぶパッチは、より大きな改善ではなく、範囲の誤りである。**

**`tests/` の中も、この経路では配布元へ戻らない** ★ — テストの土台(宣言ファイル・
環境スクリプト・テストコード)は**配布物2として一度だけ配られ、以後はプロジェクトのもの**
なので、キットの差分には**何も出ない**。ここを直して「戻したつもり」になると、
**配布元にもこのプロジェクトにも、戻っていないことが誰にも分からない。**

**他のプロジェクトにも効く改善だと思ったら、パッチではなく言葉で人間に伝える** —
「`tests/scripts/bootstrap.sh` のこの直しは、どのプロジェクトでも要るはずだ」のように、
**何をどう直したかと、なぜ一般に効くのかを報告に書く。** 運ぶのは人間である。
黙っていると、その改善はこの1つのプロジェクトの中で終わる。

## 1. 控えの状態を見る(最初の編集の前に)

```bash
python3 .claude/scripts/kit-patch.py status     # これ1つ。控えが無い/前の版ならここで取り直す
```

`diff` は控えと現物を比べるので、**編集した後に取った控えは、空のパッチと「差分なし」を生む** —
これは**最初の編集の前に**、必ず走らせる。

印字されたものを読む。**各行には次の一手がちょうど1つ在る**:

| status の行 | 意味 | 次の一手 |
|---|---|---|
| パッチの置き場: `<絶対パス>` | §4 のパッチがここにできる(まだ無くても出る) | 報告(§5)にはこの絶対パスを使う |
| 控え: 無かったので今の姿を控えた | 初回。ここが基準 | そのまま §2 へ |
| 控え: 前の版のものだった…ので取り直した | 新しい配布物を展開した後。控えは自動で更新済み | そのまま §2 へ |
| 未回収の変更 n 件 | **前回の改善が本流へ戻っていない** | 先に §4 の `diff --slug` で出し切り、本流へ渡す。今回の編集はその後 |
| 未転送のパッチ n 本 | パッチが手元に残っている = 渡していない | §5 の形で人間に運んでもらう(移動)。渡すまで次の改善を始めない |

**「控えを取り直す」という人間の判断は存在しない**(旧 `snapshot --force` は廃止した — 意味を
覚えていられない操作は忘れられ、忘れると過去の変更が相乗りしたパッチが出る)。取り直しは
`diff` の成功時と、配布物の入れ替わりを見た `status` が行う。

既に編集してしまい控えが無いときだけ、配布物を基準に後追いで記録する:
`kit-patch.py snapshot --from <展開に使った tarball>` → §4 の `diff`。
**渡す版はこのプロジェクトが展開した版であること**(違う版を渡すと、他人の変更が自分の
パッチに乗る)。tarball が手元に無ければ、その旨を人間に報告して指示を仰ぐ — 推測で代用しない。

## 2. キットを直接編集する

`CLAUDE.md` / `.claude/` をその場で編集する。**提案メモを溜めない**:
適用されなかった改善は、**適用されなかったという事実によって記録されている。**
変更は最小限にとどめ、**その変更が古くするすべての規範とスクリプトを報告で名指す。**

`.claude/improvements/` が持つのは**引き渡す途中のパッチだけ**である。改善についてのメモ・草稿・
作業ログは本流へ運ばれず、**`diff` がそれらを消す**(§4)—
人間に知らせる必要があるものは §5 の報告へ入れるのであって、
**パッチより長生きするファイルへ入れるのではない。**

**本流のリポジトリ(`claude-md/<kit>/`)へ決して書かない。** 設計上ここからは手が届かず、
そこでパッチを当てるのは人間の段である(§5)。

## 3. パッチの前の自己検査

変更が触れたものを走らせ、**何を走らせたかを述べる**:

```bash
python3 -m py_compile .claude/scripts/<changed>.py      # スクリプトを直したとき
python3 .claude/scripts/<changed>.py --selftest         # selftest を持つものは必ず(下の例外を読む)
python3 .claude/scripts/check-kit-refs.py               # 規範の節・原則番号・パスを直したとき必須
python3 .claude/scripts/test-kit-scripts.py            # ★同梱の道具の自己検査。無条件で打つ
```

**最後の1行を「`.py` を直したときだけ」にしない** ★ — `kit-patch.py` の自己検査は
**隣の実物の `kit-dist.json` を読む**ので、**あの JSON を直しただけでも落ちる。**
「直したファイル」を見て打つ相手を選ぶと、そこを取りこぼす。

**2行目の例外は1つだけ在る** ★ — 直したのが `kit-migrate.py` / `kit-patch.py` /
`kit-manifest.py` のどれかなら、**その道具の個別の `--selftest` は省いてよい。**
`test-kit-scripts.py` が、**同じ3つに同じ `--selftest` を同じように打つ**からである
(同じ検査を二度打つことになる)。**省いてよいのはその3つだけで、他の道具は従来どおり
個別に打つ。一括検査そのものは省かない**(無条件のままである)。
**省けるのは、一括検査を打った後に1バイトも直していないときだけである** — 直したなら
打ち直す。**どちらを打ったか判らないなら、個別にも打つ。**

**そして §0 の検証の縛りが要求する独立の検査を、ここで通す**(艦隊なら中央へ要求して
起こしてもらう `@review` — 形は `orchestration.md` §1.2。単体なら codex か文脈の
空いたサブエージェント)。渡すのは**変更した現物のパスと、何をなぜ変えたか**であり、
**あなたの結論を渡さない** — 結論を渡された検査は、それを確かめる検査ではなく、
それに同意する検査になる。**指摘は直してから §4 へ進む。**

**`.claude/directions/baseline.md` を触ったなら、独立の検査の観点に
`baseline.md` §5 を必ず入れる** ★ — 「この一覧を言い直している写しが、キットのどこかに
増えていないか」である。**これを毎回明示するのは、機械が見つけられない型だからである**
(実測: 基本要件の項目を足した直近3回すべてで、同型の直し忘れが独立検査に拾われた)。
項目を足した/廃止したなら、**費用の一覧は `baseline.md` §4 が持つ。**

スクリプトの改名・削除は、`.claude/settings.json` の項目(許可リスト)と
`.claude/tools-readme.md` の行も要る。**本流の `make check` が両方を強制する** —
そこで捕まえさせるということは、**パッチが跳ね返ってくる**ということである。

## 4. パッチを書き出す ★これが成果物

```bash
python3 .claude/scripts/kit-patch.py diff --slug <slug>
```

**パッチがどこに落ちるかは道具の決定であって、あなたの決定ではない**: `--slug` は
キットの根の下の `.claude/improvements/patches/KIT-<slug>.patch` へ書き、**絶対パスを印字する。**
その印字されたパスを報告(§5)へ**逐語で写す** — 出力から読んでいないパスを打ち直してはならない。
(`status` は編集する前から同じ場所を印字するので、「どこにできるのか」の答えは常に画面に在る。
`-o <FILE>` は一度きりの宛先のために残っている。**この2つは排他である。**)

- `<slug>` は改善の内容を表す英小文字ハイフン。1つの改善 = 1本のパッチ。
- **パッチの先頭に `# キット: <名前>` が入る**(`kit-dist.json` の `kit` から)。本流にはキットが
  複数在って同じ名前のファイルを持つので、**これが無いと当てる人間が総当たりで宛先を探すことに
  なる**(2026-08-22 に実際に起きた)。この行が出ていないと `diff` が注意を印字する。
- 出力の**控えの日時**を読むこと。今回の改善の開始時刻と合わないなら、過去の変更が相乗り
  している(§1 に戻る)。
- 分類に **[その他]** が出たら、キットの構成要素として分類できなかったもの =
  プロジェクト固有の改造が混ざっている疑い。名指しで報告する。
- 「差分なし」と出たら、それは成果物が無いということである。§1 の控えの取り違えを疑い、
  **パッチができないまま完了と報告しない**。

書けた時点で `diff` が2つの後始末を済ませる。**どちらも報告に1行で載せる**:

- **控えを取り直す** — 今の姿が次の改善の基準になる。ゆえに**このパッチを渡さなければ、この改善は
  もう差分に出ない**(出し直しは `snapshot --from <展開に使った tarball>` だけ)。§5 は省略できない。
- **改善の作業跡を削除する** — `.claude/improvements/` の `*.patch` 以外を消す。消したファイルは
  名指しで出るので、そのまま報告に写す。

## 5. 報告 — 人間がパッチを本流へ運び、当てる

**パッチはこのプロジェクトを出なければならない**: 本流はたいてい別のホストに在り、
このプロジェクトからは手が届かない。人間に**両方の段を逐語で渡す** — 先に運搬、次に適用:

> キットの改善をパッチにしました(変更 n 件 / 控え <日時>)。**できたパッチはここです**:
>
> ```
> <diff が出力した絶対パス>
> ```
>
> 1. このファイルを本流のリポジトリの `inbox/` へ**移して**ください(転送手段はお使いのもので
>    構いません。同じホストなら `mv`):
>
>    `<上の絶対パス>` → `<claude-md のパス>/inbox/`
>
>    **複製ではなく移動**です — 渡したらこちら側からは消してください。残っている間は
>    `kit-patch.py status` が「未転送のパッチ」としてその絶対パスを出し続けます。
>
> 2. 本流(claude-md)側で当ててください:
>
> ```bash
> make patch DRYRUN=1   # inbox/ のパッチが当たるかだけ見る
> make patch            # 当てる
> python3 sysdev-multi/.claude/scripts/kit-manifest.py update --root sysdev-multi   # ★これを飛ばさない
> ```
>
> **どのキットへ当てるかの指定は要りません** — パッチの先頭に `# キット: <名前>` が
> 刻んであり、当てる側がそれを読んで宛先を決めます(違う宛先を指定すると、その場で
> 止まります)。
>
> **マニフェストの作り直しを飛ばさないでください** — キットのファイルが1バイトでも
> 変われば、次の `make check` が「マニフェストが古い」で必ず落ちます(`make patch` は
> 作り直しません)。
>
> 当てた後は本流で `make check` → コミット → `make` で配布物を作り直し、このプロジェクトへ
> 展開し直してください。**控えの取り直しは要りません**(次の `status` が自動でやります)。
>
> 3. **展開し直した直後に、`docs/` を廃止語で1回だけ掃いてください**(§5.1。これはプロジェクト側の
>    1手です):
>
> ```bash
> python3 .claude/scripts/kit-manifest.py check   # 入れ替わりで消えた/取り残されたスキル・スクリプトの名が出る
> grep -rn '<その名>' docs/                        # 名ごとに1回
> ```

そのうえで1行ずつ並べる: 何をなぜ変えたか、何が古くなったか、§3 で何を走らせたか、
**独立の検査が何を言い、それをどう直したか**(§0 の検証の縛り。「所見なし」もそう書く —
書かれていない検査は、走らせなかった検査と見分けが付かない)、
そして `diff` が何を消したか(§4)。

## 5.1 配布物を入れ替えた後の掃引 — 廃止語が `docs/` に残る

**入れ替えでスキルやスクリプトが消えても、`docs/` はそれを現在形で参照したまま残る。** 2026-08-20 の
実測では、廃止スキル・廃止スクリプトの**現在形参照が11箇所**あり、そのうち `docs/README.md` は
**規範の逆**(「SSOT を直接書き換える作業は存在しない」)を人間の入口で述べていた。拾ったのは
偶然通りかかった `/verify-docs` である。

- 名の出どころは `kit-manifest.py check`(取り残し・欠落・管理外)。名ごとに `grep -rn <名> docs/`。
- **直すのは現在形の参照だけ**。`docs/README.md` は人間の入口なので最初に見る。
- **過去形の来歴は違反ではない** — `<!-- 来歴: 突き合わせ対象外 -->` の印が付いた節はそのまま残す
  (`conventions.md` §1)。2026-08-20 は 27箇所の過去記録を正しく残している。
- 掃引の書き込み先は `docs/` なので、**このスキルの仕事ではない**: 直しは `/build`(クロージャ内)か
  `/verify-docs` の自動修正が持つ(原則1)。**このスキルが負うのは、上の1手を §5 の引き渡し文に
  必ず載せること**である。

## 6. 禁止

- キットを編集したのにパッチを書かないまま run を終えること(§4)。
- **パッチがどこに在るかを言わずに**報告すること — 道具が印字した絶対パスである(§4)。
- 運搬の段を人間に渡さないまま run を終えること(§5)— このプロジェクトに留まったパッチは
  次の配布物が消し、**控えは既にそれを追い越している。**
- `status` を読む前に編集すること。古いと分かっている控えを、そう言わずに使い回すこと(§1)。
- 変更の代わりに、あるいは変更に加えて提案メモを書くこと(§2)—
  `.claude/improvements/` は、運搬中のパッチ以外の何かを置く場所ではない。
- 未転送のパッチが `patches/` に残っているのに2つ目の改善を始めること(§1)—
  **1箇所に2本のパッチが在ると「どれが未反映か」が答えようのないものになる。**
- 本流を編集すること。あるいは人間にリポジトリの根で裸の `git apply` を打つよう伝えること —
  それは作業コピーの `.claude/` を宛先にするのであってキットではなく、
  **変更は黙って出荷されないままになる。**
- §5 の文に §5.1 の掃引の段を入れずにパッチを渡すこと — 配布物の入れ替えは、
  **消えたスキルとスクリプトへの現在形の参照を `docs/` に残し、他の誰もそれを探さない。**
- `docs/`・`*.local.json`・タスクの成果物をパッチに含めること(`kit-dist.json` の allowlist
  が構造的に落とすが、**落ちたことを成果と誤解しない** — 落ちた分は戻らない)。
