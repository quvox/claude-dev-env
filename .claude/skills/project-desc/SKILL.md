# 引き継ぎ資料 — `PROJECT_DESC.html` を1本作る

出力はすべて日本語で書く。

**このスキルの成果物は1つだけである: リポジトリ直下の `PROJECT_DESC.html`。**
読み手は**初めてこのプロジェクトの担当になった人間**であり、このキットの規範も、
このプロジェクトの用語も、作業の経緯も知らない。**その人がこの1ファイルだけを開いて、
プロジェクトの目的から現在の状況までを理解できること**が完成の条件である。

## 0. このスキルの位置づけ ★

- **フローの外に在る。書くのは `PROJECT_DESC.html` の1ファイルだけである。** `docs/`・製品コード・
  `tests/`・`.claude/` には1バイトも書かない。鮮度スタンプも記録しない。**git にも書かない** —
  コミットするかどうかは起動した側が決める(艦隊運用なら作業指示がそれを言う)。
- **この資料は仕様ドキュメントではなく、ある時点の写しである。** 写しは必ずずれる
  (`conventions.md` §4)。だからこの資料は**保守しない** — 次の3つでずれを読み手に見せる:
  1. **手で直さない。** 古くなったら、このスキルをもう一度走らせて**ファイルまるごと作り直す**。
     既存の `PROJECT_DESC.html` は読まずに上書きする(前の版の誤りを引き継がないため)。
  2. **冒頭に、作成した日時と、元にしたコミット**(`git rev-parse HEAD`)と、
     作成時点で**システムの中身**に未コミットの変更が在ったかどうか(§3 のコマンド。在れば
     そのパスを5件まで)を書き、
     「正は `docs/` の仕様ドキュメントであり、この資料はその時点の写しである」と明記する。
     **システムの中身とは、作業の管理に使う `.claude/`・`.agents/` と、この資料自身を除いたもの**である —
     艦隊運用の `.claude/missions/` のように作業中は常に未コミットになる置き場を数えると、
     毎回「在った」と出て、読み手はこの印を読まなくなる。
  3. **どのフローもスキルもこの資料を入力にしない。** `docs/README.md` を含め、仕様ドキュメントや
     規範からこの資料へリンクを張らない — 張ると、正が2つになる。
- **無人で走り、人間に問わない。** 確かめられなかったことを推測で埋めない(`CLAUDE.md` §1)。
  資料の中に「この資料の作成時点では確認できなかった」と書き、**何を見て見つからなかったか**を
  読み手の言葉で添える。
- **見つけた食い違いを直さない・裁定しない。** 仕様ドキュメントどうし、仕様ドキュメントとコードが食い違っていたら、
  資料には「食い違っている」とだけ書き(§2 の3)、**報告(§7)に両側の `path:line` を挙げる**。
  直すのは `/verify-docs` と `/verify-impl` であり、走らせるかは起動した側が決める。
- **艦隊運用の中央エージェントは、これを自分で走らせない** — `docs/` を読むスキルなので、
  作業指示として配る(`orchestration.md` §2)。

## 1. 何を書くか — 8つの項目と、それぞれの出どころ

**項目と順序は固定である**(§5 の構成がこの順に並ぶ)。「正として読む場所」が**いまの姿**であり、
資料の文はここから書く。「補う場所」は**なぜそうなったか**を説明するためにだけ読み、
そこから文を書くときは §2 の規則を通す。見出しの名前は雛形(`.claude/templates/`)のものである —
プロジェクトが見出しを変えていれば、同じ役目の節を探す。

| 項目 | 正として読む場所(いまの姿) | 補う場所(理由・経緯) |
|---|---|---|
| 1. このプロジェクトの目的 | `docs/00-requests/request.md` 「背景と目的」「やること」「やらないこと」「完成イメージ」 | `docs/00-requests/decisions/` の区分「決定」の「理由」 |
| 2. 想定している利用者 | `docs/00-requests/request.md` 「対象ユーザー」/ `docs/01-requirements/usecases.md` の各ユースケースの登場人物 | `docs/ux/policy.md`(在れば) |
| 3. システムアーキテクチャ | `docs/02-design/architecture.md` 「全体構成」「コンポーネントの責務」「データの流れ」「外部システムとの境界」/ `docs/02-design/system.md` 「モジュール分割定義」/ `docs/03-impl/feature-graph.md` | `docs/02-design/architecture.md` 「設計判断」/ `docs/02-design/system.md` 「分割の根拠」 |
| 4. システム構成(バックエンド・フロントエンド・ローカル開発環境・デプロイの道具と手順) | `docs/02-design/architecture.md` 「インフラ構成の設計」/ `docs/02-design/environments.md` 「セットアップ手順」「lint・テストコマンド」「コンテナ・実行環境」「CI」/ `docs/03-impl/environments/` / `docs/03-impl/infra/` 「構成図」「デプロイ手順」「シークレットの置き場所」/ `docs/01-requirements/system.md` 「実行環境の要件」「外部システム・サービスへの依存」 | `docs/03-impl/infra/` 「既知の制限・運用上の注意」 |
| 5. 開発言語(と主なフレームワーク) | **コードが正**: リポジトリに在る依存の宣言ファイル(`package.json`・`pyproject.toml`・`go.mod`・`Cargo.toml` など)と、`git ls-files` の拡張子の内訳 | `docs/01-requirements/system.md` 「開発言語・フレームワークの要件」(要件とコードが違えば §2 の3) |
| 6. 開発にあたって気をつけたこと | `docs/00-requests/decisions/` と `docs/01-requirements/decisions/` の区分「決定」/ `docs/02-design/architecture.md` 「設計判断」/ `docs/01-requirements/non-functional.md` / `docs/ux/policy.md`(在れば) | 決定の「理由」「見直す条件」 |
| 7. 絶対に譲れないこと | `docs/01-requirements/system.md` 「必須制約(交渉不可能)」/ `docs/00-requests/request.md` 「制約・前提」/ `docs/01-requirements/non-functional.md` で「不可分」とされた行 / 決定のうち「見直す条件」が「なし(恒久)」のもの | それぞれの「理由」 |
| 8. 現在のプロジェクトの状況 | `python3 .claude/scripts/stamps.py check` と `python3 .claude/scripts/check-debt.py` の出力 / `docs/build-records/` の各記録ファイルの frontmatter の `state`(**`index.md` は読まない** — 生成された目次であり、作り直されるまで各記録より古いことがある。どの層の `index.md` も、件数や状態の正にしない) / `docs/issues/` / `docs/pendings.md` / `docs/residual.md` / 各層の「未解決事項」/ `docs/00-requests/acceptances.md` | `git log` の直近の流れ / `.claude/missions/*/`(在れば) |

**項目 4 の4つの区分は、どれも省かない。** プロジェクトに無い区分(画面の無いシステムの
フロントエンドなど)は「このプロジェクトには無い」と、その根拠になる仕様ドキュメントの記述と一緒に書く。

**項目 8 は、機械の出力をそのまま貼らない。** 読み手の言葉に開く — たとえば
「公開してよいかを機械で判定する検査は、いま通っていない。理由は〈何が足りないか〉」
「作業ごとの記録のうち、作業中のものが n 件、検証待ちのものが n 件」
「見つかっていて、まだ直していない不具合が n 件(内容)」「意図して先送りした項目が n 件(内容と、いつ再開するか)」。

## 2. 生き残っている内容だけを書く — 作業の記録の精査 ★

**生き残っているかどうかの判定の基準は、いまの仕様ドキュメントとコードである。** 仕様ドキュメントは
「いまのシステムの姿だけ」を書く決まりなので(`.claude/directions/core.md` §1)、
**仕様ドキュメントとコードに在るものが生き残っており、記録にしか無いものは生き残っていない。**
作業の記録 — `docs/build-records/` の本文・`docs/histories/`・`docs/feedbacks/`・各層の `decisions/`・
`.claude/missions/*/` の要望台帳と台帳・`git log` — は精査するが、**そこから項目 1〜7 の文を書いて
よいのは、同じ内容がいまの仕様ドキュメントかコードに在ると `path:line` で確かめたときだけ**である。

**作業の記録を精査する目的は2つだけであり、読む量もこの2つで決まる**(§3 の E):
(a) **除いたものを人間が確かめられるようにする** — 退けた・取りやめた・置き換えた案を拾い、
§7 の「除いた主なもの」に挙げる。(b) **退けたはずの案が、いまの仕様ドキュメントやコードに
残っていないかを見る** — 記録が「取りやめた」と言う内容がまだ在れば、それは下の3の食い違いである。
**記録から項目 1〜7 の文を書き起こすことは無い**(理由と経緯は §1 の表の「補う場所」— 決定台帳と
設計判断 — から書く)。だから記録は頭から読み通さず、退けた・変えたことを述べる箇所だけを拾う。

**項目 8(現在の状況)だけは、いまの姿の置き場が違う** — 作業の状態は仕様ドキュメントにもコードにも
書かれない決まりなので、§1 の表の項目 8 の「正として読む場所」**そのものが**いまの姿である:
構築記録の frontmatter の `state`、`docs/issues/` に**いま在る**課題票(閉じた課題票はファイルごと
消える決まりである — `issues-pendings.md`)、`docs/pendings.md` と `docs/residual.md` に**いま在る**行、
各層の「未解決事項」、そして `stamps.py check` と `check-debt.py` の出力。**項目 8 はこれらから書き、
仕様ドキュメントとの突き合わせを求めない。** ただし構築記録の本文に書かれた内容(何をどう作ったか)は
作業の記録であって、項目 1〜7 へ持ち込むときは上の規則に戻る。

1. **書かないもの**(作業の記録に残っていても、いまの姿ではない):
   - 決定台帳の「却下した案」、設計判断が退けた案、機能表の「棄却した候補辺・確認済みの境界辺」
   - 見出しの直下に `<!-- 来歴: 突き合わせ対象外 -->` の印が付いた節(過去の記録であり、
     いまの姿ではない — `conventions.md` §1)
   - 要望台帳(`.claude/missions/*/requests.md`)や作業ごとの記録に在るが、いまの仕様ドキュメントにも
     コードにも着地しておらず、項目 8 の置き場(上の段落)のどこにも載っていない要望・案。
     **項目 8 の置き場に載っているもの — たとえば `docs/pendings.md` の先送り項目、作業中の構築記録 — は、
     項目 8 で「意図して先送りしたこと」「作業中のこと」として書いてよい**(いまも生きている状態である)
   - 書き換えられた古い決定・古い要求の文面 — 矛盾する新しい要求は古い文を書き換える決まり
     なので(`00-requests.md`)、記録に残る古い文面ではなく、いまの仕様ドキュメントの文面を読む
   - `git log` にしか無い変更(取り消されたコミット、後で消えたファイル)
2. **作業途中のもの**: 構築記録の `state` が `building` の作業は、項目 8 で「作業中」として
   何をしているかだけを書く。**その内容を、いまのシステムの姿として項目 1〜7 に書かない。**
3. **食い違い**: 記録といまの仕様ドキュメントが違えば、いまの仕様ドキュメントを書く。**仕様ドキュメントどうし、または仕様ドキュメントと
   コードが違い、どちらが正しいか判らないときは、どちらも断定しない** — 資料には
   「仕様ドキュメントでは〜、実装では〜となっており、作成時点で食い違っている」と書き、§7 の報告に挙げる。
4. **資料の段落ごとに、出典の `path:line` を手元に持つ。** 出典を言えない段落は書かない。
   出典の一覧(ファイル単位)は資料の末尾に置く(§5)。

## 3. 読み方 — 書く材料は自分で読み、探す・拾う読み取りは委ねる

`bulk-read` サブエージェントに委ねてよいのは、**多く読んで少なく返す**読み取りだけである
(`.claude/directions/core.md` §7。サブエージェントを持たないウィンドウは、艦隊運用なら中央へ
`@survey` を求める)。この資料の文は §1 の表の「正として読む場所」の**節の本文そのもの**から書くので、
その本文を委ねても、返ってくる量は読んだ量と変わらない — 委ね先は返し切れずに要約へ崩れ、
あなたは結局読み直すことになる。だから分ける:

- **書く材料の節は、あなたが自分で読む。** 下の A が返す行番号をもとに、§1 の表が挙げた節だけを
  行の範囲を指定して読む。**文書を頭から全部読まない。**
- **どこに在るかを探す読み取りと、大量の中から少しを拾う読み取りを委ねる。** 単位の例 —
  それぞれ独立に並べて出してよい:
  - **A. 節の在りか**: §1 の表が挙げた文書の、見出しの `path:line` と各節の行数(本文は返させない)
  - **B. 元の図**: `docs/02-design/` と `docs/03-impl/` の Mermaid のブロックを原文のまま、`path:line` つきで
  - **C. 決定**: 各層の `decisions/` の区分「決定」のエントリの、内容・理由・見直す条件の行。
    「却下した案」の行も原文のまま(案と却下の理由が1行に在る。書かないものを見分け、§7 で
    除いたものとして挙げるために要る)
  - **D. 状況**: `docs/build-records/` の各記録ファイルの frontmatter(`index.md` ではない)、
    `docs/issues/` の各ファイルの見出しと `closes_when:`、`docs/pendings.md`、`docs/residual.md`、
    各層の「未解決事項」
  - **E. 記録**(目的は §2 の (a)(b) だけ): `docs/build-records/*.md` の本文・`docs/histories/`・
    `docs/feedbacks/`・`.claude/missions/*/requests.md` と `ledger.md` から、**退けた・取りやめた・
    置き換えた・上書きした・見送ったことを述べる行を、前後2行つきで原文のまま**。語で本文を走査させる —
    たとえば 却下・不採用・取りやめ・やめる・廃止・撤回・退役・置き換え・差し替え・上書き・見送り・
    代わりに。記録の書きぶりに合わせて語を足してよい。**見出しだけで済ませない**(破棄された案は
    本文にしか書かれていない)。**語の走査は、別の言い回しで書かれた変更を取りこぼす** — だから
    同じ委任で、記録ファイルごとの見出しの一覧(`path:line` つき)も返させる。**判定は節ごとに行う** —
    見出しが方針の変更・やり直し・取りやめを示している節のうち、語の走査がその節の中で1行も
    拾えていない節は、あなたが自分で読む(同じファイルの別の節で語が拾えていても、その節は読む)。
    **記録の精査の網はこの2つであり、それより細かい取りこぼしは残りうる** — §7 の報告に、走査した語と、
    見出しを見て自分で読んだファイルを書く(人間が網の目の粗さを確かめられるように)
- **1つの委任が返す量は、引用で 400 行までにする。** 超えそうなら、文書の層ごと・ファイルの群ごとに
  分けて別の委任にする。`path:line` と原文の無い要約だけが返ってきたら、それは使わず、範囲を狭めて
  出し直す。

指示には**範囲と、返す形(`path:line` と原文の逐語引用)だけ**を書く。何を書くつもりかを渡さない。
**どれを生き残りと判定するか(§2)、どう書くか(§4)は委ねない** — それはこのスキルを走らせている
あなたの仕事である。

自分で直接打ってよいのは、出力が短い読み取りだけである:

```bash
git rev-parse HEAD                                       # 冒頭に書く「元にしたコミット」
git status --porcelain -- . ':(exclude).claude' ':(exclude).agents' ':(exclude)PROJECT_DESC.html' | head -5
                                                         # 冒頭に書く「システムの中身の未コミットの変更」(空なら無し)
git log --oneline -n 100                                 # 項目 8 の直近の流れと、§2 の (a)(b) の手がかり
python3 .claude/scripts/stamps.py check                  # 項目 8
python3 .claude/scripts/check-debt.py                    # 項目 8
# 項目 5: 製品のコードの拡張子の内訳。キットの道具(.claude/・.agents/)と文書(docs/)を除き、tests/ は別に数える
git ls-files -- . ':(exclude).claude' ':(exclude).agents' ':(exclude)docs' ':(exclude)tests' \
  | sed -n 's/.*\.\([A-Za-z0-9]*\)$/\1/p' | sort | uniq -c | sort -rn | head -15
git ls-files -- tests | sed -n 's/.*\.\([A-Za-z0-9]*\)$/\1/p' | sort | uniq -c | sort -rn | head -10
```

項目 5 には、文書や設定の拡張子(`.md`・`.json`・`.yml` など)を開発言語として数えない。`tests/` の
下には、テストを動かすために配られた道具が混ざりうるので、製品のコードの言語とは分けて書く。

## 4. 書き方 — 初めての人が、他のファイルを開かずに読める ★

この資料は**人間に読ませるために書くもの**なので、`delegation.md` §1.1 の4つの規則がそのまま掛かる。
加えて、読み手がこのプロジェクトに初めて触れる人であることから:

- **内部識別子を本文に出さない。** 要件や決定やモジュールの番号(英大文字とハイフンと数字の記号)は、
  このプロジェクトの中でしか通じない。**番号ではなく中身を書く。** どうしても出すなら、初出に丸括弧で
  中身を書く。
- **キットの言い回しを使わない。** 禁じる語の正は `.claude/directions/glossary.md` の「人」欄(★)と
  「使ってはならない表記」欄である。たとえば「仕様ドキュメント」は初出で「`docs/` の下に置いた、このシステムの仕様を書いた文書」と説明を添え、
  「構築記録」は「作業ごとの記録」、「デプロイゲート」は「公開してよいかを機械で判定する検査」と開く。
- **プロジェクトの用語**(`docs/00-requests/terminology.md`)は、本文の初出で1文の説明を添え、
  末尾の用語集にもまとめる。
- **略語は初出で正式な名前と意味を書く** — 一般的なもの(API・CI・DB など)も、初出で一言添える。
  **勝手に縮めた呼び名を作らない。**
- **曖昧な語・程度の語を使わない**(`conventions.md` §1)— 数・条件・具体例で書く。
- **結論から書く。** 各項目の冒頭に、3行以内の要点を置く。
- **項目 6・7 は、1件ごとに「何を」「なぜ」「破るとどうなるか」**を書く。理由が仕様ドキュメントに無いものは、
  理由が確認できなかったと書く(推測で理由を作らない)。

## 5. HTML の形

**1ファイルで完結する。** ネットワークに繋がっていない環境で開いても、印刷しても、同じものが読める:

- **外部の読み込みを一切持たない** — `<script src>`・外部のスタイルシート・Web フォント・外部の画像・
  CDN を使わない。スタイルは `<style>` に書く。**JavaScript は使わない**(図の描画も含めて)。
  別のサイトへのリンク(`<a href>`)は、読み込みではないので置いてよい。
- **図は手書きのインライン SVG で描く。** Mermaid は描画にライブラリの読み込みが要るので使わない —
  仕様ドキュメントの Mermaid 図は、**同じ要素と矢印のまま** SVG に描き直す。**仕様ドキュメントに無い要素を図に足さない。**
- **元の図どうしが食い違うとき**(同じ呼び出しが一方の図では実線・他方では破線、一方の図にしか無い要素):
  まず元の図それぞれの凡例と本文で、線の種類が何を意味するかを確かめる — 意味が同じで描き方だけが
  違うなら、食い違いではない。意味が違う、または確かめられないなら、2つの図を1つにまとめない。
  それぞれを別の図に描くか、まとめた図ではその線や要素を描かずに、本文で「〜の図では…、〜の図では…
  となっており、作成時点で食い違っている」と書き、§7 に挙げる(§2 の3)。
- **Mermaid の図が無い項目**(デプロイの手順・フロントエンドの構成など)は、**仕様ドキュメントの文から
  図を起こしてよい。** そのとき、図の箱・矢印・順序の1つずつに出典の `path:line` を手元に持つ(§2 の4)。
  文に書かれていない箱・矢印・順序は足さない。
- `<html lang="ja">`・`<meta charset="utf-8">`・`<title>` は「〈プロジェクト名〉の引き継ぎ資料」。

**構成はこの順で、見出しは固定である**(項目が空でも見出しを消さず、確認できなかったと書く):

0. 冒頭 — この資料の位置づけ(作成日時・元にしたコミット・未コミットの変更の有無・正は `docs/` の
   仕様ドキュメントであること・古くなったら作り直すこと)と目次
1. このプロジェクトの目的
2. 想定している利用者
3. システムアーキテクチャ
4. システム構成(バックエンド/フロントエンド/ローカル開発環境/デプロイ)
5. 開発言語
6. 開発にあたって気をつけたこと
7. 絶対に譲れないこと
8. 現在のプロジェクトの状況
9. 用語集
10. この資料の元になった文書(ファイルのパスの一覧と、それぞれに何が書いてあるかの1行。
    もっと深く知りたい読み手のための道案内である)

**図**: 3(アーキテクチャ)と 4(システム構成)には**図を必ず1つ以上**置く。他の項目は、
文だけでは関係が追いにくいときに置く。どの図も:

- 図の直後に、**図が言っていることを文でも書く**(図だけに情報を置かない)
- `<svg role="img" aria-labelledby="…">` と `<title>` を付ける
- 矢印の意味(呼び出し・データの流れ・デプロイの向き)を凡例か図の中の文字で書く
- **色だけで区別しない**(線の形や文字でも区別する)
- 図の中の名前は本文と同じ語を使う

## 6. 自己検査 — 書いたら確かめる

**機械の検査**(外部の読み込み・スクリプト・図の数・説明の無い内部識別子らしき記号・キットの言い回し)。
キットの言い回しの一覧は `check-sheet.py` が規範用語集から読むものをそのまま使う(写さない):

```bash
python3 - PROJECT_DESC.html <<'EOF'
import importlib.util, re, sys
from html.parser import HTMLParser
path = sys.argv[1]
src = open(path, encoding="utf-8").read()
class P(HTMLParser):
    def __init__(s):
        super().__init__(); s.skip = 0; s.text = []; s.ext = []; s.scripts = 0; s.svgs = 0
    def handle_starttag(s, tag, attrs):
        a = dict(attrs)
        if tag in ("style", "script", "title"): s.skip += 1
        if tag == "script": s.scripts += 1
        if tag == "svg": s.svgs += 1
        if tag != "a":   # <a href> は移動であって読み込みではない。それ以外の参照は相対パスも別ファイル
            for k, v in attrs:
                if k == "srcset" or (k in ("src", "data", "href", "xlink:href", "poster", "background")
                                     and v and not v.strip().startswith(("data:", "#"))):
                    s.ext.append(f"<{tag} {k}={v}>")   # srcset は候補が複数在るので値によらず数える
    def handle_endtag(s, tag):
        if tag in ("style", "script", "title"): s.skip -= 1
    def handle_data(s, d):
        if s.skip <= 0: s.text.append(d)
p = P(); p.feed(src)
css = re.findall(r"url\(\s*['\"]?([^)'\"]*)", src)
ext = p.ext + [f"url({u})" for u in css if not u.strip().startswith(("data:", "#"))] \
    + re.findall(r"@import[^;]*", src)
text = "\n".join(p.text)
ids = sorted(set(m.group(0) for m in re.finditer(r"\b[A-Z][A-Z0-9]{0,6}(?:-[A-Za-z0-9]+)+\b", text)))
spec = importlib.util.spec_from_file_location("cs", ".claude/scripts/check-sheet.py")
cs = importlib.util.module_from_spec(spec); spec.loader.exec_module(cs)
terms = cs.jargon_terms(open(".claude/directions/glossary.md", encoding="utf-8").read())
jargon = sorted(t for t in terms if t in text)
print("外部の読み込み :", ext or "なし")
print("script 要素    :", p.scripts)
print("svg の数       :", p.svgs)
print("内部識別子らしき記号:", ids or "なし")
print("キットの言い回し:", jargon or "なし")
EOF
```

- **外部の読み込み・`script` 要素は 0 でなければならない**(画像は data: の URI で埋め込み、`srcset` は使わない)。 svg は 2 以上でなければならない。
- **内部識別子らしき記号・キットの言い回しは、1件ずつ本文を見て判断する** — その場で丸括弧の説明が
  付いているか、その語が一般の言葉として使われているか(英大文字とハイフンの記号には、製品名や
  規格名のような一般の名前も混ざる)。説明の無いものは、中身を書く形に直す。

**描画して見る検査** — 上の機械の検査は、図の中の文字が線や箱と重なっていても、図の端で切れていても
通る。だから図を1つずつ画像にして、自分の目で見る(画像は `Read` で開ける)。画像は**リポジトリの外の
一時ディレクトリ**に書く(§8):

```bash
python3 - PROJECT_DESC.html <<'EOF'
import os, pathlib, re, shutil, subprocess, sys, tempfile
src = open(sys.argv[1], encoding="utf-8").read()
b = next((x for x in ("google-chrome", "chromium", "chromium-browser") if shutil.which(x)), None)
if not b:
    sys.exit("headless で動かせるブラウザが無い — 描画して見る検査はできなかったと §7 に書く")
repo = pathlib.Path.cwd().resolve()   # リポジトリの根で打つ
bases = [pathlib.Path(p).resolve() for p in (tempfile.gettempdir(), "/tmp", "/var/tmp", pathlib.Path.home())]
base = next((p for p in bases if p.is_dir() and not p.is_relative_to(repo)), None)
if base is None:
    sys.exit("リポジトリの外に一時ディレクトリを作れない — 描画して見る検査はできなかったと §7 に書く")
out = pathlib.Path(tempfile.mkdtemp(prefix="project-desc.", dir=base))
style = "".join(re.findall(r"<style\b.*?</style>", src, re.S))
for i, svg in enumerate(re.findall(r"<svg\b.*?</svg>", src, re.S), 1):
    m = re.search(r'viewBox="\s*[-\d.]+[\s,]+[-\d.]+[\s,]+([\d.]+)[\s,]+([\d.]+)', svg)
    w, h = (int(float(m.group(1))) + 40, int(float(m.group(2))) + 40) if m else (1280, 900)
    f = out / f"fig{i}.html"
    f.write_text(f'<!doctype html><meta charset="utf-8">{style}<body style="margin:20px">{svg}', encoding="utf-8")
    png = out / f"fig{i}.png"
    r = subprocess.run([b, "--headless", "--disable-gpu", "--hide-scrollbars", f"--window-size={w},{h}",
                        f"--screenshot={png}", f.as_uri()], capture_output=True, text=True, timeout=60,
                       env={k: v for k, v in os.environ.items() if k != "TMPDIR"})   # 長い TMPDIR ではブラウザが起動しない
    ok = r.returncode == 0 and png.is_file() and png.stat().st_size > 0
    print(png if ok else f"図{i}: 描画に失敗した(終了コード {r.returncode})— {r.stderr.strip()[-300:]}")
EOF
```

印字された画像を1枚ずつ開き、(1) 文字が線・矢印・箱と重なっていないか、(2) 文字や箱が図の端で
切れていないか、(3) 矢印が本文の言う箱を指しているか、を見る。直したら、もう一度描画して見る。

**初見の読み手の検査**(独立の検査)— 書いた本人には、自分が置いた前提が見えない。
**文脈の空いたサブエージェント**(艦隊運用でサブエージェントを持たないウィンドウは、中央へ `@review` を
1行で求める — 形は `orchestration.md` §1.2)に、**`PROJECT_DESC.html` のパスと次の指示だけ**を渡す。
あなたの意図や、うまく書けたと思う点は渡さない:

> あなたはこのプロジェクトを初めて担当する人である。このファイルだけを読み、`docs/` もコードも開かずに、
> 次を該当する文の引用つきで挙げてほしい: (1) 意味の分からない語・略語・記号、(2) 他のファイルを
> 開かないと分からない箇所、(3) 図と本文が食い違う箇所、(4) 読み終えても答えられない問い
> (目的・利用者・構成・言語・注意点・譲れないこと・現状のどれについてか)。
> 挙げるのは、**この資料の役目 — 担当を引き継ぐ人が、目的・利用者・構成・言語・注意点・譲れないこと・
> 現状を掴むこと — に要るものだけ**である。接続の形式の細部・設定ファイルの書き方・費用の内訳のような、
> 末尾の一覧の文書を開けば分かる詳細は挙げない。重要な順に **20 件まで**。直し方の提案は要らない。

受け取った所見は1件ずつ、資料の役目の内か外かを決める。役目の外のものは本文に足さず、末尾の
「この資料の元になった文書」に、それを知るにはどの文書を開けばよいかが書いてあることだけを確かめる。
所見を直したら、機械の検査と描画して見る検査をもう一度打つ。**直す周は2回まで**であり、残った所見は §7 の報告に書く。
独立の検査を立てられなかったときは、そのことを報告に書く(書かれていない検査は、走らせなかった
検査と見分けが付かない)。

## 7. 報告

`principles.md` §11 の形で、結論から書く:

- 書いたファイルの絶対パスと、元にしたコミット
- 8つの項目それぞれが「書けた」か「一部確認できなかった(何が無かったか)」か
- 入れた図(何の図か、1行ずつ)
- **生き残っていないと判断して除いた主なもの**(1件1行。何を、なぜ除いたか、根拠の `path:line`)—
  人間がこの判断を確かめられるようにする
- **食い違いの一覧**(両側の `path:line` と原文)— 直すのは `/verify-docs` か `/verify-impl`
- 作業の記録の精査で走査した語と、見出しを見て自分で読んだファイル(§3 の E)
- 機械の検査の結果、描画して見る検査で見つけて直したもの(できなかったなら、そう書く)、
  初見の読み手の検査の所見と、それをどう直したか・役目の外として残したもの(「所見なし」もそう書く)
- 「次にあなたがすること」— 資料を開いて読むこと、食い違いがあれば検証フローを走らせるか決めること、
  コミットするかどうか決めること

## 8. 禁止

- `PROJECT_DESC.html` 以外のファイルに書くこと(`docs/`・コード・`tests/`・`.claude/`・git)。
  例外は、描画して見る検査がリポジトリの外の一時ディレクトリに書く画像と HTML だけである
- 確かめられなかったことを推測で埋めること。出典を言えない段落を書くこと
- 作業の記録にしか無い内容(破棄された案・却下した案・来歴・着地しなかった要望)を、いまの姿として書くこと
- 外部の読み込み・JavaScript を使うこと。仕様ドキュメントに無い要素を図に足すこと
- 既存の `PROJECT_DESC.html` を部分的に手直しすること — 古くなったら、まるごと作り直す
- 仕様ドキュメントや規範からこの資料へリンクを張ること、この資料を他の作業の入力にすること
- 見つけた食い違いを自分で直す・どちらが正しいか裁定すること
