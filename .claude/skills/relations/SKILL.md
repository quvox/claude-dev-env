# Relations — 機能表と機能間連携仕様書をコードから導く

対象: $ARGUMENTS
生成する文書と報告はすべて日本語で書く。
**このスキルはコードを変更してはならない。**

**このスキルが `/retrofit` を呼ぶことは決してなく**、`/retrofit` がこれを呼ぶことも決してない
(順序は固定である — `.claude/directions/core.md` §5)。書式・粒度・ID の規則・道具立ての唯一の正は
`.claude/directions/features.md` と `.claude/directions/relations.md` であり、
**このファイルはそれらを複製しない。**

**コードが在る既存プロジェクトでは、このスキルが第1段である**(`/retrofit` より前)。
機能間連携仕様書が無ければ波及も呼び出し関係も引けず、
**上流の逆生成が当てずっぽうになる。**

**このスキルが負う規範の節** — `.claude/directions/reading.md` のこのスキルの行。
それは**床**である: 多く読むことは決して違反ではない。
**読んでいない節から決めることが違反である**(原則9)。

## 0. この仕事の形 — 機械がすること、人間が決めること

**`--apply` を付けて走らせるとき(= `docs/` へ書き込むとき)は、最初に1行走らせる** ★:

```sh
python3 .claude/scripts/guard-branch.py --slug relations
```

**終了コードが `0` でなければ、そこで止まって報告する。** 既存プロジェクトへの導入では
このスキルが**最初に `docs/` を書くもの**であり、ここで枝を切らないと、**導入は最初から
最後まで保護ブランチの上で走る** — 大量の文書を生成し古い文書を削除したあとで、
**気に入らなくても枝ごと捨てられない。** 正は `.claude/directions/flows.md` §7.1。
(**検査だけのとき(`--apply` を付けないとき)は判定しない** — このモードが書くのは、判断を
1つも含まないツール生成領域(コールグラフと `feature-graph.md`)だけだからである。
**「1バイトも書かない」ではない** — このモードでもその2つは必ず再生成する
(入力が変わっていなければ同じバイト列になるだけである)。
正は `.claude/directions/principles.md` §1。)

**境界(何を1つの機能と数えるか)さえ固定すれば、機械が機能間の関係を作れる。**
このスキルの構造はそこから従っている。**AI は「連携を見つける」のではない —
機械が出した辺を確認するか棄却し、それを記述する**(`.claude/directions/features.md` §7)。

```
コード ──build-callgraphs──► callgraphs/            (関数・辺・エンドポイント。機械)
       ──propose-features──► 機能候補・共通基盤候補  (提案。機械)
              ↓ ★ここだけが判断: AI が機能表を起案し、人間が合意する(§3A で1回だけ)
       ──cluster-features──► feature-graph.md       (機能間の辺・共有関数・未到達・資源結合。機械)
              ↓ AI がコードを読んで意味を書く
                            relations/MODULE-*.md
       ──callgraph-check──► FT/CG 検査(実装している ID は `--list`)
```

**このスキルが人間に問う点はちょうど1つ、§3A だけである** — 境界を、1回だけ問う。
それ以外はすべて自分で決めて開示する(`.claude/directions/delegation.md`:
何を問えるかは §1、開示行は §3)。

| モード | 起動 | ツール生成領域の生成先 | それ以外の書込み先 |
|---|---|---|---|
| **検査**(既定) | 引数だけ | `docs/03-impl/callgraphs/`(`resolve-callgraph-out.py --ssot` — `.claude/directions/callgraphs.md` §3.1)と `docs/03-impl/feature-graph.md` | **ツール生成領域以外は何も書かない**(判断を担うものを1つも書かない) |
| **反映** | `--apply` | 同上 | `docs/03-impl/features.md`、`relations/`、`contracts/`、`index.md` |
| **ブートストラップ** | `--apply --bootstrap` | 同上 | 上に加えて、`docs/02-design/system.md` の**モジュール分割定義の節だけ** |

**検査モードもツール生成領域は作り、その場で再生成する** —
そのうちコールグラフが**読む場所の一覧**であり、**このスキルがリポジトリを掃かない理由**である。
**このスキルが書くツール生成領域はちょうど2つである** ★: `docs/03-impl/callgraphs/`(段階の側はもう無い —
`resolve-callgraph-out.py --ssot` が正)と `docs/03-impl/feature-graph.md`。
どちらの再生成も**判断を伴わない書き写しである** — 前者はコードを、後者はコールグラフと機能表を
写すだけで、**入力が変わっていなければ同じバイト列に再生成される**
(原則1 の書き手の一覧はツール生成領域をこの形で持つ)。
**`feature-graph.md` がここに入るのは、検査モードが §3A の締めでそれを生成するからである**(§3)。
検査モードが書いてはならないのは、**判断を担うものすべて**である —
`features.md`、`relations/`、`contracts/`、`index.md`、そして 02。
それらが動くのは `--apply` のときだけである。

`--apply` が許されるのはちょうど3つの場合である(**これはこのスキルがオプションを渡してよいのはいつか**の
話であり、**そもそもどの SSOT への書込みが許されるかの正は CLAUDE.md 原則1 である**)。
それ以外で渡されたときは、**理由を述べて検査モードへ落ちる**:

1. **`/verify-impl` に駆動されている。** 実際には `/verify-impl` が再生成を自分で行う
   (その §1: 同じスクリプトを `resolve-callgraph-out.py --ssot` で SSOT に向ける)。
   その仕事のどれかがこのスキルを通って走るなら、それは F3 駆動として数え、同じ SSOT の宛先へ書く。
2. **タスクが進行しておらず**、人間が「03-impl をコードに同期させて」と明示的に求めた。
   **これは正当な操作である** — SSOT はコードの鏡像なので、タスクが存在せず両者がずれているとき、
   03-impl を直すことは**不変則を回復すること**そのものである
   (例外条項を通した hotfix の後など)。**履歴を1件残す**(変更の理由: コードとの同期)。
3. **ブートストラップ**(`--bootstrap`): `docs/03-impl/relations/` が空で、
   02 にもモジュール分割定義が無い = **文書の無い既存コード**である。これは
   **明示的なブートストラップの例外**である(`/retrofit` と同じ扱い)。理由:
   **機能の境界はモジュールの境界に依存するので、分割を決めずに relations は書けない。
   しかし分割を決めるには実装の構造を知らねばならない。**
   **分割定義と機能表は §3A の1枚のシートで人間へ行く**(§2 と §3 で起案し、
   1回で、一緒に問う)。**生成したものに `verified` を決して書かない。**

**再生成の範囲と重なるクロージャを持つ `state: building` の構築記録が在るあいだ、
*単独での* `--apply` を決して行わない。** その過渡はその構築が閉じるものである(`flows.md` §3)。
構築の途中で上書きすると、**どちらが SSOT の真実なのかが決定不能になる。**
検査モードで報告し、その記録の 申し送り に所見を書く。
**この見張りを検査モードへ広げない** ★ — 検査モードもツール生成領域(§0)を書くが、
その再生成は**いまのコードといまの機能表から機械的に導かれるだけで、新しい判断を1つも
加えない**(§0)。この禁止が防いでいるのは**判断を担うものを構築の途中で上書きすること**であり、
それはここでは起きない。広げれば、`building` の最中に読む**軽い手立て**(引数だけの検査モード)が
消え、`/verify-impl` のリポジトリ全体の再生成に頼るしかなくなる。
**場合1 — `/verify-impl` に駆動されている場合 — はこれが禁じているものではない**:
F3 は `building` のクロージャを判定から除外するので、**黙った衝突は残らない。**

## 1. 範囲を決める(まず道具で絞る)

| 引数 | 対象 |
|---|---|
| `MOD-<slug>` | 02 の分割定義でそのモジュールに割り当てられたコード |
| ディレクトリ / ファイルのパス | そのパスの下のすべて |
| `all` | リポジトリ全体(**高くつく。ブートストラップのとき、または人間がリポジトリ全体の再導出を求めたときだけ**) |
| 省略 | `git diff` で最近変わったファイルから推定する。**自分で決め、推定した対象とその根拠を §8 の報告で述べる** — 1つの run の範囲は 進め方 であり、`DS-08` が委任している(`.claude/directions/delegation.md` §2)ので、**宣言するものであって、問うものではない** |

**リポジトリで初めてこれを走らせるときは、まず解析の対象を絞る。**
`excludes`・`tooling_markers`・`languages.<lang>.enabled` を
`callgraph-config.local.json` へ書く。**`internal_roots` はそこで絞れない**:
ローカルの配列は和として併合されるので、配布された既定の `.`(= リポジトリ全体)が必ず生き残る。
モノレポでは、**ローカルのファイルの `excludes` に兄弟パッケージ等を並べて絞る**
(除外を足すのは、和であっても縮む向きである。恒久的な直し方はスクリプトの変更であり、
それは汎用的な直しなので `/kit-improve` の2つの縛り(`.claude/directions/core.md` §3)を満たせば
いつでも直してよい)。設定の鍵の正は `.claude/tools-readme.md` の設定の表。
精度の段は `.claude/directions/callgraphs.md` §5.8。
依存が足りなければ各スクリプトが `setup-tools.py` を走らせろと言う — それに従う。

```bash
# ★ 出力先は常に SSOT(.claude/directions/callgraphs.md §3.1)
CG_OUT=$(python3 .claude/scripts/resolve-callgraph-out.py --ssot)
python3 .claude/scripts/build-callgraphs.py --out "$CG_OUT"   # ★ まずコールグラフを作る
python3 .claude/scripts/propose-features.py             # ★ 機能候補・共通基盤候補
python3 .claude/scripts/callgraph-check.py              # 既存 relations との整合(初回は空)
python3 .claude/scripts/relations-query.py --health     # 既存グラフの構造(初回は空)
```

**`$CG_OUT` が読む場所の一覧である。その出力から始める。**
**自分でリポジトリを掃かない**(それが文脈を燃やし精度を落としていた主な原因である)。

コールグラフを読むときの注意(`.claude/directions/callgraphs.md` §5):

- **必ず `Tier` を見る。** Tier 3 では呼び出し関係が不完全であり、
  **「網羅した」と報告してはならない。**
- **必ず「未解決の呼び出し」の表を読む。** 空白は「呼び出しが無い」を意味し、
  未解決の表は「機械には見えなかった」を意味する — **この2つは別物である。**
  AI がコードを読み、未解決のぶんだけ埋める。
- **道具にエンドポイントの「呼び出し元」は決められない。** そこは AI の領分である。
- 抽出器の無い言語(`Python` / `Go` / `TypeScript` / `Rust` / `infra` / **`shell` / `make`** 以外)では、
  最後の手段として `python3 .claude/scripts/scan-entrypoints.py <target>` を使い、
  **その領域は実質 Tier 3 であることを明示的に述べる。**
  shell と make には抽出器が**在る**が、正規表現ベースである(**Tier 3**):
  **その呼び出し辺は構造上不完全なので、出力を網羅として決して報告しない。**

## 2. モジュール分割を起案する(ブートストラップのときだけ)

`02-design/system.md` に既に分割定義が在るなら、**それに従い**、この節を飛ばす。

無いなら(`--bootstrap`):

0. **まず既存の文書を棚卸しする**(README、設計メモ、リポジトリ内の wiki)。
   コードを読みながら(§4)、**それらがコードと矛盾するすべての箇所**を記録し、
   その全件を §8 の「既存仕様ドキュメントとコードの矛盾」の節へ転記する —
   **全件の列挙が、コードを正とすることの対価である**(CLAUDE.md 原則2 のブートストラップの例外)。
   あの節の「なし」は、**この棚卸しの*後*に行う主張**であって、既定値では決してない。
1. コードの構造・ディレクトリ・依存・入口の分布から、**分割案**を起案する。
2. モジュールごとに表を起案する: ID(`MOD-<slug>`)、責務、含むパス、依存、エントリポイント数。
3. **ここで問わない。** 起案を §3A のシートへ1ブロックとして持っていく —
   ここと §3 で二度問うのは、**1つの境界の決定に往復を2回払うこと**である。
4. §3A が決着したら、`02-design/system.md` の**モジュール分割定義の節だけ**を書く
   (他の節は書かない — テスト戦略・要件カバレッジ・UX 文書(`docs/ux/` — `ux.md`)は `/retrofit` の仕事である)。
   `version: 1.0.0`、`verified` は書かない。

## 3. ★ 機能表を起案する(この仕事の中で唯一の判断)

規範は `.claude/directions/features.md`。雛形は `.claude/templates/03-features.md`。

**検査モードでは**、機能表が既に在り FT2 の追加候補が無いとき、§3 の起案と §3A の停止を飛ばす —
**ただし §3A の締めの `cluster-features.py` の実行は飛ばさない**(§1 の `$CG_OUT` で走らせる)。
飛ばした後は **§4**(読むだけ)へ続け、飛ばしたことを §8 の報告で述べる。

**機械は境界を決めない** — `propose-features.py` が出すのは候補だけであり、
分担は `features.md` §7 が所有する。**起案は無人で行う**: 下の行をすべて自分で決め、理由を記録する。
その起案がどこへ行くか、そして問うことは §3A である。

1. **機能候補をそのまま貼る。** 既定の粒度は**入口1つ = 機能1つ**である
   (REST エンドポイント1つ / Lambda ハンドラ1つ / `cmd` の分岐1つ)。
   提案された機能ID・所属・概要は**起案なので、直す。**
   - 機能ID は `MODULE-<feature-slug>` であり、**ファイル名 `relations/<機能ID>.md` と同一**である。
   - 入口の表記はコールグラフと**1文字も違わず**一致させる。さもないと突き合わせが黙って外れる。
2. **共通基盤候補を、ファンインの高い順に検討する**(ファンインが何を意味するか、
   なぜファンイン ≥ 2 が境界*そのもの*なのか、なぜ反復が収束するのか: `features.md` §4)。
   **昇格させないという決定も機能表に記録する** —
   さもないと同じ候補が次の run で戻ってきて、同じ議論をやり直すことになる。
3. **統合候補を検討する**(関数集合が大きく重なる機能の対)。併合するには、1行の入口の欄に
   複数の項目を書く。**機械が自分で併合することは決してなく、1つの入口を2つの機能に割ることは
   禁止である**(`features.md` §2)— 割りたいなら、代わりに `#分岐値` の合成シンボルを入口として足す。
4. **FT2(機能表に無い入口)をゼロにする。** 足すか、足さない理由を決めるかのどちらかである。

## 3A. ★ 人間に問う唯一の点 — 境界を、1回だけ

§2 の分割の起案と §3 の機能表の起案を、**1枚のシートにまとめて**提示して止まる
(書式: `.claude/templates/sheet.md`。根拠 は `.claude/skills/relations/SKILL.md` §8 の
報告の節を引く — `build-record.md` §3)。
ブロックは2つ: 分割定義(ブートストラップのときだけ)と機能表。どちらも同じ
**間違えたときの戻し方**を持つ — 「機能表か分割定義を直し、`cluster-features.py` から §4 以降と
関係する `relations/MODULE-*.md` を全件やり直す」。**1行で答えられる形で提示する。
行ごとの承認は求めない。**

- **検査モードは待たない**(ブロックは §8 の報告へ入る)。§4 と §6 を**読むだけで**進み
  (§5 は書く段なので飛ばす — §0 のモードの表のとおり)、§6-6 が最後の**検査**の段である。
  そのうえで §7 と §8 を行って終える。
- **SSOT への2つの書込みは、回答の後、ここで起きる**: `02-design/system.md` の分割定義の節(§2-4)と
  `docs/03-impl/features.md`(§3)。どちらかを先に書くのは、`features.md` §7 が禁じる
  「黙って決着させること」である(行2 — **合意することが人間のする唯一のことである**)。
- **決着した境界を二度提示しない。** そして**回答が生んだ問いのために2回目を開かない。**

そのうえで、機械に関係を作らせる:

```bash
python3 .claude/scripts/cluster-features.py --out "$CG_OUT"   # feature-graph.md を生成(§1 の $CG_OUT を引き継ぐ)
python3 .claude/scripts/propose-features.py      # 昇格後の残りを再確認(最大2回)
```

**この繰り返しの上限は2回である**(run の中の反復の回数であって、検証の周の本数ではない)。
2回で尽きなかった候補は、昇格しなかった理由とともに §8 の報告の表へ
出して終わる — `.claude/directions/features.md` §4 が論じているのは反復が収束することであって、
1つの run で収束しきることではない。上限の数字は検証フローと同じである(`.claude/directions/core.md` §3)。

機能表をクロージャに含む `/build` が `state: building` のあいだは、
`.claude/directions/callgraphs.md` §6.1 を見る — そこでの FT1 と「古い」の終了コード1 は**仕様である。**

`feature-graph.md` は**生成物である。決して手で編集しない。**
**relations の代わりに使うことも決してない**(関係だけを持つので、仕様ではない)。

## 4. コードを読んで機能を記述する(ここが AI の仕事である)

**コールグラフのすべての関数をそれぞれ仕様にしてはならない。**
機械が作ったのは関係だけであり、**この段がコードを読んでそれに意味を与える。**

`feature-graph.md` を手元に、各機能のコードを読んで決着させる:

1. **`callees` は `feature-graph.md` の「機能間の辺」から写す。自分で探しに行かない。**
   **資源結合(呼び出し辺を持たずに同じ資源を触る機能)を `callees` に決して書かない** —
   それは呼び出しではなく、書くと対称性の検査と CG3 が壊れる。それが属するのは
   **戻り値・副作用**(書き込む資源を名指す)と**連携先と連携内容**(読む資源を名指す)である。
   根拠は `callgraphs/resources.md`。2つ以上の機能がその形式を共有するなら、
   生産する側と消費する側の `contracts:` すべてに共通の `CTR-*` を要求し、
   **形式そのものは 02/03 の契約の対に置く**(`callgraphs.md` §5.11)。
   **MODULE の散文で繰り返さない。**
   - 確度 `確定` の辺 → そのまま `callees` へ入れる。
   - 確度 `候補` の辺 → **コードを読んで確認する。** 名前衝突の候補を数えて繋いだものであり、
     実在しないことがある。**棄却してよいが、理由を報告に書く**(**決して黙って消さない**)。
   - **機械に見えない辺は自分で足す** — REST の呼び出し元、動的ディスパッチ、
     未解決の表に残った呼び出し。足した1本ごとに、**どのコードが呼ぶのか**の根拠を本文に書く。
2. **テストも読む**(**振る舞いについて最も信頼できる根拠である**)。テストの識別子を `tests:` へ。
3. 契約(API・データ形式・イベント・永続化スキーマ)の**実際の**検証・既定値・エラー応答を読む。
   それらが定義されている `path:line` を記録する。
4. **事実と推測を厳密に分ける。** コードから読めないもの(なぜこの設計か、この分岐の意図は何か)は
   **推測で埋めてはならない** — 判断の節に「判断なし: コードから読み取れない」と書き(`CS19`)、
   原則8 の記録先の振り分けを通して記録する
   (`.claude/directions/issues-pendings.md` §1: 既定は `docs/residual.md` の `残務` 1行 —
   **書く前にその鍵を既存の行と突き合わせ、当たったら何も書かない**(§2.1)。
   **書いたら `python3 .claude/scripts/doc-health.py --rotate` を打つ** — 50行以上なら
   ファイルがローテーションされる(1行も落ちない。§2.1 (2))。
   `docs/issues/` のファイルは、不具合か完了定義の阻害のときだけ)。
   **シートへ届くのは、問う基準を満たすときだけである**(`.claude/directions/delegation.md` §1)。

間違えやすい点:

| 状況 | どうするか |
|---|---|
| `requirements` / `design` が引けない | `なし` と書き、**本文に理由を書く**。空欄にしない。ブートストラップでは 01/02 がまだ無いのが普通で、**論点ではない** — `/retrofit` §4「Fill back」が埋める |
| `tests` が無い | `なし(未実装)`。**テストが無い振る舞いは全件レポートに列挙する** |
| 同じ機能のコピーが複数ある | `impl` に**全部列挙する**(重複自体が情報) |
| `feature-graph.md` の「未到達」に出ている | **消さない**(動的呼び出しや外部参照がありうる)。**入口の登録漏れでないかを先に疑い**、違えば理由を機能表の記録節に書き、記録先の振り分けに従って記録する(既定は残務1行。不具合・完了定義を阻害するもののときだけ `docs/issues/`)。問う基準を満たさない(`.claude/directions/delegation.md` §1) |
| 巨大な神クラス・神関数 | 実質的な機能ごとに分けて複数本にし、**その事実を報告する**(設計の問題として) |

## 5. 書く

`.claude/templates/03-relation.md` と `.claude/templates/03-contract.md` を使う。
frontmatter の欄はすべて**1行に**書く(grep が唯一の参照手段である)。`updated` は今日の日付。
**`impl` は機能表の入口を含む**(入口はその機能の代表シンボルであって、`impl` の全体ではない)。

**本文の「連携先と連携内容」は、`callees` の項目1つにつき小節1つを持たねばならない** —
frontmatter に在って本文に無いものが在れば、**その文書は未完成である。**
`check-relations.py` は callee ごとの `###` の見出しを数える:
欠けているものは警告、重複はエラーである(`.claude/directions/relations.md` §6.3)—
**判定できないのは各小節の中身であり、それを確かめるのはあなたである。**

## 6. 照合と機械検査

1. **機能表 ⇄ コールグラフ ⇄ 機能間連携仕様書**:
   ```bash
   python3 .claude/scripts/callgraph-check.py
   ```
   **各検査が何を意味するかは `.claude/directions/callgraphs.md` §6 が持ち、ID の一覧は
   `callgraph-check.py --list` が持つ。どちらもここに書き写さない** —
   この節が所有するのは、**所見に対してこのスキルが何をするか**だけである。

   **反映モードでは、重大度「高」が1件でも残っていれば、仕事は終わっていない。検査モードでは
   高は所見であって関所ではない** — 高を消す既定の対処(機能表に行を足し、relations を1本足す)
   はどちらも書込みであり、検査モードはそれを禁じられているからである(§7 の独立レビューの所見に
   ついて、このスキルが既に採っているのと同じ書き分けである)。ただし:
   - 「低(経路の有無を断定できない)」の CG3 → **道具が未解決の呼び出しの向こうを見られなかった
     だけである。** コードを読み、判断し、根拠を本文の「連携先と連携内容」に書く。
   - 「中(確度は候補)」の CG4 → 候補で繋がった辺である。
     **コードを読み、採否を決め、理由を書く。**

   **照合と修正の繰り返しは最大2回である**(修正ループの上限と同じ数字 — `.claude/directions/core.md` §3。
   この「2」は run の中の反復の回数であって、検証の周の本数ではない)。2回で残った高は
   報告(§8)に「未解決の高 N 件」と名乗って出し、記録先の振り分け
   (`.claude/directions/issues-pendings.md` §1)を通して残す。**閉じないまま繰り返さない。**

2. **内部整合**: `python3 .claude/scripts/check-relations.py`。
   **反映モードでは、落ちたら仕事は終わっていない**(検査モードでは所見として §8 の報告へ出す —
   直す手段が書込みしか無いからである)。
3. **02 ⇄ 03**: `02-design/relations.md` の `PLAN-*` と照合する
   (手順は `.claude/directions/relations.md` §7)。差はそれぞれ原則2 で振り分ける
   (`.claude/directions/03-impl.md`): **事実はコードに対して。そして裁定できない意図の差異だけが
   論点になる。それを自分で決着させることは決してない。** ここへ来る時点で §3A は既に回答済みなので、
   それは **§8 の報告の 決定シート の節**へ行く — そして**このスキルはタスクのディレクトリを
   決して持たないので、論点1つにつき `docs/issues/` を1件**起こす
   (`.claude/directions/issues-pendings.md` §5)。**§3A を決して開き直さない**(その節自身の規則:
   2回目は開かない)。
4. **構造の健全性**: `python3 .claude/scripts/relations-query.py --health`。
   肥大したモジュール(1モジュールに 15 本を超える relations)・循環・到達不能コード・
   テストの欠落・要件の欠落を表に出す。
   **肥大したモジュールについては、02 の分割定義の見直しを提案する**(**自分で割らない**)。
5. **反映モードのときだけ**: 書いた後に `build-callgraphs.py --out "$CG_OUT"`、
   `cluster-features.py --out "$CG_OUT"`、`build-index.py`、`check-relations.py`、
   `callgraph-check.py` を走らせ、導出できない注記が変わったなら `docs/03-impl/index.md` を
   更新する(「この層の状態」は鮮度の数字を保存しない — 件数と合格日は、その雛形が名指す
   コマンドで測る)。relations を反映したら、**`index.md` の版を必ず1回、MINOR で上げる** —
   それが層の代表なので、**自分の本文が変わっていなくても上げる**
   (`verified` は書かない — それは verify 系フローの仕事である)。
   **`callgraphs/` と `feature-graph.md` を決して手で編集しない。**
   直すなら、コードか、機能表か、抽出器を直す。
6. **検査モードのときだけ**: **ツール生成領域以外は何も書かず**(§0 のとおり、コールグラフと
   `feature-graph.md` はこのモードでも再生成する)、差分を報告する。タスクが進行しているなら、
   「この結果をその構築記録の調査メモに転記することを推奨」と述べる。

## 7. 独立レビュー(必須。免除は `/verify-docs` §2 が定めるものだけ)

**コードを読み違え、それが黙って「仕様」になること** — それがまさにこの仕事の危険である。
読むだけの相互確認を**1つの独立レビュー — ここで使えるなら Codex、でなければ新しい文脈の
サブエージェント** へ委任する(起動の規則: `/verify-docs` §2。方針: `.claude/directions/core.md` §5):
導出した `MODULE-*` がコードと一致しているか(`impl` のパス、公開インターフェース、
呼び出し関係、テストが実在するか)を確かめさせ、
**対応する `MODULE-*` を持たない入口**を見つけさせる。
**対象のコードと範囲を渡すのであって、自分の読みを渡すのではない。**
その所見は根拠である: 高 と振る舞いに関わるものを裁定し、事実の食い違いを直し、
残りを問う基準で振り分ける。**所見そのものは関所ではない** — 高 でないものが run を止めることはない。
**起こすこと自体は必須である。** 免除は `/verify-docs` §2 が定める2つだけである
(対象0件 / 対象3ファイル以下かつ `critical: true` 非含有)。免除に当たるなら報告(§8)に
その旨と理由を書いて続ける。免除に当たらないなら**レビューを空のままにしない** —
§2 の経路を尽くす(**艦隊なら中央へ要求して起こしてもらい**、でなければ Codex、それも
駄目なら新しい文脈のサブエージェント。**要求の形と、返らなかったときの出口は
`orchestration.md` §1.2 が持つ**)。尽くしても得られなかったときは 「独立レビュー: なし(理由)」 と
報告に名乗って続ける。**ただし `critical: true` のクロージャが範囲に在るときは別**であり、
そのときは §2 のとおり **green を記録せず、「中断(独立レビューが成立しない)」** とする。
