# Retrofit — 仕様ドキュメント群を規範に合わせて作り直す。過不足なく

対象: $ARGUMENTS。生成する文書と報告はすべて日本語で書く。
**このスキルはコードを変更してはならない。**

**ブラウンフィールド導入の第2段**である(第1段は `/relations all --apply --bootstrap` であり、
機能表・モジュール分割・relations・契約をコードから作る — それらが無ければ上流は当てずっぽうに
なる)。**2つの出発点の両方**を覆う:

- **仕様ドキュメントが無い** → コードから 03の残り → 02 → 01 → 00 を逆生成する。
- **古い / 膨れた / 規範に合わない仕様ドキュメントが在る** → 同じ下降を、既存の文書を**材料**として
  行う: すべての節を仕分け(§2)、生き残ったものを規範の形に書き直す。
  **事実についてはコードが正である。**

これは**原則1 のブートストラップの例外**である(SSOT を直接書く。タスクが進行していては
ならない)。そして**原則2 のブートストラップの例外**を負う:
コードが既存の文書を上書きしてよいのは、**矛盾するすべての箇所を報告に全件列挙したときだけ**
である。**`verified` を決して書かない**(それはこの後の `/verify-docs` の仕事である)。
**`request.md` を決して生成しない**(00 は人間のものである。骨子を提案する)。

**`/retrofit` は意図的に `.claude/directions/reading.md` の表に無い**(あのファイルがそう述べ、
理由も述べている)。その母集団は**書き直すすべての層の規範を、まるごと**である —
**行が無いことを「床が無い」と決して読んではならない。**

## 0. 前提条件(成り立たない限り着手しない)

**最初に、保護ブランチで書かないことを確かめる** ★:

```sh
python3 .claude/scripts/guard-branch.py --slug retrofit
```

**終了コードが `0` でなければ、そこで止まって報告する。** このスキルは既存の文書を
**大量に書き直し、古い文書を削除する** — 保護ブランチの上で走ると、**気に入らなくても
枝ごと捨てられない。** 正は `.claude/directions/flows.md` §7.1。

```bash
CG_OUT=$(python3 .claude/scripts/resolve-callgraph-out.py) || exit 2
python3 .claude/scripts/build-callgraphs.py --out "$CG_OUT" --check
python3 .claude/scripts/cluster-features.py --out "$CG_OUT" --check
python3 .claude/scripts/check-relations.py
python3 .claude/scripts/callgraph-check.py
```

| 状態 | 対処 |
|---|---|
| `docs/build-records/` の下に `state: building` の記録が1件でも在る | 止めて報告する(原則1 — 構築が進行しているあいだブートストラップはしない) |
| `features.md` が無い / `MODULE-*` が無い / 02 にモジュール分割が無い | **止めて報告し、`/relations all --apply --bootstrap` を先に走らせてもらう**(単独運用なら人間に、艦隊下なら中央エージェントに)。CLAUDE.md §5 の導入経路は `/relations` と `/retrofit` を別の段として並べており、**このスキルが他のフローを自分で始めることはない**(艦隊下では1作業指示=1フロー — `roles/work.md`)。ブートストラップが済んだら再入する |
| `--check` が古い、または `check-relations.py` が落ちる | 人間に `/relations <target> --apply` を走らせてもらってから再入する — 明示の要請が無いと `--apply` は検査モードに落ちる(`/relations` §0 の3つの場合。その要請が原則1 の既存の例外である) |
| `callgraph-check.py` に 高 が在る | 03-impl が未完成である。人間に `/relations <target> --apply` を走らせて埋めてもらう(同じ原則1 の経路。判断保留のものが数件なら課題票にして通してよい) |

**段取りを宣言してから始める**(規模、モジュール数、この run の範囲 — `DS-08`: 宣言するもので
あって、問うものではない)。**告げずに全体を走らせない。**

## 1. 既存の文書を棚卸しする

既存の文書をすべて並べる(`docs/` の中でも外でも — README、wiki の書き出し、設計メモ)。
それぞれについて記録する: **どの層だと主張しているか / この仕組みの構造に従っているか /
最後に真だったのはいつか**(git)。この棚卸しが §2 の入力であり、矛盾の一覧の土台である。
**文書が既に規範に合っていて最新なら、止めて報告する** — それは `/build` の領分である。

## 2. すべての節を仕分ける — 一度きりの全件の帰属監査 ★

**キットの中で、既存の文が文のかたまり単位で、層への帰属と存在する権利を監査される唯一の場所で
ある。** 既存のすべての文書の節ごとに、この順で当てる:

1. **どの層が所有するか?** 主語テスト(我々/利用者/事業 → 00。システム → 01)→
   置き換え/観測者テスト(機構を丸ごと差し替えても真のままで、かつ外から観測できる → 01。
   でなければ 02/03 — 試験は `.claude/directions/01-requirements.md` が所有する)→
   再生成テスト(コードから 03 を再生成したらそれは消えるか? 消える → それは意図なので 02。
   残る → 03)。**2つが食い違ったら上の層が勝つ。**
2. **処分** — ちょうど1つ:
   | 判定 | 対処 |
   |---|---|
   | 適合 | 残す。言い回しがずれているなら雛形の形に書き直す |
   | 移送 | 別の層に属する: **同じ下降の中で両側を書く**(ここから消し、あちらへ書く)。00 への出入りは §6 のシートに載せる |
   | 廃止 | 計画/TODO/願望。コードを言い換えた散文(03 の鏡が再生成する)。他の層の主張の複製。理由の記録が無く `DS-*` が既に覆っている値 |
   | 欠落 | 規範が要求しているのに何も無い — 生成の一覧(§3〜§5)へ載る |
3. **「過不足」の判定基準**は `.claude/directions/conventions.md` §2 の4条件である: **何かを制約する / 変えるのが高くつく /
   所有の境界をまたぐ / 検証に要る** のいずれかのときだけ、その文を残す。
   **それ以外は削除が既定である** — 消した文は git に生き残り、報告は**落としたものを分類ごとに**
   並べる(1行ずつではない)。

仕分けは文書1つにつき表1つとして記録する(報告のために持つ。仕様ドキュメントとしてではない)。

## 5A. 独立レビュー(必須。免除は `/verify-docs` §2 が定めるものだけ)

**retrofit はコードの読み違いが最も危険な場所である**: 既存の文書がコードを正として書き直される
ので、読み違いが黙って「仕様」になる — そしてタスクと違い、**`/verify-docs` が突き合わせる
相手の状態が存在しない。** §6 の前に、読むだけの相互確認を
**1つの独立レビュー — ここで使えるなら Codex、でなければ新しい文脈のサブエージェント** へ委任する
(起動の規則: `/verify-docs` §2。方針: CLAUDE.md §6): 渡すのは対象・範囲・検査項目・出力様式だけ
である — **自分の仕分け表も、書き直した文書の結論も、期待する判定も決して渡さない。**
コードに対して次を確かめさせる: (a) §2 の 廃止/移送 の判定を抽出したもの —
落とした文は本当に何も制約していなかったか。(b) 上へ生成した 02/01 の主張 —
それぞれが 03 かコードに根拠を持ち、発明ではないか。(c) §6 の矛盾の一覧 —
抽出した1モジュールでの網羅性。
**その所見は根拠であって判定ではない**: 高 と振る舞いに関わるものを裁定し、事実の食い違いを直し、
残りを問う基準で振り分ける。**所見そのものは関所ではない** — 高 でないものが run を止めることはない。
**起こすこと自体は必須である。** 免除は `/verify-docs` §2 が定める2つだけであり、
**retrofit は既存の全文書を対象にするのでどちらにも当たらない**(対象0件でも3ファイル以下でもない)。
つまりここでは**レビューを空のままにしない** — §2 の経路を尽くす(**艦隊なら中央へ要求して
起こしてもらい**、でなければ Codex、それも駄目なら新しい文脈のサブエージェント。
**要求の形は `orchestration.md` §1.2**)。尽くしても
得られなかったときだけ、§6 の報告に 「独立レビュー: なし(理由)」 と書いて続ける。
**ただし `critical: true` のクロージャが範囲に在るときは別である** — そのときは
`/verify-docs` §2 のとおり **この run を完走させず**、§6 の報告を
「中断(独立レビューが成立しない)」 として、何が起こせなかったかを1行で書く
(§0 が止めるのは `state: building` の記録だけなので、`awaiting-verify` の critical は
retrofit の範囲に残りうる)。
**どのレビューが走ったかを報告で名乗る**
(`Codex` / `サブエージェント` / `なし(理由)` — CLAUDE.md §6)。

   ここで確定している)。**未宣言のあいだ F3/F4 の鮮度スタンプはデプロイゲートで `未宣言` = red であり、

5. 締めの案内: 決定シートへの回答(一括回答1行で可)と `request.md` の執筆の後、
   **`/verify-impl all` → `/verify-docs all`** の順で検証する(request.md が無いと全層が上流
   未検証で終わる。順が F3 → F2 なのは検証の周の正順と同じ理由 — retrofit 直後は事実の差異の自動修正が
   最も出やすく、逆順だと F3-all の書込みが F2-all の鮮度スタンプを失効させて覆い直しを1回必ず払う。
   inspection-17 V-7)。以降この文書群が SSOT になる。
   **回答をどこへ落とすかの台帳は作らない。** この skill にはタスクが無いので、論点は §6-3 の時点で
   すでに `docs/issues/` の1件ずつになっており(`issues-pendings.md` §5)、その `closes_when:` が
   「人間が回答し、**回答が反映されたとき**」である。**回答は該当する候補ファイルへ上流→下流の順で
   適用し、適用したらその課題票を閉じる**(閉じることが反映の記録である)。
   **`/verify-docs all` に渡す前に、この run が起こした課題票が1件も開いていないことを確かめる** —
   開いたまま渡すと、未回答の候補ファイルがそのまま SSOT として検証される。

**「全体」は仕分けの母集団であり、段取りは1つの run の書き直しの単位である** —
**この2つは別物**であり、既定の対象(all)が定めるのは前者であって、決して後者ではない。
だから: 母集団の全体を棚卸しして仕分け(§1〜§2)、そのうえで
