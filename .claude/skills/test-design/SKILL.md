# テスト設計とテストコード規約

**フローではなく、SSOT を書かない参照スキルである。**構築フローのテスト設計・実装と、試験フローのレビューで引く。呼び出し元のフローが書込みと記録を担当する。コマンドと宣言ファイルは `/test-runner-usage`、落ちたテストの扱いは `/verify-tests` §2 と `/build` §3 が所有する。

**このスキルが負う規範の節** — `.claude/directions/reading.md` の `/test-design` の行。

## 1. 受け入れ基準からケースを導出する

導出元は受け入れ基準と公開契約。実装の計算式・分岐・実際の返却値から期待値を逆算しない。受け入れ基準が無い・曖昧なら、`delegation.md` §1 の問う基準を通してシートへ載せる。実装から受け入れ基準を補わない。独立に進められる作業は続ける。

観点は名指しで洗い出す:

| 観点 | 見るもの |
|---|---|
| 境界値 | 数値・文字数・日付・件数の境界とその前後 |
| 異常系 | 不正入力、外部依存のエラー・タイムアウト・通信断 |
| 権限 | ロールごとにできること・できないことの両方 |
| 同時実行 | 二重送信、冪等性、競合 |
| 大量データ | ページング境界、処理時間、件数上限 |
| 状態遷移 | 許される経路・禁止される経路の両方 |

**洗い出した観点のうち、その条項に必要だと判断したものは、すべて対応表の行にする** ★ — 行の単位は「条項」ではなく**「条項 × 必要と判断した観点」**である。同じ条項 ID が、正常系の行と権限の行を持ってよい。**まだ書いていない観点も、テスト識別子を `-` にして `未検証(テスト未実装)` の行として残す** — 行が無ければ、その観点が「不要と判断された」のか「書き忘れた」のかを後から誰も区別できず、正常系1行だけで網羅したと読める。**不要と判断した観点の行は作らない**(正常系に加えて6観点を全条項に並べると表が数倍になり読まれなくなる)。要否を判断した理由は「テスト設計の判断」に1行で開示し、**その1行は対象を名指す**: `- [DS-01] <条項 ID をコンマ区切りで列挙> の <観点> は作らない — 理由: <> / 見直す条件: <>`。**「全条項」「その他」とは書かない** — どの条項の話か決まらない行は、省略の記録にならない。同じ理由が当てはまる条項は1行にまとめてよい。規則の正は `.claude/directions/03-impl.md`「tests/」、雛形は `.claude/templates/03-tests-module.md`。

## 既にあるテストを流用するとき ★

既にコードとテストが在るプロジェクトへ後から入れるときは、**既存のテストを片っ端から実行対象へ入れない。** 入れると、何を確かめているか誰も言えないまま緑が出る。**次の4つを全部満たすものだけを流用する**(種類は問わない — 単体テストでも順序に依存するなら流用できないし、E2E でも自己完結していれば配線できる):

1. **単独で走る** — 他のテストが先に走っていることに依存しない(順序依存が無い)。
2. **後始末をする** — 残したデータが次の実行に影響しない。
3. **何を確かめているかが読んで分かる** — 受け入れ基準のどれに当たるかを言える。
4. **落ちる条件が仕様から来ている** — 「いまの実装がこう動くから」で書かれていない。

**条件を外れるが中身に価値があるものは、捨てずに「移植候補」として記録する** — 置き場は `docs/03-impl/tests/<module-slug>.md` の「テスト設計の判断」(**複数のモジュールをまたぐものは `tests/e2e.md` の同じ節**)で、**何が足りなくて流用しなかったかを1行添える**(「順序に依存する」「期待値が実装の写しに見える」など)。記録しないと、そのテストは次の設計のときに二度と見つからない。

**流用すると決めた分は、対応表に行を作る**(**置き場は既存の区分に従う** — モジュールに属するものは `tests/<module-slug>.md`、複数のモジュールをまたぐ E2E のシナリオは `tests/e2e.md` である) — 受け入れ基準の条項に結び付け、`@req:<ID>` の印を付ける。**印の付かない流用は、集計にも照合にも現れない。**

**承認は要らない。これは設計の判断である**(DS-01 の委任の範囲)。**ただし E2E のシナリオは例外である** ★ — `tests/e2e.md` に行を作れるのは **02 が `E2E-nn` として持っているシナリオだけ**で(`03-impl.md`「tests/」)、**02 の一覧に無い E2E を流用して行を足さない。** 価値があるなら、上の「移植候補」として記録し、**02 にそのシナリオを足すことを提案する**(足すかどうかは 02 の持ち主が決める)。

ただし**上の4つを満たすと判断した理由**は「テスト設計の判断」に残す — 後から見て、流用が妥当だったかを確かめられるようにするためである。

同値分割・境界値分析・デシジョンテーブル・状態遷移・エラー推測の選び方は `references/techniques.md`。すべてを E2E にせず、計算やバリデーションは単体、外部依存との境界は結合、画面をまたぐ業務フローは E2E に割り当てる。

**導出結果の置き場は `docs/03-impl/tests/<module>.md` の対応表と「テスト設計の判断」(DS-01 の開示)。**E2E の対応は `e2e.md`、共通の流儀は `strategy.md` に置く。構造・状態の値・参照の持ち方は `03-impl.md`「tests/」と `.claude/templates/03-tests-*.md` が正。独自の観点マトリクス文書や2部構成のテスト仕様ドキュメントは作らない。02 の一覧に無い E2E シナリオを独断で足さない。

**期待値とアサーションの隔離執筆は `delegation.md` §2.2 が唯一の正。**ここでは適用段階や例外を定義しない。依頼文の雛形と汚染の徴候だけを `references/isolated-authoring.md` に置く。

## 2. 配置と命名

判断基準は「実装が移動したら一緒に移動すべきか」。単体は実装の隣、結合・E2E・スモークは `tests/` 配下に置く。具体的な言語の配置はプロジェクトの `docs/03-impl/tests/strategy.md` に合わせる。

| 種別 | 配置例 |
|---|---|
| 単体 | `src/order/calculate-tax.test.ts` |
| 結合 | `tests/integration/order/checkout.test.ts` |
| E2E | `tests/e2e/specs/checkout.spec.ts` |
| スモーク | `tests/smoke/critical-path.spec.ts` |
| マイグレーション | `tests/migration/2026-09-add-order-status.test.ts` |

`tests/` 直下はテストレベルを表し、機能の横断的な分類はタグで表す。単体・結合は `.test.*`、ブラウザを起動するものは `.spec.*`。CLI の配置と固有の観点は `references/cli-variant.md`。

**テスト名は「〜のとき、〜になる」。**前提と期待を両方入れ、バグ再現テストは issue ID も含める。

```typescript
test('regression #1234: 同一の冪等キーで2回POSTしたとき、注文は1件になる', ...)
```

`smoke/` は本番で実行可能な、副作用を起こさないテストだけを置く。データを作る E2E と混ぜない。E2E を書く前に `references/evidence-wiring.md` を読み、`TESTRUNNER_ARTIFACTS` 配下への出力と失敗時の証拠を配線する。

## 3. タグ

ディレクトリは実行の重さ、タグは何を検証するかを表す。タグの組合せをスイート名に結ぶ宣言は `tests/suites.yml`。

| タグ | 付ける対象 |
|---|---|
| `@critical` | 認証・認可、主要業務、決済・課金、データ作成/更新の主経路 |
| `@smoke` | 本番で実行可、副作用なし。`tests/smoke/` のみ |
| `@req:<ID>` | 受け入れ基準・要件の実在 ID。対応するテストに必ず付ける |
| `@regression:<issue>` | バグ再現テスト |
| `@a11y` / `@perf` | アクセシビリティ / 性能計測 |
| `@slow` / `@flaky` | 重いテスト / 一時除外中の不安定テスト |
| `@bv` / `@neg` | 境界値 / 異常系 |
| `@perm` / `@st` | 権限・認可 / 状態遷移 |
| `@conc` / `@vol` | 同時実行・冪等性 / 大量データ |

```typescript
test('@req:FR-order-01-2 @bv @neg 数量が101のとき、上限エラーになる', ...)
```

正常系専用の観点タグは無い。観点タグなしは集計上の「分類なし」であり、正常系を網羅した証拠ではない。`@perm` は観点とスイート選択の両方に使う。`require_negative_tests` はテスト名の語句の正規表現だけを見ており、`@neg` タグは判定に使わない。`@neg` はマトリクス集計用であり、異常系の網羅を保証しない。言語ごとの記法は `references/tagging-languages.md`。

**`@perf` のテストは、01 が約束した測定条件をそのまま再現する** ★ — 負荷・データ量・集計の期間と母数・失敗した応答の扱いの4つである(`.claude/directions/01-requirements.md` の `non-functional.md`)。**どれか1つでも変えたら、そのテストはその要件を確かめていない** — 空いた状態で測った値は、混んだ状態の約束を何も保証しない。**再現できないなら、テストを書く前にそう言う**: 何が再現できないかを `docs/03-impl/tests/strategy.md` の「性能測定の条件」に書き、**目標値の側を直すのか、測れないと宣言するのかを 01 へ差し戻す**(緩い条件で測って緑にしない)。**4条件の値をここに書き写さない** — 正は 01 の要件の行である。**観点タグは対応表の `種別` の写しである** ★ — 対応表の行に `境界値` と書いたなら、そのテストに `@bv` を付ける。**付け忘れても対応表は変わらない**ので、期待値を別の文脈に書かせるかどうかの判定は `種別` のほうで決まる(正は `delegation.md` §2.2)。付け忘れそのものは集計と照合の欠陥なので `--report matrix` で見つけて直す。

**付けたら必ず `--list` で対象に入ったことを確かめる。**`@critcal` の誤記は静かに選択から漏れる。`min_count` だけでは個々の付け間違いを検出できない。

```bash
./tests/tools/test-runner --suite critical --list
./tests/tools/test-runner --report traceability
./tests/tools/test-runner --report matrix
```

集計は索引であり、期待値の正しさは証明しない。タグに一度も現れない要件は出力に無いので、テスト仕様の対応表から突き合わせる。任意の `tests/test-plan.yml` を使う場合も、その正は対応表と「テスト設計の判断」であり、別の仕様体系にはしない。`@critical` を減らした理由は呼び出し元の記録に残す。

## 4. モックとデータ

**外部境界より内側はモックしない。**モックを増やしてテストを通すと、モックがモックを検証するだけになる。スタブは固定値を返し、モックは呼ばれ方(回数・引数)も検証する。結合テストで外部依存をスタブ化するときは、タイムアウト・エラー応答・リトライ・冪等性も含める。実挙動との乖離で見逃したものは結合テストで補う。

データ・乱数・時刻・外部通信・資格情報のガードレールは `delegation.md` §2 の DS-01 に従う。環境の起動は `tests/scripts/setup.sh`、作るのが高価で不変の土台はスイート専用アダプタ、テスト固有の対象は `tests/data/factories/` とフィクスチャで用意する。テスト固有の前提を共通の起動スクリプトへ持ち上げない。実行ごとの接頭辞は `TESTRUNNER_TEST_DATA_PREFIX` と `TESTRUNNER_RUN_ID` を使う。

保存した期待出力を丸ごと比較する golden ファイル(保存済みの期待値ファイル)の配線・正規化は `references/golden.md`。更新の権限は DS-01 が正である。画面の見え方を同じ形で持つ基準画像は `references/visual-baselines.md`。**あれだけは合否に入れない** — 規範の正は `.claude/directions/ux.md`「見え方の基準」である。

## 5. 「そのテストは失敗しうるか」

新規・期待値を変えたテストの欠陥注入の正は `delegation.md` §2.2、不具合修正前に赤を見る手順は `/build` §3。不安定なテストの扱いは `/verify-tests` §1、失敗の振り分けは同 §2 を使う。期待値をずらすだけでは、実装を呼ばない定数比較でも赤くなる。確認するのは製品の不具合を検出できることである。

再現テストは「エラー画面が出ない」だけでなく「同一の冪等キーなら注文が1件」という、受け入れ基準・契約の不変条件を検証する。根本原因の層にレベルを合わせ、起動失敗や依存不足による赤をバグ再現と数えない。

## 6. 呼び出し元へ返すもの

導出元の ID と対応表のパス、選んだ観点・レベルと DS-01 の判断、テストの配置・タグ確認の結果、隔離側から返った未解決の質問を返す。作者と欠陥注入の証拠は `/build` §3 の進捗メモへつなぐ。判断が必要な質問は `delegation.md` §1 の問う基準を通す。このスキル独自の承認記録・鮮度スタンプ・SSOT は作らない。
