# プロダクト種別による読み替え

出典: `testing-structure.md` 11章 / `idea-revise.md` 4.9。
出典の docs/ は配布元(systest)の一次資料であり、このプロジェクトには無い。

**構築フローと試験フローの責務は変えない。**実行方法は `02-design/environments.md`、失敗の振り分けは `/verify-tests` §2 が正。タグ語彙と宣言ファイルのスキーマは同じものを使う。

**差し替わるのは3点だけ。**

| | Web サービス | CLI ツール |
|---|---|---|
| **E2E の実体** | ブラウザ操作（Playwright） | 子プロセス起動 + 出力の golden |
| **dev 検証の代替** | 共有 dev 環境 | プレリリースチャネル + 製品の成果物のインストール検証 |
| **復旧手段** | フィーチャーフラグOFF / ロールバック | パッチ版 + 非推奨マーク |

---

## 種別ごとの3点

| 種別 | E2E の実体 | dev 検証の代替 | 復旧手段 | リリース判定 の重み |
|---|---|---|---|---|
| **Web サービス** | ブラウザ操作 | 共有 dev 環境 | フィーチャーフラグOFF / ロールバック | 標準 |
| **CLI ツール** | 子プロセス起動 + golden | プレリリースチャネル + インストール検証 | パッチ版 + 非推奨マーク | **大** |
| **ライブラリ** | 利用側サンプルでのビルドと実行 | プレリリース版 + 主要利用先での事前検証 | パッチ版 + 取り下げ | **大** |
| **バッチ / ジョブ** | 実データ相当での実行 + 冪等性・再実行・中断復帰 | dev で縮小データセット | 再実行 / 補正ジョブ | 標準 |
| **API サーバ（画面なし）** | HTTP クライアントでの契約テスト + スキーマ検証 | 共有 dev 環境 | フィーチャーフラグOFF / ロールバック | 標準 |
| **モバイルアプリ** | 実機・シミュレータでの操作 | 内部テスト配信 | **不可**（審査待ち）→ リモート設定で機能を切る | **最大** |

**復旧手段が弱いほどリリース判定の重みが増す。**Web は「フィーチャーフラグOFFで退避できる」前提で判定を短縮できるが、CLI・ライブラリ・モバイルにはその根拠がない。

---

## CLI ツール — ディレクトリの差分

置き換えは3つ。**`e2e/` → `cli/`**、**`a11y/` → `tty/`**、そして **`install/` と `compat/` の新設**。

**ただし「変わらない」のはファイルの並びだけで、中身は書き替えが要る** ★ — 下の
「宣言ファイルの書き替え」を必ず読むこと。読まずに進むと、**出荷前の全体試験が対象0件で
必ず落ちる。**

```
tests/
├─ suites.yml / environments.yml / gates.yml / quarantine.yml   ← ファイルは同じ(中身は下記)
├─ integration/               結合（変わらない）
├─ cli/
│  ├─ specs/                  ビルド済み実行ファイルを起動して検証
│  ├─ golden/                 期待出力（--help / --json / エラーメッセージ）
│  └─ trees/                  入力となるファイルツリーのフィクスチャ
├─ install/                   ★ 新設。CLI では最重要
│  ├─ from-pack.test.*        ビルド成果物から
│  ├─ from-registry.test.*    公開後、レジストリから
│  └─ images/                 クリーンなコンテナ定義
├─ compat/matrix.yml          ★ 新設。OS × シェル × ランタイム × アーキ
├─ smoke/                     公開後のスモーク（レジストリから実際に入れる）
├─ nonfunctional/
│  ├─ performance/            起動時間・大入力処理
│  └─ tty/                    ← a11y/ の置き換え
└─ support/
   ├─ sandbox.<ext>           ← guards.<ext> の CLI 版
   └─ golden.<ext>            正規化と比較
```

## なぜ `install/` が最重要か

**CLI のリリース事故は、ほぼすべてパッケージングで起きる。**

- 公開アーカイブに必要なファイルが入っていない（`files` / `.npmignore` / `MANIFEST.in` / `go:embed` の設定漏れ）
- 実行ファイルのシェバンや実行権限が壊れている
- 実行時に必要な依存が開発依存に入っていた
- インストール後スクリプトがユーザー環境で失敗する
- ビルドしたバイナリのアーキテクチャが違う

**これらはリポジトリ内で実行するテストでは1つも検出されない。**リポジトリには全ファイルが揃っていて依存も全部入っているため、テストは通る。

ビルド成果物からのインストール検証は**毎PRで回す**。`adapters.yml` の `install` に実際の検証コマンド（文字列）を定義し、`test-runner --suite install --env built` で実行する。たとえば Node プロジェクトなら次のようにし、`from-pack.test.ts` が成果物を一時ディレクトリへインストールして動作を検証する。

```yaml
adapters:
  typescript:
    root: .
    install: "./tests/modules/node_modules/.bin/vitest run {paths} -t '{name_filter}' --reporter=junit --outputFile={report_out}"
    report: junit
```

`install` は `from: pack` という設定オブジェクトを受け取るキーではない。成果物の準備はビルド工程で行い、検証対象のパスは環境変数などでテストに渡す。

「1つ前のバージョンを入れ直せる」の確認が、Web のダウンマイグレーション確認に相当する。

## CLI 固有のテストタイプ

**Web の「画面」に相当するものが「出力とプロセスの振る舞い」**なので、そこが厚くなる。

| テストタイプ | 何を確かめるか | 置き場所 |
|---|---|---|
| **終了コード** | 成功は0、失敗は種類ごとに固定の非0。**スクリプトから分岐に使われる API** | `cli/` |
| **stdout / stderr の分離** | データは stdout、ログ・進捗・警告は stderr。パイプしても壊れない | `cli/` |
| **出力の互換性（golden）** | `--help`、`--json`、エラーメッセージのスナップショット固定 | `cli/golden/` |
| **引数・設定の優先順位** | オプション > 環境変数 > 設定ファイル > 既定値 | `cli/` |
| **TTY / 非TTY** | パイプ時に色・スピナーを出さない。`NO_COLOR` / `TERM=dumb` を尊重 | `nonfunctional/tty/` |
| **stdin** | パイプ入力、EOF、空入力、バイナリ入力 | `cli/` |
| **シグナル** | `SIGINT` で中断したとき一時ファイルを残さない・状態を壊さない | `cli/` |
| **冪等性・再実行** | 二重実行、中断後の再実行が安全か | `cli/` |
| **ファイルシステム安全性** | 想定外のパスへ書かない。相対パス・シンボリックリンク・空白や日本語を含むパス | `cli/` |
| **インストール検証** | **製品の成果物**から入れて起動できるか(キットの配布物ではない) | `install/` |
| **互換性マトリクス** | OS × シェル × ランタイム × アーキ | `compat/` |
| **ロケール・文字幅** | 日本語・絵文字を含む出力の桁揃え、`LANG=C` での動作 | `compat/` |

## アクセシビリティの読み替え

`axe` は使えないが、対応する関心事は存在する。`nonfunctional/tty/` でまとめて検証する。

| Web での関心 | CLI での対応 |
|---|---|
| スクリーンリーダーで読めるか | 色・記号だけで情報を伝えていないか（色を落として意味が残るか） |
| キーボードのみで操作できるか | 対話プロンプトに非対話の代替（オプション / `--yes`）があるか |
| コントラスト比 | `NO_COLOR` / `TERM=dumb` の尊重、`--no-color` |
| 機械可読性 | **`--json` などの構造化出力**があるか。人間向け整形と機械向け出力を分けているか |

## 環境軸の読み替え

`local / dev / production` が「**どこからバイナリを持ってくるか**」の3段に置き換わる。

```yaml
environments:
  source:      # 構築フロー の高速ループ。ソース直接実行
    allow: { write: true, destructive: true, home: sandbox, network: stub }
    suites: ["*"]
  built:       # ビルド成果物
    allow: { write: true, destructive: true, home: sandbox, network: stub }
    suites: ["*"]
  prerelease:  # dev 環境の代替
    allow: { write: true, destructive: false, home: sandbox, network: sandbox }
    suites: [cli, install, compat, smoke, tty]
  released:    # 公開済み安定版
    allow: { write: limited, destructive: false, home: sandbox, network: blocked }
    suites: [smoke]
```

上の例で `allow` に **`home`** が加わっているのが、CLI 版のテスト環境の隔離である(下の「テスト環境の隔離 の CLI 版」)。

`--print-schema` で確認できる環境のキーは `allow` / `suites` などであり、`target` は存在しない。`--env built` は許可とスイートを選ぶだけなので、実行対象はプロジェクト独自の環境変数で明示する。

```bash
CLI_TARGET="$PWD/dist/bin/my-tool" ./tests/tools/test-runner --suite cli --env built
```

CLI テスト側で `CLI_TARGET` を読み、絶対パスでその実行ファイルを起動する（ランナーが自動で解釈する変数ではない）。**変数の名前はプロジェクトが決める** — 共用の `environments.yml` のコメントは `MYTOOL_BIN` を例に挙げているが、どちらも総称であって規約ではない。

## 宣言ファイルの書き替え — 画面を持たない製品では必須 ★

**放置すると出荷前の全体試験が必ず落ちる。** 既定の `f4-e2e` は `e2e-full` というスイートを
呼び、そのスイートは `tests/e2e/**` だけを探す。上のとおり `e2e/` を `cli/` に置き替えると、
**対象が0件になる。** `f4-e2e` は `strict: true` を持つので、0件は skipped ではなく
**不合格**に昇格する(`references/declarations.md` の `strict` の節)。製品に不具合は
1つも無いのに、出荷の判定が通らない。

**誰がいつ書き替えるか**: **導入したプロジェクトが、テスト基盤を入れた直後に書き替える。**
`/setup` は雛形を逐語で展開するだけで宣言の中身を決めない(判断だからである)ので、
**ここを引き継ぐのはプロジェクトの側である。** 書き替えは3か所:

| ファイル | 何をするか |
|---|---|
| `tests/suites.yml` | コメントアウトされている `cli` / `golden` / `install` / `compat` / `tty` の定義を有効にする。`e2e-local` / `e2e-full` は消してよい(使わないので、残すと0件の元になる)。**`critical-e2e` は消さず、`include` を `tests/cli/**/*.spec.*` に替える**(下の注を読むこと) |
| `tests/gates.yml` | `f4-e2e` の `e2e: { suite: e2e-full, ... }` を `cli: { suite: cli, ... }` に替える。**`f4-critical` の `e2e` ステップは消さない** — ステップ名はそのままにして、`critical-e2e` の中身(上の行)を替える |
| `docs/02-design/environments.md` | 表の「E2Eテスト」の行の**コマンド文字列**を、実際に打つものへ直す(テスト実行ゲートの名前 `f4-e2e` は変わらないので、多くの場合この行に手は要らない。環境の指定を替えたときだけ直す。**この表の文字列が正であり、スキルは逐語で打つ**) |

| `tests/environments.yml` | **流してよいスイートを名前で列挙している環境には、`critical-*` を足す** ★ — 上の例の `prerelease` のように `suites: [cli, install, …]` と列挙している環境では、**列挙に無いスイートは環境の関所が `exit 3` で弾く**(`suites: ["*"]` の環境は素通しなので何もしなくてよい)。重要テストを流す環境には `critical-unit` / `critical-integration` / `critical-e2e` を加える |

**`f4-critical` の `e2e` ステップを消してはならない** ★ — 試験の手順は
`--gate f4-critical --only e2e` を**ステップ名で名指しして打つ**ので、消すと
「該当するステップがありません」で `exit 2` になり、**その試験区分の run が毎回止まる。**
`f4-critical` に `strict` は無く、`critical-e2e` の最小件数もコメントアウトされているので、
**中身が0件でも skipped で通る** — 消す必要がそもそも無い。
そして画面を持たない製品にも重要テストは在りうるので(`tests/cli/` の下)、
**消すとその保護だけが静かに外れる。**

**`f4_scopes`(出荷時に合格を求める試験区分の一覧)はそのままでよい** — `e2e` という試験区分の
名前は残り、その中で何を実行するかが `gates.yml` の側で替わるだけである。
**試験区分そのものを外せるのは、人が直接操作する面(画面もサブコマンドも)が1つも無い成果物だけである。**
画面が無いだけでは外せない — サブコマンドが在るなら探索的CLI QA が走る
(`.claude/skills/cli-qa/SKILL.md`。規範の正は `.claude/directions/ux.md` §0)。

## テスト環境の隔離 の CLI 版 — サンドボックスの強制

Web の「本番データを触らない」に相当するのが、CLI では「**開発者自身の環境を壊さない**」。しかもこちらのほうが事故が起きやすい。

1. テストが開発者の `~/.config/<tool>/` を読み書きして**手元の設定を壊す**（あるいは手元の設定に依存してテストが通り、他人の環境で落ちる）
2. テストが**本物の API を叩く**（認証情報が手元にあるので気づかない）
3. テストがカレントディレクトリのファイルを**消す・上書きする**

規律ではなく仕組みで防ぐ。

- **`HOME` / `XDG_CONFIG_HOME` / `XDG_CACHE_HOME` / `APPDATA` を一時ディレクトリに差し替える。**差し替えられていなければテストを実行しない
- **cwd はテストごとに新しい一時ディレクトリ**にする
- **ネットワークは既定で遮断**し、`blocked` で送信しようとしたら遮断だけでなくテストを失敗させる
- **実行ファイルは絶対パスで固定する。**`PATH` 経由で起動すると、開発者がグローバルインストールした別バージョンを叩いていることに気づけない

最後の点は地味だが実害が大きい。`PATH` 越しだと「手元では通るが CI で落ちる」の原因が特定できない。

## 互換性マトリクス

```yaml
# tests/compat/matrix.yml
minimal:                        # 毎PR（試験フロー）
  os:      [linux]
  runtime: ["<最小サポート版>", "<最新版>"]
  shell:   [bash]

full:                           # 試験フロー 相当 / ナイトリー
  os:      [linux, macos, windows]
  runtime: ["<最小サポート版>", "<LTS>", "<最新版>"]
  shell:   [bash, zsh, powershell]
  arch:    [x64, arm64]
  env:
    - { NO_COLOR: "1" }
    - { TERM: dumb }
    - { LANG: C }
    - { tty: false }
```

- **最小サポート版のランタイムを必ず含める。**最新版だけで通しているとサポート宣言が嘘になる
- **Windows を入れるなら最初から入れる。**パス区切り・改行コード・シェバン・実行ファイルの解決が根本的に違うため、後から追加すると大量の修正が必要になる
- `env` の4つは軽いので `minimal` に入れてよい。とくに `tty: false` は事故が多い（パイプするとエスケープシーケンスが混入する）

## リリース・復旧の読み替え

| Web での手段 | CLI での対応 | 効き方 |
|---|---|---|
| フィーチャーフラグ OFF | 設定 / 環境変数での無効化、新機能は既定OFFで出す | **ユーザーの手元では即座に効かない** |
| ロールバック | **できない。**公開したバージョンは取り消せない | 代替は「パッチ版を出す」+「壊れた版に非推奨マーク」 |
| Canary / 段階公開 | プレリリースチャネル + 社内先行利用 | **自発的に入れた人にしか届かない** |
| Expand-Contract | **非推奨サイクル**: 追加 → 旧に非推奨警告 → メジャーで削除 | 対象はオプション名・終了コード・stdout形式・設定キー・既定値 |
| 監視 | テレメトリ（opt-in）、クラッシュレポート、issue 流入、ダウンロード数 | **ほぼ効かない** |
| 四半期のロールバック訓練 | **パッチ版を最短で公開する訓練** | 権限・鍵・二要素認証が実際に通るかを障害時以外に確かめる |

**この表の最後の行(定期の訓練)は、このキットの決まりではない** ★ — **運用はこのキットの
守備範囲の外である**(2026-09-11 の裁定)。ここに残してあるのは、**復旧手段が弱い製品では
何を考えておくべきかの参考**としてであって、**やることの一覧ではない。**
**頼まれてもいない訓練の段取りを始めない。**

**下の項目も、出荷の判定の条件に自動で加わるわけではない** ★ — 出荷してよいかの条件は
`.claude/directions/core.md` §3 が持つ唯一の一覧であり、**そこに無いものは条件ではない。**
ここに並べたのは、**画面を持たない製品では何が効かなくなるかを示す材料**である。
条件として足したいなら、**プロジェクトがそう決めて、プロジェクトの文書に書く** — 置き場は
`docs/01-requirements/system.md` の「必須制約(交渉不可能)」か、`docs/pendings.md` の棚上げである。
**このキットの `CLAUDE.md` を書き換えない** — あれはどのプロジェクトへ配っても成り立つことだけを
書く場所で、1つのプロジェクトの合意を入れる場所ではない。

**参考として考えておくとよい項目:**

- 1つ前のバージョンに戻せることを確認（ダウングレード手順が動くか）
- 破壊的変更の有無をレビュー観点として明文化（オプション名 / 終了コード / stdout形式 / 設定キー / 既定値 / 最小サポートランタイム）
- プレリリースチャネルでの実使用期間を設ける（Web の「dev 環境での検証」の代替が **時間** になる）

## 性能の対象が違う

CLI で効くのは**起動時間**（毎回のコマンド実行で体感する）と**大入力の処理時間**。レスポンスタイムやスループットではない。**起動時間はライブラリを1つ増やすだけで悪化する**ため、baseline 比較を入れる価値が高い。
