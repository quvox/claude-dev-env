# 隔離執筆の依頼文と汚染の徴候

**規範の正は `.claude/directions/delegation.md` §2.2。**ここは依頼文の雛形と出力の点検だけを持つ。起動方法・渡せる情報・配線との分担・赤いときの再依頼・記録は、その節に従う。

## 依頼文の雛形

パスと条項 ID は対象に合わせて置き換える。受け入れ基準と契約の本文をコピーせず、読む場所を名指す。

```text
あなたは期待値とアサーションを書く担当です。製品コードを読まないでください。

対象: <受け入れ基準の条項 ID>、観点 <境界値 / 異常系 / 権限など>
出力先: <テストコードのパス>

読んでよいパスと節(ここに挙げたものだけ):
  <docs/01-requirements/...md の対象条項>
  <docs/02-design/contracts/...md の公開契約、入出力の型、エラーの仕様>

読んではいけないもの:
  製品コード、実装方針、内部の設計詳細、修正差分・コミット、実装者の期待する値

書き方:
  テスト名は「〜のとき、〜になる」。バグ再現テストには issue ID を入れる。
  @req:<実在の条項ID> と観点タグを付ける。
  根拠にした条項・契約の節をコメントに残す。
  配線が分からない箇所は TODO(wiring): <必要なもの> を残す。
  受け入れ基準から期待値が決まらない箇所は推測せず、質問で返す。

返すもの:
  テストコード、読んだパスの一覧、判断できなかった点の質問
```

バグ再現では issue ID と症状の再現手順を対象の識別に使い、期待値の根拠は許可した受け入れ基準・契約に置く。修正方針や原因箇所のコードを渡さない。隔離側の質問は消さず、`delegation.md` §1 の問う基準を通してシートへつなぐ。

## `critical: true` の作業では、製品コードを含まない作業ディレクトリを渡す ★

構築記録に `critical: true` と記録した作業(認証・決済・不可逆な操作・個人データ・監査可能性に触れるもの)では、**上の依頼文に加えて、製品コードを含まない作業ディレクトリを用意して、そこを作業場所として渡す。**

- 置くもの: 対象の受け入れ基準・契約・入出力の型・エラーの仕様と、テストコードの出力先。
- 置かないもの: 製品コード、実装方針、修正差分。
- 依頼文の「読んでよいパスと節」は、そのディレクトリの中のパスで書く。

**理由**: 指示で「読むな」と書いても、手元に読めるものが在るかぎり、読まなかったことは確かめられない。期待値が実装の写しになると**テストは緑のまま実装の誤りを追認する**ので、金額・権限・データ破壊として本番で表面化する。下の「汚染の徴候」は読んだ後の点検であり、写した期待値を必ず見抜けるとは限らない。

**`critical: true` でない作業では、このディレクトリを作らない。**毎回作ると手数が増え、本当に分離が要る場面まで負担を理由に省かれる。分離の強さを危険度に合わせるのが狙いである。

**どこまで隔離するかは3通りある**(正は `delegation.md` §2.2 の表): **隔離なし**(表示・文言・低リスクの正常系。**実装を知っている側が書いてよい**)/ **分けて書かせる**(上の依頼文の形。対応表の `種別` が 境界値 / 異常系 / 権限 / 状態遷移 / 同時実行 / 大量データ のもの、重要経路、不具合の再現テスト。**コードの印はその写しであって、判定の根拠ではない**)/ **作業場ごと分ける**(この節。分けて書かせるのに作業ディレクトリを足したもの)。**この資料だけを読んで「全件に隔離が掛かる」と読まないこと。**

## 汚染の徴候

| 徴候 | 点検すること |
|---|---|
| 内部関数・private フィールド・内部定数の名前が現れる | 許可した公開契約には無い名前ではないか |
| 仕様に無いエラー文言が実装と一致する | 期待値の根拠が実装になっていないか |
| ケースが実装の分岐と1対1で対応する | 仕様の区分から導出されたものか |
| 「実装では〜しているので」というコメント | 許可した情報の外を根拠にしていないか |
| 根拠コメントが条項でなく「現在の挙動」を指す | 現行挙動をそのまま期待値にしていないか |

徴候は疑いの入口であり、自己申告だけで独立性を証明しない。根拠を突き合わせ、汚染した部分は実装側で期待値を書き換えず、§2.2 に従って情報を整えて再依頼する。質問なしで大量のケースが返ったときも、仕様に無い判断を埋めていないか確認する。
