# テスト設計技法

出典: `idea-revise.md` 2.1(テスト設計) / 4.8。
出典の docs/ は配布元(systest)の一次資料であり、このプロジェクトには無い。

**技法は「観点の抜けを機械的に見つける道具」。**思いつきでケースを挙げると必ず正常系に偏るので、どれかを当てはめて網羅する。

---

## 使い分け

| 対象の性質 | 使う技法 |
|---|---|
| 入力に範囲がある（数値・文字数・日付・件数） | 同値分割 + **境界値分析** |
| 複数の条件が絡む | **デシジョンテーブル** |
| ステータスを持つ | **状態遷移テスト**（必須） |
| 過去に類似のバグがある | エラー推測 |

---

## 同値分割

入力を「同じ結果になるグループ」に分け、各グループから代表値を1つ選ぶ。全ての値は試せないので代表値で網羅する。

```
数量: 1〜100 が有効
  → 無効（下）: 0 以下
  → 有効:       1〜100
  → 無効（上）: 101 以上
  → 型が違う:   空文字、null、小数、負数、文字列
```

**最後の行を忘れやすい。**「有効値のグループ」と「無効値のグループ」だけでなく、**そもそも型・形式が違う入力**を必ず1グループとして立てる。

---

## 境界値分析

グループの境界に不具合が集まるという経験則。**境界とその前後**を試す。

```
上限100  →  99 / 100 / 101
下限1    →   0 /   1 /   2
```

境界は数値だけではない。

| 種類 | 境界の例 |
|---|---|
| 文字数 | 0文字、1文字、最大長、最大長+1 |
| 日付 | 月末、月初、閏日、年またぎ、**タイムゾーン境界** |
| 件数 | 0件、1件、ページサイズちょうど、ページサイズ+1 |
| 時刻 | 00:00:00、23:59:59、日付が変わる瞬間 |

**ページサイズちょうど／+1 は本番データ量で初めて露出する類型。**大量データの観点と重なる。

---

## デシジョンテーブル

複数条件の組み合わせを表にして網羅する。条件が絡む仕様の抜けを可視化できる。

| # | ログイン済み | 所有者 | 公開設定 | 期待 |
|:-:|:-:|:-:|:-:|---|
| 1 | ○ | ○ | 非公開 | 閲覧できる |
| 2 | ○ | × | 非公開 | **403** |
| 3 | × | — | 非公開 | **401** |
| 4 | ○ | × | 公開 | 閲覧できる |
| 5 | × | — | 公開 | 閲覧できる |

**「期待が拒否になる行」が権限テストの本体。**表を作ると、この行が抜けていることが一目で分かる。条件が3つあれば最大8通りで、そのうち何行を実装したかを数えられる。

---

## 状態遷移テスト

状態を持つ機能では必須。**遷移可能な経路と、遷移してはいけない経路の両方**を試す。

```
下書き → 申請中 → 承認済 → 公開
           ↓
         却下

試すもの:
  正常な遷移      下書き→申請中、申請中→承認済、承認済→公開
  禁止された遷移  下書き→公開（申請を飛ばす）、公開→申請中（巻き戻し）
  自己遷移        申請中→申請中（二重申請）
  終端からの遷移  公開→承認済
```

**禁止された遷移が抜けやすい。**「できること」だけをテストすると、直接 API を叩いて状態を飛ばす経路が守られない。

## エラー推測

過去の不具合から「ここも同じでは」と逆引きしてケースを起こす。構築フローの原因調査で得た観点は、`docs/03-impl/tests/<module>.md` の対応表と「テスト設計の判断」へ反映し、次のケース導出に使う。

**新しいモジュールのテストを設計するときは、他のモジュールの「テスト設計の判断」も横断して読む** ★ — 不具合の型はモジュールをまたぐ(同じ勘違いを別の場所でもう一度やる)。**書いた場所にしか残らないので、読みに行かなければ「その教訓は無かった」のと区別が付かない。** `docs/03-impl/tests/` の下を一覧して、各ファイルの「テスト設計の判断」の節に目を通す(量が多いときは読む対象を絞ってよいが、**絞ったことを判断の節に1行残す**)。

汎用の類型:

| 類型 | 具体例 |
|---|---|
| 二重実行 | 二重送信、リトライ、Webhook の重複配信 |
| 部分失敗 | 3件中2件成功したときのロールバック |
| 順序 | 非同期処理の完了順が逆転する |
| 空・NULL | 一覧が0件、任意項目が未入力、外部APIが空配列を返す |
| 型の境界 | 桁あふれ、浮動小数の丸め、文字コード |
| 時刻 | 処理中に日付が変わる、サーバとクライアントの時差 |
| 権限の変化 | 処理の途中で権限が剥奪される |

## テストレベルへの割り当て

技法で挙げたケースを、どのレベルで実行するかを決める。**ここを決めないと、全部を E2E に置いて遅くて壊れやすいスイートになる。**

| ケースの性質 | レベル |
|---|---|
| ロジック・計算・バリデーション・境界値 | **単体** |
| 外部依存との境界（タイムアウト・エラー応答・リトライ・冪等性） | **結合** |
| 画面をまたぐ業務フロー、認可の画面越しの確認 | **E2E** |
| 実システムで受け入れを照合する | 試験フローの AC 照合(`/verify-tests` §1) |

**認可は2層で見る。**ロジックとしての可否は単体/結合、画面越しの権限は E2E。構築フローでは触ったテスト、試験フローでは試験区分の全件を実行する。

## 導出結果の置き場

`docs/03-impl/tests/<module>.md` の受け入れ基準⇄テストの対応表に結び、観点・技法・レベルを選んだ理由を「テスト設計の判断」に DS-01 の開示として残す。E2E の対応は `e2e.md`、共通の流儀は `strategy.md` が持つ。構造と状態の値は `03-impl.md`「tests/」と `.claude/templates/03-tests-*.md` に従う。別のケース一覧文書や観点マトリクス文書は作らない。
