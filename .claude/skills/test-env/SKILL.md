# テストを走らせられる状態にする

**`tests/` は在るのにテストが動かない**ときの入口である。**フローの外に在る参照スキルで、
SSOT は1バイトも書かない。**

**`tests/` がまだ無いなら `/setup` が先である**(あちらが雛形を展開する)。
あちらがやるのは**判断の要らない展開まで**である。**そこから先は、対象で担当が分かれる** ★:

| 何を書くか | 担当 |
|---|---|
| `tests/scripts/bootstrap.sh`(依存を入れる手順そのもの) | **このスキル**(下の1章) |
| `tests/scripts/setup.sh` / `teardown.sh` / `reset.sh`(環境の起動・停止・作り直し) | **このスキル**(下の5章。**これらも空で配られる**) |
| `tests/modules/` の依存の宣言(`package.json` / ロックファイル / `requirements.txt`) | **このスキル**(同上。`bootstrap.sh` が読むものなので一緒に用意する) |
| `tests/adapters.yml`(言語ごとのテストの実行コマンド) | **`/build`** — 触ったモジュールが使う言語のぶんずつ埋める |
| `tests/` の残りの宣言(`suites.yml` / `gates.yml` / `environments.yml` / `quarantine.yml` / `test-plan.yml`) | **`/build`**(不備は `/verify-tests` が `origin_layer: 02` の課題票にする) |
| `tests/environments-guide.md`(接続先・疎通確認・資格情報の入手先) | **このスキル**(下の4.5章) |

**このスキルは `adapters.yml` を埋めない** — 埋まっていなければ、そう報告して `/build` へ渡す。

**「実行した」で終わらせない。** `bootstrap.sh` が終了コード0でも、依存の入り先が違う・
連結が無い・ブラウザが未取得、といった理由でテストは動かない。**動くことを確かめるまでが範囲。**

---

**この資料に出てくるコマンドは標準的な配置の例である** ★ — **実行する前に
`docs/02-design/environments.md` の表と照合する。** あの表の文字列が正であり、スキルはそれを
そのまま打つ(`02-design.md`)。スクリプトの名前も配置も、プロジェクトが分けていることがある。

**表がまだ無いこともある** ★ — `/setup` はあの文書を作らない(コマンドが実在してから書く)。
**そのときは標準の配置で進めてよい。決めた文字列は §7 の報告に出す** — 表に書くのは `/build` の
仕事であり、**このスキルは SSOT を書かない。**

**`bootstrap.sh` は「仕組み」なので、その説明の置き場は `03-impl/environments/` である**
(`features.md`)。**ここでは書かない** — 何を書いたかを §7 の報告に出し、**`/build` が
そちらへ残す。**

---

**書く前に、保護ブランチに居ないことを確かめる** ★ — **どの章から始めても掛かる。**
このスキルが追跡対象のファイル(`tests/scripts/` のスクリプト、`tests/modules/` の依存の宣言、
`tests/environments-guide.md`、`tests/.gitignore`)を1バイトでも書くなら、**その前にここを通る。**
非0で戻ったら**止めて報告する**(`git branch -D` を打たない。規則の正は `flows.md` §7.1):

```bash
python3 .claude/scripts/guard-branch.py --slug test-env
```

**何も書かずに終わる run では打たない** — 0章(足りないものを見る)と6章(テストが動くかを
確かめる)だけを回す診断がこれである。何も書かないのに枝を作って切り替えることになる
(`/dependabot` が同じ理由で打たないことを明文にしている)。

## 0. 何が足りないかを先に見る

**テストは動くが、試験のビルドがディスクを埋める・CI の実行機で溢れる・遅い、という症状なら、
この章ではなく `references/build-footprint.md` へ進む**(測るのはこのスキルでもできるが、
設定を変えるのは `/build` である)。

```bash
test -d tests || echo "tests/ が無い → /setup が先"
ls tests/scripts/ 2>/dev/null
./tests/tools/test-runner version
```

**`tests/tools/bin/` は git 管理されているので、clone した時点で動くのが正しい。**
ここで失敗するのは依存の問題ではない。

| 症状 | 原因 | 対処 |
|---|---|---|
| `... が見つかりません` | このプラットフォームの実行ファイルが意図的に削除されたか、コミットし忘れ | 配布元で配布物3(実行ファイルだけの塊)を作ってもらい、`tar xzf <その tar> -C .` で展開してコミットする。`tests/` の他は触らない |
| `Permission denied` | 実行ビットが落ちている | `chmod +x tests/tools/test-runner tests/tools/bin/*` |

## 1. `bootstrap.sh` の中身を書く(まだプレースホルダなら)

**雛形は中身が空で配られる** — 実行すると「まだこのプロジェクト用に書かれていません」と出て
終了コード1になる。**何を入れるかはプロジェクト固有の判断なので、雛形には書けない。**
**書くのはここである**(`/setup` は判断の要らない展開までしかやらない)。

**書く前に、同梱の3つを読む** — `tests/modules/README.md`(依存の置き場と作り方)、
`tests/scripts/` の `README.md`(スクリプトの責務分担)、`tests/scripts/bootstrap.sh` 自身のコメント
(言語ごとの実コマンドの雛形が入っている)。**そこに書いてあることを書き直さない。**

### 守ること

- **依存は宣言も実体も `tests/modules/` に集める。** 製品側の各ディレクトリに散らさない
  (どこに何が入っているか追えなくなり、「手元では動くが他の人の環境で動かない」の原因になる)。
  **ここに集めるのはテスト専用の道具(テストの実行系・アサーションのライブラリ・ブラウザ自動化)
  である** ★ — 製品の依存を重ねて宣言しない。テストの環境に製品の依存が要るなら、製品の
  ロックファイルから入れる(版をビルドと揃えるため。`delegation.md` §2.4)。
- **Python は専用の実行環境(venv)を必ず作る。** 使うときは有効化せず、
  **実体を直接呼ぶ**(`tests/modules/venv/bin/pytest`)。有効化はこの道具の外の話なので、
  有効化されていない環境から引けない。
- **Node は連結(symlink)を必ず張る** — `tests/node_modules` → `modules/node_modules`。
  **無いと Playwright が `did not expect test() to be called here` で落ちる**(テストの側から
  ライブラリを解決できない)。
- **Go / Rust は環境変数で向ける**(`GOMODCACHE` / `GOBIN` / `CARGO_HOME` を `tests/modules/` の下へ)。
- **`tests/.gitignore`**(ルート直下のものではない)**に、除外を解除する `!` の行が在るかを見る。**
  雛形には Node・Python・Go・Rust のぶんが最初から入っているので、**それらを使うなら足す必要は
  無い。新しい言語を足したときだけ1行足す**(`tests/modules/` の `README.md`)。
  **足りないと宣言(`package.json` / ロックファイル / `requirements.txt`)が git から漏れ**、
  エラーにならないまま再現性が失われる。
- **冪等にする。** 2回目以降は「導入済み」と出て即座に終わるのが正しい。毎回フルインストールが
  走るなら作りが悪い。
- **`bootstrap.sh` と `setup.sh` を混ぜない。** 前者は「マシンを整える」(clone 直後に1回)、
  後者は「環境を動かす」(毎回)。混ぜると、テストのたびに依存の導入が走るか、逆に導入の手順が
  どこにも無い状態になる。
- **`sudo` を使う手順を足さない。** 自動で回す環境とコンテナで通らなくなる。
- **グローバルに入れて済ませない**(`npm i -g` / `pip install --user` / `brew install`)。
  その場では動くが、**他の人の環境では再現しない。**

**書いたら、末尾の終了コード1を消す。**

## 2. 実行する

```bash
./tests/scripts/bootstrap.sh
```

**失敗したら中身を読んでから対処する。** よくある原因:

| 症状 | 見るところ |
|---|---|
| ツールチェーンの版が合わない | `.node-version` / `.python-version` / `go.mod` の指定と、手元の実際の版 |
| ロックファイルと合わない | `--frozen-lockfile` で落ちているなら、ロックファイルが古いかコミット漏れ |
| 通信 | 取得元へ到達できているか(社内の中継が要るか) |
| 権限 | `sudo` が要る導入をスクリプトが含んでいないか(含むなら設計が悪い。1章へ戻る) |

## 3. 入った場所を検証する

**先に、書いたものをコミットする** ★ — `bootstrap.sh`、依存の宣言
(`tests/modules/package.json` / ロックファイル / `requirements.txt`)、`tests/.gitignore` を
触ったならそれも。**コミットしないと、下の `git ls-files` は必ず「漏れている」と出る。**
依存の**実体**(`node_modules` / `venv`)はコミットしない — あれは `.gitignore` の対象である。
**コミットは明示のパスで stage し、コミットにもそのパスを名指す**(`flows.md` §2)。

**4.5章と5章で書いたもの(環境ガイド、`setup.sh` / `teardown.sh` / `reset.sh`、実行ビット)は、
そこでもう一度コミットする** — あの章はこの章より後ろに在るので、ここでは拾えない。
**§7 の報告を出す前に、`git status` で未コミットが残っていないことを確かめる。**

**「導入が成功した」と「テストから見える」は別である。**

```bash
ls tests/modules/                       # node_modules / venv / go / cargo
ls -ld tests/node_modules               # ★ modules/node_modules への連結か
ls tests/modules/venv/bin/python        # Python を使うなら

# ★ 宣言が git から漏れていないか(.gitignore の ! の行の足し忘れ)
# ★ 見るのは**使う言語のぶんだけ**である。Node だけのプロジェクトに
#   requirements.txt が無いのは正常であって、漏れではない。
git check-ignore -v tests/modules/package.json tests/modules/requirements.txt
git ls-files -- tests/modules/package.json tests/modules/requirements.txt
#   ★ check-ignore は**除外を解除している行(! で始まるもの)も表示する**ので、
#     「何か出たら NG」ではない。出た行が ! で始まっていれば正常である。
#     **見るのは2つ**: 除外する側のパターンに当たっていないか(check-ignore)と、
#     実際に追跡されているか(ls-files に出るか)。**出ないなら漏れている。**
```

| 確認 | 期待 | 外れているとどうなるか |
|---|---|---|
| `tests/modules/` が在る | 依存の実体がここ | 各アダプタの root に散っている = 規約違反。`bootstrap.sh` を直す |
| **`tests/node_modules` が連結** | Node の解決経路に乗る | **Playwright が落ちる**(上記) |
| `tests/modules/venv/bin/` に在る | 専用の実行環境が作られた | システムの Python を汚している可能性 |
| **使う言語の宣言が `ls-files` に出る** | git 管理されている | **漏れている。** エラーにならないので気づきにくい(`check-ignore` に出るかどうかでは決まらない — 上の注) |

**連結が無いのに「なんとなく動く」場合は疑う。** 別の場所の `node_modules`(製品側のものなど)を
拾っている。版が違えば「手元では通るが他所で落ちる」になる。

## 4. 資格情報が揃っているか

**依存が入ってもテストは動かない。** 多くのテストは認証を要し、値は git に入っていない。
**ここで止まるのが、新しく入った人のいちばん多い詰まり所である。**

```bash
ls tests/.env.example                            # 何が要るかの一覧(git 管理)
ls tests/.env.* 2>/dev/null | grep -v example    # 実体が在るか
```

| 状態 | どうするか |
|---|---|
| `.env.example` が無い | 資格情報が要らないのかもしれない。`tests/environments.yml` の `secrets:` と `tests/environments-guide.md` を確認する |
| `.env.<環境名>` が無い | `cp tests/.env.example tests/.env.local` して値を入れる。入手先は `tests/environments-guide.md` |
| 入手先が書かれていない | **勝手に探さず人に聞く。** 得られた答えは環境ガイドに追記してもらう(次の人が同じことを聞かずに済む) |

**★ 値を推測で埋めない。** 空のまま進めると 401 やリダイレクトという分かりにくい形で落ち、
切り分けに時間を取られる。

**★★ 値を教えてもらおうとしない。** 要るのは「値が在ること」であって「値そのもの」ではない
(テストのプロセスが `.env` を読めば動く)。**置き場所と変数名を示して、人自身に書いてもらう。**

```
E2E_LOGIN_PASSWORD が未設定です。
tests/.env.local に追記してください(このセッションに値を貼らないでください)。
入手先: tests/environments-guide.md「資格情報」
```

**チャットに貼られた値はセッションの記録に残り、後から消せない。**
コミットしてしまった秘密情報と同じ構造の問題になる(`delegation.md` DS-01)。

**★ 本番の値を手元の `.env` に置かない。**

## 4.5 `tests/environments-guide.md` を書く(まだ雛形のままなら)

**この資料は雛形で配られる** — **章の骨格と、埋める表と、書き方の注意**(「〜のはず」を
書かない / 確かめていないことは「未確認」と明記する)が入っており、**中身を実機で確かめて
書き換える**ことになっている。**書くのはここである** ★(上の4章と下の5章で実際に調べるのが
この作業だからである)。**`tests/` の中なので SSOT ではない。**

**雛形の章を上から順に、全部見る** ★ — 下に挙げるのは落としやすいものであって、
**これだけ埋めれば終わりではない。** 各章の記入指示に従い、**該当しない章は「非該当」、
確かめられなかったことは「未確認」と明記して残す**(空欄のまま飛ばさない)。
**とくに落としやすいのは次のものである** — **数ではなく、項目そのもので点検する:**

- **環境ごとの接続先と起動の手順**
- **疎通確認の方法**(起動コマンドが成功しただけでは足りない)
- **資格情報の入手先**(「誰に聞くか」「どの保管庫か」。**値そのものは書かない**)
- **環境ごとの持ち主**(共有環境を誰が持ち、誰が壊してよいか)
- **この道具を通さない既存テストの実行経路と、印を置く1行** ★ — **経路を1つ残らず挙げる。**
  挙げ漏れた経路から既存のテストが走ると、**配線済みの側は汚染に気づけない**(印が立たない)。

**最後の2つ(持ち主と、印を置く経路)は、5章で汚れの印に出くわした人が読むところである。**
空のまま残すと次の人が止まる。

**分からないことを推測で埋めない。** 人に聞いて、聞いた答えをここへ書く —
**次の人が同じことを聞かずに済むようにするためである。**

## 5. 環境を起動する

**`setup.sh` も空で配られる** ★ — `bootstrap.sh` と同じく、実行すると
「まだこのプロジェクト用に書かれていません」と出て終了コード1になる。**中身を書くのもここである。**
`teardown.sh`(停止。データは残す)と `reset.sh`(作り直し。**破壊的**)も同じである。

**書くときに守ること**(規約の正は `tests/scripts/` の `README.md`):

- **`bootstrap.sh` と混ぜない** — あちらは「マシンを整える」(clone 直後に1回)、
  こちらは「環境を動かす」(毎回)。混ぜると、テストのたびに依存の導入が走る。
- **何度呼んでも同じ結果になるようにする**(起動済みなら何もしない)。
- **末尾の汚れの印の判定は書き換えない**(下記)。
- 環境を「起動する」概念が無いプロジェクトでは、`setup` / `teardown` / `reset` を
  **削除してよい**(`bootstrap.sh` は残す)。**削除したなら、そう `tests/environments-guide.md`
  に書く** — 次の人が「実行し忘れ」と誤解しないためである。

書けたら実行する:

```bash
./tests/scripts/setup.sh
```

**「起動コマンドが成功した」で済ませず、`tests/environments-guide.md` に書かれた疎通確認まで行う**
(起動直後はまだ受け付けていないことがある)。

**このスクリプトは「汚れの印」を見て止まることがある** — `tests/.test-env-dirty` が在ると、
**この道具を通していない既存のテストが環境を触った後だ**という意味である。**止まったら、
まずなぜ印が付いたかを調べる**(素のテストコマンドを直接叩いた可能性が高い)。作り直してよいと
判断できたら `TESTS_ALLOW_AUTO_RESET=1` を付けて呼び直す(**破壊的である**。データは消える)。
**付けてよい条件は2つあり、両方要る** ★ — **人(または自動で回す仕組み)が明示的に付けること**と、
**`tests/environments.yml` のその環境が `allow.destructive: true` を持つこと**である
(`tests/scripts/` の `README.md`)。**スクリプトが見るのは変数だけである** — `allow.destructive` の値は読まないので、
**そちらは読み手が守る。`allow.destructive` が false の環境で付けない。**
**変数を付けても止まることがある** — この道具の実行中(`TESTRUNNER_RUN_ID` が立っている)は、
テストの最中に環境を作り直さないために終了コード2で止まる。作り直す `reset.sh` が無い・
実行権が落ちている場合も止まる。

## 6. テストが実際に動くかを確かめる(ここが本題)

**順に叩く。前が通らないうちに次へ進まない。**

**その前に、テストを走らせる環境がビルドと同じ版かを確かめる** ★(2026-11-04。
`delegation.md` §2.4)— 単体・結合・E2E は、ビルドと同じ版の処理系・ツールチェーン・
実行基盤・製品の依存で走らせる。版の固定(`docs/02-design/environments.md` の「コンテナ・実行環境」)と、
テストを走らせる環境とを、**§2.4 の確かめ方で項目ごとに突き合わせる。ここは確かめるだけで、
何も書かない**(この章は診断である)。合わなかったときの行き先は、何が合わないかで分かれる:

| 合わないもの | 行き先 |
|---|---|
| このマシンに入っている処理系・ツールチェーンの版が固定と違う | 利用者の権限で入る版管理の道具(`rustup` / `pyenv` など)で入るなら、固定どおりの版を入れる手順を `bootstrap.sh` に書く(1章の規則のまま。書くなら先に保護ブランチの確認を通る)。**`sudo` や全体への導入が要るもの(Xcode・OS のパッケージなど)は書かない** — 何をどの版で入れる必要があるかを報告し、人間に入れてもらう |
| テストがビルドと同じイメージの中で走っていない / 製品の依存がロックファイルどおりに入っていない | テストを走らせるコマンド(`tests/adapters.yml`)の問題なので、報告して **`/build`** へ渡す |
| 宣言(`### ビルドとテストの版の固定` の見出し)はあるが中身が `<>` のまま | 決めずに報告して **`/build`** へ渡す(このスキルは SSOT を書かない) |
| 宣言の見出しそのものが無い(移行前) | **合否には掛からない**(`delegation.md` §2.4 の2)。見比べられた不一致だけを報告し、移行 `2026-11-05-build-test-version-pin` が未適用であることを書く。見出しは足さない |

**宣言済みのプロジェクトで、一致を確かめていない環境を「整った」と報告しない。**

```bash
# 6-1 設定が健全か(何も変更しない)
./tests/tools/test-runner setup

# 6-2 何が実行される予定か。★ skip だらけでないことを目で見る
./tests/tools/test-runner --gate f1-fast --dry-run

# 6-3 実際に走らせる
./tests/tools/test-runner --gate f1-fast
```

**`f1-fast` は単体と結合しか回さない** ★ — **E2E 用のブラウザが取れているか、E2E の資格情報が
揃っているかは、これでは分からない。** E2E を持つプロジェクトでは
`--gate f4-e2e --env <宣言した環境>` も回す。**回せない事情があるなら、
「E2E は未確認」と報告に書く**(§7)。**確かめていない試験区分を「整った」に数えない。**
**ただし `f4-e2e` は導入直後には落ちるのが普通である** — あれは証拠を厳しく要求する組なので、
対象0件・未配線・結果ファイルの欠落で不合格になる。**それは環境の問題ではない**ので、
下の切り分けの表(`f1-fast` を前提にしている)をそのまま当てない。**宣言が埋まっていないなら
`/build` へ渡す。**

| 段 | 通らないときに疑うもの |
|---|---|
| 6-1 | 宣言ファイルの不備。**この環境に固有ではない**ので `/test-runner-usage` へ |
| 6-2 | **出た理由をそのまま読む。** 「このステップを実行できるアダプタがありません」と出たなら宣言の不備なので `/test-runner-usage`(埋めるのは `/build`)、コマンドは在るが実行ファイルが見つからないなら依存のパスなので3章へ戻る。**dry-run はコマンドを表示して返すだけで、実行ファイルの存在は確かめていない** |
| 6-3 | ここで初めて「環境の問題」と「テストの問題」が分かれる(下記) |

**6-1 は導入直後、終了コード1で終わるのが正常である** — 雛形の `adapters.yml` は全部
コメントアウトで配られるからである。**埋めるのは `/build`**(触ったモジュールのぶんずつ。上の担当の表)。
**未解決が並ぶこと自体は失敗ではない。** ここでやるのは、何が未解決かを報告に写すことである。

**6-3 が落ちたときの切り分け**:

**比較は手掛かりであって、原因の決め手ではない** ★ — **エラーの中身と設定を必ず見る。**

- **他の人の手元でも同じように落ちるなら**、この環境に固有の問題ではない可能性が高い
  (テストか実装か、あるいは**全員に共通する依存の漏れや、止まっているサービス**)。
  テストか実装だと判断できたら `/verify-tests` §2 の振り分けへ。
- **自分の環境でだけ落ちるなら**、依存の実体・パス・環境変数・接続先・資格情報を順に確かめる。
  **依存の導入漏れとは限らない** — 1台だけ資格情報が空、ということも同じ形で落ちる。

## 7. 報告

**「実行しました」で終わらせない。** 何が整ったかと、残っている制約を出す。

```
テストを走らせられる状態になりました。

  test-runner  <version>(<os>-<arch> の実行ファイル)
  依存         tests/modules/ に <入ったもの>
               node_modules の連結: あり / なし
  資格情報     tests/.env.<環境名>: あり / 無い(<入手先> に依頼が要る)
  環境         setup.sh 実行済み / 対象外
  版の一致     ビルドと一致(<固定の場所>) / 不一致(<何が何と違うか>) / 固定が未記入(/build へ)
               / 未宣言(移行前。見比べられた不一致: <…> / 未確認: <…>)
  確認         test-runner setup  : 合格 / 未解決 N 件(埋めるのは /build)
               --gate f1-fast     : <結果。実行件数と skip 件数。落ちたステップは名前と理由>
               --gate f4-e2e      : <同上 / 回していないなら「未確認」と理由>
  決めた文字列 <bootstrap.sh / setup.sh の配置と呼び方。02-design/environments.md の表が
               まだ無いときに標準の配置で進めたなら、ここに出す。表に書くのは /build>
  枝とコミット <作った作業ブランチの名前と、コミットしたもの(単独運用なら人間が戻す)>

次にあなたがすること
  <落ちているなら、その切り分け(環境かテストか)>
  <テストを書くなら /test-design へ>

未了・この環境に固有の制約
  <取得できなかったもの、飛ばした手順。無ければ「無し」>
```

**「動いた」と言えるのは、版の一致を確かめたうえで(宣言済みのプロジェクトのとき)6-3 まで通ったときだけである。** 6-1 や 6-2 で止まった状態を
「環境は整った」と報告しない。

## やってはいけないこと

- **SSOT を書かない。** このスキルはフローの外に在り、`docs/` の仕様文書を1バイトも書かない。
  直すべき記述を見つけたら、報告に書いて `/build` へ渡す。
- **落ちたテストを「環境のせい」で片づけない。** 他の環境でも落ちるかを確かめる。
- **連結が無いまま「動いているように見える」状態を放置しない**(3章)。
- **資格情報を推測で埋めない。分からなければ人に聞く**(4章)。
- **本番の資格情報を手元の `.env` に置かない。**
