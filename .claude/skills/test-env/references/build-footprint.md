# 試験のビルドの生成物と時間を減らす — 測ってから減らし、変わっていないことを確かめる

日本語で書く。**この資料が正である**(同じことを他の場所に書かない。`/test-env` と `/build` の
SKILL.md は、ここを1行で指すだけである)。

**読むとき**: 開発機のディスクが試験のビルドで埋まる / CI の runner(CI の実行機)のディスクや
メモリが足りずに止まる / ビルドやテスト実行ゲート(試験を一括で回す手順)が遅い — のどれかに
当たったとき、**およびそれを直すために、試験の束ね方・ビルドの設定・CI のジョブを変えるとき**。

**誰が何をするか**: 測ること(§1)は `/test-env` の run でもできる(何も書かない診断である)。
**ファイルを書く変更 — 掃除の入口(§2)も、設定・束ね方・CI の変更(§3〜§8)も — は `/build` の
タスクで行う。** `/test-env` が書くのは `tests/` の下の決まったファイルだけであり、製品の
ファイル(ビルドの設定・Makefile・CI の定義)は書かない。`/test-env` の run で測った値は、
その run の報告(SKILL.md §7 の「未了・この環境に固有の制約」)に出す。変えた理由と測った値を
構築記録に残すのは、変更をする `/build` のタスクである。

**順番**: 測る(§1)→ 掃除の入口(§2)→ 試験のビルドの設定(§3)→ 束ねる・作らない(§4)→
並べる(§7)→ CI のジョブ分け(§8)。**どの段の後にも §5 の不変の確認を通し、§4 をしたら §6 の
検査を置く。** 効き目の大きい順ではなく、**戻しやすく、他を壊しにくい順**である。

## 1. 測ってから減らす — 大きさは「件数」ではなく「単位の数 × 1単位の重さ」で決まりうる

- **まず仮説を捨てて測る。** ディスクとビルドの時間は、試験の**件数**ではなく、ビルドの
  **単位**(試験のファイルごとにできる実行ファイル、パッケージごとのテスト用の実行ファイル
  など)の**数 × 1単位の大きさ・重さ**で決まることがある。1単位の大きさは中の件数ではなく、
  **依存とデバッグ情報**で決まる。確かめ方: **試験が1件しかない単位と、数十件ある単位の大きさを
  比べる**。同じくらいなら、件数を減らしても効かない。
- **置き場の内訳を先に出す**: 置き場ごとの大きさ、単位(実行ファイル)の本数と合計、1本の中の
  デバッグ情報の割合。**同じ試験の名前で、指紋(末尾のハッシュ)だけが違う単位が並ぶ**なら、
  設定の違うビルドが2組溜まっている疑い、または依存や道具の版を変える前の古い出力が残っている
  疑いがある。**各組のビルドの設定を比べて確かめる**(推測のまま原因と書かない)。
- **ビルドの時間は段ごとに見る**: 依存・本体・試験の単位のどこに時間が掛かっているかを、
  ビルドの道具が出す段ごとの時間で見る。**共通の部品を1つ触った後のビルドし直しの時間**も
  測る(単位が多いと、触るたびに全部の単位が作り直される)。
- **テスト実行ゲートの時間は、ステップごとの壁時計から見る**: テスト実行ゲートの時間を決めているのは、
  **いちばん遅い直列のステップ**であることが多い(言語の試験ではなく、別の道具の試験が直列に
  走っていた、など)。1件ごとの上位は、その後に見る。
- **直す前に、道具の既定がいま何をしているかを見る**: 本番のビルドに「デバッグ情報が入って
  いるはず」と思い込まない。ビルドの道具が既定で抜いていることがある。**実際にコンパイラへ
  渡っている引数と、出力の中身(デバッグ情報・シンボルの有無)を見てから決める。**
- **測るのは使い捨ての写しの中で**: 作業ツリーの置き場で測ると、前から溜まっていた分と混ざり、
  他の作業のディスクも食う。リポジトリを別の場所へ写し(ハードリンクを使わない clone など)、
  **ビルドの置き場と依存のダウンロードの置き場もその中に置き**、測り終えたら写しごと消す。
  測る前にディスクの空きを見る。
- **混ざった値は捨てる**: 他のコンテナ・他のプロセスの読み書きが混ざった値は使わない。
  メモリのピークは、**名前を付けた専用のコンテナで、CPU を CI の実行機と同じ数に絞って**測る。
- **CI の実行機の上限は、公式の値と、それ以外の出どころの値を分けて控える**(「保証された空き」
  などが公式の文書ではなく、開発元の発言であることがある)。

## 2. 生成物の掃除の入口を1つ用意する

- **ビルドの置き場と試験成果物を消す入口を、1つのコマンドとして用意する**(例: `make clean`)。
  他のコマンドと同じく、その文字列は `docs/02-design/environments.md` の表に書く(書くのは
  `/build`)。
- **消す前に、置き場ごとの大きさとファイルの数を出し、消した後にディスクの空きを出す。**
  2回続けて打っても成功で終わる(冪等)こと。**自分の持ち物でないファイルが在れば、消さずに
  止まる**こと(別の利用者・コンテナが作ったものを巻き込まない)。
- **消さないものを明記する**: 依存のダウンロードの置き場、手元の確認環境のデータ、コンテナの
  イメージとボリューム、ロックファイル、ソース、他のプロジェクトのもの。
- **いつ打つかはプロジェクトが決める**: 消すと次のビルドは空から始まり、その分だけ遅いので、
  フローが毎回自動で打つものにはしない。**試験を回し終えた後(検証の周の後など)に置き場の
  大きさを測り、目安を超えていれば打つ** — 目安の値はプロジェクトの判断であり、決めたら
  `docs/02-design/environments.md` に書く。測るための使い捨ての写し(§1)は、目安と関係なく
  測り終えたら消す。

## 3. 試験用のビルドと本番のビルドの設定を混ぜない

- **デバッグ情報を切るのは試験のビルドだけにする。** 試験の呼び出し側の環境変数など、
  **試験のビルドにだけ届く経路**で切り、開発者が手で打つビルドの共有の設定は変えない(手元で
  調べるときはデバッグ情報つきのまま)。失うもの(多くはバックトレースのファイルと行)を書いて
  おく。**単体と結合で同じ値にする** — 値が違うと依存ごとビルドし直し、置き場が2組になる。
- **コンテナの中でビルドするなら、変数を名指しで渡す**: コンテナはホストの環境変数を引き継が
  ない。CI のジョブに変数を置いても、包むスクリプトがコンテナへ渡していなければ効かない。
- **試験が遅いなら、最適化なしで遅い依存(暗号の処理など)だけ、試験のビルドでも最適化する**
  手がある。効果は前後で試験の時間を測って確かめる。
- **本番のビルドの設定は、全項目を明示する**: 道具の既定に任せると、道具の版で出来上がりが
  動く。**環境変数や道具の設定ファイルは、プロジェクトのファイルに書いた本番の設定に勝つ
  ことがある** — 本番のビルドには試験用の変数を一切置かず、コンテナへは名指しした変数しか
  渡さず、上書きする設定ファイルが在れば止める。
- **本番を小さくする設定は、処理の速さと引き換えのことがある**: 大きさだけで選ばず、重い処理
  (暗号など)の速さを測ってから決める。**振る舞いが変わる設定**(異常時の止まり方など)を
  変えるかは、人間の判断として残す。
- 本番の設定を変えるときは、**まず「既定と同じ値を明示しただけ」のビルドの出力が変更前と
  一致する**ことを確かめ、それから1項目ずつ変えて測る。

## 4. 束ねる・作らない — 単位の数を減らす

§1 で「単位の数 × 1単位の重さ」が置き場の大半だと分かったら、**単位の数そのものを減らす。**
件数を減らすより、ずっと効くことがある。

- **試験のファイルを、パッケージなどの大きな単位ごとに1つのビルドの単位へ束ねる。** 束ねる
  ときは、**試験のファイルを動かさず、名前も変えない形**を選ぶ(入口のファイルが元の場所の
  ファイルを読み込む形など)。仕様と試験の対応表と、ファイルの履歴をそのまま使えるからである。
- **試験を持たない単位では、テスト用の実行ファイルを作らせない。** 本番の出力名・道は変えない。
- **束ねると、自動で拾う仕組みを止めることになりやすい** — そのときは §6 の検査を必ず置く。
  束ねた後は、試験どうしの分離(§5 の 4)と、名前で絞る式の付け替え(§5 の 3)も確かめる。

## 5. 「減らす」変更の不変の確認 — どの段の後にも

**減らす変更は、試験の件数・名前・合否と、本番の出力を変えないことが前提である。** 毎回次を
確かめ、結果を構築記録に書く:

1. **試験の一覧を前後で突き合わせる** — 作業前と作業後の木をそれぞれ一時置き場へ出し、両方で
   **無視・除外の指定が付いた試験も含めた**一覧を取る。名前の付け替え(束ねたことで頭に付く
   名前など)を読み替えて1件ずつ照合し、**前にだけ在るもの0件・後にだけ在るもの0件**。件数と
   合否も同じであること。
2. **本番の出力が同じ** — 本番に触れない段なら、出力のハッシュと大きさが前後で一致すること。
3. **仕様と試験の対応が壊れない** — `docs/03-impl/tests/` の対応表が指すファイルと関数の名前が
   そのまま使えること(§4 の形を選ぶ理由)。名前で絞る式が変わるなら、**頭や末尾で縛って**、
   別のファイルの同じ名前を拾わないようにする。
4. **束ねたら、試験どうしの分離を確かめる** — 別々のプロセスで走っていた試験が同じプロセスに
   入ると、環境変数などを書き換える試験が互いに混ざりうる。1件1プロセスで走らせる道具を使うか、
   混ざらないことを確かめる。手で打つ案内のコマンドもその形にする。

## 6. 束ねたとき、足し忘れが黙って走らない — 検査で止める

- **自動で拾う仕組みを止めると、足したものが黙って走らなくなる**: 試験のファイルを並べた一覧で
  束ねる形にすると、一覧に並べ忘れたファイルは**ビルドもされず、1件も走らない**。試験を持たない
  単位でテスト用のビルドを止めると、後でそこに書いた試験も黙って走らない。
- **テスト実行ゲートの頭で、並べ忘れ・止め忘れを名指して落とす検査を置く**: 「試験のファイルの
  どれもが一覧に並んでいるか」「テスト用のビルドを止めた単位に試験の印が無いか」。注釈にした
  行は数えない。広めに見て止まる側に倒す。
- **検査を足したら、わざと欠陥を入れて落ちることを見てから戻す。**
- 絞って走らせて0件だったときの扱いは `/build` の SKILL.md §3「実装する」の手順3が正である
  (0件を合格と読まない)。

## 7. 並べる — 状態を共有しない単位で切り、取り合いを見る

- **並べる単位は、状態を共有しないもの**(試験のファイルなど)にする。初期化は各単位で行い、
  共有の鍵のファイル(ロックファイルなど)は**読むだけ**にする(並列の初期化が同時に書き換え
  ない)。
- **結果をまとめて数え直し、欠けも失敗にする**: 1つでも失敗なら全体が失敗、**結果が出なかった
  単位が在っても失敗**、単位が0本でも失敗。1件をわざと落として、全体が落ちることを確かめる。
- **CPU とメモリの取り合いを見る**: 同じテスト実行ゲートの中で並行に走る他のステップ(言語の
  ビルドなど)にコアを残す数にする(例: コアの半分)。CPU の少ない CI の実行機では、重い
  ビルドどうしを同時に走らせない。

## 8. CI — ジョブを分け、コンテナを外すのは「同じ環境」と証明できたときだけ

- **試験と本番のビルドを別のジョブ(別の実行機・別のディスク)にする。** ジョブごとの山
  (イメージ + 置き場 + 部品)を見積もり、実行機の空きと比べる。**各ジョブの最後で、失敗しても
  ディスクの使用量を出す**。
- **キャッシュに載せるのは、依存のダウンロードと本番のビルドの途中の置き場だけ** — 試験の
  デバッグつきのビルドは載せない。キーにジョブの名前を入れる(同じキーだと、同時に走るジョブの
  うち最初に保存したものだけが残る)。
- **実行機の版を固定する**(「最新」を指す名前は、中身が予告なく変わる)。
- **コンテナのイメージを片づけるなら、ビルドのキャッシュの層まで消す**手段を使い、前後の
  使用量で効果を見る。
- **ビルドの環境に合わせるために試験をコンテナの中で回しているなら、CI でそのコンテナを外して
  よいのは、ビルドの環境と同じ環境だと証明できる段だけである。** 試験の相手のサービス(データ
  ベースの代わりなど)のコンテナは、ビルドの環境ではないのでこの判断の対象外である。
  「同じ」= **OS・C の標準ライブラリ(libc)の版・道具の版・ターゲットが同じ**。証明の仕方は、
  イメージの中の実行ファイルと公式の配布物のハッシュを比べる・静的リンクかを見る・
  libc と OS の版を比べる。**証明できたものも、外す得を測ってから決める** — 得が小さいなら、
  CI が手元と同じ定義を回す性質を保つほうを選んでよい。**静的リンクでも OS の中身に依る部分は
  残る**(素の OS のイメージに証明書が無い、など)。
- 「同じ」の基準を緩めて外したいときは、その基準を人間が決める。

## 9. 道具ごとの置き換えの例(最小限)

原則は §1〜§8 である。以下は、あるプロジェクト(2026-11)で使った**例**であり、他の言語・道具
では同じ役目のものに置き換える。

| 原則 | 例(Rust / cargo・terraform) |
|---|---|
| 試験のファイルを1単位に束ねる(§4) | `autotests = false` と `[[test]]` 1つ、`#[path = "../<ファイル>.rs"] mod <名前>;` を並べた入口(試験のファイルは動かさない) |
| 試験を持たない単位のテスト用ビルドを止める(§4・§6) | `[lib]` / `[[bin]]` に `test = false` |
| 試験のビルドだけデバッグ情報を切る(§3) | 試験を呼ぶ側の環境変数 `CARGO_PROFILE_DEV_DEBUG=0`(test は dev を継ぐ)。CI では `CARGO_INCREMENTAL=0` も |
| 本番の設定を上書きする経路(§3) | `CARGO_PROFILE_RELEASE_*` と `.cargo/config.toml` が `[profile.release]` に勝つ |
| 無視指定も含めた一覧(§5 の 1) | `cargo nextest list --workspace --run-ignored all` |
| 1件1プロセスで走らせる(§5 の 4) | cargo-nextest(`cargo test` は同じプロセスの別スレッドで並ぶ) |
| ビルドの段ごとの時間(§1) | `cargo build --timings` |
| ファイル単位の並列(§7) | `terraform test -filter=<ファイル>`、初期化は `-lockfile=readonly` |
