# clone 後のテスト実行環境 — 診断の入口

出典: 配布元の規範。出典の `docs/` は配布元の一次資料であり、このプロジェクトには無い。

**環境を整える手順そのものは `/test-env` が持つ** ★ — 依存が入っていない / `bootstrap.sh` が
プレースホルダのまま / 資格情報が無い / clone した直後、はすべてあちらである。
**ここに手順を書き写さない**(2026-09-12 に重複を解消した。同じことを2か所へ書くと必ず食い違う
— `conventions.md` §4)。

## この資料が受け持つのは、症状からの振り分けだけである

| 症状 | どこへ行くか |
|---|---|
| 依存が入っていない / スクリプトが空のまま / 資格情報が無い | **`/test-env`** |
| 設定を調べるコマンドに未解決が並ぶ | `references/declarations.md`(埋めるのは `/build`) |
| 未配線・skip だらけ・対象0件・終了コードが読めない | `references/troubleshooting.md` |
| テストは動いたが落ちた | `/verify-tests` §2(振り分け)と `/build` §3(通す方向へ直さない) |

**実行コマンドの正は `02-design/environments.md`** であり、スキルはその文字列をそのまま打つ。
**表がまだ無いなら、それ自体が `/verify-tests` の赤である**(コマンドを発明しない)。

**例外は初回の環境づくりだけである** ★ — `/setup` はあの表を作らない(コマンドが実在してから
書く)ので、**`/test-env` が初めて環境を整えるときには表が無いのが普通である。** そのときは
標準の配置で進め、**決めた文字列を報告に出して `/build` が表へ書く**(`/test-env` §0)。
**試験フローで表が無いのは赤のままである** — あちらは既に整っている前提で走るからである。
