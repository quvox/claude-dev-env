# 文書整合 — F2、SSOT の内部整合のフロー

対象: $ARGUMENTS。人間に向けた出力はすべて日本語で書く。
**書いた本人としてではなく、独立した批判的な読み手として読む。**

**目的**: SSOT の内部整合 — 00⇄01⇄02 の追跡可能性、記述規約、曖昧語、雛形の構造、frontmatter、
検証済み記録(`verified`)。このフローは二重の網の2枚目であり(`flows.md` §1)、
**00〜02 について `verified` を書く唯一のもの**である(原則6。03 層の代表は `/verify-impl` のもの)。
**無人で走るように設計されている**: **AskUserQuestion はここでは構造的に不可能である** —
すべての所見は3チャネルを通って出て(`flows.md` §5)、run は必ず判定を残して終わる
(鮮度スタンプも残す — **唯一の例外は対象が0件の run である**。§2)。
**起動元から独立している**: 人間も cron の行も中央エージェントも、同じ手順と同じ報告を得る。

**このフローは止まる。** 修正のループは**最大2回**。所見ゼロの PASS は正当な結果である
(見た中で最も弱い点を名指す)。**検証は文書を太らせてはならない**
(但し書きを足すのではなく、置き換えるか削除して直す)。

**このスキルが負う規範の節** — `.claude/directions/reading.md` の `/verify-docs` の行と、
**実際に走らせる検査を所有する directions の節だけ**(自己制限: 検査が要るものを読むのであって、
ファイルを読むのではない)。

## 0. 範囲 — 鮮度スタンプで差分駆動する

**この節が決める、その run で見るファイルの集まりを「対象集合」と呼ぶ。**
独立レビューへ渡すのはこれであり、免除の条件もこの数で決まる(§2)。

**最初に、保護ブランチで書かないことを確かめる** ★ — 走らせるのは1行である:

```sh
python3 .claude/scripts/guard-branch.py --verify
```

**この固定名(`work/<YYYY-MM-DD>-verify`)を使うのは、このフローが slug を持たないからである**
— 名前を発明しない。**終了コードが `0` でなければ、そこで止まって報告する**
(`1` は、こちらの知らない事情が在るという意味である。**`git branch -D` を打たない**)。
判定の中身 — 既定ブランチの求め方、同じ名前の枝が既に在るときの2分岐、止まる条件 — の正は
`.claude/directions/flows.md` §7.1 である。**ここには写さない。**

既定: 最後の `verify-docs` の green 鮮度スタンプ以降に変わった SSOT の文書すべて
(`git diff --name-only <stamp-commit>..HEAD -- docs/` と未コミットの変更。鮮度スタンプは
`python3 .claude/scripts/stamps.py show` から取る — **記録された red はこの基準点を消さない:
印字される 最終green の行を使う**、inspection-17 判断4)、**加えて**その `source` の下流、
**加えて**検証済み記録が失効している/無い文書 —
**ただし自分の検証済み記録を持つ文書に限る(00〜02 と 03 の索引。`relations/` と `features.md` は
索引を通して検証されるので(原則6 の例外)、自分の検証済み記録が無いことで範囲に入ることは
決してない)**。`all`(または使える green 鮮度スタンプが1つも無いとき)は SSOT 全体を検証する。

**除外**: **ツール生成領域は、動いていても範囲に入らない** ★ —
`docs/03-impl/callgraphs/` と `docs/03-impl/feature-graph.md` である(§1 の分担の宣言。
このフローの母集団に入っていないので、差分に出ても数えない)。**これを数えると、`/verify-impl` が
コールグラフを再生成した直後の増分 run が、生成物だけで3ファイルを超え、
§2 の免除(3ファイル以下・critical 非含有)を外して独立レビューを1つ起こす** —
誰も読んではならないファイルのために払う恒常費であり、`stamps.py` の `EXCLUDES` が
失効の側で消したものが範囲の側から戻ってくる(inspection-20 V-2)。
`state: building` のすべての構築記録のクロージャも範囲の外である —
**過渡は不整合ではない**(`flows.md` §3)。`awaiting-verify` のクロージャは**優先の対象**であり、
その記録の 主張 を手元に置いて読む(**文書がそれと矛盾する主張は、その記録を名指した所見である**)。
`critical: true` のクロージャは常に独立レビューの対象集合に含まれる。
**管理欄と生成区画だけが動いたファイルも、対象集合に数えない** ★
(2026-09-15。inspection-28 B-23)— 失効の判定は既にそう扱っている
(`stamps.py` の `machine_owned_only`。`updated:` の行・`verified:` の区画・
形の揃った `version:` の行だけが動いた変更は、依存の変更と数えない)。
ところが対象集合の側はそれを見ておらず、**検証済み記録を書いただけの文書が4本並ぶと、
§2 の免除(3ファイル以下)を外して独立レビューが1つ起きる。**
**読む中身が1文字も変わっていないのに払う恒常費である。**
**判定は `stamps.py` の `machine_owned_only` と同じものである**(区画単位で、
`updated:` の行・`verified:` の区画・形の揃った `version:` の行だけが動いたかを見る)。
**`stamps.py deps` ではない** — あれは依存の**置き場の一覧**を印字するだけで、
個々のファイルが管理欄だけ動いたかどうかは言わない。
**手で確かめるなら、その文書の差分を見て、動いたのがその3つだけかを読む。**
**別の理由で対象に入るものは、そのまま残す** ★ — `critical: true` のクロージャ、
`awaiting-verify` のクロージャ、そして**検証済み記録が失効しているか付いていない文書**である。
**「管理欄だけ動いた」は、対象から外す理由であって、見なくてよい理由ではない。**
**記録を手で書き換えることは決してない**: 鮮度スタンプを記録した後に
`python3 .claude/scripts/stamps.py promote` を走らせる — それが `awaiting-verify` の記録ごとに
**その記録自身のコミット時点**で、`flows.md` §2 の区間の規則によって判定する
(記録より*前*に記録された鮮度スタンプでも*後*に記録された鮮度スタンプでも、それを満たしうる)。

対象は frontmatter からシェル1回で導く。**大量の読取は委任する**(`CLAUDE.md` §1)。

## 1. 検査

**まず機械検査**を回し、その結果を所見として畳み込む(**決して手で漁らない**):

```bash
python3 .claude/scripts/build-facts.py check      # ★ いちばん先。機械の欄の差分ゼロと、参照先の実在
python3 .claude/scripts/check-ssot.py docs        # 一括検査(CS 群 — --list で ID が出る)
python3 .claude/scripts/doc-health.py --health
```

**`build-facts.py check` を先頭に置くのは、走らせ忘れを起こさないためである** ★ —
**このフローの合格の条件に「差分ゼロ」が入っている**(下)。**違反が出たら、まず
`python3 .claude/scripts/build-facts.py update` を打って埋め直し、その差分を自動修正として
コミットする**(機械的に正解が定まる — `flows.md` §5)。**埋め直しても消えない違反**
(参照先のファイルや節が無い / 宣言の誤り)は、機械の欄の話ではなく**参照か宣言の誤り**なので、
3チャネルの振り分けを通す。**宣言(`docs/facts.json`)が無いプロジェクトでは 0 を返す** —
この道具は、宣言した分だけ働く。

`check-ssot.py` は SSOT 全体を掃き、**この run の範囲へ絞るオプションを持たない**: 機械の所見のうち
パスが `building` の記録のクロージャの内側に在るものは「作業中(除外)」として報告する —
**自動修正もせず、止めもしない**(その過渡はその構築が閉じるものである。`flows.md` §3)。
**これは母集団の中から範囲を選ぶ話であって、母集団そのものの話ではない** —
ツール生成領域は、そもそもこのフローの母集団に入っていない(下の分担の宣言)。

そのうえで、範囲に対して:

- **A0(00 の内部)**: 「やらないこと」が空でないこと。request / acceptances / terminology /
  decisions のあいだに矛盾が無いこと。すべての 委任 が範囲とガードレールを持つこと。
  すべての 要確認 が 論点 と 誰がいつまでに を持つこと。参照された ID が実在すること。
  **`all` のときだけ**: 用語の例が埋まっていること。すべての 決定 の 見直す条件 が成立して
  いないかを点検すること(中。止めない。**製品を動かす必要があるものは 判定不能 が期待される答え**)。
- **A1(00→01)**: すべての やること の項目が要件に覆われていること。
  やらないこと から紛れ込んだものが無いこと。決定 と矛盾する要件が無いこと。
  すべての `AC-nn` が UC によって形式化されていること。
  **すべての機能要件が、どれかの UC のフローに現れているか、`## シナリオ外要件` の節に
  理由つきで並んでいること**(`01-requirements.md` — この網羅は条項ではなく要件の単位で見る。
  「シナリオ外要件」に理由つきで在る行は所見にしない)。
  **非機能要件が、規範の定める分類のすべてに節を持っていること** ★ — 分類の一覧は
  `01-requirements.md` の `non-functional.md` の節が正である(**ここに書き写さない**)。
  **節が消されていれば 高** — 消えた分類は、要件が無いのか見落としたのかを誰にも区別できない。
  そのうえで、`適用外` と書かれた分類がすべて**理由を持ち、その理由が上流を引いているか**を
  読む(**機械はこの節の有無すら見ていない** — CS24 も CS25 も要件の行の中しか見ないので、
  **分類が丸ごと消えた穴を見るのはここだけである**)。
  **数値の目標を持つ要件が、測り方の4つの条件を実際に書いていること** ★
  (2026-09-15。inspection-28 A-1)— **負荷 / データ量 / 集計の期間と母数 / 失敗した応答の扱い**
  である(規則の正は `01-requirements.md`。**ここに書き写さない**)。
  **機械はこれを1つも見ていない** — 検査の一覧に項目が無く、形の検査も通る。
  **4つのうち欠けているものを名指しで挙げる**(「測定方法が薄い」では直せない)。
  **4つを決められないなら、目標値をまだ決めていないということである** —
  そのときは値そのものを所見にする。
  **画面を使える手段(BR-13)の水準が、想定する利用者に照らして著しく低くないこと** ★
  (2026-09-15。inspection-28 A-3)— 水準を決めるのは製品であり、**この役はそれを書き換えない。**
  低いと見たなら**判断の材料として報告する**(「キーボードだけで終えられる操作が
  主要な流れに1つも無い」のように、何をもって低いと見たかを書く)。
  **理由の欄は、中身を読む** ★(2026-09-15。inspection-28 A-10)— `段階可` の理由・
  `適用外` の理由・省略の理由は、**機械には形しか見えない。**
  **その理由が、実際にその判断を支えているか**を読む(支えていないなら所見である)。
  **書いてあること自体を合格と読まない。**
- **A2(01→02)**: すべての要件の条項がカバレッジ表に在り、主担当行がちょうど1行であること。
  すべての `SR-nn`(`01-requirements/system.md` の `## 必須制約(交渉不可能)` の節が持つもの)が
  カバレッジ表に行を持ち、その `充足` が
  `満たす` か `破れている(課題票 ID)` のどちらかであること —
  **`破れている` は1件でも 高 であり、完了定義を満たさない**(`.claude/directions/core.md` §3)。
  `部分(P-nnn)` が、空でない 解消条件 を持つ棚上げの項目に解決すること —
  そして**既に範囲に入っているものから**、その条件が成立したかを判定する
  (**報告するだけ。決して新しい課題票にも 残務 の行にもしない** — `issues-pendings.md` §8)。
  **`不可分` の要件が `段階可` に化けていないこと** ★ — 権限・金・データ整合・監査証跡に触れる
  要件が `段階可(理由)` になっているなら、その理由がその4つの害を実際に打ち消しているかを読む
  (`01-requirements.md` の `分割可否`。**機械が見るのは形だけである** — CS24 が見るのは
  値の形(記載・選択肢がちょうど1つ・`段階可` の理由の有無)だけなので、
  **判定の当否を見るのはここだけである**)。
  **`不可分` のまま部分実装になっていないこと** ★ — これは上とは別の抜けである。
  値が正しく `不可分` のときでも起きる: **その要件の条項が、02 のカバレッジ表で
  `部分(P-nnn)` の `充足` を持っていないか**を照合する。**1件でも在れば 高 であり、
  完了定義を満たさない**(規範が「そういう要件に `部分` の条項が在ることは、例外なく PASS を
  止める」と定めている — `01-requirements.md` の `分割可否`)。
  **値だけを読んで終えない** — 値と設計の組合せを見るのがこの点検である。
  例: 操作の権限の判定と操作の記録を一体で約束した要件で、記録の側だけを棚上げした設計が
  これに当たる。
  **この所見の行き先は `origin_layer: 01` の課題票だけである** — この判断は 01 が所有し
  人間には問わないので(同「どこで決まるか」)、**修正の段(下の §3)の質問シートへは決して回さない。**
  水準ごとのテスト戦略。E2E の一覧がすべての UC を覆っていること。
- **C(文書の品質)**: 曖昧語 — **既知の語を自分で探し直さない** ★。一覧に載った語の列挙は
  `check-ssot.py` の `CS8` の仕事であり(§1 で回している)、**その所見の行をそのまま引用して
  畳み込む。** ここで読むのは、**機械が出せないほう**の2つである:
  (1) 機械が拾った語が、**その文脈で本当に曖昧か**(拾っただけで所見にしない)、
  (2) **一覧に無い曖昧さ** — 程度・頻度の言い回し、主語や条件の落ちた文、
  「必要に応じて」に類する逃げ。EARS が試験可能な粒度であること。
  空でない 未解決事項 が検証済み記録を止めること。frontmatter の妥当性。
  `DS-*` の開示行が 理由 と 見直す条件 を持ち、判断の節がいまも「なぜこうなっているのか」に
  答えていること — **見直す条件 が成立している行は 高 である**(検証済み記録を持った偽の主張)。
  **ここで歩くのは 00〜02 の開示行だけである** — 実装層の「実装上の判断」/「テスト設計の判断」の
  行は `/verify-impl` が所有する(所有者の宣言は `delegation.md` §3.1。同じ行を1周のうちに
  二度読み直さない。inspection-21 V-16)。
  pendings / issues が完全性の主張と矛盾していないこと。

(コード ⇄ 03 と 02 ⇄ 03 の連携の差は `/verify-impl` のものである — ここで重複させない。
**`check-relations.py` をこのフローが回さないのは、まさにそれが理由である** — その所見の主要な
部分はコード側の事実(`impl` のパスの実在など)であり、このフローの自動修正は PATCH級に
限られるので**ここで違反を出しても直せる者が居ない**。あれは `/verify-impl` が毎 run 回す
(inspection-21 V-1)。)

**機械の欄の中身も、このフローの母集団に入っていない** ★(2026-08-27)。
`<!-- BEGIN GENERATED: <道具名> ... -->` から `<!-- END GENERATED: ... -->` までは
**手で編集してはならない場所**なので、そこの曖昧語や件数の主張を所見にしても直せる者が居ない
(`check-ssot.py` が中身を空行に置き換えて読む。**外すのはファイルではなく区画である** —
手で保守する文書の中に在るからで、そこが下のツール生成領域との違いである)。
**正しさは上の `build-facts.py check` が見る**(差分ゼロ)。
**そして残務(`docs/residual.md`)も母集団ではない** ★ — あれはこのフロー自身が所見を書き出す
先(3チャネルの「キュー」)であって、読み比べる対象ではない。行の形と件数は
`check-backlog.py` と `doc-health.py` が見る。**だから `stamps.py` の `EXCLUDES` は
それも F2 の依存から差し引いている**(`flows.md` §2)。

**このフローの母集団に、ツール生成領域は入っていない** ★ —
`docs/03-impl/callgraphs/` と `docs/03-impl/feature-graph.md` の中身を検査しない。
そこはコードの書き写しであって、突き合わせる相手はコードであり、**それは `/verify-impl` の領分**
である(`callgraphs/` は `build-callgraphs.py --check` と `callgraph-check.py`、
`feature-graph.md` は `cluster-features.py` が見る)。**手で編集してはならない領域なので、
ここで違反を出しても直せる者が居ない** — `check-ssot.py` と `doc-health.py` も同じ理由で
これらを対象から外している(**`doc-health.py` は索引 `index.md` も外す** — 原則10 の
「生成領域」はこの2つより広い)。**`build-index.py` も外すが、理由は同じではない** —
`callgraphs/` を外すのは「専用の索引が在る」からであり、`feature-graph.md` を外すのが
「別の道具の生成物だから」である。
`relations/` と `features.md` は違う — それらは 03 の索引を通して検証される(§0)。
**この分担の宣言が、失効判定の除外の根拠である**: 見ないと宣言した場所は、動いてもこのフローの
検証結果を古くしない。`stamps.py` の `EXCLUDES` がこの2つと残務を F2 の依存から差し引いているのは
そのためであり(`flows.md` §2)、**この宣言を変えるなら `EXCLUDES` も同時に変える。**
**機械の欄だけは `EXCLUDES` では書けない** — パス単位の除外はファイルごと外すので、
同じ文書の手書きの部分まで失効しなくなる。そちらは `stamps.py` の
`machine_owned_only`(管理欄と同じ**区画単位**の判定)が受け持つ。

## 2. 独立レビュー — 1つ、最初に起こし、重大度で裁定する

**実効モードと主実行エンジンを作業指示から読む。** 作業指示に無いときは、**自分が動いている
エンジンから既定を取る — claude なら a1、codex なら o1** である(2026-09-20。
`orchestration.md` §1.2.1。この4モードでは、どのモードでも主実行者は中心側のエンジンなので、
自分のエンジンからその既定が決まる)。**a2/o2 は自分のエンジンからは見分けられない** —
そのモードで走っているなら、作業指示がそう書いてあるはずであり、書いていないなら
**中央へ1行で確かめる**(勝手に反対側のエンジンのレビューを要求しない)。
a1/o1 は主実行者の反対側、a2/o2 は同一エンジンの別文脈を使う。
役の配車表・隔離手段・縮退の正は orchestration.md §1.2.1・§1.3。
F2・F3 と関連フローの小さい対象の免除は以下の現行条件を共通に保つ。
同じ基準コミット・対象・範囲をレビューへ渡し、両方の所見が揃ってから主実行者が裁定する。
修正・課題票・残務・質問シート・鮮度スタンプを書くのは主実行者だけである。


**この節が、独立レビューを走らせるすべてのスキルのための起動を所有する**
(`/verify-impl`、`/retrofit` §5A、`/relations` §7 もここを引く)。

**下のコマンドの `$TMP` は、この run のスクラッチパッドである** — **`docs/` の下でも
リポジトリの中でもない**。最初に1度だけ決めて書き出す:

```bash
TMP="${TMPDIR:-/tmp}/verify-$$" && mkdir -p "$TMP"
```

**自分の検査の前に、読むだけのレビューを1つ背景で起こす**: 対象集合・読む範囲・検査項目の本文・
出力様式(重大度・`path:line`・引用を持つ JSON の所見)を渡す —
**自分の所見も、修正も、期待する判定も決して渡さない。** 判定の前に回収する。
**機械が出した曖昧語の所見(語と `path:line`)は渡す** ★ — あれは**観測であって結論ではない。**
渡さなければ、レビューは同じ列挙をもう一度やることになる。渡したうえで、
**その語がその文脈で曖昧かどうか**と、**機械が拾わない曖昧さ**を独立に見させる
(上の検査項目 C と同じ分担である)。**渡さないのはあなたの判定**である —
「これは問題ない」「これは直す」は、渡した時点でレビューを同意の作業に変える。
**併せて「リポジトリへ1バイトも書かない。所見は返信の本文だけで返す」を渡す** ★ —
サブエージェントの経路は**砂箱では止まらない**(あの種別は Bash を持つ)ので、
**そこを守るのはこの1文だけである**(段3 の書込みの確認は当てない。下)。
範囲に在るすべての `critical: true` の `awaiting-verify` のクロージャが、その対象集合に入る。

**対象が0件の run は独立レビューを起こさず、鮮度スタンプも記録しない。** ★ §0 の対象集合が空
(最終 green 鮮度スタンプ以降に動いたものが無く、失効した検証済み記録も無い)なら、レビューに渡す
読む対象が無い — 起こすのはウィンドウとトークンだけの支出である。**打ち直す green も無い**:
失効判定は前回の green のコミットを基準にするので、同じ状態へ green を打ち直しても機械的な効果は
無く、一方で覆いを持たない green は**リポジトリに1件でも** `critical: true` の `awaiting-verify` が
在れば独立レビューの申告を要求するので(`flows.md` §2)、走っていないレビューの名前を書かない限り `record` に拒まれる。
報告に 「独立レビュー: なし(対象0件)」 と 「鮮度スタンプ: 記録なし(対象0件)」 と書いて終わる —
**前回の green はそのまま有効である。**

**対象が3ファイル以下で `critical: true` が対象集合に無い run は、覆い直しの run か増分の run かを
問わず独立レビューを起こさない**(inspection-16 D6 を増分の run へ拡大 — inspection-17 判断7)。
小型の run は最も頻度が高く、そこへ毎回ウィンドウを1つ払うと恒常費になる。critical 非含有では独立レビューの
所見は証拠であって、run を止めるものではない(次項)。**省略が作るのは遅れではなく、閉じない区間の
在る漏れである** — 拾い直せるのは**その対象が再び変わった後の run** と**人間が出す `all` の全数**
だけであり(§0 の対象集合の定義と、全数の起動契機を持つ `flows.md` §2.1)、そのどちらも来ない
あいだ、その対象は独立の目を一度も通らない。**失うのは「初回の独立の目」だけではない** —
その代償は裁定済みである(判断7。この2文の訂正は inspection-23 C-1)。報告には
「独立レビュー: なし(対象3ファイル以下・critical 非含有)」 と書く。critical が在るとき、
および `all` の run では従来どおり必須。

**`critical: true` のクロージャが対象集合に在るときは、独立レビュー無しでこの run を完走させない。**
`.claude/directions/core.md` §5 がそれを必須と定めているので、独立レビューが起こせない・返らないときは
**green を記録せず**、報告を 「中断(独立レビューが成立しない)」 として、何が起こせなかったかを
1行で書く(艦隊なら `orchestration.md` §1.3 — 差し替えを知らされた側は出し直して結果を受け取る)。
critical が1つも無い run では、独立レビューの所見は証拠であって、run を止めるものではない。
**`record` の `--lens` 要求も同じ粒度である**: `--covers` を添えた run は、その覆いに
クロージャが掛かる critical 記録だけを見る — この免除で独立レビューを起こさなかった
run が、そのせいで記録できなくなることはない(`flows.md` §2。inspection-19 V-2)。

**艦隊運用の a1/o1 では**(`CLAUDE.md` §2)レビュー役は **`@review`** であり、
**下の番号付きの段は適用されない** — `codex exec` もサブエージェントも使わない。
a2/o2 の艦隊では中央が作業ごとに隔離手段を指定する。サブエージェント指定でも作業側が
自分から起こさず中央から所見を受け取り、利用不可なら同一エンジンの colabtmux を要求する。
**そのウィンドウはまだ立っていない** ★(2026-08-25 に先行起動をやめた。`orchestration.md` §1.2)。
だから**対象集合を確定して、上の免除に当たらないと判った時点で**、中央エージェントへ1行で
要求する(`独立レビューを1本要求する(対象 <N> ファイル / critical <有・無> / 主実行 <kind> / 実効モード <mode>)`)。
**免除に当たるなら要求しない** — それが起こさない唯一の方法である。
**要求を出したら待たずに自分の検査へ入る**(id は届いた通知で受け取る)。
返ってきた id は数分前に起こされたプロセスなので**この仕事を何も見ておらず**、
`.claude/roles/review.md` が既に「レビュー対象には何も書かない(自分の所見ファイルだけは
リポジトリの外のスクラッチパッドに書いてよい)・何も裁定しない」を縛っている:

```bash
# 依頼文はファイルに書く(複数行。対象・範囲・検査項目の本文・出力様式だけ)
# **宛先は中央が返した id である**(以後 @review でも届く)。要求より前に投げない —
# 失われはしないが、依頼文は対象集合が決まってからしか書けない(orchestration.md §1.2)
colabtmux post --to <中央が返した id> --body-file "$TMP/lens.md" --no-wait --json
# → 自分の検査を先に済ませる(独立レビューはその間に走っている)。終わったら1度だけ待つ:
colabtmux wait --message <その ID> --timeout 540
# → それでも来なければ turn を終える。届いた通知で起き、`inbox` で受け取って裁定に入る
```

**レビューを待って止まってはならない** — シェル呼び出しが止まってよいのは最大10分である
(`orchestration.md` §3.1)。そして**要求と依頼を自分の検査より*前*に出すのは、
まさにこの2つを同時に走らせるためである**(単独運用では、下の番号付きの段が同じことをする)。 **パスを渡すのであって、ファイルの本文を渡さない**
(レビューは自分でファイルを読む。引用するとその代金を二度払うことになる)。
下の段3 の書込みの確認は依然として当てる。走ったレビューとして `@review` を名乗る —
**実際に答えたのがどの kind かを言う**(`colabtmux agents` が各エージェントの `kind` を返す。
フォールバックの後の claude の `@review` は「別ウィンドウの claude(codex フォールバック)」であり、
**決して Codex の独立レビューとして報告しない**)。
**艦隊下のレビューは実効モードと主実行者から決める。** a1/o1 は反対側、a2/o2 は
同一エンジンの別文脈。縮退は中央が台帳へ記録し、その通知を受けた後の実効モードを使う。
実際の組と縮退理由を報告へ書き、エンジンの多様性と文脈の独立を取り違えない。
**要求してもレビュー役が返らないとき**は、自分で起こさず、下の段へも落ちず、**続けもしない**:
**green を記録せず**、報告を 「中断(艦隊がレビュー役を用意していない)」 として中央エージェントへ返す。
**要求を1度も出していないなら、それは中断ではなく自分の手落ちである** ★ — 起こすのは要求を
受けた中央の仕事だが、**要求を出すのはこちらの仕事である**(`orchestration.md` §1.2)。
`/verify-tests` が `@qa` を要求せずに `qa` を red へ倒せないのと同じ扱いであり、
**「役が用意されていなかった」は免除ではない** — 免除は `.claude/directions/core.md` §5 のちょうど2つだけである。

**艦隊でないときもエンジンの組は同じ。** 次の番号付き起動例は a1(Claude 主実行)の互換経路。
o1(Codex 主実行)では同じ対象・範囲・項目・形式を、空の文脈の Claude の読取専用レビューへ
渡す。起動時に役本文を注入し、auto 権限と応答可能性を確認する。
a2/o2 は同一エンジンの空の文脈を作業要件に合う隔離手段で起こす(§1.2.1)。
CLI・認証・起動値・必要機能の可否を確かめ、利用不可なら同一エンジンの隔離ウィンドウを使う。
中心側が使えないときに反対側へ勝手に中心を替えない。混在モードの反対側不調は §1.3 に
従って実効モードと理由を記録してから同一エンジンの別文脈へ縮退する。
以下の a1 の Codex 失敗時のサブエージェントは a2 への縮退として記録する。
どの経路でも別文脈が得られず critical が含まれるなら green にせず中断する。

1. `command -v codex` → 使える: **まず、起こす前に、この経路が渡すモードで1回測る** ★ —
   ホストによっては砂箱のオプションそのものが起動失敗を起こすので、**測ってから起こす**:

   ```bash
   codex sandbox -c sandbox_mode=read-only -- /bin/true; echo $?   # 0 なら使える
   ```

   **測る `sandbox_mode` は、下の起動行が渡す値そのものである**(この経路では `read-only`)—
   起動行を変えたら測る値も変える。**オプションを足さない `codex sandbox -- /bin/true` は使わない**:
   それは「読み取り専用を測る」という**別の約束**の上に立っており、下の起動行と一致することが
   読み手に見えないので、起動行が変わった日に黙って外れる
   (判定の形の正は `orchestration.md` §1.1.1。**単独運用にも掛かるのは、この形と
   「既定では `$HOME` へ書けない」の2つだけであり**、同 §1.1.1 の起動行 A / B の表は
   艦隊運用の機構なので掛からない — 同 §10)。
   **どのホストで非ゼロになるのか** — `use_legacy_landlock = true`(コンテナ型)の環境で、
   **渡したモードによっては**旧 landlock と非互換で panic し(exit 101)、コマンドを1本も
   起動できないまま終わる。**2026-08-20 の実測でそうなったのは `workspace-write` を渡したときで、
   同じホストの読み取り専用の測りは 0 を返している** — **`read-only` が必ず失敗するわけではない。
   だから測らずに諦めない。**
   **非ゼロだったときだけ**下の 2 へ落ち、**恒常的に非ゼロならその旨を報告に1行残す** —
   理由の残らない縮退は、環境を直す糸口を消す。

   **0 だったら**、依頼文をセッションのスクラッチパッドへ書き(**決して `docs/` の
   下ではない**)、ファイルの本文ではなくパスを渡す。背景で走らせる:
   ```bash
   timeout 900 codex exec --cd "$PWD" --sandbox read-only --ephemeral \
     --model gpt-6.1-sol -c model_reasoning_effort="high" \
     --output-last-message "$TMP/lens.json" - < "$TMP/lens-prompt.txt"
   ```
   `timeout 900` はこの**プロセスの寿命**であって、あなたが待つ時間ではない — 背景で走らせて
   turn を終えるので、シェル呼び出しの10分上限(`CLAUDE.md` §2)とは衝突しない。
   未選択 a1 のモデルと effort は上の互換既定を保つ。明示モードでは起動ごとに人間が確認する。
   **作業指示が「モデル制限: あり」を伝えているなら、ここの `--model` も軽い層の値
   (`gpt-6-luna`)にする** — `-c model_reasoning_effort` はそのままである
   (`orchestration.md` §1.5)。`--sandbox read-only` と `--ephemeral` は
   必須である。承認や砂箱を迂回するオプションは禁止である。秘密情報は決して依頼文に入れない。
   **Codex の出力をコマンドとして実行することは決してない。**
2. `codex` が無い・拒否された・失敗した・解析できない → 明らかに環境由来の失敗なら1回だけ
   やり直し、それから**同じ依頼文**を、読むだけの新しい文脈のサブエージェントへ通す
   (`subagent_type: "Explore"`)。報告の「次にあなたがすること」が許可の1行の直し方を持つのは、
   **許可の拒否が原因だったときだけ**である — **キットは実行の許可の既定モードを配らないので、
   ふつうは許可リストが効いており、この案内は意味を持つ。** ただし**その環境が起動時のオプションか個人設定で
   bypass を選んでいるなら決して書かない**(その下では許可リストは判定に関与しないので、
   この案内は別原因の失敗を隠すだけである)
   (`.claude/settings.local.json` の `permissions.allow` に `Bash(codex exec *)` と
   `Bash(command -v codex)` を追加)。
3. `git status --porcelain` を起動前の控えと比べる ★ — **これを当てるのは、書き込みのできる
   砂箱で起こした相手(艦隊の `@review`)だけである。**
   上の 1(`--sandbox read-only` の codex)は**砂箱が構造的に書かせない**ので、控えを取る意味が無い。
   **失うものは在る** — 砂箱の設定が崩れていた場合(読み取り専用が効いていない)を拾えなくなる。
   **承知して落としている**: 読み取り専用が効いていない codex は、このキットの他の前提も
   同時に壊しているからである。
   上の 2(サブエージェント)は**読取専用の役として起こしている** — **構造的に書けないわけでは
   ない**(あの種別は Bash を持つ)が、**控えの費用に見合わない**: 取れば、このフロー自身の
   書込みを「レビューが書いた」と読む誤検出の面だけが増える。
   **ここは指示で守らせている** — その旨を承知して免除している。
   当てるときは: **何かを書いたレビューは即座に停止である** —
   その所見を捨て、そのことを報告する。**控えはレビューを起こす直前に取り、比べるときは
   このフロー自身がその後に書いた領域を除く** — `/verify-impl` は §1 の再生成でツール生成領域を、
   §2 で自動修正を、§3-1 で索引を書く。控えを先に取ると自分の書込みが「レビューが書いた」と読まれ、
   後だけを見ると後段の書込みが混じる(inspection-21 V-11)。

**個別に裁定するのは重大度「高」と振る舞いに関わる所見だけ**である。残りは畳むか列挙する。
**再監査するのは新しい判断を含む修正だけ。** 両方のレビューが失敗するのは道具の問題である:
「独立レビュー: なし(理由)」と書いて続ける。**実際に走ったレビューを名乗る**
(`@review(codex)` / `@review(claude)` / `Codex` / `サブエージェント`)—
**サブエージェントの run を Codex の独立レビューとして報告することは決してなく、claude の `@review` が
codex のものとして通ることも決してない。**

**報告と鮮度スタンプの証跡には**、基準コミット・対象集合・主実行エンジン・レビューエンジン・
隔離手段・受け取った返信(または所見ファイル)・免除/失敗・縮退理由を残す。
高重大度・製品の振る舞い・安全に関わる不一致は証拠を読んで解消するまで green にしない。
多数決やエンジン名で裁定しない。文脈の独立と両エンジンの実行を別々に申告する。
記録には `--mode <実効モード> --selected-mode <選択モード> --executor <kind> --review-engine <kind|none>` を添え、
none なら `--review-reason <免除または不成立の理由>`、縮退後は `--degradation-reason <理由>` を
添える。--lens は従来どおり実際の独立レビューの名前で、走っていない名前は書かない。
**作業指示が「モデル制限: あり」を伝えているなら `--model-limit あり` も添える**
(`orchestration.md` §1.5)。台帳にその欄が在るときは台帳が正で、食い違う値は拒まれる。
**報告にも、軽い方のモデルだけで検査したことと、それで何を手放したかを書く** —
とくに深さでモデルの独立を買い戻す経路(`orchestration.md` §1.5 の規則4・規則5)は
そこで効きが弱い。

**コミットの規律**(裁定 D'-2): 自動修正は **`auto-fix:`** を頭に付けた専用のコミットとして
**現在の作業ブランチ**へ入る — **構築のコミットに混ぜず、自動修正のために別ブランチを作らない**
(作業ブランチそのものは `flows.md` §7.1 が用意する。**保護ブランチに居たまま書かない**)。
自動修正は1つの run につき1コミットで足りる(鮮度スタンプのコミットは別で、
**1周に1回**である — `flows.md` §2)。
報告が、触れたファイルをすべて並べる。**その1コミットは §4 の書込み
(version・`verified`・sweep・索引)まで含めてから打つ** — 記録の前に**そのフローの依存が
空になっている**ことが green の条件である(`flows.md` §2)。
**green の条件はもう1つ在る** ★ — **`build-facts.py check` が 0 を返すこと**
(機械の欄の差分ゼロと参照先の実在。§1 の先頭で走らせたもの)。埋め直した差分は同じ
`auto-fix:` のコミットに入り、**埋め直しても消えない違反が残るあいだ green は書かない**
(それは参照か宣言の誤りである)。

## 4. 検証済み記録と鮮度スタンプ

1. 直した文書の版をそれぞれ1回上げ(意味が変わったなら MINOR、そうでなければ PATCH)、
   `updated` を設定する。**直していない文書の版は上げない** ★ — 検証済み記録を打ち直すだけ、
   あるいは `against` の行が上流の版に追随するだけの文書は、`version:` を据え置く(原則6)。
   偽の版上げは下流の `against` を連鎖して動かし、他のフローの鮮度スタンプを無意味に殺す。
2. **上流から下流の順に**、止める所見の無い文書へ `verified` を書く —
   止める所見とは、上流に対する虚偽、どちらが正でもありうる未解決の矛盾、空でない 未解決事項 である。
   **検証済み記録が主張しているのは「この文書は正しく書かれている」であって、
   「このシステムに不具合が無い」ではない** — 記録済みの課題票がそれを古くすることはない。
   有効性は**自分の版の MAJOR.MINOR の一致**である(原則6)。
   上流が動いた下流は**再検証候補の作業一覧として報告する。決して無効として報告しない。**
   **ただし `docs/03-impl/index.md` には書かない** ★ — 03 層の代表の `verified` を発行するのは
   `/verify-impl` だけである(原則6 の例外)。索引が §0 の範囲に入るのは**文書として読むため**
   であって、印を打つためではない: 代表の印が失効しているあいだ、この run は索引を毎回範囲に
   取り込んでは印を書かずに終わる — それを閉じるのは `/verify-impl` の run である。
3. 掃いてから再生成する(掃くのはこのフローだけである — `issues-pendings.md` §2.1):
   ```bash
   python3 .claude/scripts/doc-health.py --as-of=<今日> --sweep --record=docs/histories/<この実行の履歴>.md
   python3 .claude/scripts/doc-health.py --rotate
   python3 .claude/scripts/doc-health.py
   ```
   意味のあるものを直した run は、履歴を1件残す(`--record` の宛先がそれである)。
   **掃き出しとローテーションは別の操作である** ★: 掃き出し(`--sweep`)が落とすのは
   **同じ鍵の重複と、対象が実在しない行の2つだけ**で、このフローだけが打つ。
   ローテーション(`--rotate`)は**1行も落とさない**ので、残務へ書いたフローはどれも打つ
   — ここで打つのは、上の段でこの run 自身が残務へ書いているからである。
4. 鮮度スタンプ — green になるのは、run が完走し、**振り分けられていない止める所見が残っていない**
   ときだけである。**そして 02 の要件カバレッジ表の `SR-*` の行に `破れている` が1件も
   残っていないこと** ★ — 起票済みかどうかによらず green にしない(完了定義の5項目目。
   `.claude/directions/core.md` §3)。**この1件はこの run の範囲に依らず見る** — 範囲の外に落ちた
   `破れている` が合格側に倒れるのを防ぐ。
   **この run が書いたものを先に全部コミットする**(§3 の1コミット):
   `record` は依存に未コミットの
   変更が在るとき green を拒む — 未コミットのままの green は書いた瞬間に失効するからである
   (`flows.md` §2)。**手前で `git status` を目で見て確かめない** — 裸の出力は依存の外の汚れも
   並べるので、依存の中の汚れだけを問う問いには答えられない。**拒まれたら、`record` が印字した
   パスをコミットして打ち直す**(依存の外の汚れは record を止めない)。
   そのうえで、このスキルの冒頭で名指した昇格の周を回す:
   ```bash
   python3 .claude/scripts/stamps.py record verify-docs <green|red> --evidence artifacts/verify-docs.log   # all なら --full を添える
   # critical: true の awaiting-verify 記録が在る run では、green に --lens <実際に走った独立レビューの名前>
   # が必須(record が拒む — `.claude/directions/core.md` §5 の機械接続。inspection-17 判断9)。red に --lens は不要
   python3 .claude/scripts/stamps.py promote
   # promote が「遷移 N 件」(N>0)を報告したら、その書込みをコミットして残す —
   # 作業ツリーにだけ在る verified は HEAD・CI・別 checkout には無い(flows.md §2)
   git add docs/build-records && git commit -m "promote: awaiting-verify → verified" -- docs/build-records
   ```
   **`green` には `--evidence <path>` が要る** ★(2026-09-15。inspection-28 A-7)— 走らせた
   結果を `artifacts/` の下へ書き出し、そのパスを渡す(複数可)。**実在して中身が在る
   ことだけを機械が見る** — 中身が本物かどうかは見ない。それでも、後から人間や別の
   エージェントが**現物を開いて確かめられる**ようになる。`red` には要らない。
   **鮮度スタンプ自身のコミットはここでは打たない** — `.claude/state/stamps.json` は git で
   共有するが、コミットするのは**1周の終わりに1回だけ**である(`flows.md` §2)。
   **SSOT の一部しか読まなかった差分駆動の run は、その一部だけを記録する**:
   実際に調べた文書(またはディレクトリ)ごとに `--covers <path>` を1つずつ —
   `stamps.py check` が写すべき行を印字する。
   **裸の `record` は `stamps.py deps verify-docs` のすべての依存を主張する。**
   **`all` で回した run は `--full` を添える** — 全数でしか回らない検査(§1 A0 の用語の例の点検・
   決定の見直す条件)が最後にいつ回ったかを残す印であり、判定には効かない(`flows.md` §2.1)。
