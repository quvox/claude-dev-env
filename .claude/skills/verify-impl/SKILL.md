# 実装整合 — F3、コード ⇄ 仕様のフロー

対象: $ARGUMENTS。人間に向けた出力はすべて日本語で書く。

**目的**: **どのタスクの外でも、独立した文脈で**、コードと `03-impl` と `02-design` が
一致していることを確かめる — **意図と実装の突き合わせ**であり、このキットの中心そのものである
(`.claude/directions/core.md` §1)。F1 のタスク内整合確認は似て見えるが、**1つのクロージャに閉じた自己点検**である。
このフローは、**その自己点検には見えないものをリポジトリ全体で捕まえるために在る。**
無人・問いゼロ・3チャネル出力・完走時に鮮度スタンプ(**対象が0件の run は記録しない** —
あちらの §2 と同じ) — `/verify-docs` と同じ常在の規則である
(あちらの §2 が独立レビューの起動を、§3 がチャネルとコミットの規律を所有する:
`auto-fix:` を頭に付けた作業ブランチへのコミット、修正ループ上限2、誰にも答えられないものは飛ばす)。
**起動元から独立している。**

**書くもの**: ツール生成領域(全面)、コードに対して決着した事実の修正
(原則2 が既に定めている)、03 層代表の `verified`、鮮度スタンプ、キューの項目、質問シートの項目。
**決して書かないもの**: 製品コード(修繕は `/build --repair` のもの)、意図の変更(キューへ)、
00/01 の文書。

**このスキルが負う規範の節** — `.claude/directions/reading.md` の `/verify-impl` の行。

## 0. 範囲

**最初に、保護ブランチで書かないことを確かめる** ★ — 走らせるのは1行である:

```sh
python3 .claude/scripts/guard-branch.py --verify
```

**この固定名(`work/<YYYY-MM-DD>-verify`)を使うのは、このフローが slug を持たないからである**
— 名前を発明しない。**終了コードが `0` でなければ、そこで止まって報告する**
(`1` は、こちらの知らない事情が在るという意味である。**`git branch -D` を打たない**)。
判定の中身 — 既定ブランチの求め方、同じ名前の枝が既に在るときの2分岐、止まる条件 — の正は
`.claude/directions/flows.md` §7.1 である。**ここには写さない。**

既定: 最後の `verify-impl` の green 鮮度スタンプ以降の差分(コードと `docs/02-design/` /
`docs/03-impl/`)を、`relations-query.py --impact` の到達で閉じたもの —
差分が触れたモジュールと、その呼び出し元・呼び出し先を1ホップ分。`all` は全モジュールを覆う。
`building` のクロージャは除外する。`awaiting-verify` のクロージャは優先の対象であり、
その記録の 主張 と `## 基本要件の点検` に照らして読む。`critical: true` のクロージャは**常に独立レビューへ届く**
(起動は `/verify-docs` §2 のとおり)。

## 1. 再生成してから検査する

**独立レビューはこの再生成の直後に起こす**(起動は `/verify-docs` §2)。
**書込みの控え(`git status --porcelain`)を取るのは、書き込みのできる砂箱で起こしたとき
だけである**(`/verify-docs` §2 の段3)。取るならそのときに取る — 「自分の検査の前に起こす」の「検査」とは
下の読取の検査であり、**先に控えを取ると、このフロー自身の再生成が「レビューが書いた」と
読まれる**(inspection-21 V-11)。

再生成の宛先は SSOT である — タスクの装置が無いので段階の側は存在しない。
変わっていないモジュールは同じバイト列に再生成されるので、**書き出しの費用は差分ぶんである**。
**地図の JSON は1回だけ書き出し、以降は `--from` で渡す** ★(2026-09-15。inspection-28 B-4。2026-09-23 に JSON を渡す形へ直した)—
`cluster-features.py` と `callgraph-check.py` は **`--from` を渡さないと自分でコードを
解析し直す。** 上のコマンド列はそれを渡す形にしてある。**渡し忘れると、同じコードの解析を
この1回の検証の中で何度も払う**(何倍になるかは**未確認**である — 実測が無い)。
**`--from` が取るのは地図の JSON ファイルであって、SSOT のディレクトリではない** ★
(2026-09-23 の実測: `--from "$CG_SSOT"` と書いていた頃は、ディレクトリを JSON として読もうとして
2本とも落ちた)。JSON は `build-callgraphs.py --format json` が標準出力へ出すだけで、
`--out` の書き込みとは別の1回である — **地図の解析は `build-callgraphs.py` の2回に減るが、
1回にはなっていない**(残っている費用。2回目を消す口はまだ無い)。
**`check-contracts.py` には渡す口が無い** ★ — あれは契約の定義も読むので、
**いまは自分で解析する。** ここは残っている費用であり、消せていない。
**何を違反と見るかは道具ごとのままである** — 共有するのは読み取りの結果だけで、判定は混ぜない。

```bash
python3 .claude/scripts/build-facts.py check           # ★ いちばん先。機械の欄の差分ゼロと、参照先の実在
CG_SSOT=$(python3 .claude/scripts/resolve-callgraph-out.py --ssot)
python3 .claude/scripts/build-callgraphs.py --out "$CG_SSOT"
# ★ 以降は --from で、いま作った地図を読ませる(2026-09-15。inspection-28 B-4)—
#    渡さないと、それぞれが自分でコードを解析し直す(同じ解析を何度も払う)。
#    **渡すのは JSON のファイル**であって "$CG_SSOT"(ディレクトリ)ではない(2026-09-23)
mkdir -p artifacts
python3 .claude/scripts/build-callgraphs.py --format json > artifacts/verify-impl-cg.json
python3 .claude/scripts/cluster-features.py --from artifacts/verify-impl-cg.json --out "$CG_SSOT"
python3 .claude/scripts/callgraph-check.py --from artifacts/verify-impl-cg.json   # コード ⇄ 機能間連携仕様書(重大度「高」ゼロが green の条件)
python3 .claude/scripts/check-contracts.py             # 契約(OpenAPI)⇄ 設計 ⇄ コード
python3 .claude/scripts/check-relations.py             # 機能間連携仕様書集合の内部整合
python3 .claude/scripts/relations-query.py --health    # 構造の健全性(肥大・循環・到達不能)
```

**`build-facts.py check` が先頭に在るのは、走らせ忘れを起こさないためである** ★ —
**このフローの合格の条件に「差分ゼロ」が入っている。** 機械の欄はコードから書き写した値を
持つので、**実装が変われば必ずずれる** — それを人間が12本の文書の46か所で手直しするのを
やめるための道具である(2026-08-26 の実測)。違反が出たら
`python3 .claude/scripts/build-facts.py update` を打ち、その差分を**事実の差異の自動修正**と
してコミットする(このフローの既定の扱いそのものである — 下の振り分けの表)。
**埋め直しても消えない違反は、参照か宣言の誤り**なのでキューへ回す。
**宣言(`docs/facts.json`)が無いプロジェクトでは 0 を返す。**

**機能表に足すべき行の候補はここでは出さない** — 機能表の行は人間の合意事項であり
(`.claude/directions/features.md` §7)、このフローは人間に問えないので、受け取っても行き先が無い。
入口の取りこぼしは同じ run の `callgraph-check.py` が見る — **見るのは2本である** ★
(2026-09-15。inspection-28 A-8)。**FT2** は外から呼ばれる口(エンドポイント)の取りこぼしを、
**FT5** は**口を持たない入口**(画面の操作を受け取る関数のような)の取りこぼしを見る。
**FT5 のほうを落とすと、まとめて登録した書き方の下で足した関数が、どの検査にも掛からずに
静かに積み上がる**(実測: 画面1枚で入口の宣言が23のまま実装が37になり、14件が
どの入口からも到達しないものに化けていた)。
**この2本が「未検査」と報告されたら、それは合格ではない** ★ — 呼び出し関係を組み立て
られなかったとき、`callgraph-check.py` は **FT2〜FT5 を検査せずにその旨だけを報告する。**
**実装が既に在るのに地図が空なら、そこで落ちる**(2026-09-15。inspection-28 A-8)—
**「まだ書いていない」と「見られていない」を分けている**ので、実装前の周は今までどおり通る。
**落ちた run は `red` にする**(組み立てられない原因を直してから回し直す)。
**何が未検査だったかを報告に逐語で書く。**
(inspection-21 V-4)

各検査が何を意味し、既定の対処が何かは、**それを所有する節に在る**(書き写さない) —
`callgraph-check.py` は `.claude/directions/callgraphs.md` §6、`check-contracts.py` は
`.claude/directions/02-design.md` の contracts の節、`check-relations.py` は
`.claude/directions/relations.md` §6.3 である。再生成の2本(`build-callgraphs.py` と
`cluster-features.py`)は検査ではなく再生成であり、その出力は下の振り分けの表の**自動修正**
(ツール生成領域)そのものである。
**`relations-query.py --health` の行き先だけはこの節が持つ**: 肥大・循環・到達不能・テストの
欠落・要件の欠落は**キュー**へ出す(原則8 の記録先の振り分けで課題票か残務1行)。
**肥大したモジュールは 02 の分割定義の見直しの提案として出すのであって、決して自分で割らない。**
そのうえで、範囲に対して読取の検査を行う:

- **B(03 ⇄ コード)**: `impl` のパスと frontmatter が実物のコードと一致すること。
  並べられたテストが実在すること。散文の本文は、それが何かを主張しているところだけ見る。
  触ったモジュールの「実装上の判断」/「テスト設計の判断」の行を歩く:
  **見直す条件 が成立している行は所見である**(検証済み記録を持った偽の主張)。
- **E(02 ⇄ 03 の連携の差 — 中心そのもの)**: `PLAN-*` を `MODULE-*` と照合する
  (手順: `relations.md` §7)。PLAN が在って MODULE が無いのは、02 がそれを未実装として
  並べているときだけ普通である。MODULE が在って PLAN が無いのは設計漏れである。
  callees / contracts の食い違いは — **事実はコードに対して、意図はキューへ。**
- **主張の突き合わせ**: 各 `awaiting-verify` の記録の主張を、再生成したグラフとコードが
  実際に示すものと突き合わせる。**偽の主張はその記録を名指した所見である。**
  **見るのは、ここで反証できるものだけである** ★:
  - **外部挙動の変化 あり/なし** と **critical 接触 あり/なし** — グラフとコードから確かめられる。
  - **`## 基本要件の点検` の判定**(`BR-nn` の 該当 / 非該当)★ — **これもグラフとコードに
    照らす。判定の当否を見るのはここである**(**誰が何を見るかの正は `baseline.md` §1 の4。
    ここでは言い直さない**)。「`BR-02` 非該当: 外から値を受け取らない」と1行書けば、
    入力の検証はそのタスクから永久に消えていた。
    **誤った `非該当` は、その記録を名指した所見である。**
    **`awaiting-verify` だけを見て終わらない** ★ — この節が読むのはその run の対象集合の
    記録だけなので、過去の記録はここに入らない。その隙間で同型が9度再発した。
    **run ごとに1回、全記録を計器に掛ける**:

    ```bash
    python3 .claude/scripts/check-baseline-verdicts.py   # 全状態・全記録(計器。疑いでは拒まない)
    ```

    印字された疑いのうち、**この run の対象集合に掛かるものは、ここで裁定して直す**
    (クロージャのファイル全体に照らす — `baseline.md` §1 の1)。
    **対象集合の外のものはキューへ**(原則8 の振り分けで課題票か残務1行)。
    **「検査できなかった行」と「記録に判定行が無い BR」の数も報告に写す** — 疑い0件は
    「全部見た」ではない。**後者は、足したばかりの項目が過去の記録に対して盲目であることを
    言っている。遡って埋め直さない**(`baseline.md` §4.3)。
  - **「触ったテスト green」は見ない** ★ — グラフからもコードからも判定できず、
    **テストを実際に走らせるしかない。** それは F4 の仕事であり、ここで走らせると
    F4 が同じ周でこれから払う最も高い費用を先に重複して払う(しかも成果物の置き場を誤れば
    F3 と F4 の鮮度スタンプを自分で失効させる)。**反証するのは F4 である**
    (`/verify-tests` §0)。`lint / build` の主張も同じ理由でここでは見ない。

## 2. 振り分け — 3チャネル

| チャネル | このフローでの中身 |
|---|---|
| 自動修正 | ツール生成領域(全面 — それが再生成である)。**事実の食い違いはコード側に合わせて直す**(パス・シグネチャ・呼び出しの有無 — 原則2 が既に定める。直した箇所は全部レポートへ)。03 の `impl`/`callers`/`callees`/`tests` の転記ミスもここ |
| キュー | **意図の食い違い**(設計が期待した連携と実装が違う — どちらが正か判定できないもの)、02 に無い MODULE(設計漏れ)、02 にあるのに無い実装。原則8 の記録先の振り分けで課題票か残務1行 |
| 質問シート | 問う基準を満たす解釈の割れだけ。`docs/sheets/questions-<YYYY-MM-DD>.md` に追記(新規作成時は `created:` frontmatter — `/verify-docs` §3 と同じ書式) |

**`残務` に満杯は無い。いつでも書ける** ★ — 書き終わったら
`python3 .claude/scripts/doc-health.py --rotate` を打つ。50行以上なら
`docs/residual.md` が `docs/residual-NNN.md` へ押し出され、同じ名前の新しいファイルが作られる
(**ローテーション**。`glossary.md`)
(**1行も落ちない。権限の制限も無い**)。50 未満なら何もしない(`issues-pendings.md` §2.1)。

修正ループの上限は2。コミットは `auto-fix:`。**文書を太らせない。**

## 3. 検証済み記録と鮮度スタンプ

1. `relations/` か `features.md` を変えた run は `docs/03-impl/index.md` の MINOR を上げ、
   検証済み記録を打ち直す(`verified` — 03 層はその索引によってまとめて検証される。原則6 の例外)。
   索引を再生成する: `python3 .claude/scripts/build-index.py`。
2. **自動修正が意味のあるものを変えた run は、履歴を1件残す**
   (`.claude/templates/history.md`。`record:` に「なし(taskless — flow: verify-impl)」)—
   `/verify-docs` §4-3 が負うのと同じ義務であり、原則1 の書き手の一覧がこのフローを名指して
   いるのはそのためである。
3. 鮮度スタンプ — green の条件: 再生成が完走したこと、**`build-facts.py check` が 0 を返すこと**
   (機械の欄の差分ゼロと参照先の実在。§1 の先頭で走らせたもの — 埋め直した差分は同じ
   `auto-fix:` のコミットに入る)、`callgraph-check.py` が重大度「高」ゼロを
   報告すること、残るすべての所見が振り分けられていること。**この run が書いたものを先に全部
   コミットする**(再生成した領域、事実の修正、索引の版上げ、`build-index.py` の出力 —
   `auto-fix:` のコミット1本): `record` は依存に未コミットの変更が在るとき green を拒む
   (`flows.md` §2 — 未コミットのままの green は書いた瞬間に失効する)。
   この run が起票した課題票は `docs/issues/index.md` も再生成する
   (`python3 .claude/scripts/build-index.py`。`issues-pendings.md` §6)— 同じコミットの中で。
   **手前で `git status` を目で見て確かめない** — 裸の出力は依存の外の汚れも並べるので、
   依存の中の汚れだけを問う問いには答えられない。**拒まれたら、`record` が印字したパスを
   コミットして打ち直す**(依存の外の汚れは record を止めない — `flows.md` §2)。
   そのうえで昇格の周を回す:
   ```bash
   python3 .claude/scripts/stamps.py record verify-impl <green|red> --evidence artifacts/verify-impl.log   # all なら --full を添える
   # critical: true の awaiting-verify 記録が在る run では、green に --lens <実際に走った独立レビューの名前>
   # が必須(record が拒む — `.claude/directions/core.md` §5 の機械接続。inspection-17 判断9)。red に --lens は不要
   python3 .claude/scripts/stamps.py promote
   # promote が「遷移 N 件」(N>0)を報告したら、その書込みをコミットして残す(flows.md §2)
   git add docs/build-records && git commit -m "promote: awaiting-verify → verified" -- docs/build-records
   ```
   **`green` には `--evidence <path>` が要る** ★(2026-09-15。inspection-28 A-7)— 走らせた
   結果を `artifacts/` の下へ書き出し、そのパスを渡す(複数可)。**実在して中身が在る
   ことだけを機械が見る** — 中身が本物かどうかは見ない。それでも、後から人間や別の
   エージェントが**現物を開いて確かめられる**ようになる。`red` には要らない。
   **鮮度スタンプ自身のコミットはここでは打たない** — コミットするのは**1周の終わりに1回だけ**
   である(`flows.md` §2)。
   **リポジトリの一部に範囲を絞った run は、全体ではなくその一部を記録する**:
   実際に見た範囲ごとに `--covers <path>` を1つずつ添える(`stamps.py check` の red の出力が
   その行をそのまま渡す)。`--covers` を省いてよいのは、その run がすべての依存
   (`stamps.py deps verify-impl`)を覆ったときだけである —
   **部分的な run に完全な green を記録するのは、読んでいない範囲について green だと主張すること
   である。** **`all` で回した run は `--full` を添える**(全数の最終実行を残す印。
   判定には効かない — `flows.md` §2.1)。

## 4. 報告(日本語。無人の run は 40行 / 2,000バイト以内)

```
## 実装整合(F3): <対象 N モジュール / 増分 or all>
判定: green / red(高 N 件) / 鮮度スタンプ: 記録済み @ <sha>
最弱点(所見ゼロでも1行): <>
独立レビュー: <@review(codex) / @review(claude — 症状) / Codex / サブエージェント / なし(理由)>
### 機械検査
| スクリプト | 結果 |
### 自動修正(auto-fix: コミット <sha>。事実はコードが正 — 原則2)
| 箇所 | 内容 |
### キューへ(意図の差異・設計漏れ)
| 行き先 | 内容 | 関係する構築記録 |
### 質問シートへ(0件が既定)
### 次にあなたがすること
```
