# 試験 — F4、製品の振る舞いのフロー

対象: $ARGUMENTS。人間に向けた出力はすべて日本語で書く。

**目的**: 製品が実際に動くこと — テストスイートの全件、実システムに対する `AC-nn` の全件、
そして探索的ブラウザQA。**このフローは、`/build` が意図的に先送りしたものすべてが実行される
場所である。** 無人・問いゼロ・試験区分ごとの鮮度スタンプ。デプロイゲートは
`flow-config.json` の `f4_scopes` の全試験区分の green を要求する(`flows.md` §2)。
**起動元から独立している。**

**書くもの**: キューの項目(`docs/issues/` の項目と `residual.md` の `残務` 1行 — `flows.md` §5)、
試験成果物(`docs/` の外)、鮮度スタンプ、質問シートの項目、
そして §1-3 の「適用外(操作面なし)」の宣言(`flow-config.local.json` の `f4_scopes` +
`pendings.md` の棚上げ(`P-nnn`))、**一時除外の登録**(`tests/quarantine.yml` の項目と `due` —
§1。課題票と同じ期限を機械が読む場所へ置くための1筆である)。
**設定への書込みはこの3種だけである** — ほかの宣言ファイル(`suites.yml` / `gates.yml` /
`adapters.yml` / `environments.yml`)は書かない。それらの不備は `origin_layer: 02` の課題票にする。
**製品コードを決して書かず、SSOT も決して書かない** — F4 は原則1 の書き手の一覧に無い:
古くなった `03-impl/tests/` の状態の列は**事実の差異としてキューへ載せ**、`/verify-impl` が
決着させる。修繕は `/build --repair` の仕事である。
**検証する対象を自分で直すことは、検証する側が自分の対象に手を触れることである。**

**このスキルが負う規範の節** — `.claude/directions/reading.md` の `/verify-tests` の行。

## 0. 範囲と入力

**最初に、保護ブランチで書かないことを確かめる** ★ — 走らせるのは1行である:

```sh
python3 .claude/scripts/guard-branch.py --verify
```

**この固定名(`work/<YYYY-MM-DD>-verify`)を使うのは、このフローが slug を持たないからである**
— 名前を発明しない。**終了コードが `0` でなければ、そこで止まって報告する**
(`1` は、こちらの知らない事情が在るという意味である。**`git branch -D` を打たない**)。
判定の中身 — 既定ブランチの求め方、同じ名前の枝が既に在るときの2分岐、止まる条件 — の正は
`.claude/directions/flows.md` §7.1 である。**ここには写さない。**

引数は試験区分を選ぶ — **1つでも、空白で区切って複数でもよい**(並べたときは並べた試験区分だけを1本の run で走らせ、その並べた分だけを記録する。inspection-23 B-6)。**引数なしはすべてを走らせ**(裁定 D'-4)、全試験区分を記録する。
入力: `02-design/environments.md` の正確なコマンド(**コマンドが無い、または未定であること自体が
red である** — `origin_layer: 02` で起票し、red を記録する。**決してコマンドを発明しない**)、
`00-requests/acceptances.md` の `AC-nn` の一覧、02 のテスト戦略の E2E シナリオ一覧、
そして最後の green 鮮度スタンプ以降の `awaiting-verify` の構築記録(犯人探しの範囲を絞る集合 —
`build-record.md` §1)。

**その記録の「触ったテスト green」の主張は、ここが反証する** ★ — 実際に走った結果と
突き合わせ、**主張が偽ならその記録を名指した所見である**(現実が勝つ。`build-record.md` §2)。
**F3 はこれを見ない** — グラフとコードから判定できないものを F3 に持たせると、テストを
重複して走らせる誘因になる(`/verify-impl` §1 の「主張の突き合わせ」)。
**反証できる者が反証する。**

**`lint / build green` の主張は、どのフローも直接には反証しない** ★ — このフローが走らせるのは
unit / integration / e2e / qa の4つだけで、**lint も build も試験区分に無い。**
壊れたビルドはここの試験一式が落ちることで**間接的に**露見するだけである。
**これは指針であり、執行者は読み手である**(`delegation.md` §3 が「理由が本当に理由か」を
検査を持てないものに分類しているのと同じ扱い)。**宛先を書いて反証しないのが、いちばん悪い** —
「誰かが見ている」と読めてしまうからである。

## 1. 実行する

試験区分ごとに、すべて要求されているときはこの順で: unit → integration → e2e → qa。

**回す試験区分ごとに、重要テストだけを除外なしで通す実行を1つ足す** ★ — `f4-unit` /
`f4-integration` / `f4-e2e` が呼ぶスイートは `@flaky` と一時除外(quarantine。期限付きで実行対象から
外す登録)を除外する。**`@critical` の印だけではこの除外を免れないので、重要テストを一時除外に
入れたままでもその試験区分は緑になる。** `f4-critical` は除外を一切かけずに同じ3つの試験区分を通す
テスト実行ゲートで、`gates.yml` が持つ。
**同じテストを二度走らせない** ★(2026-09-15。inspection-28 B-6)— 通常の実行の側を
**重要でないテストに絞り**、重要テストは除外なしの実行だけで通す。
**絞るのはスイートの宣言(`tests/suites.yml`)である** — `unit` / `integration` / `e2e-full` の
`exclude_tags` に `@critical` を足す。**テスト実行ゲートのステップには、タグを外す指定が無い**
(属性の一覧は `test-runner-usage/references/declarations.md`)。
**スイートはプロジェクトのものなので、配布物では書けない** — 移行の記録
`.claude/migrations/2026-09-15e-critical-once.md` が案内する。
**合わせた対象が、絞る前と1件も違わないこと**が条件である(片方から落ちて両方から
漏れるものが在ってはならない)。**全部が重要なプロジェクトでは通常の実行が0件になる** —
それは正常であり、「対象0件」と書いて終える。
**構築の途中で使う共通の実行は狭めない** — あれは速さのための実行であり、
出荷の判定とは別である。

**この節が掛かるのは、テスト基盤(`tests/tools/test-runner`)を使っているプロジェクトだけである** ★
— `02-design/environments.md` が言語のテストコマンドを直接呼ぶ形で宣言しているなら、
`f4-critical` というテスト実行ゲート自体が存在しない。その構成では**この節を飛ばし、飛ばしたことを
§4 の報告に1行で書く**(§1 の「表の網羅」③ と同じ扱い)。**`qa`(探索的ブラウザQA)にも掛からない**
— 対応するステップが無いためで、`qa` だけを回す run では呼ばない
(該当するステップが0本の `--only` はランナーがエラーにする)。

**呼ぶのは、その run が回している試験区分に当たるステップだけである** ★ — `f4-critical` は
`unit` / `integration` / `e2e` の3ステップを持つので、`--only` で絞る:

```bash
./tests/tools/test-runner --gate f4-critical --only unit          # unit を回す run
./tests/tools/test-runner --gate f4-critical --only integration   # integration を回す run
./tests/tools/test-runner --gate f4-critical --only e2e --env <宣言した環境>   # e2e を回す run
```

**`--only` を省いて丸ごと回さない** — 単体だけの run が E2E の環境の可用性に縛られ、
**試験区分ごとに1つのテスト実行ゲートへ分けてある理由**(実行証拠とその試験区分を一致させる。
`gates.yml` の F4 の節)がそこで壊れる。**結果はその試験区分の green の条件に入る**(§3)。
`@critical` を1件も付けていないプロジェクトでは、そのステップが「対象テスト0件」の skipped に
なる — **それは正常であり、下の「0件を合格と読まない」の対象ではない**(重要テストをまだ
書いていないという事実がそのまま出ているだけである)。

1. **unit / integration / e2e**: コマンドを逐語で走らせる。**各コマンドの最終出力行を報告に
   逐語で引く。** 不安定な合格(何も変えずに、落ちてから通る)は合格ではなく所見である —
   記録すること。**再実行は同じテストにつき2回まで** ★ — 2回を超えて安定しないテストを
   「通ったことに」しない: まず §2 の表で裁定し(テストコードだけで直り切るなら auto-fix で
   閉じてよい)、この run の中で安定させられなかったものは、解消の条件(安定化の確認、または
   削除の裁定)を `closes_when:` に持つ課題票にする。**一時除外をいつまで許すかの期限は課題票の
   本文に書く** — `closes_when:` は外から観測できる解消の条件の欄であって、期限の欄ではない
   (`issues-pendings.md` §3)。
   **実行対象から外す経路は、台帳への登録1本だけである** ★(2026-09-15。inspection-28 A-5)—
   **`@flaky` の印を付けただけで外さない。** スイートの宣言は `exclude_tags: ["@flaky"]` で
   その印の付いたテストを丸ごと外すので、**印を付けるだけで、期限を1日も持たないまま
   実行されなくなる。** 期限切れを見る仕組みは `quarantine.yml` の `due` しか読まないので、
   **印だけで外れたテストには、期限の検査が永久に掛からない。**
   だから印と台帳の役割を分ける: **`@flaky` は「結果が揺れる」という分類**であり、
   **外すかどうかを決めるのは台帳である。**
   **これは機械が見る** ★(2026-09-15。inspection-28 A-5)—
   `python3 .claude/scripts/check-quarantine.py` を走らせる。
   **印が付いているのに台帳に無いファイルが在れば、そう言って落ちる。**
   **見つけたら、実行に戻すか、期限を付けて台帳に登録するかのどちらかにする。**
   どちらもしないまま次へ進まない。**結果は報告に1行で書く**(0件なら「0件」と書く)。
   **この検査は取りこぼす側へ倒してある** — 見ているのはファイル単位の突き合わせなので、
   **鳴らなかったことは「1件も無い」の証明ではない。**
   **同じ期限を `tests/quarantine.yml` の `due` にも書いて登録する** ★ — 課題票の本文は人間が
   読む場所であって、**機械は読まない**。`gates.yml` の `quarantine_overdue: fail` が期限切れを
   不合格にできるのは、`quarantine.yml` に登録された `due` に対してだけである。登録しないと、
   **期限の検査が空振りする** — 何が起きるかは、そのテストに `@flaky` の印が付いているかで
   変わる ★(2026-09-15。inspection-28 A-5):
   **印が付いていなければ**、そのテストは実行対象に残り続けるので、**試験区分が赤で居座る。**
   **印が付いていれば**、スイートの宣言(`exclude_tags`)がそれを外すので**緑になってしまう** —
   期限を1日も持たないまま、静かに実行されなくなる。**後者のほうが危ない。**
   だから上のとおり、**外す決定は台帳への登録1本**である。**2か所の役割は違う**: `quarantine.yml` の `due` が機械に効く期限、課題票が人間の裁定と
   経緯である。**どちらかを直したら、もう一方を同じ日付に合わせる** — 延長の判断は課題票に書き、
   決まった日付を `quarantine.yml` へ写す。**登録も更新も、この run を回している側がやる。**
   **`tests/quarantine.yml` が効くのは、テスト基盤(`tests/tools/test-runner`)を通す構成だけである** ★
   (2026-09-13)— 言語のテストコマンドを直接呼ぶ構成では、**この宣言を読む者が居ない。**
   **その構成で一時除外が要るときは、書いて済ませない**: 課題票は同じように立てたうえで、
   **その実行系の側で期限までの除外が実際に効くこと**(除外の指定と、期限が来たら不合格に
   なる仕組み)を確かめ、**確かめられないならその試験区分を red にする。**
   **効かない宣言を書いて緑にするのが、いちばん悪い** — 除外されていないのに除外したつもりの
   テストが残り、期限の検査も空振りする。
   **一時除外を1件も使わない直接実行は、この段の対象ではない**(red にする理由が無い)。
   **`@critical` を付けたテストは `quarantine.yml` に登録しない** ★ — クリティカルパスの
   テストが不安定なら、それはテストの問題ではなく**製品またはテスト設計の問題**として扱う
   (`test-runner-usage` の `references/declarations.md`)。一時除外で緑にせず、§2 の表で裁定する。
   不安定だったテストの**件数**は §4 の報告に1行で出す。
   **「再実行すれば通る」が常態になると、スイート全体が合否の判定として機能しなくなる** —
   動いて見えるが何も守っていない状態は、テストが無いより悪い。
   **0件と skip を合格と読まない** ★ — 実行が 0件で終わったスイートと、説明の付かない skip は、
   テストの失敗ではなく**「検証できていない」という観測**である: その試験区分を red にし、
   原因は §2 の表で裁定する — 環境の不備と**判明したものだけ**を `origin_layer: 02` で起票する
   (テストコードに紛れ込んだ skip も、消えたテスト定義も、同じ形に見える — 空振りは環境が
   原因である証拠ではない)。**緑に見えて何も検証していないことが、このフローの最も危険な
   失敗である** — だから報告の表には結果だけでなく**実行件数(走った数と skip の数)**を含める。
   **この判定は機械と手順の二重であり、重複ではない** ★ — `gates.yml` の `strict: true` は
   対象0件・未配線・証拠欠落を不合格にし、`forbid_skip` は実行結果の skip が1件でもあれば
   不合格にする。**ただし機械が効くのは、このランナーを通して回したときだけである** —
   `02-design/environments.md` が宣言したコマンドが別の実行系(言語のテストコマンドを直接
   呼ぶなど)なら、0件も skip もそのまま緑で返る。**だから手順側のこの判定を省かない。**
   ランナーを使っているプロジェクトでは同じ判定が二度掛かるが、費用は件数を読むことだけで、
   テストが二度走るわけではない。
   **版がビルドと揃っていない環境での実行も、合格と読まない** ★(2026-11-04。
   `delegation.md` §2.4)— `unit` / `integration` / `e2e` を走らせる前に、テストを走らせる環境が
   `02-design/environments.md` の「コンテナ・実行環境」が名指す固定と一致するかを確かめる。
   **確かめるのは §2.4 の定義の項目すべてである**(処理系とツールチェーン・実行基盤・製品の依存。
   それぞれの確かめ方は §2.4 が持つ)。`e2e` で見るのは、試験される側がビルドの出荷物そのもので
   あることである。**掛かり方は、`02-design/environments.md` に `### ビルドとテストの版の固定` の
   見出しが在るか(版の固定の宣言)で分かれる**(2026-11-05。§2.4 の表):
   **在れば、一致しない、または確かめられないとき、その試験区分を red にし**、環境の不備として
   `origin_layer: 02` で起票する。**無ければ(移行前)、合否には掛けず起票もしない** — 見比べられた
   不一致と、見比べられなかった項目を報告に書くだけである。
   結果は報告に1行で書く(「版の一致: 一致(<固定の場所>)/ 不一致(<何が何と違うか>)/
   未確認(<理由>)/ 未宣言(移行前。不一致: <…> / 未確認: <…>)」)。
   **`qa` には掛からない**(台本を走らせる試験ではない)。
2. **AC 照合**(e2e と一緒に): すべての `AC-nn` を実システムに対して判定し、表にする。
   **あえて全件である** — どの `AC-nn` がどの変更に影響されるかを機械で言えない間は、
   **全件を判定して表にするのが既定**である(§3 のスイートを丸ごと走らせるのと同じ理由)。
   **その対応づけを機械で言える道具が入った時点が、この既定を見直す契機である。**
   判定は `合格` / `不合格` / `未判定条項` / `適用外(P-nnn)` の4値である。
   **未判定条項**(この実行環境に無い環境が要るなどで、実システムに対して合格とも不合格とも
   判定できなかったもの)は**そのものとして報告する。決して合格としない** — **`e2e` の green を
   止める**(§3)。**鮮度スタンプと再検証の `判定不能` とは別の語である**(あちらは機械が
   比較できなかった状態を指す — `flows.md` §2 と `doc-health.py` の解消条件の判定)。
   **`適用外(P-nnn)` と書けるのは、その環境をこのリリースでは用意しないと人間が決め、棚上げの
   項目(`docs/pendings.md` の `P-nnn`。決めた日・決めた人・なぜ今は OK か・どうなったら解消が
   必要か)が実在するときだけである**(`issues-pendings.md` §2.2)。**このフローは `適用外` を
   自分で宣言しない** — 未判定条項 を報告して `e2e` を red にし、仕様の解釈が割れるものは
   質問シートへ載せる。根拠を持たない `適用外` は、確かめていないものを合格側に倒す抜け道になる。
3. **qa — 探索的QA**: 台本の外側。**実体は2つ在り、持っている操作面の分だけ走る** ★ —
   画面を触る**探索的ブラウザQA**(手順の正は **`.claude/skills/browser-qa/SKILL.md`**)と、
   サブコマンドを叩く**探索的CLI QA**(手順の正は **`.claude/skills/cli-qa/SKILL.md`**)である。
   **両方の面を持つ製品では両方が走り、両方が green になって初めて qa が green になる。**
   **片方が適用外でも qa は消えない** — qa 試験区分が丸ごと適用外になるのは、
   人が直接操作する面が1つも無いとき(他のプログラムから呼ばれるだけの部品など)だけである
   (`.claude/directions/ux.md` §0)。
   **qa は `docs/ux/`(UX 文書)にも依存する**(`stamps.py deps verify-tests:qa`)— UX 文書
   だけを直しても qa は失効する(あの層は文書検証・実装整合検証の外に居るので、実画面との
   突き合わせはこの試験区分だけが受け皿である — `.claude/directions/ux.md` §0)。
   **走らせる前に `python3 .claude/scripts/check-ux.py` を回す** — red(条項参照・画面ファイル・
   指摘番号の実在、達成条件の欄の未記入)はブラウザを触る前に直せる種類のずれなので、
   先に依頼元へ返す(`docs/ux/` が無いプロジェクトでは何も見ずに green である)。
   **注記(達成条件の表が無い画面の一覧)は red ではない** — 止めずに依頼元への報告へ載せる
   だけである(`.claude/directions/ux.md`「達成条件」)。
   **独立した文脈で走らせる** —
   **艦隊運用では `@qa` のエージェント**(`orchestration.md` §1.4)。**まず作業指示を見る** ★ —
   **`@qa` の id が名指されていればそのウィンドウは既に立っている**ので、要求せずにそこへ渡す
   (**qa が走る作業指示**では中央エージェントが先に起こす。その語の定義は §1.4)。
   **名指されていないときだけ**、`qa` を実際に走らせると決めた時点で中央エージェントへ1行で
   要求する。**要求するのは、その製品が持っている面のぶんだけである** ★
   (2026-09-15。inspection-28 C-6)— 画面が在れば `探索的ブラウザQAを1本要求する`、
   サブコマンドが在れば `探索的CLI QAを1本要求する`、両方在れば両方。
   **持っていない面の担当を要求しない。** どちらの経路でも、id へ渡すのは
   対象・起動手順・触ってよい範囲・出力様式である(**自分の所見は決して渡さない**)。
   **依頼しても返らないときだけ** ★(要求して id が返らないときも、**名指された id へ依頼して
   返らないとき**も。後者を落とすと、名指された `@qa` が死んでいる run に出口が無くなる)、
   自分でブラウザを動かすのではなく「艦隊が @qa を用意していない」で `qa` を red にする —
   **依頼も要求もしていないのに red にしてはならない。**
   艦隊でなければ codex + `chrome-devtools` MCP に、その SKILL.md をパスで指して走らせる —
   **codex が使えないときは claude + `claude-in-chrome`** を §1.4 の2条件のもとで。
   **書込みの控えを取るのは依頼元、つまりこのウィンドウである** ★ — 依頼を投げる前と報告を
   受けた後に控えを取り、**差が出たら所見ではなく違反として報告する**。**控えの2行と、それが
   見ないものは `orchestration.md` §1.1.1 の `@qa` の段が正である**
   (要旨: `@qa` は砂箱を持たないので、書込みを止めているのは役の規範だけである。
   **2026-09-20 からは codex のどの役も砂箱を持たない**ので、この事情は `@qa` に限らない)。
   **口によらず取る**(claude + `claude-in-chrome` でも同じ)。**`@qa` の自己申告は控えではない。**
   **運用形態にもよらない** ★ — 単独運用には別ウィンドウの依頼元が居ないので、
   **控えを取るのはこの `/verify-tests` を走らせているウィンドウ自身である**
   (人間の手なのは起動行だけである — `orchestration.md` §10)。
   **このウィンドウがするのは、返ってきた所見の裁定だけである**(重大度「高」と振る舞いに
   関わるものは個別に、残りは列挙する)。「適用外(操作面なし)」の宣言は
   **`02-design/system.md` の「操作面の宣言」の節が所有する** ★(2026-09-15。inspection-28 C-20。
   正は `02-design.md`)— **`environments.md` の2つの節**(「ブラウザQAの宛先 allowlist」と
   「CLI 検証の実行条件」)が持つ「適用外(画面なし)」「適用外(コマンドの面なし)」は、
   **そのレーンが走らないことを言うだけで、試験区分を外す宣言ではない。**
   そして `flow-config.local.json`(`qa` を除いた `f4_scopes`)と `pendings.md` の棚上げに属し、
   **デプロイゲートと設定が同じことを言う**ようにする。
   **古い導入先では、環境文書の側にだけ全体の省略が書いてあることがある** — 見つけたら
   `system.md` の「操作面の宣言」へ移すよう、依頼元へ返す。
   **★ 外せるのは「人が直接操作する面が1つも無い」ときだけである**(2026-09-15 の裁定)—
   **画面が無いだけでは外せない**: サブコマンドが在るなら探索的CLI QA が走る
   (`.claude/directions/ux.md` §0。既に外しているプロジェクトの直し方は
   `.claude/migrations/2026-09-15-qa-cli-lane.md`)。
   **02 の行が先である**(`conventions.md` §1)— その行が無いあいだは、上の2筆
   (`flow-config.local.json` と `pendings.md` の棚上げ)だけで適用外を名乗れない。
   **そのときは `qa` を red のまま報告し、02 にその行を書く課題票を1件起こす**
   (`origin_layer: 02`。`issues-pendings.md` §1)— **このスキルは SSOT を書かないので、
   行そのものは構築フローが書く。**
   **道具を動かせないことは、合格でも適用外でもない** — `qa` を red にし、
   環境の不備を報告に載せる。
   **ただし、止めるのは「その面に要る道具」が無いときだけである** ★
   (2026-09-15。inspection-28 C-6)— **画面の面にはブラウザ、コマンドの面には
   シェル(端末)が要る。**
   **画面を持たない製品でブラウザが動かないことは、この試験区分の不備ではない** —
   そこでブラウザを理由に red にすると、**要らない道具が無いというだけで出荷判定が止まる。**
   **報告では「実施した面」と「道具が無くて実施できなかった面」を分けて書く** —
   合わせて1つの red にすると、何が確かめられていないのかが読み取れない。
4. **表の網羅**(その run で1回。試験区分を1つだけ回した run でも見る): 表と表の突き合わせであり、
   テストは走らない。① 02 の要件カバレッジ表で**主担当**になっている条項が、すべて
   `03-impl/tests/` のどれかのテスト対応表に行を持つか。**行は条項ごとではなく
   「条項 × 必要と判断した観点」ごとである** ★ — 同じ条項 ID が複数行に並ぶのは正しい状態で、
   重複として潰さない(`03-impl.md`「tests/」)。**観点の行が足りているかどうかは、ここでは
   判定しない** — 何が必要かを決めたのは設計時の判断で、その理由は「テスト設計の判断」に在る。
   ここで見るのは**行が1つも無い条項**である。
   **02 の `充足` と、03 のテストの状態を並べて見る** ★(2026-09-15。inspection-28 A-2)—
   `完全` は**設計として割り当てた**という意味だけで、**テストが在るとも通ったとも言っていない。**
   **両方が揃っていない条項を報告に並べる**(「設計は `完全` だがテストは未実装: N 件」)。
   **それ自体を red にはしない** — 人が承認した未実装や、理由つきの対象外は正当である。
   **見えないまま出荷されることだけを止める。**
   **行が無い条項にも、行が在って「未実装」と書かれた条項と同じ説明を求める** ★
   (2026-09-15。inspection-28 A-21)— いまは、**未実装だと明記した要件のほうが厳しく
   扱われ、書き忘れた要件は何も問われない**という逆転が起きている。
   **行が1つも無い条項は、対応表に行を足させたうえで**(なぜ未実装か / 代替の確認 /
   解消の条件 / 人間の回答)、**足りるまでは事実の差異としてキューへ載せる。**
   **未実装そのものを出荷禁止にする話ではない** — 説明の無い穴をなくす話である。
   **`テスト対象外(…)` の行は、括弧の中が人間の回答の着地を名指しているかまで見る** ★ —
   「テストを書かない」は人間に問う判断であり(`delegation.md` の DS-01 の 対象外 の欄)、
   理由だけの行は**問うたのか問わずに決めたのかを区別できない**(`03-impl.md`「tests/」)。
   **名指していない行は red にせず、事実の差異としてキューへ載せる** — 過去に書かれた行を
   一斉に赤くするための検査ではない。② すべての `NFR-<cat>-nn` が
   **ちょうど1つ**の「NFR ⇄ テスト対応」の表に行を持つか(`03-impl.md`「tests/」)。
   **行が無いことは「未検証」ではない** — 空欄にも未検証の全件列挙にも出ないので、
   ここで見なければ誰も見ない。欠けている行は事実の差異としてキューへ載せる
   (F4 は SSOT を書かない)。
   **行が在ることと、今回それが走ったことは別である** ★(2026-09-15。inspection-28 A-4)—
   **数値の目標を持つ要件の試験は、出荷前に走る試験区分のどれかに割り当てられていること**、
   そして**この run で実際に走った試験区分に属するものは、実行結果と突き合わせて、
   その数値を満たしたことまで見る**。
   **今回走らせていない試験区分に属するものは、割り当てが在ることだけを見る** ★ —
   試験区分を名指して回す run は正当であり(§0)、**そこに無い実測を求めると、
   正しく分けた run が毎回未確認になる。**
   どの試験区分でも走らないなら、**それは「試験を用意した」であって「確かめた」ではない** —
   事実の差異としてキューへ載せる。
   **突き合わせるのは、測り方の4つの条件つきの値である**(負荷 / データ量 /
   集計の期間と母数 / 失敗した応答の扱い。`01-requirements.md`)— 条件の違う実測は
   別のことを言っているので、満たした証拠にならない。
   **専用の試験区分を新たに設けない** — 既にある区分のどれかへ割り当てる話である。
   ③ **コード側の印と対応表を突き合わせる** ★ — 同じ「どの条項をどのテストが確かめるか」を、
   対応表と、テストに付ける `@req:<ID>` の印の**2か所へ手で書かせている**。①②は表と表の
   突き合わせなので、**印だけが古いままでも通る。**
   **`02-design/environments.md` の「要件とテストの対応の一覧」の行のコマンドを逐語で**打つ
   (試験区分のテスト実行ゲートはこのレポートを作らない — `test-runner-usage` の
   `references/reports.md`。表に無ければコマンドを発明せず、§0 のとおり red にする)。
   **標準の実行基盤を通さない構成でも、この突き合わせを飛ばさない** ★
   (2026-09-15。inspection-28 A-12)— 印を集める仕組みが無いなら、
   **`@req:` をテストコードから直接拾って**(`grep -rn '@req:' <テストの置き場>` のように)
   対応表と比べる。**拾い方と、拾えなかった範囲を報告に書く**(言語や書き方によっては
   拾い切れない — **拾えなかったことを「印が無い」と読まない**)。
   **飛ばした run を、照合済みと取り違えさせない** — 飛ばすしかないなら、飛ばしたと書く。出力の
   印の無いテストの一覧(`--json` を付けたときの `untagged_tests`。文字だけの出力では
   「`@req:` が付いていないテスト N 件」と出る)と、印から作られた条項ごとの一覧を、
   `03-impl/tests/` の対応表と比べる。**印の付け漏れ**と、**対応表にあるのに印の無い条項**の両方を見る。
   食い違いは事実の差異としてキューへ載せる。
   **テスト基盤を入れていないプロジェクトでも、この③を飛ばさない** ★
   (2026-09-15 に改めた。inspection-28 A-12)— 印を集計する道具が無いなら、
   上のとおり `@req:` をテストコードから直接拾って比べる。
   **どうしても拾えない範囲が在るときだけ、その範囲を飛ばす** — そのときは
   §4 の報告に「何を拾い、何を拾えなかったか」を1行で書く(黙って飛ばすと、
   ③を見た run と見ていない run が report の上で区別できない)。

### 1.5 判断部分の独立レビュー

**明示選択したモードと、中央が codex で既定が o1 になったミッションでは、**
受け入れ条件との対応、失敗原因の分類、課題票への振り分け、
探索的QAの所見の扱いを独立レビューへ渡す。a1/o1 は反対側、a2/o2 は同一エンジンの別文脈。
**モード明示のない a1(人間の明示が無く、中央が claude だったもの)の F4 は、
現行の試験・デプロイゲートのままにする**(版上げだけで強化しない)。
既定の o1 を除外に読まない理由は `orchestration.md` §1.2.1 に在る —
そこには保たねばならない旧動作が無いからである。
対象集合は、今回の試験区分に対応する受け入れ条件・テスト戦略・テスト対応表と実行成果物。
その集合と基準コミットを確定し、自分の判断より前に /verify-docs §2 の起動・免除・書込み禁止・
critical 時の中断条件を適用する。中央への要求に主実行エンジンと実効モードも書く。
最初は仕様と判断項目だけを渡し、試験後に結果・QA の逐語所見を追加する。
主実行者の期待する分類や判定は渡さない。レビューが返ってから主実行者が §2 で裁定する。
所見の不一致は証拠で決め、高重大度・振る舞い・安全上重要な未解消が在れば green にしない。

試験コマンドは主実行者が1回だけ走らせる。レビュー側は再実行・操作・書込みをしない。
探索的QA も操作面ごとに1エンジン1回。安全上重要な変更などで人間が両方の操作を明示した
場合だけ、状態の初期化・許可された副作用・環境・費用を確認して2回目を別文脈へ配る。
自動試験の重要テスト区分や既存の失敗再現の規則は §1 のままである。

報告と鮮度スタンプの証跡へ実際の主実行/レビューエンジン、隔離手段、免除・縮退理由、
受け取った所見を保存する。記録の拡張引数は /verify-docs §2 のとおりで、
**作業指示が「モデル制限: あり」を伝えているなら `--model-limit あり` も添え、
軽い方のモデルだけで試験と判断を行ったことを報告にも書く**(`orchestration.md` §1.5)。
免除では review-engine=none と理由を記録し、両エンジンの実行とは名乗らない。

## 2. 失敗を振り分ける — 犯人の範囲を絞ったキュー

**このフローも止まる。** テストコードの自動修正と再実行のループは**最大2回**である
(`.claude/directions/core.md` §3・`principles.md` §12。F2・F3 と同じ上限)。2回目の後に残った失敗は
**振り分けるのであって、それ以上争わない** — `中`/`低` は `residual.md` の `残務` へ回り、
run は判定と鮮度スタンプで終わる。**ただし行き先を決めるのは種類が先で、重大度は後である**
(`issues-pendings.md` §1): 製品の不具合は重大度に関わらず下の表のとおり課題票になる。
**重大度は問題の深刻さであって、行き先ではない** ★(2026-09-15。inspection-28 D-17。どれから手を付けるかの順番の話でもない)。行き先はまず**問題の種類**で決まる。`残務` へ回るのは、**製品の不具合でない** `中`/`低` の残りである。

**`残務` に満杯は無い。いつでも書ける** ★ — 書き終わったら
`python3 .claude/scripts/doc-health.py --rotate` を打つ。50行以上なら
`docs/residual.md` が `docs/residual-NNN.md` へ押し出され、同じ名前の新しいファイルが作られる
(**ローテーション**。`glossary.md`)
(**1行も落ちない。権限の制限も無い**)。50 未満なら何もしない(`issues-pendings.md` §2.1)。

すべての失敗を裁定し(製品の不具合 / テストの欠陥 / 環境の不備 / 仕様の問い)、
チャネルを通して出す(`flows.md` §5):

| 失敗の種類 | 行き先 |
|---|---|
| 製品の不具合・仕様に対する誤動作 | `docs/issues/` に1件(`closes_when:` 必須、`origin_layer:` は直す起点)。**最終 green 鮮度スタンプ以降の構築記録に紐付ける** — 本文に `関連する構築記録: docs/build-records/<slug>.md` を書く(範囲限定が構築記録の存在理由の1つ)。重大度 高 は `pattern:`+`pattern_survey:` まで(`issues-pendings.md` §3.1) |
| テスト自体の欠陥(壊れたフィクスチャ・陳腐化した期待値) | 修正はテストコードに限り自動修正してよい(`auto-fix:` コミット)。**期待値・アサーションの変更は自動ではしない** — 合否を決める部分の変更は仕様の判断なのでキューへ(`delegation.md` §2.2)。**「製品の不具合か、テストのほうが悪いか」を判断する材料は `/test-design` が持つ** ★ — 期待値とアサーションの設計、観点の選び方、モックの境界、保存済みの期待値の扱いはあちらが正である(このフローは書かないが、読んで判断する) |
| 環境の不備 | 課題票(`origin_layer: 02` — environments.md が正されるべき起点) |
| 仕様の解釈が割れる失敗 | 質問シートへ(`docs/sheets/questions-<YYYY-MM-DD>.md`。新規作成時は `created:` frontmatter — `/verify-docs` §3 と同じ書式) |

**起票したら索引を再生成する** — `python3 .claude/scripts/build-index.py`(手書き禁止。
`issues-pendings.md` §6)。これは `docs/issues/index.md` を動かすので **F2 の依存が動く**
(`stamps.py deps`)。「F4 は誰も失効させない」は誤りである(`flows.md` §2)。

**試験成果物は `code_roots` の外か `.gitignore` の中に置く。** 失効判定は未追跡ファイルも見るので
(`flows.md` §2)、コードの置き場の下に落ちた成果物は **F3 と F4 全試験区分を自分で失効させる**。

真実を述べなくなった `03-impl/tests/` の状態の列は、**編集するのではなくキューへ載せる**
(F4 は SSOT を書かない — `/verify-impl` が事実の差異として決着させる)。
残っている「未検証(テスト未実装)」は**件数と参照先のパスの1行**で報告する —
「未検証(テスト未実装): N 件(全件は `03-impl/tests/` の各ファイルの
「未検証(テスト未実装)の全件」節)」。**全件をここへ書き写さない**: 理由と解消の条件は
その節が所有しており(`03-impl.md`「tests/」)、40行の報告を再掲で埋めない。
**それらは重大度 高 だが、鮮度スタンプの記録を止めることは決してない**
(完了定義の項目がそれに乗っているときだけ *green* を止める)。
**ただし、記録そのものが空の行は *green* を止める** ★ — その試験区分が読む
「未検証(テスト未実装)の全件」節の各行が、**なぜ未実装か / 代替の確認 / 解消の条件 /
人間の回答(記録)**の4つを空けずに持っていること(`03-impl.md`「tests/」)。
**4つ目は実在するパスを指していること** — 「後で聞く」「未」のような文字列は空と同じに扱う。
**指した先を開いて、その回答がこの穴を受容しているかまで見る** ★
(2026-09-15。inspection-28 A-11)— パスが実在することは、**そこに何が書いてあるかを
1文字も保証しない。** 別の件についての回答や、条件つきの承認(「この範囲なら」)を
そのまま流用した行が在りうる。**受容していると読めないなら所見である**
(その場で red にはしない — 事実の差異としてキューへ載せる。F4 は SSOT を書かない)。
**数えるのは行の中身だけで、
未実装そのものの件数では止めない** — 止めるのは「必要だと判断したのに、なぜ残すのかを
誰も書いていない」状態である。**報告には、埋まっていない行を `file:line` で全件出す**
(件数だけの1行にしない — ここは直せる場所が特定できる所見である)。
**この4つがそろっても *green* にならない行が2種類ある**: 完了定義の項目が乗っている行
(従来どおり)と、**`baseline.md` が受け入れ基準として自動テストを求めた行**である。
後者を保留の外に置くのは意図である — あれは「上流が黙っていても備えていなければならない」
性質であり、**受容してよいかどうかを、その場のタスクが決められる種類のものではない。**

## 3. 鮮度スタンプ

実行した試験区分ごとに。**先にコミットする** — 自動修正したテストコードと再生成した課題票の索引は
このフロー(および F3)の依存なので、未コミットのあいだ `record` は green を拒む
(`flows.md` §2)。**手前で `git status` を目で見て確かめない** — 裸の出力は依存の外の汚れも
並べるので、依存の中の汚れだけを問う問いには答えられない。**拒まれたら、`record` が印字した
パスをコミットして打ち直す**(依存の外の汚れは record を止めない):

```bash
python3 .claude/scripts/stamps.py record verify-tests <green|red> --scope <s> [...] \
  --evidence artifacts/verify-tests-<試験区分>.log   # green には必須(A-7)
```
**`green` には `--evidence <path>` が要る** ★(2026-09-15。inspection-28 A-7)— 走らせた
結果を `artifacts/` の下へ書き出し、そのパスを渡す(複数可)。**実在して中身が在る
ことだけを機械が見る** — 中身が本物かどうかは見ない。それでも、後から人間や別の
エージェントが**現物を開いて確かめられる**ようになる。`red` には要らない。

**引数なしで回した run は全試験区分を1回で記録する**(F4 に全数の印 `--full` は無い ★ —
**「全数」は文書・実装の全体確認だけを指す語である**。2026-09-15。F4 は毎回が
**スイート全体**であり、スイート全体でしか回らない検査も無い。`flows.md` §2.1)。**試験区分を名指して回した run は、名指した分だけを記録する**(1つでも複数でも同じ)
— デプロイゲートは `f4_scopes` の全試験区分の green を要求するので、**1周とは `stamps.py check` が green で
ないと言った試験区分を1本にまとめて回すことである**(コード変更の直後は全試験区分に一致する。green の試験区分は
回し直さない — `flows.md` §2.1。スケジューラ側の形は `orchestration.md` §3.0 の4)。
**red の試験区分は、分けずに1本の run にまとめるのが既定である** — 全試験区分が red なら引数なし、
**一部だけが red ならその red の試験区分を並べて渡す**(inspection-23 B-6)。後の試験区分の
自動修正のコミットが先の試験区分の打ちたての green を失効させる増幅が、どちらでも消える(inspection-20 V-3)。
**green の試験区分は並べない** — 走らせ直さないことがこの形の目的である。
**収まらないときは、詳細をファイルに書いてパスで示す。これは失敗したときだけの話ではない** ★ —
全部通った run でも、逐語で引くコマンドと最終行が多ければ超える(重要テストと突き合わせの行を
足したぶん、1回あたり最大4行増えている)。**行を削って辻褄を合わせない** — 逐語の引用と実行件数は
この報告の要である。**超えたら、実行の表を丸ごとファイルへ出してパスを示し、本文には試験区分ごとの
結果の1行だけを残す。**
収まらないときは、詳細をファイルに書いてパスで示し、
本文は要約に落とす。

**試験区分の一部だけを走らせたとき**(デプロイゲートが最小の範囲を名指した、または引数が
狭めた)は、実際に動かした範囲ごとに `--covers <path>` を1つずつ添える。
裸の `--scope` は、その試験区分の依存集合まるごとを主張する(`stamps.py deps verify-tests:unit`)。
**「そのパスを覆った」と言えるのは、そのパスに掛かる試験を実際に走らせた run だけ**である —
どの試験がどのパスを覆うかを機械で言えない間は、**スイートを丸ごと走らせて試験区分単位で記録するのが
既定**であり、`--covers` は走らせた範囲を狭く申告する形に限る(広く申告する形ではない)。

**試験区分ごとのコードの置き場は `scope_roots` に宣言できる**(`flow-config(.local).json`。
未宣言の試験区分は広いほうへ倒す — qa は `ui_roots`、それ以外は `code_roots` 全体)。宣言すると、
その試験区分の置き場に掛からない変更ではその試験区分が失効しなくなる。**減るのは「無関係な試験区分まで
一律に失効する」ぶんであって、試験区分の中は当面スイート丸ごとのままである**(inspection-21 V-9)。

試験区分ごとの green = スイートが完走し(**実行 0件、説明の付かない skip、2回を超える再実行で
通した合格は、完走ではない** — §1)、**未起票の重大度 高 の製品の不具合の所見がゼロ**であること。
**版の固定を宣言したプロジェクトでは、`unit` / `integration` / `e2e` に、版がビルドと一致した環境で
走ったことも要る**(§1。`delegation.md` §2.4。不一致も未確認も green にしない。未宣言のプロジェクトでは
報告するだけで、この条件は掛からない)。
**`unit` にはもう1つ条件が付く — 資格情報の混入検査が、この run の中で1回走って通ること** ★。
テスト基盤を使うプロジェクトでは `f4-unit` の `secret_scan` ステップがそれである
(`strict` の下なので、コマンドが未設定なら skipped ではなく failed になる)。
**テスト基盤を使わず、言語のテスト命令を直に走らせる構成でも同じだけ要る** —
`02-design/environments.md` の「資格情報の混入検査」のコマンドを1回走らせ、
**最終出力行を報告に逐語で引く。** **未設定・未実行・失敗のどれでも `unit` を green にしない** —
出荷を止めるのはここだけだからである(`principles.md` §12 の完了定義の1項目目)。
**二度走らせない** — 基盤を使う構成では `f4-unit` の1回がこの条件を満たす。
**これに加えて、その試験区分に当たる `f4-critical` のステップが通っていること** ★
(**テスト基盤を使っていないプロジェクトと `qa` には掛からない** — §1)—
`f4-*` の各スイートは `@flaky` と一時除外を除外するので、**これを見ないと「重要テストを一時除外に
入れたまま緑」を止められない**(§1)。**見るのはその試験区分のステップだけである** —
`unit` の green に `f4-critical` の `e2e` ステップは掛からない(§1 の `--only`)。
`@critical` が0件でそのステップが skipped になった run は通ったものとして扱う —
**0件は「重要テストをまだ書いていない」という事実であって、除外ではない。**
**`e2e` はこれに加えて、未判定条項が0件であること** ★ — 完了定義の2項目目(`AC-nn` が全件、
実システムに対して通る。`.claude/directions/core.md` §3)を、確かめていないものを合格側に倒さない形で閉じる。
`適用外(P-nnn)` と書かれた行は、この0件に数えない。
起票済みの課題票は、それが `AC-nn` を阻害しない*限り*、鮮度スタンプを red に止めない
(完了定義自身の行 — `.claude/directions/core.md` §3。複合のデプロイゲートは、修繕されるまで **`type: bug` かつ
`severity: 高`** の課題票が1件でも在れば依然として red になる — **かつ**である。
`severity: 中` の bug も、bug でない `severity: 高` も、デプロイゲートを止めない —
`flows.md` §2)。

**`qa` 試験区分は、起票の有無について条件が違う** ★ — 起票したかどうかによらず重大度「高」がゼロでなければ
green にならない(完了定義の**探索的ブラウザQAの項**が「高 が0件」とだけ定める — `.claude/directions/core.md` §3)。
**その条件の正は `.claude/skills/browser-qa/SKILL.md` §4 であり、ここには写さない**(原則10)。

記録した後、昇格の周を回す:
`python3 .claude/scripts/stamps.py promote` — そして 遷移 が報告されたら、書き換わった記録を
コミットする(`git add docs/build-records && git commit -m "promote: awaiting-verify → verified" -- docs/build-records`):
**作業ツリーにしか居ない `verified` は、HEAD にも CI にも他のどのチェックアウトにも見えない**
(`flows.md` §2)。**鮮度スタンプ自身のコミットはここでは打たない** — あれは git で共有するが、
コミットするのは**1周の終わりに1回だけ**である(同 §2)。

## 4. 報告(日本語。無人の run は 40行 / 2,000バイト以内)

```
## 試験(F4): <試験区分一覧>
鮮度スタンプ: <試験区分: green/red @ sha>...
最弱点(所見ゼロでも1行): <>
### 実行
| 試験区分 | コマンド | 最終行(逐語) | 実行件数 / skip | 結果 |
| 重要テスト(<その試験区分>) | <f4-critical --only … の逐語> | <最終行> | <件数 / skip> | <結果> |
  ↑ **回した試験区分ごとに1行**(§1)。**この行のぶん、報告は最大4行増える** — 40行に収まらなく
    なったら §3 の逃げ道(詳細をファイルに書いてパスで示す)を使う。**行を削って辻褄を合わせない。**
    `@critical` が0件なら 実行件数 0 / 結果 skipped と書く
    — それが正常な状態である。**行を落とさない**: green の条件に入っているので、根拠が要る。
    **`qa` の run と、テスト基盤を使っていないプロジェクトでは、この行を書かない**
    (掛からない — §1)。代わりに「重要テスト: 適用外(理由)」と1行だけ書く
版の一致(§1): <一致(<固定の場所>)/ 不一致(<何が何と違うか>)/ 未確認(<理由>)/ 未宣言(移行前。不一致: <…> / 未確認: <…>)/ 適用外(qa だけの run)>
不安定テスト: <N 件(うち再実行の上限到達 M 件 — 課題票を参照)| 0 件>
要件とテストの対応の突き合わせ(§1 の「表の網羅」③): <実施 — 印の欠落 N 件 / 飛ばした(テスト基盤なし)>
### AC 照合(e2e 実行時)
| AC | 判定 | 根拠 |
  ↑ 判定は `合格` / `不合格` / `未判定条項` / `適用外(P-nnn)`。**未判定条項 は丸括弧で開く**
    (「未判定条項(実システムに対して合格とも不合格とも判定できなかったもの)」— `glossary.md` §0)
### ブラウザQA(qa 実行時)
実行形態: @qa(codex) / @qa(claude) / codex+chrome-devtools / claude+claude-in-chrome
  ↑ **どの口で走ったかを必ず名乗る**(`orchestration.md` §1.4)/ 所見: 高 N・中 N(高の裁定は個別に列挙)
### 起票(構築記録に紐付け)
| 課題票 | severity | 関連する構築記録 |
### 質問シートへ(0件が既定)
### 次にあなたがすること
<red の試験区分の復旧手順 / /build --repair の対象 / 「無し」>
```
