# 受け入れ基準

## AC-01 プロジェクトを隔離コンテナで開発開始

- 対応要求: RQ-env-01 / RQ-env-02 / RQ-env-03
- 前提: 初回セットアップと Claude のログインが済んでいる。あるリポジトリで開発したい。
- 操作:
  1. プロジェクトディレクトリで `claude-dev start` を実行する。
  2. 立ち上がった端末の中で `claude` を実行する。
- 期待される結果: そのプロジェクト専用のコンテナが起動し、カレントディレクトリの中身が見える状態で
  Claude Code が動く。ホストの秘密鍵ファイルや Docker 生ソケットはコンテナに渡っていない。
  ブラウザ確認ありの構成なら、起動時に noVNC の URL が表示される。
- こうなったら不合格: 別プロジェクトの SSH 鍵がコンテナから見える / ホストの Docker を無制限に操作できる。

## AC-02 Web アプリをクライアントのブラウザで確認

- 対応要求: RQ-env-01 / RQ-env-02
- 前提: コンテナ内で Web アプリが起動し、**コンテナの外から接続を受け付ける形**で待ち受けている。
- 操作:
  1. サーバ上で `claude-dev forward 5173` を実行する。
  2. 表示された SSH トンネルのコマンドをクライアント PC で実行し、案内された URL を開く。
- 期待される結果: クライアントのブラウザにコンテナ内 Web アプリが表示される。`claude-dev ports` で
  今開いているフォワードを確認できる。**`claude-dev start` しただけの時点では、利用者の
  Web アプリ用のポートは1つも公開ポートになっていない**(用語集「公開ポート」)。
  **ブラウザ確認ありの構成が開く noVNC の 6080 番台は、この基準の対象外である**
  (`D0-env-01` で動的に割り当てると決めた補助 UI のポートであり、`D0-env-02` が
  「`start` の時点では Web アプリ用のポートマッピングを行わない(**ブラウザ確認ありの
  noVNC ポートを除く**)」と例外を明記している)。
- こうなったら不合格: `start` しただけで、利用者の Web アプリ用のポートが意図せず公開ポートになる。
  noVNC 以外のポートが `start` の時点でホストへ公開される。

## AC-03 危険な Docker 操作が拒否される

- 対応要求: RQ-env-04
- 前提: コンテナ内から Docker を使う既定の構成で起動している。
- 操作: コンテナ内で、ホストのルートディレクトリを丸ごと持ち込むような `docker run` を試みる。
- 期待される結果: プロジェクト作業領域の外をホストから持ち込む操作・特権コンテナ・ホストの
  ネットワークやプロセス空間の共有は**拒否**される。作業領域配下の持ち込みと、
  持ち込みを含まない `docker run` は許可される。
- **この保証の限定**: 拒否できるのは、要求の中身を検査できた場合に限る。**検査できなかった要求は
  止められず、その要求が通るか止まるかは実行してみるまで分からない**(独自解釈で正常な操作を
  誤って止めないための割り切り)。**この割り切りは `D0-sec-05`(Docker API 検査の厳密さ)の
  委任範囲——「解釈できない入力を通すか止めるか」——の中で下した判断であり、独立した決定事項では
  ない。** 残存リスクは `docs/issues/005` が追跡する。
- こうなったら不合格: ルートディレクトリの持ち込みや特権コンテナが**検査できる形で**通ってしまう。

## AC-04 オーケストレーターで並列実装し、要判断だけ対応する

- 対応要求: RQ-orch-01
- 前提: コンテナが起動している。実装したい案件がある。
- 操作:
  1. `claude-dev orchestrate` を実行する。
  2. 対話でゴールと作業計画を固め、確定して対話を終える。
  3. 複数の作業者が並行して実装している間、離席する。
  4. 「要判断 N 件」の通知が来たら戻り、待機している作業だけを選んで回答する。
- 期待される結果: 要判断になった作業だけが待機し、他の作業は止まらず走り続ける。回答するとその作業が
  再開する。すべて終わると成果が統合され、完了の通知が届く。
- こうなったら不合格: 1件の要判断で全部が停止する / 再開時に完了済みの作業をやり直す。

## AC-05 端末が壊れても実行を失わず復旧する

- 対応要求: RQ-orch-01
- 前提: オーケストレーターで実行中。表示崩れ等でクライアント端末を全部閉じるしかなくなった。
- 操作:
  1. 端末をすべて閉じる。
  2. 改めて接続し直し、`claude-dev orchestrate` を再実行する。
- 期待される結果: 同じ状態に戻る。実行の中身が生きていればそのまま合流し、死んでいても保存された
  状態から続きが始まる。完了済みの作業はやり直さず、計画や履歴が勝手に消えることもない。
- こうなったら不合格: 端末を閉じた時点で実行が失われる / 再開で最初からやり直しになる。

## AC-06 Codex CLI をコンテナで使い、認証をホストと共有する

- 対応要求: RQ-env-03
- 前提: 初回セットアップが済んでいる。OpenAI 側のアカウントを持っている。サーバは SSH 越しで、
  ブラウザはクライアント PC 側にしかない。
- 操作:
  1. ホストで `claude-dev login-codex` を実行し、表示された URL とコードをクライアント PC の
     ブラウザで開いて認証を済ませる。
  2. 別のプロジェクトディレクトリで `claude-dev start` を実行する。
  3. コンテナ内で `codex` を実行し、ファイルの読み書きとコマンド実行を伴う作業を依頼する。
  4. 別の使い方として、書き換えを禁じた読み取り専用の状態で調査だけを依頼する。
- 期待される結果: 2 回目以降・別プロジェクトのコンテナでもログインし直さずに `codex` が使える。
  依頼した作業で `codex` が実行するコマンドが実際に成功し、作業領域のファイルを読み書きできる。
  読み取り専用を指定した場合も、読むことはできて調査が完了し、書き込みは拒否される。
  認証の更新は次に起動するコンテナへ引き継がれる。設定と履歴はプロジェクトごとに独立している。
- こうなったら不合格: プロジェクトごとにログインを求められる / 認証の更新が他のコンテナへ伝わらない /
  トークンがイメージに焼き込まれている / `codex` が起こすコマンドが毎回失敗する / コマンドが失敗した
  のに成功したかのような応答が返る / 読み取り専用にすると読むことまで失敗して調査が成立しない。

## 対象外とするシナリオ

| シナリオ | 対象外とする理由 |
|---|---|
| 作業者ごとに隔離された環境で並列実装する | 「やらないこと」1(個別隔離)に該当する |
| 信頼できない第三者のコードを持ち込んで実行する | 「やらないこと」2 に該当する |
| ブレインストーミングを人間抜きで自動的に完了させる | 「やらないこと」4 に該当する |
| 完了基準を満たしていない箇所を自動でタスク化して埋める | 「やらないこと」5 に該当する(v1 では助言に留める) |
