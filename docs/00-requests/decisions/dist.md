## D0-dist-01 イメージの取得・更新経路の使い分け

- 区分: 委任
- 決めた日: 2026-07-30
- 委任範囲: 配布イメージを取得する経路(レジストリからの取得 / ローカル再ビルド)をどのコマンドに
  割り当てるか、取得後にどう名前を付け替えて以降の存在判定を単純にするか。
- 制約(ガードレール): 利用者から見て「セットアップ済みかどうか」の判定規則を増やさないこと
  (既存の判定を1本の名前に集約する)。取得元を勝手に切り替えないこと。

- 関連: RQ-dist-01 / FR-env-09

## D0-dist-02 イメージは GHCR へマルチアーキで日次配布する

- 区分: 決定
- 決めた日: 2026-07-30
- 内容: GitHub Actions で GHCR へ amd64/arm64 のマルチアーキイメージを日次(03:30 JST)で push する。
  `YYYYMMDDHHmm`(JST)のタイムスタンプタグと `latest` タグを付ける。
- 理由: チーム全員がビルドせずに pull で同一構成を得られるようにする。Apple Silicon でネイティブに
  動かすため arm64 も要る。
- 却下した案: 各自ローカルビルド — 構成が揃わずビルド時間もかかる。単一アーキ配布 —
  Apple Silicon でエミュレーションになり実用にならない。
- 関連: RQ-dist-01 / FR-env-09 / FR-env-10

## D0-dist-03 同梱する Claude Code は latest を CI で解決してピン留めする

- 区分: 決定
- 決めた日: 2026-07-31
- 内容:
  1. **チャネル**: 配布イメージに焼く Claude Code は、**ビルド時点の `latest` チャネルの公開バージョン
     そのもの**に固定する(**解決とピン留めの手段は 02/03 が定める**)。インストーラの引数なし既定
     (`stable` チャネル)は使わない。
  2. **逃げ道**: 不良版を引いた場合は手動実行の入力で特定バージョンを指定して焼き直せるようにする。
  3. **再取得の範囲**: **同梱バージョンが変わらない日は、利用者の取得が増分に留まること**を条件とする
     (新版が出た日だけ当該レイヤーが失効する)。**そのためのレイヤー構成とキャッシュの作り方は
     02 の設計判断が定める。**
  4. **日次更新の意味**: 「日次で更新」の保証はタグが変わることではなく、**同梱 Claude Code が
     `latest` に追随すること**を含む。
- 理由: バージョンをレイヤーチェーンから外した結果、ラベルだけが日次更新され**同梱版が凍結する**
  事故が実際に起きた(2026-07-19 の 2.1.214 で停止)。`stable` は段階公開のため現行 `latest` より
  古い版を指すことがあり(2026-07-29 観測: stable=2.1.212 / latest=2.1.220)、`stable` 追随では
  むしろ現状より古い版を焼くことになる。`latest` ピン留めならホスト側 claude と版が揃い、
  認証共有時のバージョン差が問題になりにくい。
- 却下した案: `stable` チャネル追随 — 現行より古い版を焼きうる。時刻由来の cache-bust —
  新版が無い日も毎日レイヤーが失効し pull が増分にならない。実行時の自動更新 —
  ファイアウォール下・オフライン起動で不確定になり「同一構成の保証」を失う。
- 関連: RQ-dist-01 / FR-env-09 / FR-env-12 / NFR-perf-01

## D0-dist-04 Codex CLI の同梱・バージョン・認証共有・サンドボックス方針

- 区分: 決定
- 決めた日: 2026-07-31
- 内容:
  1. **同梱**: 配布 2 イメージ(ブラウザ確認あり/なし)に OpenAI Codex CLI(npm パッケージ
     `@openai/codex`)を導入する。**イメージのどの位置に導入するかは Claude Code と同じ扱いとし、
     位置そのものは 02 の設計判断が定める。**
  2. **バージョン**: **ビルド時点の最新公開バージョンそのもの**に固定する(`@latest` の直書きは
     しない)。手動実行の入力で特定バージョンを指定して焼き直せるようにする。**解決とピン留めの
     手段は `D0-dist-03` 項1 と同じで、02/03 が定める。**
  3. **認証**: `codex login --device-auth`(ヘッドレス前提のデバイス認証)を採り、
     `$CODEX_HOME/auth.json` **のみ**を既存の認証共有ボリュームの `codex/` サブディレクトリ経由で
     共有する。方式は `D0-auth-03` と同じ。`config.toml`・セッション履歴はコンテナ固有に保つ。
  4. **ログイン導線**: ホスト CLI に独立サブコマンド `claude-dev login-codex` を追加する
     (既存 `login` は Claude 専用のまま。`logout` は共有ボリュームを空にする挙動を維持する)。
  5. **スコープ**: 本決定は「開発者がコンテナ内で codex を使える状態」までである。
  6. **サンドボックス方針**: コンテナ内の codex は**既定では自前のサンドボックスを使わず**、
     **読み取り専用を明示要求された場合に備えて landlock バックエンドを有効化しておく**。
     既定として `sandbox_mode = "danger-full-access"` / `approval_policy = "never"` /
     `[features] use_legacy_landlock = true` の 3 鍵を置く。`config.toml` が無ければ 3 鍵を生成し、
     既にある場合は**利用者が書いた鍵と値を一切書き換えず、書かれていない鍵だけを追記**する。
     コンテナ側の seccomp/AppArmor を緩める案は採らない。landlock でも動かない `workspace-write`
     (書き込みを伴う自動化・QA)は `danger-full-access` で走らせる。
- 理由: codex も更新が速く、`@latest` を直書きすると文字列が変化せずレイヤーキャッシュが永久ヒット
  して**中身だけ凍結**する(`D0-dist-03` で実際に起きた事象)。`auth.json` はファイル保存・0600・
  その場書き換えで、トークンリフレッシュにより内容が変わるため書き戻し同期が必要。認証の器を既存
  ボリュームへ相乗りさせるのは、インフラ作成・`logout`・`reset` の分岐を増やさないため。
  ⑥については、codex 0.146.0 の Linux サンドボックスが bubblewrap 実装であり、
  (a) Docker 既定 seccomp が `CLONE_NEWUSER` を拒否し、(b) それを外しても `docker-default`
  AppArmor が `mount --make-rslave /` を拒否する——の2段で起動できないことを 2026-07-31 に配布
  イメージで実測した。既定のままでは codex が起こすシェルコマンドが例外なく失敗し、しかも**モデルが
  失敗を認識せず出力を捏造する**(`codex doctor` も検知しない)。隔離境界はコンテナ/ホスト間のみと
  決めており(`D0-sec-06`)、コンテナ内の二重サンドボックスは元から前提にしていない。一方
  `--sandbox read-only` のようにサンドボックスを明示要求する呼び出しは config の既定を上書きして
  bubblewrap 経路に戻るため、ユーザー名前空間を必要としない landlock を有効化しておく
  (実測で「読み取り成功 / 書き込み拒否 / 名前解決不可」を確認済み)。
- 却下した案: `--security-opt` で seccomp と AppArmor を外す — 隔離境界そのものを弱める。
  `workspace-write` のまま運用する — シェルコマンドが例外なく失敗する。`config.toml` をイメージへ
  焼き込む — プロジェクトごとに設定を変える余地を失う。landlock を使わず読み取り専用の依頼は常に
  「対象ファイルをプロンプトへ添付する方式」で回避する — 退避手段としては有効だが、恒久策にすると
  codex にファイルを読ませる経路が使えないままになる(`use_legacy_landlock` が将来撤去された場合の
  退避先としては残す)。起動時に疎通確認を走らせて警告する — codex を使わない利用者にも毎起動の
  コストがかかるため採らず、確認は E2E-06 に持たせる。
- 関連: RQ-env-03 / FR-env-03 / FR-env-09 / FR-env-12 / AC-06

## D0-dist-05 外部実行ファイルは保守者が externals/ へ手で置き、公開イメージへ同梱する

- 区分: 決定
- 決めた日: 2026-08-18
- 内容:
  1. **置き場と主体**: 配布イメージへ同梱する外部実行ファイルは、**保守者がリポジトリ直下の
     `externals/` へ手でコピーする**。イメージのビルドはそこに在るものを設置するだけで、
     ビルド時に外部から取得しない(`request.md`「やらないこと」6)。
     **`externals/` の中の規約(アーキテクチャ別の置き分け、同梱しないファイル)と、
     イメージ内の設置先は 02/03 が定める。**
  2. **公開範囲**: **CI が公開する GHCR イメージにも同梱する。** その帰結として、
     `externals/` に置いたものは (a) 公開リポジトリにコミットされ、(b) 公開イメージを
     `docker pull` した誰もが取り出せる。**この2点を承知のうえで採る。**
  3. **ガードレール**(置く側が守る。置いてよいものの条件):
     - **認証情報・秘密鍵・API キーを置かない。** `SR-03` と `NFR-sec-01` が既に禁じている
       ことを、この新しい経路について名指しで再掲する。
     - **公開配布してよいものに限る。** 再配布が許されているかどうかを、置く前に置く側が確認する。
  4. **スコープ**: 本決定は「保守者が置いた実行ファイルが、開発者のコンテナ内でコマンド名だけで
     起動できる状態」までである。版の記録・署名・チェックサムの検証は含まない。
- 理由: 同梱したい社内ツールは別リポジトリで作られており、その多くは非公開である。
  ビルド時の自動取得(配布サイトやリリース資産からの取得、ソースリポジトリを取得してのビルド)は、
  **取得元の資格情報をビルドへ持ち込む経路を作る**うえ、取得元の可用性にビルドの成否が依存する。
  手で置く形にすると、同梱物の出所と版を決めるのは常に人間になり、ビルドは
  「在るものを設置するだけ」の決定論的な処理に留まる。
  公開イメージへも焼くのは、**チーム全員が pull だけで同一構成を得る**という `RQ-dist-01` の
  約束を、同梱物についても崩さないためである。ローカルビルド限定にすると、
  `claude-dev pull` で入れた人と `make build` した人で中身が違うイメージができる。
  ガードレールを置くのは、**公開イメージへ焼いたものは回収できない**からである。
- 却下した案:
  - **配布サイトやリリース資産から取得する**(2026-08-18 に人間が採らなかった) —
    非公開の取得元では資格情報をビルドへ渡すことになる。取得元にリリースを作る運用を
    先に整える必要もある。
  - **ソースリポジトリを取得してビルドする**(同日) — 同じく資格情報が要り、
    「バイナリだけを同梱する」という要求とも合わない。同梱物のビルド環境を
    このリポジトリが抱えることにもなる。
  - **ローカルビルドにだけ同梱し、公開イメージには入れない**(同日) — pull した人と
    ビルドした人で中身が違うイメージができ、`RQ-dist-01` の「同一構成」が崩れる。
  - **アーキテクチャを区別せず1つの置き場に平らに置く**(同日) — 配布イメージは
    amd64 と arm64 の2つあり、片方のアーキ向けの実行ファイルがもう片方のイメージにも入って
    実行できない状態になる。
- 見直す条件: (a) 配布先が公開 GHCR でなくなったとき(項2 の帰結と項3 の2条目の前提が消える)/
  (b) 同梱物が増えて手で置く運用が回らなくなったとき(そのときは自動取得の是非を
  `request.md`「やらないこと」6 から見直す)/ (c) 同梱物の版を利用者が知る必要が生じたとき
  (項4 のスコープ外を範囲へ入れる)。
- 関連: RQ-dist-02 / FR-env-13 / SR-03 / SR-24 / NFR-sec-01 / NFR-perf-01 / NFR-perf-02 /
  `D0-dist-02`(公開先が GHCR であること)/ `D0-dist-03`・`D0-dist-04`(同梱物の位置を 02/03 へ
  委ねる書き方の先例)/ `request.md`「やらないこと」6

## D0-dist-06 ブラウザ操作用の MCP サーバーも配布イメージへ同梱し、版を固定する

- 区分: 決定
- 決めた日: 2026-08-22(**同日、項4 に構成の条件を人間の回答で足した**)
- 内容:
  1. **同梱**: ブラウザ確認のためにエージェントが使う MCP サーバー(chrome-devtools MCP)を、
     配布 2 イメージ(ブラウザ確認あり/なし)へ導入する。**イメージのどの位置に導入するかは
     エージェント CLI と同じ扱いとし、位置そのものは 02 の設計判断が定める。**
  2. **バージョン**: **ビルド時点の最新公開バージョンそのもの**に固定する(`@latest` の直書きは
     しない)。手動実行の入力で特定バージョンを指定して焼き直せるようにする。**解決とピン留めの
     手段は `D0-dist-03` 項1 と同じで、02/03 が定める。**
  3. **実行時の取得に依存しない**: コンテナ起動時にも実行時にも、この MCP サーバーを
     ネットワークから取得してはならない。
  4. **登録先**: 起動時に **Claude Code と Codex CLI の双方**の設定へ、この MCP サーバーを
     登録する。**利用者が既に書いている値は変えない**(書式・登録の手段・置き換えてよい条件は
     01 の受け入れ基準と 02/03 が定める)。
     **登録するのはブラウザ確認ありの構成のときだけである**(2026-08-22 に人間の回答で足した。
     回答の逐語: 「1.A」= 「ブラウザ画面を持たない構成では書かない」)。**ブラウザ確認なしの
     構成には接続先のブラウザが無く、登録しても使えないまま失敗の原因が分かりにくくなる。**
     この条件を外す契機は、ブラウザ確認なしの構成からコンテナの外のブラウザへ繋ぐ使い方を
     認めたときである。
  5. **スコープ**: 本決定はブラウザ操作用の MCP サーバー1件についてである。**他の MCP ツールを
     増やすかどうかは `D0-env-07`(要確認)のままで、本決定はそれを動かさない。**
- 理由: この MCP サーバーだけが、コンテナが起動するたびにネットワークから取得される形で残って
  いた。**同梱物の可用性がネットワークと取得先に依存する**ため、ファイアウォールの下や取得先の
  障害時にブラウザ確認が成立しない。`D0-dist-03`・`D0-dist-04` は同じ理由で Claude Code と
  Codex CLI について「実行時のダウンロードに依存しない」と決めており、この1件だけが例外に
  なっていた。**エージェントが使う道具は、エージェント CLI 自身と同じ扱いにする。**
  双方の設定へ登録するのは、`RQ-env-03` が同梱するエージェント CLI を2つとしており、
  **どちらで作業するかによってブラウザ確認の可否が変わるのは、利用者から見て説明できない**ためである。
- 却下した案:
  - **実行時取得のまま据え置く**(2026-08-22) — 取得先の可用性とファイアウォールに
    ブラウザ確認の成否が依存し続ける。`D0-dist-03` が同じ事象を理由に退けた形である。
  - **ブラウザ確認ありのイメージにだけ同梱する**(同日) — 配布物ごとに中身の規則が変わり、
    「同梱物は両方の配布イメージに入る」(`FR-env-12-1` / `FR-env-13-1`)という既に在る
    一貫した扱いから外れる。ブラウザ確認なしの構成でも、利用者が自分で登録して使う余地が消える。
  - **Claude Code 側にだけ登録する**(同日) — codex で作業している利用者だけブラウザ確認が
    できず、`RQ-env-03` が2つの CLI を等しく同梱している意味が失われる。
  - **`externals/` の仕組みで同梱する**(同日) — あれは保守者が手で置く社内バイナリのための
    経路であり(`D0-dist-05`)、公開パッケージの版を CI が解決してピン留めする本件とは
    出所も更新のされ方も違う。2つの経路を混ぜると、どちらの規約に従うのかが決まらない。
- 見直す条件: (a) この MCP サーバーがブラウザ確認以外の用途にも使われ始め、「ブラウザ確認のための
  同梱物」という位置づけが実態と合わなくなったとき / (b) 同梱する MCP サーバーが 2 件以上に
  なったとき(そのときは `D0-env-07` の要確認を先に決着させる) / (c) この MCP サーバーの更新頻度が
  上がり、`NFR-perf-01` の「同梱物が変わらない日は取得が増分に留まる」が実態として崩れたとき。
- 関連: RQ-env-02 / RQ-env-03 / FR-env-11 / FR-env-12 / NFR-perf-01 /
  `D0-dist-03`・`D0-dist-04`(版の解決とピン留めの手段を 02/03 へ委ねる書き方の先例)/
  `D0-env-01`(ブラウザ確認をコンテナ内 Chrome と chrome-devtools MCP で行うと決めた項目)/
  `D0-env-07`(他の MCP ツールの導入は要確認のまま)
