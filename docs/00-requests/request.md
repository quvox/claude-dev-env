# 要求定義書:claude-dev-env

## 背景と目的

チームのリソースは簡単には増やせない一方、顧客からの要望は増え続けている。単一プロジェクトを
速く終わらせることよりも、**複数プロジェクトを並列に進められること**を優先したい。今のボトルネックは
「単一案件の速度」ではなく、**人間が進行管理(オーケストレーション)を兼ねているために並列度を
上げられない**ことにある。各プロジェクトの内容を常に人間が追わねばならず、管理に時間を取られている。

同時に、エージェント(Claude Code 等)にコードを書かせ実行させると、レビュー前のコードがホストの
資産(認証情報・ホストのファイルシステム)へ到達しうるという安全上の懸念がある。開発者ごと・
プロジェクトごとに環境がばらつくと、再現性も損なわれる。

目的は次の3つである。

- Claude Code を**隔離された Docker コンテナ**内で動かし、レビュー前コードがホストへ到達する経路を
  作らない。プロジェクトごとにコンテナを分離する。
- 環境一式を **Docker イメージとして配布**し、コマンド一発で立ち上げてチーム全員が同一構成を使える。
- 各プロジェクトに **AIオーケストレーターを1体**立て、人間は「検討(ブレインストーミング)」と
  「例外対応(介入)」だけに関与する。狙いは速さではなく**人間1人あたりの担当プロジェクト数を増やす**こと。

## 対象ユーザー

| 呼称 | 誰か | この人の目的 |
|---|---|---|
| 開発者 | 社内の開発者(日本語話者)。本ツールの主たる利用者 | プロジェクトのコンテナを起動して Claude Code で開発する。オーケストレーターを使って複数案件を並列に回す |
| 保守者 | 本ツール自体を保守する社内の開発者 | イメージの配布・更新と、オーケストレーターの振る舞いの確認を行う |

前提として**信頼できる社内開発用途に限定**する(信頼できないコードを扱う用途・本番に近い環境は対象外)。

## やること

| ID | 要求 | 補足 |
|---|---|---|
| RQ-env-01 | ホスト CLI によるコンテナのライフサイクル管理・ポートフォワード・認証・SSH 鍵転送 | Linux は `claude-dev`、macOS は `claude-dev-mac` |
| RQ-env-02 | 開発ツール入りコンテナイメージ(VNC あり/なし)と、noVNC 経由のブラウザ確認 | クライアント PC のブラウザからコンテナ内 Chrome を見る |
| RQ-env-03 | エージェント CLI の同梱(Claude Code と OpenAI Codex CLI)と、認証のホスト共有 | プロジェクト間で再ログインを不要にする |
| RQ-env-04 | ホストの Docker を制限付きで使うための Docker Socket Proxy | 生ソケットを渡さずに `docker` を使えるようにする |
| RQ-env-05 | 重い Docker 案件向けの VM モード(オプトイン) | QEMU+virtiofs、VM 内ネイティブ Docker |
| RQ-env-06 | macOS(Docker Desktop)対応 | OS 依存はホスト CLI に閉じる |
| RQ-orch-01 | AIオーケストレーター(2モード・外部制御ループ・介入設計・相互レビューによる品質ゲート) | プロジェクトに1体 |
| RQ-dist-01 | イメージの GHCR 配布(マルチアーキ) | チーム全員が pull で同一構成を得る |

## やらないこと

| # | やらないこと | 理由 |
|---|---|---|
| 1 | **各エージェントの個別隔離**(microVM 等での worker ごとの隔離) | 本構成は単一コンテナ同居型とし、隔離境界はコンテナ/ホスト間にのみ置く。個別隔離が要る用途は別構成(Docker Sandboxes 等)で検討する |
| 2 | **信頼できないコード・本番に近い環境での利用** | 信頼できる社内開発用途に限定するという前提を置いたうえで、隔離の強度を決めているため |
| 3 | ホストの Docker 生ソケットをコンテナへ直接マウントする運用 | ホスト掌握のリスクがあり、原則採用しない |
| 4 | オーケストレーターの**ブレインストーミング(人間の検討)の自動化** | ここは人間の価値が宿るため自動化しない |
| 5 | 完了基準の未充足を自動でタスク化して埋める機能 | v1 では検証は助言に留める |

## 完成イメージ

- 開発者は任意のプロジェクトディレクトリで `claude-dev start` と打つ。プロジェクト専用のコンテナが
  立ち上がり、カレントディレクトリが `/workspace` に見え、認証もファイアウォールも設定済みで、
  tmux の中で `claude` や `codex` がすぐ動く。ホストの秘密鍵ファイルも Docker 生ソケットも
  コンテナには入っていない。
- Web アプリを作ったら `claude-dev forward 5173` で必要なときだけポートを開き、クライアント PC の
  ブラウザで確認する。コンテナ内の Chrome を noVNC 越しに見ることもできる。
- 案件を任せるときは `claude-dev orchestrate` を実行する。対話でゴールと plan を固めたあとは離席でき、
  複数の worker が並列に実装する。要判断が出たタスクだけが待機し、Slack の通知を見て戻ってきて
  そのタスクにだけ答える。端末が壊れても、入り直せば同じ状態から続きが始まる。
- チームの他のメンバーは、ビルドせずに GHCR から pull するだけで同じ環境を得る。

## 制約・前提

- 実行環境: Linux サーバ(Ubuntu 22.04+ / Debian 12+ 推奨)または macOS + Docker Desktop。
  Docker Engine 24+。
- 認証: Claude Pro / Max プラン(OAuth)、および Codex 利用時は OpenAI 側アカウント
  (`codex login --device-auth` によるデバイス認証)。API キー・トークンはイメージに焼き込まず
  環境変数等で注入する。
- 外部 CLI(`claude` 等)と各ツールは変化が速い。採用・更新時に公式ドキュメントで最新仕様を確認する。
- OS 依存はホスト CLI に閉じる。コンテナ内資産(イメージ・entrypoint・firewall・docker-proxy)は
  OS 非依存に保つ。
