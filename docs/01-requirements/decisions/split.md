# 分割可否の決定事項

## D1-split-01 既定を不可分とし、段階可は「部分でも価値が増える」5件に限る

- 区分: 決定
- 決めた日: 2026-08-07
- 内容: 機能要件 21 件・非機能要件 13 件の全 34 件に `分割可否` を明記する。既定は `不可分` とし、
  `段階可(理由)` は次の5件だけとする。
  1. `NFR-perf-01`(pull の増分取得) — 再取得される層が減るだけでも取得時間の短縮という利用者価値があり、目標「再取得ゼロ」へ層単位で段階的に近づけるため。
  2. `NFR-perf-02`(イメージの層共有) — 共有されるベース層が増えるほど追加ディスクが減る形で目標へ段階的に近づけ、部分達成にもディスク削減の価値があるため。
  3. `NFR-scale-01`(同時起動の衝突ゼロ) — 衝突源(コンテナ名・ネットワーク名・公開ポート・Chrome プロファイル)は互いに独立で1つずつ解消でき、解消済みの資源の分だけ同時起動の安全が増すため。
  4. `FR-env-01`(コンテナのライフサイクル管理) — **段階的なのは条項 `FR-env-01-19` だけ**である
     (別ディレクトリの compose 資源を巻き込まない)。**何も満たさない状態 = compose
     プロジェクト名を一意化しない設計**では、`/workspace` にマウントされる全プロジェクトの
     既定名が `workspace` に一致し、他プロジェクトの compose 資源を**必ず**巻き込む
     (`D0-env-05` の理由欄)。一意化を入れた現在は巻き込みが起きるのはハッシュ先頭6桁が
     衝突した場合だけで、**残っている取り違えの余地は減るほど利用者の作業が守られる**。
     桁数を増やせばさらに近づく。**他の 20 条項は不可分**である。
  5. `FR-env-07`(Docker アクセスの制限) — **段階的なのは条項 `FR-env-07-5` だけ**で、
     `FR-env-01` と同じ機構(`DSN-env-03`)による。何も満たさない状態との比較も同じである。
     **他の9条項は不可分**である。
- 理由: 規範の既定が「未記載 = 不可分」というフェイルクローズであり、全件に `不可分` を明記することは
  現状の意味を変えない(現状を明示するだけ)。`段階可` にする5件は、いずれも
  **「部分的に満たした状態が、何も満たさない状態より利用者にとって価値がある」**という
  `不可分` の裏返しの条件を満たす。1〜3 は目標値へ段階的に近づく性能・規模の要件、
  4・5 は、一意化を一切行わない状態では**全プロジェクトが必ず衝突する**のに対し、
  部分的な一意化でも**衝突する組み合わせが減った分だけ利用者の作業が守られる**要件である
  (`docs/pendings.md` P-005 が「高い確率で起きる衝突を実用上無視できる確率の衝突に変えるもの」と
  記録しているのが、この段階性そのものである)。
- **`段階可` の射程は要件全体に掛かるが、実際に段階的な条項は限られる。**
  4・5 の理由欄が名指す条項(`FR-env-01-19` / `FR-env-07-5`)以外を `部分` にしてよいという意味では
  ない。とくに `FR-env-01` の「破壊的操作が他プロジェクトの資源を巻き込まない」という約束
  (条項 1〜18・20・21)は不可分である。
- 却下した案:
  - **34 件を1件ずつ人間が仕分ける** — 既定(不可分)から変わる可能性がある要件は限られ、
    全件の個別判断は決定シートの往復を増やすだけである(決定シート概念1で人間が「委任」と回答)。
  - **`FR-env-01` / `FR-env-07` を `不可分` のまま残す** — 02 のカバレッジ表が
    `FR-env-01-19` / `FR-env-07-5` を `部分(P-005)` とするため、規範により 01・02 が恒久的に
    検証済みにできなくなる(衝突検出を実装するまで)。2026-08-07 に人間が案 A で裁定した
    (決定シート 論点5)。
  - **充足を `完全` に戻して衝突を「設計の範囲外」と扱う** — 設計が覆いきれていない事実を表から
    消すことになり、条項単位カバレッジ導入の目的(部分充足を見えるようにする)と正面から反する。
- 関連: 機能要件の全21件(FR-env-01〜12 / FR-orch-01〜09)と非機能要件の全13件
  (NFR-perf-01〜03 / NFR-avail-01〜03 / NFR-sec-01・03 / NFR-ops-02〜04 / NFR-scale-01・02)。
  うち段階可は `FR-env-01`, `FR-env-07`, `NFR-perf-01`, `NFR-perf-02`, `NFR-scale-01` の5件 /
  `docs/pendings.md` P-005(`FR-env-01` / `FR-env-07` を段階可とする直接の根拠)/
  `docs/issues/060`(起点)

## D1-split-02 段階可を増やす・不可分へ戻す判断は委任しない

- 区分: 委任
- 決めた日: 2026-08-07
- 委任範囲: `分割可否` の**値と理由文を変えない**編集だけ — 要件を新設したときに既定の `不可分` を
  書き添えること、表記の位置と列の体裁、表現の平明化。
- 制約(ガードレール): 次の3つはいずれも**委任範囲外**であり、決定シートで人間に問う。
  1. 既存要件の `分割可否` の値を変える(`不可分` → `段階可`、またはその逆)。
     **`D1-split-01` が列挙する `段階可` の集合を AI の判断で増減させない**
     (件数はこの決定の本文が正であり、ここには書き写さない — 写すと更新が片側に取り残される)。
  2. 新設要件を `段階可` として起こす。
  3. **`段階可` の理由文が名指す条項の集合を変える**(`FR-env-01` で段階的なのは `FR-env-01-19`
     だけ、という限定が緩むことは、`不可分` へ戻す判断と同じ重みを持つため)。
  なお `段階可` には理由を必ず併記する(理由の無い `段階可` は重大度「高」の指摘 —
  `.claude/directions/01-requirements.md`)。
- 報告義務: 変えた場合は該当の変更指示と決定シートに `D1-split-02` と共に記録する。
- 関連: `D1-split-01` / 決定シート 論点5(2026-08-07 の裁定)
