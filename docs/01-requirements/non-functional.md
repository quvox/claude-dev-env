# 非機能要件

## 性能

| ID | 要件 | 目標値 | 測定方法 | 分割可否 |
|---|---|---|---|---|
| NFR-perf-01 | 日次ビルドの更新後も、利用者の `docker pull` は増分取得に留まること。同梱エージェント CLI が更新されたときに再取得させる層は、その導入層以降のみとする | 同梱 CLI のバージョンが変わらない日は、配布 2 イメージのどの層も再取得が発生しない | 前日分のイメージを持つ環境で `docker pull` を実行し、`Already exists` 以外の層が出ないことを確認する | 段階可(理由: 再取得される層が1つ減るだけでも取得時間の短縮という利用者価値があり、目標「再取得ゼロ」へ層単位で段階的に近づけるため) |
| NFR-perf-02 | ブラウザ確認ありのイメージは、なしのイメージのベースレイヤーを共有し、追加ディスクを VNC/Chrome 分に限定すること | (1) 2 イメージのベース層が同一ダイジェストであること。(2) **ブラウザ確認ありイメージだけが持つ追加層が導入するのは、ブラウザ確認(`FR-env-11`)を成立させる資産だけであること**。具体的には (i) VNC・ディスプレイ・ウィンドウマネージャ・noVNC、(ii) GUI ブラウザとその追加依存、(iii) 日本語入力とロケール(`FR-env-11` 受入基準3)、(iv) GUI セッションの端末・キー操作と gsettings/dconf バックエンド、(v) フォント、(vi) computer-use MCP の6カテゴリであり、**いずれにも属さない導入やファイル追加(開発ツール・言語ランタイム・ビルド済み成果物)が1件も現れないこと**。**同梱エージェント CLI の導入層は両イメージが等しく持つので (2) の対象外**である | `docker history --no-trunc` で両イメージの層を並べ、共通部分より後ろの層の `CREATED BY` を1行ずつ読む。(1) は共通部分の最終層のダイジェスト一致で判定する。(2) は追加層の `CREATED BY` に現れる導入物を上の6カテゴリへ1件ずつ割り当て、**どのカテゴリにも割り当てられないものが1件でもあれば不合格**とする。**対象の層は、02 が定めるステージ構成のうちブラウザ確認資産を積むステージである**。**付随処理(D-Bus の machine-id 生成・GTK の IM モジュールキャッシュ更新など、それ単体では上のどれでもないが、無いと特定のカテゴリが動かないもの)は、動かなくなるカテゴリへ帰属させる**(帰属先が1つも無いものだけを不合格とする) | 段階可(理由: 共有されるベース層が増えるほど追加ディスクが減る形で目標へ段階的に近づけ、部分達成にもディスク削減の価値があるため) |

## 運用・保守性

| ID | 要件 | 目標値 | 測定方法 | 分割可否 |
|---|---|---|---|---|
| NFR-ops-02 | OS 依存はホスト CLI に閉じ、コンテナ内資産(イメージ・entrypoint・firewall・docker-proxy)は OS 非依存に保つこと | コンテナ内資産に OS 分岐が 0 件 | コンテナ内資産のコードに OS 判定が無いことを確認する(**どのテストがこの確認を覆っているかは 03 のテスト対応表が正である**) | 不可分 |
| NFR-ops-03 | 利用可能な操作を一覧できること | `make help` で全ターゲットが表示される。CLI は引数なし/未知の引数でヘルプを表示する | 実機で確認する | 不可分 |
| NFR-ops-05 | 利用者へ向けた説明・警告・エラー・案内の文が日本語であること(ホスト CLI と entrypoint。常駐プロセス docker-proxy のログは対象外) | ホスト CLI と entrypoint が利用者へ向けて出力する文のうち、日本語でないものが 0 件(コマンド名・フラグ・パス・URL・識別子・絵文字はここでいう「文」に含まない) | `claude-dev` を引数なし・未知の引数・各サブコマンドの異常系で実行し、標準出力と標準エラーに現れる説明文を読む。entrypoint 側は `docker logs <コンテナ名>` の起動ログを読む。**英語由来の技術用語(`Docker` / `SSH` / `tmux` などの固有名詞)を含む文は、その語を除いた残りが日本語であれば日本語の文として数える**(除外する語と同じ扱い)(**どのテストがこの確認を覆っているかは 03 のテスト対応表が正である**) | 不可分 |

## 拡張性

| ID | 要件 | 目標値 | 測定方法 | 分割可否 |
|---|---|---|---|---|
| NFR-scale-01 | 複数プロジェクトを同時に起動しても、コンテナ名・ネットワーク名・公開ポート・Chrome プロファイルがプロジェクト間で衝突しないこと | 同時起動数 5 プロジェクトで衝突 0 件 | 異なる 5 ディレクトリで同時に `claude-dev start` し、生成リソース名とポートが重複しないことを確認する | 段階可(理由: 衝突源(コンテナ名・ネットワーク名・公開ポート・Chrome プロファイル)は互いに独立で1つずつ解消でき、解消済みの資源の分だけ同時起動時に衝突する組み合わせが減るため) |
| NFR-scale-02 | エージェント CLI を追加しても、認証共有・片付けの経路が増えないこと | 第1文: 認証共有ボリュームは 1 つのまま。**「`logout` / `reset` の分岐が増えない」は測らない** | 第1文: `docker volume ls` で認証共有ボリュームが 1 つであることを確認する。第2文: **測らない**。理由 = 比較の基準となる版と「分岐」の数え方が一意に決まらず、エージェント CLI を追加しない限り値が変化しない(観測しても常に同じ結果になり、合否の情報を持たない)。エージェント CLI を追加するときは、そのタスクが第1文だけで判定する | 不可分 |

## 法令・コンプライアンス

対象外(理由: 社内開発者だけが使う内製の開発環境であり、個人情報・決済情報・外部公開サービスを
扱わない。取り扱う資産は利用者自身のソースコードと認証情報に限られ、これらはセキュリティの節
(`NFR-sec-01`)で扱う)。
