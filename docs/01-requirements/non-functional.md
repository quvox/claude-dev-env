# 非機能要件

## 性能

| ID | 要件 | 目標値 | 測定方法 |
|---|---|---|---|
| NFR-perf-01 | 日次ビルドの更新後も、利用者の `docker pull` は増分取得に留まること。同梱エージェント CLI が更新されたときに再取得させる層は、その導入層以降のみとする | 同梱 CLI のバージョンが変わらない日は、配布 2 イメージのどの層も再取得が発生しない | 前日分のイメージを持つ環境で `docker pull` を実行し、`Already exists` 以外の層が出ないことを確認する |
| NFR-perf-02 | ブラウザ確認ありのイメージは、なしのイメージのベースレイヤーを共有し、追加ディスクを VNC/Chrome 分に限定すること | (1) 2 イメージのベース層が同一ダイジェストであること。(2) **ブラウザ確認ありイメージだけが持つ追加層が導入するのは、ブラウザ確認(`FR-env-11`)を成立させる資産だけであること**。具体的には (i) VNC・ディスプレイ・ウィンドウマネージャ・noVNC、(ii) GUI ブラウザとその追加依存、(iii) 日本語入力とロケール(`FR-env-11` 受入基準3)、(iv) GUI セッションの端末・キー操作と gsettings/dconf バックエンド、(v) フォント、(vi) computer-use MCP の6カテゴリであり、**いずれにも属さない導入やファイル追加(開発ツール・言語ランタイム・ビルド済み成果物)が1件も現れないこと**。**同梱エージェント CLI の導入層は両イメージが等しく持つので (2) の対象外**である | `docker history --no-trunc` で両イメージの層を並べ、共通部分より後ろの層の `CREATED BY` を1行ずつ読む。(1) は共通部分の最終層のダイジェスト一致で判定する。(2) は追加層の `CREATED BY` に現れる導入物を上の6カテゴリへ1件ずつ割り当て、**どのカテゴリにも割り当てられないものが1件でもあれば不合格**とする。対象の層がどれかは `03-impl/environments/images.md` が指す `vnc-base` ステージである。**付随処理(D-Bus の machine-id 生成・GTK の IM モジュールキャッシュ更新など、それ単体では上のどれでもないが、無いと特定のカテゴリが動かないもの)は、動かなくなるカテゴリへ帰属させる**(帰属先が1つも無いものだけを不合格とする) |
| NFR-perf-03 | worker への割り当ては、**1タスクが1回の worker 起動で完結する粒度**とすること(同一 Attempt の再開と、レビュー指摘による改訂は起動回数に数えない)。**worker へ渡す文脈の絞り方は設計層が定める**(`CTR-orchestrator-prompt` の `DSN-prompt-03`。要件としては上限値を課さない) | 1タスクあたり worker プロセスの起動は 1 回(再開・改訂を除く) | `.orchestrator/audit.jsonl` の起動イベント数をタスク数と突き合わせる |

## 可用性・信頼性

| ID | 要件 | 目標値 | 測定方法 |
|---|---|---|---|
| NFR-avail-01 | クライアント端末が失われてもコントローラは生存し、再実行で復旧できること。tmux サーバごと失われた場合も運用状態から再開できること | 端末全終了 → 再実行で、完了済みタスクの再実行が 0 件 | E2E-05(端末全終了 → `claude-dev orchestrate` 再実行)で、完了済みタスクの状態が変化しないことを確認する |
| NFR-avail-02 | コンテナは SSH 切断・tmux デタッチで停止しないこと | 切断後もコンテナが running を維持する | `claude-dev list` で状態を確認する |
| NFR-avail-03 | 補助機能(ファイアウォール適用・通知・VM 起動・ホスト設定の取り込み)の失敗が、主機能(コンテナ起動・run の継続)を止めないこと | 補助機能の失敗時も主機能の成功率 100% | 各補助機能を意図的に失敗させ、起動と run が継続することを確認する |

## セキュリティ

| ID | 要件 | 目標値 | 測定方法 |
|---|---|---|---|
| NFR-sec-01 | 隔離と最小権限: Docker 生ソケット・SSH 秘密鍵ファイルをコンテナへ渡さないこと。API キー/トークンをイメージに焼き込まないこと。docker-proxy をホストへ公開しないこと。コンテナの confinement(seccomp / AppArmor)を緩めないこと | 上記4項目すべてが常に成立(例外なし) | `docker inspect` でマウント・`SecurityOpt`・公開ポートを確認する。イメージ内に認証情報が無いことを確認する。E2E-03 で危険操作の拒否を確認する |
| NFR-sec-03 | 秘密情報(通知トークン等)の到達範囲が必要な発信源に限られること。エージェント(worker・対話 Claude)の環境に含まれないこと | **worker・レビューアー・対話 Claude の3種すべて**について、そのプロセス環境に**通知トークン `SLACK_BOT_TOKEN` が存在しない**こと。これを持ってよいのは通知を実際に送るコントローラとフックだけである。**環境変数として渡る秘密はこの1つだけである**(認証情報は共有ボリューム上のファイルとして渡り、環境変数を経由しない)ため、環境の検査でこの要件の全体を測れる | 3種それぞれの起動環境を取得し、`SLACK_BOT_TOKEN` が含まれないことを確認する。**対話 Claude は `orchestrator` の単体テストが、起動スクリプトに `unset SLACK_BOT_TOKEN` が含まれることを固定している。worker とレビューアーはこれを固定する単体テストが無いため、E2E-04 の実機確認手順で当該 worker ウィンドウ内の `env` を確認する。** テスト識別子と実装状況は `03-impl/tests/orchestrator.md` が正 |

## 運用・保守性

| ID | 要件 | 目標値 | 測定方法 |
|---|---|---|---|
| NFR-ops-02 | OS 依存はホスト CLI に閉じ、コンテナ内資産(イメージ・entrypoint・firewall・docker-proxy)は OS 非依存に保つこと | コンテナ内資産に OS 分岐が 0 件 | コンテナ内資産のコードに OS 判定が無いことを確認する |
| NFR-ops-03 | 利用可能な操作を一覧できること | `make help` で全ターゲットが表示される。CLI は引数なし/未知の引数でヘルプを表示する | 実機で確認する |
| NFR-ops-04 | モデル/effort ポリシーは 1 箇所で切り替え可能であること。運用状態は機械が読み書きし、人間が編集しない前提であること | 第1文: ポリシー定義が 1 ファイルに閉じている。**第2文(運用状態の読み書き主体)は測らない** | 第1文: 定義箇所を確認する(`docs/03-impl/relations/MODULE-orchestrator-claude-exec.md` の実装参照)。第2文: **測らない**。理由 = 「人間が編集しない」は利用者の**運用上の前提**であって、システムが強制する振る舞いではない。強制するには権限設定か改竄検知の仕組みが要るが、それを求める決定は 00 に無い。前提が破られたことをシステムが検知する要件も無いため、合否を判定できる観測点が存在しない |

## 拡張性

| ID | 要件 | 目標値 | 測定方法 |
|---|---|---|---|
| NFR-scale-01 | 複数プロジェクトを同時に起動しても、コンテナ名・ネットワーク名・公開ポート・Chrome プロファイルがプロジェクト間で衝突しないこと | 同時起動数 5 プロジェクトで衝突 0 件 | 異なる 5 ディレクトリで同時に `claude-dev start` し、生成リソース名とポートが重複しないことを確認する |
| NFR-scale-02 | エージェント CLI を追加しても、認証共有・片付けの経路が増えないこと | 第1文: 認証共有ボリュームは 1 つのまま。**「`logout` / `reset` の分岐が増えない」は測らない** | 第1文: `docker volume ls` で認証共有ボリュームが 1 つであることを確認する。第2文: **測らない**。理由 = 比較の基準となる版と「分岐」の数え方が一意に決まらず、エージェント CLI を追加しない限り値が変化しない(観測しても常に同じ結果になり、合否の情報を持たない)。エージェント CLI を追加するときは、そのタスクが第1文だけで判定する |
