# ユースケース

## UC-01 プロジェクトを隔離コンテナで開発開始

- 形式化した受け入れ基準: AC-01
- アクター: 開発者
- 目的: 自分のリポジトリを隔離環境で Claude Code 開発する
- 事前条件: 初回セットアップと Claude のログインが済んでいる
- 事後条件: プロジェクト専用コンテナで Claude Code が動作している
- 関連要件: FR-env-01, FR-env-02, FR-env-03, FR-env-04, FR-env-05, FR-env-11, FR-env-12, NFR-sec-01

基本フロー:

1. 開発者がプロジェクトディレクトリで `claude-dev start` を実行する。
2. システムはカレントディレクトリを `/workspace` にマウントしたコンテナを起動し、UID/GID 追従・
   認証コピー・**選択済み SSH 鍵だけの agent 転送(秘密鍵ファイルはマウントしない。FR-env-04)**・
   ファイアウォール適用・(ブラウザ確認ありなら)VNC/Chrome の起動・tmux の開始を行う。
3. システムは noVNC の接続 URL を表示し、tmux にアタッチする。
4. 開発者が tmux 内で `claude` を実行する。

代替フロー:

| # | 分岐条件 | 振る舞い |
|---|---|---|
| A1 | `--no-vnc` が指定された | ブラウザ確認資産を持たない軽量イメージで起動する |
| A2 | 同一ディレクトリで再実行した | 既存コンテナへ再接続する(tmux セッションが無ければ再作成する) |
| A3 | Codex CLI を使う | 手順4で `claude` の代わりに(または並行して)`codex` を実行する(UC-06) |
| A4 | `--vm` が指定された | ゲスト VM を起動し、その中のネイティブ Docker を使う(FR-env-08) |

例外フロー:

| # | 例外条件 | 振る舞い |
|---|---|---|
| E1 | 前提コマンドが不足している | 不足を列挙して導入方法を案内し、終了コード 1 で終わる |
| E2 | `.claude-dev.yaml` が無い | 端末があれば鍵選択、無ければ空で作成して起動を続ける(SSH 転送なし) |
| E3 | ファイアウォールの適用に失敗した | 警告を出して起動を継続する |
| E4 | noVNC のポートが競合した | 別ポートで最大 20 回まで再試行する。上限超過は終了コード 1 |
| E5 | tmux の起動待ちが上限を超えた | 状況を案内して終了コード 0 で終わる(コンテナは稼働を続ける) |

## UC-02 Web アプリをクライアントのブラウザで確認

- 形式化した受け入れ基準: AC-02
- アクター: 開発者(Linux サーバ + SSH 運用)
- 目的: コンテナ内 Web アプリを手元のブラウザで確認する
- 事前条件: コンテナ内で Web アプリが外から届く形で待ち受けている
- 事後条件: クライアントのブラウザにコンテナ内 Web アプリが表示されている
- 関連要件: FR-env-06, FR-env-10

基本フロー:

1. 開発者がサーバ上で `claude-dev forward <port>` を実行する。
2. システムはホスト側ポート(8100 番台)を割り当て、中継プロキシを立て、クライアント用の
   SSH トンネルのコマンドを表示する。
3. 開発者がクライアントで SSH トンネルを張り、案内された URL を開く。
4. 開発者が `claude-dev ports` で現在のフォワードを確認する。

代替フロー:

| # | 分岐条件 | 振る舞い |
|---|---|---|
| A1 | macOS の場合 | ポートは直結で、SSH トンネルは不要(FR-env-10) |
| A2 | 同じポートのフォワードが既にある | 二重に作らず、現在のホストポートを表示して終わる |
| A3 | 不要になった | `claude-dev unforward <port>` で解除する |

例外フロー:

| # | 例外条件 | 振る舞い |
|---|---|---|
| E1 | 対象コンテナが起動していない | 日本語エラーを表示して終了コード 1 |
| E2 | 割り当て範囲に空きが無い | 作成に失敗し、非0終了する |
| E3 | コンテナ側でそのポートが待ち受けていない | 中継は作られるが、接続時に接続拒否となる |

## UC-03 危険な Docker 操作が拒否される

- 形式化した受け入れ基準: AC-03
- アクター: 開発者(コンテナ内から Docker を使う)
- 目的: ホストを危険に晒さずにコンテナ内から Docker を使う
- 事前条件: 既定の DooD 構成(`DOCKER_HOST` が docker-proxy を指す)で起動している
- 事後条件: 危険操作が遮断され、安全な操作のみが Docker Engine に届いている
- 関連要件: FR-env-07, NFR-sec-01

基本フロー:

1. 開発者がコンテナ内で `docker run` 等を実行する。
2. システム(docker-proxy)がエンドポイントとリクエストボディを検査する。
3. システムが許可・書き換え・拒否のいずれかを行う。

代替フロー:

| # | 分岐条件 | 振る舞い |
|---|---|---|
| A1 | `/workspace` 配下の bind | 実ホストパスへ書き換えて許可する |
| A2 | bind を含まない通常操作 | そのまま中継する |
| A3 | 複数プロジェクトで同時に `docker compose` を実行した | compose プロジェクト名が一意化され、生成リソースが衝突しない |

例外フロー:

| # | 例外条件 | 振る舞い |
|---|---|---|
| E1 | 作業領域外のホストバインド・privileged・ホストのネットワーク/プロセス空間 | 403 で拒否する |
| E2 | `..` でパスを脱出しようとした | 正規化して判定し、拒否する |
| E3 | ボディが解釈できない | 中継を許可する(最終判断は Docker Engine が行う) |
| E4 | 上流への中継に失敗した | 502 を返してログへ記録する |

## UC-04 並列実装し、要判断だけ対応する

- 形式化した受け入れ基準: AC-04
- アクター: 開発者
- 目的: 案件を自律・並列で実装させ、人間は検討と例外対応だけに関与する
- 事前条件: コンテナが起動している
- 事後条件: 要判断のタスクだけが待機し他の worker は継続、回答後に実行復帰、完了で成果が統合される
- 関連要件: FR-orch-01, FR-orch-02, FR-orch-03, FR-orch-04, FR-orch-06, FR-orch-07, FR-orch-08, NFR-ops-01

基本フロー:

1. 開発者が `claude-dev orchestrate` を実行する。
2. システムはコントローラを常駐起動し、ダッシュボードをホーム表示する。
3. 開発者はブレインストーミングウィンドウの対話 Claude と plan を確定し、対話を終える。
4. システムは実行モードに入り、各タスクを worker(git worktree で分離)へ並行ディスパッチする。
5. 開発者は detach して離席する。
6. あるタスクが要判断になると、システムは「要判断 N 件」を通知し、そのタスクだけを待機させる。
7. 開発者は attach し、ダッシュボードのセレクタで待機中の worker を選び、対話で回答して終える。
8. システムはそのタスクの実行を復帰させ、全タスク完了時に成果を統合して完了を通知する。

代替フロー:

| # | 分岐条件 | 振る舞い |
|---|---|---|
| A1 | `D0-orch-18` の発火条件のいずれにも該当しない(不可逆でない / 試行回数が `stuck_limit` 未満 / その試行で行き詰まっていない / worker が「人間が必要」を**`D0-orch-18` が列挙する4理由(曖昧さ・方針分岐・前提崩れ・重大判断)のいずれかで**申告していない) | 仮定を置いて自律継続し、仮定を記録する |
| A2 | レビューで重大指摘が出た | 改訂ループへ入る(終了条件は重大指摘の解消または最大回数) |
| A3 | 通知先が未設定 | 通知せずに実行を継続する |

例外フロー:

| # | 例外条件 | 振る舞い |
|---|---|---|
| E1 | plan が実行不可(未 ready / 完了条件の欠落) | 理由を端末に明示してブレインストーミングへ戻す |
| E2 | 同一フォーマットエラーが 2 回続いた | 自動リトライを打ち切り介入へ回す |
| E3 | 依存先タスクが失敗した | 依存するタスクをブロック状態にする |
| E4 | 通知の送信に失敗した | 実行を止めない |

## UC-05 端末が壊れても復旧する

- 形式化した受け入れ基準: AC-05
- アクター: 開発者
- 目的: 端末破壊・中断が起きても run を失わず同じ状態へ戻る
- 事前条件: `orchestrate` で実行中
- 事後条件: 同じ状態へ復帰し、完了済みタスクは再実行されず、plan/履歴も削除されていない
- 関連要件: FR-orch-02, FR-orch-05, NFR-avail-01

基本フロー:

1. 端末(tmux クライアント)が全終了する。
2. 開発者が `claude-dev orchestrate` を再実行する。
3. システムはコントローラの生存を判定し、生存していれば合流、不在なら運用状態から再開する。

代替フロー:

| # | 分岐条件 | 振る舞い |
|---|---|---|
| A1 | 中断シグナルまたは終了操作で終えた | 実行中の worker に中間コミットの猶予を与えて状態を保存し、終了コード 0 で終わる |
| A2 | 同一 Attempt の再開 | 保存したセッション ID で続きから再開する |

例外フロー:

| # | 例外条件 | 振る舞い |
|---|---|---|
| E1 | セッションはあるがコントローラが死んでいる | 空き殻とみなして作り直す(run は状態から再開される) |
| E2 | 状態ファイルが読み取れない | 既存の内容を破壊しない |

## UC-06 Codex CLI をコンテナで使う

- 形式化した受け入れ基準: AC-06
- アクター: 開発者
- 目的: 一度のデバイス認証で、どのプロジェクトのコンテナでも codex を使う
- 事前条件: 初回セットアップ済み。OpenAI 側アカウントを持っている
- 事後条件: 別プロジェクトのコンテナでも再ログインなしで codex が使え、通常依頼ではシェル実行と
  読み書きが成功し、読み取り専用指定では読み取り成功かつ書き込み拒否になる
- 関連要件: FR-env-03, FR-env-12

基本フロー:

1. 開発者がホストで `claude-dev login-codex` を実行する。
2. システムは一時コンテナでデバイス認証を起動し、認証 URL とコードを表示する。
3. 開発者がブラウザでデバイス認証を完了する。
4. システムは認証ファイルを共有ボリュームへ保存する。
5. 開発者がプロジェクトディレクトリで `claude-dev start` し、tmux 内で `codex` を実行する。
6. 開発者が codex に、ファイルの読み書きとコマンド実行を伴う作業を依頼する。システムは既定設定
   (FR-env-12 の受け入れ基準5)のもとでシェルコマンドを実行し、`/workspace` を読み書きする。
7. 開発者がサンドボックスを明示指定した読み取り専用で調査を依頼する。システムは landlock
   バックエンドで読み取りを成功させ、書き込みは拒否する。

代替フロー:

| # | 分岐条件 | 振る舞い |
|---|---|---|
| A1 | 共有ボリュームに既に codex 認証がある | `login-codex` は不要(`start` 時にコピーされる) |
| A2 | 利用者が `config.toml` を書いている | 既存の鍵と値を変えず、不足している既定鍵だけを追記する |
| A3 | `workspace-write` を明示指定した | landlock では書き込みが成立しないため本 UC の対象外(書き込みを伴う自動化は既定設定で実行する) |

例外フロー:

| # | 例外条件 | 振る舞い |
|---|---|---|
| E1 | デバイス認証を完了せず終了した | 認証は保存されず、次に `codex` を実行しても未認証のままとなる |
| E2 | 端末を持たない環境で実行した | 非0終了する |
| E3 | `config.toml` が解釈できない | 既存ファイルを書き換えず、警告のみを出して起動を続ける |

## シナリオ外要件

| 要件 ID | どの UC にも現れない理由 |
|---|---|
| FR-env-09(イメージ配布) | CI がイメージをビルドして GHCR へ公開する処理であり、利用者の操作フローの中に現れない(利用者側の取得操作 `claude-dev pull` は任意で、UC-01 の事前条件「初回セットアップ」を満たす手段の1つに過ぎない)。確認は CI 側の成果物検証で行う |
| FR-orch-09(自己検証) | **保守者がこの仕組み自体を検証するための機能**であり、UC-01〜06 が対象とする「開発者がシステムを使って開発する」旅程の外にある。保守者の旅程は E2E シナリオ(`E2E-04` / `E2E-05`)が直接担うため、UC を別に設けていない |
| NFR-perf-01〜03 / NFR-avail-02〜03 / NFR-sec-02〜03 / NFR-ops-02〜04 / NFR-scale-01〜02 | 非機能要件であり、特定のユーザ旅程を持たない |
