# CTR-cli-container ホスト CLI → コンテナ/entrypoint

- 当事者: MOD-cli-start(および同じ起動経路を使う MOD-cli-code / MOD-cli-orchestrate) → MOD-entrypoint
- **管理ラベルの読み手**: MOD-cli-stop / MOD-cli-logout / MOD-cli-reset。
  この3モジュールは自分では起動しないが、**削除対象を決めるためにこの契約の
  「破壊的操作の対象の識別」節に依存する**(`D0-env-08`)。したがって発行側(MOD-cli-start)が
  ラベルの付与をやめると、読み手側の削除対象が空になる。
- 対応要件: FR-env-01, FR-env-02, FR-env-03, FR-env-05, FR-env-06, FR-env-07, FR-env-08, FR-env-11, FR-env-12
- 責任モジュール(結合テスト): MOD-entrypoint

## 破壊的操作の対象の識別

`D0-env-08` が「破壊的操作の対象は自分が作った資源に限る」と決め、識別方法をこの契約に委ねた。
ここが**唯一の正**である(`D0-env-10` の委任で名前と値を決めた)。

## 渡す環境変数

**真偽を表す変数は厳密一致で判定する**が、**既定が有効か無効かで見る値が違う**: 既定が無効のものは
**`1` に厳密一致したときだけ有効**(`true` / `yes` / `TRUE` は無効)、既定が有効のものは
**`0` に厳密一致したときだけ無効**(それ以外の任意の値は有効のまま)。どちらに属するかは下表の
「型・値域」に書く。判定はすべて受け側(entrypoint)が行い、**値の検証で起動を止めることはしない**。

| 変数 | 型・値域 | 付与するのは誰か | 必須 | 既定値 | 想定外の値のときの扱い |
|---|---|---|---|---|---|
| `DOCKER_HOST` | `tcp://<ホスト名>:<ポート>` 形式の URL | CLI(ホストに Docker ソケットがあるときだけ) | 条件付き | 付与しない | 形式を検証しない。到達できなければコンテナ内から Docker が使えないだけで、起動は続く。**VM モードでは entrypoint が上書きする** |
| `COMPOSE_PROJECT_NAME` | 小文字英数と `_` `-` のみ | CLI | **必須** | `<正規化名>-<起動ディレクトリの絶対パスのハッシュ短縮値>`。正規化名は起動ディレクトリ名を**小文字化してから** `[a-z0-9_-]` 以外の1文字を `-` に置換した値、ハッシュ短縮値は**絶対パスの SHA-256 の先頭6桁(16進小文字)**。詳細は下の「compose 資源の識別(プロジェクト名の一意化)」 | 付与しない経路が無いので発生しない。**ハッシュを足すことで、正規化後に衝突する別ディレクトリが同じ値にならない**(`NFR-scale-01`) |
| `CLAUDE_DEV_VM` | `1` のみが有効 | CLI(VM モード指定時) | 任意 | 付与しない(= 無効) | **`1` 以外はすべて無効**として扱う |
| `VM_PORTS` / `VM_MEM` / `VM_SMP` / `VM_DISK` / `VM_SWAP` | 文字列(ゲスト VM のパラメータ) | CLI(VM モードで、かつホスト側の同名変数が空でないときだけ転送) | 任意 | 付与しない(ゲスト側の既定に従う) | 値を検証しない。ゲスト VM の起動に失敗した場合は VM 無しで続行する |
| `CLAUDE_DEV_DOOD_PORTSYNC` | `0` で無効、それ以外は有効 | 利用者(CLI は付与しない) | 任意 | 未設定 = 有効 | **`0` の厳密一致のときだけ無効**。他の値は有効として扱う |
| `CLAUDE_DEV_VNC` | `1` のみが有効 | **イメージの `ENV`**(CLI は付与しない) | 任意 | ブラウザ確認資産を含むイメージでは `1` | `1` 以外はすべて無効として扱う |
| `CLAUDE_DEV_SSH_BRIDGE_PORT` | ポート番号の文字列 | CLI(**macOS のみ**) | 条件付き | 付与しない | **範囲も数値かどうかも検証しない。** 非空なら TCP ブリッジの接続先として使う。ソケットが用意できなくても起動は続く |
| `SSH_AUTH_SOCK` | コンテナ内の固定パス | CLI(**Linux のみ**、ホストに agent ソケットがあるとき) | 条件付き | 付与しない | 受け側はソケットの実在で判定する。無ければ agent 転送なしで続行する |
| `NODE_OPTIONS` | Node の起動オプション文字列 | CLI | **必須** | `--max-old-space-size=4096` | 付与しない経路が無い |
| `container` | `docker` | **イメージの `ENV`**(起動時ではない) | **必須** | `docker` | コンテナ内であることの判定マーカー。上書きは想定しない |

**VM モードと DooD ポート同期は排他**である: VM モードのときポート同期は起動しない
(ポート同期はホスト共有 daemon 経路のときだけ意味を持つため)。

|---|---|---|---|---|
| カレントディレクトリ | `/workspace` | 読み書き | **必須** | 常に。ここの所有者が UID/GID 追従の基準になる |
| 共有ボリューム(認証) | ホームディレクトリ配下の共有先 | 読み書き | **必須** | 常に。認証の受け渡しと書き戻しに使う。**Codex の認証も同じボリュームの `codex/` に相乗りする**(`D0-auth-01`) |
| 共有ボリューム(シェル設定) | 同上 | 読み書き | **必須** | 常に |
| 共有ボリューム(コマンド履歴) | 同上 | 読み書き | **必須** | 常に |
| tmux 設定 | ホームディレクトリ配下の固定パス | 読み取り専用 | **必須** | 常に |
| キット同梱の `CLAUDE.md` | ホームディレクトリ配下の固定パス | 読み取り専用 | **必須** | 常に |
| ホストの git 設定(`~/.gitconfig`) | コンテナ内の同名パス | 読み取り専用 | 任意 | **ファイルとして存在するときだけ** |
| ホストの gh 設定(`~/.config/gh`) | コンテナ内の同名パス | 読み取り専用 | 任意 | **ディレクトリとして存在するときだけ**。読み取り専用なのでホストの認証は書き換わらない |
| SSH agent ソケット | コンテナ内の固定パス | 読み取り専用 | 任意 | Linux で agent のソケットが存在するときだけ。**秘密鍵ファイルは渡さない** |
| `~/.ssh/known_hosts` | コンテナ内の同名パス | 読み取り専用 | 任意 | ファイルとして存在するときだけ |
| `~/.ssh/config` を加工した一時コピー | コンテナ内の同名パス | 読み取り専用 | 任意 | ファイルとして存在するときだけ。**`IdentityFile` / `IdentitiesOnly` / `IdentityAgent` の行を除去**してから渡す(コンテナ内に鍵ファイルが無く、ホスト固有の agent パスは agent を不通にするため) |
| ブラウザプロファイル用ボリューム | ホームディレクトリ配下 | 読み書き | 任意 | ブラウザ確認資産を使うときだけ |
| ゲスト VM 用ボリューム | ホームディレクトリ配下 | 読み書き | 任意 | VM モードのときだけ。**プロジェクトごとに別ボリューム**にして同時起動の競合を避ける |

## 渡す起動オプション

| 項目 | 値 | 必須 | 理由 |
|---|---|---|---|
| 実行形態 | デタッチ(`-d`)+ 疑似 TTY 割り当て | **必須** | 常駐させ、後から接続する |
| コンテナ名 / ホスト名 | 起動ディレクトリ名から決めた同一の名前 | **必須** | 名前で再接続する |
| ネットワーク | キット専用のユーザー定義ネットワーク | **必須** | docker-proxy と名前解決で繋ぐ |
| **管理ラベル** | 下の「破壊的操作の対象の識別」が定める3つのラベル(Claude コンテナに付ける) | **必須** | 破壊的操作が「自分が作った資源」だけを対象にするための印(`D0-env-08`) |
| 追加ケーパビリティ | ネットワーク管理に必要なもの(`NET_ADMIN` / `NET_RAW`)のみ | **必須** | ファイアウォールを適用するため |
| `--security-opt` | **付けない** | — | Docker 既定の seccomp / AppArmor を有効なまま使う(`NFR-sec-01`) |
| 再起動ポリシー | 明示的に停止するまで再起動 | **必須** | SSH 切断でコンテナを失わない |
| 公開ポート | ブラウザ確認資産を使うときだけ、空きポート → 固定のコンテナ側ポート | 任意 | 同時起動で衝突させない |
| デバイス | CPU 仮想化・高速ネットワーク・TUN/TAP のうち**ホストに実在するものだけ** | 任意 | 明示指定時のみ。存在しないデバイスは黙って外す。**CPU 仮想化デバイスの扱いは指定の仕方で分かれる**: デバイスを渡すだけの指定なら警告して続行し、**VM モードの指定なら中止する**(下の「エラーケース」参照) |

## 認証の受け渡し

- CLI が起動前に用意し、entrypoint が引き取る。
- Claude: 共有ボリューム直下 → プロジェクトディレクトリ配下の作業用ディレクトリ。
- Codex: 共有ボリュームの `codex/` → プロジェクトディレクトリ配下の作業用ディレクトリ。
- 共有ボリュームを増やさない(`D0-auth-01`)。所有者はホストの UID/GID に合わせる。

## エラーケース

| 条件 | 期待する振る舞い |
|---|---|
| 共有ボリュームに認証が無い | 何もコピーせず起動を完了する(未ログインのまま使える) |
| ホストの git 設定 / gh 設定が無い | そのマウントを省いて起動する |
| SSH 鍵が選択されていない | agent ソケットを渡さず、指定方法を案内して起動する |
| Docker ソケットが無い(macOS) | `DOCKER_HOST` を設定せずに起動する |
| 環境変数が想定外の値 | **上表の「想定外の値のときの扱い」に倒し、起動を止めない**。既定が無効の変数(`CLAUDE_DEV_VM` / `CLAUDE_DEV_VNC`)は無効のまま、既定が有効の変数(`CLAUDE_DEV_DOOD_PORTSYNC`)は**有効のまま**になる |
| 公開ポートが競合して起動に失敗した | ブラウザ確認資産を使う場合に限り、**稼働していない作りかけのコンテナだけを削除して**別のポートを取り直して再試行する(上限 20 回)。上限に達したか、競合以外の失敗なら、エラーを表示して終了コード 1 で終わる |
| **コンテナ名が衝突して起動に失敗した**(同名のコンテナが既に存在する) | **既存のコンテナを削除しない。** 同名のコンテナが稼働中であることと、別ディレクトリの同名プロジェクトである可能性を表示し、**再試行せずに**終了コード 1 で終わる。同名の稼働中コンテナは利用者の作業中セッションでありうるため、後片付けの対象にしてはならない |
| **CPU 仮想化デバイスを渡す指定(`--kvm`)をしたが、そのデバイスが無い** | **警告を出して続行する**(渡せるデバイスだけを渡す) |
| **VM モードの指定(`--vm` / `--vm-fresh`)をしたが、CPU 仮想化デバイスが無い** | **中止して終了コード 1 で終わる。** ソフトウェアエミュレーションでは実用的な速度が出ないため、VM 無しで続行させるのではなく、利用者に通常起動を選ばせる |
| ゲスト VM の**起動**に失敗した(デバイスはあるが provision / ブートが失敗) | **VM 無しで続行する**(起動そのものは失敗させない)。調査手段を案内する |
| 常駐セッションの起動が待ち時間内に完了しない | コンテナは起動したまま残し、状況と再実行の方法を案内して**終了コード 0** で戻る(黙って接続失敗にしない) |
| macOS で SSH の TCP ブリッジのソケットが用意できない | 待ち時間(最大 4 秒)を過ぎたら agent 転送なしで続行する |
| **ロックを取得できない**(同じキーを別の操作が保持している) | **待たない。** 保持している操作の名前とプロセス ID、再実行の方法を stderr へ出し、**削除も作成も一切行わずに**終了コード 1 で終わる |
| **ロックが、既に存在しないプロセスに保持されたまま残っている** | その事実を表示してからロックを引き継ぎ、処理を続ける(永久に取得できない状態を作らない) |
| **集合として列挙する削除の対象に、管理ラベルを持たない Claude コンテナがある** | そのコンテナは**削除しない**。名前と「本変更より前に起動した可能性がある」ことを表示して残す(規則 A) |
| **`stop <name>` の対象コンテナが管理ラベルを持たない** | その1件は**削除する**。管理ラベルを持たないことを表示する(規則 B) |
| **`logout` / `reset` が標準入力を TTY として持たない環境で `--yes` 無しに実行された** | **何も削除せずに中止**し、`--yes` の指定方法を表示して終了コード 1 で終わる。**`stop <name>` はこの行の対象ではない**(利用者が名前で1件を明示的に指した削除であり、確認を求めない = 規則 B。**根拠は `D0-env-08` 項3 が明示する `stop` の免除**であって項1 ではない — 項1 はラベルの要否についての例外である)。`--yes` を受け付けるのも `logout` / `reset` だけである |
| **`claude-dev stop <name>` の `<name>` が `[A-Za-z0-9._-]` 以外を含む** | **何も削除せず**、受理できない文字を含むことを表示して終了コード 1 で終わる(ロックを取る前に検証する) |
| **`stop <name>` の対象コンテナが `claude-dev.project-dir` ラベルを持たない、または既に存在しない** | **compose 資源の削除を行わない。** 一意化名のハッシュ源(起動ディレクトリの絶対パス)はこのラベルにしか無く、推測して作った名前で削除すると別ディレクトリを巻き込む(`docs/issues/024` の欠陥そのもの)。compose 資源が残っている可能性と手動で片付ける方法を表示して続行する(`FR-env-01` 受入基準21)。**本体コンテナの削除・`fwd-*` の片付け・遊休判定は通常どおり行う** |
| **`stop` の時点で旧い名前(ハッシュ無し)の compose 資源が残っている** | **削除しない。** 旧名は別ディレクトリと衝突しうるため対象に含めてはならない。可能性があることと、確認・手動削除の方法(`docker ps --filter label=com.docker.compose.project=<正規化名>` → `docker compose down`)を表示して続行する |
| **削除中に `INT` / `TERM` を受けた**(Ctrl-C など) | **進行中の1件を終えてから中断する**(1件の削除を途中で切ると中途半端な状態が残る)。**そこまでに削除した資源と、未削除のまま残った資源を1件ずつ列挙**し、**終了コード 130** で終わる(SIGINT の慣行値)。「削除しました」「完了」の文言は出さない。ロックは `trap` が解放する |
| **共有ボリュームの中身を消したが、削除後の列挙に何か残っていた** | 残っていたパスを列挙して終了コード 1 で終わる。**判定は「削除後の列挙結果」で行い、削除コマンドの終了コードでは行わない**(`rm -rf /auth/* /auth/.*` は `.` と `..` に当たって非0を返しうる一方、通常のファイルは消えているため、終了コードは「消えたか」を表さない) |
| **`logout` / `reset` の削除対象のうち1つ以上が削除できなかった** | 消えなかった資源を1件ずつ列挙し、終了コード 1 で終わる。**成功時の文言を出してはならない** |
| **遊休判定に使う Docker への問い合わせが失敗した**(ネットワークが存在しない / `docker` が応答しない) | **遊休でないと判定して docker-proxy を残す**(安全側へ倒す)。判定できなかったことを表示する。`FR-env-01` 受入基準9 は「稼働中なら止めるな」であり、判定不能を「遊休」と読み替えてはならない |

## 設計判断

### DSN-env-01 所有権は「起動時に付けたラベル」で表し、名前とイメージでは表さない

- 内容: **Claude コンテナ**には作った時点で `claude-dev.managed` / `claude-dev.role` /
  `claude-dev.project-dir` を付け、破壊的操作が集合として列挙する削除はこのラベルを根拠にする。
  **他の資源にはラベルを付けない**(固定名・固定接頭辞で識別できるため。上の
  「識別の手段は資源ごとに違う」)。
- 理由: 所有権の根拠になりうる候補は「名前」「イメージ」「ラベル」の3つである。Claude コンテナだけは
  名前が起動ディレクトリ名から決まるため一意でなく(`NFR-scale-01` / `docs/issues/028`)、
  イメージは `latest` が動くとそれ以前のコンテナを取りこぼす(`docs/issues/045`)。
  この1種類にだけラベルが要る。**逆に固定名を持つ資源にラベルを足すと、既存の資源がラベルを
  持たないという移行問題を、必要も無いのに作り込むことになる。**
- 却下した案:
  - **イメージ ID の履歴を並べて `--filter ancestor` に渡す** — 削除済みイメージから作られた
    コンテナを依然取りこぼす。取りこぼしの原因を減らすだけで、無くせない。
  - **コンテナ名の規約(命名の一意化)で表す** — 利用者に見える名前が変わり、既存コンテナの
    移行手順が必要になる(`docs/issues/028`)。本契約はそれを伴わずに成立する。
  - **`docker inspect` で起動引数を見て判定する** — 起動経路が増えるたびに判定条件が増える。
  - **すべての資源にラベルを付けて統一する** — 固定名の資源にとっては移行問題を増やすだけで、
    得られる情報が無い。
- 影響: **管理ラベルが付く前に起動された Claude コンテナはラベルを持たない。** 規則 A の対象から外れるため、
  `logout` / `reset` はそれを消さずに名前を表示して残す。利用者は `claude-dev stop <name>`(規則 B)で
  1件ずつ止めるか、`docker rm -f` で手動削除する。**遊休判定(規則 C)はラベルに依存しない**ため、
  ラベルの無い既存コンテナが稼働している間も docker-proxy は保護される。
  移行が完了する条件は「ラベルを持たない Claude コンテナが1つも残っていないこと」である。
  `logout` / `reset` が残したものを名前で列挙して表示するので、利用者はその表示が空になったことで
  移行の完了を判別できる(既存の他コマンドの表示は変えない)。
- 関連: `D0-env-08` / `D0-env-10` / `FR-env-01` 受入基準 9・14・15 / `FR-env-03` 受入基準 17

### DSN-env-02 排他は「プロジェクト単位」と「共有資源単位」の2段に分け、待たない

- 内容: `start` / `stop` / `logout` / `reset` / `login` / `login-codex` の**6コマンド**は上の
  「排他(ロックキー)」の表に従ってロックを取る。取得できなければ待たずに終了コード 1 で終わる。
- 理由: 保護すべき競合が2種類ある。(1) 同じコンテナ名を対象にする `start` ⇄ `stop` の競合、
  (2) 共有ボリュームと docker-proxy を対象にする `start` の認証コピー ⇄ `logout` / `reset` の競合
  (`docs/issues/020`。**認証が空のままコンテナが起動する**という、利用者が気づけない失敗を生む)。
  1つのロックに束ねると別プロジェクトの `start` が互いに待つことになり、`NFR-scale-01`
  (5プロジェクト同時起動)を損なう。
  **待たない**のは、CLI が対話的に使われる前提で、固まるより失敗して理由を示すほうが回復が速いため。
- 却下した案:
  - **1つのグローバルロックにする** — 別プロジェクトの同時起動が直列化し、`NFR-scale-01` を損なう。
  - **待つ(タイムアウト付きで再試行する)** — `logout` は稼働中コンテナを消してから認証を消すため
    保持時間が長く、待ち時間の上限を決められない。
  - **排他を入れず「同時に実行しない」を前提として明文化する** — 前提を守らせる手段が無く、
    破ったときの失敗が静かである(`docs/issues/020` の事象そのもの)。
- 関連: `D0-env-08` 項6 / `D0-env-09` / `FR-env-01` 受入基準 16・17 / `NFR-scale-01`

### DSN-env-03 compose プロジェクト名にパスのハッシュを足して一意にする

- 内容: `COMPOSE_PROJECT_NAME` を `<正規化名>-<絶対パスの SHA-256 先頭6桁>` にする。
  `stop` の compose 片付けはこの一意な名前だけを対象にする。
- 理由: compose 資源は**ラベルを付けられない**唯一の資源で、識別に使えるのは
  `com.docker.compose.project` の値だけである。ラベルという印を足せないなら、**印の代わりに名前を
  一意にする**しかない。従来の正規化(`[a-z0-9_-]` 以外を `-` に置換)は非可逆で、
  `~/work/My.App` と `~/other/my-app` が同じ `my-app` に落ちるため、一方の `stop` が他方の
  実行中サービスを削除しうる(`docs/issues/024`。データの破壊に至りうる)。
  絶対パスはプロジェクトを一意に決める唯一の値なので、それをハッシュ源にする。
- 却下した案:
  - **`stop` が削除前に対象名を列挙して確認を取るだけにする** — 名前の非一意性という根本が残るので、
    確認を読み飛ばした利用者は同じ被害に遭う。日常操作である `stop` に確認を足す代償も大きい。
  - **`stop` の compose 片付けをやめる** — `FR-env-01` 受入基準6 と `D0-env-05` のライフサイクルの
    決定に反し、compose コンテナが孤児として残り続ける。
  - **コンテナ名そのものを一意化する**(`docs/issues/028`) — 利用者に見える名前と 11 の呼び出し元が
    動く。compose 名の一意化はそれを伴わずに `024` を閉じられる。
  - **ハッシュだけにする**(正規化名を捨てる) — `docker ps` の出力から人がプロジェクトを見分けられない。
- 影響: **一意化名が導入される前に作られた compose 資源は古い名前を持つため `stop` の対象から外れる**
  (上の「compose 資源の識別」と「エラーケース」)。`docker ps` に現れる compose のコンテナ名・
  ネットワーク名が変わる(`<正規化名>_default` → `<正規化名>-<ハッシュ>_default`)。
- 関連: `D0-env-08` 項7 / `NFR-scale-01` / `FR-env-01` 受入基準6・19 / `docs/issues/024`

### DSN-auth-01 の適用

認証を**共有ボリュームからの symlink 参照ではなくコピー**で渡すのはこの契約の帰結である
(理由は `architecture.md` の `DSN-auth-01`)。コピー先はプロジェクトディレクトリ配下
(`/workspace/.claude/` `/workspace/.codex/`)で、**コンテナのホームからそのコピー先を symlink で
指すのは `DSN-auth-01` が定める形の一部である**(共有ボリュームを直接指すのではない)。
CLI は「置く」だけで、書き戻しは entrypoint の同期ループが担う。

## 順序性・冪等性・並行性の背景

- **冪等**: 同じディレクトリで再実行しても、再接続経路に入るため二重にコンテナを作らない。
- **並行**: 異なるディレクトリでの同時起動を前提とする。名前・ポート・プロファイルの一意化で
  衝突を避ける(`NFR-scale-01`)。空きポートの選定から起動までは原子的でないため、競合時は
  再試行で吸収する。
- **排他**: 上の「排他(ロックキー)」の2段のロックで、`start` / `stop` / `logout` / `reset` /
  `login` / `login-codex` の相互の競合を防ぐ。**別プロジェクトの `start` 同士は直列化しない**
  (プロジェクト単位のキーが異なるため)。共有資源単位のキーを取る区間だけが直列化する。
- **取得順**: 両方のキーを取る操作は「プロジェクト単位 → 共有資源単位」の順に取る。
  この順序は固定であり、逆順に取ってはならない。
- **ロックが守れない範囲**: ロックはホスト CLI のプロセス間だけで有効である。**利用者が
  `docker rm -f` を直接実行する場合、および別のホストから同じ Docker デーモンを操作する場合は
  保護されない**(この契約の範囲外)。

## 認可の考え方

ホスト CLI を実行できるユーザ(= ホストの Docker を操作できるユーザ)だけがこの契約を発行できる。
コンテナ内から本契約を書き換える経路は無い。

### 識別の手段は資源ごとに違う(ラベルが要るのは Claude コンテナだけ)

**本システムが作る Docker 資源のうち、名前から所有権が読み取れないのは Claude コンテナだけ**である
(名前が利用者の起動ディレクトリ名から決まるため、任意のコンテナと区別できない)。
他の資源は本システムが決めた固定名または固定接頭辞を持つので、名前で一意に識別できる。
**したがって管理ラベルは Claude コンテナにだけ付ける。**

| 資源 | 識別の手段 |
|---|---|
| **Claude コンテナ** | **管理ラベル**(下の表)。名前は利用者のディレクトリ名由来で一意でない |
| `fwd-<コンテナ名>-<ポート>` 中継コンテナ | **名前の接頭辞 `fwd-`**。本システムが決めた固定接頭辞である |
| docker-proxy コンテナ | **固定名 `claude-dev-docker-proxy`** |
| 共有ボリューム | **固定名** `claude-dev-auth` / `claude-dev-history` / `claude-dev-config`、および接頭辞 `claude-dev-chrome-` / `claude-dev-vm-` |
| ネットワーク | **固定名 `claude-dev-net`** |
| イメージ | **固定名** `claude-dev-claude` / `claude-dev-claude-vnc` / `claude-dev-docker-proxy` |
| **コンテナ内 `docker compose` が作った資源** | ラベル `com.docker.compose.project` のみ(**本システムはこれらにラベルを付けられない** — compose がコンテナ内で作るため)。そこで**その値そのものを一意にする**: 下の「compose 資源の識別(プロジェクト名の一意化)」 |

### 管理ラベル

| ラベル名 | 値 | 付与する資源 | 誰が付与するか |
|---|---|---|---|
| `claude-dev.managed` | `1`(固定) | Claude コンテナ | ホスト CLI(`docker run` の `--label`) |
| `claude-dev.role` | `claude`(固定。将来の資源種別の追加に備えて値を持たせる) | Claude コンテナ | 同上 |
| `claude-dev.project-dir` | 起動時のホスト側カレントディレクトリの**絶対パス**(`pwd` の値をそのまま。正規化・短縮をしない) | Claude コンテナ | 同上 |

- 接頭辞は `claude-dev.` に固定する。`com.docker.*`(Docker / compose の予約)は使わない。
- 値の検証は行わない。**受け側は存在するかどうかだけを見る**。ただし `claude-dev.project-dir` の
  **値そのものには2つの用途がある**: (1) 利用者への表示、(2) **`stop` が compose の一意化名を
  再現するためのハッシュ源**(下の「compose 資源の識別」)。**削除するかどうかの判定には使わない**
  (判定に使うと、ラベルを持たない既存コンテナを取りこぼす)。
- **ラベルを増やすことは互換の破れにならないが、名前と値を変えることは破れになる**
  (既存の稼働コンテナが古いラベルを持ったまま残るため)。変える場合は移行期の扱いを併記する。
- `claude-dev.project-dir` は「どのディレクトリで起動したか」という**事実の唯一の在り処**である。
  そのため次の2つが成立する: 同名コンテナとの衝突時(`FR-env-01` 受入基準12)に
  「別ディレクトリの同名プロジェクトである可能性」を推測ではなく事実として示せる。
  そして **`stop <name>` を別のディレクトリから実行しても compose の一意化名を再現できる**
  (`stop` の入力は `NAME` だけで、絶対パスは他のどこにも記録されていない)。
  **したがって `stop` は本体コンテナを削除する前にこのラベルを読まなければならない**。

### 削除対象の決め方(3つの規則)

| 規則 | 適用する操作 | 対象 |
|---|---|---|
| **A. 集合として列挙して消す** | `logout` / `reset` のコンテナ削除、`stop` の `fwd-<コンテナ名>-*` 一括削除 | Claude コンテナは `claude-dev.managed=1` を持つものだけ。**ラベルを持たない Claude コンテナは削除せず、名前を表示して残す**(表示対象の集合の求め方は下の「残したものをどう列挙するか」)。`fwd-*` と docker-proxy は上の表の名前規則で識別する(移行問題は起きない) |
| **B. 名前で1件を指して消す** | `claude-dev stop <name>` の本体コンテナ | ラベルの有無を問わず削除する(利用者が明示的に指したものである)。ラベルが無い場合はその旨を表示する。**ただし `<name>` は `[A-Za-z0-9._-]` だけを受理する**(下の「ロックキーとして使える文字」) |
| **C. 共有資源を止めてよいかの判定** | `stop` / `logout` / `reset` の docker-proxy の停止判定、および `reset` の `claude-dev-net` の削除判定(**`stop` と `logout` は `claude-dev-net` を削除する経路を持たない**。`FR-env-01` 受入基準9) | 下の「遊休判定」に従う。**ラベルとイメージのどちらにも依存させない**。`logout` と `reset` は Claude コンテナを削除したあとに判定する(**ラベルを持たない既存コンテナが稼働している間は docker-proxy と `claude-dev-net` を残し、残した理由を表示する**)。`reset` も例外ではない: `D0-env-08` 項2 は例外を書いていない |

### 残したものをどう列挙するか(ラベルを持たないコンテナの表示)

規則 A は「ラベルを持たない Claude コンテナは削除せず名前を表示する」と定める。**ラベルが無いのだから
ラベルでは引けない**ので、集合はこう求める。

**`claude-dev-net` に接続している稼働中コンテナから、名前が `claude-dev-docker-proxy` のものと
名前が `fwd-` で始まるものと `claude-dev.managed=1` を持つものを除いた残り**が、
「本システムのものかもしれないがラベルを持たないコンテナ」である。これを名前で表示する。

- 遊休判定(下)と**同じ集合の求め方を使う**。判定に使った集合をそのまま表示に流用できる。
- **停止中のラベル無しコンテナは列挙できない**(`docker network inspect` は稼働中のコンテナしか
  返さない)。これは意図した限界である: 停止中のコンテナは利用者の作業を壊さないので急がず、
  `claude-dev stop <name>`(規則 B)で1件ずつ消せる。**この限界を表示にも書く**
  (「停止中のものは列挙していない」)。
- **利用者が自分で立てた無関係なコンテナも混じりうる**(`claude-dev-net` に手で繋いだ場合)。
  混じっても**削除はしない**(表示だけ)ので害はない。

### ロックキーとして使える文字

排他のロックはキーをファイルシステムのパス要素として使い、残骸の回収でそのパスを削除する。
したがって**キーに使える文字は `[A-Za-z0-9._-]` だけ**とする。

- `claude-dev stop <name>` の `<name>` は利用者が任意の文字列を渡せるため、**ロックを取る前に
  検証し、受理できない文字を含むなら何も削除せず終了コード 1 で終わる**
  (`FR-env-01` 受入基準18)。`/` や `..` を含む名前を通すと、ロックのパスが意図した
  ディレクトリの外を指す。
- 引数を省略したときのコンテナ名は既に `[a-z0-9._-]` へ正規化済みなので、この条件を満たす。
- 共有資源単位のキーは固定文字列 `shared` である。

### 遊休判定(docker-proxy と `claude-dev-net` を削除してよい条件)

**`claude-dev-net` に接続している稼働中コンテナの集合から、名前が `claude-dev-docker-proxy` の
ものと名前が `fwd-` で始まるものを除いた結果が空**のときだけ、docker-proxy と `claude-dev-net` を削除してよい。
**`reset` にも同じ条件が掛かる**(`reset` はラベルを持たない Claude コンテナを残すため、無条件に消すと
残したコンテナの中から Docker が使えなくなる)。

**この条件が `claude-dev-net` について効くのは `reset` だけである。** `stop` と `logout` は
**遊休かどうかにかかわらず `claude-dev-net` を削除しない**(そもそも削除する経路を持たない)ので、
この判定が両者に対して決めるのは docker-proxy を削除してよいかだけである
(`FR-env-01` 受入基準9。**02 の操作範囲を 01 より広げてはならない**)。

- **イメージ名・イメージ ID を判定に使ってはならない**: `docker ps --filter ancestor=<名前>` は
  その名前が**今**指しているイメージ ID から作られたコンテナにしか一致しないため、イメージを
  再ビルド・再取得するとそれ以前に起動したコンテナを数え落とす(`FR-env-01` 受入基準9 の違反。
  `docs/issues/045` で実機観測)。
- **管理ラベルを判定に使ってはならない**: 管理ラベルが付く前に起動された既存コンテナはラベルを持たないため、
  数え落として同じ違反を起こす。ネットワークへの接続は起動経路によらず必ず成立する
  (「渡す起動オプション」の「ネットワーク」は必須項目である)ため、判定の根拠として最も広い。
- 除外を名前だけで行うのは、`fwd-` 接頭辞と docker-proxy の固定名がラベルの有無に関係なく
  成立するためである。判定全体がラベルから独立するので、**既存コンテナも新規コンテナも同じに数える**。
- **VM モードのコンテナも同じに数える**(VM モードでも Claude コンテナ自身は `claude-dev-net` に
  接続する。compose がゲスト内で完結するだけである)。
- **`login` / `login-codex` の一時コンテナも `claude-dev-net` に接続するため、この判定は
  それらを「稼働中」として数える**(名前が付いていないので除外できない)。結果は
  「ログイン操作の最中は docker-proxy を消さない」であり、**過剰に数える=消さない側**なので
  受入基準9 を破らない。次の `stop` が回収する。

### compose 資源の識別(プロジェクト名の一意化)

コンテナ内の `docker compose` が作る資源には**本システムのラベルを付けられない**
(compose が Claude コンテナの中で `docker-proxy` 経由に作るため、ホスト CLI の `--label` が届かない)。
識別に使える手段は `com.docker.compose.project` ラベルだけである。そこで
**そのラベルの値そのものをプロジェクト間で一意にする**(`D0-env-08` 項7)。

**`COMPOSE_PROJECT_NAME` = `<正規化名>-<ハッシュ短縮値>`**

| 部分 | 定義 |
|---|---|
| 正規化名 | 起動ディレクトリ名を小文字化し、`[a-z0-9_-]` 以外の1文字を `-` に置換した値(**人が読める部分をコンテナ名に残すため**、ハッシュだけにはしない) |
| ハッシュ短縮値 | **起動ディレクトリの絶対パス**(`pwd` の値)の **SHA-256 の先頭6桁**(16進小文字) |

- ハッシュの入力は**絶対パス**である(ディレクトリ名ではない)。これにより
  `~/work/My.App` と `~/other/my-app` は正規化名が同じ `my-app` でも別の値になる。
- 6桁(24ビット)にした理由: 同時に扱うプロジェクト数は数十のオーダーで、衝突確率が実用上無視できる
  一方、コンテナ名として読める長さに収まる。**桁数を変えると既存の compose 資源が対象から外れる**
  ので、変える場合は移行期の扱いを併記する。
- **衝突は検出しない**(2026-08-04 に人間が受容。`docs/pendings.md` **P-005**)。
  異なる絶対パスが同じ先頭6桁になった場合、その2ディレクトリでは一方の `stop` が他方の
  compose 資源を削除しうる(`docs/issues/024` と同じ事象が、確率は桁違いに低い形で残る)。
  **この一意化が保証するのは「衝突の確率が実用上無視できる水準であること」までであり、
  衝突がゼロであることは保証しない**(絶対パスをハッシュ源にしているため、正規化名が同じでも
  別の値になるが、先頭6桁の一致は起こりうる)。解消が必要になる条件と選択肢は P-005 が持つ。
- 実装は Linux と macOS で**同じ値**を出さなければならない(`D0-scope-03`)。
  コマンド名が OS で違う点は 03 の実装上の判断が扱う。
- **`stop` はハッシュ源(起動ディレクトリの絶対パス)を `claude-dev.project-dir` ラベルから読む。**
  `stop` の入力は `NAME` だけで絶対パスを持たないため、**本体コンテナを削除する前に読む**必要がある
  (削除後はラベルが消える)。**ラベルが無い/対象コンテナが存在しない場合は compose の片付けを
  行わず、手動手順を案内する**(推測でハッシュを作ると別ディレクトリを巻き込む)。
- **`stop` の compose 片付けはこの一意な名前だけを使う**。これで別ディレクトリの compose 資源を
  巻き込む経路が閉じる(`docs/issues/024`)。
- **ハッシュ短縮値を持たない古い名前(`<正規化名>` だけ)の compose 資源が既存環境に残っている場合、
  それは `stop` の片付け対象から外れる**(その名前を作った時点の実装が一意化していなかった)。
  `stop` はその可能性を表示し、
  `docker ps --filter label=com.docker.compose.project=<正規化名>` で確認して
  `docker compose down` するか `docker rm -f` する方法を案内する(`D0-env-08` 項7)。
  **古い名前を対象に含めてはならない**: それをすると衝突する別ディレクトリを巻き込む今の欠陥が
  そのまま残る。

### 排他(ロックキー)

`D0-env-08` 項6 の排他は次の2つのキーで行う(実装手段と置き場所は `D0-env-09` の委任で 03 が決める)。
**対象は共有ボリュームまたは docker-proxy を触る6コマンド**(`start` / `stop` / `logout` / `reset` /
`login` / `login-codex`)である。

| キー | 値 | 取得する操作と区間 |
|---|---|---|
| プロジェクト単位 | 対象コンテナ名(`<NAME>`) | `start`(全区間)/ `stop`(全区間) |
| 共有資源単位 | 固定文字列 `shared` | `logout`(全区間)/ `reset`(全区間)/ **`login`(全区間)/ `login-codex`(全区間)** / **`start`(認証コピーの開始からコンテナ作成の確定まで。ポート競合の再試行ループを含む)** / `stop`(遊休判定から docker-proxy 削除までの区間) |

- **両方を取る操作は「プロジェクト単位 → 共有資源単位」の順で取る**(デッドロックを避けるため
  取得順を固定する)。
- **待たない。** 取得できなければ「エラーケース」の行に従う。
- **`login` / `login-codex` は対話認証を含むため保持時間が長い**(利用者がブラウザで認証を終えるまで)。
  その間 `start` の認証コピー区間・`logout` / `reset` の全区間は取得できず、理由を表示して非0で終わる。
  これは意図した振る舞いである: 認証を書いている最中に消す/読むほうが害が大きい。
- **ロックが守る資源**: プロジェクト単位 = 当該コンテナとそのプロジェクトディレクトリ配下の生成物。
  共有資源単位 = 共有ボリューム(`claude-dev-auth` / `-history` / `-config`)**の中身**と
  docker-proxy、**および「共有ボリュームを読んで作られたコンテナ」**。
  **含まないもの**: イメージ、共有ネットワーク `claude-dev-net`、共有ボリュームそのものの存在
  (上の「冪等に作られる共有資源の『用意』」)。
- **`start` の共有資源単位の区間がコンテナ作成の確定まで及ぶ理由**: 起動したコンテナの entrypoint は
  30 秒ごとに認証を共有ボリュームへ**書き戻す**(`FR-env-03` 受入基準3・8)。認証コピーの直後に
  ロックを離すと、(a) `logout` が完走した直後に作られたコンテナが認証を書き戻して
  **`logout` が静かに巻き戻る**、(b) `stop` の「遊休判定と削除を同一区間に入れる」保護が、
  `start` の docker-proxy 作成(`ensure_docker_proxy_container`)と競合して成立しない。
  **直列化されるのは認証コピーからコンテナ作成までの短い区間だけ**なので、
  `NFR-scale-01`(5プロジェクト同時起動)への影響は限定される。
- **冪等に作られる共有資源の「用意」はロックの保護対象ではない。** 該当するのは2つで、
  **イメージのビルド**(`require_setup`。セットアップ未実施ならイメージを自動ビルドする事前条件
  ゲート)と、**ネットワーク `claude-dev-net` と共有ボリューム3本の作成**
  (`ensure_infrastructure`)である。どちらもロックを取る前に走ってよく、その結果として
  イメージ・ネットワーク・空のボリュームが作られても `FR-env-01` 受入基準16 の
  「削除も作成も行ってはならない」に反しない。**どちらも冪等に作られる共有資源であり、どの操作から
  作っても結果が同じで、利用者から見た状態を壊さないためである**(既に在れば何も起きず、無いときに
  作られるのは中身の無い器だけで、認証や作業内容を含まない)。
  **保護対象なのは「器」ではなく「中身」である**: 共有ボリュームの**中身**(認証情報)と
  docker-proxy、および共有ボリュームを読んで作られたコンテナは保護対象のままである。
  `start` / `login` / `login-codex` がこの2つをロックの取得より前に置くのはこの理由による
  (各機能の「実装上の判断」)。
- **解放は取得したプロセスだけが行う**: ロックに記録された**保持者のプロセス ID** が自分と一致しない
  ときは削除しない(明示的に解放したキーを、後から別の操作が取り直した場合に消してしまうのを防ぐ)。
  **保持者をどう記録するかは実装手段の選択であり、`D0-env-09` で AI に委任している**
  (この契約が課すのは「保持者が判別できること」だけである)。
