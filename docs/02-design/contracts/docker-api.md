# CTR-docker-api コンテナ → docker-proxy

- 当事者: Claude コンテナ内の Docker クライアント → MOD-docker-proxy → ホストの Docker Engine
- 対応要件: FR-env-07, NFR-sec-01
- 責任モジュール(結合テスト): MOD-docker-proxy

## 通信の形

| 項目 | 内容 |
|---|---|
| 経路 | `DOCKER_HOST` が指す HTTP エンドポイント(`claude-dev-net` 内のみ。ホストへ公開しない) |
| 対象 | Docker Engine API のすべてのパス(透過中継) |
| 検査の対象 | コンテナ作成要求のボディ、コマンド実行(exec)作成要求のボディ、および要求パス |
| 結果 | 許可(透過)/ 書き換えて許可 / 拒否 |

## 検査する要素と判定

| 要素 | 条件 | 判定 |
|---|---|---|
| 要求パス | 版接頭辞(`/v1.45` 等)を除いた先が `/swarm` / `/plugins` / `/configs` / `/secrets` のいずれかで始まる | **メソッドを問わず拒否**(ボディを見ない。クラスタ管理・プラグイン・機密の操作面をまるごと閉じる) |
| バインドマウント | 作業領域(`/workspace`)配下 | **書き換えて許可**(実ホストパスへ変換する。既定有効。`CLAUDE_DEV_ALLOW_WORKSPACE_BINDS` を `0`/`false`/`no`/`off` にすると全面拒否へ倒す) |
| バインドマウント | 上記以外のホストパス | **拒否** |
| バインドマウント | 正規化すると呼び出し元のプロジェクトディレクトリ外を指す(`..` による脱出) | **拒否** |
| バインドマウント | 呼び出し元コンテナを特定できない | `/` 始まりをすべて**拒否**(名前付きボリュームのみ許可) |
| 特権(privileged) | 有効 | **拒否** |
| ネットワークモード | ホストのネットワーク空間の共有 | **拒否** |
| PID モード | ホストのプロセス空間の共有 | **拒否** |
| ユーザー名前空間 | ホストのユーザー名前空間の共有 | **拒否** |
| 追加ケーパビリティ | 危険なケーパビリティ(`SYS_ADMIN` / `SYS_PTRACE` / `SYS_RAWIO` / `SYS_MODULE` / `DAC_READ_SEARCH`。大文字化して突き合わせる) | **拒否** |
| デバイスの割り当て | 1件でも指定されている | **拒否** |
| 特権(exec) | コンテナ内でのコマンド実行を特権で要求 | **拒否** |
| 上記を含まない要求 | — | **許可**(透過) |

判定の順序: **要求パスの遮断を最初に行い**、ボディの検査はそのあと
特権 → ホスト名前空間の共有 → バインドマウント → ケーパビリティ → デバイス、の順に
判定する。バインドをケーパビリティ・デバイスより先に判定するのは、利用者が最も踏みやすい
「作業領域外の持ち込み」の理由を優先して返すためである。

## エラーケース

| 条件 | 期待する振る舞い |
|---|---|
| 拒否に該当する | `403 Forbidden` を返し、拒否理由を本文に含める(本文は `blocked: <理由>` の平文) |
| ボディが解釈できない | **中継を許可する**(独自解釈で誤って弾かない。最終判断は Docker Engine が行う) |
| 上流への中継に失敗した | 502 を返し、ログへ記録する |
| 起動時に Docker ソケットが無い | 待ち受けを開始せず終了する |

## 設計判断

### DSN-dp-01 判定できない入力は通し、判定できる危険だけを止める

- 判断: 解釈できないボディは中継する。一方、判定できる危険(作業領域外バインド・特権・ホスト空間の
  共有)は例外なく止める。
- 理由: プロキシが独自に解釈を広げると、Docker の仕様変更のたびに正常な操作を誤って弾くようになる。
  中継しても最終的な検証は Docker Engine が行うため、未知の形式を通すことは防御の穴にはならない。
  逆に、判定できる危険を「たぶん大丈夫」で通すと隔離境界が崩れる。
- 却下した案: 解釈できないボディを一律拒否する — Docker の仕様変更で正常な操作が止まる。
  許可リスト方式でエンドポイントを絞る — 開発で使う API を列挙しきれず、運用が破綻する。

### DSN-dp-02 パスの封じ込めは字句的に行う

- 判断: バインド元パスの封じ込め判定を、正規化した文字列の前方一致で行う(symlink の実体解決は
  しない)。
- 理由: プロキシはホストのファイルシステムを持たないため、実体解決が原理的にできない。
- 却下した案: 実体解決してから判定する — プロキシからは解決できず、常に失敗する。
- **既知の制限**: ホスト側の symlink による脱出は検出できない。この制限は 03 側の「既知の制限」に
  記載し続ける。

## 順序性・冪等性・並行性の背景

- **並行**: 複数コンテナからの同時アクセスを前提とする。判定は要求ごとに独立し、状態を持たない。
- **冪等**: プロキシ自身は状態を持たないため、同じ要求は常に同じ判定になる。

## 認可の考え方

`claude-dev-net` に参加しているコンテナだけがアクセスできる。ホストへは公開しない。
呼び出し元コンテナの特定は接続元アドレスから行い、特定できない場合は安全側(ホストパスの
バインドを全拒否)に倒す。
