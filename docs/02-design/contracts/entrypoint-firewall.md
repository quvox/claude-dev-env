# CTR-entrypoint-firewall entrypoint → firewall

- 当事者: MOD-entrypoint → MOD-firewall
- 対応要件: FR-env-05
- 責任モジュール(結合テスト): MOD-entrypoint

## 呼び出しの形

| 項目 | 内容 |
|---|---|
| 契機 | コンテナ起動シーケンス中に**1度だけ** |
| 引数 | なし |
| 前提 | ネットワーク管理のケーパビリティが付与されていること。必要なコマンド群がイメージに同梱されていること |
| 結果 | 外向き通信にブラックリストが適用される |
| 戻り値の扱い | **成否に関わらず entrypoint は起動を継続する** |

## エラーケース

| 条件 | 期待する振る舞い |
|---|---|
| ケーパビリティが無い | 適用は失敗するが、entrypoint は起動を止めない(警告を起動ログへ出す) |
| ブロック対象の名前解決に失敗 | 当該の1件だけをスキップし、残りを適用する(そのドメインは塞がれない) |
| 許可 IP レンジの取得に失敗 | 名前解決へフォールバックする。それも失敗した場合は当該通信が不許可になる |
| 適用後の到達性が想定と異なる | 警告行を出力する(起動は継続する) |
| 再実行された | 既存のルールの有無にかかわらず同じ結果になる(冪等) |

## 設計判断

### DSN-fw-01 起動を止めないことを契約の一部にする

- 判断: ファイアウォールの適用失敗を、コンテナ起動の失敗として扱わない。
- 理由: ネットワーク制限は防御であって前提条件ではない。適用に失敗するのは環境側の事情
  (ケーパビリティ不足・DNS 不通)であることが多く、そこで起動を止めると開発そのものができなくなる。
  代わりに、成否が起動ログから判別できることを要件にしている(`FR-env-05` の受け入れ基準5・6)。
- 却下した案: 適用失敗で起動を中止する — 環境要因で開発が止まる。失敗を黙って無視する —
  制限がかかっていないことに利用者が気づけない。

## 順序性・冪等性・並行性の背景

- **順序**: ネットワークを使う後続処理(認証の取得・MCP 設定)より前に適用する。
- **冪等**: 再適用は同じ結果になる。既存ルールが無い状態での実行も失敗としない。
- **並行**: 同一コンテナ内で並行呼び出しは起きない。

## 認可の考え方

コンテナ内の初期化プロセスだけが呼ぶ。利用者向けには表示専用の入口(`MODULE-cli-firewall`)しか
提供せず、ルールの書き換え口を与えない。
