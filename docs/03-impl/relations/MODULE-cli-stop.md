# MODULE-cli-stop セッションの停止

## 目的

1つのプロジェクトの Claude セッションと、**そのセッションが作った資源**を片付ける
(`FR-env-01`・`FR-env-07`)。片付けの範囲は **「セッションが作ったものは全部」** であり、
例外は名前付きボリューム(利用者のデータ)とイメージ(`D0-env-05` 項2)、および**所有者を特定できなかった資源**である(`FR-env-01` 受入基準22。この2つ目の例外の中身は「既知の制限」が持つ)。

**集合として列挙して消す資源は「自分が作った資源」に限る**(`D0-env-08` 項1)。**識別の手段は
資源ごとに違い、正は契約 `CTR-cli-container`「識別の手段は資源ごとに違う」である**(この機能が
実際にどう引くかは下の「処理の流れ」、引けないときに何が残るかは「既知の制限」が持つ)。

## 処理の流れ

1. `MODULE-cli-common-container-name` で対象コンテナ名を決める(引数 `NAME` 優先)。
   **`NAME` が明示されている場合、`[A-Za-z0-9._-]` 以外の文字を含むなら何も削除せず、受理できない
   文字を含むことを表示して終了コード 1 で終わる**(`FR-env-01` 受入基準18。この名前が次の手順で
   ロックキー=パス要素になるため)。省略時の名前は既に `[a-z0-9._-]` へ正規化されている。
2. `MODULE-cli-common-lock` で**プロジェクト単位**のロック(キー = 手順1 のコンテナ名、操作名 `stop`)を
   取る。取得できなければ**削除を一切行わずに**非0で終わる(`FR-env-01` 受入基準16)。
3. `fwd-<name>-*` の中継コンテナを片付ける。**中継コンテナは本システムが決めた固定接頭辞 `fwd-` と
   対象コンテナ名から名前が一意に決まるため、管理ラベルではなく名前で識別する**
   (契約 `CTR-cli-container` の「識別の手段は資源ごとに違う」)。既存分にラベルが無いという
   移行問題は起きない。
4. **本体コンテナを削除する前に**、`docker inspect` で管理ラベルを読む(**この順序は固定**。
   削除するとラベルが失われ、以降 compose の一意化名も所有者ラベルの値も再現できない。契約
   `CTR-cli-container` の「compose 資源の識別」と `DSN-env-04`)。
   - `claude-dev.managed` の有無 → 手順5 の表示に使う。
   - **`claude-dev.project-dir` の値 → 手順6 の compose 一意化名のハッシュ源、および手順8 の
     所有者ラベルの照合値**にする。
   - **ラベルが無い、値が空である、または対象コンテナが存在しない場合は `PROJECT_DIR` を
     得られないので、手順6・7 の compose 片付けと手順8 のセッション由来の資源の片付けを行わず、
     その旨を表示する**(推測した値で削除すると別ディレクトリ・別セッションを巻き込む。
     `FR-env-01` 受入基準21・23)。**`container_project_dir()` は `<no value>` を空文字へ潰すので、
     「ラベルが無い」と「値が空」はこの1つの判定で同じ経路に入る。**
5. `MODULE-cli-common-container-exists` で本体コンテナの存在を確認し、`docker rm -f "$NAME"` する。
   **本体は名前で1件を指した削除なので、管理ラベルの有無を問わず削除する**(規則B)。
   ラベルを持たない場合はその旨を表示する(`FR-env-01` 受入基準15)。
6. 当該コンテナ内から起動された compose コンテナ群をラベル
   `com.docker.compose.project=<一意化名>` で特定して `docker rm -f` する。
   **削除できた名前はその場では表示せず、手順8-3 の列挙へ渡す**(compose コンテナも用語集の
   「セッション由来の資源」であり、`FR-env-01` 受入基準26 の表示対象である。**経路ごとに
   表示が分かれると、利用者から見て「何が消えたか」が2箇所に散る**)。**`<一意化名>` は
   `<正規化NAME>-<手順4 で読んだ `claude-dev.project-dir` の SHA-256 先頭6桁>`**(契約
   `CTR-cli-container` の「compose 資源の識別」)。**旧い名前(ハッシュ無しの `<正規化NAME>`)を
   対象に含めてはならない**(別ディレクトリと衝突しうる)。
   ラベル `com.docker.compose.project=<正規化NAME>` のコンテナが**存在する場合は、削除せずに**
   「一意化名が導入される前に作られた compose 資源が残っている可能性」と確認・手動削除の方法
   (`docker ps --filter label=com.docker.compose.project=<正規化NAME>` → `docker compose down`)を
   表示する(`FR-env-01` 受入基準20)。**この案内だけは `claude-dev.project-dir` を読めたかにかかわらず出す**(旧名は正規化名だけから作れるため、起動元ディレクトリが要らない)。**実際の表示位置は手順8-3 の列挙のあと**であり、手順の記述順とは違う。
7. 当該プロジェクトの compose デフォルトネットワーク `<一意化名>_default` が残っていれば
   `docker network rm` する。**他から使用中で削除できない場合は続行する**
   (`FR-env-01` 受入基準11)。**削除できた名前は手順8-3 の列挙へ渡す**(手順6 と同じ理由)。
8. **セッション由来の資源を削除する**(`FR-env-01` 受入基準22。`DSN-env-04` の規則 D)。
   手順4 で読んだ `claude-dev.project-dir` の値を `<OWNER>` として、次の順で行う。
   **順序は固定**(使用中のネットワークは削除できないので、必ずコンテナを先に消す)。
   1. `docker ps -a --filter "label=claude-dev.owner-project-dir=<OWNER>" --format '{{.Names}}'` で
      **コンテナ**を名前で列挙し、1件ずつ `docker rm -f` する。**停止中のものも含む**(`-a` を付ける)。
   2. `docker network ls --filter "label=claude-dev.owner-project-dir=<OWNER>" --format '{{.Name}}'` で
      **ネットワーク**を名前で列挙し、1件ずつ `docker network rm` する。
   - **列挙の問い合わせそのものが失敗した場合(非0で返る)は、失敗した側の削除(8-1 または 8-2)を
     行わずに続行し、引けなかったことを表示する**(契約 `CTR-cli-container`「エラーケース」。
     削除の失敗とは別で、**0件で返ったことと問い合わせが失敗したことを同一視してはならない**。
     推測で削除しない)。**片方だけが失敗したときは、成功した側の削除はそのまま行う**
     (コンテナ側が失敗したらネットワーク側は削除しない — 使用中で必ず失敗するため)。
     **8-3 の列挙は必ず実行する**: 手順6・7 で消えた compose 資源の名前はこの1つの列挙にしか
     出ないので、飛ばすと `FR-env-01` 受入基準26 を満たさない。
   3. **削除に成功したセッション由来の資源の名前を、種別(コンテナ / ネットワーク)つきで
      1行ずつ表示する**(`FR-env-01` 受入基準26)。**手順6・7 で消えた compose コンテナと
      compose 既定ネットワークもこの列挙に含める**(どちらも用語集の「セッション由来の資源」で
      あり、経路が違うだけである)。**合計が0件なら何も表示しない**(同27)。
      **同じ資源が手順6 と手順8-1 の両方で消えることはない**。理由は列挙のタイミングである:
      手順8 の所有者ラベルによる列挙は**手順6・7 が compose 資源を消し終えたあとに行う**ので、
      既に消えた資源はそもそも列挙に現れない。**列挙を先に取る形へ変えるとこの保証は崩れる**
      (存在しない資源への `docker rm -f` は失敗し、失敗は握られずに「削除できませんでした」と
      表示される)。
   4. **削除に失敗した資源は握って続行する**(`FR-env-01` 受入基準24)。失敗した名前は表示する。
   - **名前付きボリュームとイメージは対象にしない**(`D0-env-05` 項2)。
   - 手順6 の compose コンテナとは**対象が重なりうる**(compose 経由で作られたコンテナも所有者ラベルを
     持つ)。ただし**二重削除は起きない**: この列挙(`claude-dev:1639`)は手順6 の削除(`:1620`-`:1625`)
     より後に `docker ps -a --filter label=...` を引くため、先に消えたコンテナは結果に現れない。
9. **macOS 版のみ**: `stop_ssh_bridge <NAME>` で当該プロジェクトの socat ブリッジを停止する
   (専用 ssh-agent は鍵を保持するため残す)。`MODULE-cli-common-dev-agent-path` で
   `.bridge.pid` / `.bridge.port` の位置を得る。
10. `MODULE-cli-common-lock` で**共有資源単位**のロック(キー `shared`、操作名 `stop`)を取り、
   `stop_proxy_if_idle`(本機能に畳み込み)を実行する。**判定と削除を同一のロック区間の中で行う**
   ことで、他プロジェクトの `start` が docker-proxy を作った直後に消す競合を防ぐ。
   取得できなければ docker-proxy には触れず、その旨を表示する(手順3〜9 は済んでいるので
   全体は失敗させない)。
11. 遊休判定は次のとおり行う(`FR-env-01` 受入基準9 / 契約の「遊休判定」)。
   - **`claude-dev-net` に接続している稼働中コンテナ**を列挙する
     (`docker network inspect claude-dev-net` の接続コンテナと `docker ps` の稼働集合の積)。
   - そこから**名前が `claude-dev-docker-proxy` のもの**と**名前が `fwd-` で始まるもの**を除く
     (どちらも本システムが決めた固定名・固定接頭辞なので、ラベルの有無に依存しない)。
   - 残りが**0件のときだけ** `MODULE-cli-common-is-running` で docker-proxy の稼働を確かめ、
     `docker rm -f` する。**共有ネットワーク `claude-dev-net` は削除しない**(`stop` は
     `D0-env-05` 項2 のとおり共有ネットワークを残す。削除するのは `reset` だけである)。1件以上残るなら docker-proxy を残し、**残した理由(稼働中のコンテナ名)を
     表示する**。
   - **この判定を手順8 より後に置くのは固定の要件である。** 手順8 で消える資源が
     `claude-dev-net` に接続していた場合、順序が逆だと**自分のセッションが作ったコンテナを理由に
     docker-proxy を残し続ける**(数え落としではなく数え過ぎの側だが、遊休のはずの proxy が
     永久に回収されない)。
   - **`docker ps --filter ancestor=<イメージ>` を判定に使わない。** イメージを再ビルド・再取得すると
     それ以前に起動したコンテナを数え落とし、稼働中の他プロジェクトから Docker が使えなくなる。
   - **問い合わせが失敗したら(ネットワークが存在しない / `docker` が応答しない)、遊休でないと
     判定して docker-proxy を残す**。判定できなかったことを表示する(安全側へ倒す。
     契約の「エラーケース」)。
12. 取得したロックを解放する(`trap` により異常終了時も解放される)。

## 呼び出され方

- 契機: 利用者が `claude-dev stop [NAME]` を実行したとき。
- 前提条件: なし(未起動でもエラーにしない)。
- 引数:

| 引数 | 型 | 必須 | 実装が行う検証 | 受理/拒否と結果 |
|---|---|---|---|---|
| `NAME` | 文字列 | 任意 | 非空かどうかに加えて、**明示指定のときだけ受理する文字集合 `[A-Za-z0-9._-]` を検査する**(ロックキー=パス要素になるため。`FR-env-01` 受入基準18) | 非空かつ受理する文字だけならその文字列をコンテナ名として使う。**受理できない文字を含むならロックを取る前に何も削除せず終了コード 1**。省略・空文字ならカレントディレクトリ名を小文字化し `[a-z0-9._-]` 以外を `-` に置換した値を使う(この経路は既に受理する文字集合に収まるので検査しない) |
| 第2引数以降 | — | — | — | **黙って無視する** |

**`NAME` の境界値の実際の扱い**(検証が無く、名前の文字列一致だけで対象を決める):

| 入力 | 実際の結果 |
|---|---|
| 実在するコンテナ名 | 停止・削除して `✅ <name> を停止しました` |
| 実在しない名前・綴り違い・大文字を含む名前 | `ℹ️ <name> は存在しません` と表示して**終了コード 0**(綴り違いと本当に無い場合を区別しない) |
| compose 名として衝突する名前 | 一意化(`DSN-env-03`)の導入後に残るのは**先頭6桁のハッシュが衝突したときだけ**である(同時に 100 プロジェクトで約 0.03%。`docs/pendings.md` P-005)。一意化より前の欠陥そのものは解消済みである |

- 認可: CLI を実行できるホストユーザ。

## 連携先と連携内容

### MODULE-cli-common-lock

- 何のために呼ぶか: `start` との競合(起動直後のコンテナを消す)と、他プロジェクトの `start` との
  競合(作られた直後の docker-proxy を消す)を防ぐため。プロジェクト単位を手順2 で、
  共有資源単位を手順10 で取る(取得順は契約が定める固定順)。
- 何を渡すか: キー(コンテナ名 / `shared`)と操作名 `stop`。 / 何を受け取るか: 終了ステータス。
- **失敗したときどうなるか**: **プロジェクト単位が取れなければ何も削除せずに非0で終わる。**
  共有資源単位が取れなければ docker-proxy に触れずに続行する(手順3〜9 の後片付けは完了している)。
  **セッション由来の資源の削除(手順8)はプロジェクト単位のロックの中で行う**ので、
  共有資源単位が取れなくても実行済みである。

### MODULE-cli-common-container-name

- 何のために呼ぶか: 停止対象・compose プロジェクト名・**ロックキー**の決定。 / 何を渡すか: なし。 / 何を受け取るか: コンテナ名。
- **失敗したときどうなるか**: 想定されない。

### MODULE-cli-common-container-exists

- 何のために呼ぶか: 停止中の残骸も削除対象に含めるため。 / 何を渡すか: コンテナ名。 / 何を受け取るか: 終了ステータス。
- **失敗したときどうなるか**: 削除がスキップされ残骸が残る。次回 `start` が消す。

### MODULE-cli-common-is-running

- 何のために呼ぶか: 遊休と判定したあと、docker-proxy 自身が稼働しているかを確かめるため。
  **Claude コンテナの数を数えるためには使わない**(数え方は手順11 のネットワーク接続で行う)。
- 何を渡すか: docker-proxy のコンテナ名。 / 何を受け取るか: 終了ステータス。
- **失敗したときどうなるか**: 非稼働と判定され、proxy の削除がスキップされる(害はない)。

### MODULE-cli-common-dev-agent-path

- 何のために呼ぶか: macOS の socat ブリッジの PID / ポートファイルの位置を得るため。
- 何を渡すか: コンテナ名と種別(`bpid` / `bport`)。 / 何を受け取るか: ファイルパス。
- **失敗したときどうなるか**: 未知の種別なら空パスとなり、ブリッジ停止がスキップされる(ブリッジが残る)。

### MODULE-cli-common-compose-project-name

- 何のために呼ぶか: 削除対象の compose 資源を引く一意化名を**`start` と同じ関数で再計算する**ため
  (手順6)。あわせて旧い名前(ハッシュ無し)の案内にも使う(手順6・`claude-dev:1615` / `:1692`)。
- 何を渡すか: コンテナ名 `NAME` と、手順4 で読んだ `claude-dev.project-dir` の値。
  **旧い名前の案内はコンテナ名だけで作れる**ので、起動元ディレクトリを読めなくても出せる。
- 何を受け取るか: 一意化名 `<正規化名>-<6桁>` と、旧い名前 `<正規化名>`。
- **失敗したときどうなるか**: ハッシュが空になる経路では `start` 側も同じ値になるため、
  この機能から見た食い違いは起きない(別ディレクトリとの衝突は残る)。

### MODULE-cli-common-container-project-dir

- 何のために呼ぶか: compose 一意化名のハッシュ源と、所有者ラベルの照合値を得るため(手順4)。
  **本体コンテナの削除より前に呼ぶ**(削除するとラベルが失われる)。
- 何を渡すか: コンテナ名。
- 何を受け取るか: 起動時のホスト側の絶対パス、または空文字列。
- **失敗したときどうなるか**: 空文字列が返る。**手順6・7 の compose 片付けと手順8 の
  セッション由来の資源の片付けを行わず**、残っている可能性と手動の片付け方を表示して続行する
  (`FR-env-01` 受入基準21・23)。推測した値で削除すると別ディレクトリ・別セッションを巻き込む。

### MODULE-cli-common-net-other-running-containers

- 何のために呼ぶか: docker-proxy を止めてよいかの遊休判定に使う集合を得るため(手順11)。
- 何を渡すか: なし(対象ネットワークは定数)。
- 何を受け取るか: `claude-dev-net` に接続している稼働中のコンテナ名(固定名 `claude-dev-docker-proxy`
  と固定接頭辞 `fwd-` のものを除いたもの)。空なら遊休である。
- **失敗したときどうなるか**: 非0が返る。**遊休でないと判定して docker-proxy を残し**、
  判定できなかったことを表示する(安全側)。

### MODULE-cli-common-spawned-resources

- 何のために呼ぶか: セッション由来の資源(コンテナ → ネットワークの順)を列挙するため(手順8-1・8-2)。
- 何を渡すか: 種別(`container` / `network`)と、ラベルフィルタ式
  `claude-dev.owner-project-dir=<手順4 で読んだ絶対パス>`。
- 何を受け取るか: 資源の名前を1行ずつ。
- **失敗したときどうなるか**: 非0が返る。**失敗した側の削除を行わずに続行し、引けなかったことを
  表示する**(0件と区別する)。コンテナ側が失敗したらネットワーク側も削除しない
  (使用中で必ず失敗するため)。

## 戻り値・副作用

| 種別 | 内容 |
|---|---|
| 戻り値 | 既定は **0**(対象が存在しない場合も 0)。**この機能が明示的に `exit 1` するのは**「`<name>` が受理できない文字を含む」と「プロジェクト単位のロックを取得できない」の2つ。**これとは別に、本体コンテナと docker-proxy の削除だけは失敗を握らないので、`set -e` により `docker` の終了コードをそのまま返して終わる経路がある**(多くの場合 1 だが、`docker` の返す値による)。**130**: `acquire_lock` を**呼んだ後**に `INT` / `TERM` を受けた。`trap '_release_all_locks; exit 130' INT TERM` は**取得を試みる前**に張られる(`claude-dev:452` / `claude-dev-mac:517`)ので、**取得に失敗して 1 で終わる経路も、終わるまでは 130 の区間**である。加えて**本体コンテナの削除と docker-proxy の削除は失敗を握らない**(どちらも `docker rm -f` に `\|\| true` が無く `set -e` により非0終了する)。中継コンテナ・compose コンテナ・compose ネットワーク・**セッション由来の資源**の削除は握って続行する(`FR-env-01` 受入基準11・24) |
| 永続化 | コンテナ `<name>` と `fwd-<name>-*` を削除。**compose の一意化名 `<正規化名>-<起動ディレクトリ絶対パスの SHA-256 先頭6桁>`** を持つ compose コンテナと、compose ネットワーク `<一意化名>_default` を削除。**ラベル `claude-dev.owner-project-dir=<起動ディレクトリの絶対パス>` を持つコンテナとネットワーク(セッション由来の資源)を削除**。遊休のときだけ `claude-dev-docker-proxy` を削除。**共有ネットワーク `claude-dev-net`・名前付きボリューム・イメージ・旧い名前の compose 資源・所有者ラベルを持たないセッション由来の資源は削除しない**。ロックのシンボリックリンク `${HOME}/.claude-dev/locks/proj-<name>.lock` と `shared.lock` を作成・削除する。macOS では `~/.claude-dev/agents/<name>.bridge.{pid,port}` を後始末する |
| 発火するイベント | なし |
| ログ | 標準出力へ停止結果・管理ラベルが無い場合の通知・compose とセッション由来の資源の片付けを行わなかった理由・旧い名前の compose 資源の案内・**削除したセッション由来の資源の名前(種別つき。0件なら出さない)**・docker-proxy を残した理由。ロックの取得失敗と残骸の引き継ぎ、**セッション由来の資源の削除に失敗した名前**は stderr |

### 並行性

**プロジェクト単位のロックで `start` と直列化し、共有資源単位のロックで遊休判定〜docker-proxy
削除の区間を保護する**(`CTR-cli-container` の「排他(ロックキー)」)。**待たない**ので、
取得できなければ理由を表示して終わる。

| 同時に起きること | 実際の結果 |
|---|---|
| 同じ対象に `stop` を2つ | **後発はプロジェクト単位のロックを取得できず、何も削除せずに終了コード 1 で終わる**(先発が終わってから再実行すればよい) |
| `stop` と `start`(同じディレクトリ) | **同じキーのロックで直列化される**。後発は取得できずに終了コード 1。**起動直後のコンテナが消える経路は閉じている** |
| `stop` と他プロジェクトの `start` | **遊休判定から docker-proxy 削除までを共有資源単位のロックの中で行う**。`start` は認証コピーからコンテナ作成の確定まで同じキーを保持するので、**判定の直後に作られた proxy を消す競合は閉じている**。ロックを取れなかった場合は docker-proxy に触れずに続行する |
| `stop` と、そのセッションの中で走っている `docker run` | **保護されない。** ロックはホスト CLI のプロセス間だけで有効で、コンテナ内の Docker クライアントは対象外である。手順8 の列挙の直後に作られたコンテナは消し残る(次回の `stop` が回収する) |
| `stop` と他セッションの `stop` | **セッション由来の資源は所有者ラベルで絞るので互いに干渉しない**(同じ絶対パスを2つのセッションが同時に使う経路は `start` の同名衝突拒否で閉じている) |
| `stop` と `forward` | 中継コンテナを `fwd-<name>-*` の一括削除で消すため、`forward` が直後に作った中継が消える(またはその逆)。**`forward` はロックを取らない**ので保護されない。害は「フォワードが無い」だけで、`unforward` と同じ状態になる |
| 利用者が直接 `docker rm -f` する | **保護されない**(ロックはホスト CLI のプロセス間だけで有効) |

**順序**: 名前の検証 → プロジェクト単位のロック → 中継コンテナ → **管理ラベルの読み取り** →
本体 → compose コンテナ → compose ネットワーク → **セッション由来の資源(コンテナ → ネットワーク)**
→(macOS)ブリッジ → 共有資源単位のロック → 遊休判定と docker-proxy の順に片付ける。
**この順序は固定**で、とくに次の2つは動かしてはならない。

1. **管理ラベルの読み取りは本体削除より前**(削除するとハッシュ源と照合値が失われる)。
2. **セッション由来の資源の削除は遊休判定より前**(逆だと自分が作ったコンテナを数えて
   docker-proxy を残し続ける)。

**本体の削除と docker-proxy の削除に失敗した場合はそこで非0終了して後続に進まない**(`set -e`。
docker-proxy の削除は最後の手順なので、そこで止まっても後続の片付けは残らない)。
それ以外の削除は失敗を握って後続を続ける(`FR-env-01` 受入基準11・24)。

## 異常系

| 条件 | 実際の振る舞い | 呼び出し元への影響 |
|---|---|---|
| **引数 `NAME` が `[A-Za-z0-9._-]` 以外を含む** | **何も削除せず**、受理できない文字を含むことと受理する文字集合を stderr へ出して `exit 1`。**ロックも作らない** | 削除は一切起きない(`FR-env-01` 受入基準18) |
| **プロジェクト単位のロックを取得できない** | 保持している操作名と PID、再実行の方法を stderr へ出し、**何も削除せずに** `exit 1` | `start` と競合しても起動直後のコンテナを消さない(受入基準16) |
| **ロックが存在しないプロセスに保持されたまま残っている** | 引き継いだ旨を stderr へ出して処理を続行する | 永久に取得できない状態にならない(受入基準17) |
| 対象が存在しない | 「存在しません」と表示して続行し **0** で終わる。`fwd-*` の片付けと遊休判定はそのまま行う | なし(受入基準8) |
| **対象が `claude-dev.project-dir` ラベルを持たない、または既に存在しない** | **compose 資源の削除も、セッション由来の資源の削除も行わない。** どちらもこのラベルの値を必要とし、推測して削除すると別ディレクトリ・別セッションを巻き込むため。残っている可能性と手動の片付け方(`docker ps --filter label=claude-dev.role=spawned` で確認)を表示して続行する | compose 資源とセッション由来の資源が残りうる(受入基準21・23) |
| **旧い名前(ハッシュ無し)の compose 資源が残っている** | **削除しない。** 残っていることと確認・手動削除の方法を表示して続行する | 旧い資源は手動で片付ける(受入基準20) |
| compose ネットワークが他から使用中 | `docker network rm` が失敗するが握って続行する | ネットワークが残る(受入基準11) |
| **セッション由来のコンテナの削除に失敗した** | **握って続行する。** 失敗した名前を stderr へ出す | そのコンテナが残る(受入基準24)。次回の `stop` が回収する |
| **セッション由来のネットワークが使用中で削除できない** | **握って続行する。** 失敗した名前を stderr へ出す | ネットワークが残る(受入基準24)。所有者ラベルを持つので次回の `stop` が回収する |
| **compose 既定ネットワーク `<一意化名>_default` の削除に失敗した**(手順7) | **握って続行するが、失敗した名前は表示しない**(削除に成功したときだけ列挙へ積む実装であり、所有者ラベル経由のネットワークとは扱いが違う) | ネットワークが残り、利用者はそれに気づけない。`docs/issues/088` が追跡する |
| **セッション由来の資源が1件も無い** | **何も表示しない**(受入基準27) | なし |
| **セッション由来の資源を引く問い合わせが失敗した**(`docker ps` / `docker network ls` が非0) | **手順8 の削除を行わずに続行する。** 引けなかったことを表示する(安全側。0件と区別する) | 資源が残りうる。次回の `stop` が回収する(契約「エラーケース」) |
| **共有資源単位のロックを取得できない** | **docker-proxy に触れずに続行する**(全体は失敗させない)。触れなかった旨を表示する | proxy が残る。次回の `stop` が回収する |
| **遊休判定の問い合わせが失敗した**(ネットワークが無い / `docker` が応答しない) | **遊休でないと判定して docker-proxy を残す**。判定できなかったことを表示する | 安全側に倒れる(契約「エラーケース」) |
| **`claude-dev-net` に接続している稼働中コンテナが残っている** | docker-proxy を残し、**残した理由(コンテナ名の一覧)を表示する** | 他プロジェクトの Docker アクセスが維持される(受入基準9) |
| 本体コンテナの削除に失敗した | `set -e` によりその場で非0終了する(`docker rm -f "$NAME"` に `\|\| true` が無い) | 後続の片付けが行われない |
| **遊休と判定したあとの docker-proxy の削除に失敗した** | `set -e` によりその場で非0終了する。**失敗を握らないのは、この1件と本体コンテナの2つだけである** | 最後の手順なので、後続に残る片付けは無い。共有資源単位のロックは `trap` が解放する |
| 引数 `NAME` に実在しない名前を渡した | 「存在しません」と表示して 0 で終わる。**綴り違いと本当に無い場合を区別しない** | 利用者は停止できたと誤解しうる |
| VM モードのセッション | compose もセッション由来の資源もゲスト内 Docker で完結し、ホストの Docker に現れないため手順6〜8 の対象外 | なし |

## 既知の制限

| 制限 | 影響 | 関連 issue |
|---|---|---|
| **compose 既定ネットワークの削除失敗を表示しない** | `<一意化名>_default` は削除に成功したときだけ列挙へ積むため、使用中などで消えなかったことが利用者に伝わらない(所有者ラベル経由のネットワークは失敗も表示する) | `docs/issues/088` |
| **一意化名が導入される前に作られた compose 資源は旧い名前(ハッシュ無し)を持つため片付けられない** | 移行期のあいだ、旧い compose 資源は手動で削除する必要がある(表示で気づける) | なし(閾値の外: 表示で気づける) |
| **compose 一意化名のハッシュ衝突を検出しない** | 異なる絶対パスの先頭6桁が一致すると、一方の `stop` が他方の compose 資源を削除しうる | `docs/pendings.md` **P-005**(2026-08-04 に人間が受容) |
| **`claude-dev.project-dir` ラベルを持たない対象では compose もセッション由来の資源も片付けられない** | 管理ラベルが付く前に起動されたコンテナを `stop` すると、両方が残る | なし(閾値の外: 残ることと手動手順を**表示する**ので気づける) |
| **所有者ラベルが付く前に作られたセッション由来の資源は片付けられない** | `DSN-env-04` の導入より前にコンテナ内から `docker run` で作られたコンテナとネットワークは、所有者を示す印を持たないため対象外である。**利用者への表示も行わない**: 印が無い以上「そういう資源が存在するか」を本システムが知る手段が無く、当てのない警告しか出せないため(`D0-env-08` 項8)。利用者は `docker ps -a` で自力で見つけて手動で消す | なし(閾値の外: **00 が「そう決めた」と明示しているもの**。`D0-env-08` 項8) |
| **解釈できないリクエストボディで作られた資源は片付けられない** | docker-proxy はボディを解釈できない要求を検査せず中継するため、所有者ラベルを注入できない(`FR-env-07` 受入基準8・12)。その資源は所有者を持たず、対象から外れる | `docs/issues/005-modify-docker-proxy-relays-unparseable-bodies.md`(同じ根の残存リスク) |
| **遊休判定が `claude-dev-net` への接続で行われるため、利用者がコンテナ内から起動した資源も「稼働中」に数える** | docker-proxy が回収されにくくなる。**過剰に数える=消さない側**なので `FR-env-01` 受入基準9 は破らない。**手順8 で自セッション分は先に消えるので、残るのは他セッション分と所有者ラベルを持たない分だけである** | なし(2026-08-04 の決定シート #1 で人間が案A=現状のままと裁定) |
| **停止中のコンテナは `claude-dev-net` の接続情報に現れない** | 停止中のコンテナがあっても遊休と判定する | なし(閾値の外: 停止中のコンテナは Docker を使っておらず、proxy を消しても壊れない) |
| **共有ネットワーク `claude-dev-net` が存在しないと、遊休判定は「問い合わせ失敗」になる** | ネットワークを手で消したあとは docker-proxy が回収されない(安全側に倒れる) | なし(閾値の外: 契約「エラーケース」が明示している) |
| **所有者ラベルを利用者がホスト側から手で付けられる** | `docker run --label claude-dev.owner-project-dir=<任意>` はホストの Docker CLI が直接叩くので docker-proxy を通らず、上書き(`DSN-env-04`)を受けない。そのラベルを持つコンテナは `stop` / `reset` の削除対象に入る | `docs/pendings.md` P-007(この範囲に入ることを受容した記録。前提は `SR-05`) |
| **ロックはホスト CLI のプロセス間でしか有効でない** | 利用者が直接 `docker rm -f` / `docker run` する経路、別ホストから同じデーモンを操作する経路、**および `stop` の実行中にコンテナ内から作られた資源**は防げない(後者は次回の `stop` が回収する) | なし(契約 `CTR-cli-container`「ロックが守れない範囲」が明示) |
