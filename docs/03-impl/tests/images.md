## テスト設計の判断

<!-- このファイルのテストの作り方(DS-01 で AI が決めた部分)の理由を置く。何を検証するかは 01 が正である。 -->

- **自動テストランナーを割り当てないのは、このファイルの判断ではない。** イメージのビルドと GHCR 配布はコールグラフに入口を持たずモジュールにしていないため(`DSN-mod-05`)、テストの割り当ては `DSN-test-01` の既定(Go の docker-proxy に集中させ、それ以外は実機確認)と `SR-32` に従うだけである。**確認の手順そのものは上の「未検証(テスト未実装)の全件」が持つ**(このファイルではそこが唯一の手順の在り処である)。
- [DS-01] `FR-env-13` の観測点を、**確認用の実行物を実際に実行し、固定の出力と終了コードを見ること**にする — 理由: 存在と権限だけを見る手順(`command -v` と `ls -l`)では、**壊れた実行形式・別アーキテクチャ向けのバイナリ・動的ローダーの欠落**でも通過してしまい、`FR-env-13-1` と `AC-07` が求める「起動できる」を検証しない。出力を固定した確認用の実行物を自分で用意すれば、同梱物ごとに終了コードの意味が変わる問題も同時に避けられる。**実行には `--entrypoint /bin/sh` を必ず挟む** — このイメージの ENTRYPOINT は渡したコマンドを実行せず待機に入るので、挟まないと手順が何も観測しないまま固まる / 見直す条件: 同梱物を実行せずに起動可否を判定できる手段ができたとき
- [DS-01] 確認に使う実行物は**その場で作り、リポジトリにコミットせず、確認後に消す** — 理由: このタスクが納めるのは器と仕組みだけで、同梱物そのものは保守者が置く(`RQ-dist-02`)。確認用のファイルをコミットすると、意図しないものが公開イメージへ焼かれる(`D0-dist-05` 項2 は一度公開したものを回収できないと述べている) / 見直す条件: 常設の同梱物ができ、その存在自体を回帰確認したくなったとき
- [DS-01] `FR-env-13-3` の確認を**1つのアーキテクチャのビルドだけで両方向とも行う** — 理由: 「用意したアーキテクチャのものが入る」と「用意していないアーキテクチャのものが入らない」は、片方のアーキテクチャのイメージ1つで同時に観測できる。両アーキテクチャの機材を揃える必要が無くなり、**手順が実施されないまま残る**事態(`docs/pendings.md` P-006 が macOS 版について記録している型)を避けられる。**残る限界は手順18 に明記した** — 実装がアーキテクチャ名を固定していた場合はこの片側の観測では検出できない / 見直す条件: アーキテクチャの判定手段が変わり、ビルドした側のイメージからは判定結果を観測できなくなったとき
