# AI駆動開発ドキュメント体系 — 最終設計まとめ

本書は、4階層ドキュメント駆動開発の体系(本キット)の最終仕様と、設計判断の経緯をまとめたものである。
対象は数人月〜数十人月規模のシステム開発、実装エージェントは Claude Code を想定する。

**読者は人間**(体系を深く知りたい人・メンテナ・疑問視する人)。AIの運用規範は CLAUDE.md・
commands・templates・steering にあり、AIが本書を日常的に読む必要はない。本書はそれらの
「解説」であり、規範と食い違う記述があれば規範が正(食い違いは本書のバグとして修正する)。

## 1. 体系の一言要約

**人間は「意図」だけを表明し(要求を書く・変更を説明する・質問に答える)、AIがドキュメントと
コードを前進させ、品質は機械的な検証ゲートが担保する。** ドキュメントは常に「システムの現在
あるべき姿」を表す Single Source of Truth であり、コードと一致していることが不変条件である。

## 2. 設計原則

1. **仕様ドキュメント(4階層)はSSOT。** `docs/` 直下の 00〜03 は常に現在あるべき姿を表し、
   変更時はインプレース更新する。実行計画・タスク・TODOを書かない。
2. **階層ごとに粒度が異なり、分割単位(モジュール)は設計の成果物である。** 要求を書く時点で
   分割を知っている必要はない。分割は 02-design で定義され、03-impl と実装がその単位で
   ファンアウトする。
3. **役割の三分離。** specs(現在の姿)/ histories(変更の経緯)/ tasks(AIの作業状態)。
   それぞれ性質が異なる: インプレース更新 / 追記専用 / 進行中のみ存在し完了時削除。
4. **品質ゲートは人間の承認ではなく検証。** 人間のレビューは任意(見たいときだけ見る)。
   /doc-check が唯一の検証者であり、整合性チェック一式の通過がゲートとなる。
5. **検証状態は宣言せず、証拠から導出する。** statusフィールドは存在しない。検証の証拠
   (verifiedブロック)と現在のversionの照合だけが状態を決め、上流の変更で自動的に失効する。
6. **人間の操作は定型4スキルと意図の表明のみ。** 固有名(モジュール名・slug)を覚えて
   指定する必要はなく、対象の判定はAIが行う。

## 3. ドキュメント体系

```
project-root/
├── CLAUDE.md                  # 運用ルール(常時読込。約90行のルールブック兼インデックス)
├── docs/
│   ├── 00-requests/           # 要求パッケージ(WHY+判断台帳): request.md(人間の言葉)・
│   │                          # decisions.md(決定/委任/要確認)・glossary.md・acceptance.md・examples/
│   ├── 01-requirements/       # 要件(WHAT): 最初はcore.md 1つ。大きければ業務領域で分割
│   ├── 02-design/
│   │   ├── system.md          # 全体設計。★モジュール分割定義(この体系の要)
│   │   └── <module>.md        # モジュール詳細設計(任意)
│   ├── 03-impl/
│   │   └── <module>.md        # 実装説明書: モジュールごと。実行計画ではなく実装内容の詳細記述
│   ├── histories/             # ドキュメント変更履歴(追記専用・フラット時系列)
│   │   └── YYYY-MM-DD-<slug>.md
│   ├── tasks/                 # AIの作業用タスク(進捗永続化+DoD。進行中のみ存在、完了時削除)
│   │   └── <作業slug>.md
│   ├── _steering/             # 共通ルール: product.md(概要・用語集) / tech.md(技術) / structure.md(構成・規約)
│   ├── _templates/            # 各ドキュメントのテンプレート(見出し構成と責務境界の唯一の基準)
│   │                          # _付き=仕様ドキュメント本体(00〜03等の成果物)ではなく、前提・ひな形の区別
│   └── WORKFLOW-GUIDE.md      # 運用ガイド(人間向け)
└── .claude/skills/<name>/SKILL.md   # スキル8個
```

### 各階層の役割と粒度

| 階層 | 役割 | 粒度 | 分割の根拠 |
|---|---|---|---|
| 00-requests | なぜ作るか(WHY)+先回りした判断。request.md は人間が思いの丈を書く(「やらないこと」必須)。decisions.md は判断を決定/委任/要確認に仕分けた台帳(委任=下流AIが聞かずに裁量判断してよい範囲の明示)。glossary/acceptance/examples が具体性を担う | システム全体1ディレクトリ(役割別の定型ファイル) | 機能では分割しない |
| 01-requirements | 満たすべき振る舞い(WHAT)。EARS記法の受け入れ基準+非機能6分類+ユースケース(UC-n。E2Eシナリオの導出元) | 全体1つ→業務領域で分割 | 業務構造 |
| 02-design | 実現する構造。アーキテクチャ・**モジュール分割定義**・契約・テスト戦略(3レベル方針・結合テスト担当・E2Eシナリオ一覧)・設計判断と理由 | system.md必須+詳細設計任意 | 設計判断そのもの |
| 03-impl | 実装内容の詳細な説明(ファイル構成・モジュール詳細・API・テスト対応表)。コードと常に一致 | モジュールごと+e2e.md(唯一の標準例外: E2Eシナリオ一覧に従う) | 02の分割定義に従う |

各階層は「何を決め、何を決めないか」の責務境界を持つ(例: 01はアーキテクチャに踏み込まない、
02は実装スニペットを書かないが契約は型つきで書く、03は要件・設計を蒸し返さない)。境界は
各テンプレート冒頭のコメントに明記されている。

### steeringの常時読込とその規律

steering 3ファイルは CLAUDE.md から @import され、**毎セッション必ずコンテキストに載る**
(分離はコンテキスト節約のためではなく、更新主体・記入者・変更管理が異なるためのガバナンス措置。
トークン量はCLAUDE.mdに直書きした場合と同じ)。常時読込に値するのは「全セッションで必要な前提」
(正確なコマンド文字列・命名規約・用語集)だからであり、遅延読み込みは読み忘れ事故と引き換えになる。
代償として肥大化が単調なコスト増になるため、「全セッションで必要なものだけを置き、状況依存の
詳細は02/03へ」を規律とし、月次棚卸しで守る。

### 汎用と固有の区別(キット更新の境界)

| 分類 | ファイル | キット改訂時 |
|---|---|---|
| **汎用**(方法論の一部) | CLAUDE.md / docs/_templates/ / .claude/skills/ / ガイド類(workflow-guide, onboarding, DESIGN, 各README) | 新版で上書きしてよい |
| **固有**(プロジェクトの資産) | docs/00〜03 / histories/ / tasks/ / **_steering/**(ひな形として出荷されるが初回記入以降は固有) | 絶対に触らない |

運用原則: プロジェクト固有の規約・制約は steering に書き、**テンプレート・スキルを直接改造
しない**(改造した瞬間そのファイルは固有になり、キット更新のたびに手動マージが必要になる。
方法論自体の改善はキット側に還元する)。CLAUDE.md がプロジェクト情報を含まずルールとインデックス
に徹しているのは、この境界を成立させるためでもある。

### UI設計の扱い

画面の分割・構成は構造であり、モジュール分割と同じく**02-designの成果物**。02のUIセクション
(必須。UIなしのシステムは理由を明記)に画面一覧・遷移・主要項目・状態を置き、これが画面構成の
SSOTとなる。**ピクセルレベルの見た目は文書で規定しない**: steeringのデザイン原則・トークンに
従いAIの実装に委ねる(テキストSSOTと外部デザインツールの二重化を避ける割り切り)。UI挙動は
01のEARS基準で、ルーティング・コンポーネント構成は該当モジュールの03-implで扱う。見た目の
検証は/doc-checkの対象外。

### histories と tasks

- **histories**: 1つの変更理由につき1エントリ。「変更理由/変更内容の要約/affected(更新した
  全ドキュメントのversion遷移)」のみを記録。タスク・進捗は書かない。追記専用で、確定した
  エントリは書き換えない(訂正は新エントリ)。初版(1.0.0)とPATCHのみの変更は記録不要。
- **tasks**: 役割は2つだけ——(1)セッションをまたぐ進捗の永続化(チェックボックス+進捗メモ)、
  (2)その作業の Definition of Done。人間の承認対象ではない使い捨ての足場で、完了時に削除する
  (記録はgitとhistoriesに残る)。1作業=1ファイル。
  **作業の単位は「実装が一度に完了・検証できる範囲」**とした: 変更起点なら1変更セットで1作業
  (影響範囲が複数モジュールに跨っても1つ。受け入れ基準が1組であり、モジュールごとに割ると
  どのファイルもDoDを満たせない状態が続く)、新規構築なら1モジュールで1作業(依存順に立ち上がるため、
  全モジュールを1作業にするとテストがgreenにならない期間が長すぎる)。
  ドキュメント生成の単位(層)とは意図的に一致させていない——`/gen` の1回の実行が複数の作業を生み、
  各作業のタスクドキュメントは03-implを書いた時点で作られる(`phase: ドキュメント` = 着手待ち。
  未決点と調査メモの置き場が必要だから)。作業が大きすぎる場合に作業を割ることは禁止で、
  02の分割定義の見直しを提案する(モジュール過大のシグナルであり、作業だけ割ると03-implと単位がずれる)。
  **1ファイルが決定→ドキュメント→実装の3フェーズを貫く**ため、進捗の永続化の一部として
  影響範囲(closure)・回答済み決定シート・未決点・質問キューもここに置く。これらは仕様ドキュメント
  ではない(作業状態であり、システムのあるべき姿ではない)。

## 4. 検証メカニズム(この体系の中核)

### 証拠と導出

検証状態を表すフィールドは存在しない。/doc-check がPASS時に書き込む**証拠**と、現在のversionの
**照合**だけが状態を決める:

```yaml
version: 1.3.0                 # MAJOR.MINOR.PATCH
verified:                      # /doc-check だけが書き込める
  at: 2026-07-09
  version: 1.3.0               # 検証した時点の自分のversion
  against:
    - doc: docs/00-requests/request.md
      version: 1.0.0           # 検証した時点の上流のversion
```

**検証済みの判定(唯一の規則)**: verifiedブロックが存在し、その version と自分の現在version、
against の各 version と上流の現在version が **MAJOR.MINOR部分で一致**すること。1つでも不一致
なら失効=未検証。失効の波及は下向きのみ(上流には及ばない)。

### versionの2層意味論

- **MINOR以上**: 意味に影響する変更(要件・契約・振る舞い・構造)。自分と下流の検証を失効させる。
- **PATCH**: 意味を変えない軽微修正(誤字・表記・書式)。検証を維持し、カスケードを起こさない。
  history記録も不要。
- 迷ったらMINOR(安全側)。

編集時にやることは「versionを上げる」だけ。statusの付け替えという操作自体が存在しない。

### カスケード制御(往復コストの主因への対策)

この体系の実運用コストの大半は「/doc-check を何度も打ち直す」ことであり、その多くは
**自分の修正が自分の合格証を壊す**ことによる自己誘発だった。4つの規則で抑える:

1. **1フェーズ1バンプ** — 1フェーズ内の複数回の編集でversionを上げるのは1回だけ。
2. **認証は最後** — 影響範囲の全versionが確定してから verified を一括で書く。書いた合格証が
   同じフェーズ内で壊れる状態そのものを作らない。
3. **ラン内収束** — そのランの修正で失効した下流はそのランの対象集合に加える。自分が壊した
   失効を残して終わるのは規範違反(人間への引き継ぎではなく欠陥)。
4. **差分検証** — 自分の本文が前回PASS時から無変更で、上流のversion移動だけが失効理由の場合、
   検証義務は「上流の**差分**×自分」に縮小する。差分が自分の参照範囲(トレーサビリティ表・契約・
   UC/AS/D-n引用・派生節)に届いていなければ、`against` の版のみ更新して合格証を維持する
   (バンプなし・history不要)。判定材料は history の affected のドキュメント別 `change:` 一行と
   `git diff`。特定できなければ安全側で全面検証。B・Cチェックを省けるのは、同じversionで既に
   認証済みかつ本文が無変更だからで、根拠のある縮小である。

### 増分検証

/doc-check は全ドキュメントの**フロントマターだけ**をスキャン(head/awk等で先頭ブロックのみ読む。
軽量)して状態を導出し、**本文の検証は未検証のものだけ**行う。読む範囲も限定される(対象+source
+steering、02検証時のみ01全ファイル、03検証時のみ契約と対象モジュールのコード)。
`full` 指定で全再検証(節目での実行を推奨)。

### 収束ループ(修正ステージ→認証ステージ)

1回の検証では取り切れず、修正が新たな不整合を生むため、/doc-check は**上限10周のチェック→修正
ループ**で収束させる(修正点がなくなり次第、上限を待たず終了)。構造は2ステージ:

- **修正ステージ**: まず全チェックを影響範囲に**通しで**走らせて指摘を全部集める(読みながら
  直すと、03で見えた指摘の真の起点が01であることが隠れる)。次に各指摘を**起点層に振り直し**、
  00→03を1回下って直す。この間バンプはしない。自動修正してよいのは意味保存または上流から
  機械的に導出できる修正のみ(表記統一・EARS整形・フロントマター機械誤り・カバレッジ表の
  欠落補完・必須セクション補完・上流が既に答えている未決点)。加えて**委任枠内の判断は決める**
  (D-n+フィードバックログに記録)。それ以外の仕様判断は収集する。
- **認証ステージ**: 修正が止まってから、各ドキュメントのバンプを1回行い、最後に verified を
  一括で書く。締めに「自分の修正が原因の失効が残っていないか」を再導出して確認する。

人間への質問は**フェーズ末に1枚の決定シートとして一括提示**する(途中で1件ずつ止めて聞かない。
それが人間を端末に張り付かせる原因だった)。MINOR修正が入ったらhistoryに1エントリ記録。
同一セッションでの修正+再検証は独立性を弱めるため、節目にはフレッシュセッションでの
`/doc-check full` を推奨する。

### 検証内容(4分類)

- **A. 縦の整合性**: 00→01のカバレッジと混入・ユースケースの網羅(全機能要件がいずれかのUCに登場)、
  01→02のカバレッジ・分割定義・steering違反・テスト戦略の充足(結合テスト担当の全契約割当、
  E2Eシナリオ一覧の全UCカバー)、02→03の分割定義との対応・契約一致・受け入れ基準→テスト割当・
  E2Eシナリオ→e2e.mdテスト割当
- **B. 03-impl⇄コードの一致**: ファイル構成・公開I/F・環境変数・テストの実在(e2e.md含む)
- **C. 品質**: 曖昧語の残存、EARS記法とテスト可能な粒度、未解決事項、フロントマター妥当性と照合
- **D. 実装可能性(深度)**: 受け入れ基準・契約が正常系だけで終わっていないか(境界値・異常系・
  エラーケース・順序/冪等性)、そして**実装ドライラン** — コードを書かずに仕様だけでタスク分解と
  テスト一覧を導出し、「決めないと進めない点(未決点)」を全列挙する。未決点は
  (a)ドキュメント記載 (b)委任枠内で決定(D-n) (c)決定シートで人間に、のいずれかで必ず閉じ、
  **未決点が残る03-implはPASSしない=実装に入れない**

ドライランは2パスに固定する。**パス1はドキュメントのみ**(コード・テストを読まない。独立レンズも
同条件)で未決点を列挙し、**パス2で技術調査**を行う。順序が逆だとコードから答えを補ってしまい、
「決まっていないのに決まって読める文」を通してしまうため、この順序自体が検査の一部である。
両者は性質が違う: 未決点は**決めないと進めない**もの(ゲート)、技術調査事項は**調べれば分かる事実**
(ゲートではない)。後者はタスクドキュメントの「調査メモ」に置く — 仕様ドキュメントは
「システムのあるべき姿」であって調査の残骸の置き場ではなく、かつ実装フェーズが同じ調査を
やり直すのは純粋な無駄だから。

調査メモの位置づけは**派生キャッシュ**であり、SSOTではない。この体系のSSOTは仕様ドキュメント
(あるべき姿)とコード(実際の姿)の2つで、メモが持つのは「コードを読めば分かる事実」への索引に
すぎない。ゆえに各行に根拠(path:line)を要求し、矛盾時はコード/03-implを正とし、どのドキュメントの
`source:` にもしない。陳腐化を許容できるのは、行が安く再確認できる形に制約されているからである
(1行1事実のポインタ表。長い引用や設計案を書き始めた時点で第二のSSOTになる)。
置き場をタスクドキュメント内の1セクションにしたのは、`docs/tasks/` にファイルが存在すること自体が
「作業進行中」の判定に使われており、兄弟ファイルを置くと進行中作業の誤認を招くため(1作業=1ファイルを
崩さない)。完了・中断時には削除するが、その前に**昇格の振り分け**を必須にした: モジュールの恒久的
事実→03-impl、横断的な技術前提→steering/tech.md への追加提案、非自明な学びや罠→docs/knowledge/、
残骸→破棄。キャッシュを永続化して第二のSSOTを作るのではなく、恒久的価値のあるものだけを
既存の置き場へ移すのが、この体系で唯一整合する扱いである。

Dが必要なのは、A〜Cを通る「もっともらしいが浅い」文書が実装フェーズで穴を露呈し、層をまたぐ
手戻りを生んでいたため。曖昧語スキャン(C)では「決まっていないのに決まっているように読める文」を
捕まえられない。捕まえる唯一の実効手段が、実装を試して詰まる点を数えることである。

### 独立監査(Codex / フォールバックはサブエージェント)

同じClaudeセッションが書き・直し・検証すると、作成時の前提と思い込みがそのままレビューに
持ち込まれる。これを補うため、**別モデルのCodexを独立監査者**として組み込む。

- 文書監査: `/doc-check` が自分のチェックの**前に** `/codex-audit docs` を呼び、読み取り専用
  (`--sandbox read-only --ephemeral`、ネットワークなし)でチェーンを独立監査させる。呼ぶ前に
  自分の指摘・修正方針・期待する結論を渡さないことが独立性の条件。
- 実装可能性(readiness): 同じ枠組みで**独立の実装ドライラン**を行わせ、未決点を列挙させる
  (`/codex-audit readiness`)。自分が書いた文章の浅さは自分では見えにくいため、独立レンズだけが
  挙げた未決点が最も価値の高い成果になる。
- **Codexが使えないときはフレッシュコンテキストのClaude Codeサブエージェントに同じ依頼を回す**
  (独立レンズを空にしない)。同一モデルゆえ盲点は共有するが、「その推論を見ていないコンテキスト」
  であることが独立性の実質の大半を担う。レポートではレンズを必ず区別し、サブエージェントの結果を
  Codex監査として扱わない。`full`・節目の検証でPASSを出す条件としては、Codexまたは人間の明示判断を
  要求する(弱いレンズで最上位のゲートを通さない)。
- QA: `/implement` Phase C が `/codex-qa` を呼び、Codex自身がE2Eを実行して失敗を適応的に調査し、
  green後にCDP探索的ブラウザテストを行う。実行と調査が同一セッションで連続するため、終了コード・
  trace・console・ネットワーク・データ状態を取りこぼさない。
- 権限の線引き: Codexは証拠を返すだけで、仕様ドキュメント・コード・`verified` を書かず、未決事項
  も決めない。裁定と修正はClaude、最終回帰ゲートはCI。未解決の重大度「高」はPASSと完了を阻止する。
- 分業の副作用として、重い読み取り・実行作業がClaudeのコンテキストから外れる(負荷分散)。

規範は CLAUDE.md の「External-agent delegation」節(不変条件7項)、手順と実行環境・段階導入は
`.claude/skills/codex-audit/SKILL.md`(§6〜§7)と `.claude/skills/codex-qa/SKILL.md`。

### 段階導入と評価指標

段階導入は「ゲートを増やしていく」設計であり、ゲートを外す設計ではない。**Phase 1(観測モード)**:
未解決の重大度「高」はこの段階でもPASSを阻止する(不変条件はフェーズ設定で無効化できない — 既定が
Phase 1 なので、ここを緩めると出荷時の既定でゲートが消えてしまう)。Phase 1 の意味は、それ以上の
ブロック条件を足さないこと(中・低は既存基準、最終監査は必須化しない)と、誤検知率・追加検出・
追加所要時間を計測することにある。QAはCodexの調査をClaude自身の読みと並行評価し(同じChromeは
同時操作しない)、CDP探索は代表1〜2画面に限定。**Phase 2(高重要度ゲート)**: 未解決の重大度「高」だけがPASSを阻止し、`full`・節目では最終監査を
必須化。E2Eの一次適応調査と2段のE2E実行をCodexへ移管し、UI変更と重要UCではCDP探索を必須化。
**Phase 3(安定運用)**: 実行種別ごとの呼び出し回数と失敗ポリシー、レポート形式、排他制御、証拠保存期間を
確定し、複数プロジェクトで有効性が確認された規則だけを汎用キットへ還元する。

判断材料を作るため、最初の5件程度はPhase 1で回し、次を記録する(定量結果が出るまでモデルや推論設定を
変えない。比較可能性が失われる):

| 指標 | 定義 |
|---|---|
| 有効指摘率 | 指摘のうち修正または人間確認につながった割合 |
| 追加検出数 / 高重要度追加検出数 | Claude単独では見つからず独立レンズが見つけた指摘数 |
| 誤検知率 | 根拠付きで棄却された指摘の割合 |
| 監査成功率 / 追加所要時間 | 正常完了した割合と、検証時間の増加 |
| 収束影響 | 導入前後の check→fix 反復回数の差 |
| 原因分類的中率 / 最小再現成功率 / 調査時間 | QAレーンの調査品質 |
| 探索追加検出数 / 状態リセット成功率 | CDP探索の有効性と後始末の信頼性 |

Phase 2への移行は次が満たせたときとする(要点): 読み取り専用でCodexを起動でき、JSON Schemaに適合した
結果が返り、**ファイルを変更していないことを機械的に確認**でき、指摘を4分類に裁定でき、未解決の
重大度「高」がPASSにならず、`verified` をCodexが書けず、`full` の監査失敗でPASSが出ず、レポートに
監査結果と棄却理由が出ること。QA側は、既存ChromeへCDP接続でき、Claude/Codex/Playwrightの排他制御が
機能し、失敗時にtrace・video・screenshot・console・network・ログを収集でき、原因分類と最小再現手順を
含むレポートが返り、探索前後で専用シードを投入・リセットでき、プロダクト/E2Eコードが変更されていない
ことを確認できること。

### 明示された限界

1. 「versionを正しく上げる」規律に依存する。上げない編集、意味のある変更をPATCHと申告する編集は
   失効検出をすり抜ける(厳密化するなら内容ハッシュ方式へ強化可能)。
2. 検証の相当部分はAIの判断であり、網羅的な証明ではない。「検証済み」の意味は「/doc-check の
   チェック一式がこの版の組に対して通った」である。Codex独立監査は**自己レビュー性**を緩和する
   が、AIの判断であること自体は変わらない(別モデルの合議に近づくだけ)。誤検知の裁定コストも
   増えるため、Phase 1では観測モードで誤検知率を測ってからゲートを有効化する。
3. フロントマター抽出とversion照合は完全に決定的な処理なので、スクリプト化(AIの判断を挟まない
   機械実行)が信頼性強化の第一手となる。
4. 差分検証の「影響なし」はAIの判断であり、history の `change:` の具体性に依存する。曖昧な
   `change:` は判定不能=全面検証に落ちる(安全側)が、**誤って「影響なし」と判断すれば下流の
   不整合が合格証付きで残る**。ガードレールは、本文無変更であること・判定根拠(どの差分項目を
   なぜ届かないと見たか)をレポートに明示すること・1項目でも影響ありなら文書全体を通常検証に
   落とすこと。
5. 未決点ゼロは「AIが列挙できた未決点」に対するゼロであり、列挙漏れは残る。二重レンズ
   (自分+独立レンズ)はこれを緩和するが消さない。

## 5. スキル(10個)

| スキル | 役割 |
|---|---|
| `/setup` | 開始時の対話セットアップ(調査→確認方式で steering/ を生成。「未定」は正当な回答) |
| `/gen` | 次に作るべき**層**をAIが判定し、その層を1回のパスで生成(03は実装ドライラン込み。ファイル単位で止まらない) |
| `/change <変更内容>` | フェーズ1: 影響範囲の確定→決定シートで一括質問→タスク作成→全層を1回下って更新→history記録 |
| `/implement` | フェーズ3: 未決点ゼロを確認し、無人で実装→03-impl同期→締めの再検証1回→DoD実検証→タスク削除 |
| `/doc-check [module\|full]` | 唯一の検証者。修正ステージ(起点層で一括修正)→認証ステージ(最後に一括で証拠を書く)(新セッションでの実行推奨) |
| `/doc-status` | 全ドキュメントの検証状態(導出)と進行中タスクの一覧表示 |
| `/reverse-doc <module>` | 既存コードからの仕様逆生成(ブラウンフィールド導入用) |
| `/estimate-fp` | 仕様ドキュメントからのFP算出レポート(02完了で概算=NESMA、03完了で詳細=IFPUG準拠。導出値でありドキュメントに書かない) |
| `/codex-audit [docs\|diff\|readiness]` | 独立監査(読み取り専用)の実行と結果の受け渡し。readiness=実装ドライランのレンズ。Codex不在時はサブエージェントにフォールバック。裁定・修正・verified更新は行わない |
| `/codex-qa [対象]` | 独立QA: E2E実行→失敗の適応的調査→CDP探索的ブラウザテスト(サブエージェント・フォールバックあり)。コードは修正しない |

後者2つは委譲の手順書であり、通常は `/doc-check` と `/implement` が内部から呼ぶ。

スキル(10個)は体系の必須要素ではなく「手順のピン留め+コンテキスト経済性」のための最適化であり、
自然言語での依頼でもCLAUDE.mdのルールは適用される。品質を支えるのはCLAUDE.mdの原則と
テンプレートである。

実装形式は `.claude/skills/<name>/SKILL.md`(Claude Code ではカスタムスラッシュコマンドと
スキルが統合されており、`/name` で人間が起動できるほか、AIが必要と判断して自律起動することも
できる)。規律の担保はフロントマターの起動制限ではなく、**各スキル内のゲート手順(検証済み確認・
人間への合意取得・停止条件)と CLAUDE.md の規範**が担う。起動者が誰であってもゲートは省略されない。

## 6. ワークフロー

3フェーズモデル(1作業=決定→ドキュメント→実装、同席はフェーズ1だけ)が土台であり、以下の
フローはその具体形。フェーズを抜けて入り直さないこと、質問をまとめること、未決点ゼロを実装の
入場条件にすることが、往復コストの3つの主対策である。

### 新規開発

```
人間が00-requests/を用意する(request.mdは自分の言葉で。「やらないこと」必須。
上流の要求定義ファクトリーで作成するのが理想。decisions.mdの委任が問い合わせを減らす)
→ /gen(1回で1層まとめて生成。03は全モジュール+実装ドライラン)
→ /doc-check(その層を一括検証。合格証は最後に一括)
→ /gen → /doc-check → …(01→02で分割が決まる→03へ)
→ /implement(未決点ゼロを確認して無人実行。締めの再検証も内包)
```

### 変更(要件変更・機能追加・修正)

```
/change <変更内容>(複数まとめて渡してよい)
  → 影響範囲(closure)を00〜03で確定、起点階層を判定
     (起点判定: 目的・スコープ→00 / 振る舞い→01 / 構造・分割→02 / 実装詳細→03)
  → **決定シートを1枚提示**(この作業で聞く全件。推奨案と未回答時の既定つき)= 唯一の同席点
  → 起点から下流へ1回だけ下って全層更新、最後にバンプ1回、historyに記録(change:一行つき)
→ /doc-check(AIがfresh-contextサブエージェントとして自動起動。修正ステージ→認証ステージ。
   差分検証で不要な再読み込みを省く)
→ /implement(無人。作業slug=変更slug)
```

/change の対話は「(1)曖昧さの解消 (2)影響範囲への合意」を**1枚の決定シートに畳んだ**もので、
これが「変更が意図と合っているか」という機械検証できない唯一の確認を担う。個別diffへの承認は
取らない(方針合意+事後の差分サマリ。全diffの逐次承認は形骸化しやすく、同席時間だけが増える)。
対話中に別の変更を思いついたら言ってよく、まとめて1つの決定シート・1回の下降で処理する
(1変更理由=1historyエントリは常に維持)。

### その他のケース

| ケース | 扱い |
|---|---|
| 新モジュールが要る機能追加 | /changeが02の分割定義を変更 → /genが新03を生成 → 通常フロー |
| バグ(コードがドキュメント違反) | /change不要。数行なら直接修正(例外規定)、大きければ/implement |
| バグ(ドキュメント自体の誤り) | /change(誤りの階層が起点) |
| ドキュメントの誤字・表記 | PATCHを上げるだけ(/change不要・検証維持・history不要) |
| 既存コードに体系を導入 | /reverse-doc で変更するモジュールだけ直前に逆生成(一括逆生成はしない) |

## 7. 主要な設計判断とその経緯

議論を通じて確立・変更された判断の記録。

| 判断 | 採用した設計 | 却下した設計と理由 |
|---|---|---|
| 実装仕様書の性格 | 実装内容の詳細記述(03-impl)。コードと常に一致するSSOT | タスクリスト/実行計画 — 完了後に価値を失い、SSOTになれない。計画はtasksへ分離 |
| 実行計画の扱い | AI作業用の使い捨てドキュメント(進捗永続化+DoD)。人間の承認対象外、完了時削除 | 人間が承認する計画書 — 現実には精読されず、ゲートとして機能しない |
| histories | 全ドキュメントの変更履歴のみ(理由・要約・version遷移)。追記専用 | 計画・進捗の同居 — 履歴と作業状態は性質が異なる別もの |
| ドキュメントの構造 | 階層で切り、階層ごとの粒度でファンアウト(00=全体、01=業務領域、02=全体+詳細、03=モジュール) | 機能フォルダ縦割り(specs/<feature>/00〜03) — 分割単位は設計の成果物であり、要求時点で知り得ない |
| 品質ゲート | /doc-checkによる整合性検証。人間のレビューは任意 | 人間の承認(approved) — 現実には全文精読されず形骸化する |
| 検証状態の表現 | statusフィールドなし。証拠(verifiedブロック)+version照合による導出 | 宣言的status — 陳腐化(戻し忘れ)と自己申告の問題で信用できない |
| 軽微修正 | PATCH(照合外)で検証維持・カスケードなし | 一律version上げ — 誤字修正で全下流が失効する過剰なカスケード |
| スキルの粒度 | /gen・/implementは引数省略可、対象はAIが判定 | 階層別gen-*3個+引数必須 — 「次に何を作るか」は状態から導出でき、人間が覚える必要がない |
| 命名 | 03は"impl"、フォルダはdocs/直下、スキルはdoc-* | "spec"の多重使用(specs/フォルダ、03-spec、spec-check) — 一貫した誤読の原因だった |
| UI設計 | 02のUIセクション必須(画面一覧・遷移・項目・状態)。ピクセルレベルは規定しない | ビジュアルモックをSSOTに含める — テキストSSOTと二重化し「どちらが正か」問題を生む |
| スキルの起動権限 | 全スキルAI起動可。規律はスキル内のゲート手順とCLAUDE.md規範で担保 | disable-model-invocation で人間限定 — 対象判定までAIに委ねた本体系のAI駆動方針と不整合。ユーザー起動まで塞ぐ不具合報告もある |
| doc-checkの収束 | 上限10周のチェック→修正ループ(修正点ゼロで早期終了。自動修正は意味保存・機械導出のみ、仕様判断は人間へ) | 1回検証+手動往復 — 確率的な検証は1回で取り切れず、修正が新たな不整合を生むため収束しない |
| 作業の単位 | 3フェーズモデル(決定→ドキュメント→実装)。同席はフェーズ1のみ、以降は無人 | スキルごとに人間が同席 — 修正→検証→実装→また修正の往復ごとに人間が張り付くことになり、実運用で最大の摩擦だった |
| 質問の出し方 | フェーズ末に決定シートで一括(推奨案+未回答時の既定つき)。委任が既定 | 見つけ次第1件ずつ停止して質問 — 正しさは同じでも人間が端末から離れられない。**規範を「止めて聞く」から「分類して溜め、まとめて聞く」に変更** |
| 技術調査の結果 | タスクドキュメントの「調査メモ」(派生キャッシュ。根拠path:line付き・1行1事実・完了時に昇格振り分けの上で削除) | (a)仕様ドキュメントに書く — あるべき姿ではない情報が混入しSSOTが濁る (b)恒久的な調査ノートを新設 — 03-implと競合する第二のコード地図になり、陳腐化しても誰も気づかない (c)残さない — 実装フェーズが毎回コードを読み直す純粋な無駄 |
| ドキュメントの深さ | 実装ドライラン(コードを書かずタスク分解+テスト一覧まで導出)で未決点を洗い出し、ゼロを実装の入場条件にする。独立レンズと二重で実施 | 曖昧語スキャンとカバレッジ表だけ — 「決まっていないのに決まって読める」浅い記述を通してしまい、実装フェーズで層をまたぐ手戻りになる |
| 上流変更時の下流検証 | 差分検証(上流の差分×自分。届いていなければ`against`更新のみで合格証維持) | 上流MINORで下流を無条件に全面再検証 — 1行の変更で全下流の読み直しが発生し、往復の主因になる |
| 認証のタイミング | 影響範囲の全versionが確定してから一括で verified を書く(1フェーズ1バンプ) | 直したものから順に合格証を書く — 直後の上流修正で自分が書いた合格証を壊し、自己誘発のカスケードを生む |
| 規範文書の言語 | CLAUDE.md・スキル本文とも英語(トークン効率。CLAUDE.mdは常時読込で節約効果最大)。出力雛形・見出し引用・定型文・「仕様ドキュメント」等の定義用語は日本語、応答と生成物は日本語を規則で強制 | 全文日本語 — 規範は保守時にしか人間が精読せず、実行時の恒常トークンコストが毎回発生する |

## 8. 人間とAIの役割分担(最終形)

| 人間 | AI |
|---|---|
| 00-requests を用意する(request.md は自分の言葉で。decisions.md で委任範囲を宣言) | 01以降の全ドキュメントの生成・差分更新(委任範囲内は自律判断+記録) |
| /change で変更の意図を説明する | 影響範囲(closure)・起点階層・実装対象の判定 |
| **決定シートに1回まとめて答える**(「推奨でよい」「この範囲は委任で」で済む) | 判断点の洗い出しと分類(委任枠内は決める / 溜める / シートに載せる) |
| (任意)見たいドキュメントを見る、修正指示、full再検証の要求 | 整合性検証と証拠の管理(/doc-check)、未決点ゼロの担保 |
| | 実装・テスト・コミット・03-impl同期・DoD実検証(フェーズ2・3は無人) |

定常操作: `(00を書く) → /gen → /doc-check → … → /implement`、
変更時: `/change <説明> → /doc-check → /implement`(締めの再検証は /implement に内包)。
人間が反応を求められるのは、決定シートが提示されたときだけである。

第三の担い手として **Codex**(独立監査・独立QA)と **CI**(クリーン環境での最終回帰)が入る。
どちらも判定と修正の権限は持たず、Claudeの自己レビューを補う証拠の供給源である。

## 9. 導入手順と今後の強化候補
