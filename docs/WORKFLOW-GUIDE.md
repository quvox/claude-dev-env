# WORKFLOW-GUIDE.md — 運用ガイド(人間向け)

このドキュメントは人間のための運用マニュアルです。AIはこのファイルを常時読み込む必要はありません。
本書はAI向け規範(CLAUDE.md・skills・templates)の「解説」であり、食い違いがあれば規範が正です。
なお規範のうち CLAUDE.md とスキル本文はトークン効率のため英語で書かれています(AIの応答・
生成物は日本語になるよう規則で強制されています)。日本語で読みたい内容は本書がカバーします。

## 体系の考え方

**階層ごとに粒度が異なり、分割単位(モジュール)は設計の成果物である**——これがこの体系の骨格です。
要求を書く時点でモジュール分割を知っている必要はなく、分割は02-designで決まり、03-implと実装が
その単位でファン アウトします。

| 階層 | 粒度 | 分割の根拠 |
|---|---|---|
| 00-requests | システム全体で1ディレクトリ(request.md 必須+decisions.md 必須+glossary/acceptance/examples) | 機能では分割しない(役割別の定型ファイル) |
| 01-requirements | 全体1ファイル→大きければ業務領域で分割 | 業務構造(要件定義の時点で分かる) |
| 02-design | system.md(必須)+モジュール詳細設計(任意) | **分割はここで定義する(設計判断)** |
| 03-impl | モジュールごと | 02の分割定義に従う |

3種類のドキュメントの分担:

| 場所 | 役割 | 性質 | 人間の関与 |
|---|---|---|---|
| docs/(00〜03) | システムの**現在あるべき姿**(SSOT) | インプレース更新 | 見たいときだけレビュー(任意) |
| docs/histories/ | **ドキュメントの変更履歴**(仕様ドキュメント+steering) | 追記専用・フラット時系列 | 必要なとき読む |
| docs/tasks/ | **AIの作業用**(進捗永続化+DoD+影響範囲・決定シート・未決点・質問キュー・調査メモ) | 決定フェーズで作成、実装完了時に削除(調査メモは削除前に昇格先へ振り分け) | 承認しない |

- 03-implは実行計画ではなく「実装内容の詳細説明書」。**コードと常に一致**が不変条件。
- 品質ゲートは人間の承認ではなく**検証(/doc-check)**。statusフィールドは持たず、検証状態は
  証拠(verifiedブロック=いつ・自分のどの版・上流のどの版に対して検証したか)と現在のversionの
  照合から**導出**する。自分または上流が変われば照合の不一致で**自動的に失効**する。

## フェーズモデル(同席は最初の1回だけ)

この体系で最も高くつくのは「修正 → 検証 → 実装 → また修正 → また検証」の往復です。往復は
2つの原因から生まれます: (a) ドキュメントが**表面的**で、実装を始めてから穴が見つかる。
(b) 質問と承認が**1件ずつ**来るので、人間が端末から離れられない。そこで1つの作業を3つの
フェーズに固定し、人間が付き合うのは原則フェーズ1だけにしています。

| フェーズ | 使うスキル | 人間 | このフェーズを出る条件 |
|---|---|---|---|
| 1 決定 | `/change`(新規なら層の境目で `/gen`) | **ここだけ同席** | 影響範囲(closure)の確定と、**決定シート**への回答(この作業で聞くことの全件を1枚で提示) |
| 2 ドキュメント深掘り | `/change` の下降 or `/gen` → `/doc-check` | 不要 | 全層を1回だけ下って修正、**実装ドライラン**で未決点ゼロ、versionを1回上げ、closure全体に verified |
| 3 実装 | `/implement` | 不要 | コードとテストがgreen、03-impl同期、締めの再検証**1回** |

支える規則:

- **質問は必ずまとめて。** 1フェーズにつき最大1回、フェーズ末に一括提示。1件ずつ聞くのは禁止
  (これが端末に張り付く原因)。各項目に推奨案と「未回答時の既定」が付くので、まとめて「推奨で
  よい」と答えれば終わります。
- **委任が既定。** 設計・実装レベルの判断は decisions.md の委任枠内でAIが決める。よく聞かれる
  論点は決定シートでそのまま委任に登録すると、次回から聞かれません。
- **止めずに溜める。** その場で解けない論点はタスクドキュメントの「質問キュー」に積み、AIは
  次の作業に進みます。
- **未決点ゼロが実装の入場条件。** ドキュメントだけで実装を始めて値や方針を発明せざるを得ない
  点(=未決点)が1つでも残っていると `/implement` は開始しません。これが (a) の対策です。
  ドライランは2パス構成で、**先に「ドキュメントだけ」で未決点を洗い出し**(コードを先に見ると
  コードから答えを補ってしまい、浅さを見逃す)、**その後に技術調査**(既存ヘルパの場所・実際の
  シグネチャ・fixture作法・近隣コードの罠)を行って結果をタスクドキュメントの「調査メモ」に残します。
  実装フェーズはこのメモを読むのでコードの読み直しが減ります。
  調査メモは **SSOT ではなく派生キャッシュ**です(SSOT は仕様ドキュメントとコードの2つ。メモはそこを
  指す索引で、根拠 path:line 付き・矛盾したらコードが正・1行1事実のポインタ表に留める)。完了時
  および中断時にタスクファイルごと消えますが、消える前に振り分けます: モジュールの恒久的事実 →
  03-impl、横断的な技術前提 → steering/tech.md への追加提案、非自明な学びや罠 → docs/knowledge/、
  残骸 → 破棄。どこへ振ったかは完了レポートに出るので、捨てたことが事故にならないようにしています。
- **フェーズを抜けて入り直さない。** 検証中に「原因は上流だった」と分かっても、そのフェーズの
  中で00〜03をまとめて直します。

**作業の単位**（＝タスクドキュメント1ファイルの単位）は「実装が一度にまとまって完了・検証できる範囲」:

| 起点 | 作業の単位 | slug |
|---|---|---|
| 変更(`/change`) | **1変更セットで1作業**(影響範囲が複数モジュールに跨ってもまとめて1つ。受け入れ基準が1組なので実装も一度に閉じる) | 変更slug（例 `add-mfa`) |
| 新規構築(`/gen`→`/implement`) | **1モジュールで1作業**(依存順に立ち上げるため) | `initial-<module>` / `initial-e2e`(最後) |

ドキュメント生成は**層**単位、作業は**変更セットまたはモジュール**単位で、意図的に一致しません
（`/gen` の1回の実行が複数の作業を生む）。`/gen` はモジュールの 03-impl を書いた時点でその作業の
タスクドキュメントを作り（`phase: ドキュメント` ＝着手待ち。未決点と調査メモの置き場）、`/implement`
が依存順に1つ選んで `phase: 実装` に切り替えます。`/doc-status` では「着手待ち」と「着手済み」が
区別されて並びます。ファイル内の「タスク」の粒度は従来どおり **1タスク=1コミット・単独で検証可能**。

作業が大きすぎて一度に完了できないときは、**作業を割らずに 02 の分割定義の見直しを提案**します
（モジュール過大のシグナルであり、勝手に作業だけ割ると03-implと単位がずれる）。逆に数行の修正は
例外規定でタスクドキュメント不要です。

## 新規システム開発の手順

1. **要求定義パッケージを用意する(人間)** — `docs/00-requests/` を置く。上流の
   要求定義ファクトリー(別セッションの支援キット)で作って持ち込むのが理想。直接書く場合は
   `docs/_templates/00-requests/` から作成する。request.md はシステム全体について自分の言葉で
   (「やらないこと」は必須)。decisions.md で判断を「決定/委任/要確認」に仕分けておくと、
   以降のAIからの問い合わせが大きく減る(委任=AIが聞かずに裁量で決めてよい範囲の宣言。
   要確認=そこに来たらAIが自分で決めず、決定シートに載せて聞く)。書き上げ後の /doc-check がパッケージの形式・
   明確さ・ファイル間整合を検証して verified にする。
2. **`/gen` と `/doc-check` を層単位で交互実行** — 以降のドキュメント作成はAIが駆動する。
   /gen は**1回で1つの層を作りきる**(01の全業務領域ファイル、03の全モジュール+e2e.md)。
   ファイルごとに検証で止まることはない。/doc-check がその層を検証してPASSなら verified になり、
   次の層へ進める。検証は自己レビューを避けるため必ず**新しい文脈**で走るが、そのために人間が
   `/clear` する必要はない: /gen が fresh-context サブエージェントとして /doc-check を自動で
   起動する。人間の操作は `/gen` を層ごとに繰り返すだけ。
   - 01生成時: 決定シートの質問に**まとめて**答える。規模が大きければ業務領域の分割案に合意する
   - 02生成時: アーキテクチャ案と**モジュール分割案**が提示される。ここが最重要の意思決定ポイント
     (選択肢は一度にまとめて出る)
   - 03生成時: 分割定義の依存順に**全モジュール**の実装説明書(to-be)が1回で作られ、各ファイルで
     **実装ドライラン**(コードを書かずにタスク分解とテスト一覧を導出し、未決点を洗い出す)が
     回る。02のE2Eシナリオ一覧にシナリオがあれば 03-impl/e2e.md も同じ回で作られる
3. **`/implement`** — 未決点ゼロと検証済みチェーンを確認してから、`docs/tasks/` の作業ファイルに
   沿って**無人で**実装する(計画の承認待ちはしない。途中の疑問は質問キューに溜め、フェーズ末に
   一括提示)。完了時に03-implが実装結果に同期され、締めの再検証が**1回**走り、DoDが1項目ずつ
   検証され、タスクファイルは削除される。
4. 層の依存順に `/gen` → `/doc-check` → `/implement` を繰り返す(実装の締めの再検証は
   /implement の中に含まれる)。

**品質は /doc-check の検証で担保する。人間のレビューは任意**(見たいときに見て、修正指示や
再検証の要求ができる)。フェーズ2・3は無人で走るので、応答が必要なのは決定シートが提示された
ときだけです。

## 変更(機能追加・要件変更)の手順

1. **`/change <変更内容>`** — 複数の変更をまとめて渡してよい(1枚の決定シート・1つの影響範囲・
   1回の下降で処理される。変更理由ごとにhistoryは分かれる)。AIはまず**影響範囲(closure)**を
   00〜03の全層について確定し、起点階層を判定する:
   目的・スコープ→00 / 振る舞い→01(該当domain) / 構造・**モジュール分割**→02 / 実装詳細→03(該当module)
2. **決定シートが1枚で提示される** — この変更で聞くことの全件(曖昧点、要確認に当たった論点、
   00の書き換え、実装時に判断が必要になりそうな点)が、推奨案と「未回答時の既定」付きで並ぶ。
   ここが唯一の同席ポイント。「推奨でよい」「この範囲は委任で」とまとめて答えれば済む。
   **個別のdiff承認は取らない**(方針だけ合意し、適用後に差分サマリが出る)。
3. AIが起点から下流へ**1回だけ**下って全層を更新し、最後にversionを1回上げる。経緯は
   `docs/histories/YYYY-MM-DD-<変更slug>.md` に記録される。
4. AIが続けて **`/doc-check`**(新しい文脈のサブエージェントとして自動起動) — 影響範囲を
   まとめて検証し、合格証は最後に一括で書かれる。
   上流の変更が届かない下流は**差分検証**で合格証が維持され、再読み込みされない。
   お伺いすることが残っていなければ、そのまま **`/implement`**(無人)へ進める。
5. 完了後: 仕様ドキュメントは変更後の「現在の姿」、historyに経緯、タスクファイルは消えている。

新しいモジュールが必要な変更は、必ず02-designの分割定義の変更(=設計判断)を経由します。
AIが分割定義にないモジュールを勝手に作ることは禁止されています。

## 仕様ドキュメント未整備の既存コードを変更したいとき(ブラウンフィールド)

1. **`/reverse-doc <module> <対象コードのヒント>`** — AIがコードから03/02/01を逆生成する
   (00の骨子だけ提案されるので人間が書く)。system.mdがなければ分割定義の骨子から逆生成される。
2. AIが提示する「要ヒアリング事項」に答え、`/doc-check` で検証する。
3. 以降は通常の `/change` フロー。※一括逆生成はせず、変更するモジュールだけ直前に。

## レビューのコツ(見るとき用・任意)

レビューは任意だが、見るなら効率のよい箇所は以下(全文精読は不要。/doc-check の指摘一覧と
セットで見るのが最短):

| 対象 | 重点 |
|---|---|
| 要件 | 受け入れ基準が意図と一致するか / ユースケースが実際の利用の流れと一致するか / 未解決事項が残っていないか / 非機能の数値が現実的か |
| 全体設計 | **モジュール分割の単位・根拠に納得できるか**(この体系最大の意思決定) / 要件カバレッジ表に空欄がないか / E2Eシナリオ一覧が重要なユースケースを外していないか / 設計判断の「理由」 |
| 実装説明 | テスト対応表に「未検証」が残っていないか(e2e.md 含む) / 既知の制限に許容できないものがないか |
| /change の差分 | 依頼していない変更が紛れていないか / 「やらないこと」への抵触判定が妥当か |

## 検証状態の仕組み

statusフィールドは存在しない。verified は /doc-check が合格時に書き込む**合格証**であり、
検証状態は次の1規則で導出される:

**検証済み** = フロントマターに `verified` ブロックが存在し、その `version` と自分の現在の
version、`against` の各 version と上流(source)の現在の version が **MAJOR.MINOR部分で**
一致すること。1つでも不一致なら失効=未検証。

versionは MAJOR.MINOR.PATCH の3層: 意味に影響する変更(要件・契約・振る舞い・構造)は MINOR
以上を上げ、自分と下流の検証を失効させる。意味を変えない軽微修正(誤字・表記・書式)は PATCH
のみ上げ、**検証は維持される**(02の誤字修正で全03が失効するようなカスケードを防ぐ)。
迷ったら MINOR(安全側)。失効の波及は下向きのみで、上流には及ばない(03-implは最下流なので、
その編集で失効するのは03自身だけ)。

```yaml
verified:              # /doc-check だけが書き込める(PASS時)。不合格時は削除される
  at: 2026-07-09
  version: 1.2         # 検証した時点の自分の version
  against:
    - doc: docs/00-requests/request.md
      version: 1.0     # 検証した時点の上流の version
```

- 編集時にやることは「versionを上げる」だけ。付け替え作業は存在せず、照合の不一致で自動失効する。
- ゲート(/gen・/implement)も /doc-status もこの導出で判定する。
- /doc-check は**増分検証**: フロントマターの全スキャン(軽量)で状態を導出し、本文の検証は
  未検証のものだけ行う。`/doc-check full` で全再検証(節目での実行を推奨)。
- /doc-check は**上限10周のチェック→修正ループ**で収束まで自動で回る(1回打てばよい。修正点がなくなれば上限を待たず終了)。
  自動修正されるのは意味を変えない修正と機械的に導出できる補完、および委任枠内の判断だけで、
  それ以外の仕様判断は決定シートとしてまとめて返ってくる。10周で取り切れない指摘も残存として報告される。

カスケード(連鎖失効)を抑える4つの規則 — 「何度も /doc-check を打たされる」の対策:

- **1フェーズ1バンプ**: 1つのフェーズ内で何度直しても、versionはフェーズ末に1回だけ上げる。
- **認証は最後**: 影響範囲の全ドキュメントのversionが確定してから、verified をまとめて書く
  (書いた合格証が同じフェーズ内で壊れることがなくなる)。
- **ラン内で収束**: そのランの修正が原因で失効した下流は、そのランの対象に加えて処理しきる。
  「自分の修正のせいで、もう一度 /doc-check してください」は仕様違反。
- **差分検証**: 自分の本文は無変更で、上流のversionが動いたことだけが失効理由なら、検証の対象は
  「上流の**差分**×自分」に絞られる。差分が自分に届いていなければ `against` の版だけ更新して
  合格証を維持し(バンプもhistoryもなし)、全面再検証をしない。判定の材料は history の
  affected に書かれた**ドキュメントごとの `change:` 一行**なので、ここが曖昧だと下流の
  全面再検証コストとして跳ね返る。差分が特定できないときは安全側で全面検証。
- 限界: (a)「versionを正しく上げる」規律に依存する。上げない編集、および意味のある変更を
  PATCHと申告する編集は、失効検出をすり抜ける(厳密化するなら version の代わりに内容ハッシュへ
  強化可能)。(b) 検証の相当部分はAIの判断であり網羅的な証明ではない。検証済みの意味は
  「/doc-check のチェック一式がこの版の組に対して通った」である。

history/task に検証状態はない(historyは記録のみ、taskはファイルの有無=進行中/完了)。

## UIの扱い(割り切り)

構造・振る舞い・項目・状態(画面一覧・遷移・主要項目・loading/error等)は**テキストが正**で、
02-designのUIセクションに置く(必須。UIがないシステムは「UIなし(理由)」と明記)。
ピクセルレベルの見た目は文書で規定せず、steering/product.md のデザイン原則・トークンに従って
AIが実装時に判断する。見た目の検証(ビジュアルリグレッション)は本体系の /doc-check の対象外で、
必要ならスクリーンショット比較等の別レイヤーで担保する。

## Codexへの委譲(独立監査と独立QA)

品質ゲートの一部を、別モデルである **Codex** に「独立した第三者」として担当させる。同じClaude
セッションが書いて直して検証すると、作成時の思い込みがレビューに持ち込まれるため、その弱点を
補うのが目的(あわせて重い読み取り作業の負荷分散)。

| レーン | 起動 | Codexの担当 | Claudeの担当 |
|---|---|---|---|
| 文書監査 | `/doc-check` が自動で `/codex-audit docs` を呼ぶ | 読み取り専用で仕様チェーンを独立監査し、指摘をJSONで返す | 指摘の裁定・修正・`verified` の書き込み |
| 実装可能性(readiness) | `/doc-check`・`/gen` が `/codex-audit readiness` を呼ぶ | 仕様だけで実装を試み(コードは書かない)、**未決点**を独立に列挙 | 未決点の帰着(記載/委任で決定/決定シート) |
| QA | `/implement` Phase C が `/codex-qa` を呼ぶ | E2Eを自ら実行 → 失敗を適応的に調査 → green後にCDP探索テスト | 原因の裁定・コード修正・再実行の指示 |

readinessレーンが「表面的なドキュメント」の検出役です。自分が書いた文章の穴は自分では見えにくい
ため、独立レンズが挙げる未決点がいちばん価値があります。

**Codexが使えない環境では、同じ依頼をClaude Codeのサブエージェント(フレッシュコンテキスト・
読み取り専用)に回します**(独立レンズを空にしない)。同一モデルなので独立性はCodexより弱い —
レポートには必ずどちらのレンズが走ったか表示され、サブエージェントの結果がCodex監査として
扱われることはありません。

Codexの呼び方には2軸あります(設定は tech.md の「Codex実行設定」、詳細は `/codex-audit` §6)。

- **フロントエンド**: CLI(`codex exec`)か、MCPサーバ登録(`codex mcp-server`)。MCPにすると
  実行種別ごとのモデル・推論強度指定が実際に効き、結果も構造化されて返る。ただし**サンドボックス層は
  同じ**なので、サンドボックスが壊れた環境ではMCPにしても直らない
- **監査の実行方式**: スコープ渡し(Codexが自分でファイルを読む。サンドボックス必須)か、
  添付方式(内容をプロンプトに添付。**サンドボックス不要**で、ファイルアクセスが無いため構造的に
  読み取り専用。対象が固定の文書監査向き。E2E実行やコード探索には使えない)
- サンドボックスが使えるかは `codex sandbox -- /bin/true`(exit 0)で先に確認する
  (`codex doctor` はこの検査を含まないので、doctorが全項目OKでも壊れていることがある)

### Codexのサンドボックスが起動しないとき(Linuxのみ)

**症状**: Codexは正常にログインでき応答も返るのに、**モデルが実行するシェルコマンドが全部失敗**する。
ログに次のいずれかが出る。

```
bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted
bwrap: setting up uid map: Permission denied
warning: Codex's Linux sandbox uses bubblewrap and needs access to create user namespaces.
```

結果として監査は「ファイルを読めなかった」という理由で `audit_failed` になる。**Codexやネットワークの
問題と誤診しやすい**ので注意(`codex doctor` は全項目OKを返す。認証・通信しか見ていない)。

**確認**(1つ目が非0なら該当):

```bash
codex sandbox -- /bin/true; echo $?          # 0 でなければサンドボックスが起動できていない
cat /proc/sys/kernel/apparmor_restrict_unprivileged_userns   # 1 なら制限が有効
grep -rl bwrap /etc/apparmor.d/ || echo "bwrap用プロファイルなし"
```

**原因**: Ubuntu 24.04 系の既定では `kernel.apparmor_restrict_unprivileged_userns=1` が有効で、
拘束されていないプロセスが無特権ユーザ名前空間を作ると `/etc/apparmor.d/unprivileged_userns`
プロファイルへ遷移する。その中身は `audit deny capability,`(全ケーパビリティ拒否)なので、bubblewrap
はサンドボックスの初期化(uid map や loopback の設定)に失敗する。Chrome・Brave・lxc-usernsexec などは
これを回避するための専用スタブプロファイルを同梱しているが、**`/usr/bin/bwrap` にはそれが無い**。

**対処(推奨。bwrapだけに限定して緩める)**: Ubuntu自身のスタブプロファイルと同型のものを追加する。

```bash
sudo tee /etc/apparmor.d/bwrap >/dev/null <<'EOF'
# bubblewrap needs to create unprivileged user namespaces.
# This profile allows everything and only exists to grant userns creation,
# preventing the transition into the capability-denying unprivileged_userns profile.
abi <abi/4.0>,
include <tunables/global>

profile bwrap /usr/bin/bwrap flags=(unconfined) {
  userns,

  # Site-specific additions and overrides. See local/README for details.
  include if exists <local/bwrap>
}
EOF
sudo apparmor_parser -r /etc/apparmor.d/bwrap
```

**適用後の確認**(1・2が0、3が拒否、4が実際の行数を返せば成功):

```bash
bwrap --ro-bind / / --unshare-net /bin/true; echo $?     # 1
codex sandbox -- /bin/true; echo $?                      # 2
codex sandbox -- /bin/sh -c 'touch /tmp/x'               # 3: 「読み込み専用ファイルシステム」で拒否される
codex exec --sandbox read-only "シェルで wc -l CLAUDE.md を実行し数値だけ返して"   # 4
```

4を**実行が必要な質問**にするのが重要。「先頭の見出しを返して」のような質問はファイルを読まずに
推測で答えられてしまい、動いていないのに動いたと誤判定する(実際に一度踏んだ)。

**影響範囲とリスク**: 緩むのは `/usr/bin/bwrap` の無特権ユーザ名前空間作成のみで、他プログラムの制限は
そのまま。bwrapは元々この用途のツール(Flatpak等が同じ前提で動く)で、既にプロファイルを持つ
Chrome・Braveと同じ扱いに揃える形になる。将来Ubuntuが同名プロファイルを配布するとdpkgのconffile
競合になり得る点だけ留意する。

より広く緩める案として `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`
(恒久化は `/etc/sysctl.d/`)もあるが、全プログラムが無特権userns を作れるようになるため上の案より
攻撃面が広い。**`--dangerously-bypass-approvals-and-sandbox` や `--sandbox danger-full-access` で
回避してはならない**(不変条件5違反。モデルが生成したコマンドが無サンドボックスで走る)。

**直さない場合**: 文書監査は添付方式で回せる(サンドボックス不要)。ただし**QAレーン(E2E実行・CDP
探索的テスト)は添付方式では代替できない**ので、`/codex-qa` はサブエージェントかClaude自身のE2E実行に
なる。なおmacOSはSeatbeltを使うためこの問題は起きない。

人間が直接 `/codex-audit` `/codex-qa` を打つこともできる(節目の抜き打ち監査など)。

守られる線引き:

- Codexは**仕様ドキュメント・コード・履歴・フィードバックログ・`verified` を書かない**。
  第二の /doc-check ではなく、未決事項を決める主体でもない。
- Codexの出力は**証拠**であって判定ではない。Claudeが「確認済み(自動修正可)/確認済み(人間
  判断が必要)/誤検知(根拠必須)/判定不能」に裁定する。提案をそのまま適用することはない。
- **未解決の重大度「高」の指摘はPASSと作業完了を阻止する。**黙って無視されない(棄却したなら
  レポートに理由が出る)。
- 文書監査は完全な読み取り専用。**QAはアプリケーション状態を変える**ので、専用シード投入 →
  ブラウザの排他確保 → 終了時リセットを伴う(Claude・Codex・Playwright・人間の同時操作は禁止)。
- Codexが使えない・失敗したときは、まずサブエージェントにフォールバックする。それも走らせられない
  場合は、増分検証なら警告して続行、`full` と節目の検証はPASSを出さずに停止する。E2Eは
  省略されず、最後の手段としてClaude自身が実行する。
- CIはCodex QAの代わりではなく、その後にクリーン環境で回帰を再実行する最終ゲート。
- **待ち時間はほぼ増えない**: 監査もQAもバックグラウンドで起動し、Claudeは自分のチェックや
  記録作業を並行して進める。独立した監査を複数本走らせても並行なので実時間は1本とほぼ同じ。
- **どこに何回使うか**: 増分検証は対象集合に1回(未検証分のみが対象)。`full` と節目は**層ごとに
  並行**して初回監査し、最終監査は**観点を分けて2本**(層間の整合 / コード一致+文書品質)。
  同じ依頼の反復はしない(検出が増えないため)。1回の /doc-check で合計8回が上限。
- **意味のある修正(MINOR)を入れたら、その文書だけ再監査される**。検証中の自動修正で文書は
  書き換わるので、「独立監査を受けていない版に合格証が付く」ことを防ぐため。誤字レベル(PATCH)は
  前回結果を再利用する。

**段階導入**(どの段階で何を止めるか。設定の「フェーズ」で切り替える):

| 段階 | 文書監査 | QAレーン |
|---|---|---|
| Phase 1 観測モード | **未解決の重大度「高」はこの段階でもPASSを阻止する**(不変条件はフェーズ設定で無効化されない)。Phase 1 の意味は「それ以上のゲートを足さない＋計測する」こと: 誤検知率・追加検出・追加所要時間を記録する | Claude自身の読みと並行評価(同じChromeは同時操作しない)。CDP探索は代表1〜2画面 |
| Phase 2 高重要度ゲート | 未解決の重大度「高」だけがPASSを阻止。`full`・節目は最終監査必須 | E2Eの一次調査と2段のE2E実行をCodexへ移管。UI変更と重要UCはCDP探索必須 |
| Phase 3 安定運用 | 呼び出し回数・失敗ポリシー・レポート形式・排他制御・証拠保存期間を確定 | 同左 |

最初の5件程度はPhase 1で回し、実績を見てからゲートを上げる(評価指標と移行条件は RATIONALE.md)。

設定は `/setup` の質問で `docs/_steering/tech.md` の「Codex実行設定」に入る(Codexを入れない
場合は「Codex連携: 無効」で、独立レンズはサブエージェントが務める)。Codex側の常時制約は
`AGENTS.md`、手順と実行環境は `.claude/skills/codex-audit/SKILL.md` / `codex-qa/SKILL.md`。

## やってはいけないこと

- **コードだけ直して03-implを放置する。** 03-impl⇄コードの一致がこの体系の生命線。
- 02-designの分割定義にないモジュールの03-implやコードを作る(唯一の例外は 03-impl/e2e.md。
  こちらは02のE2Eシナリオ一覧が根拠で、一覧にないE2Eテストを作ることが同様に禁止)。
- 仕様ドキュメントの中にタスク・TODO・チェックボックスを書く(計画はtasksの管轄)。
- historyにタスク・進捗を書く / 確定したエントリを書き換える(訂正は新エントリ)。
- versionを上げずにドキュメントを編集する、または意味のある変更をPATCHで済ませる
  (どちらも検証失効の検出をすり抜ける。最も危険な違反)。
- /doc-check 以外が verified ブロックを書き込む。
- **未決点を残したまま実装を始める**(フェーズ2の手抜きを実装フェーズの手戻りに変える最短経路)。
- **質問を1件ずつ人間に投げる / フェーズの途中で止めて聞く**(まとめて決定シートで出す)。
- フェーズを抜けて入り直す(上流に原因があっても、そのフェーズの中で00〜03をまとめて直す)。
- 自分の修正が原因の失効を残して /doc-check を終える。
- history の affected に「見直した」等の曖昧な `change:` を書く(下流の全面再検証を招く)。
- Codexに仕様ドキュメント・コード・verified を書かせる / 未決事項を判断させる。
- Codexの指摘を根拠なく棄却する、未解決の重大度「高」を残したままPASS・完了とする。
- Codexに自分の指摘や期待する結論を渡してから監査させる(追認になり独立性が消える)。
- Claude・Codex・Playwright・人間が同じChromeを同時に操作する。

## 汎用と固有の区別・キットの更新

- **汎用(キット管理)**: CLAUDE.md / AGENTS.md / docs/_templates/ / .claude/skills/ / ガイド類。
  方法論の一部であり、キットの新版が出たらこれらを丸ごと上書きして更新する。
- **固有(プロジェクト管理)**: docs/00〜03 / histories/ / tasks/ / steering/。
  キット更新で触らない。steeringはひな形として同梱されるが、記入した時点から固有。
- 原則: プロジェクト固有の規約はsteeringへ。**テンプレート・スキルは直接改造しない**
  (改造すると固有化し、以後のキット更新で手動マージが必要になる。方法論の改善はキット側へ還元)。
