## 状況

仕様を先に更新してから実装へ入る運用で、**同じ判断が3回連続で必要**になった。
仕様を更新すると版が上がって実装側の合格証が失効し、実装ゲート(対象とその上流がすべて検証済み)を
形式的に満たせなくなる。しかし実装しない限り再合格もしないため、循環に入る。

3回目には実害が出た。仕様だけが一貫更新されて作業ディレクトリが空だったため、
**決定として完了しているのに実装が無い状態が誰にも気づかれず**、未コミットの作業ツリーに残っていた。

## AI の提案

1回目に「ゲートの趣旨(未検証の仕様から実装しない)は上流がすべて検証済みなら満たされ、
失効の理由は本作業の対象そのものである」と判断して着手し、根拠を作業メモに残した。

## 人間の判断とその理由

この判断は是認された。ただし**同じ判断を3回させたこと自体が仕組みの欠陥**である。

## 今後どう活かすか

- **仕様が先行している期間には、必ず目印(タスクディレクトリ)を作る。** 目印が無いと、
  未了であることを検出できるのが全件検証だけになる。
  → 現行の4フェーズ体系では `/task-new` が必ずタスクディレクトリを作り、`/task-close` まで
  残るため、この穴は構造的に閉じている。
- 検証の不合格には「**文書が誤り**」と「**コードが未了**」の2種があり、混同すると
  進めなくなる。報告する側は必ず区別する。
- 「同じ判断を2回した」時点で、判断ではなく**規約の穴**として扱う。
