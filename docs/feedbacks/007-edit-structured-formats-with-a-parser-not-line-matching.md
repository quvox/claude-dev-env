## 状況

利用者が書いた `config.toml` に不足している既定値だけを追記する処理を、行単位の正規表現で実装した。
独立レビューが**重大度「高」3件**を検出した。

- 複数行文字列の中の `[features]` を見出しと誤認し、文字列の**値**に鍵を挿入する
- quoted key(`"sandbox_mode" = ...`)を見落として同一鍵を二重定義し、TOML 全体を壊す
- リダイレクトが書き込み前に元ファイルを切り詰めるため、失敗時に元ファイルが壊れる

作り直したあとも、**挿入位置の特定だけが行単位の文字列一致に戻っており**、正当な TOML
(`[features] # comment` / `["features"]` / 暗黙の親テーブル)で補完自体が失敗していた。

## AI の提案

行指向の編集で足りると考えた(「既存の鍵と値を書き換えない」は満たしているつもりだった)。

## 人間の判断とその理由

人間ではなく独立レビューの指摘。**末尾追記は既存の鍵を書き換えていなくても、
新しく足した鍵の意味を変えてしまう**(テーブル見出し以降の鍵は当該テーブルに属するため)。

## 今後どう活かすか

- 構造化フォーマット(TOML / YAML / JSON)の部分編集は、**判定・生成・検証をすべて専用パーサで行う**。
  「破壊はしない」だけでは不十分で、**意味が変わらない**ことを検証する。
- 方式は「候補を作る → 意味的に検証する → 通ったときだけ原子的に置き換える」。
  リダイレクトによる上書きは使わない(一時ファイル + 原子的置換)。
- パーサ方式へ移したあとも、**一部だけ文字列一致に戻っていないか**を確認する。今回はそこで
  2度目の指摘を受けた。
- 所有権の復元は `chown` → `chmod` の順(逆だと setuid/setgid ビットが落ちる)。復元できないなら
  差し替えを中止する。
