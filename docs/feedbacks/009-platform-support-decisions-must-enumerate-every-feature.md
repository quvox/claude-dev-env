## 状況

macOS 対応の決定は「SSH agent は TCP ブリッジ、ポート直結、VM/KVM 非対応、arm64 ネイティブ」と
**個別機能の可否を列挙する形**で書かれていた。その後に追加されたオーケストレーターについては
何も書かれておらず、**macOS で成立していない**ことが実装との突き合わせで初めて表面化した。

## AI の提案

(A) 要件を実装に合わせて「macOS はオーケストレーター非対応」と書く /
(B) 実装を要件に合わせて macOS 版に生存判定と resume を実装する /
(C) ギャップを明示的に保持する。

## 人間の判断とその理由

**「オーケストレーターは後で開発するので放置する」** = 当面 C、将来 B。
機能そのものを今変える意思は無いが、ギャップを隠さず記録する。

## 今後どう活かすか

- プラットフォーム対応の決定は、**その時点で存在する全機能について 対応 / 非対応 / 未検討 の
  いずれかを必ず埋める**形式で書く。列挙形式だと、後から足された機能が漏れる。
- 機能を追加するときは、**プラットフォーム対応の決定を見直す対象**として紐づける。
- ギャップを保持する判断をしたときは、必ず `docs/issues/` に残す(黙って放置しない)。
