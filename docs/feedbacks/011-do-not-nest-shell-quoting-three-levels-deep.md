## 状況

一時コンテナ内に作る設定ファイルが不正な JSON になり、エージェントが設定破損を報告した。
原因は3段ネストのクォート破綻である。

1. ホスト側シングルクォートで括られたコンテナ内スクリプト
2. その内側の `su -c "..."` の中の `echo '...'` の最初の `'` が外側の引用を閉じ、
   JSON がホストシェルに裸で露出する
3. ホストシェルがトップレベルの `{A,B}` を**ブレース展開**し、`-c` の引数が2つのスクリプトに分裂する

## AI の提案

当初はエスケープを増やして解決しようとした。

## 人間の判断とその理由

エスケープを足すのではなく、**生成処理を `su` の内側から外側(root 実行部)へ移してネストを
1段減らす**。構造で減らすのが最も確実な対策である。

## 今後どう活かすか

- **シェルのクォートを3段ネストしない。** 破綻すると静かで致命的なバグになる
  (文字列の裸露出 → ブレース展開 → 引数の分裂)。
- ファイル生成のようなリテラル出力は、**なるべく最外で行い、後から所有権を合わせる**。
- ネストしたシェル起動の検証は目視ではなく、**実際に渡った引数配列**(`docker inspect` の `Cmd`)と
  生成物のパーサで機械的に行う。「引数が想定個数か」が破綻検知の急所。
- 壊れやすい検証ハーネスを常設するより、**クォート制約をドキュメントに明記**して再発を防ぐ
  割り切りも妥当。
