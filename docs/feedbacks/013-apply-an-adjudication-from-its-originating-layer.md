# 013 裁定は起点層から降ろす — 下流だけ直しても必ず見つかる

## 状況

`task-impl-depth` で人間から4回にわたって裁定を得た(`issue 034` = レビュー出力のスキーマ強制、
`issue 018` = `--vm` で KVM が無いときの中止、`issue 035` = 文脈の絞り方、`issue 040` = 認証の置き場所)。
いずれも「実装が正 → ドキュメントを実装に合わせる」という形の裁定である。

## AI の提案

私は裁定を**その issue が名指ししていた層にだけ**反映した。

- `issue 034`(実装が正)→ `01` の `FR-orch-06` 受入基準3 だけを直した
- `issue 018`(実装が正)→ `02` の `CTR-cli-container` だけを直した

いずれも「その issue の `related` に挙がっていた層」で、そこを直せば矛盾は消えると考えた。

## 人間 / 検証の反応

`/doc-check ssot` の独立レンズ(Codex `docs` の 00+01 スコープ)が**単独で**発見した:

- `D0-orch-15`(**00 の決定**)は「レビュー結果は構造化出力(**スキーマ強制**)で受け取り」のまま
- `D0-sec-10`(**00 の決定**)は「無ければ**警告して**ソフトウェアエミュレーションにする」のまま

つまり **01/02 を実装に合わせた結果、起点の 00 と下流が正面から矛盾する状態を作っていた**。
CLAUDE.md 原則3(変更は起点層から下降させる)違反であり、`functional.md` の再認証を止めた。
同じ形が `issue 040` でも起きた(`D0-auth-03` を直したが、**同じファイルの `D0-auth-02` の
ガードレール**に「(symlink にしない)」が残った)。

## 一般化した教訓

**裁定を反映する前に「この判断は最初にどの層で決まったか」を grep で確認する。**

1. 裁定の対象になっている語(「スキーマ強制」「警告して続行」「コンテナローカル」など)を
   **00〜03 の全層に対して grep する**。issue の `related` を信用しない —
   `related` は起票時に見えていた範囲しか挙げていない。
2. 見つかった最上流の層から順に直す。**同じファイル内の他の決定・委任のガードレールも見る**
   (`D0-auth-03` を直して `D0-auth-02` を見落としたのはこれ)。
3. 「下流だけ直しても機械検査は通る」ことに注意する。`check-relations.py` も
   `callgraph-check.py` も**層をまたぐ意味の矛盾は見ない**。見つけるのは
   `/doc-check` の check A(縦の整合)と独立レンズだけである。

**この教訓は「裁定を得たあと」に最も効く。** 裁定そのものは正しくても、
反映の入口を間違えると SSOT に矛盾を作り込む。
