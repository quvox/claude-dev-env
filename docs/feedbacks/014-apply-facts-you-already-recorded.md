# 014 自分で記録した事実を裁定に適用し忘れる

## 状況

`MODULE-cli-pull` の異常系を書くとき、`claude-dev:668` の `docker tag` が戻り値を検査していない
ことに気づき、`issue 037` として「古いイメージを黙って使い続ける = `FR-env-09` 受入基準11 違反」と
起票した。人間には「② `docker tag` の未検査は**要件が正 = バグ**」という選択肢を推奨として提示し、
その回答を得て 01 に受入基準11 を残した。

## AI の提案

「`docker tag` の戻り値を見ていない → 失敗が検出されない → 古いイメージが残ったまま完了と表示される」
という推論。コードの当該行だけを見て組み立てた。

## 人間 / 検証の反応

`/doc-check ssot` が指摘した: `docker tag` は `if docker pull …; then` の**成功ブロックの中**にあり、
**`claude-dev:8` の `set -e` が効く**。失敗すればその時点で非0終了し、`_pull_ok=1` にも
「✅ pull 完了」にも到達しない。**受入基準11 は満たされている。**

さらに悪いことに、**`set -e` の存在は私自身がフェーズ2の調査メモ #9 に
「`claude-dev` に `set -e` がある(`claude-dev:8`)。したがって `docker run` の失敗はその場で
スクリプトを非0終了させる」と記録していた**。同じセッションの中で、自分が確定させた事実を
別の推論に適用し忘れた。

## 一般化した教訓

**シェルスクリプトの「戻り値を検査していない」は、`set -e` の有無を確認するまで結論にならない。**
`set -e` 下では「検査していない」= 「失敗したら即座に止まる」であり、
「失敗を無視する」の反対の意味になる。`|| true` / `if …; then` / `&&` の文脈も同じく判定を変える。

より一般に: **裁定・起票の直前に memo.md の調査メモを読み返す。** 調査メモは
「後で使うために確定させた事実」であって、書いた時点では使い道が決まっていない。
使うべき場面で参照されなければ、記録した意味が無い。

**推論の単位を1行にしない。** 当該行の前後(ブロック構造)とファイル冒頭(`set -e` / `set -o pipefail`)
まで読んでから結論を書く。
