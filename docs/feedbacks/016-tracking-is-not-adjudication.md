# 016 「issue で追跡済み」を裁定と数えてはならない

## 状況

`/doc-check task-impl-depth` の反復5 で PASS を出した。PASS 条件④は
「E の 02⇄03 差分が全部『意図された未実装』か『解消済み』か『人間が判定済み』のいずれか」である。

## AI の提案

差分5件それぞれに `docs/issues/` の ID を書いてあることを根拠に、
「全件追跡済み = 条件④を満たす」と判定した。

## 人間 / 検証の反応

新しい実行の独立レンズ(Codex `readiness`)が**単独で**、`issue 018`
(`--vm` で `/dev/kvm` が無いときの中止)が**一度も人間に問われていない**ことを指摘した。
**追跡は裁定ではない。** issue を作った時点では「どちらが正か要確認」であり、
人間が選ぶまで差分は未解決のままである。反復5 の PASS は誤りだった。

## 一般化した教訓

**3つを厳密に区別する。**

| 状態 | 意味 | PASS 条件④を満たすか |
|---|---|---|
| **追跡済み** | `docs/issues/` に ID がある | **満たさない** |
| **裁定済み** | 人間がどちらが正かを選び、その記録が issue の「裁定の記録」にある | 満たす |
| **解消済み** | 裁定に従って文書(またはコード)が直っている | 満たす |

- issue に「**裁定の記録**」節を作り、**日付と選んだ案と反映先**を書く。issue の存在だけでは
  後から「誰がいつ決めたか」が分からない。
- 裁定の記録を**タスクの memo.md にしか書かない**のも同じ誤り。memo は `/task-close` で
  ディレクトリごと消えるので、**issue 側に残す**(この教訓自体、`/doc-check` が
  「人間の裁定が memo.md にしか無い」と検出して `issue 014`/`015` に追記させた)。
- 検証する側は「issue ID が書いてあるか」ではなく「**裁定の記録があるか**」を見る。
