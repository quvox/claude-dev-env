# 017 引き継いだ推奨案は、提示する前に受け皿の実在を確かめる

## 状況

`task-impl-depth` のフェーズ4 を再開し、memo.md に残っていた未回答の決定シートを人間へ提示しようとした。
論点の1つは `docs/issues/044`(用語「資源逼迫」の閾値定義に承認の記録が無い)で、
**memo の決定シートは案C(数値は 00 の用語集から外し、02 が定める)を推奨**していた。
一方 **issue 044 本体は案A(承認する)を推奨**しており、同じ論点に2つの推奨が並んでいた。

## AI の提案

最初は memo の推奨(案C)をそのまま選択肢の先頭に置いて提示しようとした。
「00 は実装の既定値に縛られない」という理屈は筋が通って見えたためである。

## 人間 / 検証の反応

人間が「**もう一度ドキュメント全体を見直して、懸念が本当に懸念なのか、推奨案が本当に理に
かなっているのかを、関連する親兄弟子孫のドキュメントを確認して検討してほしい**」と差し戻した。

確認した結果、**案C は成立しなかった**。

- `.claude/directions/00-requests.md:52` は用語集について「**定義が揺れる語を残すな。揺れは 03 まで
  伝播して実装の不一致になる**」と定めている。用語集が定義を持たない形は規範に反する。
- 現行の `terminology.md` 1.1.0 は既に「**既定**」「環境変数で上書きできる」と書いており、
  案C が避けようとした「実装の既定値を要件として固定する」問題は**すでに避けられていた**。
- 決定的な点として、**案C の受け皿が 02 に存在しなかった**。`02-design/logging.md:88` の
  第3列「検知した指標と閾値」は*ログに何を書くか*の欄で、定義の置き場ではない。
  案C を採ると「00 は『閾値は 02 が定める』と言うのに 02 に数値が無い」状態を新たに作る。

裁定は案A′(承認 + 00 から環境変数名だけ落とす)になった。

## 一般化した教訓

**推奨案には必ず「その案が要求する受け皿」がある。** 「数値を下の層へ降ろす」「別の文書へ移す」
「委任範囲に足す」型の案は、**移動先の文書に実際にその欄があるかを確認しないと成立しない。**
確認せずに提示すると、人間は成立しない案を選ぶ立場に置かれる。

さらに**引き継いだ推奨は、書いた実行とは別の情報量で書かれている**。前の実行は
「00 に実装の既定値を書いてよいか」という一点を見て C を書いたが、
用語集の規範(00-requests.md)と 02 側の受け皿を同時に見ていなかった。
`.claude/improvements/KIT-recommendation-grounding.md`(上流/同層/下流の三方向読み)が
**推奨を書くとき**の規範として既にあるが、本件は**他人の推奨を引き継いで提示するとき**にも
同じ三方向読みが必要だという事例である。

**同じ論点に2つの推奨(issue 側と memo 側)が並んでいたら、それ自体が検証を要求する信号である。**
どちらかが古い情報で書かれている。

## どう行動を変えるか

- 決定シートを**提示する前**に、各推奨案について「この案が書き込みを要求する場所」を列挙し、
  その場所が実在するかを開いて確認する。
- issue 本体の推奨と memo の決定シートの推奨が**食い違っていたら、必ず両方の根拠を辿る**。
  食い違いを黙って一方に寄せて提示しない。
- 引き継いだ推奨をそのまま出すときも、**自分が検証した根拠を添えて出す**
  (「前の実行がそう書いていた」は根拠ではない)。
