# 018 `mv` の原子性は「パス」の話であって「中身」の話ではない

## 状況

排他ロックを「向き先に `<PID> <操作名>` を入れたシンボリックリンク」で実装した。
保持プロセスが `SIGKILL` などで消えた残骸を回収するため、`kill -0` で保持者の不在を確かめてから
`mv <lock> <lock>.stale.$$` で引き取る、という設計にした。

`rm -f` で直接消す案を退けた理由は正しかった。「同じ残骸を見つけた2プロセスが両方 `rm -f` →
`ln -s` すると、後から来た側が先行者の新しいロックを消して双方が臨界区間に入る」。
そこで **「`rename` が成功するのは1プロセスだけだから引き取り権が一意に決まる」** と考えて `mv` にした。

## AI の提案

`mv` に成功したら、その事実だけを根拠に `rm -f` して自分のロックを張る、という実装にした。
コメントにも「同じ残骸を同時に見つけた複数プロセスのうち1つだけが成功する」と書いた。

## 何が間違っていたか

**「同時に」が成立するのは、2つの `mv` が本当に同じ瞬間に走ったときだけである。**
実際に起きるのはこうだった。

1. A と B が同じ残骸(PID 100)を観測する。
2. B が `mv` に成功し、`rm -f` して自分のロック `300 start` を張り、**臨界区間に入る**。
3. その後で A が `mv` を実行する。**`mv` は向き先の内容を見ないので、B の生きているロックに対して成功する。**
4. A はそれを `rm -f` して `200 stop` を張り、**同じ臨界区間に入る**。

しかも B の `release_lock` は PID 不一致を見て何もしないので、**この破れはログにも終了コードにも
一切現れない**。症状は「なぜか認証が消えた」という形で遠くに出る。

再現は 6 行のシェルで確認できた。

```bash
ln -s "100 stop" lock                      # 残骸
mv lock lock.stale.300; rm -f lock.stale.300; ln -s "300 start" lock   # B が引き取り完了
mv lock lock.stale.200 && readlink lock.stale.200   # → "300 start" が返る（A が奪えた）
```

## 一般化できる形

**「観測してから操作する」手順では、原子的な操作を使っただけでは足りない。
その操作が「観測したものに対して」行われたことを、操作の後に検証しなければならない。**

- `rename` / `mv` が保証するのは**パスの付け替えが一度きり成功すること**であって、
  **付け替えた対象の同一性**ではない。
- `ln -s` は逆に「同名パスがあれば失敗する」ため、**観測と取得が不可分**である。だからロックの
  取得そのものには使えるが、**回収**には使えない。
- 検証は「操作した結果を読み直して、観測した値と一致するか」で行う。一致しなければ**元に戻して
  失敗として扱う**。戻せなかったこと自体も利用者に見せる(黙って進まない)。

## 次回どうするか

競合を扱うコードで「この操作は原子的だから安全」と書きそうになったら、**その原子性が何について
のものかを一文で言えるか**を確かめる。言えないなら、それは検証を省く理由になっていない。

とくに「TOCTOU を潰した」と考えたときこそ、**潰したのは check-then-act のどの辺なのか**を
具体的に書く。今回は「取得」の TOCTOU は潰していたが、「回収」の TOCTOU が残っていた。
