# 019 bash で「書いたのに効かない」3つの罠

シェルで排他ロックと中断処理を実装した際に踏んだ、いずれも**エラーにならず静かに効かない**罠。

## 罠1: 同じ `local` 文の中では、前の変数がまだ展開されない

```bash
release_lock() {
    local key="$1" lockfile="${LOCK_DIR}/${key}.lock"   # ← lockfile は ".../.lock" になる
```

bash は `local` の**全ワードを展開してから**代入するため、`${key}` はまだ空である。
結果として `lockfile` が `.../.lock` を指し、**ロックは解放されず、配列からも外れなかった**。
構文エラーにも実行エラーにもならない。

**対処**: 他の変数を参照する代入は `local` から出して別の文にする。

**見つけ方**: 「解放したはずのものが残る」系の症状。`set -x` で1行追えば即座に分かるが、
そこに疑いを向けるまでが長い。**単体テスト(取得 → 解放 → 残っていないことの確認)を先に書けば
一発で出る。**

## 罠2: `&` で起動した子プロセスは SIGINT を無視するので `trap ... INT` が効かない

中断処理(`INT`/`TERM` を受けたら進行中の1件を終えてから終了コード 130)を検証しようとして、

```bash
"$CLI" logout --yes & PID=$!
sleep 1.2
kill -INT $PID
```

としたが、**何事もなく最後まで完走した**。原因は bash が非同期コマンド(`&`)の子で
SIGINT/SIGQUIT を `SIG_IGN` にすること。**入口で無視されていたシグナルは `trap` で捕まえ直せない**
ため、スクリプト側の `trap '...' INT` は書いてあっても無効になる。
しかも `SIG_IGN` は `exec` した子へ**継承される**ので、`setsid`・`script` で包んでも解除されない。

**対処**: 検証は SIGTERM(こちらは無視されない)で行うか、`SIGINT` の disposition を
`SIG_DFL` に戻してから `exec` する小さなランチャ(Python の `preexec_fn` など)を使う。
両方で確かめると、実装が本当に正しいかを切り分けられる。

## 罠3: 端末の Ctrl-C は子プロセスにも直接届く（＝「1件を終えてから中断」は自動では成立しない）

`trap 'FLAG=1' INT` は**シェル自身の反応**を遅らせるだけである。非対話シェルではジョブ制御が
無効で、子プロセスはシェルと同じプロセスグループに入る。したがって端末で Ctrl-C を押すと
**`docker rm -f` にも SIGINT が直接届き**、進行中の1件は「終えてから」ではなく途中で切られる。

`kill -TERM <シェルの PID>` で試すと意図どおり動くので、**テストの通し方によっては
この差が見えない**。

**対処**: 子プロセスをサブシェルで包み、そのサブシェルで無視を宣言する。

```bash
( trap '' INT TERM; docker rm -f "$name" )
```

`trap ''` が設定する `SIG_IGN` は `exec` した子へ継承されるので、`docker` 自身がシグナルを
無視して削除を完了する。**`setsid` は macOS に標準では無い**ため、両 OS で同じ形に書ける
この方法を採った(罠2 の「継承される」性質を、ここでは逆に利用している)。

## 次回どうするか

シェルで「書いたのに効かない」を疑うときは、**まず 10 行の再現スクリプトを書く**。
今回の3件はいずれも実装コードを読んでいる限り気づけず、**動かして初めて出た**。
とくにシグナル絡みは、**検証の起動方法そのものが結果を変える**ので、
SIGTERM と SIGINT の両方・前景と背景の両方で確かめる。
