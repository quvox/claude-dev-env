# 021 品質特性は「測る/測らない」だけでなく「追わない」と決められる

## 何が起きたか

`docs/issues/043`(NFR の目標値が要件本文の一部しか測っていない)と
`docs/issues/041`(ブロック対象ドメインの集合が未定義)に対して、AI は決定シートに
**測定可能にする方向の選択肢しか並べなかった**。

| 論点 | AI が並べた選択肢 | 人間の裁定 |
|---|---|---|
| 概念#2 `NFR-sec-02`(外向き通信の制御) | 集合を「設定で与えられる集合」と定義して測定可能にする(案D)/ 委任範囲に足す(A)/ 00 に決定として起こす(B)/ 許可リストへ変える(C) | **`NFR-sec-02` を撤回・削除する。ブロックは不要** |
| 概念#6 `NFR-ops-01`(運用補助と可観測性) | 不可分として3事象すべてに観測点を書く / 段階可へ落とす | **`NFR-ops-01` は廃止する** |

理由は「**その品質特性自体を本システムでは追わない**」であった。

## なぜ AI は選択肢に並べられなかったか

`docs/issues/043` が「正はどちらか = **ドキュメントが誤り**(要件の意図は妥当で、測定方法が
追いついていない)」と書いており、AI はその判定をそのまま前提にした。
だが **「要件の意図が妥当か」は issue の起票者(AI)が決めてよいことではない**。
issue は「測定方法が無い」という事実までは正しく、そこから先の
「だから測定方法を足すべきだ」は**要件の存続を前提にした推論**である。

同じ形の取りこぼしが `docs/feedbacks/016-tracking-is-not-adjudication.md` にもある
(追跡していることと裁定が済んでいることを混同した)。今回は
**「要件が存在すること」自体を裁定の対象に載せなかった**という形で出た。

## 次からどうするか

測定不能な非機能要件を決定シートに載せるときは、**必ず3つ目を並べる**:

1. 測れる形に書き直す(目標値と測定方法を具体化する)
2. 測らないと明記する(理由つき。要件としては残す)
3. **その品質特性を追わないと決めて、要件そのものを削除する**

3 を並べるときは、**削除の波及を先に実測して選択肢に添える**こと。今回は後追いで測って
次が分かった(これを先に出していれば人間は一度で判断できた):

- `NFR-sec-02` の参照は 8 箇所。`FR-env-05` が別に残るので**実装の要件の裏付けは消えない**。
- `NFR-ops-01` の参照は 20 箇所以上(PLAN 5件・MODULE frontmatter 5本)。ただし
  **NFR-ops-01 だけを根拠にしている機能は1つも無く**、唯一の「それだけが根拠」は
  `02-design/logging.md` の追記型ログ2行(`dispatch` / `result`)だった。

**「削除できるか」は参照の数ではなく「それだけが根拠のものが何か」で決まる。**
`relations-query.py --requirement <ID>` と frontmatter の `requirements:` の突き合わせで機械的に出る。
