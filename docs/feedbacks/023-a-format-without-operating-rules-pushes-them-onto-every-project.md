# 023 書式だけの規範は、運用規則を全プロジェクトの決定シートへ押し付ける

## 状況

`docs/issues/060`(01 に条項ID と分割可否が無く、02 のカバレッジ表に充足列が無い)を
`/task-new` でタスクへ昇格し、決定シートを 8 項目(概念4・論点3・委任1)で提示した。

## AI の提案

8 項目すべてを**このプロジェクトの決定**として人間に問うシートを作った。
根拠として `.claude/directions/01-requirements.md` と `02-design.md` を各項目に引いており、
「規範が定めていないから人間に問う」という形式的には正しい手順を踏んでいた。

## 人間の判断とその理由

> そもそもここで問うていることは一般的なルールではないか?
> そうだとすると規範に最初から決めておくべきではないか?

**指摘のとおりだった。** 提示後に分類し直すと、8 項目のうち **7 項目が一般規則**で、
このプロジェクト固有なのは「どの要件を `段階可` にするか」の 1 項目だけだった。

| 項目 | 実際は | 規範の状態 |
|---|---|---|
| 条項ID の安定性(欠番を埋めない・並べ替えない・再利用しない) | 一般 | `01-requirements.md:36` は**形式**しか定めず、安定性に沈黙 |
| `SR-*` を分割可否の対象にするか | 一般 | 同:127 は "functional and non-functional" とだけ書き、システム要件に沈黙 |
| 「充足」が設計の話か実装の話か | 一般 | `02-design.md:60` は**4値**を定めるが、**何の軸か**を定義していない |
| 条項IDを入れたら 03 の対応表も同時に移すか | 一般 | 同時性の要求が無い |
| `部分` 以外の pending も条項IDを持つか | 一般 | `部分(P-nn)` の3条件はあるが、適用範囲に沈黙 |

## 今後どう活かすか

**規範が「書式」を定めたら、同時に次の4種の「運用規則」を定めたか自問する。**
書式だけを定めた規範は、空白を決定シートへ押し出し、**全プロジェクトが同じ問いを別々に埋める**。
決定シートは「このプロジェクト固有の判断」を書く場所であって、規範の欠落を各自が補う場所ではない。

| 種 | 問い |
|---|---|
| **安定性** | その識別子は一度振ったら動かないのか。動かせるなら、参照している側はどう追随するのか |
| **適用範囲** | どの対象に適用され、どの対象には適用されないのか(「AとB」と書いたとき、Cはどちらなのか) |
| **軸の意味** | その値が言っているのは何についての事実か(設計の話か、実装の話か、テストの話か) |
| **連動** | それを入れたとき、同時に直さないと参照が壊れるものはどれか |

**決定シートを書き終えたら、提示の前に1項目ずつ「これは他のプロジェクトでも同じ答えになるか」を
判定する。** 「同じ答えになる」なら、それは規範の欠落であって、シートの項目ではない。
その項目は `/kit-improve` へ回し、シートには**プロジェクト固有の残りだけ**を載せる。

**なぜ今回それを見落としたか(再発防止の要点)**: `docs/issues/060` が示すとおり、
この書式は**規範に書かれてから一度も実装されたことがなかった**。書かれたが実行されていない規範は、
運用の問いが表面化する機会を持たない。**初回実行は、欠けた運用規則が現れる場所である** —
「規範にこう書いてあるから従う」と読むだけでなく、**従おうとして詰まった点はすべて規範の欠落を
疑う**。詰まりを人間への問いに変換するのは、その次である。
