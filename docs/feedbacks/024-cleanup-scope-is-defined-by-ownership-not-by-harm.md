# 024 片付けの範囲は「害の有無」ではなく「所有」で決める

## 状況

`claude-dev stop` が、セッションのコンテナ内から作られた Docker 資源を片付けるようにする変更。
決定シートの概念3 で「片付ける資源の種類はどこまでか」を人間に問うた。

## AI の提案

**コンテナ + compose 既定ネットワークまで**を推奨した。独立ネットワーク
(`docker network create`)は対象外とし、理由を「残っても利用者の作業を壊さず、ディスクも
食わない」とした。名前付きボリュームは `D0-env-05` 項2 が「保持する」と決めているので対象外。
つまり**資源ごとに「残ったときの害の大きさ」を見積もって線を引いた**。

## 人間の判断とその理由

**ネットワークも含める**(2026-08-07)。理由は
**「片付けの範囲を『セッションが作ったものは全部』としたい」**。
害の見積もりではなく、**範囲を1文で言い切れることそのもの**を選んだ。

## 今後どう活かすか

**片付け・削除・回収の範囲を提案するときは、まず「所有」の軸で線が引けないかを先に試す。**
資源の種類ごとに害の大小を見積もって切り分けた案は、次の2つの点で弱い。

1. **説明が資源の種類の数だけ必要になる。** 「コンテナは消すがネットワークは残す、ボリュームも
   残す」は、利用者にとって3つの別ルールで、どれがどれか覚えられない。
   「そのセッションが作ったものは全部消す(ただしデータを持つ名前付きボリュームは残す)」なら、
   規則1つと明示された例外1つで済む。
2. **害の見積もりは AI が勝手に置いた前提に依存する。** 今回の「ディスクも食わない」は
   サブネット枯渇を数えていなかった。**害の大小は利用者の運用を見ないと決まらないので、
   AI が独断で切ってよい軸ではない**(`D0-scope-02` の委任は「観測できる振る舞いを変えない」
   範囲であり、削除対象の増減はその外側である)。

**例外を置くときは「害が小さいから外す」ではなく「別の決定が既に保持を命じているから外す」と
書けるものだけにする。** 今回の名前付きボリュームは後者(`D0-env-05` 項2)であり、
これは規則の一貫性を壊さない。
