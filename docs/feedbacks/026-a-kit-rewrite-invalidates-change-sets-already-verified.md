# 026 キットの書き換えは検証済みの変更指示を無効化する

## 状況

`task-remove-orchestrator` は 2026-08-08 にフェーズ2 を終え、変更指示 68 件が
`/doc-check`(task モード)で **PASS** していた。2026-08-10 にキット(`CLAUDE.md` /
`.claude/`)を大きく書き換えたあと、同じタスクをフェーズ3〜4 で進めたところ、
**成果物とキットが 7 箇所で食い違った**。

| # | 食い違い | 気づいた時機 | 症状 |
|---|---|---|---|
| 1 | `change: replace` に `version_bump` が必須になった | 反映の直前(`compose-changeset.py`) | `エラー: version_bump は patch|minor|major` で異常終了 |
| 2 | 親見出しの本文経由で子見出しを新設・改名できなくなった | 同上 | `親本文経由の新規子見出しは禁止` で異常終了 |
| 3 | 省略による子見出しの削除が効かなくなった(`deletes:` 必須) | 合成結果の目視 | 消えるはずの `DSN-orch-01` などが残る |
| 4 | relations の `change: replace` が全文置換になった | 合成結果の行数比較 | `MODULE-cli-start` が 350 行 → 53 行に**縮んだ** |
| 5 | `bump_version` が `verified:` のキー行だけを落とす | 合成結果の frontmatter | `at:` `against:` が宙に浮き **YAML が壊れた** |
| 6 | `generic_replace` が変更指示の frontmatter を無視する | `source:` の実在検査 | 削除したファイルを指す `source:` が残った |
| 7 | `close-task.py` の条件 (b) が `change: delete` の行にも検証済み記録を要求する | 削除ゲート | **SSOT を削除するタスクは構造的に閉じられない**(実体が無いので合格証を持ちようがない) |

**1・2・5・7 は止まるので気づける。3・4・6 は黙って壊れる。** 4 は
「350 行が 53 行になる」という致命的な欠落だが、`check-changeset.py` は合格したままだった
(合成しないと見えない)。

## なぜそうなったか

変更指示は**規範に対する差分の表現**であって、自己完結した文書ではない。
記法・必須フィールド・合成器の意味論が変われば、既に書かれた差分の意味も変わる。
`/doc-check` の PASS は「そのときの規範のもとで正しい」ことしか言っていない。
**合格証は規範の版に対する条件付きの保証である** — この条件は `verified.against` にも
書かれていない(`against` は上流ドキュメントの版だけを記録する)。

## 教訓

- **キットを書き換えるときは、進行中タスクの変更指示を必ず合成し直す。**
  `check-changeset.py` は合成しない検査なので、記法の意味論の変化を検出できない。
  最低限 `compose-changeset.py --preview` を走らせ、**合成結果の行数を反映前と比べる**。
- **黙って壊れる変更を機械検査へ落とす。** 4(全文置換への意味論変更)は
  「合成後のファイルが著しく縮んだら止める」で検出できる。5 は
  「合成後の frontmatter が YAML として読めるか」で検出できる。どちらも
  `compose-changeset.py` の中で1行ずつ確かめられる性質である。
- **`.claude/` は `.gitignore:4` で git 追跡外である。** キットの書き換えも、
  今回入れた 6 箇所の修正も、版管理の外にある。何がいつ変わったかを後から追えないので、
  キットの変更は最低限 `docs/histories/` か `docs/pendings.md` に痕跡を残す。
- CLAUDE.md §3 の「製品の DoD が未達のあいだキットは凍結する」は、まさにこの事故を
  避けるための規則だった。**凍結を破るなら、進行中タスクの再合成をセットにする。**
