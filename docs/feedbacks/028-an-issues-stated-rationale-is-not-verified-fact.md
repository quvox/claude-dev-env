# issue の「理由」は検証済みの事実ではない

## 何が起きたか

`docs/issues/053`(`logout` が列挙不能の共有ボリュームを「空」と扱う)は、対処案として
案A(印だけを見る)と案B(受入基準19 を先に直す)を挙げ、**案B を推す理由の一つに
「A だけだと同じ穴が `reset` 側に残る」と書いていた**。

フェーズ1 の調査でこれを現物と突き合わせたところ、**事実として誤りだった**:
`reset` は削除対象0件の早期終了経路を持たず、`_auth_empty` に相当する判定も持たない
(共有ボリュームは `docker volume rm -f` で器ごと消す)。つまり `reset` に同じ穴は無い。

結論は変わらなかった(案B は**それ自身の理由** — 確かめていない状態を「空」と同一視すると
認証が残ったまま終了コード 0 で終わる — で選ばれた)。しかし理由欄を鵜呑みにしていれば、
`reset` 側の変更を closure に入れて範囲を余計に広げていた。

## なぜ起きたか

issue は**問題を見つけた時点**で書かれる。事象と再現手順はその場で確かめられるが、
「対処案の比較」や「他の機能にも同じ形がある」といった記述は、しばしば**その場の推測**である。
`docs/issues/` のどの欄が検証済みでどの欄が推測かを区別する書式は無い。

## 次にどうするか

- **issue の `## 事象` は再現手順として信頼し、対処案の比較に書かれた事実は着手時に現物で数え直す。**
  同型の有無は「そう書いてある」ではなく `grep` の件数で決める(このケースは
  `grep -c '_auth_empty' claude-dev` = 1 で足りた)。
- 同じ注意はレーン判定の根拠にも及ぶ。本タスクは `security_payment_privacy=true` で
  `critical` になったが、用語集「安全」は claude / codex のログイントークンを**一過性**として
  「鍵情報」から除外しており、`NFR-sec-01` の4項目にも `logout` は現れない。
  **`true` は fail-closed の選択であって、プロジェクトの「安全」定義に照らした事実認定ではない** —
  `check-lane.py` は根拠の欠落を `critical` へ倒すので、この差は明示しないと後から読めない。
  レーンを上げた理由を書くときは、**倒した理由(fail-closed)と事実認定を書き分ける。**
