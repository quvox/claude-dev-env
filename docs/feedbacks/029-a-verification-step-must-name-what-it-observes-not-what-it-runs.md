# 029 検証手順は「実行するもの」ではなく「観測できるもの」で書く

## 状況

`FR-env-13`(同梱外部バイナリ)の実機確認手順を `docs/03-impl/tests/images.md` に書いていた。
イメージの中に同梱物が入っていて、コマンド名だけで起動できることを確かめる手順である。

## AI の提案

最初は `command -v <名前>` と `ls -l /usr/local/bin/<名前>` の2つを観測点にし、
**同梱物そのものは実行しない**と決めた(`DS-01`)。理由は「同梱物ごとに終了コードの意味が
変わるので、設置の妥当性ではなく同梱物の正しさを測る手順になってしまう」であった。

独立レビュー(Codex)がこれを重大度「高」で覆した。**存在と権限だけを見る手順は、壊れた実行形式・
別アーキテクチャ向けのバイナリ・動的ローダーの欠落のいずれでも通過してしまい、
`AC-07` が求める「起動できる」を検証しない。**

書き直した手順(`docker run --rm <イメージ> <コマンド>` で確認用の実行物を実行する)に対して、
**同じレビューが2回目で再び重大度「高」を出した**: このイメージの `ENTRYPOINT` は初期化のあと
`exec tail -f /dev/null` で待機に入るため、**渡したコマンドを実行しない**
(`scripts/entrypoint-claude.sh` の末尾)。手順は何も観測しないまま固まる。

## 人間の判断とその理由

人間の差し戻しではない(独立レビューの指摘を AI が裁定して受け入れた)。
どちらの指摘も**事実として正しいことをコードで確認**してから直した。

## 今後どう活かすか

**手順を書き終えたら、コマンド列ではなく「不合格になる状態」を数え上げる。**
「この手順を通過してしまう壊れ方は何か」を1つでも挙げられるなら、その手順は観測点として弱い。

具体的に効いた2つの問い:

1. **「対象が完全に壊れていても、この手順は合格するか」** — 存在確認(`command -v` / `ls`)は
   ほぼ常に「する」。したがって**振る舞いを要求する受入基準に対して、存在確認は観測点にならない**。
2. **「この実行の形は、対象の環境で本当に実行されるか」** — コンテナなら `ENTRYPOINT` /
   `CMD` / 既定ユーザー、CI ならシェルの種類とフラグ。**実行の器が引数を捨てる形になっていても、
   コマンド列を読むだけでは気づけない。**実際に1回走らせるまで、手順は仮説である。

**この2つは、手順を書く側が自分では見つけにくい**(2回とも見つけたのは独立レビューだった)。
`/doc-check` の独立レビューへ渡すプロンプトに、**実機手順があるときは「その手順が通過して
しまう壊れ方を挙げよ」を明示的に含める**とよい。
