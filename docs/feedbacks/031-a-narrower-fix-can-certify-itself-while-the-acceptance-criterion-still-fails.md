# 031 狭く直した修正は、受入基準を落としたまま自分を合格にできる

## 状況

`entrypoint` が tmux セッションを `su -l` で起こすため、コンテナへ渡した環境変数が tmux の窓の中の
プロセスから1つも見えない、という欠陥を直していた。**対象を「本システムが予約している名前」に絞り、
その集合だけを `su` に渡すコマンドの中で載せ直す**形で設計し、01 に条項 `FR-env-07-13` を新設して、
`/doc-check` の PASS(独立レビュー Codex 込み)と E2E-01 の新設手順の合格まで取った。

その直後、人間が **「`.claude-dev.yaml` に env ファイルを指定できるようにした機能と、この修正は
干渉しないか。両方正しく動作するか」** と問うた。実機で測ると、**利用者が env ファイルに書いた組は
tmux の窓の中で1件も見えず、`AC-08`(プロジェクトごとの環境変数がコンテナ内のツールに見える)が
実機に対して不合格**だった(`docs/issues/107`)。

## AI の提案

**対象を予約名の集合に絞る**ことを、決定シートに載せずに決めて開示していた。根拠は上流にあった —
02 の契約が「予約する環境変数名の集合は次の2つで尽くされる」と定義しており、その集合全体を採るのは
上流を引いただけの事実判断だ、と読んだ。

実現方法は `[DS-05]` で「`su` に渡すコマンドの中で名前を列挙して載せ直す」を選び、
**「`-l` を外すと `PATH` / `HOME` / 作業ディレクトリまで同時に変わる」**という理由で `-l` を外す案を
退けていた。

## 人間の判断とその理由

「1.b(issue をこのタスクへ畳み込む)。2.B(`su` から `-l` を外す)。」

理由は問いそのものが示していた — **利用者にとって「コンテナへ渡した環境変数」は1つの概念であり、
どれが本システムの予約名かは関心の外**である。「両方正しく動作するか」という問い方が、
守備範囲を予約名で切ったことが利用者の見え方と合っていないことを指していた。

あわせて、**退けた理由が事実として誤り**だった。実機で `su <user> -s /bin/zsh -l -c` と
`su <user> -s /bin/zsh -c` を並べて測ると、**`PATH` も `HOME` も完全に同一**で、違うのは `PWD` だけ
(コマンドが自分で `cd` するので影響しない)。`-l` を外す案は1箇所の変更で、予約名も env ファイルの
組も `TZ` も `LC_ALL` も同時に解決した。

## 今後どう活かすか

**1. 「上流がその集合を定義している」は、守備範囲を切ってよい根拠にならない。**
上流に集合の定義が在ることと、その集合が**直すべき範囲と一致すること**は別である。今回、02 の契約は
予約名の集合を正しく定義していたが、それは「利用者の指定で差し替えさせない名前」という**別の目的**の
ための集合だった。**定義を引くときは、その定義が何のために作られたかまで引く。**

**2. 同じ根の欠陥は、直す前に「この根で壊れているものを全部数える」。**
`su -l` を越えられない変数を機械的に走査したのは、issue を起票する段(severity 「高」の同型走査が
義務になった段)になってからだった。**走査は起票の義務ではなく設計の入力**である。先に数えていれば、
予約名で切る案は最初から選ばれなかった。

**3. 検証の経路が本番の経路と違うと、壊れたまま合格する。**
`docker exec` はコンテナの環境をそのまま継ぐので、`printenv` で確かめると値が見える。
一方 `claude-dev start` がアタッチするのは tmux で、そちらでは見えなかった。**「コンテナ内で確認する」
と書いた手順は、利用者が実際に使う入口で踏まなければ意味がない。** 手順にその一文
(「`docker exec` で確かめて済ませないこと」)を明記した。

**4. 却下の理由は、退ける前に測る。**
`[DS-05]` の「`-l` を外すと `PATH` / `HOME` が変わる」は、`su` の一般論としてはありうるが、
**この環境で確かめてはいなかった**。1分の測定で覆る理由で案を1つ落としていた。
**判断を1つ捨てるコストが、それを測るコストより高いなら、測る。**
