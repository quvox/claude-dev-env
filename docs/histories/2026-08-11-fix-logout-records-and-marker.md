# 2026-08-11 `logout` の削除判定の記録と印の判定を直す

## 変更理由

**起点層は 01(`FR-env-03` 受入基準19)。** 直前の `task-fix-logout-zero-target-path` で0件の経路を
直したときに、その周辺で「消えていないものを消したと表示する」「確認できていないものを0件と数える」
経路が3つ残っていることが分かった。いずれも `D0-env-08` 項5「削除の失敗を握りつぶさない」と
`D0-scope-07` の観測点の定義「成功時と同じ表示・同じ終了コードになる」に反する。

**要件側に穴があったのは1つ**である: 受入基準19 は共有ボリュームについて
「空であることを**確認できた**」と書き、確認できなければこの経路に入ってはならないと課していたが、
**コンテナの集合については「無く」と世界の状態だけを書き、状態が不明なときの禁止を課していなかった**。
`docs/issues/099` は `origin_layer: 03` で起票されていたが、`/task-new` §2 の判定で **01 へ改めた**
(この欠陥を閉じるには要件に義務を1つ足す必要があり、03 だけでは閉じない)。

## 変更内容の要約

- `FR-env-03-19` の0件条件のうち**コンテナの集合**にも「無いことを確認でき」を課し、
  **確認できなかった場合はそのことを「消えなかった資源」として受入基準18 に従って列挙し、
  終了コード 1 で終わる**ことを課した(引けなかった実行の終了コードが 0 → 1 に変わる)。
- 02 に3点足した: 契約のエラーケース「`logout` が削除対象の Claude コンテナの集合を引けなかった」、
  `logging.md` の「削除対象の Claude コンテナの集合を引けなかった」(WARN)、
  同じ文書の共通制約への**「削除した資源」の外延**(消えたことを確認できた資源だけ / 同じ資源を
  両方の一覧に出さない / 残したものの表示を削除の成否で条件づけない)。
- 実装(`claude-dev` / `claude-dev-mac` の `logout` 分岐、両 OS でバイト単位で同一)で
  手順4 の問い合わせの成否を捨てないようにし、手順6・手順10 の「空」判定を**位置**
  (1行目が印 / 2行目以降が中身)へ改め、**手順10 に一時コンテナの終了ステータスの条件**を加え、
  消去を確認できなかった資源を「削除した資源」に記録しないようにし、
  削除に失敗した実行でもラベル無しコンテナの表示を出すようにした。

## 検討した代替案

| 論点 | 採用した案 | 棄却した代替案 | 棄却の理由 / 崩れる条件 |
|---|---|---|---|
| コンテナの集合について「無い」と「無いことを確認できた」を区別するか(概念1) | 区別する | 非対称のまま(共有ボリュームだけ「確認できた」) | 非対称に技術的な根拠が無い。どちらも Docker への問い合わせが失敗しうる。崩れる条件: `docker ps` の失敗が起こらないと判定できたとき(filter の構文エラーや部分的な権限エラーは daemon が生きていても起こるので、現時点で判定できない) |
| 引けなかったときの振る舞い(概念2) | 0件経路に入らず確認へ進み、**引けなかったこと自体を消えなかった資源に数えて終了コード 1** | 何も削除せず即座に 1 で中止する | 共有ボリュームの検査は成功しているのに**認証を消す手段が失われる**。崩れる条件: 「`logout` は認証が消えれば成功」という定義を採り、コンテナの取りこぼしを失敗に数えないと決めたとき |
| 「削除した資源」の外延(概念3) | 消えたことを確認できた資源だけ。同じ資源を両方の一覧に出さない | 明文化しない(共通制約の読みに委ねる) | 従来の制約は成功の見出しの文言についての規定と読めたため、資源ごとの一覧に対する規定として実装に届いていなかった。崩れる条件: 「削除した資源」を「削除を試みた資源」の意味で使う設計へ変えたとき |
| 「印以外の行」の外延(概念4) | 印の行より後ろ(1行目が印 / 2行目以降が中身) | 文字列一致で除く(従来) | 内容で除くと `/auth/__CLAUDE_DEV_AUTH_LISTED__` を印と区別できず、中身があるのに空と判定する。崩れる条件: 一時コンテナが印より前に別の行を出すようになったとき |
| 削除に失敗した実行でラベル無しコンテナの警告を出すか(論点1) | 出す(4件目の欠陥をこのタスクに畳む) | `docs/issues/101` として別タスクにする | 直す場所が同じ 10 行の中にあり、概念3 で手順11 の表示そのものを書き直すので同じ降下で触る。崩れる条件: 受入基準17 に「削除が成功したときに限る」という条件が実は意図されていたと分かったとき |
| 記録の排他をどこで担保するか([DS-05]) | 呼び出し側(`logout` の手順10) | `MODULE-cli-common-destructive` に番人を置く | 同じ形の二重記録は `reset` に無く、共有基盤を変えると `reset` へ波及する。崩れる条件: 3つ目の呼び出し元ができたとき、または `reset` に同型が見つかったとき |
| 失敗に記録する表示名([DS-03]) | `destructive_plan` と同じ名前 | 理由を添えた `（消去を確認できず）` 付きの名前 | 記録関数は**名前が一致した予定行だけ**を消すので、違う名前だと予定側が「(未着手)」として残り、**同じ資源が結果表示に2行出る**(実装中に実測)。崩れる条件: `destructive_report` が予定と結果を名前以外で対応づけるようになったとき |
| 手順10 の終了ステータスを条件にするか(独立レビューの指摘) | 条件にする | 印だけを見る(従来) | 渡すコマンドの**最後が列挙**なのでコンテナの終了ステータスは `ls` の状態であり、`rm -rf` の状態ではない。見ないと印の直後に列挙が失敗した場合を「消去に成功して空になった」と読み替える(**実測で、修正前は exit 0 で「削除しました」と報告していた**)。崩れる条件: 一時コンテナのコマンドの最後が列挙でなくなったとき |
| 実機 E2E-01 手順8 を誰が流すか | 前タスクの `sheet.md` 論点4 の裁定(案A)を同型として適用し、残務へ回した | 新しくシートに載せて問う | 状況・証拠の種類・破壊の対象がまったく同じで、`delegation.md` §1 の「過去の回答が settles する項目はシートに載せない」に当たる。崩れる条件: 隔離ハーネスで再現できない経路が対象に入ったとき |
