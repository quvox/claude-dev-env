# 005 解釈できないボディを中継する経路が AC-03 の保証と食い違う

## 事象

`docker-proxy` はコンテナ作成要求のボディが JSON として解釈できない場合、**検査せずにそのまま
上流の Docker Engine へ中継する**(`docker-proxy/main.go:493`〜`496` が警告ログを出して `return nil`)。
これは意図的な設計で、01 と 03 の双方に明記されている。

- `01-requirements/functional.md` FR-env-07 受け入れ基準8(異常系):
  「IF リクエストのボディが解釈できないならば、システムはそれを中継してよい(独自解釈で誤って
  弾かない。最終判断は Docker Engine が行う)」
- `03-impl/contracts/docker-api.md`「既知の制限」:
  「独自解釈で正常な操作を弾かない代わりに、検査をすり抜ける要求が Docker Engine まで届く」

一方、00 層の受け入れ基準は無条件の保証として書かれている。

- `00-requests/acceptances.md` AC-03:
  「期待される結果: …特権コンテナ・ホストのネットワークやプロセス空間の共有は**拒否**される」
  「こうなったら不合格: ルートディレクトリの持ち込みや特権コンテナが通ってしまう」

**解釈できないボディに特権指定やルート bind が含まれていれば、それは拒否されずに通る。**
したがって AC-03 の「こうなったら不合格」に該当する状態が、仕様上許容された経路として存在する。

## なぜ今すぐ直さないか

- 直すとすれば **fail-closed(解釈できないボディを拒否する)への変更**であり、
  観測可能な振る舞いが変わる。`task-docs-restructure` は「コードを1行も変更しない」タスクなので
  範囲外である。
- 現在の挙動は `D0-sec-05`(委任: Docker API 検査の厳密さと安全側の倒し方)の範囲で選ばれたもので、
  「独自パーサで正常な操作を誤って弾かない」ことを優先している。安全性と可用性のトレードオフであり、
  どちらへ倒すかは**人間の判断**である。

## 論点(人間の判断が要る)

解釈できないボディに対して、

- **A: 現状維持**(中継する)。AC-03 に「ボディが解釈できる要求について」という限定を付け、
  00 の保証を実態に合わせる。→ 00 層の編集が必要。
- **B: fail-closed へ変更**(解釈できないボディは拒否する)。AC-03 の保証をそのまま守る。
  → コード変更。正常な操作を誤って弾くリスクを受け入れる。
- **C: 中間**(コンテナ作成と exec 作成の要求に限って fail-closed、他は現状維持)。
  危険な操作を持ちうるエンドポイントだけ厳しくする。→ コード変更。影響範囲は B より狭い。

実際に解釈できないボディが発生する頻度は測定していない。判断の前に、
`docker-proxy` の警告ログ(`main.go:493`)の出現実績を確認すると材料になる。

## 影響

- 悪用には「Docker Engine は受理するが docker-proxy の JSON パーサは失敗する」ボディを作る必要が
  あり、容易ではない。ただし本システムの隔離は**この1本の境界に依存している**(`SR-04` / `D0-sec-06`)
  ため、穴の存在自体を把握しておく価値がある。
- 利用は信頼できる社内開発用途に限る前提(`SR-05`)があるため、緊急度は高くない。
