# 029 `logout` が確認なしで全プロジェクトのセッションを落とす

## 事象

`logout` は認証を消す前に、**イメージから逆引きした全 claude-dev コンテナ**(稼働中・停止中の
両方、**プロジェクトを問わない**)と docker-proxy を強制削除する(`claude-dev:638`〜`:643`)。

```
docker ps -a --filter "ancestor=$IMG_CLAUDE" --filter "ancestor=$IMG_CLAUDE_VNC" -q | xargs -r docker rm -f
```

**確認プロンプトは無い。** 同じ破壊性を持つ `reset` には確認プロンプトがある
(`claude-dev:1377`〜`:1382`)のに対し、`logout` は `claude-dev logout` の1コマンドで即座に実行される。
表示は「実行中のコンテナを停止中...」の1行だけで、**どのコンテナを消すかは示されない**。

再現手順:

1. `~/a` と `~/b` の2つのディレクトリでそれぞれ `claude-dev start` する。
2. `~/a` で作業中(tmux に未保存の実行がある)のまま、別の端末で `claude-dev logout` を実行する。
3. `~/b` だけでなく `~/a` のコンテナも消えていることを確認する(確認は求められない)。

## 影響

他プロジェクトの**実行中の作業が予告なく失われる**(コンテナ内の tmux セッション・
未コミットの作業・起動中の compose サービス)。`/workspace` はホストのディレクトリなので
ファイル自体は残るが、実行中の処理と tmux の状態は失われる。
`D0-scope-07` の起票の閾値 (a)「データの破壊」に当たり、(b) を満たす
(`issue 020` は同時実行のレース、`issue 025` は削除失敗と残存コピーで、**本件を含まない**)。

severity を「中」とした根拠: ファイルは失われず再 `start` で復旧できる。一方で
**同じ破壊性の `reset` が確認するのに `logout` はしない**という非対称は、利用者の予想を裏切る。

## 原因の見当

推測: 「共有ボリュームが使用中だと消せない」という技術的制約から先にコンテナを消す手順にし、
その破壊性が `reset` と同等であることが意識されなかった。

## 正はどちらか

| 観点 | 実装(03)はどう言っているか | 要件・設計(00〜02)はどう言っているか | 判定 |
|---|---|---|---|
| 破壊的操作の確認 | `logout` は確認しない / `reset` は確認する(`MODULE-cli-logout` / `-reset` の「既知の制限」に事実として記述) | 00〜02 に「`logout` は確認しないと決めた」記述は**無い**(走査済み)。`MODULE-cli-reset` の実装上の判断1 は「破壊的操作なので確認プロンプトを必須にする」と述べている | **設計が正**(同じ方針が `logout` に適用されていない) |

## 対処案

| 案 | 内容 | 影響範囲の見込み |
|---|---|---|
| A | `logout` に**削除対象のコンテナ名を列挙した確認プロンプト**を足す(`reset` と同じ形。非 TTY はキャンセル) | `claude-dev` / `claude-dev-mac` の `logout`、`MODULE-cli-logout`、`FR-env-03` の受入基準 |
| B | 削除対象を**カレントディレクトリのコンテナだけ**に絞る(共有ボリュームが使用中なら、その旨を表示して中止する) | 同上。ただし「全体をログアウトする」という現在の意味が変わる |
| C | 現状を仕様として確定させ、`FR-env-03` に「`logout` は全プロジェクトのコンテナを削除する」と明記し、`logout` の表示に警告を足す | ドキュメント + 表示文 |

推奨は **A**(`reset` との非対称を解消する)。
