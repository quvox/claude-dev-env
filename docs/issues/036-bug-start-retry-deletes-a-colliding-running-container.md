# 036 `start` の再試行前の後片付けが同名の稼働中コンテナを削除する

## 事象

`claude-dev` の `start` は `docker run` が失敗すると、**再試行の前に必ず**次を実行する。

```
docker rm -f "$NAME" >/dev/null 2>&1 || true   # 作成途中コンテナを掃除
```

(`claude-dev:928`)

この `docker rm -f` は **「自分が作りかけたコンテナかどうか」を確認しない**。`$NAME` は
`basename $(pwd)` から導く名前で、パスを区別する情報を持たない(`docs/issues/028`)。したがって
**同名の稼働中コンテナが他方に存在する状態で `docker run` が名前衝突で失敗すると、
その稼働中コンテナを削除する**。

再現の筋道(いずれも `~/a/web` と `~/b/web` のように **basename が同じ2つのディレクトリ**、
または同じディレクトリでの同時実行):

1. `is_running "$NAME"` の判定(`claude-dev:715` 付近)を2つのプロセスが同時に通り抜ける
   (排他機構が1つも無い = `docs/issues/020`)。
2. 先行が `docker run` に成功してコンテナを作る。
3. 後続の `docker run` が `Conflict. The container name "/<NAME>" is already in use` で失敗する。
4. 後続が `docker rm -f "$NAME"` を実行し、**先行が作ったコンテナを削除する**。
5. エラー文言が「ポート競合」に当たらないため後続は再試行せず `exit 1`(`claude-dev:936`〜`:938`)。
   結果として**どちらのプロセスも動くコンテナを残さない**。

現在の 03-impl はこの局面を `MODULE-cli-start`「並行性」で
「先に `docker run` した方が勝ち、もう一方は名前衝突で失敗する」とだけ書いており、
**勝った側のコンテナが消える**ことを書いていない。

## 影響

削除されるのは**作業中の開発コンテナ**である。`docker rm -f` は稼働中でも強制削除するため、
コンテナ内の tmux セッション・実行中の `claude` / orchestrator・`/workspace` 以外に置いた
一時ファイルが失われる。`/workspace` はホストの bind マウントなのでソースコードは残るが、
**コミットしていない作業のうちコンテナ内にしかない状態(tmux のスクロールバック・
`.orchestrator/` 以外の一時生成物・実行中の worker)は失われる**。

`docs/issues/020`(排他機構が無い)の「同じディレクトリで `start` を2つ」の行は
観測結果を「一方が名前衝突で失敗する」としか書いておらず、**この被害を含まない**。
`docs/issues/028`(名前の一意性)も「既存コンテナへ再接続される」ケースを扱っており、
**削除は含まない**。よって `D0-scope-07` の起票の閾値
「(a) データの破壊 / (b) その被害を説明する issue がまだ無い」の両方を満たす。

利用者が失うのは作業状態であり、かつ**失敗表示は「コンテナ起動に失敗しました」だけで
「他方を消した」ことは表示されない**ため、severity は「高」。

## 原因の見当

コメント(`claude-dev:928`)が「作成途中コンテナを掃除」と書いているとおり、**意図は
自分が作りかけた残骸の掃除**である。noVNC ポート競合での再試行を成立させるために置かれた
処理だが、**失敗理由を問わず、また対象が自分の作ったものかを問わず**実行される。
**推測**: 名前衝突は「そもそも起きない」(直前に `is_running` を見ている)と想定していた。

## 正はどちらか

**実装が誤り。** `FR-env-01` は各プロジェクトが独立したセッションを持つことを求め、
`NFR-scale-01` は名前がプロジェクト間で衝突しないことを求めている。他方の稼働中コンテナを
消す振る舞いを要求している記述は 00〜02 に無い。

## 対処案

| 案 | 内容 |
|---|---|
| A | 後片付けを**自分が作ったときだけ**に限る(`docker run` の出力が名前衝突を示す場合は `rm` せず、既存コンテナへの attach か明示エラーへ倒す) |
| B | `docker run` の直前に `docker create` で名前を予約し、衝突を検出したら何も消さずに終わる |
| C | 名前にパスのハッシュを含めて衝突自体を無くす(`docs/issues/028` の対処と一体で行う) |

A が最小。C は `028` と同時に扱うと根本解決になる。**`task-impl-depth` はコードを1行も
変更しないタスクなので、いずれも別タスク**である。本 issue が閉じるまで、
`MODULE-cli-start`「並行性」には**削除まで含めた事実**を書いておく必要がある。

## 裁定の記録(2026-08-04)

**人間の裁定: 案A(`task-impl-depth` は閉じ、コード修正は別タスク)。**
`task-impl-depth` は「コードを1行も変更せず 03-impl の深度を上げる」タスクであり、本件はその過程で
見つけた別件である。`MODULE-cli-start` の「並行性」「既知の制限」に**事実を記録**した上で、
**次のタスクで優先的に修正する**(重大度は「高」のまま。`docs/issues/028` と同じ根なので
一意化と併せて直すのが効率的)。
