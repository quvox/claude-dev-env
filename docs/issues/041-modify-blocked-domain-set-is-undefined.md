# 041 「ブロック対象ドメイン」の集合が仕様のどこにも定義されていない

## 事象

ネットワーク隔離の受け入れ基準と目標値が、いずれも定義されていない集合を参照している。

| 出どころ | 記述 |
|---|---|
| `NFR-sec-02`(`docs/01-requirements/non-functional.md:41`) | 目標値 = 「**ブロック対象ドメイン**へ到達できないこと」 |
| `FR-env-05` 受入基準4 | 「IF **ブロック対象ドメイン**の名前解決に失敗したならば、システムはその1件だけをスキップして残りの適用を続けなければならない」 |
| `FR-env-05` 受入基準6 | 「IF 適用直後の到達性スモークテストで想定外の結果(**ブロック対象へ到達できた**、または Anthropic API へ到達できない)が出たならば、システムは警告行を出力しなければならない」 |

**「ブロック対象ドメイン」がどの集合を指すのかは 00 にも 01 にも書かれていない。**
`FR-env-05` 受入基準4 の書き方(「名前解決に失敗した1件をスキップし、当該ドメインは塞がれないまま
残る」)から、方式は**許可リストではなく拒否リスト**であることが読み取れる。したがって集合の中身は
「許可リストの補集合」として導出できず、**列挙が必要**である。

## この指摘が前回棄却されていた経緯(重要)

2026-08-04 の前回の `/doc-check ssot` は、同じ指摘(「ブロック対象ドメインの集合が 00/01 に無い」)を
**誤検知として棄却**し、理由を「`D0-sec-04` が**委任**として実装へ委ね、ガードレール3件を持つ」と
記録した。**この棄却理由は成立しない。**

`D0-sec-04` の委任範囲は次のとおりで、**集合の中身は含まれていない**:

> 委任範囲: ブロック対象の**表現方法**(ホスト名指定か IP 集合か)、名前解決のタイミング(起動時の
> 一回解決か追従か)、どのチェインに規則を置くか。

ガードレール3件も「適用に失敗しても起動を止めない」「成否が起動ログから判別できる」
「**既定の通信(Anthropic API 等)を塞がない**」であり、**塞ぐ対象**については何も定めていない
(最後の1件は塞いではならない対象を定めるもので、逆向きである)。

## 影響

- `NFR-sec-02` は目標値と測定方法を持つ形をしているが、**集合が未定義なので合否を判定できない**。
  `FR-env-05` 受入基準4・6 も同様にテストの入力を決められない(check C8 / D13)。
- 実装者は遮断対象を**発明**することになる。安全境界そのものを実装が決めている状態である。
- 現に集合はコード側にしか存在しない。`D0-sec-04` の報告義務(「決めた内容を該当機能の
  『実装上の判断』表に `D0-sec-04` と共に記録する」)が、集合の中身についても果たされているかを
  確認する必要がある(`MODULE-firewall-init`)。

## 原因の見当

**推測**: `D0-sec-04` は「実装方式」の委任として書かれており、**方式を決めれば対象も決まる**という
前提が置かれていた。実際には方式(表現方法)と対象(集合)は独立で、対象は要件レベルの判断である。

## 正はどちらか

**人間判断。** 遮断対象の集合を決めるのは**セキュリティ方針の判断**であり、
`D0-scope-07`(コードから一意に読み取れる事実だけを書く)の委任範囲外である。
「実装が持っている集合をそのまま仕様に写す」ことは可能だが、それは
**現状の集合が妥当だという判断を追認する**ことになるため、自動修正の対象にしない。

| 案 | 内容 |
|---|---|
| A | `MODULE-firewall-init` の実装が持つ集合を 03 に明記し、`D0-sec-04` の委任範囲に「集合の中身」を明示的に追加する(= 実装が正。**集合の妥当性は別途レビューが必要**) |
| B | 00 に「ブロック対象ドメインの集合」を決定事項として起こし、01 の `NFR-sec-02` / `FR-env-05` からそれを参照する(= 要件レベルで決める) |
| C | 方式を拒否リストから**許可リスト**へ改める(`NFR-sec-02` の目標値が「許可リスト以外へ到達できないこと」になり測定可能になる。**コード変更 → 別タスク**) |

## ★2026-08-04 追記: 実装を読んだ結果、A/B/C は前提がずれている(案D を追加)

`scripts/init-firewall-claude.sh:36`〜`:64` を読むと、集合は**利用者が編集する前提の既定リスト**である。

```
# =============================================================================
# ここにブロックしたいドメインを追加してください
BLACKLIST_DOMAINS=(
    # --- 本番環境（誤アクセス防止）---
    # "production-api.yourcompany.com"        ← コメントアウトされた雛形
    ...
```

既定は 20 件で、**paste 系9件 / webhook テスト系3件 / トンネル系4件**(+ 本番環境の雛形は
コメントアウト)という**カテゴリ単位のテンプレート**である。`MODULE-firewall-init.md:61` も
「設定は環境変数ではなくスクリプト内配列 `BLACKLIST_DOMAINS` を編集する」と記述している。

したがって本 issue の論点は「**現状の集合が妥当かを追認するか**」ではない。
**01 が「設定で与えられる集合」と書いていないこと**が欠落の実体である。

| 案 | 内容 |
|---|---|
| **D** | **01 の語を定義する**:「ブロック対象ドメイン = **設定で与えられるドメイン集合**(既定は同梱の20件)」。`NFR-sec-02` の目標値を「**設定に列挙したドメイン**へ到達できないこと」にすると、集合の中身を要件で固定せずに測定可能になる。既定20件はカテゴリとともに `MODULE-firewall-init`(03)へ列挙する。`docs/02-design/system.md:58` は既に「ブラックリスト型ファイアウォールの構成」と書いており整合する |

**D なら人間が「どのドメインを塞ぐべきか」を裁定する必要が無い**(それは運用時に利用者が決める)。
`D0-sec-04` の委任範囲(表現方法・解決タイミング・チェイン)にも触れずに済む。
A は「集合の中身」を委任へ足す形で、既定リストを仕様上の固定値に近づけてしまう点が D と違う。
