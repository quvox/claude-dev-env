# 044 terminology.md の閾値定義に承認の記録が無い

## 事象

`docs/00-requests/terminology.md` が version 1.0.0 → **1.1.0** で用語 **「資源逼迫」** の行を追加し、
次の閾値付きの定義を与えている(現在 1.1.0、`updated: 2026-08-04`)。

> ゲスト VM の QEMU プロセスの CPU 使用率が、割り当て上限(`-smp` の値)に対して 60% 以上
> (既定 `VM_HEALTH_CPU_PCT`)である状態が、15 秒周期(既定 `VM_HEALTH_INTERVAL`)で
> 12 回連続(既定 `VM_HEALTH_SUSTAIN`。合計約3分)観測された状態

同時に下流の 2 箇所が**この定義を指す文へ書き換わっている**(いずれも PATCH bump)。

| ドキュメント | version 遷移 | 変わった箇所 |
|---|---|---|
| `docs/01-requirements/non-functional.md` | 1.2.0 → 1.2.1 | `NFR-ops-01` の「要件」列が「資源逼迫(`terminology.md` に閾値の定義あり)」になった |
| `docs/01-requirements/functional.md` | 1.3.1 → 1.3.2 | 先頭コメントの残課題一覧が「資源逼迫(`terminology.md` の定義: …)」を引くようになった |

**この一連の変更について、次のいずれにも記録が無い。**

- `docs/histories/`(2026-08-04 の3件はいずれもこの変更を挙げていない。
  `2026-08-04-doc-check-ssot-impl-depth-recertification.md` は「`docs/issues/017` に測定不能語を
  7 箇所**追加した**」とだけ書いており、terminology.md を直したとは書いていない)
- `docs/tasks/task-impl-depth/memo.md` の「進捗メモ」「自動修正 8 件」の一覧
- `terminology.md` 自身の合格証(`verified.version` が **1.0.0** のまま = **失効**)

## 影響

3点ある。

1. **00 層の承認手続きの逸脱。** `.claude/directions/00-requests.md` は
   「**この層は人間のもの。AI は差分を起案してよいが、00 への意味のある変更はすべて人間の合意が要る**」
   と定める。用語集は「**全層がこの用語集に従う**」規範であり、そこに閾値を書くことは意味のある変更である。
2. **未回答の決定シート論点の先取り。** `task-impl-depth` の決定シート論点6(**未回答**)は
   `docs/issues/017`(測定不能語)/ `041` / `043`(NFR の測定可能性)をどう閉じるかを人間に問うている。
   「資源逼迫」に定義を与えることはその答えの一部であり、回答前に SSOT へ入っている。
3. **委任範囲外。** `D0-scope-06` の委任は「軽微な曖昧さの穴埋め」に限られ、
   ガードレールが「**要件・契約・観測可能な振る舞いに関わる食い違いは委任範囲外**」と定める。
   本件は `FR-env-08` 受入基準4 と `NFR-ops-01` の測定可能性を変えるので該当しない。
   `D0-scope-07` の委任範囲は `03-impl/relations/` と `contracts/` だけで、00 を含まない。

**内容の誤りではない。** severity「高」は手続きと合格証の失効に対するものである。

## 原因の見当

`docs/issues/017` の追記(2026-08-04)が「`資源逼迫` は 01 → 02 の 5 箇所へ伝播しており、
`FR-env-08` 受入基準4 を測定可能にするときは 02 の 5 箇所を同じ下降で直す必要がある」と
**やるべきことを具体的に書いた**ため、その下降のうち**最上流の1歩だけ**が、
論点6 の回答を待たずに実行された、という**推測**。02 の 5 箇所と `FR-env-08` 受入基準4 の本文は
手つかずなので、下降は途中で止まっている(**事実**)。

## 正はどちらか

**定義の内容については実装が正で、記述はそれと一致している。**

| 観点 | 実装(03)はどう言っているか | 要件・設計(00〜02)はどう言っているか | 判定 |
|---|---|---|---|
| 閾値そのもの | `scripts/vm-healthd.sh:28`〜`:30` が `VM_HEALTH_INTERVAL:-15` / `VM_HEALTH_CPU_PCT:-60` / `VM_HEALTH_SUSTAIN:-12`(コメントに `12×15s≒3分`)。認証済みの `MODULE-vm-mode-healthd`(処理の流れ 2〜4・引数表)も同じ値を書く | `terminology.md` 1.1.0 の定義と**一致する** | **一致(食い違いは無い)** |
| 定義を 00 に置いてよいか | — | `.claude/directions/00-requests.md`「00 への意味のある変更は人間の合意が要る」 | **要確認**(人間の承認が無い) |
| `FR-env-08` #4 / `NFR-ops-01` を測定可能とみなすか | 実装は閾値を環境変数で上書きできる(要件の値として固定されていない) | `FR-env-08` 受入基準4 の本文は「資源逼迫を検知して利用者へ提示しなければならない」のままで、閾値も観測期間も書いていない | **要確認** |

## 対処案

| 案 | 内容 | 影響範囲の見込み |
|---|---|---|
| A | **承認する。** `terminology.md` 1.1.0 を人間が承認し、`/doc-check` が合格証を発行する。あわせて `FR-env-08` 受入基準4 と 02 の5箇所(`architecture.md:87` / `system.md:61` / `logging.md:88`,`:100` / `relations.md:98`)を同じ下降で用語集参照へ揃え、`docs/issues/017` から「資源逼迫」7箇所を外す | 00×1・01×2・02×4・(03 は既に一致)。`logging.md:88`「検知した指標と閾値」の指標と閾値もこの定義で確定する |
| B | **差し戻す。** 1.1.0 の行を削除して 1.0.0 相当へ戻し、`non-functional.md` / `functional.md` の参照文も外す。定義は論点6 の「測定可能性タスク」で 00 から改めて下降させる | 00×1・01×2。`docs/issues/017` / `043` は現状のまま残る |
| C | **定義の置き場所を変える。** 閾値は環境変数で可変なので 00 の用語集には「CPU 使用率が既定の閾値を一定時間連続で超えた状態(閾値と観測期間は `02-design` が定める)」だけを置き、数値は 02 へ降ろす | 00×1・02×1。要件が実装の既定値に固定されない |

**推奨は A** — 定義はコードと 03 に一致しており、削除すると測定不能な語に戻るだけである。
ただし A は「実装の既定値を要件の閾値として追認する」ことを含むので、**人間の承認が必要**であり、
`/doc-check` の委任では行えない。**C は A と B の中間として検討の価値がある**
(閾値が環境変数で可変であるという事実と、00 が実装の既定値に縛られない形を両立できる)。
