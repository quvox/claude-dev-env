## 事象

| 出どころ | 記述 |
|---|---|
| `FR-env-07` 受入基準8(異常系) | 「IF リクエストのボディが解釈できないならば、システムはそれを**中継してよい**(独自解釈で誤って弾かない。最終判断は Docker Engine が行う)」 |
| `D0-sec-05`(委任)の**委任範囲** | 「…**解釈できない入力を通すか止めるか**」 |
| `D0-sec-05` の**ガードレール** | 「拒否すべき操作(作業領域外のホストバインド・特権・ホストのネットワーク/プロセス空間)を**通してはならない**」 |

委任範囲は「通すか止めるか」を選ばせている一方、ガードレールは「禁止操作を通すな」と課している。
**ボディが解釈できないなら、そこに禁止操作が含まれるかどうかを判定できない**ので、
「通す」を選ぶとガードレールを満たせない場合がある。**委任範囲とガードレールが同じ論点で
食い違っている。**

「最終判断は Docker Engine が行う」という受入基準8 の根拠も、`NFR-sec-01` の隔離モデルと合わない:
docker-proxy は**ホストの Docker を守るための検査点**であり、Docker Engine は禁止操作を
拒否する主体ではない(Engine から見れば正当な API 呼び出しである)。

## 影響

- **理屈のうえでは、検査を迂回する経路になりうる**: コンテナ内から意図的に「解釈できない」形の
  ボディで bind mount や特権付き `docker run` を要求できれば、proxy を素通りする。
  実際に迂回できるかは実装(どこまでを「解釈できない」と扱うか)に依存する。
- `E2E-03`(危険な `docker run` → 拒否)は**正常に解釈できるボディ**しか試していないため、
  この経路はテストで覆われていない。
- `D0-sec-05` は「判定に必要な情報が手元に無い場合は、その事実を該当機能の**「既知の制限」に
  書くこと**」も課している。`MODULE-docker-proxy-serve` にその記述があるかの確認も要る。

## どちらが正か(人間の判断が要る)

| 案 | 内容 | 影響 |
|---|---|---|
| A | **解釈できないボディは拒否する**(安全側)。受入基準8 を反転する | 正当だが proxy が解釈できない形の要求が壊れる。互換性の調査が要る |
| B | **委任範囲を狭める**: 「解釈できない入力を通すか止めるか」を委任から外し、ガードレールと矛盾しない形(たとえば「禁止操作に関係しうるエンドポイントだけ拒否、無関係なら通す」)を 00 で決める | エンドポイントの分類が要る |
| C | **現状を追認し、残存リスクとして `docs/pendings.md` に記録する** | 検査点に穴があることを明示的に受容する。`NFR-sec-01` の主張と整合するかの再確認が要る |

**推奨は B**。エンドポイント単位なら「解釈できない」が問題になる範囲は限定でき、
`FR-env-07` の他の受入基準(bind の判定など)と同じ粒度で書ける。

まず**実装が実際にどう振る舞うか**(何を「解釈できない」と扱い、そのとき何をするか)を
`MODULE-docker-proxy-serve` とコードで確認してから判断するのが順序として正しい。

## なぜ task-fix-destructive-scope で直さないか

同タスクの影響範囲は破壊的操作(`stop` / `logout` / `reset` と排他)であり、
`FR-env-07` 受入基準8・`D0-sec-05`・docker-proxy はいずれも含まない。
CLAUDE.md 原則8 に従い起票にとどめる。
