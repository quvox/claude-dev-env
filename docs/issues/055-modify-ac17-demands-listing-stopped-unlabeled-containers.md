# 055 受入基準17 が停止中のラベル無しコンテナの表示まで求めている

## 事象

`FR-env-03` 受入基準17(`docs/01-requirements/functional.md`):

> WHEN `logout` / `reset` が削除対象を**集合として列挙する**とき、Claude コンテナは本システムの
> **管理ラベルを持つものに限らなければならない**(…)。管理ラベルを持たない Claude コンテナは
> 削除せず、**その名前と「本変更より前に起動した可能性がある」ことを表示して残さなければならない**

**稼働中に限定していない。** 一方で `docs/02-design/contracts/cli-container.md`
「残したものをどう列挙するか」は次のように書いている。

> **停止中のラベル無しコンテナは列挙できない**(`docker network inspect` は稼働中のコンテナしか
> 返さない)。これは意図した限界である(…)。**この限界を表示にも書く**

したがって:

- **削除しない**という前半の義務は、停止中のコンテナについても満たされている(消していない)。
- **名前を表示する**という後半の義務は、**停止中のものについては満たされていない**。

`docs/03-impl/relations/MODULE-cli-logout.md` / `MODULE-cli-reset.md` の「既知の制限」は
この限界を「なし(閾値の外)」として記録しており、**issue としては起票されていなかった**。

## 影響

本変更より前に作られて**停止中**のまま残っている Claude コンテナがある利用者は、
`logout` / `reset` の表示からその存在を知れない。次に `claude-dev start` で同名のコンテナを
起動しようとすると名前衝突で失敗する(`FR-env-01` 受入基準12)経路に入るため、
そこでは気づける。データは失われない。よって severity は「中」。

## 原因の見当

01 の受入基準を書いた時点では「残したものの列挙」を遊休判定の集合(= `claude-dev-net` に
接続している**稼働中**コンテナ)から流用する設計がまだ決まっていなかった。
02 で流用が決まったときに、01 側の条件へ「稼働中」を降ろさなかった(推測)。

## 正はどちらか

| 観点 | 01(要件)はどう言っているか | 02(設計)はどう言っているか | 判定 |
|---|---|---|---|
| ラベル無しコンテナの表示範囲 | 稼働中に限定していない(全部) | `docker network inspect` の制約により稼働中だけ。限界を表示にも書く | **要確認**(01 を実態へ合わせるか、02 を拡張して停止中も列挙するか) |

## 対処案

| 案 | 内容 | 影響範囲の見込み |
|---|---|---|
| A | `FR-env-03` 受入基準17 の表示義務を**稼働中のコンテナに限定**し、停止中は列挙していないことを表示する(現行実装と 02 の限界がそのまま正になる) | 01(`FR-env-03` 受入基準17)/ `MODULE-cli-logout` と `-reset` の「既知の制限」から本 issue の参照を外す |
| B | 停止中も列挙する: `docker ps -a` から**イメージ名ではなく命名規則**で候補を挙げ、管理ラベルの有無で分ける(**ラベルにもネットワークにも依存しない第3の識別手段が要る**ので、`docs/issues/028`(名前の一意性)と絡む) | 02 契約の「残したものをどう列挙するか」/ 実装2箇所 / `E2E-01` 手順8-5 |
| C | 現状のままとし `docs/pendings.md` へ受容として記録する | なし(01 の字面を満たさない状態が残る) |

**推奨は A**(02 が「意図した限界」と明記しており、`D0-env-08` の目的=他プロジェクトの資源を
巻き込まないことは停止中コンテナについても満たされているため。ただし
**受入基準の意味を変える判断なので人間が決める**)。
