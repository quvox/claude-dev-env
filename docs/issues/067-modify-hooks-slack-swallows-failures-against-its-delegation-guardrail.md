# 067 フック側の Slack 通知が委任のガードレールに反して失敗を無記録で握りつぶす

## 事象

`docs/03-impl/relations/MODULE-hooks-send-slack-message.md` は次の3つを同時に述べている。

1. **異常系**: 「Slack への POST 失敗 / API エラー | **握りつぶす。ログも残さない** |
   Claude の本処理は妨げない。**失敗に気づけない**」
2. **実装上の判断 #1**: 「通知失敗を非致命として握りつぶす(hook の失敗が Claude の作業を
   止めないようにする)| 根拠(委任ID): **`D0-orch-07`**」
3. **既知の制限**: 「POST 失敗をログに残さない | 届かないときの切り分けが難しい |
   関連 issue: **なし**」

しかし引用されている委任 `D0-orch-07`(`docs/00-requests/decisions/orch.md`)のガードレールは
次のとおりで、**2文ある**:

> - 制約(ガードレール): **通知の失敗で実行を止めないこと**(通知は補助であり、実行の可否を
>   左右させない)。**失敗を握りつぶす場合でも、利用者が状況を追える手段(ログ)を残すこと。**

実装上の判断 #1 が満たしているのは**第1文だけ**である。第2文(ログを残すこと)は満たしていない。

`docs/02-design/logging.md`「主要イベントのログ仕様」も同じ事象に対して
「**通知の送信失敗 | WARN | 失敗した旨のみ(トークンは出さない) | `FR-orch-07`(受け入れ基準5)**」
を要求している。実装(`scripts/sendslackmsg.sh`)は `curl -sS -X POST` の結果を検査せず、
成否にかかわらず何も出力しない。

再現手順:

1. `SLACK_BOT_TOKEN` に無効なトークンを設定してコンテナを起動する。
2. Claude Code のフックが発火する操作を行う。
3. Slack に通知が届かないが、**端末にもログにも何も現れない**ことを確認する。

## 影響

利用者は通知が届かない原因(コンテナ `settings.json` のマージ / トークンの権限 /
プロンプト一時ファイルの有無)を**切り分ける手掛かりを1つも得られない**。
既知の制限表が自らそう書いている。

**`docs/issues/013` はこの事象を覆っていない**。013 の対象は `MODULE-orchestrator-slack`
(オーケストレーター本体の Go 実装。通信エラーだけは標準エラーへ1行出す)であり、
`related` にも本モジュールは含まれていない。フック側(`scripts/sendslackmsg.sh`)は
**通信エラーすら出さない**ので、013 より状態は悪い。にもかかわらず**どの issue からも
追跡されていなかった**。

severity は「中」: 013 と同型・同程度である。振る舞い(Claude の本処理)は壊れておらず、
`FR-orch-07` 受入基準5「通知の送信に失敗したならば、システムは実行を止めてはならない」は
**満たしている**(この受入基準はログを要求していない)。`severity: 高` ではないので認証を妨げない。

## 原因の見当

**委任のガードレールが2文あり、報告義務が第1文しか確認していない**のが構造的な原因である
(推測ではなく、`D0-orch-07` の報告義務が「決めた内容を『実装上の判断』表に `D0-orch-07` と共に
記録する」としか書いておらず、**ガードレールを満たしたことの記録は求めていない**ことから読める)。
その結果、`D0-orch-07` を根拠として引用しながらガードレールの半分を外れている状態が、
「実装上の判断」表の書式のうえでは正しく見える。

`FR-orch-07` 受入基準5 が「止めてはならない」だけを課し、ログを課していないことも重なっている
(ログの要求は 00 の委任と 02 の設計にだけあり、01 に無い)。

## 正はどちらか

| 観点 | 実装(03)はどう言っているか | 要件・設計(00〜02)はどう言っているか | 判定 |
|---|---|---|---|
| 送信失敗で Claude の処理を止めるか | 止めない(`exit 0`) | `D0-orch-07` 第1文「通知の失敗で実行を止めないこと」 | **一致** |
| 送信失敗を記録するか | **何も記録しない** | `D0-orch-07` 第2文「利用者が状況を追える手段(ログ)を残すこと」/ `02-design/logging.md`「通知の送信失敗 → WARN」 | **設計が正**(実装が要求を満たしていない。`docs/issues/013` の同じ行と同じ裁定) |
| `FR-orch-07` 受入基準5 | 満たしている | 「実行を止めてはならない」しか課していない | **一致**(01 にはログの要求が無い) |

## 対処案

| 案 | 内容 | 影響範囲の見込み |
|---|---|---|
| A | `scripts/sendslackmsg.sh` が `curl` の HTTP ステータスと `ok:false` を検査し、失敗時に **WARN 相当の1行を標準エラーへ出す**(トークンは出さない)。`MODULE-hooks-send-slack-message` の異常系・既知の制限を実装へ揃える | `scripts/sendslackmsg.sh` + `MODULE-hooks-send-slack-message.md`。`docs/issues/013` と**同じタスクでまとめて直すのが自然**(同じ欠陥の2実装) |
| B | まず**記述だけ**を直す: 既知の制限表の「関連 issue」欄を本 issue で埋め、`D0-orch-07` のガードレール第2文を満たしていない事実を「実装上の判断」表へ明記する(コードは触らない) | `MODULE-hooks-send-slack-message.md` のみ。**原則2 は保たれる**(記述がコードに合う)が、ガードレール逸脱は残る |
| C | `D0-orch-07` のガードレール第2文に「ただしフック実装は対象外」という例外を足す(00 の変更なので人間の裁定が要る) | `docs/00-requests/decisions/orch.md` + 下流の合格証 |

**推奨は A**(`docs/issues/013` と同一タスクで扱う)。理由: 013 は既に「設計が正」と裁定済みで、
同じ設計要求(`logging.md` の WARN)を2つの実装が別々に破っている。片方だけ直すと
**同じ欠陥が2回起票される状態が続く**。**B は暫定策としてのみ**(ガードレール逸脱を可視化するが
解消しない)。**C は採らない**ことを推奨する — フックこそ利用者が直接触らない経路であり、
切り分け手段を落とす合理性が無い。
