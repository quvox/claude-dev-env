# 080 破壊的操作の条項に対応するユースケースが無い

## 事象

`docs/01-requirements/usecases.md` の UC-01〜UC-06 の基本フロー・代替フロー・例外フローに
`claude-dev stop` / `claude-dev logout` / `claude-dev reset` が**一度も現れない**。
UC-01 の事後条件も「プロジェクト専用コンテナで Claude Code が動作している」だけで、
セッションを終える旅程を持たない。

同ファイルの「シナリオ外要件」表(`docs/01-requirements/usecases.md:230` 付近)にも
`FR-env-01` / `FR-env-03` の行は無い。載っているのは `FR-env-09`(イメージ配布)/
`FR-orch-09`(自己検証)/ 非機能要件だけである。

その結果、`docs/02-design/system.md`「E2Eシナリオ一覧」の **E2E-01 の手順8**
(破壊的操作が「自分が作った資源」にだけ効くことの実機確認。
`FR-env-01` 受入基準 9・14〜27 / `FR-env-03` 受入基準 14〜23 を覆う)は、
**上流の UC を持たない検証**になっている。

## 影響

- **要件単位では欠落ではない**: `FR-env-01` は UC-01 に、`FR-env-03` は UC-01 / UC-06 に現れるので、
  `/doc-check` の A1(「各機能要件が最低1つの UC フローに現れる」)も
  A2(「上流の UC を持たない E2E シナリオを作らない」)も**機械的には通る**。
  破れているのは**条項単位**の対応であり、これを検査する規則は現在どこにも無い。
- 実害は「読者が `stop` の利用者旅程にたどり着けない」こと。破壊的操作は
  `docs/00-requests/decisions/env.md` の `D0-env-08` が5つの issue をまとめて閉じた重い領域で、
  条項は現在 `FR-env-01` が 27・`FR-env-03` が 23 ある。旅程が無いまま条項だけが増え続けると、
  「この条項は誰のどの操作を守るためのものか」を 01 の中で確かめられない。

severity を「低」とする根拠: 観測可能な欠陥は生じない(条項は 02 のカバレッジ表と
03 のテスト対応表で全件が追跡されており、実機確認の手順も存在する)。
壊れているのは**上流へのたどりやすさ**だけである。

## 原因の見当

UC-01〜06 は「開発者がシステムを使って開発する」旅程として書かれており、
**片付けは旅程の終わりであって目的ではない**ため、書き起こす動機が生まれなかったと見られる(推測)。
`FR-env-09` と `FR-orch-09` については同じ判断が「シナリオ外要件」に理由つきで明記されているので、
**判断そのものは前例があり、記録だけが無い**状態である。

## 正はどちらか

| 観点 | 実装(03)はどう言っているか | 要件・設計(00〜02)はどう言っているか | 判定 |
|---|---|---|---|
| 破壊的操作の旅程 | `docs/03-impl/tests/e2e.md` の E2E-01 手順8 が 30 を超える確認項目を持つ | `usecases.md` はどのフローにも書いておらず、シナリオ外要件にも載せていない | **要確認**(人間が決める) |

## 対処案

| 案 | 内容 | 影響範囲の見込み |
|---|---|---|
| A | **UC-01 に代替フローを足す**(「A5 セッションを終える → `claude-dev stop` でコンテナとそのセッションが作った資源が片付く」)。`logout` / `reset` は「シナリオ外要件」に理由つきで載せる | `docs/01-requirements/usecases.md` 1ファイル。02 の E2E-01 の対応 UC は変わらない |
| B | **3コマンドすべてを「シナリオ外要件」に理由つきで載せる**(旅程を増やさない) | 同上。記録だけで済むが、「利用者が最も使う `stop` に旅程が無い」状態は残る |
| C | **破壊的操作の UC を新設する**(UC-07)。E2E-01 手順8 を E2E-07 として切り出す | `usecases.md` / `02-design/system.md` の E2E 一覧 / `03-impl/tests/e2e.md`。E2E-01 が長すぎる問題も同時に解ける |

**推奨は A**(最小で、`FR-env-09` の先例と同じ書き方に揃う)。
ただし C は「E2E-01 が手順16 まで伸びている」という別の読みにくさも同時に解くので、
E2E-01 をこれ以上伸ばす変更が次に来るなら C を選ぶ価値がある。
