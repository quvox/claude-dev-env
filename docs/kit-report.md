# キット診断報告書 — なぜ収束しないのか、どう直すのか

- 作成日: 2026-08-08
- 対象: `CLAUDE.md` / `.claude/directions/` / `.claude/skills/` / `.claude/templates/` / `.claude/scripts/` / `.claude/improvements/`
- 位置づけ: 仕様ドキュメント(SSOT)ではない。キット(規範)そのものの診断と改修提案。
- 改修方針: `/kit-improve` を経由せず、根本修正として直接適用する(人間の決定による)。

## 1. 結論

**製品(claude-dev)は既に動いている。収束していないのは、製品ではなく規範と文書である。**

規範は「欠陥を見逃さないこと」を最大化する方向に成長し続けた結果、**欠陥を消化する速度より速く欠陥を生成する系**になった。停止条件がどこにも定義されていないため、原理的に終わらない。

直すべきは個々のルールの中身ではなく、**系の3つの構造欠陥**である。

1. 生成が消化を上回るループに減衰項が無い(第3章 原因1)
2. 成果物が製品からキットへすり替わり、その入れ替わりを測る基準線も失った(原因2)
3. 「プロジェクトの完了」が定義されていない(原因3)

## 3. 発散の機構(4つの原因)

### 原因1 — 減衰項の無い正のフィードバックループ

```
検査を走らせる(/doc-check・/codex-audit・/relations・CS/SH/CG)
   → 指摘が出る → issue になる → タスクになる
   → タスクが SSOT を動かす
   → SSOT が動くと 他タスクの変更指示と verified 65件が無効になる(CLAUDE.md §3)
   → 再検査が必要になる → 最初に戻る
```

1件直すと平均1.5件生まれる系は止まらない。しかもループの各段が規範で**義務化**されているため、途中で降りる出口が無い。`/doc-check` は反復5回まで自動で回り(`doc-check/SKILL.md:522`)、反復そのものが増幅器になっている。

### 原因2 — 成果物のすり替わり

`.claude/improvements/` に 109件・1.44 MB。規範を1つ足すたび、書き終わった全文書が「新規範に照らして未検査」に戻る。コミット `7c6d0d1`「規範更新の反映と階層の点検(**5周**)」がその状態そのものを記録している。

2026-08-02 に規範が git 追跡外になったため(2.5)、この増殖は**測定不能**になった。

### 原因3 — 停止条件の不在

`CLAUDE.md` §9 が定義しているのは**タスクの**完了である。`docs/00-requests/acceptances.md:19-106` に AC-01〜AC-06 があるが、これが停止条件として運用されていない。フェーズモデル(§3)は次のタスクを生む機械であって、最後のタスクを判定する機械ではない。

### 原因4 — スコープを切る判断の遅延(原因1〜3の帰結)

`orchestrator` は 2026-06-28 実装、**2026-07-06 が最終コミット**。以後コードは1行も動いていないのに、その文書整合だけが1ヶ月続いた(issues 001/009/012/013/014/015/021/022/026/057…)。2026-08-08 になって `docs/tasks/task-remove-orchestrator/` で全削除が決まった。判断は正しいが、**1ヶ月遅い**。

規範には「作らない/やめる」を促す機構が無く、「整合させる」義務だけがある。だから止まっているものほど文書コストを食う。

## 5. 提案(削除・変更)

各提案は「対象 / 現状 / 変更後 / 効果 / リスク」で書く。番号順が実施順ではない(実施順は第6章)。

### 提案1 — プロジェクトの停止条件を新設する ★最優先

- **対象**: `CLAUDE.md`(新設)、`docs/00-requests/acceptances.md`
- **現状**: タスクの完了条件しかない(§9)。プロジェクトの完了が未定義。
- **変更後**: 「**完了 = `acceptances.md` の AC が実機で全通過すること。AC を落とさない作業は完了を妨げない**」を規範の先頭に置く。orchestrator 削除後の対象は AC-01 / AC-02 / AC-03 / AC-06 の4件。
- **効果**: 原因3 を直接消す。以降のあらゆる作業に「これは AC に効くか」という判定軸が生まれる。
- **リスク**: AC に現れない品質(セキュリティ・保守性)が落ちる。→ AC-03 が危険操作の拒否を担っているので致命的にはならない。足りなければ AC を足す(AC を足すのは人間の決定であり、AI が勝手に増やさない)。

### 提案2 — issue の受入ゲートを新設し、既定の行き先を pendings へ反転する ★最優先

- **対象**: `.claude/directions/issues-pendings.md`、`CLAUDE.md` 原則8
- **現状**: 発見物は issue / pending / タスクの3択で、実際には issue に流れている(95件発行・61件現存、うち49件が文書整合)。
- **変更後**: 発見物は**2択**にする。
  - **AC を落とすか?** → Yes: issue を作り即タスク化する / **No: `pendings.md` に1行書いて終わり**(以後追跡しない)
  - issue に「深刻度」列は不要になる。AC を落とすものだけが issue なので全件が対処対象。
- **効果**: 原因1 の入力を止める。現存61件は仕分けで 12件前後(bug のうち AC に効くもの)まで落ちる見込み。
- **リスク**: pendings が膨らむ。→ pendings は1行で、再検査の対象にしない。膨らんでも系は回る。

### 提案3 — 原則2(コード⇄03-impl の 1:1)を AC 連動の限定適用にする

- **対象**: `CLAUDE.md` 原則2、`.claude/directions/03-impl.md`、`.claude/directions/relations.md`
- **現状**: 全モジュールについて `relations/MODULE-*.md` をコードと 1:1 で維持する義務。`docs/03-impl` は 135ファイル / 1.1 MB。製品を1行直すたびにこの規模の税を払う。
- **変更後**: 手書きの `MODULE-*.md` を持つのは **AC トレース表に載るモジュールだけ**。それ以外は `callgraphs/`(機械生成)で足りるとし、原則2 の検査対象から外す。
- **効果**: 03-impl 135ファイル → 40前後。製品作業の再開コストが 1/3 になる。`/doc-check` の B・E 群の検査量も同じ比率で減る。
- **リスク**: 対象外モジュールの「なぜこの実装か」が追えなくなる。→ コールグラフとコード内コメントで足りる範囲だと**明示的に受容**し、`pendings.md` に1行残す。判断が要る箇所だけ AC トレース表に載せれば戻せる。

### 提案4 — `verified` を 00〜02 の4文書に限定する(原則6の縮小)

- **対象**: `CLAUDE.md` 原則6、`.claude/skills/doc-check/SKILL.md` の certification stage
- **現状**: **65文書**が `verified` を持ち、`version` × `against` の三重管理。1文書が動くと連鎖的に無効化され、再認証が新しい作業を生む(原因1のループの一段)。
- **変更後**: `verified` を持つのは `00-requests/request.md` / `00-requests/acceptances.md` / `01-requirements/functional.md` / `02-design/architecture.md` の**4本のみ**。03-impl の `verified` は**廃止**し、機械検査(コールグラフ整合)の合否で代替する。
- **効果**: 再認証の連鎖が 65 → 4 に縮む。`doc-check` の認証段階がほぼ消える。
- **リスク**: 「検証されていない文書」が増えたように見える。→ 検証の単位を**文書から AC へ移す**のが本提案の趣旨であり、AC 通過が検証そのものになる。

### 提案5 — `/doc-check` の反復を1回に固定し、検査群を6群→3群にする

- **対象**: `.claude/skills/doc-check/SKILL.md`(734行)、`.claude/directions/change-set.md`(369行)
- **現状**: 検査群 A〜F の6群、反復上限5回(`SKILL.md:522`)、機械検査ID 40件。**反復が増幅器**になっている。
- **変更後**:
  - 反復は**1回**。1回で出た指摘のうち AC に効くものだけ直し、残りは提案2 のゲートで pendings へ。
  - 検査群を **A(層間の縦整合) / E(02⇄03 の連携差分) / B(03⇄コード、提案3の限定範囲)** の3群に。**C(個別文書の品質)・D(実装可能性)・F(変更指示の妥当性)の散文検査は廃止**し、機械検査(CS)に残った分だけで判定する。
  - 機械検査ID を **40 → 12前後**に統廃合(CS20→6 / SH9→3 / CG・FT 11→3)。
- **効果**: 原因1 のループ利得を 1 未満にする最大の一手。`doc-check` 734行 → 250行程度。
- **リスク**: 見逃しが増える。→ **意図した取引**である。見逃しゼロを狙った結果が現状の 3.4倍発散であり、AC が最終防波堤になる。

### 提案6 — 変更指示の SSOT 構造ミラーを1ファイルに畳む

- **対象**: `.claude/directions/change-set.md`、`.claude/skills/task-doc/SKILL.md`、`.claude/templates/`
- **現状**: `docs/tasks/<slug>/new-features/` が 00〜03 の階層を丸ごとミラーする。`task-remove-orchestrator` では 40以上のファイルになっている。
- **変更後**: 1タスク = **`changes.md` 1本**。節見出しが反映先のパス、本文が差分。原則1(SSOT を未来にしない)は**完全に保持**され、消えるのはミラーの維持コストだけ。
- **効果**: フェーズ2の作業量とファイル数が1桁減る。`change-set.md` 369行 → 80行程度。CS 検査の半分は対象が消えて不要になる(提案5と重なる)。
- **リスク**: 反映先の取り違え。→ 節見出しをパスにする形式なので、`/task-close` 側は機械的に辿れる。

### 提案7 — `.claude/improvements/` を廃止し、`/kit-improve` を削除する

- **対象**: `.claude/improvements/`(109ファイル / 1.44 MB)、`.claude/skills/kit-improve/`(332行)
- **現状**: 規範改善の検討メモが製品の要求〜設計の3倍。**原因2 の器そのもの**。

- **リスク**: 過去の検討経緯が失われる。→ 適用済みのものは既に規範本体に入っており、未適用のものは**入らなかったという事実が結論**である。
