# 構造化設定ファイルへの「不足している既定値だけ追記」は、行指向の追記では成立しない

## 状況

codex の `config.toml` に既定 3 鍵（`sandbox_mode` / `approval_policy` /
`[features] use_legacy_landlock`）を entrypoint が保証する、という要件を実装しようとしていた。
要件（core/12-6）と決定（D-27 ⑥）はこう書かれていた——

> 既に存在する場合は**利用者が書いた鍵と値を一切書き換えず、上記のうち書かれていない鍵だけを追記する**
> （不足既定の補完。冪等）

タスクドキュメントの調査メモにも「生成する 3 鍵はいずれも `^\s*<key>\s*=` の形なので、鍵の有無は
その行の有無で判定できる」と書いてあり、実装方針は決まったつもりだった。

## 何が抜けていたか

`/doc-check` の独立監査（`readiness` レンズ）が、実装可能性のドライランで次を指摘した——
**「鍵をどこに挿入するか」が定義されていない**。

TOML はテーブル見出し（`[table]`）以降の鍵が当該テーブルに属する。したがって:

- `sandbox_mode` はトップレベル鍵だが、ファイルが `[tui]` などの見出しで終わっていると、
  末尾追記した瞬間に `tui.sandbox_mode` になる。
- `[features]` がファイルの途中にある場合、`use_legacy_landlock` を末尾追記すると
  後続の別テーブル配下の鍵になる。

どちらも**既存の行は 1 文字も変えていない**のに、追記した鍵が効かない（あるいは別の意味になる）。
「既存の鍵と値を書き換えない」という要件の文面は満たしているのに、要件の目的は満たさない。

さらに実装中に見つかった隣接の罠: 利用者がドット記法（`features.use_legacy_landlock = ...`）や
インラインテーブル（`features = { ... }`）で書いていると、行の有無で判定すると「無い」と誤判定して
`[features]` を新設し、**同じ鍵の二重定義で TOML 全体が壊れる**。壊れた設定は codex がまるごと
読めなくなるので、補完しないより悪い。

## 一般化した教訓（今後どう活かすか）

- **「既定値を後から補完する」要件は、(a) 判定 (b) 挿入位置 (c) パース不能時の振る舞い の 3 つが
  揃って初めて実装可能になる。**(a) だけ決めて「あとは実装詳細」と思うと、ドライランで初めて
  未決点として出てくる。要件・決定を書く側は (b)(c) まで書くか、明示的に委任する。
- **スコープを持つ形式（TOML / YAML / INI / 一部の JSON 運用）では、行指向の追記は禁じ手。**
  「末尾に足す」が安全なのは、スコープの概念がないフラットな形式（`.env`、単純な key=value）だけ。
- **判定は「その鍵が属すべきスコープの中に、その鍵の等価な表現があるか」で行う。**同じ意味を持つ
  別記法（ドット記法・インラインテーブル・アンカー等）を見落とすと、補完が二重定義を作って
  ファイルごと壊す。迷ったら「書かれている」側に倒す方が安全（補完し損ねても既定が効かないだけで、
  壊れた設定より害が小さい）。
- **壊れていて位置を特定できない入力は、触らずに警告して続行する。**利用者の設定ファイルは
  こちらの所有物ではない。
- 検証は「生成した結果が**その形式としてパースできるか**」まで見る。行の中身を目視で確かめても、
  スコープの誤りは見つからない（今回はホスト側の関数単体ハーネス 12 ケースを `tomllib` に通して確認した）。
