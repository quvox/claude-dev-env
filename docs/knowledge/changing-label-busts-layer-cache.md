# 日次で変わる値をレイヤーチェーンに入れると pull が全再取得になる

## 状況

`claude-dev pull`（GHCR イメージの `docker pull`）が毎回、全レイヤーを再ダウンロードして遅い、
との指摘。base 62 / vnc 85 レイヤーと多いことも問題視された。調べると `Dockerfile.claude` の
先頭付近（base ステージの上部）に、日次で変わるタイムスタンプ `IMAGE_VERSION` を焼く
`LABEL io.github.quvox.claude-dev.version="${IMAGE_VERSION}"` が置かれ、CI が毎日異なる
`IMAGE_VERSION` を build-arg で渡していた。

## 判断（原因と対処）

- **原因**: BuildKit のキャッシュはチェーン。ある命令の cache key が変わると、それ以降の全命令が
  cache-miss になる。バージョンラベルがレイヤーチェーンの前段にあり、値が日次で変わるため、
  以降の高コスト層（apt 1.68GB・go/rust/pyenv/node 等）がすべて再ビルド→新しいレイヤーダイジェスト
  →`docker pull` が全再取得。CI は `cache-from: type=gha` を持っていたが、この失効で無効化されていた。
- **対処**: バージョンは build-arg/LABEL でレイヤーチェーンに載せず、**build-push-action の `labels`
  入力**で最終イメージの config メタデータとして付与する（export 時に適用され、レイヤーキャッシュ・
  レイヤーダイジェストに影響しない）。CI から `IMAGE_VERSION` build-arg を外し、`labels` を追加した。
  Dockerfile の `ARG IMAGE_VERSION=local`＋`LABEL` は据え置き（CI では定数 `local` になりキャッシュを
  失効させない。ローカルビルドのバージョン表示に使用。pushed イメージは `labels` が上書き）。

## 一般化した教訓（今後どう活かすか）

- **毎回変わる値（タイムスタンプ・ビルド番号・コミットハッシュ等）を build-arg / ENV / LABEL で
  レイヤーチェーンの前段に入れない**。入れるとキャッシュが実効せず、増分ビルド／増分 push／増分 pull
  がすべて崩れる。メタデータは最終イメージへ export 時に付与する（buildx/`build-push-action` の
  `labels`、または最終段の LABEL）。変えたい ARG はできるだけ後段に置く。
- **「レイヤーが多い」より「キャッシュが失効している」方が本質**なことが多い。適切に順序付けされた
  多数の層は増分 pull で skip されるので害は小さく、むしろ層を統合すると変更時の再取得量が増える
  （キャッシュ粒度が粗くなる）。まずキャッシュ失効の有無を疑う。
- 症状「毎回すべて再ダウンロード」を見たら、`docker history` で前段に日次可変な入力が無いか、
  CI が cache-from/to を持ちつつそれが効いているかを確認する。

## 続報（2026-07-29）— 上記の教訓を「可変値を消す」だけで適用すると逆側に倒れる

上の対処でレイヤーチェーンから日々変わる値が**完全に消えた**結果、外部から取得するもの
（`curl https://claude.ai/install.sh | bash`）の層が**永久にキャッシュヒット**するようになった。
2026-07-19 以降の日次ビルドは毎回1分強で success を返し続けたが、同梱 Claude Code は 2.1.214 で
凍結。`labels` だけが日次で変わるためダイジェストは毎日変わり、外からは更新されているように見えた。
キャッシュを落とす `ARG CLAUDE_CACHE_BUST` は用意されていたが、渡していたのはローカルの Makefile
だけで CI は渡していなかった（＝「逃げ道はあるが使われていない」状態）。

対処は、可変値を戻すのではなく**キーの種類と位置を変える**こと:

- **種類**: 時刻由来（毎日必ず失効）ではなく**内容由来**（外部依存の実バージョン）をキーにする。
  新版が出た日だけ失効し、出ない日は完全にキャッシュヒットする。
- **位置**: そのキーを参照する層を**配布ステージの終端レイヤー**に置く。共有される中間ステージ
  （`FROM base` で連なる側）に置くと、失効が下流の高コスト層まで波及して元の問題に戻る。

## 一般化した教訓・追記

- キャッシュキー設計の問いは2つある。**①この値は内容由来か（時刻・乱数・ビルド番号は不可）**、
  **②失効したとき何層が巻き込まれるか（依存される中間ではなく終端に置く）**。①だけを見て
  「可変値を消す」と、鮮度が静かに死ぬ。
- **外部 URL から取得する層（`curl | bash`、パッケージの最新解決）は、キャッシュキーを持たない限り
  「一度ビルドした版で永久に固定される」**。固定したいなら意図的にピンし、追随したいなら実バージョン
  をキーにする。どちらでもない状態＝「暗黙の凍結」が最も危険で、気づくのが遅れる。
- 「無効化する手段を用意した」で終わらせず、**その手段を実際に使う経路（CI）に配線されているか**を
  確認する。片方の経路（ローカル）だけに配線された逃げ道は、無いのと同じ振る舞いをする。

## 続報（2026-07-30）— 終端に2つ目の依存を積むと、前の依存の版変更が後ろを道連れにする

D-27 で Codex CLI を同じ終端ステージへ積んだ結果、終端は
`claude 導入 RUN` → `codex 導入 RUN` → `codex ランチャー RUN` の順になった。ここで
`make update-claude`（`CLAUDE_VERSION` だけを渡す）を実行すると、claude 導入層以降がすべて失効し、
`CODEX_VERSION` を渡していないため codex が既定 `latest` で**入れ直される**。CI は両方をピン留め
するので、ローカル更新時だけ codex の版が成り行きになる。`/doc-check` の check B で
`03-impl/makefile.md` の「終端の claude 導入層だけを無効化」という記述が実挙動と食い違って
検出され、利用者判断（コードを正）で文書を実挙動へ同期した。

- **同一ステージに複数の外部依存を積むときは「順序＝失効の連鎖」を意識する。** 先頭の依存の版を
  変えると、後続の依存はすべて再取得され、**その版は build-arg を渡していなければ既定値**になる。
  「A だけ更新したつもりが B も動いた」は設計どおりの挙動であって事故ではないが、**気づかないと
  文書が静かに嘘になる**。
- 依存ごとに版を独立して制御したいなら、build-arg をすべての更新経路で必ず渡すか、依存を別レイヤー
  順序（更新頻度の低いものを先に）へ並べ替える。どちらも取らないなら「後続は成り行きの最新」と
  **明示的に文書化する**（今回はこれを選んだ）。
- **依存を1つ足したら、その位置に言及している既存 03-impl の記述（失効範囲・レイヤー構成）を必ず
  読み返す。** 新しい記述の追加だけでは足りず、既存の「〜だけ」という限定表現が古くなる。
