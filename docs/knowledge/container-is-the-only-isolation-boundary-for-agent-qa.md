# コンテナが唯一の隔離境界なら、エージェント QA の内側サンドボックスは要求しない

## 状況

コンテナ内 codex の全経路を使える状態にする作業で、サンドボックスのバックエンドを landlock に
切り替えると読み取り専用（`--sandbox read-only`）は成立するが、書き込みを伴う `workspace-write` は
landlock 経路でも失敗することが実測で分かった。`/codex-qa`（独立QA）は書き込みを必要とする。

## AI の提案

CLAUDE.md 不変条件5（監査・QA で承認/サンドボックス迂回フラグを使わない）を守るため、
**QA レーンはフレッシュコンテキストのサブエージェントで代替する**（不変条件7 のフォールバック）
ことを推奨した。`danger-full-access` での codex QA は不変条件5 の意味を変える判断なので人間判断が
必要、と整理して選択肢として提示した。

## 人間の決定と理由

**`danger-full-access` で codex QA を許す。** 理由は「**コンテナ自体が隔離空間だから、これ以上の
隔離は不要**」。

これは D-1（隔離境界はコンテナ／ホスト間のみ）の一貫適用である。claude 側が
`permissions.defaultMode=bypassPermissions` を既定にしているのと同じ理屈で、内側に二重の
サンドボックスを敷くことは元から前提にしていない。

## 今後どう活かすか

1. **「サンドボックスを使うか」は、そのプロセスがどの境界の内側で走るかを見て決める。** 汎用の
   規範（キットの不変条件）はホスト直実行も想定して書かれているため、実行環境がすでに隔離空間の
   場合は過剰になりうる。過剰と判断したら**逸脱として明示的に記録する**（今回は
   `docs/_steering/tech.md`「Codex実行設定」に「不変条件5 からの意図的な逸脱・コンテナ内限定」と
   理由を書いた）。黙って迂回するのとは別物である。
2. **逸脱の範囲を限定して書く。** 「コンテナ内で実行する場合に限る」「QA の他の制約（専用 seed・
   ブラウザ排他・成果物ディレクトリ以外を書かない・終了時 reset）はそのまま守る」まで書いて初めて
   運用できる記録になる。
3. **読み取り専用と書き込み可を同じ判断で扱わない。** 今回は読み取り専用だけ landlock で内側の
   隔離を生かし（仕様ドキュメントを codex が書き換えないという別の不変条件を機械的に守れる）、
   書き込みが必要な QA だけ内側を外した。「内側を全部捨てる／全部生かす」の二択にしない方が、
   守りたい性質ごとに最小のコストで守れる（[nested-agent-sandbox-blocked-by-container-confinement](nested-agent-sandbox-blocked-by-container-confinement.md)）。
