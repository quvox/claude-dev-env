# 文書だけ先に更新すると /doc-check と /implement が循環してデッドロックする

## 状況

D-26（同梱 Claude Code の latest ピン留め）を `/change` で 00→01→02→03 の順に反映し、
その日のうちに `/doc-check full` を実行した。コード反映（`/implement`）は未実施だった。

`/doc-check` は 03-impl の 4 文書（devcontainer・ghcr-workflow・makefile・cli）を
**check B（03-impl ⇄ コードの一致）で不合格**とし、合格証を剥がした。文書は「あるべき姿」を
正しく書いており、上流（decisions/core/system）はすべて verified。剥落理由は
「まだ実装していない」ことだけだった。

続けて `/implement` を起動すると、Phase A のゲートが
「対象 03-impl とその source チェーンが**すべて** verified であること」を要求する。
対象 03-impl は今まさに剥落済みなので、規約どおりならここで停止する。
そして停止している間はコードが変わらないので、`/doc-check` を回し直しても再合格しない。

## 判断

- ゲートの**趣旨**は「検証されていない仕様からは実装しない」ことであり、上流チェーン
  （00/01/02）が全 verified で、剥落理由が本作業の対象そのものであるなら趣旨は満たされている、
  と判断して実装に着手した。
- ただし判断を黙って行わず、タスクドキュメントに「前提（ゲート状況の記録）」節を設けて
  「なぜ止まらなかったか」を残した。完了後に `/doc-check` で再検証して循環を閉じた。

## 一般化した教訓（今後どう活かすか）

- **`/change` で文書を更新したら、`/doc-check` より先に `/implement` を通す**。順序を逆にすると
  必ずこの循環に入る。文書とコードの間に「文書だけ先に進んだ」期間を作らないのが本筋で、
  作ってしまった場合は「実装 → doc-check」の順で閉じる。
- **check B の不合格は「文書が悪い」とは限らない。**「コードが追いついていない」ときも同じ判定に
  なる。剥落理由が①文書の誤りか②実装の未了かを報告時に区別する。混同すると、正しい文書を
  コードに合わせて書き戻す（＝せっかくの意思決定を捨てる）方向へ倒れかねない。
- **文書だけ更新した状態で合格証を書いてはいけない。**今回は前回の /doc-check（著者セッションでの
  自己レビュー）がコードとの突合をせずに合格証を書いており、それが「実装済みのように見える」
  誤信号になっていた。検証は別セッションで、コード実測を伴って行う。
- 仕様先行の運用では、**タスクドキュメントが「文書は済み・コードは未了」の唯一の目印**になる。
  タスクドキュメントが存在しないまま文書だけ進んだ変更は、誰も未了と気づけない
  （今回、docs/tasks/ は空だった）。/change の直後にタスクを起こしておくと目印が残る。
