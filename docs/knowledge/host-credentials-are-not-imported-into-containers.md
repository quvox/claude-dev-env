# ホストの認証情報はコンテナへ取り込まない（認証共有は「コンテナ間」の意味）

## 状況

D-27（Codex CLI 同梱・認証共有）の実装後、利用者から「すでにホストで認証済みなのに、なぜ
`claude-dev login-codex` で再度認証が必要なのか」と問われた。実装を確認すると、D-3 の
「コピー＋30秒ごとの同期」の端点は **コンテナのプロジェクト `.claude`/`.codex` ⇄ `claude-dev-auth`
ボリューム**であり、ホストのホーム（`~/.codex`・`~/.claude/.credentials.json`）はどこにも現れない。
claude も同じ構造で、ホストの `claude` がログイン済みでも `claude-dev login` は必要である。

## AI の提案

「ホストと共有」という言葉に引かれ、ホストの `~/.codex` を 3 番目の端点として既存の 30 秒ループに
加える**双方向同期**を推奨した。根拠として、codex の `auth.json` はその場書き換え（tmp→rename では
ない）ため claude で symlink が壊れた問題が起きないこと、ホスト側でリフレッシュされたトークンも
引き継げることを挙げた。

## 人間の決定と理由

**現状維持**（コンテナ→共有ボリュームのみ）。判断基準として明示されたのは 2 点で、優先順位も示された:

1. **claude と同じ仕組みであること**
2. **セキュリティ的にデメリットがないこと**

この基準で見ると、双方向同期は (a) claude は tmp→rename のため別実装が必要で仕組みが二重化する、
(b) コンテナ内のレビュー前コードがホストのホームを書き換えられる経路を作る（`request.md` §2
「レビュー前コードがホストへ到達する経路を作らない」の逆向き）、(c) リフレッシュトークンの回転で
ホスト側の認証を壊しうる、という 3 点で基準に反する。片方向の取り込み（RO マウント）でも
claude との対称性が崩れる。`login-codex` は初回一度きりの操作なので、得られる利便性も小さい。

## 一般化した教訓（今後どう活かすか）

- **この環境で「認証を共有する」とは「コンテナ間で共有する」ことであり、「ホストのユーザー認証を
  流用する」ことではない。** 共有の器は常に `claude-dev-auth` ボリュームで、その外（ホストのホーム）は
  端点にしない。同種の要求（別ツールの認証共有）が来たときも、まずこの形に当てはめる。
- **利便性の提案をする前に、既存の仕組みとの同一性を評価軸に入れる。** 今回 AI は「その場書き換えだから
  技術的に可能」を根拠に新方式を推したが、実現可能性は採用理由にならない。仕組みが 2 つに分かれること
  自体がコスト（D-27 で「方式を 2 つ持たない」と決めた判断と本来一貫すべきだった）。
- **データの流れる向きを変える提案は、セキュリティ的に非対称であることを明示的に検討する。**
  コンテナ→ホストへの書き込み経路の新設は、読み取りの追加とは重みが違う。
- 既存実装にホスト資産のマウント（`~/.config/gh` を RO で共有）があることは、新たな取り込みを
  正当化しない。前例の有無より、当該モジュールの方式との一貫性を優先する。
