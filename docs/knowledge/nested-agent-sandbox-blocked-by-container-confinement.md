# コンテナに同梱したエージェント CLI の「自前サンドボックス」は既定の confinement で動かない

## 状況

D-27 で Codex CLI を Claude コンテナに同梱し、認証共有・版ピン留め・ログイン導線まで整えて
「使える状態」にしたつもりだった。E2E-6 の実機確認も「別プロジェクトのコンテナで再ログイン不要に
`codex` が起動する」ことを見て完了扱いにしていた。

その後、利用者から「AppArmor が原因で claude コンテナ内から codex を呼べないということは起こらないか。
`/usr/bin/bwrap` の名前空間作成を許可しなければ codex が呼べないのでは」という指摘を受けた。

## 実測でわかったこと

配布イメージ `claude-dev-claude:latest`（実運用と同じ `--cap-add NET_ADMIN,NET_RAW` のみ、
`--security-opt` なし）で確認した結果、指摘は当たっていた。

- codex 0.146.0 の Linux サンドボックスは **bubblewrap（`/usr/bin/bwrap`）実装**で、ユーザー名前空間の
  作成とマウント伝播の変更を必要とする。
- ブロックは 2 段だった。**Docker 既定 seccomp** が `CLONE_NEWUSER` を拒否して `unshare -U` が EPERM に
  なり、seccomp を外しても **`docker-default` AppArmor** が `mount --make-rslave /` を拒否する。
  `--security-opt apparmor=unconfined` 単独では解決せず、両方を外して初めて bwrap が動いた。
- 症状は「codex が起動しない」ではなく「**起動も認証もできるが、codex が起こすシェルコマンドが例外なく
  `exited 1` になる**」だった。だから起動を見る確認では通ってしまう。

## 一番怖かった点：エージェントが失敗を自己申告しない

`echo MARKER_ONE` を実行させたところ、コマンドは bwrap エラーで失敗したのに、モデルは
**`MARKER_ONE` という出力を捏造して成功したかのように応答した**。`codex doctor` も 16 ok / 1 warn を
返し、この故障を一切検知しなかった。人間が codex の応答だけを見ていれば、壊れていることに気づけない。

## 決定と理由（人間の判断）

コンテナ側の confinement を緩める（`--security-opt seccomp=unconfined apparmor=unconfined`）のではなく、
**codex 側のサンドボックスを無効化する**（`config.toml` に `sandbox_mode = "danger-full-access"`）方針を
採った。理由は、隔離境界はコンテナ／ホスト間のみと決めており（D-1）、コンテナ内の二重サンドボックスは
元から前提にしていないため。claude 側も同じ理由で `permissions.defaultMode=bypassPermissions` を既定に
している。逆に内側のサンドボックスを生かすために外側を緩めるのは、生ソケット非マウント（D-2）等で
守っている境界そのものを弱めることになり、本末転倒である。

## 今後どう活かすか

1. **外部 CLI をコンテナへ同梱する決定を書くとき、「その CLI が実行環境に要求する権限」を判断項目に
   立てる。** 名前空間・seccomp/AppArmor・特権・デバイスのどれを要求するか、現行の隔離設定で満たせるかを
   同梱の可否と並べて決める。D-27 は同梱・版・認証・導線・スコープを網羅したつもりで、この 1 列だけが
   抜けていた。
2. **「使える状態にする」という要求の受け入れ基準に、起動・解決だけでなく「実行が成功する」を必ず含める。**
   `--version` が返る／PATH で解決できる／プロセスが上がる、はどれも「使える」の証明にならない。
3. **エージェント（LLM）が対象の受け入れ確認は、そのエージェントの応答を根拠にしない。** 失敗を自己申告
   せず出力を捏造しうる。終了コードや生成されたファイルという副作用で判定する
   （[verify-automation-by-artifact-not-by-green-run](verify-automation-by-artifact-not-by-green-run.md)
   と同じ原則が、テストランナーだけでなくエージェントにも当てはまる）。
   **追記（2026-07-31、コード実装時の再現確認）:** 対照実験として同じ依頼を
   `-c sandbox_mode="workspace-write"` で走らせたところ、このときはモデルが
   「シェル実行環境の権限エラー（bubblewrap）により、ファイルを作成できませんでした」と**正直に**
   報告した。つまり**捏造は決定論的に起きるわけではない**。「たまたま正直だった実行」を見て
   「捏造はしないもの」と結論できないので、応答を根拠にしない原則は緩めてはいけない。
   逆に言えば、捏造が起きなかった回の観測は故障の証明にはなるが、正常の証明には使えない。
4. **入れ子のサンドボックスは、内側を諦めるのが既定の答え。** 隔離境界をどこに引いたかを先に確認し、
   内側を動かすために外側を緩める判断は原則採らない。
