# 定期自動化は「成功ログ」ではなく「成果物の中身」で検証する

## 状況

利用者から「毎日 GitHub Actions でイメージを更新しているはずなのに、コンテナ内の Claude Code が
最新にならない」と指摘された。GitHub Actions の履歴は直近8回すべて `success`。タグも `latest` の
ダイジェストも毎日変わっていた。にもかかわらず、イメージに焼かれた Claude Code は 10 日前の
2.1.214 で止まっていた（原因は
[レイヤーキャッシュキーの設計](changing-label-busts-layer-cache.md)）。

気づく契機になったのは「実行時間が毎回1分強」という違和感で、成功/失敗の別ではなかった。
実ビルド時は4分43秒かかっており、**成功したまま何もしていない**状態を時間だけが示していた。

## 判断

- 検証項目を「ワークフローが success する」「タグが push される」から、**「成果物の中身が期待通りか」**
  へ引き上げた。具体的には 03-impl のテスト表に「配布イメージ内で `claude --version` を確認し、
  ビルド時点の `latest` チャネル値と一致する」を追加。
- あわせて、日次ログで当該層が `CACHED` かどうかの**意味**を運用メモに明記した——「新版が無かった」
  なら正常、「新版が出ているのに `CACHED`」なら解決処理が壊れているサイン。同じ観測値が正常とも
  異常とも読めるため、判定の基準を文書側に置いた。

## 一般化した教訓（今後どう活かすか）

- **緑ランプは「工程が完走した」ことしか示さない。「成果物が更新された」ことは別途確かめる必要がある。**
  定期実行の自動化には、成果物の中身を外形から1つ突き合わせる検証（版・ハッシュ・件数・更新時刻の
  いずれか）を必ず含める。
- **キャッシュや冪等性を効かせた自動化は、「何もしなかった」と「正しく更新した」が同じ success に
  見える。**両者を区別できる出力（解決したバージョンを log に出す、差分の有無を明示する）を出させる。
- **所要時間の変化は「中身が動いていない」ことの安価な検知手段**。定期ジョブの実行時間が理由なく
  短くなったら、成功していても疑う。
- 利用者が「〜のはずなのに」と言うときは、たいてい**仕組みは動いていて前提が崩れている**。まず
  仕組みの成否ではなく、前提（この場合「更新される＝中身が変わる」）を検証する。
