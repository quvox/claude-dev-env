# オーケストレーター 要求定義(抽出)

> **この文書の位置づけ**
> `claude-dev-env` の仕様ドキュメント(SSOT)から、**オーケストレーターに関わる記述だけ**を
> 原文のまま抜き出した**抽出物**である。SSOT ではないので `verified`(検証済み記録)を持たない。
> ID(`RQ-*` / `D0-*` / `AC-*`)は**抽出元と同一のものを変えずに使う** — 分離後に元の議論へ
> 遡れなくなるのを避けるため。抽出元の各ファイルとその version はフロントマターが持つ。
> 分離先プロジェクトで正式な 00-requests として使うときは、下の「## 分離時に決めること」を
> 先に片付けること。

## 背景と目的

チームのリソースは簡単には増やせない一方、顧客からの要望は増え続けている。単一プロジェクトを
速く終わらせることよりも、**複数プロジェクトを並列に進められること**を優先したい。今のボトルネックは
「単一案件の速度」ではなく、**人間が進行管理(オーケストレーション)を兼ねているために並列度を
上げられない**ことにある。各プロジェクトの内容を常に人間が追わねばならず、管理に時間を取られている。

オーケストレーターの目的は次の1つである(`request.md` の目的3つのうち3番目。他の2つ
——Docker による隔離とイメージ配布——は開発環境側の目的であり、本抽出の対象外)。

- 各プロジェクトに **AIオーケストレーターを1体**立て、人間は「検討(ブレインストーミング)」と
  「例外対応(介入)」だけに関与する。狙いは速さではなく**人間1人あたりの担当プロジェクト数を増やす**こと。

## 対象ユーザー

| 呼称 | 誰か | この人の目的 |
|---|---|---|
| 開発者 | 社内の開発者(日本語話者)。本ツールの主たる利用者 | オーケストレーターを使って複数案件を並列に回す |
| 保守者 | 本ツール自体を保守する社内の開発者 | オーケストレーターの振る舞いの確認を行う |

前提として**信頼できる社内開発用途に限定**する(信頼できないコードを扱う用途・本番に近い環境は対象外)。

## やらないこと

| # | やらないこと | 理由 |
|---|---|---|
| 1 | **各エージェントの個別隔離**(microVM 等での worker ごとの隔離) | 本構成は単一コンテナ同居型とし、隔離境界はコンテナ/ホスト間にのみ置く。個別隔離が要る用途は別構成(Docker Sandboxes 等)で検討する |
| 2 | **信頼できないコード・本番に近い環境での利用** | 信頼できる社内開発用途に限定するという前提を置いたうえで、隔離の強度を決めているため |
| 4 | オーケストレーターの**ブレインストーミング(人間の検討)の自動化** | ここは人間の価値が宿るため自動化しない |
| 5 | 完了基準の未充足を自動でタスク化して埋める機能 | v1 では検証は助言に留める |

## 完成イメージ

- 案件を任せるときは `claude-dev orchestrate` を実行する。対話でゴールと plan を固めたあとは離席でき、
  複数の worker が並列に実装する。要判断が出たタスクだけが待機し、Slack の通知を見て戻ってきて
  そのタスクにだけ答える。端末が壊れても、入り直せば同じ状態から続きが始まる。

## 制約・前提

- 認証: Claude Pro / Max プラン(OAuth)。API キー・トークンはイメージに焼き込まず環境変数等で注入する。
- 外部 CLI(`claude` 等)と各ツールは変化が速い。採用・更新時に公式ドキュメントで最新仕様を確認する。
- **実行場所はコンテナ内である**(ホスト側では動かさない。理由は 02 の `DSN-arch-03`)。

### 判断に迷いやすい区別

| A | B | 何が違うか |
|---|---|---|
| ブレインストーミングモード | 実行モード | 前者は人間主導・同期・自動化しない検討。後者は自律・並列の実装。境界は仕様ドキュメント |
| 仕様(`docs/`) | 運用状態(`.orchestrator/`) | 固まった仕様は `docs/` に、進捗・仮定・plan 等の運用状態は `.orchestrator/` に置く |
| Codex CLI の同梱 | 異種ベンダー worker の常用 | 前者は開発者がコンテナ内で codex を使える状態にすること(決定済み)。後者はオーケストレーターが worker/レビューアーとして codex を常用すること(**未決** = `D0-orch-17`) |

## 受け入れ基準

### AC-04 オーケストレーターで並列実装し、要判断だけ対応する

- 対応要求: RQ-orch-01
- 前提: コンテナが起動している。実装したい案件がある。
- 操作:
  1. `claude-dev orchestrate` を実行する。
  2. 対話でゴールと作業計画を固め、確定して対話を終える。
  3. 複数の作業者が並行して実装している間、離席する。
  4. 「要判断 N 件」の通知が来たら戻り、待機している作業だけを選んで回答する。
- 期待される結果: 要判断になった作業だけが待機し、他の作業は止まらず走り続ける。回答するとその作業が
  再開する。すべて終わると成果が統合され、完了の通知が届く。
- こうなったら不合格: 1件の要判断で全部が停止する / 再開時に完了済みの作業をやり直す。

### AC-05 端末が壊れても実行を失わず復旧する

- 対応要求: RQ-orch-01
- 前提: オーケストレーターで実行中。表示崩れ等でクライアント端末を全部閉じるしかなくなった。
- 操作:
  1. 端末をすべて閉じる。
  2. 改めて接続し直し、`claude-dev orchestrate` を再実行する。
- 期待される結果: 同じ状態に戻る。実行の中身が生きていればそのまま合流し、死んでいても保存された
  状態から続きが始まる。完了済みの作業はやり直さず、計画や履歴が勝手に消えることもない。
- こうなったら不合格: 端末を閉じた時点で実行が失われる / 再開で最初からやり直しになる。

### 対象外とするシナリオ

| シナリオ | 対象外とする理由 |
|---|---|
| 作業者ごとに隔離された環境で並列実装する | 「やらないこと」1(個別隔離)に該当する |
| ブレインストーミングを人間抜きで自動的に完了させる | 「やらないこと」4 に該当する |
| 完了基準を満たしていない箇所を自動でタスク化して埋める | 「やらないこと」5 に該当する(v1 では助言に留める) |

## オーケストレーションの決定事項(D0-orch-*)

### D0-orch-01 コントローラの生存判定とセッション名の扱い

- 区分: 委任
- 決めた日: 2026-07-30
- 委任範囲: コントローラが生きているかをどう判定するか(プロセス存在で見るかセッション存在で見るか)、
  セッション名を呼び出し側にどう伝えるか。
- 制約(ガードレール): **空き殻のセッションを「生存」と誤判定しないこと**。呼び出し側にセッション名を
  推測させないこと。誤判定は「再実行したのに合流できない/二重起動する」という利用者から見える故障に
  なるため、判定方法を変えるときは再現手順で確認すること。
- 報告義務: 決めた内容を該当機能の「実装上の判断」表に `D0-orch-01` と共に記録する
- 関連: FR-orch-02 / AC-05

### D0-orch-02 worker・対話 Claude の起動パラメータと指示の渡し方

- 区分: 委任
- 決めた日: 2026-07-30
- 委任範囲: 子プロセスとして起動する Claude の起動引数(権限モード・モデル・effort・再開指定)、
  指示テンプレートをどこに置きどう渡すか、再開/新規をどう判定するか、中断をどう表現するか。
- 制約(ガードレール): モデル/effort は 1 箇所のポリシー表で決め、利用者設定では変えられないようにする
  (`FR-orch-07`)。指示テンプレートはイメージ同梱とし、プロジェクト側に置かない。中断は終了コード 0 の
  クリーン終了にする(`FR-orch-05`)。ヘッドレス実行で人間の応答を要する状態を作らないこと。
- 報告義務: 決めた内容を該当機能の「実装上の判断」表に `D0-orch-02` と共に記録する
- 関連: FR-orch-03 / FR-orch-05 / FR-orch-07

### D0-orch-03 運用状態の永続化方式

- 区分: 委任
- 決めた日: 2026-07-30
- 委任範囲: 状態ファイルの書き方(原子的置換か追記か)、一時ファイルの置き場所、`.orchestrator/` の

- 制約(ガードレール): **起動時の自動処理で plan / 状態 / 履歴を削除しないこと**(片付けは必ず

  途中で落ちても既存の記録が壊れない書き方にすること。
- 報告義務: 決めた内容を該当機能の「実装上の判断」表に `D0-orch-03` と共に記録する

### D0-orch-04 介入と統合の制御構造

- 区分: 委任
- 決めた日: 2026-07-30
- 委任範囲: 介入をどのデータ構造で保持するか、突合をどのメモリ上の実体に対して行うか、統合(マージ)を
  誰が実行するか、古い指示をどう捨てるか。
- 制約(ガードレール): **要判断のタスク1件だけを待機させ、他の worker を止めないこと**

- 報告義務: 決めた内容を該当機能の「実装上の判断」表に `D0-orch-04` と共に記録する

### D0-orch-05 レビューの採点基準と再試行の規則

### D0-orch-06 ダッシュボードの描画と操作の規則

### D0-orch-07 通知の失敗許容

### D0-orch-09 オーケストレーションは自作の外部制御ループで行う

- 区分: 決定
- 決めた日: 2026-07-30
- 内容: コントローラがループを所有する外部制御ループを自作する。推論ループは `claude -p` / 対話 Claude
  から借りる。
- 理由: 暴走しない・コンテキストを汚さない・再開可能。変化の速い依存を中核に据えると配布の安定性に
  リスクがある。
- 却下した案: Docker Agent 方式(推論と委譲の配管を任せる) — 変化が速く中核に据えられない。
  Stop-hook による力技の連続走行 — 停止条件を LLM の裁量に委ねることになり暴走を止められない。
- 関連: RQ-orch-01 / FR-orch-02

### D0-orch-10 オーケストレーターは「1実体・2モード」とする

- 区分: 決定
- 決めた日: 2026-07-30
- 内容: ブレインストーミング(人間×対話 Claude、自動化しない)と実行(自律・並列)を1つの実体の
  2モードとする。両モードの引き渡し契約は仕様ドキュメントとし、運用状態は `.orchestrator/` に置く。
- 理由: 人間の価値が宿る検討は自動化せず、実装から整合性確認までを自動化する。
- 却下した案: 検討と実行を別ツールに分ける — 引き渡しが手作業になり、状態が二重管理になる。
- 関連: RQ-orch-01 / FR-orch-01 / request.md「やらないこと」4

### D0-orch-11 コントローラは tmux に常駐させる

- 区分: 決定
- 決めた日: 2026-07-30
- 内容: コントローラを `orch-<project>-main` セッションの `dashboard` ウィンドウで常駐させる。
  各 worker とブレインストーミングは同セッションの独立ウィンドウにする。
- 理由: クライアント端末が壊れても tmux サーバがセッションを保持するため、再接続で復旧できる。
  完全デーモン化より単純で、ダッシュボード描画を別プロセスに分けなくて済む。
- 却下した案: `setsid` による完全デーモン化 — 描画を別プロセス化する必要があり複雑になる。
  常駐しない(実行のたびに起動) — 端末を閉じると実行が失われる。
- 関連: RQ-orch-01 / FR-orch-02 / AC-05

### D0-orch-12 介入はタスク単位にする

- 区分: 決定
- 決めた日: 2026-07-30
- 内容: 要判断が出たタスク1件だけを待機状態にし、他の worker は止めない。独立した最上位状態
  「介入中」は置かない。
- 理由: 全体停止方式では1件の判断が全 worker を巻き込み、大量のやり直しを生む。
- 却下した案: ストップ・ザ・ワールド方式(全 worker を止めて人間に諮る) — 前述のとおり。
- 関連: RQ-orch-01 / FR-orch-04 / AC-04

### D0-orch-13 起動時の自動処理で状態を削除しない

### D0-orch-15 品質ゲートは別 worker による独立レビューとする

- 区分: 決定
- 決めた日: 2026-07-30
- 内容: 実装した worker とは別の worker(できれば別ベンダー)による独立レビューを通す。採点は
  当該タスクの完了条件のみで行う。レビュー結果は構造化出力で受け取り、同一
  フォーマットエラーが 2 回続いたら打ち切って介入へ回す。
  **★2026-08-04 改め**: 「構造化出力(**スキーマ強制**)」という表現を撤回する。**強制はツールでは
  行わない** — プロンプトで JSON の形を明示して要求し、崩れたら1回だけ再整形を試み、
  2回続けば介入へ回す(`FR-orch-06` 受入基準3・6・7 / `CTR-orchestrator-prompt`)。
  この撤回の理由: 同じ決定の後半(フォーマットエラーが続く前提)と前半(強制)が両立しない。
  **形式の検証と採点基準の双方が実装で固定されていない**という事実は、
  `docs/issues/058-bug-unknown-severity-passes-the-review-gate.md`(形式の検証が一箇所も無く、
  未知の `severity` が「重大でない」扱いで品質ゲートを通過する)と
  `docs/issues/059-modify-review-gate-scoring-criterion-has-no-covering-test.md`
  (採点基準が当該タスクの完了条件のみであることを覆うテストが実在しない)が追跡する。
- 理由: 自己レビューでは見落としが残る。プランのゴールで採点すると差し戻しが恣意的になる。
  自由記述で受け取るとパースに失敗して試行を浪費する。
- 却下した案: 実装した worker 自身にレビューさせる — 独立性が無い。人間が全件レビューする —
  並列度を上げるという目的に反する。

### D0-orch-18 「人間を呼ぶ判断」と「自律継続してよい判断」の境界

- 区分: 決定
- 決めた日: 2026-08-03
- 内容: 「軽微な判断だから自律継続してよい」という表現を廃止し、**介入を発火させる条件の否定**として
  定義する。すなわち **下表の発火条件のいずれにも当たらない場合**が「自律継続してよい判断」
  である。発火する条件は次のとおりで、これ以外はすべて自律継続の対象とする
  (**この判定をどこで行うかは 02/03 が定める**)。

  | 局面 | 発火する条件 |
  |---|---|
  | ディスパッチ前 | タスクが不可逆と印付けされており、かつ人間の承認がまだ無い |
  | ディスパッチ後 | 同一タスクの試行回数が `stuck_limit`(既定 3)以上に達した |
  | ディスパッチ後 | その試行で行き詰まりが検出された |
  | ディスパッチ後 | worker が「人間が必要」を、曖昧さ / 方針分岐 / 前提崩れ / 重大判断 のいずれかの理由で申告した |

- **射程**: 本項が定めるのは **worker の判断**についての境界(worker が人間を呼ぶか、仮定を置いて
  進むか)である。**これ以外の理由で介入が起きる経路は別に存在する**: レビューゲートの不具合
  (レビュア出力が `review_format_error_limit` 回続けて解釈できない = `review_gate_defect`。
  `FR-orch-06` 受入基準6)は worker の判断ではないため上表に含めず、それ自体で介入へ回る。
- 理由: 「軽微」は測定できず、境界値テストの入力を決められない(issue 008)。実装は移設前から
  上表の条件で動いており(**実装が正**)、要件側の表現だけが人間の言葉のまま残っていた。
- 影響: `FR-orch-04` 受入基準4 / `UC-04` 代替フロー A1 / `NFR-perf-03` の表現を上表の条件へ置き換える。
  **振る舞いは変わらない。**
- 関連: `FR-orch-04` / `FR-orch-06` / `D0-orch-04`(起点は issue 008。**同 issue は本決定の反映と同時に解消・削除**するため、経緯は `docs/histories/` を参照)

## 分離時に決めること(この抽出物には答えが無い論点)

抽出元は「Docker 開発環境 + オーケストレーター」という1つのシステムの要求である。
オーケストレーターだけを別プロジェクトにすると、**抽出元では自明だった前提が前提でなくなる**。
下は**この抽出作業で見つかった論点**であり、分離先の 00-requests を起こすときに決める必要がある
(ここで勝手に決めていない — いずれも外から見えて後戻りしにくい判断であるため)。

| # | 論点 | なぜ抽出元では問題にならなかったか |

| 1 | オーケストレーターの**実行前提を「隔離コンテナの中」に置き続けるか** | 抽出元では同じシステムがコンテナを用意していた。`DSN-arch-03`(コンテナ起動の後段に固定)と「やらないこと」1(worker を個別隔離しない)は、**コンテナという1本の隔離境界があること**を前提に成立している。分離先が任意のホストで直接動くなら、隔離の前提そのものを決め直す必要がある |
