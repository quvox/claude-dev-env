# オーケストレーター 要件定義(抽出)

> **この文書の位置づけ**
> `claude-dev-env` の仕様ドキュメント(SSOT)から、**オーケストレーターに関わる要件だけ**を
> 原文のまま抜き出した**抽出物**である。SSOT ではないので `verified`(検証済み記録)を持たない。
> 条項 ID(`FR-orch-nn-#`)は**抽出元と同一**であり、番号を詰め直していない
> (抽出元の規則「一度振ったら動かさない」を分離後も守れるようにするため)。
> 上流は [00.md](00.md)。

## 機能要件

条項 ID(`FR-<domain>-nn-#`)は**一度振ったら動かさない**: 欠番を埋めない・並べ替えない・
廃止した番号を別の基準に再利用しない(02 のカバレッジ表・03 のテスト対応表が外部から参照するため)。

### FR-orch-01 2モードのオーケストレーション

- 対応要求: RQ-orch-01 / AC-04
- **分割可否: 不可分**
- 内容: 検討(人間主導)と実装(自律・並列)を1つの実体の2モードとして提供すること。

受け入れ基準(EARS):

| 条項 ID | 種別 | 基準 |
|---|---|---|
| FR-orch-01-1 | 正常系 | WHEN `claude-dev orchestrate` を実行したとき、システムはブレインストーミングモード(人間×対話 Claude)から開始しなければならない |
| FR-orch-01-2 | 正常系 | WHILE ブレインストーミングモードで動作している間、システムはブレインストーミング(人間の検討)を自動化してはならない |
| FR-orch-01-3 | 正常系 | WHEN ブレインストーミングで plan が確定し実行が要求されたとき、システムは実行モードへ遷移し、各タスクを worker へディスパッチしなければならない |
| FR-orch-01-4 | 正常系 | WHILE オーケストレーターが動作している間、システムはモード間の引き渡し契約を仕様ドキュメントとし、運用状態は `.orchestrator/` に保持しなければならない |
| FR-orch-01-5 | 境界値 | IF plan が実行不可(未 ready、または完了条件が欠落)ならば、システムは理由を端末に明示してブレインストーミングへ戻さなければならない |
| FR-orch-01-6 | 境界値 | IF 引き渡しの意図が判別できないならば、システムは選択肢(続ける/実行する/終了する)を提示しなければならず、勝手に実行を開始してはならない |
| FR-orch-01-7 | 異常系 | IF 古い引き渡し指示が残っているならば、システムは対話を起こす直前にそれを破棄しなければならない(古い指示を誤って消費しない) |

### FR-orch-02 外部制御ループとコントローラ常駐

- 対応要求: RQ-orch-01 / AC-05
- **分割可否: 不可分**
- 内容: 継続/停止をコードで判定し、端末が壊れても実行が失われないこと。

受け入れ基準(EARS):

| 条項 ID | 種別 | 基準 |
|---|---|---|
| FR-orch-02-1 | 正常系 | WHILE 実行モードで動作している間、システムは継続/停止をコード(外部制御ループ)で判定しなければならない(LLM の裁量に委ねない) |
| FR-orch-02-2 | 正常系 | WHEN `orchestrate` でコントローラを起動したとき、システムはコントローラを tmux セッション `orch-<project>-main` の `dashboard` ウィンドウで常駐させ、worker とブレインストーミングを同セッションの独立ウィンドウとして管理しなければならない |
| FR-orch-02-3 | 正常系 | WHILE 反復が進む間、システムは worker へ渡す文脈について、**リポジトリ全体を渡してはならず、完了した依存タスクの成果物そのものを渡してはならない**(渡してよいのは完了した依存タスクの**結果の要約**までである)。**渡す要素の構成は 02 の契約が定める** |
| FR-orch-02-4 | 境界値 | IF セッションは存在するがコントローラのプロセスが存在しないならば、システムはそれを空き殻とみなして作り直さなければならない(生存と誤判定してはならない) |
| FR-orch-02-5 | 異常系 | IF 対象コンテナが起動していないならば、システムは自動で起動してから続行するか(Linux)、起動を促して終了コード 1 で終わらなければならない(macOS) |

### FR-orch-03 worker の並列実行と分離

- 対応要求: RQ-orch-01 / AC-04
- **分割可否: 不可分**
- 内容: 複数の worker が競合せず並行作業すること。

受け入れ基準(EARS):

| 条項 ID | 種別 | 基準 |
|---|---|---|
| FR-orch-03-1 | 正常系 | WHEN worker をディスパッチするとき、システムは各 worker を `/workspace` 内の git worktree で作業させ、ファイル競合を防がなければならない |
| FR-orch-03-2 | 正常系 | WHILE worker が実行中である間、システムは worker のライブ出力を当該 worker ウィンドウで確認可能にしなければならない |
| FR-orch-03-3 | 正常系 | WHERE 設定ファイルが存在する構成において、システムは並行度(`max_workers`。既定 5)・行き詰まり上限(`stuck_limit`。既定 3)・レビュー反復上限(`max_review_rounds`。既定 10)・レビュー形式エラー上限(`review_format_error_limit`。既定 2)・worker 猶予秒(`worker_grace_seconds`。既定 10)・統合方式(`merge_strategy`。既定 `merge`)を設定ファイルで変更可能にしなければならない |
| FR-orch-03-4 | 正常系 | WHEN worker の成果を統合するとき、システムはその統合を直列に(コントローラが)実行しなければならない |
| FR-orch-03-5 | 境界値 | IF 着手可能なタスクが並行度の上限(`max_workers`。既定 5)を超えているならば、システムは上限までしか同時にディスパッチしてはならず、超過分は次の空きまで待たせなければならない |
| FR-orch-03-6 | 境界値 | IF 依存先のタスクが失敗したならば、システムは依存するタスクをブロック状態にしなければならない(依存を無視して着手しない) |
| FR-orch-03-7 | 異常系 | IF worker の出力が期待する形式で得られないならば、システムはそれを失敗として扱い、成功と解釈してはならない |
| FR-orch-03-8 | 境界値 | IF 整数の設定値(`max_workers` / `stuck_limit` / `max_review_rounds` / `review_format_error_limit`)に 0 以下または数値として解釈できない値が与えられたならば、システムはその値を**黙って無視**し、より弱い段のマージ結果を保たなければならない(起動を止めてはならない) |
| FR-orch-03-9 | 境界値 | IF `worker_grace_seconds` に 0 が与えられたならば、システムはそれを有効な値として受理しなければならない(**猶予を置かずに**強制終了する = 中断シグナルの後に待ち時間を設けない) |
| FR-orch-03-10 | 境界値 | IF `merge_strategy` に `merge` / `rebase` 以外の値が与えられたならば、システムは `merge` として扱わなければならない(未知の値をエラーにしない) |
| FR-orch-03-11 | 境界値 | WHERE 設定の解決において、システムは 組込既定 → 利用者ごとの設定 → プロジェクトごとの設定 → 環境変数 の4段でマージしなければならない(**各段の設定の置き場は 02 の契約が定める**)。**環境変数の段は Slack の資格情報(`SLACK_BOT_TOKEN` / `SLACK_CHANNEL`)にのみ適用する** |

### FR-orch-04 介入はタスク単位

- 対応要求: RQ-orch-01 / AC-04
- **分割可否: 不可分**
- 内容: 1件の要判断が他の worker を止めないこと。

受け入れ基準(EARS):

| 条項 ID | 種別 | 基準 |
|---|---|---|
| FR-orch-04-1 | 正常系 | WHEN あるタスクが介入トリガー(重大判断/曖昧さ/行き詰まり/方針分岐/前提崩れ)に該当したとき、システムはそのタスクだけを待機状態にし、他の worker を継続させなければならない |
| FR-orch-04-2 | 正常系 | WHEN あるタスクが判断待ちになったとき、システムは判断待ちを介入キューに積み、ダッシュボードのセレクタで一覧・選択可能にしなければならない |
| FR-orch-04-3 | 正常系 | WHEN 人間が回答して対話を終えたとき、システムは同じ worker ウィンドウでそのタスクの実行を復帰させなければならない |
| FR-orch-04-4 | 正常系 | IF 判断が `D0-orch-18` の発火条件のいずれにも該当しないならば、システムは仮定を1つ置いて自律継続し、その仮定を状態ストアへ記録しなければならない(記録が無いまま進めてはならない) |
| FR-orch-04-5 | 境界値 | IF 同一タスクの試行回数が `stuck_limit`(既定 3)以上に達したならば、システムは介入へ回さなければならない |
| FR-orch-04-6 | 異常系 | IF 介入の突合に使う状態が実行中の実体と異なるならば実行が恒久停止するため、システムは実行中の実体に対して突合しなければならない |
| FR-orch-04-7 | 境界値 | IF ディスパッチ前のタスクが不可逆と印付けされており、かつ人間の承認がまだ無いならば、システムは worker を起動する前に介入へ回さなければならない |
| FR-orch-04-8 | 境界値 | IF 不可逆なタスクが介入で人間に承認されたならば、システムは同じ条件で再度介入へ回してはならない(再開時の無限ループを起こさない) |
| FR-orch-04-9 | 境界値 | IF `stuck_limit` の実効値が 0 以下であるならば、システムは**試行回数による発火を行ってはならない**(その試行での行き詰まり検出と worker からの申告による発火だけが残る)。**設定ファイル経由ではこの状態に到達しない**(`FR-orch-03` 受入基準8 により 0 以下は採用されず既定 3 が残る) |

### FR-orch-05 状態の保全と中断・再開

- 対応要求: RQ-orch-01 / AC-05
- **分割可否: 不可分**
- 内容: 中断・再開で完了済み作業をやり直さないこと。

受け入れ基準(EARS):

| 条項 ID | 種別 | 基準 |
|---|---|---|
| FR-orch-05-1 | 正常系 | WHEN 起動時の自動処理を行うとき、システムは起動時の自動処理で plan/状態/履歴を削除してはならない。片付けは全タスクが完了しているか `--fresh` 指定時のみとし、その場合も**削除せずに退避先へ移さなければならない**(退避先は 02 が定める) |
| FR-orch-05-2 | 正常系 | WHEN 未完了の plan が残る状態で `orchestrate` したとき、システムはその run を継続しなければならない |
| FR-orch-05-3 | 正常系 | WHEN 中断した run を再開するとき、システムは完了・失敗・ブロックのタスクを再開時に変更してはならない(途中状態のみ正規化する) |
| FR-orch-05-4 | 正常系 | WHEN 中断シグナルまたは終了操作を受けたとき、システムは実行中の worker に中間コミットの猶予を与えて状態を保存し、終了コード 0 でクリーンに終了しなければならない |
| FR-orch-05-5 | 正常系 | WHEN 中断した run を再開するとき、システムは各 worker のセッション ID を保存し、同一 Attempt の再開時は続きから再開しなければならない |
| FR-orch-05-6 | 境界値 | IF 状態ファイルの書き込み中に異常終了したならば、既存の記録が壊れてはならない(原子的置換または追記のみとする) |
| FR-orch-05-7 | 異常系 | IF **永続する運用状態**(plan・実行状態・未解決の介入と履歴)が読み取れないならば、システムは既存の内容を破壊してはならない。**1回だけ消費される制御の受け渡しはこれに含まない**(壊れていれば削除して「無い」と同じ扱いにする。**どの記録がどちらに当たるかは 02/03 が定める**) |
| FR-orch-05-8 | 境界値 | WHERE 一貫性の単位において、システムは **1ファイル1書き込みを一貫性の境界**としなければならない。複数ファイル(plan・state・追記型ログ・git の統合結果)をまたぐ原子性は提供しない。したがって異常終了の直後に plan と state が食い違う状態が観測されうる |
| FR-orch-05-9 | 境界値 | IF 追記型ログへの追記中にプロセスが異常終了したならば、システムは**末尾に不完全な記録が残ることを許容しなければならない**(**この記録は再開の判断に使わない**ので、再開の結果は変わらない。追記の形式と方式は 02/03 が定める) |
| FR-orch-05-10 | 異常系 | IF 状態ファイル・plan ファイルが存在しないならば、システムはそれをエラーとせず「未作成」として扱わなければならない |

### FR-orch-06 品質ゲート(相互レビュー)

- 対応要求: RQ-orch-01
- **分割可否: 不可分**
- 内容: 実装を独立した観点でレビューして品質を担保すること。

受け入れ基準(EARS):

| 条項 ID | 種別 | 基準 |
|---|---|---|
| FR-orch-06-1 | 正常系 | WHEN worker が実装を終えたとき、システムは実装した worker とは別の worker による独立レビューを通さなければならない |
| FR-orch-06-2 | 正常系 | WHEN レビューを採点するとき、システムはレビューを当該タスクの完了条件のみを基準に採点しなければならない(プランのゴールで採点しない) |
| FR-orch-06-3 | 正常系 | WHEN レビュー結果を受け取るとき、システムは**プロンプトで JSON の形を明示して**構造化出力を要求しなければならない。**ツールによるスキーマ強制は行わない**(形式が崩れた場合の扱いは受入基準7 と6 が定める)。**受け取るフィールドの必須性・型・列挙値は 02 の契約が定める** |
| FR-orch-06-4 | 正常系 | WHILE 改訂ループを回している間、システムは改訂ループに終了条件(重大指摘の解消、または最大回数)を設けなければならない |
| FR-orch-06-5 | 境界値 | IF タスクに完了条件が未設定ならば、システムはディスパッチ前の検証で弾かなければならない |
| FR-orch-06-6 | 境界値 | IF 同一のフォーマットエラーが 2 回続いたならば、システムは自動リトライを打ち切り介入へ回さなければならない |
| FR-orch-06-7 | 異常系 | IF レビュー結果が構造化されていない散文で返ったならば、システムは1回だけ再整形を試み、判定内容を変えてはならない |

### FR-orch-07 モデル選択・完了検証・通知

- 対応要求: RQ-orch-01 / AC-04
- **分割可否: 不可分**
- 内容: 工程に応じたモデルで動き、状況を非同期に把握できること。

受け入れ基準(EARS):

| 条項 ID | 種別 | 基準 |
|---|---|---|
| FR-orch-07-1 | 正常系 | WHEN エージェントを呼び出すとき、システムは工程別にモデル/effort を選ばなければならない(設計系=opus/high、実装・テスト系=sonnet/high、検討・介入・レビュー=opus/high) |
| FR-orch-07-2 | 正常系 | WHEN 全タスクが完了したとき、システムは完了条件に対する助言的検証を行い、未充足の可能性を通知しなければならない(実行はブロックしない) |
| FR-orch-07-3 | 正常系 | WHILE 実行モードで動作している間、システムは状況サマリ(進捗/ブロッカー/要判断/仮定/次にやること)を非同期に通知しなければならない |
| FR-orch-07-4 | 境界値 | IF 通知先が設定されていないならば、システムは通知を行わず、実行を継続しなければならない |
| FR-orch-07-5 | 異常系 | IF 通知の送信に失敗したならば、システムは実行を止めてはならない |
| FR-orch-07-6 | 異常系 | IF 同一の作業から重複して通知が発火しうるならば、システムは重複を抑制しなければならない |

### FR-orch-08 ダッシュボード UI と日本語提示

- 対応要求: RQ-orch-01 / AC-04
- **分割可否: 不可分**
- 内容: 今どのモードで何を待っているかが分かり、誤操作なく移動できること。

受け入れ基準(EARS):

| 条項 ID | 種別 | 基準 |
|---|---|---|
| FR-orch-08-1 | 正常系 | WHILE ダッシュボードを表示している間、システムはダッシュボードをイベント駆動 TUI で描画し、カーソル選択(↑↓/jk)と Enter 確定でのみウィンドウ移動しなければならない(数字キーでの即時移動・全画面再描画は行わない) |
| FR-orch-08-2 | 正常系 | WHEN 人間に選択を求めるとき、システムは人間に選択を求めるとき、選択肢へ必ず番号を付け、番号での回答を受理しなければならない |
| FR-orch-08-3 | 正常系 | WHEN 人間の判断・入力を求める表示を行うとき、システムは人間の判断・入力を求める表示(質問・選択肢・メニュー・バナー・理由・人間向け要約)をすべて日本語にしなければならない |
| FR-orch-08-4 | 正常系 | WHILE オーケストレーターが動作している間、システムは人間に運用状態ファイルの直接編集を促してはならない(修正は対話へ誘導する) |
| FR-orch-08-5 | 正常系 | WHERE リポジトリルートに `ORCHESTRATOR.md` が存在する場合、システムはその内容を各プロンプトの先頭へ前置しなければならない |
| FR-orch-08-6 | 境界値 | IF 端末が対話的でないならば、システムは選択を求めずに既定値で処理を進めなければならない |
| FR-orch-08-7 | 異常系 | IF 補助情報(VM のヘルス等)の取得に失敗したならば、システムは描画を止めてはならない |
| FR-orch-08-8 | 異常系 | IF 異常終了したとしても、システムは端末の状態を復元しなければならない |

### FR-orch-09 自己検証(バンドル題材での実走)

- 対応要求: RQ-orch-01
- **分割可否: 不可分**
- 内容: 保守者がオーケストレーターの振る舞いを実題材で確認できること。

受け入れ基準(EARS):

| 条項 ID | 種別 | 基準 |

## ユースケース

### UC-04 並列実装し、要判断だけ対応する

- 形式化した受け入れ基準: AC-04
- アクター: 開発者
- 目的: 案件を自律・並列で実装させ、人間は検討と例外対応だけに関与する
- 事前条件: コンテナが起動している
- 事後条件: 要判断のタスクだけが待機し他の worker は継続、回答後に実行復帰、完了で成果が統合される
- 関連要件: FR-orch-01, FR-orch-02, FR-orch-03, FR-orch-04, FR-orch-06, FR-orch-07, FR-orch-08

基本フロー:

1. 開発者が `claude-dev orchestrate` を実行する。
2. システムはコントローラを常駐起動し、ダッシュボードをホーム表示する。
3. 開発者はブレインストーミングウィンドウの対話 Claude と plan を確定し、対話を終える。
4. システムは実行モードに入り、各タスクを worker(git worktree で分離)へ並行ディスパッチする。
5. 開発者は detach して離席する。
6. あるタスクが要判断になると、システムは「要判断 N 件」を通知し、そのタスクだけを待機させる。
7. 開発者は attach し、ダッシュボードのセレクタで待機中の worker を選び、対話で回答して終える。
8. システムはそのタスクの実行を復帰させ、全タスク完了時に成果を統合して完了を通知する。

  「部分的に満たした状態が、何も満たさない状態より利用者にとって価値がある」要件だけである。
