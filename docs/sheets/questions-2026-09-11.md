# 質問シート 2026-09-11

## 論点 1. AC-02・AC-06 の実機判定を、いつまでも「未判定条項」のままにするか、棚上げにするか

- **背景**: `claude-dev` には受け入れ基準が6件あります(AC-01・AC-02・AC-03・AC-06・AC-07・AC-08)。
  今回の `/verify-tests`(全区分)で、この無人・単一ホストの実行環境で実際に判定できるもの
  (AC-01: 隔離コンテナでの開発開始 / AC-03: 危険な Docker 操作の拒否 / AC-07: 同梱した実行
  ファイルがそのまま使えること / AC-08: プロジェクトごとの環境変数)は、いずれも実機のコンテナを
  起動して実際に確認し、合格でした。
  残る2件は、この環境では原理的に確認できません:
  - AC-02(サーバ上で `claude-dev forward` したポートに、**別のクライアント PC のブラウザ**から
    SSH トンネル越しに接続できること) — 検証には物理的に別のクライアント PC が要ります。
  - AC-06(**実際の OpenAI アカウント**で `claude-dev login-codex` の対話ログイン(ブラウザで
    コードを入力する形)を行い、Codex CLI が実際に動くこと) — 検証には人が実際にブラウザで
    ログイン操作をする必要があり、無人では行えません。
  この2件は「未判定条項」(合格とも不合格とも判定できなかったもの)として記録するのが検証の
  規範の定めですが、その規範は同時に「未判定条項が1件でもあると `e2e` の試験区分は合格に
  ならない」とも定めています。したがって、**この2件が今の形のまま残る限り、`e2e` は
  恒久的に合格しません**(コードや文書がどれだけ整っていても、です)。
  この状況は今回はじめて起きたことではありません — この2件が対話操作・実機を要することは
  以前から分かっており(`docs/residual.md` の 2026-09-01 の行に記録済み)、それでも過去には
  `e2e` を合格として記録した回があります(2026-09-01 時点)。今回はその過去の扱いを見直し、
  検証の規範どおり「未判定条項」として正直に報告し、`e2e` を不合格で記録しました。
- **明確にしたいこと**: この2件を今後どう扱うか
- **選択肢**:
  - A: `docs/pendings.md` に新しい棚上げ項目(P-nnn)を作り、「クライアント PC・実 OpenAI
    アカウントでの人手確認は、専有できる検証環境を用意するまで棚上げする」と決める。
    そうすると、この2件は今後「適用外(棚上げ)」として扱え、`e2e` は他の4件(AC-01・03・07・08)
    が合格している限り合格として記録できるようになります。
  - B: 今のまま「未判定条項」として扱い続け、`e2e` は恒久的に不合格のままにする(実機での
    人手確認ができる状態になるまで、デプロイゲートはこの1点で閉じません)。
  - C: 人が実際にクライアント PC とブラウザを用意し、この2件を手動で確認する(1回だけ行えば、
    以後はコードが変わらない限り再確認は不要です)。
- **AI推奨**: A。理由: この2件は艦隊の無人運用という前提そのものから生じる制約であり、コードを
  直しても解消しません。棚上げにして正直に記録するほうが、いつまでも赤いままのデプロイゲートより
  実情に合います。崩れる条件: この2件を自動化・代替確認できる手段(例: 疑似クライアントを使った
  自動テスト)が実装されたとき、そのときは棚上げを解いてその手段で判定します。
- **未回答時の既定**: 現状維持(B)。`e2e` は「未判定条項」を抱えたまま不合格で記録し続けます。
- **間違えたときの戻し方**: A を選んだ後で実際に確認できる環境ができたら、`docs/pendings.md` の
  該当項目を削除し、その回の `/verify-tests` で実際に判定すればよいだけです。
- **過去の回答**: なし(この論点についての決定シート・履歴は見当たりませんでした)。
- **転記先**: A を選んだ場合は `docs/pendings.md`(新規 P-nnn)。B・C を選んだ場合はこのシートの
  回答をそのまま記録に残すだけで、SSOT への転記はありません。
