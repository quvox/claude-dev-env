## 性能

| ID | 要件 | 目標値 | 測定方法 | 分割可否 |
|---|---|---|---|---|
| NFR-perf-01 | 日次ビルドの更新後も、利用者の `docker pull` は増分取得に留まること。**同梱エージェント CLI または同梱外部バイナリが更新されたときに再取得させる層は、その導入・設置層以降のみとする** | **同梱 CLI のバージョンと同梱外部バイナリの内容がどちらも変わらない日は**、配布 2 イメージのどの層も再取得が発生しない | **同梱 CLI のバージョンと同梱外部バイナリの内容がどちらも変わっていない日に**、前日分のイメージを持つ環境で `docker pull` を実行し、`Already exists` 以外の層が出ないことを確認する | 段階可(理由: 再取得される層が1つ減るだけでも取得時間の短縮という利用者価値があり、目標「再取得ゼロ」へ層単位で段階的に近づけるため) |
| NFR-perf-02 | ブラウザ確認ありのイメージは、なしのイメージのベースレイヤーを共有し、追加ディスクを VNC/Chrome 分に限定すること | (1) 2 イメージのベース層が同一ダイジェストであること。(2) **ブラウザ確認ありイメージだけが持つ追加層が導入するのは、ブラウザ確認(`FR-env-11`)を成立させる資産だけであること**。具体的には (i) VNC・ディスプレイ・ウィンドウマネージャ・noVNC、(ii) GUI ブラウザとその追加依存、(iii) 日本語入力とロケール(`FR-env-11` 受入基準3)、(iv) GUI セッションの端末・キー操作と gsettings/dconf バックエンド、(v) フォント、(vi) computer-use MCP の6カテゴリであり、**いずれにも属さない導入やファイル追加(開発ツール・言語ランタイム・ビルド済み成果物)が1件も現れないこと**。**両イメージが等しく持つ層は (2) の対象外**である — 該当するのは**同梱エージェント CLI の導入層**と、**同梱外部バイナリの設置層**(`FR-env-13-1` が両方の配布イメージへ等しく設置すると定めている)の2つである | `docker history --no-trunc` で両イメージの層を並べ、共通部分より後ろの層の `CREATED BY` を1行ずつ読む。(1) は共通部分の最終層のダイジェスト一致で判定する。(2) は追加層の `CREATED BY` に現れる導入物を上の6カテゴリへ1件ずつ割り当て、**どのカテゴリにも割り当てられないものが1件でもあれば不合格**とする。**対象の層は、02 が定めるステージ構成のうちブラウザ確認資産を積むステージである**。**付随処理(D-Bus の machine-id 生成・GTK の IM モジュールキャッシュ更新など、それ単体では上のどれでもないが、無いと特定のカテゴリが動かないもの)は、動かなくなるカテゴリへ帰属させる**(帰属先が1つも無いものだけを不合格とする) | 段階可(理由: 共有されるベース層が増えるほど追加ディスクが減る形で目標へ段階的に近づけ、部分達成にもディスク削減の価値があるため) |
