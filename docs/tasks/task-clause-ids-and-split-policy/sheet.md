### 論点 5. `不可分` の要件が `部分` の条項を持つ(FR-env-01 / FR-env-07。PASS をブロックする)

**これは今回の移行が可視化した既存の状態です。** 条項単位のカバレッジ表を作った結果、
`FR-env-01-19` と `FR-env-07-5`(どちらも compose 資源の一意化)の充足が `部分(P-005)` になりました。
一方この2要件の `分割可否` は、決定シート概念1(委任)の制約どおり `不可分` です。
規範は「`不可分` の要件に `部分` の条項が1つでもあれば重大度『高』で PASS をブロックする(例外なし)」と
定めるため、**このままでは `/task-close` で 01・02 を検証済みにできません**。
`分割可否` は要件単位、充足は条項単位という粒度差が原因で、委任のガードレールが
「3件以外を `段階可` にしたくなったら人間へ問う」と定めているため、ここでお伺いします。

- **選択肢**:
  A `FR-env-01` と `FR-env-07` を `段階可(理由)` に変える(理由に、段階的なのは compose 名の一意化の
    条項だけであることを明記する) /
  B 充足を `完全` に戻し、ハッシュ衝突は「設計の範囲外の残存リスク」として pendings だけで追跡する /
  C `不可分` のまま `部分` を残す(= 衝突検出を実装する別タスクが完了するまで、01・02 は検証済みにしない)
- **AI推奨**: **A**。理由: `不可分` の定義は「部分的に満たした状態が何も満たさないより悪い」であり、
  compose 名の一意化はこれに当てはまらない — 衝突確率を実用上無視できる水準まで下げた現状は、
  正規化名だけで確実に衝突していた以前より**厳密に良い**(`docs/pendings.md` P-005 が
