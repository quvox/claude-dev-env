# セキュリティ・隔離の決定事項

## D0-sec-01 コンテナの confinement を緩めない範囲での対処の選び方

- 区分: 委任
- 決めた日: 2026-07-31
- 委任範囲: コンテナ内のツールが Docker の既定 confinement(seccomp / AppArmor)の下で動かないとき、
  どう対処するか(ツール側の設定で回避する / 機能を落とす / 別バックエンドを使う)。
  リスナーの待ち受けアドレスや、強い権限を持つ MCP を既定で有効にするかどうかの判断も含む。
- 制約(ガードレール): **`docker run` の `--security-opt` を付けてコンテナ側の confinement を
  緩める選択肢は採れない**(隔離境界はコンテナ/ホスト間のみという前提〈`D0-sec-06`〉を支えている
  ものであるため)。ホストへ新規のポートを公開しないこと。強権限の機能は既定で無効にすること。
- 報告義務: 決めた内容を該当機能の「実装上の判断」表に `D0-sec-01` と共に記録する
- 関連: FR-env-12 / NFR-sec-01

## D0-sec-02 ホスト資産をコンテナへ渡すときの絞り込み方

- 区分: 委任
- 決めた日: 2026-07-30
- 委任範囲: ホストの設定ファイルをコンテナへ渡す際、そのまま渡すか・一部を除去した写しを渡すか・
  読み取り専用にするか。
- 制約(ガードレール): **秘密鍵・認証情報の実体をコンテナへ渡さない**こと。渡すものは読み取り専用に
  すること。除去したことで利用者の作業が黙って壊れないよう、影響のある項目は該当機能の異常系に書くこと。
- 報告義務: 決めた内容を該当機能の「実装上の判断」表に `D0-sec-02` と共に記録する
- 関連: FR-env-04 / NFR-sec-01

## D0-sec-03 秘密情報(トークン)の伝播範囲

- 区分: 委任
- 決めた日: 2026-07-30
- 委任範囲: 通知用トークン等の秘密情報を、どのプロセスまで渡すか(親だけに留めるか、子プロセスにも
  渡すか)。
- 制約(ガードレール): 秘密情報の到達範囲は**必要な発信源だけ**に限ること。エージェント(worker・
  対話 Claude)へ渡さないこと。渡さないことで機能が落ちる場合は、落ちる範囲を該当機能に明記すること。
- 報告義務: 決めた内容を該当機能の「実装上の判断」表に `D0-sec-03` と共に記録する
- 関連: FR-orch-07 / NFR-sec-01

## D0-sec-04 ファイアウォールの実装方式と適用範囲

- 区分: 委任
- 決めた日: 2026-07-30
- 委任範囲: ブロック対象の表現方法(ホスト名指定か IP 集合か)、名前解決のタイミング(起動時の
  一回解決か追従か)、どのチェインに規則を置くか。
- 制約(ガードレール): 適用に失敗してもコンテナの起動を止めないこと(`FR-env-05` の受け入れ基準)。
  適用の成否が起動ログから判別できること。既定の通信(Anthropic API 等、開発に必要な宛先)を
  塞がないこと。
- 報告義務: 決めた内容を該当機能の「実装上の判断」表に `D0-sec-04` と共に記録する
- 関連: FR-env-05 / NFR-sec-01

## D0-sec-05 Docker API 検査の厳密さと安全側の倒し方

- 区分: 委任
- 決めた日: 2026-07-30
- 委任範囲: docker-proxy がリクエストを検査するときの厳密さ(字句的な判定に留めるか、実体解決まで
  行うか)、解釈できない入力を通すか止めるか。
- 制約(ガードレール): 拒否すべき操作(作業領域外のホストバインド・特権・ホストのネットワーク/
  プロセス空間)を**通してはならない**。判定に必要な情報がプロキシの手元に無い場合は、その事実を
  該当機能の「既知の制限」に書くこと。
- 報告義務: 決めた内容を該当機能の「実装上の判断」表に `D0-sec-05` と共に記録する
- 関連: FR-env-07 / NFR-sec-01

## D0-sec-06 エージェントの隔離モデルは単一コンテナ同居型とする

- 区分: 決定
- 決めた日: 2026-07-30
- 内容: root/worker は同一コンテナ・同一ファイルシステムを共有し、個別隔離しない。**隔離境界は
  コンテナ/ホスト間にのみ置く**。
- 理由: 信頼できる社内開発用途に限定するという前提のもとでの割り切り。worker ごとの隔離は
  実装・運用コストが高い。この前提は下流の全判断(Codex サンドボックスの扱い・confinement を
  緩めない方針)の根拠になっている。
- 却下した案: microVM 等による worker ごとの個別隔離 — 実装・運用コストに見合わない。
  個別隔離が要る用途は別構成(Docker Sandboxes 等)で検討する。
- 関連: RQ-env-01 / NFR-sec-01 / request.md「やらないこと」1

## D0-sec-07 Docker アクセスは生ソケットではなく検査プロキシ経由にする

- 区分: 決定
- 決めた日: 2026-07-30
- 内容: 生ソケットをマウントせず、Go 製の `docker-proxy` 経由で制限付き Docker API を使う。
  作業領域(`/workspace`)配下を除くホストバインドマウント・privileged・ホストの
  ネットワーク/プロセス空間の共有を拒否する。
- 理由: 生ソケット共有はホスト掌握と同義のリスクがある。既定で危険操作を遮断する。
- 却下した案: 生ソケットの直マウント — 前述のリスク。DinD — 特権が必要で同じ問題を持つ。
- 関連: RQ-env-04 / FR-env-07

## D0-sec-08 SSH 秘密鍵はマウントせず agent 転送だけにする

- 区分: 決定
- 決めた日: 2026-07-30
- 内容: 秘密鍵ファイルはコンテナにマウントしない。プロジェクト直下 `.claude-dev.yaml` の
  `ssh_keys` で指定された鍵だけをプロジェクト専用 ssh-agent に登録し、そのソケット
  (macOS は socat の TCP ブリッジ)だけを転送する。
- 理由: 鍵ファイルの露出を避けつつ、ディレクトリごとに異なる鍵を使えるようにする。
- 却下した案: `~/.ssh` の読み取り専用マウント — 別プロジェクトの鍵まで見える。
  ホストの共有 ssh-agent の転送 — 登録済みの全鍵が使えてしまい限定にならない。
- 関連: RQ-env-01 / FR-env-04

## D0-sec-09 レビュー前コードの外向き通信はコンテナ内のファイアウォールで制御する

- 区分: 決定
- 決めた日: 2026-07-30
- 内容: コンテナ内で iptables のファイアウォールを設定する。
- 理由: レビュー前コードの外部通信を制御する。ホスト側で制御するとプロジェクト単位に分けられない。
- 却下した案: ホスト側ファイアウォールでの制御 — プロジェクト単位に分けられない。
  ネットワークを完全遮断する — 開発に必要な通信(パッケージ取得・API)まで塞がる。
- 関連: RQ-env-01 / FR-env-05

## D0-sec-10 KVM デバイスは既定で渡さない

- 区分: 決定
- 決めた日: 2026-07-30
- 内容: 既定では `/dev/kvm` 等を渡さない。`--kvm` を指定したときだけデバイスを渡す
  (無ければ警告してソフトウェアエミュレーションにする)。
- 理由: 通常はコンテナ内 Chrome での確認で足りる。過剰な特権付与を避ける。
- 却下した案: 常時渡す — 必要のない利用者にまで特権を与える。
- 関連: RQ-env-05 / FR-env-08
