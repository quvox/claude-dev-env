# 機能要件

## FR-env-01 コンテナのライフサイクル管理

- 対応要求: RQ-env-01 / AC-01
- 内容: プロジェクトごとに隔離コンテナを起動・再接続・停止・一覧できること。SSH 切断後も作業が
  維持されること。

受け入れ基準(EARS):

| # | 種別 | 基準 |
|---|---|---|
| 1 | 正常系 | WHEN `claude-dev start` を実行したとき、システムはカレントディレクトリを `/workspace` にマウントしたコンテナ(既定はブラウザ確認あり)を起動し、tmux にアタッチしなければならない |
| 2 | 正常系 | WHERE `--no-vnc` が指定された場合、システムはブラウザ確認資産を持たない軽量イメージを使わなければならない |
| 3 | 正常系 | WHILE コンテナが起動している間、SSH 切断や tmux デタッチが起きてもコンテナは動作を継続しなければならない |
| 4 | 正常系 | WHEN 同一ディレクトリで `claude-dev start` を再実行したとき、システムは既存コンテナへ再接続しなければならない(tmux セッションが無ければ再作成する) |
| 5 | 正常系 | WHEN `claude-dev list` を実行したとき、システムは実行中セッションの一覧(noVNC URL とフォワード状況を含む)を表示しなければならない |
| 6 | 正常系 | WHEN `claude-dev stop <name>` を実行したとき、システムは当該コンテナを削除し、当該コンテナ内から起動された compose コンテナ群と当該プロジェクトの compose 既定ネットワークを削除し(名前付きボリュームは保持する)、全 Claude コンテナが停止したときは docker-proxy も停止しなければならない |
| 7 | 境界値 | IF tmux の起動待ちが上限(既定 30 秒 / VM モード 420 秒)を超えたならば、システムは終了コード 0 で状況を案内して終わらなければならず、コンテナを削除してはならない(コンテナは稼働を続け、再実行の再接続経路で合流できる) |
| 8 | 境界値 | IF 停止対象のコンテナが存在しないならば、システムは削除をスキップし、その旨を表示して終了コード 0 で終わらなければならない |
| 9 | 境界値 | IF 他プロジェクトの Claude コンテナが稼働中ならば、`stop` は docker-proxy を停止してはならない |
| 10 | 異常系 | IF 前提コマンド(`docker` / `jq`、macOS では `socat` も)が不足しているならば、システムは不足を列挙して導入方法を案内し、終了コード 1 で終わらなければならない |
| 11 | 異常系 | IF compose 既定ネットワークが他から使用中で削除できないならば、システムは処理を続行しなければならない(停止全体を失敗させない) |

## FR-env-02 UID/GID 追従とホスト資産の共有

- 対応要求: RQ-env-01 / AC-01
- 内容: コンテナ内のファイル所有権がホストと一致し、git 設定とシェル資産を引き継げること。

受け入れ基準(EARS):

| # | 種別 | 基準 |
|---|---|---|
| 1 | 正常系 | WHEN コンテナを起動したとき、システムはコンテナ内ユーザーの UID/GID を `/workspace` の所有者に一致させなければならない |
| 2 | 正常系 | WHERE ホストに `~/.gitconfig` が存在する場合、システムはそれを読み取り専用でマウントしなければならない |
| 3 | 正常系 | WHILE コンテナが稼働している間、システムはシェル設定を `claude-dev-config` ボリュームでコンテナ間共有し、コマンド履歴を `claude-dev-history` ボリュームで永続化しなければならない |
| 4 | 境界値 | IF 割り当てようとする UID/GID がコンテナ内の既存エントリと衝突するならば、システムは既存エントリを一時的な空き ID へ退避してから割り当てなければならない(起動は成功する) |
| 5 | 境界値 | IF `/workspace` の所有者が root(UID 0)ならば、システムは UID/GID を変更してはならない |
| 6 | 異常系 | IF ホストの設定ファイルが存在しないならば、システムはその項目をマウントせずに起動を続行しなければならない(起動を失敗させない) |

## FR-env-03 認証の共有とセッション分離

- 対応要求: RQ-env-03 / AC-01 / AC-06
- 内容: 一度のログインで全コンテナが認証を共有し、セッションと設定はコンテナごとに独立すること。
  同梱する両方のエージェント CLI(Claude Code / Codex CLI)について成り立つこと。

受け入れ基準(EARS):

| # | 種別 | 基準 |
|---|---|---|
| 1 | 正常系 | WHEN `claude-dev login` を実行したとき、システムは一時コンテナで対話認証を行い、完了後に認証ファイル(`.credentials.json` / `.claude.json`)を `claude-dev-auth` ボリュームへ保存しなければならない |
| 2 | 正常系 | WHEN コンテナを起動したとき、システムは認証ファイルを共有ボリュームからコンテナローカルへコピーしなければならない(symlink は使わない) |
| 3 | 正常系 | WHILE コンテナが起動している間、システムは 30 秒ごとに認証ファイルの変更を検知し、共有ボリュームへ書き戻さなければならない |
| 4 | 正常系 | WHILE コンテナが稼働している間、システムはセッション・設定(`settings.json` / `projects/` / `sessions/`)をコンテナ固有に保たなければならない |
| 5 | 正常系 | WHEN `claude-dev logout` を実行したとき、システムは共有ボリュームの認証情報を削除し、実行中コンテナを停止しなければならない(共有ボリューム全体を空にするため Claude Code と Codex CLI 双方の認証が消える) |
| 6 | 正常系 | WHEN `claude-dev login-codex` を実行したとき、システムは一時コンテナでデバイス認証を行い、完了後に `auth.json` を `claude-dev-auth` ボリュームの `codex/` サブディレクトリへ保存しなければならない |
| 7 | 正常系 | WHEN コンテナを起動したとき、システムは codex の認証ファイルをコンテナローカルの `~/.codex/` へコピーしなければならない |
| 8 | 正常系 | WHILE コンテナが起動している間、システムは 30 秒ごとに codex 認証ファイルの変更を検知し共有ボリュームへ書き戻さなければならない(トークンリフレッシュの伝播) |
| 9 | 正常系 | WHILE コンテナが稼働している間、システムは codex の設定(`config.toml`)とセッション履歴をコンテナ固有に保たなければならない |
| 10 | 境界値 | IF 共有ボリューム側に codex 認証が存在しないならば、システムは何もコピーせずに起動を完了しなければならない(未ログインのままコンテナを使える) |
| 11 | 境界値 | IF 共有ボリュームのファイル所有者がコンテナ内ユーザーと異なるならば、システムは所有者を修復してから処理を進めなければならない |
| 12 | 異常系 | IF 利用者が認証を完了せずにログイン操作を終えたならば、システムは共有ボリュームを変更してはならない(次回起動は未ログインのままとなる) |
| 13 | 異常系 | IF ログイン操作が端末を持たない環境で実行されたならば、システムは非0の終了コードで失敗しなければならない(黙って未認証のまま成功を返さない) |

## FR-env-04 SSH 鍵の限定転送

- 対応要求: RQ-env-01 / AC-01
- 内容: プロジェクトごとに必要な SSH 鍵だけをコンテナへ渡し、秘密鍵ファイルは露出させないこと。

受け入れ基準(EARS):

| # | 種別 | 基準 |
|---|---|---|
| 1 | 正常系 | WHEN コンテナを作成するとき、システムは SSH 秘密鍵ファイルをコンテナにマウントしてはならない(転送するのは agent ソケットだけであり、コンテナのライフサイクルのどの時点でも秘密鍵ファイルは渡らない) |
| 2 | 正常系 | WHERE プロジェクト直下 `.claude-dev.yaml` の `ssh_keys` が指定された場合、システムはプロジェクト専用の ssh-agent を起動し、その鍵だけを登録して転送しなければならない |
| 3 | 正常系 | WHEN `claude-dev ssh-keys` を実行したとき、システムは `~/.ssh` の鍵を対話選択させて `.claude-dev.yaml` を生成しなければならない |
| 4 | 境界値 | IF `.claude-dev.yaml` が無い、または `ssh_keys` が空ならば、システムは SSH 転送なしで起動し、指定方法を案内しなければならない(起動を止めない) |
| 5 | 境界値 | IF 指定された鍵ファイルが存在しないならば、システムは当該の鍵を警告してスキップし、残りの鍵で起動を続行しなければならない |
| 6 | 異常系 | IF agent ソケットの位置に壊れた残骸が存在するならば、システムはそれを自動で除去し、除去できない場合も起動を止めず、手動での対処方法を案内しなければならない |
| 7 | 異常系 | IF 端末を持たない環境で `.claude-dev.yaml` が無いならば、システムは対話選択を行わず、空の `ssh_keys` を書き出して起動を続行しなければならない |

## FR-env-05 ネットワーク隔離とファイアウォール

- 対応要求: RQ-env-01 / AC-01
- 内容: レビュー前コードの外向き通信を制御すること。

受け入れ基準(EARS):

| # | 種別 | 基準 |
|---|---|---|
| 1 | 正常系 | WHEN コンテナを起動したとき、システムはコンテナ内でファイアウォールを設定しなければならない |
| 2 | 正常系 | WHILE コンテナが稼働している間、システムはコンテナ間通信を専用ネットワーク `claude-dev-net` 上で行わなければならない |
| 3 | 正常系 | WHEN ファイアウォールを再適用したとき、システムは既存のルールの有無にかかわらず同じ結果にならなければならない(冪等) |
| 4 | 境界値 | IF ブロック対象ドメインの名前解決に失敗したならば、システムはその1件だけをスキップして残りの適用を続けなければならない(当該ドメインは塞がれないまま残る) |
| 5 | 異常系 | IF ファイアウォールの適用に失敗したならば、システムはコンテナの起動を中止してはならず、警告を起動ログへ出力したうえで起動を継続しなければならない |
| 6 | 異常系 | IF 適用直後の到達性スモークテストで想定外の結果(ブロック対象へ到達できた、または Anthropic API へ到達できない)が出たならば、システムは警告行を出力しなければならない(起動は継続する) |

## FR-env-06 ポートフォワード

- 対応要求: RQ-env-01 / AC-02
- 内容: 必要なときだけコンテナ内 Web アプリのポートを公開できること。

受け入れ基準(EARS):

| # | 種別 | 基準 |
|---|---|---|
| 1 | 正常系 | WHEN `claude-dev start` したとき、システムは Web アプリ用のポートマッピングを行ってはならない(ブラウザ確認用の noVNC ポートを除く) |
| 2 | 正常系 | WHEN `claude-dev forward <port> [name]` を実行したとき、システムはホスト側ポートを 8100 番台から動的に割り当て、中継プロキシを立てなければならない |
| 3 | 正常系 | WHEN `claude-dev unforward <port> [name]` を実行したとき、システムは当該フォワードを解除しなければならない |
| 4 | 正常系 | WHEN `claude-dev ports [name]` を実行したとき、システムはアクティブなフォワードと noVNC URL を表示しなければならない |
| 5 | 境界値 | IF 同じポートのフォワードが既に存在するならば、システムは二重に作らず、現在のホストポートを表示して終了コード 0 で終わらなければならない |
| 6 | 境界値 | IF 割り当て範囲(8100〜8999)に空きが無いならば、システムはフォワードの作成に失敗し、非0の終了コードで終わらなければならない |
| 7 | 異常系 | IF 対象コンテナが起動していないならば、システムは日本語のエラーを表示して終了コード 1 で終わらなければならない |
| 8 | 異常系 | IF コンテナ側でそのポートが待ち受けていないならば、中継は作成されるが接続時に接続拒否となる(この状態を成功と報告してはならない) |

## FR-env-07 Docker アクセスの制限

- 対応要求: RQ-env-04 / AC-03
- 内容: コンテナ内から Docker を使えるが、ホストを危険に晒す操作は拒否されること。

受け入れ基準(EARS):

| # | 種別 | 基準 |
|---|---|---|
| 1 | 正常系 | WHILE コンテナが稼働している間、システムはコンテナに Docker 生ソケットをマウントしてはならず、`DOCKER_HOST=tcp://claude-dev-docker-proxy:2375` 経由で使わせなければならない |
| 2 | 正常系 | IF リクエストがホストバインドマウント(`/workspace` 配下を除く)・privileged・ホストのネットワーク/プロセス空間の共有を含むならば、システムはそれを拒否しなければならない |
| 3 | 正常系 | WHERE 呼び出し元の `/workspace` 配下の bind である場合、システムは実ホストパスへ書き換えて許可しなければならない(既定有効。環境変数で切替可能) |
| 4 | 正常系 | WHILE docker-proxy が稼働している間、システムは docker-proxy をホストに公開せず、`claude-dev-net` 内でのみアクセス可能にしなければならない |
| 5 | 正常系 | WHEN 複数プロジェクトのコンテナで同時に `docker compose` を実行したとき、システムは compose プロジェクト名を起動ディレクトリ名で一意化し、生成されるネットワーク名・コンテナ名を衝突させてはならない |
| 6 | 境界値 | IF bind のパスが `..` を含み、正規化するとプロジェクトディレクトリの外を指すならば、システムはそれを拒否しなければならない |
| 7 | 境界値 | IF 呼び出し元コンテナを特定できないならば、システムは `/` 始まりの bind をすべて拒否しなければならない(名前付きボリュームのみ許可) |
| 8 | 異常系 | IF リクエストのボディが解釈できないならば、システムはそれを中継してよい(独自解釈で誤って弾かない。最終判断は Docker Engine が行う) |
| 9 | 異常系 | IF 上流の Docker Engine への中継に失敗したならば、システムは 502 を返しログへ記録しなければならない |
| 10 | 異常系 | IF 起動時に Docker ソケットが存在しないならば、docker-proxy は起動を中止しなければならない(不正な状態で待ち受けない) |

## FR-env-08 VM モード(オプトイン)

- 対応要求: RQ-env-05
- 内容: bind/compose/privileged が要る重い Docker 案件を、Claude コンテナを特権化せずに扱えること。

受け入れ基準(EARS):

| # | 種別 | 基準 |
|---|---|---|
| 1 | 正常系 | WHERE `claude-dev start --vm` が指定された場合、システムはゲスト VM を起動し、その中でネイティブ Docker を利用可能にしなければならない |
| 2 | 正常系 | WHERE VM モードで起動した場合、システムは VM モードでも `/workspace` を同一パスで共有(ライブ反映)し、Claude コンテナを privileged 化してはならない |
| 3 | 正常系 | WHILE VM モードでない間、システムは既定の軽量構成(DooD + docker-proxy)で動作しなければならない |
| 4 | 正常系 | WHILE VM モードで動作している間、システムはゲストの資源逼迫を検知して利用者へ提示しなければならない |
| 5 | 境界値 | IF `--vm` が指定されたが `/dev/kvm` が利用できないならば、システムは起動を中止し終了コード 1 で終わらなければならない |
| 6 | 境界値 | WHEN VM を停止するとき、システムはゲストの正常終了を優先し、それが失敗または利用不能な場合にだけ強制終了へフォールバックしなければならない |
| 7 | 異常系 | IF ゲスト VM の起動に失敗したならば、システムは失敗を明示したうえで既定の DooD 経路を維持しなければならない(VM は使えないが Docker は使える) |
| 8 | 異常系 | IF 再構築が指示されたならば、システムは取得済みのベースイメージを保持しなければならない(完全な作り直しは利用者の明示指定に限る) |

## FR-env-09 イメージ配布(GHCR)

- 対応要求: RQ-dist-01
- 内容: ビルドせずに同一構成のイメージを取得できること。

受け入れ基準(EARS):

| # | 種別 | 基準 |
|---|---|---|
| 1 | 正常系 | WHEN 配布ワークフローが起動したとき(日次スケジュールまたは手動実行)、システムは GitHub Actions によりイメージを GHCR へマルチアーキ(amd64/arm64)で push しなければならない |
| 2 | 正常系 | WHEN 日次ビルド(03:30 JST)が実行されたとき、システムはイメージに `YYYYMMDDHHmm`(JST)形式のタイムスタンプタグと `latest` タグを付与して push しなければならない |
| 3 | 正常系 | WHEN 日次ビルドが実行されたとき、システムは同梱する Claude Code のバージョンをその時点の `latest` チャネル公開バージョンに一致させなければならない |
| 4 | 正常系 | WHEN 日次ビルドが実行されたとき、システムは同梱する Codex CLI のバージョンをその時点の npm registry 最新公開バージョンに一致させなければならない |
| 5 | 正常系 | WHEN 利用者が配布イメージを取得したとき、システムはイメージのラベルとして同梱バージョンを参照可能にしなければならない |
| 6 | 正常系 | WHEN `claude-dev pull` を実行したとき、システムは取得したイメージを以降の存在判定で使う名前へ付け替えなければならない |
| 7 | 境界値 | WHERE エージェント CLI の特定バージョンが手動で指定された場合、システムは同梱バージョンをその指定値にしなければならない(不良版を引いた際の切り戻し手段) |
| 8 | 境界値 | IF 同梱するエージェント CLI のバージョンが前回ビルドと同一ならば、システムは当該レイヤーを再ビルドしてはならない(利用者の取得を増分に保つ) |
| 9 | 異常系 | IF イメージの取得に失敗したならば、システムは非0の終了コードで失敗を報告しなければならない(古いイメージを黙って使い続けない) |

## FR-env-10 macOS 対応

- 対応要求: RQ-env-06
- 内容: macOS でも Linux と同じコマンド体系で開発できること。

受け入れ基準(EARS):

| # | 種別 | 基準 |
|---|---|---|
| 1 | 正常系 | WHEN `make install` を実行したとき、システムは OS を判定し、`/usr/local/bin/claude-dev` を Linux では `claude-dev`、macOS では `claude-dev-mac` への symlink にしなければならない |
