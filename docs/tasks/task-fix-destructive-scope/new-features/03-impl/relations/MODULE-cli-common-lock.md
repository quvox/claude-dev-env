# MODULE-cli-common-lock 排他ロックの取得と解放

## 目的

共有ボリュームまたは docker-proxy を触る6コマンド(`start` / `stop` / `logout` / `reset` /
`login` / `login-codex`)の相互の競合を防ぐ(FR-env-01 受入基準 16・17・18)。
キーの体系(プロジェクト単位と共有資源単位の2段)は契約 `CTR-cli-container` の「排他(ロックキー)」が正。

## 処理の流れ

`acquire_lock <key> <操作名>`:

1. **キーを検証する**: `<key>` が `[A-Za-z0-9._-]` 以外の文字を含むなら、受理できない文字を含む旨を
   stderr へ出して非0で返す(キーはパス要素になるため。契約の「ロックキーとして使える文字」)。
2. ロックの置き場所 `${HOME}/.claude-dev/locks` を `mkdir -p` し、`chmod 700` する
   (失敗したら非0で返す)。
3. **`trap` を先に仕掛ける**(まだロックを持っていなくてもよい)。**取得したキーを配列に積み、
   `trap` は配列のすべてを `release_lock` に通す**(1プロセスが最大2つのキーを持つため)。
   `EXIT` / `INT` / `TERM` の3つ。`release_lock` は所有者確認つきで冪等なので、
   取得前に発火しても無害である。取得(手順4)より前に仕掛けるのは、取得の直後に中断しても
   後始末が走るようにするためである。
4. **`ln -s "$$ <操作名>" <ロックファイル>` を1回試す。**
   **ロックファイルのパスは種別で名前空間を分ける**: プロジェクト単位は
   `${HOME}/.claude-dev/locks/proj-<key>.lock`、共有資源単位は
   `${HOME}/.claude-dev/locks/shared.lock`(判断13)。
   成功したら手順6へ(この時点で取得完了)。**
   **`ln -s` は同名のパスが既にあると失敗する**ため、これが原子的な取得の実体である。
   **保持者の情報(PID と操作名)はシンボリックリンクの「向き先」そのものに入るので、
   ロックの生成と所有者の記録が1回の原子的な操作で同時に成立する**
   (**別ファイルに書く方式と違い、「ロックはあるが所有者が未記録」という中間状態が存在しない**)。
   向き先は実在するパスである必要がない — ここでは文字列の格納庫として使う。
5. 失敗した場合、`readlink "<key>.lock"` で保持者を読む(`<PID> <操作名>` の形式)。
   - **`kill -0 <PID>` が成功する**: 取得失敗として扱う。保持している操作名と
     PID、および「その操作が終わってから再実行する」旨を stderr へ出し、非0で返す(**待たない**)。
   - **PID が存在しない**(残骸): **回収は「原子的な引き取り + 引き取った中身の検証」で行う。**
     `mv "<ロックファイル>" "<ロックファイル>.stale.$$"` を試す。
     - **`mv` が失敗したプロセス**は、残骸が既に他プロセスに引き取られた(または解放された)
       ということなので、**取得失敗として扱い**、非0で返す(**ロックファイルを直接 `rm -f`
       してはならない**。引き取った側が張り直した新しいロックを消してしまい、双方が臨界区間に入る)。
     - **`mv` が成功したプロセスは、引き取った中身を必ず検証する**(`readlink` で
       `<ロックファイル>.stale.$$` を読む)。**`mv` が原子的なのは「そのパスの `rename` に
       成功するのは1プロセスだけ」という点であって、引き取った中身が観測した残骸と同じで
       あることは保証しない**。同じ残骸を見つけた別プロセスが先に引き取りを完走していると、
       その後に張られた**生きているロックを奪える**(判断6)。
       - **中身が手順5 で観測した保持者と違い、かつその PID が生きている**: 生きているロックを
         奪ってしまったので、**`ln -s` で元に戻してから取得失敗として扱う**。戻せなかった場合
         (その一瞬に第三のプロセスが取得した場合)は、その事実と確認先のパスを stderr へ出す。
       - **中身が観測した保持者と同じ、またはその PID も存在しない**: 正当な引き取りである。
         「<操作名>(PID <PID>)のロックが残っていたため引き継ぎます」を stderr へ出し、
         `.stale.$$` を `rm -f` してから手順4 を**もう一度だけ**試す。2 回目も失敗したら
         取得失敗として扱い、非0で返す。
   - **`readlink` が失敗する**(リンクが消えていた = 直前に別プロセスが解放した): 手順4 を
     **もう一度だけ**試す。2 回目も失敗したら取得失敗として扱い、非0で返す。
     **時間による判定は行わない**(手順4 が所有者ごと原子的に作るため、「所有者が未記録の
     ロック」という状態は原理的に存在せず、待って読み直す必要が無い)。
6. **取得したロックファイルのパスを手順3 の配列に積む。**

`release_lock <key>`:

1. キーと種別からロックファイルのパスを組み立て、`readlink` した PID を読み、
   **自分(`$$`)と一致しないなら何もしない**(リンクが無い場合も何もしない。冪等)。
2. 一致したらロックファイルを `rm -f` し、**そのパスを手順3 の配列から外す**。
   外さないと、明示解放したあとに別の操作が同じキーを取り直した場合、こちらのプロセスの終了時に
   `trap` がそれを消してしまう。手順1 の所有者確認はその二重の防護でもある。

**`INT` / `TERM` を受けたときのロックの扱い**: `trap` が `release_lock` を呼ぶので、**中断でロックは
残らない**。呼び出し元(`logout` / `reset`)が「進行中の1件を終えてから中断し、終了コード 130 で
終わる」(契約の「エラーケース」)ため、`trap` が走るのはその報告の後である。

**両方のキーを取る操作は「プロジェクト単位 → 共有資源単位」の順で取る**(契約が定める固定順序)。
解放は取得と逆順である必要はない(`rm -f` は互いに独立)。

## 呼び出され方

- 契機: `start` / `stop` / `logout` / `reset` / `login` / `login-codex` の各分岐が、
  共有資源への削除も作成も行う前に呼ぶ。
- 前提条件: `${HOME}` が書き込み可能であること。
- 引数の型・制約: `<key>` はコンテナ名(`MODULE-cli-common-container-name` の戻り値、または
  `stop` の引数 `NAME`)または固定文字列 `shared`。**`[A-Za-z0-9._-]` 以外を含むキーは受理しない**。
  `<操作名>` は `start` / `stop` / `logout` / `reset` / `login` / `login-codex` のいずれか。
  受理する値の正は契約 `CTR-cli-container` の「排他(ロックキー)」と「ロックキーとして使える文字」。
- 認可: CLI を実行できるホストユーザ。ロックはそのユーザのホームディレクトリ配下にあるため、
  **別ユーザが同じ Docker デーモンを操作する場合は保護されない**(契約が範囲外と明記している)。

## 連携先と連携内容

連携先なし(ファイルシステム操作だけで完結し、他の機能を呼ばない)。

## 戻り値・副作用

書き込む資源: ホストのファイルシステム上の `${HOME}/.claude-dev/locks/<key>.lock`
(**シンボリックリンク**。向き先の文字列が `<PID> <操作名>` を兼ねる)と、残骸を引き取る間だけ
存在する `<key>.lock.stale.<PID>`。Docker 資源は触らない。
戻り値の形(成否と表示)は契約 `CTR-cli-container` の「エラーケース」が定める。

## 異常系

| 条件 | 実装の振る舞い | 終了ステータス |
|---|---|---|
| `<key>` が `[A-Za-z0-9._-]` 以外を含む、または空 | 受理できない文字を含む旨と受理する文字集合を stderr に出し、**ロックの置き場所も作らない** | 1 |
| `${HOME}/.claude-dev/locks` を作れない(`mkdir -p` が失敗) | 置き場所を作れない旨を stderr に出す | 1 |
| `chmod 700` が失敗 | **無視して続行する**(`|| true`)。既存ディレクトリの権限が想定と違っても排他自体は成立する | — |
| 同じキーを**生きているプロセス**が保持している | 保持者の操作名と PID、再実行の方法を stderr に出す。**待たない** | 1 |
| 同じキーが**存在しないプロセス**に保持されている(残骸) | `mv` で原子的に引き取り、引き継いだ旨を stderr に出してから `ln -s` を1回だけ再試行する | 成功なら 0 |
| 残骸の `mv` に失敗した(他プロセスが先に引き取った) | 取得失敗として扱う。**`<key>.lock` を直接 `rm -f` しない** | 1 |
| `readlink` が失敗した(直前に別プロセスが解放してリンクが消えた) | `ln -s` を1回だけ再試行する。2回目も失敗したら取得失敗 | 成功なら 0 / 失敗なら 1 |
| `release_lock` の対象リンクが存在しない、または向き先の PID が自分と一致しない | **何もしない**(冪等)。他人のロックを消さない | 0 |
| `EXIT` / `INT` / `TERM` を受けた | `trap` が保持中の全キーを `release_lock` に通す。`INT` / `TERM` は終了コード 130 で終わる(呼び出し元が独自の `trap` を張った場合はそちらが優先する) | 130 |
| `SIGKILL` で落ちた | `trap` が走らないためロックが残る。次にそのキーを取ろうとしたプロセスが残骸として引き継ぐ | — |

## 実装上の判断

| # | 判断内容 | 根拠(委任ID) |
|---|---|---|
| 1 | ロックの手段を **`ln -s` の原子性**にする。`flock` を使わないのは **macOS に `flock(1)` が無い**ためで、片方だけ `flock` にすると同じサブコマンドの成否と出力が OS で変わる。`ln -s` は両 OS で同一に書ける。**`mkdir` ではなく `ln -s` を選んだ理由は判断8** | D0-env-09(制約「Linux 版と macOS 版で同じ成否・同じ出力にする」= `D0-scope-03`) |
| 2 | 置き場所を `${HOME}/.claude-dev/locks/` にする。既存の `${DEV_DIR}/agents`(`claude-dev:67` と `claude-dev-mac:80` の `DEV_DIR="${HOME}/.claude-dev"`)と同じ親ディレクトリで、**両 OS の実装が既に同じ変数で持っている**。`/tmp` の自動掃除にも依存しない。権限も既存に倣い `chmod 700`(`claude-dev:174` と同じ扱い)にする | D0-env-09 |
| 3 | 置き場所を**環境変数で上書きできるようにしない**。上書きできると、片方の操作だけ別の場所を見て排他が成立しなくなる(排他は「全員が同じ場所を見る」ことでしか成立しない)。`${HOME}` が書けない環境では取得に失敗して非0で返す | D0-env-09 |
| 4 | **待ち時間を設けない**(1回の取得と、残骸だった場合の1回の再取得だけ)。再試行のループを入れないのは、`logout` が稼働中コンテナを消してから認証を消し、**`login` / `login-codex` は利用者がブラウザで認証を終えるまで保持する**ため、保持時間の上限を決められないからである。上限を決めない待ちは「固まる」に等しい | D0-env-09(制約「ロック待ちで固まらない」) |
| 5 | 残骸の判定を **リンクの向き先に入れた PID の `kill -0`** で行う。リンクの更新時刻(古さ)で判定しないのは、閾値を決める根拠が無く、長時間かかる `reset` を残骸と誤認しうるため | D0-env-09(制約「ロック残骸で永久に詰まらないこと」) |
| 6 | **残骸の回収を `mv` による引き取り + 引き取った中身の検証で行う**(手順5)。`rm -f` で直接消すと、**同じ残骸を同時に見つけた2プロセスが両方とも臨界区間に入る**経路がある: P1 が `rm -f` → `ln -s` 成功の直後に、P2 が(自分が読んだ古い保持者を根拠に)`rm -f` して **P1 の新しいロックを消し**、`ln -s` に成功してしまう。`mv`(`rename`)なら引き取り権が一意に決まる…**が、それだけでは足りない**。**`mv` が保証するのは「そのパスの `rename` に成功するのは1プロセスだけ」であって、引き取った中身が観測した残骸と同じであることではない**: P1 が引き取りを完走して新しいロックを張ったあとに P2 の `mv` が走ると、P2 は**生きている P1 のロックを奪って**しまい、同じ二重取得が起きる(**実装後の独立レンズが検出し、再現を実測した**)。そこで **`mv` の後に `readlink` で中身を検証し、観測した保持者と違ってその PID が生きているなら `ln -s` で元に戻して取得失敗にする** | D0-env-09(委任範囲「保持プロセスが消えた後のロック残骸をどう扱うか」)/ `/doc-check` と `/implement` の独立レンズが検出 |
| 7 | **`trap` を取得より前に仕掛ける**(手順3)。取得の直後に中断しても後始末が走るようにするため。`release_lock` は所有者確認つきで冪等なので、ロックを持つ前に発火しても無害である | D0-env-09 |
| 8 | **ロックの実体を「ディレクトリ + `owner` ファイル」ではなく「向き先に `<PID> <操作名>` を入れたシンボリックリンク」にする**(手順4)。`mkdir` 方式には **`mkdir` 成功から `owner` 書き込みまでの間、所有者が未記録のロックが存在する**という窓があり、この窓を「残骸」と誤認されると**排他そのものが成立しなくなる**一方、誤認を避けるために待つと `SIGKILL` で `trap` が走らなかった場合の**回収不能なロック**と区別できない。**時間で切り分ける方式(一定時間待って読み直す)は、その時間を超えて停止したプロセスがあると排他が破れる**ため、保証にならない。`ln -s` は**リンクの生成と保持者の記録が1回の原子的操作**なので、この中間状態が**原理的に存在しなくなり**、時間に依存する判定を一切持たずに「排他の成立」と「残骸で永久に詰まらない」を両立できる | D0-env-09(委任範囲「実装手段」。制約「ロック残骸で永久に詰まらないこと」と排他の成立の両立)/ `/doc-check` の独立レンズが検出 |
| 9 | 解放を `trap ... EXIT INT TERM` で行う。`set -e` による途中終了と Ctrl-C の双方でロックを残さないため。`KILL` では解放できないが、その場合は手順5 の残骸引き継ぎが回収する。**`trap` は「取得したロックファイルのパスの配列」を渡す**(1プロセスが最大2つのキーを持つため、後から取った方で上書きすると先のキーが解放されない) | D0-env-09 |
| 10 | **`release_lock` は向き先の PID が自分と一致するときだけ削除する**。かつ明示解放したキーは `trap` 用の配列から外す。両方入れる理由: `start` は共有資源単位のキーを**コンテナ作成の確定(手順15 の再試行ループを抜けたところ)**で明示解放し、その後も走り続ける(手順16 の tmux 待ちとアタッチ)。その間に `logout` が同じキーを取得しうるので、`start` の終了時の `trap` が**他人のロックを消す**経路が生まれる。配列から外すのが本筋で、所有者確認は取りこぼしへの二重の防護である | D0-env-09 |
| 11 | **キーの文字集合を `[A-Za-z0-9._-]` に限り、違反したら何も行わず非0で返す**。キーはパス要素になり、残骸の回収でそのパスを操作するため、`/` や `..` を含むキーを通すと意図したディレクトリの外を触りうる。`stop` の引数 `NAME` は利用者が任意の文字列を渡せる唯一の経路である | D0-env-09(`FR-env-01` 受入基準18 が観測可能な振る舞いを定める) |
| 12 | Linux 版・macOS 版の**両方に同じ関数名・同じ引数・同じ表示**で入れる | D0-scope-03 |
| 13 | **ロックファイルのパスを種別で名前空間に分ける**(プロジェクト単位 = `proj-<key>.lock` / 共有資源単位 = `shared.lock`)。**分けないと、プロジェクト名が `shared` のとき(`~/work/shared` で `claude-dev start` したとき)に2つのキーが同じファイルを指し、2段目の取得が「自分が持っているロック」を生きた保持者として読んで必ず失敗する**(`start` がそのディレクトリで永久に起動できなくなる。実装後の独立レンズが検出し、再現を実測した)。**キーの値そのものは契約 `CTR-cli-container` のとおりコンテナ名 / `shared` のままで、表示にもキーを使う**(利用者にはファイル名ではなくキーを示す) | D0-env-09(委任範囲「実装手段と置き場所」) |
| 14 | **`release_lock` は「キーと種別」を受け取り、内部でパスに直してから解放する**。配列には**キーではなくロックファイルのパス**を積む(同じ文字列のキーが種別違いで2つ存在しうるため、キーだけでは一意に指せない) | D0-env-09 |

## 既知の制限

- **ホスト CLI のプロセス間でしか有効でない。** 利用者が `docker rm -f` を直接実行する場合、
  および別のホストから同じ Docker デーモンを操作する場合は保護されない
  (契約 `CTR-cli-container` の「ロックが守れない範囲」)。
- **ロックの置き場所が `${HOME}` 配下なので、別ユーザが同じ Docker デーモンを操作する場合は
  排他が成立しない**(それぞれのホームに別のロックができる)。排他は「全員が同じ場所を見る」
  ことでしか成立しないが、共有の置き場所を持つとその権限管理が新たな問題になるため採らない。
- **`SIGKILL` された場合はロックが残る**(`trap` が走らない)。次の取得時に残骸として
  引き継がれるので永久に詰まることは無いが、**その1回は「引き継ぎます」の警告が出る**。
- **PID の再利用を検出しない。** 保持者の PID が終了したあと、同じ PID が別のプロセスに
  割り当てられていると `kill -0` が成功し、残骸を「生きている」と誤判定して取得に失敗する。
  この場合は待ってから再実行するか、ロックのリンクを手で削除する必要がある
  (発生確率が低く、失敗する側=安全側に倒れるため対処しない)。
- **残骸の引き取りには、原理的に消せない極小の窓が1つ残る**: 引き取りの `mv` で生きている
  ロックを奪ってしまい元に戻すまでの2システムコールの間に、第三のプロセスが空いたパスを
  取得すると、元の保持者と第三のプロセスの2つが同時に臨界区間に入る。**この場合は
  「ロックを元に戻せませんでした」を出して知らせる**(黙って進まない)。成立には
  「残骸がある」「2プロセスが同時に引き取る」「さらに第三のプロセスがその2システムコールの
