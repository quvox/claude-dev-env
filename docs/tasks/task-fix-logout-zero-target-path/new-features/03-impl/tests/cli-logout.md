## テスト設計の判断

| # | 判断 | 理由 | 見直す条件 |
|---|---|---|---|
| 1 | **`logout` と `reset` に共通して効く受入基準(`FR-env-01` 受入基準9 / `FR-env-03` 受入基準14〜18・23)の対応表を、主担当である本ファイルだけが持つ。`reset` 側だけ別の手順で確かめるものは、同じ条項の行を本ファイルの中で2行に分ける**(現に `FR-env-01` 受入基準9 が `logout` 側=手順8-5 と `reset` 側=手順8-12 の2行になっている) | 同じ条項の行を `tests/cli-reset.md` にも置くと、状態(未検証 / 実装済み)が2箇所に分かれて必ずずれる。手順が分かれても**状態を持つ場所は1つに保つ**のが目的なので、分岐はファイルをまたがずに行の分割で表す。`tests/cli-reset.md` が持つのは `reset` にしか無い条項(`FR-env-01` 受入基準25)だけである | **`reset` にしか無い条項が増えたとき**(そのときは `tests/cli-reset.md` にその条項の行を立てる。共通条項の手順が分かれるだけなら本ファイルの行を増やす) |
| 2 | **本モジュールの自動テストを書かず、すべて実機確認(E2E-01 手順8)に寄せる** | シェル実装に自動テストランナーを設けないという `DSN-test-01`(`SR-32`)の方針による。確認プロンプト・非 TTY・削除失敗・中断シグナルはいずれも実端末と実 Docker 資源を要し、模擬すると確認したい振る舞いから離れる | 02 の `DSN-test-01` が変わり、シェルにテストランナーを置くと決めたとき |
| 3 | **`FR-env-03-24`(`logout` 後にセッション由来の資源が `stop` で回収できないこと)を実機確認 E2E-01 手順8-16 に載せる** | 確認には「所有者ラベルを持つ資源を作ったうえで `logout` し、その後 `stop` を実行する」という実 Docker 資源の並びが要る。**確認するのは「消えないこと」であり、削除の失敗ではない**(`FR-env-03` 受入基準18 の対象外)。手順を末尾に置くのは、`logout` が Claude コンテナを消すと以降の部分手順の前提が壊れるためである | `reset` 以外の回収手段を設けたとき(そのときは回収経路の確認が要る) |
| 4 | **削除対象0件の経路の確認を、独立した手順ではなく既存の手順8-8 の (d) に相乗りさせる** | (d) は既に「認証コピーが1つも無い状態で再度 `logout` を実行する」= まさに0件の経路に入る手順である。独立させると `login` → `start` → `logout` の前提を作り直すことになり、同じ状態を2度作る。ラベル無しコンテナは手順8-5 と同じ立て方で用意できるので、書き戻しの警告の確認もこの位置で成立する | 手順8-8 が認証コピーの確認から離れ、0件の状態を作らなくなったとき |
| 5 | **共有ボリュームの状態を確かめられない場合の確認は、独立した部分手順(手順8-18)として末尾に置く** | この確認だけは **Docker 側を意図的に壊した状態**(一時コンテナが起動できない)を要し、その状態では他のどの部分手順も実行できない。途中に置くと以降の手順の前提を壊すので、後片付けの直前に置く。**壊し方は `claude-dev-auth` を別プロセスが排他的に使う / イメージを一時的に退避する のいずれでもよい**(確かめたいのは「印が出ないときにこの経路へ入らないこと」であって壊し方ではない) | 一時コンテナを使わずに共有ボリュームの中身を読む実装へ変わったとき(そのときは壊す対象が変わる) |
