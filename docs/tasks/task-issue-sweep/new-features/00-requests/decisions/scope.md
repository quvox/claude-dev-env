## D0-scope-07 03-impl を「再実装可能な深度」まで掘り下げるときの書き方

- 区分: 委任
- 決めた日: 2026-08-03
- 委任範囲: `03-impl/relations/` と `contracts/` を「ドキュメントだけから再実装・再試験できる」
  深度へ掘り下げるときの、(1) どこまで書けば十分かの停止条件、(2) 実装が振る舞いを定めていない
  観点(排他・再試行・タイムアウトなど)の書き方、(3) 掘り下げ中に見つけた実装の欠陥をどこへ記録するか。
- 制約(ガードレール):
  - **コードから一意に読み取れる事実だけを書く。** 読み取れない=「決めなければならない」ものは
    書かず、`docs/issues/` に起票する。**推測を仕様として書いてはならない。**
  - 実装が排他・再試行・タイムアウトを持たない場合は、**「持たない」という事実と、そのときの
    観測結果**を書く。あるべき姿を書いてはならない(SSOT は現在の姿だけを持つ — CLAUDE.md 原則1)。
  - 観測可能な振る舞い・契約・モジュール分割を変えないこと。これらを変える判断は委任範囲外。
  - **排他の欠如・入力検証の欠落・秘密値のログ出力**を見つけたら、下の**起票の閾値**に従って
    `docs/issues/` へ起票する(severity は影響範囲で決めてよい)。その場で**コードを直してはならない**。
  - **起票の閾値**(2026-08-03 追記。この閾値の外にあるものは 03 の「既知の制限」に記述だけ残す):
    次の**両方**を満たすものを起票する。
    (a) 観測可能な被害がある — データの破壊 / 秘密の漏洩 / **利用者が失敗に気づけない** /
    01・02 の記述との不一致 のいずれかに当たる。
    (b) その被害を説明する issue が**まだ無い**。
    逆に、**被害が既知の issue で説明できるもの**、**利用者がその場で失敗に気づけるもの**、
    **00/02 が「そう決めた」と明示しているもの**は、03 の「既知の制限」に事実を書くだけでよい。
    **判定の根拠(どちらに当たるか)を必ず書く。**
  - **観測点の定義**(上の判定を一意にするため):
    「**その場で気づける**」= 失敗が標準出力・標準エラーに現れる / 終了コードが非0になる /
    利用者が通常見る画面(ダッシュボード・`claude-dev ports` / `list` の出力)に現れる、
    のいずれかを満たす。
    「**利用者が失敗に気づけない**」= 上のいずれにも現れず、**成功時と同じ表示・同じ終了コード**に
    なる。「既知の issue で説明できる」= その issue の「事象」がこの被害を含む(ID を書く)。
  - 02 の `logging.md` が定める必須フィールド・マスキング方針に実装が従っていない箇所を見つけたら、
    03 には**実装の現状**を書き、差は `docs/issues/` へ起票する。
- 報告義務: 掘り下げた各ドキュメントの「実装上の判断」表に `D0-scope-07` と共に記録する。
  **起票の閾値で「留める」と判定したものは、03 の「既知の制限」に理由も書く**(黙って落とさない)。
  起票した issue はタスクの histories に一覧する。
- 関連: `D0-scope-01` / `D0-scope-06`(起点のもう1つは issue 008。**同 issue は本決定の反映と同時に
  解消・削除**するため、経緯は `docs/histories/` を参照)/
  **本決定を起点に掘り下げた残件は `docs/pendings.md` の残務が持つ**(2026-08-11 に、
  どの `AC-nn` も塞いでいないため原則8のゲート行4に当たるものとして残務へ移した。
  経緯は `docs/histories/` を参照)
