## AC-02 Web アプリをクライアントのブラウザで確認

- 対応要求: RQ-env-01 / RQ-env-02
- 前提: コンテナ内で Web アプリが起動し、**コンテナの外から接続を受け付ける形**で待ち受けている。
- 操作:
  1. サーバ上で `claude-dev forward 5173` を実行する。
  2. 表示された SSH トンネルのコマンドをクライアント PC で実行し、案内された URL を開く。
- 期待される結果: クライアントのブラウザにコンテナ内 Web アプリが表示される。`claude-dev ports` で
  今開いているフォワードを確認できる。**`claude-dev start` しただけの時点では、利用者の
  Web アプリ用のポートは1つも公開ポートになっていない**(用語集「公開ポート」)。
  **ブラウザ確認ありの構成が開く noVNC の 6080 番台は、この基準の対象外である**
  (`D0-env-01` で動的に割り当てると決めた補助 UI のポートであり、`D0-env-02` が
  「`start` の時点では Web アプリ用のポートマッピングを行わない(**ブラウザ確認ありの
  noVNC ポートを除く**)」と例外を明記している)。
- こうなったら不合格: `start` しただけで、利用者の Web アプリ用のポートが意図せず公開ポートになる。
  noVNC 以外のポートが `start` の時点でホストへ公開される。

## AC-03 危険な Docker 操作が拒否される

- 対応要求: RQ-env-04
- 前提: コンテナ内から Docker を使う既定の構成で起動している。
- 操作: コンテナ内で、ホストのルートディレクトリを丸ごと持ち込むような `docker run` を試みる。
- 期待される結果: プロジェクト作業領域の外をホストから持ち込む操作・特権コンテナ・ホストの
  ネットワークやプロセス空間の共有は**拒否**される。作業領域配下の持ち込みと、
  持ち込みを含まない `docker run` は許可される。
- **この保証の限定**: 拒否できるのは、要求の中身を検査できた場合に限る。**検査できなかった要求は
  止められず、その要求が通るか止まるかは実行してみるまで分からない**(独自解釈で正常な操作を
  誤って止めないための割り切り)。**この割り切りは `D0-sec-05`(Docker API 検査の厳密さ)の
  委任範囲——「解釈できない入力を通すか止めるか」——の中で下した判断であり、独立した決定事項では
  ない。** 残存リスクは `docs/issues/005` が追跡する。
- こうなったら不合格: ルートディレクトリの持ち込みや特権コンテナが**検査できる形で**通ってしまう。
