## D0-env-02 ポートは起動時に公開せず、必要なときだけ開く

- 区分: 決定
- 決めた日: 2026-07-30
- 内容: `claude-dev start` の時点では Web アプリ用のポートマッピングを行わない(ブラウザ確認ありの
  noVNC ポートを除く)。`claude-dev forward` で中継のプロキシコンテナを立て、ホスト側ポートを
  8100 番台から動的に割り当てる。**クライアントからそのポートへ到達する手順は 02 が定める。**
- 理由: 不要なホスト公開を避け、必要なときだけ最小限を公開する。
- 却下した案: 起動時に固定ポートを公開する — 意図しない公開が常時発生し、プロジェクト間でも衝突する。
- 関連: RQ-env-01 / FR-env-06

## D0-env-04 macOS 対応はホスト CLI の差し替えで行う

- 区分: 決定
- 決めた日: 2026-07-30
- 内容: ホスト CLI を `claude-dev-mac` に差し替える(**同じサブコマンド名から OS 向けの実装が呼ばれる
  ようにする。結び付けの手段は 02/03 が定める**)。SSH agent は TCP ブリッジで転送し、ポートは直結(SSH トンネル不要)、VM/KVM は非対応、
  Apple Silicon では arm64 ネイティブで動かす。
- 理由: OS 依存をホスト CLI に閉じ、コンテナ内資産(イメージ・entrypoint・firewall・docker-proxy)を
  OS 非依存に保つ。
- 却下した案: 1つの CLI に OS 分岐を書く — 分岐が全体に散り、片方の変更が他方を壊す。
  コンテナ側で OS 差分を吸収する — コンテナ資産が OS 依存になる。
- 関連: RQ-env-06 / FR-env-10

## D0-env-05 複数プロジェクト同時実行時の資源分離とライフサイクル

- 区分: 決定
- 決めた日: 2026-07-31(**2026-08-04 に項1・項2 を `D0-env-08` の決定に合わせて改めた**。
  **2026-08-07 に項2 の対象を compose 資源からセッション由来の資源へ広げた**)
- 内容:
  1. **分離**: 各プロジェクトのコンテナ内 `docker compose` が作るネットワーク名・コンテナ名を
     プロジェクト間で衝突させない。**そのために compose のプロジェクト名をプロジェクト間で一意にする。
     一意化の方法は `D0-env-08` 項7 を受けて 02 の契約 `CTR-cli-container` が定める**
     (2026-08-04 に改めた。**起動ディレクトリ名だけでは正規化後に衝突するため一意にならない** —
     それが当時の取り違えの根であった)。
     Claude コンテナと docker-proxy をつなぐ共有ネットワークは共有のまま分離しない。
  2. **ライフサイクル**: **セッションのコンテナ内から作られた資源を親の Claude コンテナに束ね、
     `claude-dev stop` 時に削除する**。対象は次のとおりで、**compose を経由したかどうかを問わない**
     (2026-08-07 に改めた。従来は compose コンテナと compose 既定ネットワークだけを対象にしており、
     `docker run` で作られたコンテナが孤児として残っていた)。
     - **削除する**: そのセッションのコンテナ内から作られた**コンテナ**(`docker run` /
       `docker create` / `docker compose up` のいずれの経路でも)と**ネットワーク**
       (compose 既定ネットワークを含む)。
     - **削除しない**: **名前付きボリューム**(利用者のデータであり、削除は破壊的である)と
       **イメージ**。
     - **削除の意味は「削除」であって「停止」ではない**(停止だけにすると孤児コンテナが名前を
       占有し続け、次の `start` で同名衝突を起こす)。**削除に使う操作は 02/03 が定める。**
     - **削除対象の特定方法は `D0-env-08` 項1・項7・項8 と `CTR-cli-container` が定める**。
     - **`claude-dev reset` にも同じ片付けを掛ける**(「初期状態へ戻す」という説明と食い違わせない)。
       **`claude-dev logout` には掛けない**(認証を消す操作であり、**利用者が自分で作った資源までは
       追わない**)。**★2026-08-07 改め(`docs/issues/090` の人間の裁定 A)**: 従来この除外の理由は
       「実行中のコンテナ群まで消すのは利用者の期待を超える」と書いていたが、**この理由は事実と違う** —
       `logout` は管理ラベルを持つ Claude コンテナを実際に削除する(`FR-env-03` 受入基準5)。
       **`logout` の後に残る帰結を、決定の側で引き受ける**: 所有者である Claude コンテナが
       消えるため、そのセッション由来の資源は `claude-dev stop` では片付けられなくなる
       (`FR-env-01` 受入基準23)。
       **この帰結を承知のうえで `logout` には掛けない**(認証を消すつもりの操作の削除範囲を
       利用者が作った資源にまで広げると、`logout` の意味そのものが変わるため)。
       **利用者から見える帰結は `FR-env-03` の受入基準が定める。**
     - **共有ネットワークと docker-proxy を停止してよい条件は `D0-env-08` 項2 が定める**
       (2026-08-04 に改めた。**この項が課すのは「遊休でなければ停止しない」であり、
       「決して停止しない」ではない**)。
     - VM モードは Docker がゲスト内で完結し、ホストの Docker にコンテナが現れないため対象外。
- 理由: 全プロジェクトが `/workspace` にマウントされるため compose の既定プロジェクト名が
  `workspace` に衝突する。分離は compose 層で足りる。
  ライフサイクルについては、**利用者から見た区別は「このセッションの中から作ったかどうか」だけで、
  compose を経由したかどうかは実装の都合である**。片付けの範囲を
  **「セッションが作ったものは全部」**という1文で言い切れる形にすると、資源の種類ごとに
  「これは消す・これは残す」を覚える必要がなくなる(2026-08-07 の人間の判断。
  気づきは `docs/feedbacks/024-cleanup-scope-is-defined-by-ownership-not-by-harm.md`)。
  例外は名前付きボリューム1つだけで、それは**別の決定(本項の「削除しない」)が保持を命じている**
  ためであり、害の大小で切ったものではない。
  共有リソースは他プロジェクトが使用中でありうるため、**使用中かどうかを判定してから**扱う。
- 却下した案: 共有ネットワークもプロジェクトごとに分ける — 単一の共有 docker-proxy 前提と両立しない。
  停止時に名前付きボリュームも消す — 破壊的で、利用者のデータを失う。
  **共有資源を一切停止しない** — 使い終わった docker-proxy が残り続け、`FR-env-01` 受入基準6 と
  両立しない(2026-08-04 に却下した)。
  **compose 経由の資源だけを片付ける**(2026-08-07 に却下した) — `docker run` で作られたコンテナが
  ホストに残り続け、利用者は残ったことに気づけない。片付けの範囲を資源の種類ごとに
  説明することにもなる。
  **停止に留めて削除しない**(同日に却下した) — 孤児コンテナが名前を占有し、
  次の `start` で同名衝突を起こす。既に対象に入っている compose 資源が削除であり、
  同じ集合の中で停止と削除が混ざると `stop` の結果を説明できない。
  **`logout` にも同じ片付けを掛ける**(同日に却下した。**2026-08-07 に理由を実態へ改めた**) —
  認証を消すつもりの操作の削除範囲が、利用者が自分で作った資源にまで広がる。
  `logout` は「ログイン状態を消す」操作であって「作ったものを片付ける」操作ではなく、
  範囲を広げるとその区別が失われる(**旧い理由「実行中のコンテナ群が消えるのは利用者の期待を
  超える」は偽である** — `logout` は管理ラベルを持つ Claude コンテナを既に削除している)。
- 関連: FR-env-01 / FR-env-03 / FR-env-07 /
  **`D0-env-08` 項1・項2・項7・項8(本決定の項1・項2 の具体を定める)** /
  `CTR-cli-container` / `docs/feedbacks/024-cleanup-scope-is-defined-by-ownership-not-by-harm.md`
  (**項2 の理由が事実と違っていた件は本改めと同時に解消・削除するため、経緯は `docs/histories/` が持つ**)

## D0-env-06 コンテナ内動作の判定マーカーをイメージに焼き込む

- 区分: 決定
- 決めた日: 2026-07-31
- 内容: 全 Claude コンテナに環境変数 `container=docker` を持たせ、コンテナ内で動作するプロセスが
  「自分がコンテナ内か」を判定できるようにする。名前と値は systemd/podman の標準慣習
  (`container=<runtime>`)に合わせる。**起動時の付与ではなくイメージ側で付ける**(起動経路に
  よらず常に付いていることを条件とするため)。**変数の名前と値の形式は 02 の契約
  `CTR-cli-container` が定める**。
- 理由: 内部プロセス(entrypoint・各スクリプト・オーケストレーター)が環境依存の分岐を
  **起動経路によらず同じ判定で**行える恒久マーカーが要る。起動時の `-e` 付与は
  `docker run` 以外の経路(一時コンテナ・`docker exec` で作られたプロセス)で欠落しうるため、
  イメージ側で常時保証する。
- 却下した案: 起動時に `-e container=docker` を付ける — `docker run` 以外の経路(一時コンテナ等)で
  漏れる。独自の変数名を使う — 外部ツールとの互換を失う。
- 関連: FR-env-01

## D0-env-08 破壊的操作の対象は「自分が作った資源」に限る

- 区分: 決定
- 決めた日: 2026-08-04(**2026-08-07 に項1・項3・項7 を改め、項8 を新設した**。
  **2026-08-07 に項8 へ「`reset` が所有者を問わない理由」を足した**)
- 用語(本決定で使う定義):
  - **破壊的操作** = 利用者の作業内容またはログイン状態を失わせうる削除を行うサブコマンド。
    現時点では `claude-dev stop` / `claude-dev logout` / `claude-dev reset` の3つを指す。
  - **管理ラベル** = 本システムが Docker 資源に付けるラベル。「本システムが作った(または
    本システムを通して作られた)」ことと「どのプロジェクトのものか」を表す。名前と値の形式は
    02 の契約 `CTR-cli-container` が定める(`D0-env-10` で AI に委任する)。
  - **セッション由来の資源** = ある Claude コンテナの中から docker-proxy を経由して作られた
    Docker 資源(コンテナとネットワーク)。用語集の定義が正である。
- 内容:
  1. **対象の限定**: 破壊的操作が削除対象を**集合として列挙して消す**とき、
     **名前から所有権が読み取れない資源(= Claude コンテナ。名前が利用者の起動ディレクトリ名から
     決まるため任意のコンテナと区別できない)は、管理ラベルを持つものだけ**を対象にする。
     **イメージからの逆引きを対象決定の手段にしてはならない**(イメージを作り直すと、
     それ以前に起動したコンテナを数え落とすため。手段の具体は 02 の契約が定める)。
     管理ラベルを持たない Claude コンテナ(本システム以外が作ったもの、および本決定より前に
     起動した既存コンテナ)は削除せず、**その存在と名前を表示して残す**。
     **本システムが決めた固定名または固定接頭辞を持つ資源**(docker-proxy / `fwd-*` 中継コンテナ /
     共有ボリューム / ネットワーク / イメージ)は**名前で所有権が読み取れるので、ラベルではなく
     名前で識別する**。
     **セッション由来の資源は名前も固定接頭辞も持たない**(利用者が任意の名前を付ける)ので、
     **項8 が定める所有者ラベルで識別する**。
     どの資源をどちらで識別するかの正は 02 の契約 `CTR-cli-container` である
     (`D0-env-10` の委任で「付与する資源の種類」を決めた結果)。
     ただし利用者が**名前で1つを指した削除**(`claude-dev stop <name>`)は、管理ラベルの有無に
     かかわらずその1件を削除する(利用者が明示的に指したものである。ラベルが無い場合はその旨を表示する)。
  2. **共有資源を止めてよい条件**: 全プロジェクトで共有する資源(**docker-proxy と共有ネットワーク**。
     どちらも本システムが名前を決めている資源で、名前は 02 の契約が定める)を停止・削除してよいのは、**他に稼働中の Claude コンテナが1つも無いときだけ**
     である。この判定は、判定対象が管理ラベルを持つかどうか、およびどのイメージから作られたかに
     **依存してはならない**(依存させると、イメージを更新した後に起動していたコンテナを数え落とす)。
     判定の手段は 02 の契約が定める。
     **この条件は `stop` / `logout` / `reset` の3つすべてに掛かる。例外は無い**
     (`reset` も同じである。ラベルを持たないコンテナを残す以上、その足元の共有資源を消すと
     残したコンテナの中から Docker が使えなくなる。**その代償として `reset` は完全な初期状態へ
     戻らないことがあり、その旨を表示する**)。
  3. **確認**: 他プロジェクトの稼働中セッションを削除しうる破壊的操作は、削除対象の名前を列挙して
     確認を取る。**端末を持たない環境(標準入力が TTY でない)では中止する**。中止せずに実行させたい
     場合は、明示同意の引数(`--yes`)を利用者が付ける。
     **対象は `logout` / `reset` の2つに限る。`claude-dev stop` は確認を求めない**
     (2026-08-04 に人間が裁定し、2026-08-07 に判定基準の書き方だけを改めた)。
     **2026-08-07 の改め**: 従来この項は対象を「削除対象を集合として列挙する操作」と書いていたが、
     `D0-env-05` 項2 の拡張により **`stop` もセッション由来の資源を集合として列挙して消す**ように
     なったため、その書き方では `stop` が対象に入ってしまう。**裁定の理由は「集合列挙かどうか」
     ではなく「日常操作を重くしないこと」だったので、対象をコマンド名で書く形に改める。**
     `stop` を免除する根拠は変わらない: 利用者が**名前で1件を明示的に指した**削除であり、
     何が消えるかは利用者が既に知っている。**セッション由来の資源についても同じである**
     (自分がそのセッションの中で作ったものである)。ただし**削除した資源の名前は事後に表示する**
     (何が消えたかを利用者が確認できるようにするため。`FR-env-01` の受入基準が定める)。
     これは項1 の「名前で1つを指した削除」の例外と**同じ根拠を、確認についても適用したもの**である
     (項1 はラベルの要否についての例外なので、確認の免除はこの項で別に定める)。
     引数を省略した `claude-dev stop`(カレントディレクトリから名前を導出)も同じ扱いである。
  4. **認証の消え残り**: `logout` は共有ボリュームだけでなく、**カレントディレクトリのプロジェクト
     配下にコピーされた認証**(Claude と codex の両方。対象ファイルは 02/03 が定める)も
     削除する。削除したパスを表示する。**他のディレクトリには触らない。**
     これは **`reset` の実装上の判断として記録されていた「利用者のリポジトリを触らない」**
     (`D0-scope-02` を根拠とするもの)を **`logout` について撤回するもの**である(理由: それが残ると `logout` 後に同じディレクトリで `start` したときに
     認証済みで起動し、「ログアウトした」という利用者の期待を静かに裏切る)。
     `reset` は対象を絞る引数を持たず、どのディレクトリを触るべきか決められないため、
     **`reset` は引き続きプロジェクト配下に触らない**(非対称を承知の上で残す)。
  5. **削除の失敗**: 認証情報を削除する操作(`logout` / `reset`)は、削除に失敗した資源を
     握りつぶさない。**消えなかった資源を1件ずつ列挙し、終了コード 1 で終わる**。
     「削除しました」と表示しながら実際には残っている状態を作ってはならない。
     `stop` の後片付けのうち **`FR-env-01` の受入基準が「続行する」と定めているもの**
     (他から使用中の compose 既定ネットワーク、**およびセッション由来の資源**)は、
     この項の対象外である(意図して続行する)。
  6. **排他**: **共有ボリュームまたは docker-proxy を触るサブコマンドは互いに排他する。**
     対象は `start` / `stop` / `logout` / `reset` / `login` / `login-codex` の6つである
     (`login` / `login-codex` は共有ボリュームに認証を**書く**唯一の経路であり、`logout` と
     重なると「ログインしたのに未ログイン」という利用者が原因に到達しにくい失敗になる)。
     単位は**プロジェクト単位**(同じコンテナ名を対象にするもの)と**共有資源単位**
     (共有ボリュームまたは docker-proxy を触るもの)の2段とする。
     **ロックを待って固まってはならない**: 取得できなければ、誰が保持しているかと再実行の方法を
     表示して終了コード 1 で終わる。実装手段と置き場所は `D0-env-09` で AI に委任する。
  7. **compose 資源の識別**: **compose プロジェクト名そのものをプロジェクト間で一意にする**ことで、
     「自分が作った資源」を名前で識別できる状態にする。一意化の方法は 02 の契約が定める。
     **本決定より前に起動した compose 資源は古い名前を持つため `stop` の片付け対象から外れる**。
     その事実を利用者へ表示し、手動で片付ける方法を案内する。
     **2026-08-07 の改め**: この項は従来「コンテナ内の `docker compose` が作る資源には
     本システムのラベルを付けられない(compose が Claude コンテナの中で作るため、ホスト CLI の
     `--label` が届かない)」を前提にしていた。**この事実認識は誤りである**: 作成要求は
     docker-proxy を必ず通るので、docker-proxy がラベルを付けられる(項8)。
     **一意化そのものは廃止しない**: 項8 のラベルを持たない古い compose 資源を引く唯一の手段が
     一意化名であり、移行期の取りこぼしを減らすために両方を使う。
  8. **セッション由来の資源の識別**(2026-08-07 新設): あるセッションのコンテナ内から
     docker-proxy を経由して作られたコンテナとネットワークには、**docker-proxy が作成要求を
     中継するときに所有者を表す管理ラベルを付ける**。`stop` はそのラベルの値が自分の
     起動ディレクトリと一致するものを、`reset` は所有者を問わず全部を削除対象にする。
     - **`reset` が所有者を問わない理由**(2026-08-07 に追記): `reset` は対象を絞る引数を持たない
       **「ホスト全体を初期状態へ戻す」操作**であり、所有者で絞ると `stop` と同じ意味になる
       (`reset` を実行する利用者は自分のセッションだけでなくホストを初期状態へ戻したい)。
       **項2 の「稼働中セッションの足元を守る」との非対称は承知の上である**: 項2 が守るのは
       他のセッションが**現に使っている共有資源**(docker-proxy と共有ネットワーク)であり、
       所有者ラベルを持つセッション由来の資源はその集合に入らない。
     - **ラベルの名前と値の形式、注入する API 経路は `D0-env-10` で AI に委任する。**
     - **所有者を表す値は「そのセッションの起動ディレクトリの絶対パス」とする**
       (`stop` が持つのは引数のコンテナ名だけで、絶対パスは既に読んでいる管理ラベルから得られる。
       **値をどこから取るかは 02 の契約が定める**)。
     - **共有資源を止めてよいかの判定(項2)にこのラベルを使ってはならない。**
     - **付与に失敗しても、または呼び出し元を特定できなくても、作成要求を拒否してはならない**
       (`D0-sec-05` の「判定できない入力は通す」と揃える)。その資源は片付けの対象から外れる。
     - **本項より前に作られた資源はラベルを持たないため対象外である。** 一意化名で引ける
       compose 資源を除き、**存在を列挙する手段が無いので表示もしない**(当てのない警告を
       毎回出すと読まれなくなる)。事実は 03 の「既知の制限」に書く。
- 理由: 「他プロジェクトの作業を壊さない」は利用者に対する約束であり、実装の裁量ではない。
  本決定より前は削除対象の絞り込みが名前とイメージに頼っており、**過去に観測した5件の欠陥**
  (排他が無く認証が空のまま起動する / compose 名の正規化の衝突で別プロジェクトの compose 資源を
  消す / 削除失敗を握って成功と表示する / 確認なしで全プロジェクトのセッションを落とす /
  イメージ更新後に稼働コンテナを数え落として共有 docker-proxy を消す)が同じ根を持っていた。
  **「自分が作った」を起動時に付けた印で識別する**と定めることで、5件を1つの機構で閉じられる。
  項8 は同じ考え方を**セッションの中から作られた資源**へ広げたものである: 印を付けられる位置に
  docker-proxy がいる以上、名前の規約や推測に頼る理由が無い。
- 却下した案:
  - **本決定を委任として書く**(識別方法の選択を AI に委ねる) — 「他プロジェクトの作業を壊さない」
    という約束の強さそのものが選択に含まれてしまう。識別**方法**だけを 02 と `D0-env-10` に降ろす。
  - **イメージ ID の履歴を並べて逆引きする** — 削除済みイメージから作られたコンテナを依然
    数え落とす。印を持たせるより確実性が低い。
  - **コンテナ名の規約で識別する**(`docs/issues/028` の命名の一意化と一体で解く) — 利用者に見える
    名前が変わり、既存コンテナの移行手順が必要になる。本決定はそれを伴わずに成立する。
  - **`logout` の対象を自プロジェクトだけに絞る** — `logout` は共有ボリューム全体を空にする操作で
    あり、対象を絞ると「全体をログアウトする」という意味が変わる(`FR-env-03` 受入基準5)。
    対象は全プロジェクトのままとし、項3の確認で守る。
  - **項4 で `logout` がプロジェクト配下を触らず、案内だけ出す** — 「消したつもりで残る」状態が
    続き、`logout` 後の `start` が認証済みで起動する(`docs/issues/025` の事象そのもの)。
  - **項7 で compose 資源の片付けをやめ、利用者に `docker compose down` を委ねる** —
    `FR-env-01` 受入基準6 が定める片付けを撤回することになり、compose コンテナが孤児として
    残り続ける(`D0-env-05` のライフサイクルの決定に反する)。
  - **項7 で削除前に compose コンテナ名を列挙して確認を取るだけにする** — 名前の非一意性という
    根本が残るので、確認を読み飛ばした利用者は同じ被害に遭う。また `stop` に確認を足すと
    「セッションを止めるだけ」の日常操作が重くなる。
  - **項6 の排他を共有ボリュームを触る `logout` / `reset` だけに入れる** — 実測した
    実害は「`start` の認証コピー ⇄ `logout`」なので `start` 側にもロックが要る。
  - **項8 で docker-proxy が作成したコンテナ ID と所有者の対応をファイルに記録する**
    (2026-08-07 に却下した) — 記録の置き場所(共有 docker-proxy はコンテナであり、消えると
    対応表も消える)と記録漏れ(proxy が落ちている間に作られたもの)を新しく抱える。
    ラベルは Docker 側に永続し、proxy を作り直しても別の端末から `stop` しても引ける。
  - **項8 の所有者ラベルに既存の `claude-dev.managed` を使う**(同日に却下した) —
    `logout` / `reset` はこのラベルの値で削除対象を集合として引くので、セッション由来の資源が
    `logout` の削除対象に入ってしまい、`D0-env-05` 項2 が定めた「`logout` には掛けない」と
    正面から食い違う。**別のラベルで表す。**
  - **項8 で一意化名(項7)を廃止してラベルだけにする**(同日に却下した) — ラベルが付く前に
    作られた compose 資源を引く手段が無くなり、移行期の取りこぼしが増える。
  - **項8 で `reset` も所有者一致に絞る**(2026-08-07 に却下した) — `reset` は対象を絞る引数を
    持たない「ホスト全体を初期状態へ戻す」操作であり、所有者で絞ると `stop` と同義になる。
    **`reset` にしかできないこと(他のセッションが残した孤児資源の回収)が失われ**、
    `logout` の後に回収不能になった資源(`D0-env-05` 項2)を片付ける手段がどこにも無くなる。
