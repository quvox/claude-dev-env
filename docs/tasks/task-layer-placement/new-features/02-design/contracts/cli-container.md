### 削除対象の決め方(4つの規則)

| 規則 | 適用する操作 | 対象 |
|---|---|---|
| **A. 集合として列挙して消す** | `logout` / `reset` のコンテナ削除、`stop` の `fwd-<コンテナ名>-*` 一括削除 | Claude コンテナは `claude-dev.managed=1` を持つものだけ。**ラベルを持たない Claude コンテナは削除せず、名前を表示して残す**(表示対象の集合の求め方は下の「残したものをどう列挙するか」)。`fwd-*` と docker-proxy は上の表の名前規則で識別する(移行問題は起きない) |
| **B. 名前で1件を指して消す** | `claude-dev stop <name>` の本体コンテナ | ラベルの有無を問わず削除する(利用者が明示的に指したものである)。ラベルが無い場合はその旨を表示する。**ただし `<name>` は `[A-Za-z0-9._-]` だけを受理する**(下の「ロックキーとして使える文字」) |
| **C. 共有資源を止めてよいかの判定** | `stop` / `logout` / `reset` の docker-proxy の停止判定、および `reset` の `claude-dev-net` の削除判定(**`stop` と `logout` は `claude-dev-net` を削除する経路を持たない**。`FR-env-01` 受入基準9) | 下の「遊休判定」に従う。**ラベルとイメージのどちらにも依存させない**。`logout` と `reset` は Claude コンテナを削除したあとに判定する(**ラベルを持たない既存コンテナが稼働している間は docker-proxy と `claude-dev-net` を残し、残した理由を表示する**)。`reset` も例外ではない: `D0-env-08` 項2 は例外を書いていない。**`reset` はこの判定を規則 D の削除を終えたあとに行う**(先に判定すると、自分がこれから消すセッション由来のコンテナを「稼働中」と数え、共有資源を残して「完全な初期化になっていない」と事実に反する表示を出す。`stop` 側の同じ制約は `02-design/relations.md` の `PLAN-cli-stop` が持つ) |
| **D. 所有者ラベルで集合として消す**(`DSN-env-04`) | `stop` / `reset` のセッション由来の資源の削除 | `stop` は `claude-dev.owner-project-dir` が**自分の起動ディレクトリの絶対パスと一致する**コンテナとネットワーク。`reset` は `claude-dev.role=spawned` を持つ**すべての**コンテナとネットワーク(所有者を問わない)。**`logout` はこの規則を使わない**(`D0-env-05` 項2)。**使用中のネットワークが残らないよう、資源間の依存を解いてから削除する**(順序の固定は 03 が持つ)。**`reset` の削除対象は `FR-env-03` 受入基準14 で確認のために列挙した集合に固定し、削除の時点で引き直さない**(引き直すと、利用者の確認を経ていない資源を消すことになる)。`stop` は削除の失敗を握って続行し(`FR-env-01` 受入基準24)、`reset` は握らない(`D0-env-08` 項5)。**削除した資源の名前は種別つきで1行ずつ表示し、0件なら表示しない**(`FR-env-01` 受入基準26・27)。**規則 A と対象が重なる場面は無い**: 規則 A が引くのは `claude-dev.managed=1`、規則 D が引くのは `claude-dev.role=spawned` で、両方を持つ資源は存在しない |

**`stop` の照合値は所有者の Claude コンテナにしか無い。** 規則 D で `stop` が使う照合値
(自分の起動ディレクトリの絶対パス)の唯一の在り処は、その Claude コンテナの
`claude-dev.project-dir` ラベルである(上の「管理ラベル」)。したがって
**規則 A が所有者の Claude コンテナを削除したあと、そのセッション由来の資源はもう `stop` では
引けない** — `logout` がまさにこの経路であり(規則 A で Claude コンテナを消すが、規則 D は使わない)、
**規則 D の `reset` 側は所有者を問わないので、`reset` からは引ける**。
これは `D0-env-05` 項2 が承知のうえで置いた範囲であり、**利用者から見た帰結(以後どの操作で消せるか)は
`FR-env-03` 受入基準24 が**、実装側の事実は `MODULE-cli-logout` の「既知の制限」が持つ。
**`stop` 自身が同じ状態に落ちる場合(ラベルを読めない)の扱いは `FR-env-01` 受入基準23 である。**

### 排他(ロックキー)

`D0-env-08` 項6 の排他は次の2つのキーで行う(実装手段と置き場所は `D0-env-09` の委任で 03 が決める)。
**対象は共有ボリュームまたは docker-proxy を触る6コマンド**(`start` / `stop` / `logout` / `reset` /
`login` / `login-codex`)である。

| キー | 値 | 取得する操作と区間 |
|---|---|---|
| プロジェクト単位 | 対象コンテナ名(`<NAME>`) | `start`(全区間)/ `stop`(全区間) |
| 共有資源単位 | 固定文字列 `shared` | `logout`(全区間)/ `reset`(全区間)/ **`login`(全区間)/ `login-codex`(全区間)** / **`start`(認証コピーの開始からコンテナ作成の確定まで。ポート競合の再試行ループを含む)** / `stop`(遊休判定から docker-proxy 削除までの区間) |

- **両方を取る操作は「プロジェクト単位 → 共有資源単位」の順で取る**(デッドロックを避けるため
  取得順を固定する)。
- **待たない。** 取得できなければ「エラーケース」の行に従う。
- **`login` / `login-codex` は対話認証を含むため保持時間が長い**(利用者がブラウザで認証を終えるまで)。
  その間 `start` の認証コピー区間・`logout` / `reset` の全区間は取得できず、理由を表示して非0で終わる。
  これは意図した振る舞いである: 認証を書いている最中に消す/読むほうが害が大きい。
- **ロックが守る資源**: プロジェクト単位 = 当該コンテナとそのプロジェクトディレクトリ配下の生成物。
  共有資源単位 = 共有ボリューム(`claude-dev-auth` / `-history` / `-config`)**の中身**と
  docker-proxy、**および「共有ボリュームを読んで作られたコンテナ」**。
  **含まないもの**: イメージ、共有ネットワーク `claude-dev-net`、共有ボリュームそのものの存在
  (上の「冪等に作られる共有資源の『用意』」)。
- **`start` の共有資源単位の区間がコンテナ作成の確定まで及ぶ理由**: 起動したコンテナの entrypoint は
  30 秒ごとに認証を共有ボリュームへ**書き戻す**(`FR-env-03` 受入基準3・8)。認証コピーの直後に
  ロックを離すと、(a) `logout` が完走した直後に作られたコンテナが認証を書き戻して
  **`logout` が静かに巻き戻る**、(b) `stop` の「遊休判定と削除を同一区間に入れる」保護が、
  **`start` 側の docker-proxy の用意**と競合して成立しない。
  **直列化されるのは認証コピーからコンテナ作成の確定までの区間だけ**で、
  `docker run` の完了までを含む(イメージが手元にある場合の実測で数秒)。
  `NFR-scale-01`(5プロジェクト同時起動)に対しては、この区間が5回直列化される分だけ
  起動の総時間が延びる。
- **冪等に作られる共有資源の「用意」はロックの保護対象ではない。** 該当するのは2つで、
  **イメージのビルド**(セットアップ未実施ならイメージを自動ビルドする事前条件ゲート)と、
  **ネットワーク `claude-dev-net` と共有ボリューム3本の作成**である。
  どちらもロックを取る前に走ってよく、その結果として
  イメージ・ネットワーク・空のボリュームが作られても `FR-env-01` 受入基準16 の
  「削除も作成も行ってはならない」に反しない。**どちらも冪等に作られる共有資源であり、どの操作から
  作っても結果が同じで、利用者から見た状態を壊さないためである**(既に在れば何も起きず、無いときに
  作られるのは中身の無い器だけで、認証や作業内容を含まない)。
  **保護対象なのは「器」ではなく「中身」である**: 共有ボリュームの**中身**(認証情報)と
  docker-proxy、および共有ボリュームを読んで作られたコンテナは保護対象のままである。
  **この2つをロックの取得より前に置くことは、`start` / `login` / `login-codex` に許される**
  (どの機能がどの順で呼ぶかは 03 の各機能の「実装上の判断」が持つ)。
- **解放は取得したプロセスだけが行う**: ロックに記録された**保持者のプロセス ID** が自分と一致しない
  ときは削除しない(明示的に解放したキーを、後から別の操作が取り直した場合に消してしまうのを防ぐ)。
  **保持者をどう記録するかは実装手段の選択であり、`D0-env-09` で AI に委任している**
  (この契約が課すのは「保持者が判別できること」だけである)。
