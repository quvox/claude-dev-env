## 実装上の判断

| # | 判断内容 | 根拠(委任ID) |
|---|---|---|
| 1 | claude と codex を個別に消す分岐を作らない(同一ボリュームに同居させた D0-auth-01 の帰結) | D0-auth-01 |
| 2 | Claude コンテナの列挙を**管理ラベル**で行う(イメージからの逆引きをやめる)。ラベルを持たない既存コンテナは消さずに名前を表示する。**docker-proxy と `fwd-*` は固定名・固定接頭辞で識別し、ラベルを見ない**(名前で所有権が読み取れるため。移行問題も起きない) | D0-env-10 |
| 3 | 削除の成否を**1件ごとに記録**し、最後にまとめて判定する(1件目の失敗で止めない)。途中で止めると、より中途半端な状態が残るため。**ただし失敗を握って成功と表示することはしない** | D0-env-08 項5 が定める形の実装。分岐の置き方は D0-scope-02 |
| 4 | 共有ボリュームの削除の成否を**削除後の `/auth` の列挙結果だけ**で判定し、**`rm -rf` の終了コードは見ない**。`rm -rf /auth/* /auth/.*` は `.` と `..` に当たって非0を返しうる一方、`.` と `..` 以外のファイルは消えているため、終了コードを混ぜると**常に失敗扱い**になる | D0-env-08 項5 が定める形の実装。判定手段は D0-scope-02 |
| 5 | 対象が0件のときは確認を求めない(受入基準19)。消すものが無いのに確認を求めるのは、利用者に「何かが消える」と誤解させるため | D0-scope-02 |
| 6 | 非 TTY で `--yes` が無い場合の終了コードを **1** にする。`reset` の現行実装は同じ状況で 0 を返すが、自動実行では「何もしなかった」ことに気づけない(`D0-scope-07` の観測点の定義で「利用者が失敗に気づけない」に当たる)ため、`reset` 側も 1 に揃える | D0-env-08 項3(「中止する」)/ `FR-env-03` 受入基準15 |
| 7 | 削除対象を Claude コンテナと docker-proxy に留め、**`fwd-*` 中継コンテナを対象に加えない**(現行実装の対象範囲を広げない)。対象範囲を広げるかどうかは `FR-env-03` を動かす判断であり、この機能の実装上の判断では決めない | D0-scope-02 |
| 8 | **docker-proxy の削除に遊休判定を通す**(手順9)。`logout` は Claude コンテナを消してから認証を消すので「その後は必ず遊休」に見えるが、**管理ラベルを持たない既存コンテナは消さずに残す**ため遊休にならないことがある。そのまま消すと、残したコンテナの中から Docker が使えなくなる(`FR-env-01` 受入基準9 違反) | D0-env-10(判定をラベルに依存させない)/ `FR-env-01` 受入基準9 |
| 9 | **`INT` / `TERM` は進行中の1件を終えてから受ける**(手順12)。1件の削除を途中で切ると、より中途半端な状態が残る。終了コード 130 は SIGINT の慣行値 | `D0-env-08` 項5 / 契約の「エラーケース」 |
| 10 | **プロジェクト配下の削除対象を認証3ファイルに限り、ディレクトリは消さない**。`.claude/` には `settings.json` / `host-hooks.json` / `host-local-bin/` が同居し、これらは認証ではないため。`D0-scope-02` の「利用者のリポジトリを触らない」を `logout` について撤回するのは `D0-env-08` 項4 の決定だが、**撤回の範囲は認証ファイルだけ**に留める | D0-env-08 項4 / D0-scope-02 |
| 11 | **対象をカレントディレクトリだけに限る**。他のディレクトリのコピーの場所を本システムは知らず、探索すると利用者のファイルシステム全体を走査することになる。`start` を実行したディレクトリの記録を持たないため(`claude-dev.project-dir` ラベルは**稼働中のコンテナにしか無い**)、網羅は原理的にできない。**この限界を表示する** | D0-env-08 項4 |
| 12 | Linux 版・macOS 版の**両方に同じ形で**入れる(同じサブコマンドの成否・出力を OS で変えないため) | D0-scope-03 |
| 13 | **削除コマンドを `( trap '' INT TERM; ... )` のサブシェルで起動する**。非対話シェルではジョブ制御が無効で子プロセスがシェルと同じプロセスグループに入るため、端末で `Ctrl-C` を押すと `docker rm -f` 自身にも SIGINT が直接届き、**「進行中の1件を終えてから中断する」が成立しない**。`trap ''` が設定する `SIG_IGN` は `exec` した子へ継承されるので、`docker` がシグナルを無視して削除を完了する。**両 OS で同じ形に書ける**(`setsid` は macOS に無い) | `D0-env-08` 項5 / D0-scope-03 / `/implement` の独立レンズが検出 |
| 14 | **ラベルを持たないコンテナを残したときは、共有ボリュームの認証が書き戻される可能性を警告する**。コンテナ内の entrypoint は 30 秒ごとに認証を共有ボリュームへ書き戻す(`FR-env-03` 受入基準3・8)ため、**残したコンテナが稼働している限り `logout` は最大 30 秒で巻き戻る**。ロックはホスト CLI のプロセス間でしか効かず、コンテナ内のループには届かない。**削除対象を広げること(=ラベル無しコンテナを消すこと)は受入基準17 が禁じている**ので、実装で選べるのは「利用者に知らせる」ことだけである | `FR-env-03` 受入基準17 と受入基準3 の帰結 / `/implement` の独立レンズが検出 |

## 既知の制限

| 制限 | 影響 | 関連 issue |
|---|---|---|
| **セッション由来のコンテナを「管理ラベルを持たない」と表示する** | `claude-dev.role=spawned` を持つコンテナが `claude-dev-net` に繋がっていると、手順4 の別枠表示に「本変更より前に起動した可能性がある」として現れる。**`CTR-cli-container`「残したものをどう列挙するか」が禁じた事実に反する表示である**(4つ目の除外が `reset` にしか実装されていない) | `docs/issues/089` |
| **セッション由来の資源を回収不能にする** | `logout` は所有者である Claude コンテナを削除するがセッション由来の資源は消さない。所有者が消えると `stop` は片付けを行えない(`FR-env-01` 受入基準23)ので、回収手段は `reset` と手動だけになる | なし(閾値の外: **`D0-env-05` 項2 が承知のうえで置いた範囲**である。利用者から見た帰結は `FR-env-03` 受入基準24 が、機構(所有者ラベルの照合値が所有者の Claude コンテナにしか無いこと)は `CTR-cli-container`「削除対象の決め方(4つの規則)」が持つ) |
| codex だけ・claude だけのログアウトができない | 片方だけ消したい場合は手作業になる | なし(閾値の外: **`D0-auth-01` がそう決めた帰結**) |
| **プロジェクト配下の認証コピーはカレントディレクトリの分しか消せない** | 他のディレクトリで `start` したプロジェクトには古い認証が残る。**この限界を表示する** | なし(閾値の外: 本システムはコピー先を記録しておらず、探索すると利用者のファイルシステム全体の走査になる。`D0-env-08` 項4 が明示) |
| **管理ラベルを持たない Claude コンテナは削除できない** | 管理ラベルが付く前に起動されたコンテナは `claude-dev stop <name>` で1件ずつ止める必要がある | なし(閾値の外: 名前を**表示する**ので気づけ、表示が空になれば移行完了と判別できる) |
| **停止中のラベル無しコンテナは列挙できない** | 残したコンテナの表示に停止中のものが出ない | なし(閾値の外: `docker network inspect` は稼働中しか返さない。停止中は利用者の作業を壊さず、`stop <name>` で消せる。**この限界を表示する**) |
| **`fwd-*` 中継コンテナは削除しない** | `logout` 後も中継コンテナが残る | なし(閾値の外: 現行の対象範囲を広げないという判断。片付けは `stop` / `unforward` / `reset` が担う) |
| **削除対象が0件のときは、非 TTY で `--yes` が無くても終了コード 0 を返す** | 「非 TTY の `logout` は必ず 1」を前提にした自動実行では判定がぶれる(`reset` は常に 1) | なし(閾値の外: 受入基準19「対象0件は確認を求めず 0 で終わる」が受入基準15 より先に効く。削除は行われないので害は無い) |
| **共有ボリュームが「空」かの判定が、列挙できなかった場合と区別できない** | 一時コンテナを起動できない状態で `logout` を実行すると、共有ボリュームに認証が残っているのに「削除対象がありません」と表示して 0 で終わる。手順10 の印による判定を手順6 に置いていないことが原因 | `docs/issues/053`(受入基準19 が前提とする「共有ボリュームも空」を確かめられていない。**独立レンズ Codex が検出**。実装を直すかは `FR-env-03` を動かす判断である) |
| **削除対象が0件の経路では、ラベル無しコンテナの列挙も認証の書き戻しの警告も出さない** | ラベル無しコンテナだけが稼働している状態で `logout` を再実行しても、`logout` が効かない理由に到達できない | `docs/issues/052`(受入基準17 の条件「集合として列挙するとき」と受入基準19 の隙間。振る舞いを変えるかは `FR-env-03` を動かす判断である) |
| **集合削除の各要素は他プロセスのプロジェクト単位ロックと排他になっていない** | 並行する `stop <name>` が同じコンテナを先に消すと、実際には目的どおり消えているのに「削除できなかった」と報告しうる | なし(閾値の外: `logout` / `reset` は共有資源単位のキーしか取らない。両方のキーを取ると別プロジェクトの `start` を`logout` の保持区間(稼働中コンテナの削除と削除用の一時コンテナの起動を含む)のあいだ止めることになり、`NFR-scale-01`(5プロジェクト同時起動)を損なう) |
| **遊休判定に利用者の compose コンテナが入る** | docker-proxy が回収されにくい。**過剰に数える=消さない側**なので受入基準9 は破らない | なし(2026-08-04 の決定シート #1 で人間が案A=現状のままと裁定) |
