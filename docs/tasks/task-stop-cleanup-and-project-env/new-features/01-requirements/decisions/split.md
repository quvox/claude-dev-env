## D1-split-01 既定を不可分とし、段階可は「部分でも価値が増える」5件に限る

- 区分: 決定
- 決めた日: 2026-08-07(**2026-08-08 に対象件数を 34 件 → 22 件へ改めた**。オーケストレーターの
  削除にともなう要件の消滅であり、`段階可` の集合は変えていない。**2026-08-18 に対象件数を
  22 件 → 23 件へ改めた**。`FR-env-13`(同梱外部バイナリ)の新設にともなう増加であり、
  `段階可` の集合は変えていない。**2026-08-19 に対象件数を 23 件 → 24 件へ改めた**。
  `FR-env-14`(プロジェクトごとの環境変数の受け渡し)の新設にともなう増加であり、
  `段階可` の集合は変えていない)
- 内容: 機能要件 14 件・非機能要件 10 件の全 24 件に `分割可否` を明記する。既定は `不可分` とし、
  `段階可(理由)` は次の5件だけとする。
  1. `NFR-perf-01`(pull の増分取得) — 再取得される層が1つ減るだけでも取得時間の短縮という利用者価値があり、目標「再取得ゼロ」へ層単位で段階的に近づけるため。
  2. `NFR-perf-02`(イメージの層共有) — 共有されるベース層が増えるほど追加ディスクが減る形で目標へ段階的に近づけ、部分達成にもディスク削減の価値があるため。
  3. `NFR-scale-01`(同時起動の衝突ゼロ) — 衝突源(コンテナ名・ネットワーク名・公開ポート・Chrome プロファイル)は互いに独立で1つずつ解消でき、解消済みの資源の分だけ同時起動時に衝突する組み合わせが減るため。
  4. `FR-env-01`(コンテナのライフサイクル管理) — **段階的なのは条項 `FR-env-01-19` だけ**である
     (別ディレクトリの compose 資源を巻き込まない)。**何も満たさない状態 = プロジェクトごとに
     compose 資源を区別しない設計**では、すべてのプロジェクトが同じ資源を指すことになり、
     他プロジェクトの compose 資源を**必ず**巻き込む(`D0-env-05` の理由欄)。一意化を入れた現在、巻き込みが起きるのは**一意化した名前が
     偶然一致した場合だけ**で、**残っている取り違えの余地は減るほど利用者の作業が守られる**。
     一意化の強さを上げればさらに近づく(**強さの決め方は 02 の設計判断が定める**)。
     **他の 33 条項は不可分**である。
  5. `FR-env-07`(Docker アクセスの制限) — **段階的なのは条項 `FR-env-07-5` だけ**で、
     `FR-env-01` と**同じ一意化による**。何も満たさない状態との比較も同じである。
     **他の11条項は不可分**である。
- 理由: 規範の既定が「未記載 = 不可分」というフェイルクローズであり、全件に `不可分` を明記することは
  現状の意味を変えない(現状を明示するだけ)。`段階可` にする5件は、いずれも
  **「部分的に満たした状態が、何も満たさない状態より利用者にとって価値がある」**という
  `不可分` の裏返しの条件を満たす。1〜3 は目標値へ段階的に近づく性能・規模の要件、
  4・5 は、一意化を一切行わない状態では**全プロジェクトが必ず衝突する**のに対し、
  部分的な一意化でも**衝突する組み合わせが減った分だけ利用者の作業が守られる**要件である
  (`docs/pendings.md` P-005 が「高い確率で起きる衝突を実用上無視できる確率の衝突に変えるもの」と
  記録しているのが、この段階性そのものである)。
- **`段階可` の射程は要件全体に掛かるが、実際に段階的な条項は限られる。**
  4・5 の理由欄が名指す条項(`FR-env-01-19` / `FR-env-07-5`)以外を `部分` にしてよいという意味では
  ない。とくに `FR-env-01` の「破壊的操作が他プロジェクトの資源を巻き込まない」という約束
  (条項 1〜18・20〜34)は不可分である。**2026-08-07 に追加した条項
  `FR-env-01-22`〜`27`(セッション由来の資源の片付け)と `FR-env-07-11`・`12`(所有者ラベルの付与)も
  すべて不可分である**: 片付けの対象を一部だけ消す状態は、利用者から見れば「消えたものと
  残ったものの区別が説明できない」状態であり、何も消さない状態より価値が高いとは言えない。
  **2026-08-18 に追加した `FR-env-13`(同梱外部バイナリ)も不可分である**: **用意した同梱物が
  一方の配布イメージにしか入っていない状態**は、利用者から見れば「使えるはずのコマンドが
  構成によって在ったり無かったりする」状態であり、何も同梱しない状態(コマンドが常に無い)より
  価値が高いとは言えない。**アーキテクチャごとに用意するかどうかは保守者が選ぶ範囲であり、
  この不可分の射程に入らない** — `FR-env-13-5` が片方のアーキテクチャだけを用意する運用を
  正常な状態として認めている(用意していないものが入らないことは、部分的な充足ではない)。
- **2026-08-19 に追加した `FR-env-14`(プロジェクトごとの環境変数の受け渡し)も不可分である**:
  **書いた変数の一部だけが渡る状態**は、利用者から見れば「書いた値が効いているかどうか分からない」
  状態であり、何も渡さない状態(値が1つも無いと分かる)より価値が高いとは言えない。
  **本システムが使う名前を採用しないことは部分的な充足ではない** — `FR-env-14-8` が
  その1件を採用しないことを正常な振る舞いとして定めている。
  **2026-08-19 に `FR-env-01` へ追加した条項 `FR-env-01-28`〜`-34`(名前付きボリュームの片付けと、
  存在しなかった資源の表示)もすべて不可分である**: 片付けの対象を一部だけ消す状態が説明できない
  ことは、2026-08-07 に追加した条項について既に判断したとおりである。
- 却下した案:
  - **全件を1件ずつ人間が仕分ける** — 既定(不可分)から変わる可能性がある要件は限られ、
    全件の個別判断は決定シートの往復を増やすだけである(決定シート概念1で人間が「委任」と回答)。
  - **`FR-env-01` / `FR-env-07` を `不可分` のまま残す** — 02 のカバレッジ表が
    `FR-env-01-19` / `FR-env-07-5` を `部分(P-005)` とするため、規範により 01・02 が恒久的に
    検証済みにできなくなる(衝突検出を実装するまで)。2026-08-07 に人間が案 A で裁定した
    (決定シート 論点5)。
  - **充足を `完全` に戻して衝突を「設計の範囲外」と扱う** — 設計が覆いきれていない事実を表から
    消すことになり、条項単位カバレッジ導入の目的(部分充足を見えるようにする)と正面から反する。
  - **セッション由来の資源の片付け(`FR-env-01-22`〜`27`)を `段階可` にする**(2026-08-07 に却下した) —
    「コンテナだけ消してネットワークは残す」のような部分状態は、`D0-env-05` 項2 が
    「セッションが作ったものは全部」と決めた範囲を資源の種類ごとに崩すことになり、
    その決定の理由(範囲を1文で言い切れること)を失う。
