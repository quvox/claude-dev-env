### 予約する環境変数名

**プロジェクト環境ファイルから採用しない名前の集合は、次の2つで尽くされる**
(`request.md`「やらないこと」7 / `D0-env-11` 項3)。

| 形 | 対象 | 予約する理由 |
|---|---|---|
| **接頭辞 `CLAUDE_DEV_`** | 本システムがコンテナの振る舞いを切り替えるために使う名前の全体(上表の `CLAUDE_DEV_VM` / `CLAUDE_DEV_VNC` / `CLAUDE_DEV_DOOD_PORTSYNC` / `CLAUDE_DEV_SSH_BRIDGE_PORT` を含む) | 個別に列挙すると、変数を増やしたときに予約の集合が追随しない |
| **固定名 `DOCKER_HOST` / `COMPOSE_PROJECT_NAME` / `SSH_AUTH_SOCK` / `NODE_OPTIONS` / `container`** | 中継先・compose 一意化名・agent ソケット・Node の起動オプション・コンテナ内判定マーカー | 前2つを差し替えられると**検査つきの中継を通らない経路へ切り替わりうる**、および**規則 D と `DSN-env-03` の片付けが空振りする**。後3つは転送・実行・判定の前提が壊れる |

**`VM_PORTS` / `VM_MEM` / `VM_SMP` / `VM_DISK` / `VM_SWAP` は予約しない。** これらはゲスト VM の
運転パラメータであり、プロジェクトごとに変えたい値そのものである。ホスト側の同名変数が
転送されている場合との優先順は、次の適用順が決める。

**適用順**: **プロジェクト環境ファイル由来の組を、本システムが付与する変数より後に置く。**
予約名は上の表で既に除外されているので、この順序が実際に効くのは `VM_*` のように
**本システムが条件付きで転送するだけの変数**に限られ、そこではプロジェクト側の値が採用される。

**VM モードと DooD ポート同期は排他**である: VM モードのときポート同期は起動しない
(ポート同期はホスト共有 daemon 経路のときだけ意味を持つため)。

### DSN-env-04 セッション由来の資源は docker-proxy が付ける所有者ラベルで識別する

- 内容: Claude コンテナの中から docker-proxy を経由して作られる**コンテナ**・**ネットワーク**・
  **名前付きボリューム**に、
  **docker-proxy が作成要求を中継するときに次の2つのラベルを付与する**。
  `stop` は所有者が自分と一致するものを、`reset` は所有者を問わず全部を削除対象にする
  (規則 D)。

  | ラベル名 | 値 | 付与する資源 | 誰が付与するか |
  |---|---|---|---|
  | `claude-dev.role` | `spawned`(固定) | セッション由来のコンテナ・ネットワーク・名前付きボリューム | docker-proxy(作成要求のボディへ注入) |
  | `claude-dev.owner-project-dir` | **呼び出し元 Claude コンテナの `claude-dev.project-dir` ラベルの値をそのまま写したもの**(= 所有者セッションの起動ディレクトリの絶対パス) | 同上 | 同上 |

  - **注入する API 経路は `CTR-docker-api` が定める**(この契約が定めるのは付けるラベルの側である)。
    **ボリューム作成要求にも注入する**(2026-08-19 に加えた。`D0-env-05` 項2 の改訂により、
    名前付きボリュームが片付けの対象になったため)。
    **名前を指定せずに作られたボリューム(匿名ボリューム)には印が付かない** — その作成要求は
    存在せず、Docker がコンテナの作成にともなって直接作るためである。**匿名ボリュームの
    片付けは印に頼らず、所有者ラベルを持つコンテナの削除に紐づけて行う**(上の規則 D)。**ボリュームを名前ではなく所有者ラベルで
    識別するのは、名前で決めると別ディレクトリの資源を巻き込みうるためである** —
    `DSN-env-03` の一意化名はハッシュ先頭6桁の衝突を検出しない設計であり(`docs/pendings.md` の
    `P-005`)、**その衝突で失われるものがボリュームでは作り直せないデータになる**。
    所有者ラベルの値は絶対パスそのものなので、この衝突を受けない。
  - **`claude-dev.managed` は付けない。** `logout` / `reset` は「Claude コンテナを集合として
    列挙する」削除の対象を `claude-dev.managed=1` で引くため、付けるとセッション由来の資源が
    `logout` の削除対象に入り、`D0-env-05` 項2 が定めた「`logout` には掛けない」と正面から
    食い違う。**このラベルは所有と種別を表すだけで、`managed` の意味(本システムが**作った**)は
    持たせない。**
  - **利用者が同じキーのラベルを自分で指定していた場合は、docker-proxy の値で上書きする**
    (所有者の判定が利用者の入力で狂うと、別セッションの資源を消しうる)。
    それ以外のフィールドは変更しない(`FR-env-07` 受入基準11)。
  - **「呼び出し元を特定できた」の定義**: 呼び出し元 Claude コンテナを引き当てられ、
    **そのコンテナが `claude-dev.project-dir` ラベルを持ち、その値が空文字でないこと**。
    **値が空文字の場合は「特定できない」に倒す**(下の付与しない経路へ入る)。
    空値のラベルを写すと `claude-dev.owner-project-dir=` を持つ資源ができ、`stop` 側は
    照合値が空になるので片付けられない一方、`reset` の `claude-dev.role=spawned` では消える —
    **両側が同じ1つのラベルに依存するという `DSN-env-04` の根拠が、その1点でだけ破れる**。
    **`/workspace` のマウント元(bind の書き換えに使う値)ではなく、ラベルの値を写す。**
    理由は「値の一致を構成で保証するため」である: `stop` は削除対象を
    `claude-dev.owner-project-dir` == `claude-dev.project-dir` の**文字列一致**で選ぶので、
    2つの値が別々の経路から得られていると、経路のどちらかが正規化・解決を挟んだ瞬間に
    **一致しなくなり、片付けが黙って空振りする**(マウント元は Docker が返す値、ラベルは
    ホスト CLI が書いた値であり、同じである保証が仕様として存在しない)。
    同じラベルを写せば、一致は**構成上の帰結**になり検証を要しない。
  - **呼び出し元を特定できない(コンテナを引き当てられない、または `claude-dev.project-dir` を
    持たない)、またはボディが解釈できない場合は、ラベルを付けずに中継する**
    (`FR-env-07` 受入基準12)。作成要求を拒否してはならない。その資源は片付けの対象から外れる。
    **管理ラベルが付く前に起動された Claude コンテナがこの経路に入る**(そのセッションの中から
    作った資源は片付けられない)。これは `stop` 側の `FR-env-01` 受入基準23 と同じ限界であり、
    **両側が同じ1つのラベルに依存しているので、片方だけが成功する状態は生じない。**
  - **`DSN-env-04` の導入より前に作られた資源はラベルを持たないため対象外である。** 一意化名で引ける
    compose 資源(`DSN-env-03`)を除き、**列挙する手段が無いので表示もしない**。
- 理由: セッション由来の資源は**名前も固定接頭辞も持たない**(名前は利用者が決める)ので、
  `DSN-env-01` が挙げた3候補のうち「名前」は使えない。「イメージ」も同じ理由で使えない
  (利用者が任意のイメージを使う)。残るのは「ラベル」だけであり、**docker-proxy は作成要求が
  必ず通る位置にいて、呼び出し元の絶対パスを既に解決している**(bind の書き換えに使っている)
  ので、印を付ける主体として過不足がない。
  所有者の値に絶対パスを選ぶのは、**`stop` の入力が `NAME` だけで、絶対パスは削除前に読む
  `claude-dev.project-dir` から得られる**ため、読み取りを1回増やさずに済むからである
  (compose 一意化名のハッシュ源と同じ値を使う)。
  **さらにその値を「マウント元」ではなく「呼び出し元コンテナのラベル」から取るのは、
  照合する2つの値を同じ1つの出所に縛るためである**(上の「定義」)。
- 却下した案:
  - **docker-proxy が作成したコンテナ ID と所有者の対応をファイルに記録する** — 記録の置き場所
    (共有 docker-proxy はコンテナで、作り直すと対応表が消える)と記録漏れ(proxy が落ちている
    間に作られたもの)を新しく抱える。ラベルは Docker 側に永続する。
  - **所有者の値に Claude コンテナ名を使う** — 名前は利用者の起動ディレクトリ名から決まり
    一意でない(`NFR-scale-01` / `docs/issues/028`)ので、別ディレクトリの同名プロジェクトの
    資源を巻き込む。絶対パスにはその問題が無い。
  - **所有者の値を `/workspace` のマウント元から取る** — `stop` が照合する
    `claude-dev.project-dir` とは別の出所になり、**両者が一致する保証が仕様として存在しない**
    (Docker がマウント元を正規化・解決した瞬間に、片付けが黙って空振りする)。
    呼び出し元コンテナのラベルを写せば、その懸念自体が消える。
  - **`claude-dev.managed=1` を付けて既存の識別に相乗りさせる** — 上のとおり `logout` の
    削除対象に入ってしまう。
  - **一意化した compose プロジェクト名(`DSN-env-03`)だけで済ませる** — `docker compose` を
    経由しない `docker run` の資源に `com.docker.compose.project` は付かない。
  - **ラベルを付けず、`stop` が「そのセッションの起動以降に作られたコンテナ」を時刻で推定する** —
    別セッションが同時に作った資源を巻き込む。時刻は所有を表さない。
- 影響: **利用者が `docker inspect` したときに、身に覚えのないラベルが2つ増える。**
  所有者ラベルで利用者自身も一覧できる。
  **ホストの絶対パスがラベル値として現れる**が、これは `claude-dev.project-dir` で既に
  起きていることであり、許容範囲は `02-design/logging.md`「起動ディレクトリの絶対パスの扱い」が
  定める。
- 関連: `D0-env-05` 項2 / `D0-env-08` 項8 / `D0-env-10`(この決めの委任元)/ `CTR-docker-api`
  (注入を行う側の契約)/ `FR-env-01` 受入基準22〜27 / `FR-env-07` 受入基準11・12 /
  `DSN-env-01` / `DSN-env-03`

### DSN-env-05 プロジェクト環境変数は「設定に場所、ファイルに値」で受け渡す

- 内容: プロジェクトごとにコンテナへ渡す環境変数は、**プロジェクト環境ファイル**(用語集)に
  `名前=値` の形で置き、プロジェクト直下の設定ファイルには**その場所だけ**を書く。
  設定ファイルに変数を直接書く経路は設けない。CLI は起動時にそのファイルを読み、
  上の「予約する環境変数名」に当たらない組だけを、本システムが付与する変数より後に置いて渡す。
- 理由: 環境変数の主な用途に社内サービスのトークンの類が含まれる一方、
  設定ファイルは `claude-dev ssh-keys` が書き出すもので**リポジトリに入る前提**である。
  値を設定ファイルへ書けるようにすると、秘密の値がリポジトリへ入る経路をこちらから作ることになる
  (`D0-sec-11` 項1)。口を1つに絞ると、同じ変数が2箇所に書かれたときの優先順を
  利用者が覚える必要も無くなる。**同じ形をこの製品は認証の共有について既に採っている**
  (同期方式を2つ持たない。`DSN-auth-01`)。
- 却下した案:
  - **設定ファイルに変数を直接書ける形にする** — 秘密の値がリポジトリへ入る経路を作る。
  - **設定ファイルにも環境ファイルにも書ける形にする** — 優先順を利用者が覚えることになり、
    秘密の置き場も2箇所に割れる。
  - **予約名も素通しで渡す** — 規則 D の片付けと `CTR-docker-api` の検査という2つの保証が、
    利用者の設定1行で外れる。
  - **環境ファイルの値を CLI 側で展開する**(`$HOME` などを解決してから渡す) —
    ホスト側で展開されるのかコンテナ内で展開されるのかを利用者が判別できない。
- 影響: **利用者が `docker inspect` したときに、自分が書いた変数が Config.Env に現れる。**
  値そのものは端末にも起動ログにも出さない(`FR-env-14-3` / `02-design/logging.md`)が、
  **コンテナの構成情報を読める者からは読める** — これは `NFR-sec-01` が禁じる4項目には当たらず、
  `D0-sec-11` 項5 が受容している範囲である。
- 関連: `D0-env-11` / `D0-sec-11` / `RQ-env-07` / `FR-env-14` / `AC-08` /
  上の「渡す環境変数」と「予約する環境変数名」 / `DSN-auth-01`(口を2つ持たない先例)

### 識別の手段は資源ごとに違う

**本システムが関与する Docker 資源のうち、名前から所有権が読み取れないのは Claude コンテナと
セッション由来の資源の2つだけ**である(前者は名前が利用者の起動ディレクトリ名から決まり、
後者は名前を利用者が自由に決める)。他の資源は本システムが決めた固定名または固定接頭辞を持つので、
名前で一意に識別できる。**したがって管理ラベルはこの2つに付ける。**

| 資源 | 識別の手段 |
|---|---|
| **Claude コンテナ** | **管理ラベル**(下の表)。名前は利用者のディレクトリ名由来で一意でない |
| **セッション由来の資源**(コンテナ・ネットワーク・名前付きボリューム) | **所有者ラベル**(下の表。`DSN-env-04`)。名前は利用者が決めるので所有権を読み取れない。**ホスト CLI は付与できない**ので docker-proxy が作成要求へ注入する |
| `fwd-<コンテナ名>-<ポート>` 中継コンテナ | **名前の接頭辞 `fwd-`**。本システムが決めた固定接頭辞である |
| docker-proxy コンテナ | **固定名 `claude-dev-docker-proxy`** |
| 共有ボリューム | **固定名** `claude-dev-auth` / `claude-dev-history` / `claude-dev-config`、および接頭辞 `claude-dev-chrome-` / `claude-dev-vm-` |
| ネットワーク | **固定名 `claude-dev-net`** |
| イメージ | **固定名** `claude-dev-claude` / `claude-dev-claude-vnc` / `claude-dev-docker-proxy` |
| **コンテナ内 `docker compose` が作った資源** | 所有者ラベル(上のセッション由来の資源と同じ)に加えて、**ラベル `com.docker.compose.project` の一意化した値**(下の「compose 資源の識別」)。**2つ持つのは移行のためである**: 所有者ラベルが付く前に作られた compose 資源は一意化名でしか引けない |

### 管理ラベル

| ラベル名 | 値 | 付与する資源 | 誰が付与するか |
|---|---|---|---|
| `claude-dev.managed` | `1`(固定) | Claude コンテナ | ホスト CLI(`docker run` の `--label`) |
| `claude-dev.role` | `claude`(Claude コンテナ)/ `spawned`(セッション由来の資源) | Claude コンテナ / セッション由来のコンテナ・ネットワーク・名前付きボリューム | ホスト CLI / **docker-proxy**(`DSN-env-04`) |
| `claude-dev.project-dir` | 起動時のホスト側カレントディレクトリの**絶対パス**(`pwd` の値をそのまま。正規化・短縮をしない) | Claude コンテナ | ホスト CLI |
| `claude-dev.owner-project-dir` | **所有者セッションの起動ディレクトリの絶対パス**(呼び出し元 Claude コンテナの `claude-dev.project-dir` と同じ値) | セッション由来のコンテナ・ネットワーク・名前付きボリューム | **docker-proxy**(`DSN-env-04`) |

- 接頭辞は `claude-dev.` に固定する。`com.docker.*`(Docker / compose の予約)は使わない。
- **`claude-dev.managed` はセッション由来の資源に付けない。** `logout` / `reset` はこのラベルで
  削除対象を集合として引くので、付けると `logout` がセッション由来の資源まで消す
  (`D0-env-05` 項2 の「`logout` には掛けない」に反する)。**「本システムが作った」ことを表すのが
  `managed`、「本システムを通して作られた」ことを表すのが `role=spawned` である。**
- 値の検証は行わない。**受け側は存在するかどうかだけを見る**。ただし `claude-dev.project-dir` と
  `claude-dev.owner-project-dir` の**値そのものには用途がある**: 前者は (1) 利用者への表示、
  (2) **`stop` が compose の一意化名を再現するためのハッシュ源**、(3) **`stop` が所有者ラベルの
  値を再現するための元**。後者は **`stop` の削除対象を絞り込む条件**である。
  **削除するかどうかの判定に `claude-dev.managed` の値を使わない**
  (判定に使うと、ラベルを持たない既存コンテナを取りこぼす)。
- **ラベルを増やすことは互換の破れにならないが、名前と値を変えることは破れになる**
  (既存の稼働コンテナが古いラベルを持ったまま残るため)。変える場合は移行期の扱いを併記する。
- `claude-dev.project-dir` は「どのディレクトリで起動したか」という**事実の唯一の在り処**である。
  そのため次の2つが成立する: 同名コンテナとの衝突時(`FR-env-01` 受入基準12)に
  「別ディレクトリの同名プロジェクトである可能性」を推測ではなく事実として示せる。
  そして **`stop <name>` を別のディレクトリから実行しても compose の一意化名と所有者ラベルの値を
  再現できる**(`stop` の入力は `NAME` だけで、絶対パスは他のどこにも記録されていない)。
  **したがって本体コンテナを削除するとこの値は失われる**(読む時機の固定は 03 が持つ)。

### 削除対象の決め方(4つの規則)

| 規則 | 適用する操作 | 対象 |
|---|---|---|
| **A. 集合として列挙して消す** | `logout` / `reset` のコンテナ削除、`stop` の `fwd-<コンテナ名>-*` 一括削除 | Claude コンテナは `claude-dev.managed=1` を持つものだけ。**ラベルを持たない Claude コンテナは削除せず、名前を表示して残す**(表示対象の集合の求め方は下の「残したものをどう列挙するか」)。`fwd-*` と docker-proxy は上の表の名前規則で識別する(移行問題は起きない) |
| **B. 名前で1件を指して消す** | `claude-dev stop <name>` の本体コンテナ | ラベルの有無を問わず削除する(利用者が明示的に指したものである)。ラベルが無い場合はその旨を表示する。**ただし `<name>` は `[A-Za-z0-9._-]` だけを受理する**(下の「ロックキーとして使える文字」) |
| **C. 共有資源を止めてよいかの判定** | `stop` / `logout` / `reset` の docker-proxy の停止判定、および `reset` の `claude-dev-net` の削除判定(**`stop` と `logout` は `claude-dev-net` を削除する経路を持たない**。`FR-env-01` 受入基準9) | 下の「遊休判定」に従う。**ラベルとイメージのどちらにも依存させない**。`logout` と `reset` は Claude コンテナを削除したあとに判定する(**ラベルを持たない既存コンテナが稼働している間は docker-proxy と `claude-dev-net` を残し、残した理由を表示する**)。`reset` も例外ではない: `D0-env-08` 項2 は例外を書いていない。**`reset` はこの判定を規則 D の削除を終えたあとに行う**(先に判定すると、自分がこれから消すセッション由来のコンテナを「稼働中」と数え、共有資源を残して「完全な初期化になっていない」と事実に反する表示を出す。`stop` 側の同じ制約は `02-design/relations.md` の `PLAN-cli-stop` が持つ) |
| **D. 所有者ラベルで集合として消す**(`DSN-env-04`) | `stop` / `reset` のセッション由来の資源の削除 | `stop` は `claude-dev.owner-project-dir` が**自分の起動ディレクトリの絶対パスと一致する**コンテナ・ネットワーク・名前付きボリューム。`reset` は `claude-dev.role=spawned` を持つ**すべての**コンテナ・ネットワーク・名前付きボリューム(所有者を問わない)。**ボリュームだけは既定で対象に入らない**: `--volumes` が指定されたときにだけ集合へ加える。**名前を指定せずに作られたボリューム(匿名ボリューム)は所有者ラベルを持てない**(作成要求が docker-proxy を通らず、Docker がコンテナの作成にともなって直接作る)ので、**集合として引くのではなく、所有者ラベルを持つコンテナを削除するときに「そのコンテナが抱えていた名前無しのボリュームも一緒に消す」指定を添えて消す**。**この指定も `--volumes` があるときだけ添える**(既定では消えない点は名前付きと同じ)。**匿名ボリュームは削除した資源の列挙にも、残っている資源の表示にも出さない**(`FR-env-01-29`)(`FR-env-01-28`・`-32`。指定が無ければ残っているボリュームの名前と削除する方法を表示する — `FR-env-01-29`・`-33`)。**`logout` はこの規則を使わない**(`D0-env-05` 項2)。**使用中のネットワークとボリュームが残らないよう、資源間の依存を解いてから削除する**(コンテナ → ネットワーク・ボリュームの順。順序の固定は 03 が持つ)。**`reset` の削除対象は `FR-env-03` 受入基準14 で確認のために列挙した集合に固定し、削除の時点で引き直さない**(引き直すと、利用者の確認を経ていない資源を消すことになる)。`stop` は削除の失敗を握って続行し(`FR-env-01` 受入基準24)、`reset` は握らない(`D0-env-08` 項5)。**削除した資源の名前は種別つきで1行ずつ表示し、0件なら表示しない**(`FR-env-01` 受入基準26・27)。**規則 A と対象が重なる場面は無い**: 規則 A が引くのは `claude-dev.managed=1`、規則 D が引くのは `claude-dev.role=spawned` で、両方を持つ資源は存在しない |

**`stop` の照合値は所有者の Claude コンテナにしか無い。** 規則 D で `stop` が使う照合値
(自分の起動ディレクトリの絶対パス)の唯一の在り処は、その Claude コンテナの
`claude-dev.project-dir` ラベルである(上の「管理ラベル」)。したがって
**規則 A が所有者の Claude コンテナを削除したあと、そのセッション由来の資源はもう `stop` では
引けない** — `logout` がまさにこの経路であり(規則 A で Claude コンテナを消すが、規則 D は使わない)、
**規則 D の `reset` 側は所有者を問わないので、`reset` からは引ける**。
これは `D0-env-05` 項2 が承知のうえで置いた範囲であり、**利用者から見た帰結(以後どの操作で消せるか)は
`FR-env-03` 受入基準24 が**、実装側の事実は `MODULE-cli-logout` の「既知の制限」が持つ。
**`stop` 自身が同じ状態に落ちる場合(ラベルを読めない)の扱いは `FR-env-01` 受入基準23 である。**

## 破壊的操作の対象の識別

`D0-env-08` が「破壊的操作の対象は自分が作った資源に限る」と決め、識別方法をこの契約に委ねた。
ここが**唯一の正**である(`D0-env-10` の委任で名前と値を決めた)。

**この取り決めの当事者は次のとおりである**(識別についてはこの節が唯一の正である)。

| 役割 | モジュール | 何を付ける / 読むか |
|---|---|---|
| **発行側(2つ)** | `MOD-cli-start` | Claude コンテナへ `claude-dev.managed` / `claude-dev.role=claude` / `claude-dev.project-dir` を付ける(`DSN-env-01`) |
| | **`MOD-docker-proxy`** | セッション由来のコンテナ・ネットワーク・**名前付きボリューム**へ `claude-dev.role=spawned` / `claude-dev.owner-project-dir` を付ける(`DSN-env-04`) |
| **読み手(3つ)** | `MOD-cli-stop` / `MOD-cli-logout` / `MOD-cli-reset` | 下の「削除対象の決め方(4つの規則)」に従って削除対象を決める |

**どちらかの発行側がラベルの付与をやめると、対応する読み手側の削除対象が空になる**
(`MOD-cli-start` が止めれば規則 A が、`MOD-docker-proxy` が止めれば規則 D が空になる)。
結合テストの責任モジュールが読み手側にあるのはこのためである
(`docs/02-design/system.md`「結合テスト対象」)。

## 渡す環境変数

**真偽を表す変数は厳密一致で判定する**が、**既定が有効か無効かで見る値が違う**: 既定が無効のものは
**`1` に厳密一致したときだけ有効**(`true` / `yes` / `TRUE` は無効)、既定が有効のものは
**`0` に厳密一致したときだけ無効**(それ以外の任意の値は有効のまま)。どちらに属するかは下表の
「型・値域」に書く。**真偽を表す変数**の判定はすべて受け側(entrypoint)が行い、**値の検証で起動を止めることはしない**。**ホスト側から与えられた値を CLI が付与前に検証する変数が1つだけある**(下表の `CLAUDE_DEV_SSH_BRIDGE_PORT`)。それも起動は止めない。

| 変数 | 型・値域 | 付与するのは誰か | 必須 | 既定値 | 想定外の値のときの扱い |
|---|---|---|---|---|---|
| `DOCKER_HOST` | `tcp://<ホスト名>:<ポート>` 形式の URL | CLI(ホストに Docker ソケットがあるときだけ) | 条件付き | 付与しない | 形式を検証しない。到達できなければコンテナ内から Docker が使えないだけで、起動は続く。**VM モードでは entrypoint が上書きする** |
| `COMPOSE_PROJECT_NAME` | 小文字英数と `_` `-` のみ | CLI | **必須** | `<正規化名>-<起動ディレクトリの絶対パスのハッシュ短縮値>`。正規化名は起動ディレクトリ名を**小文字化してから** `[a-z0-9_-]` 以外の1文字を `-` に置換した値、ハッシュ短縮値は**絶対パスの SHA-256 の先頭6桁(16進小文字)**。詳細は下の「compose 資源の識別(プロジェクト名の一意化)」 | 付与しない経路が無いので発生しない。**ハッシュを足すことで、正規化後に衝突する別ディレクトリが同じ値にならない**(`NFR-scale-01`) |
| `CLAUDE_DEV_VM` | `1` のみが有効 | CLI(VM モード指定時) | 任意 | 付与しない(= 無効) | **`1` 以外はすべて無効**として扱う |
| `VM_PORTS` / `VM_MEM` / `VM_SMP` / `VM_DISK` / `VM_SWAP` | 文字列(ゲスト VM のパラメータ) | CLI(VM モードで、かつホスト側の同名変数が空でないときだけ転送) | 任意 | 付与しない(ゲスト側の既定に従う) | 値を検証しない。ゲスト VM の起動に失敗した場合は VM 無しで続行する |
| `CLAUDE_DEV_DOOD_PORTSYNC` | `0` で無効、それ以外は有効 | 利用者(CLI は付与しない) | 任意 | 未設定 = 有効 | **`0` の厳密一致のときだけ無効**。他の値は有効として扱う |
| `CLAUDE_DEV_VNC` | `1` のみが有効 | **イメージの `ENV`**(CLI は付与しない) | 任意 | ブラウザ確認資産を含むイメージでは `1` | `1` 以外はすべて無効として扱う |
| `CLAUDE_DEV_SSH_BRIDGE_PORT` | **1〜65535 の整数**(10進表記) | CLI(**macOS のみ**) | 条件付き | 付与しない | **CLI は付与する前に値を検証する**: 同名のホスト側変数で中継ポートが指定され、その値が 1〜65535 の整数でなければ**採用せず**、受理できない値であることと受理する範囲を表示して **agent 転送なしで続行する**(`FR-env-04-8`)。**「SSH agent 転送が有効である」と読める表示を出さない。** 付与された値そのものは受け側で検証しない。非空なら TCP ブリッジの接続先として使う。ソケットが用意できなくても起動は続く |
| `SSH_AUTH_SOCK` | コンテナ内の固定パス | CLI(**Linux のみ**、ホストに agent ソケットがあるとき) | 条件付き | 付与しない | 受け側はソケットの実在で判定する。無ければ agent 転送なしで続行する |
| `NODE_OPTIONS` | Node の起動オプション文字列 | CLI | **必須** | `--max-old-space-size=4096` | 付与しない経路が無い |
| `container` | `docker` | **イメージの `ENV`**(起動時ではない) | **必須** | `docker` | コンテナ内であることの判定マーカー。上書きは想定しない |
| **プロジェクト環境ファイルの各行** | 利用者が書いた `名前=値` の組(名前は英大文字・数字・下線で始まりうる識別子) | CLI(プロジェクト直下の設定で場所が指定され、そのファイルを読めたときだけ) | 任意 | 付与しない | **下の「予約する環境変数名」に当たる名前は採用しない。** 組として読めない行はその行だけ採用しない。**値は検証せず、展開もしない。** どの場合も起動を止めない(`FR-env-14-6`〜`-10`) |

## プロジェクト設定ファイルとプロジェクト環境ファイル

プロジェクト直下の設定ファイルは**ホスト CLI が所有し、利用者も手で編集する**。
本節はその書式と、CLI が守る取り決めを定める(`DSN-env-05` / `D0-env-11`)。

| 項目 | 取り決め |
|---|---|
| 設定ファイルの位置 | プロジェクトディレクトリの直下。ファイル名は固定(名前の実体は 03 が持つ) |
| 設定ファイルの書式 | 行指向の簡易な形。**キーごとに独立した節**を持ち、`ssh_keys`(使う SSH 鍵の一覧)と `env_file`(プロジェクト環境ファイルの場所)の2つを持つ |
| **CLI が設定ファイルを書き換えるときの規則** | **利用者が書いた他のキーと、その配下の行を保存する。** 書き換えてよいのは自分が担当する節だけであり、ファイル全体を作り直してはならない。**節の境界を見ずに行を消してはならない**(`docs/issues/002` が記録している欠陥) |
| `env_file` の値 | プロジェクトディレクトリからの相対パスを**1つだけ**書く。**既定のファイル名は無く、この鍵が無ければ何も読まない**(`FR-env-14-5`)。**プロジェクトディレクトリの外を指す値は採用しない**(`FR-env-14-9`) |
| プロジェクト環境ファイルの書式 | 1行1組の `名前=値`。空行と `#` で始まる行は読み飛ばす。値の引用符の扱いと、値の中の `=` の扱いは 03 が定める。**値は展開しない** |
| 版管理の追跡から外す手段 | 認証ファイルについて既に行っているものと同じ手段を使う(具体は 03 が持つ)。**外せなくても起動は止めない**(`FR-env-14-4`) |

- **設定ファイルは版管理に入る前提、プロジェクト環境ファイルは入らない前提である**
  (`D0-sec-11` 項1・項2)。この非対称が、値の置き場を分ける理由そのものである。
- **`env_file` の指定が無いことと、指定されたファイルが読めないことは別に扱う**
  (前者は表示しない、後者は表示する。`FR-env-14-5` / `-6`)。

## エラーケース

| 条件 | 期待する振る舞い |
|---|---|
| 共有ボリュームに認証が無い | 何もコピーせず起動を完了する(未ログインのまま使える) |
| ホストの git 設定 / gh 設定が無い | そのマウントを省いて起動する |
| SSH 鍵が選択されていない | agent ソケットを渡さず、指定方法を案内して起動する |
| Docker ソケットが無い(macOS) | `DOCKER_HOST` を設定せずに起動する |
| 環境変数が想定外の値 | **上表の「想定外の値のときの扱い」に倒し、起動を止めない**。既定が無効の変数(`CLAUDE_DEV_VM` / `CLAUDE_DEV_VNC`)は無効のまま、既定が有効の変数(`CLAUDE_DEV_DOOD_PORTSYNC`)は**有効のまま**になる |
| 公開ポートが競合して起動に失敗した | ブラウザ確認資産を使う場合に限り、**稼働していない作りかけのコンテナだけを削除して**別のポートを取り直して再試行する(上限 20 回)。上限に達したか、競合以外の失敗なら、エラーを表示して終了コード 1 で終わる |
| **コンテナ名が衝突して起動に失敗した**(同名のコンテナが既に存在する) | **既存のコンテナを削除しない。** 同名のコンテナが稼働中であることと、別ディレクトリの同名プロジェクトである可能性を表示し、**再試行せずに**終了コード 1 で終わる。同名の稼働中コンテナは利用者の作業中セッションでありうるため、後片付けの対象にしてはならない |
| **CPU 仮想化デバイスを渡す指定(`--kvm`)をしたが、そのデバイスが無い** | **警告を出して続行する**(渡せるデバイスだけを渡す) |
| **VM モードの指定(`--vm` / `--vm-fresh`)をしたが、CPU 仮想化デバイスが無い** | **中止して終了コード 1 で終わる。** ソフトウェアエミュレーションでは実用的な速度が出ないため、VM 無しで続行させるのではなく、利用者に VM モードでない起動を選ばせる |
| ゲスト VM の**起動**に失敗した(デバイスはあるが provision / ブートが失敗) | **VM 無しで続行する**(起動そのものは失敗させない)。調査手段を案内する |
| 常駐セッションの起動が待ち時間内に完了しない | コンテナは起動したまま残し、状況と再実行の方法を案内して**終了コード 0** で戻る(黙って接続失敗にしない) |
| macOS で SSH の TCP ブリッジのソケットが用意できない | **有限時間で諦めて**(待ち時間の値は 03 が持つ) agent 転送なしで続行する |
| **macOS で agent 転送の中継ポートがホスト側から指定され、その値が 1〜65535 の整数でない** | **その指定を採用しない。** 受理できない値であることと受理する範囲を表示し、agent 転送なしで起動を続行する(`FR-env-04-8`)。**「SSH agent 転送が有効である」と読める表示を出してはならない** |
| **ロックを取得できない**(同じキーを別の操作が保持している) | **待たない。** 保持している操作の名前とプロセス ID、再実行の方法を stderr へ出し、**削除も作成も一切行わずに**終了コード 1 で終わる |
| **ロックが、既に存在しないプロセスに保持されたまま残っている** | その事実を表示してからロックを引き継ぎ、処理を続ける(永久に取得できない状態を作らない) |
| **集合として列挙する削除の対象に、管理ラベルを持たない Claude コンテナがある** | そのコンテナは**削除しない**。名前と「管理ラベルが付く前に起動した可能性がある」ことを表示して残す(規則 A)。**削除する集合が空(`logout` の削除対象が0件)の場合も同じく表示する** — 削除しないことと、残したという事実を伏せることは別である(`FR-env-03` 受入基準19) |
| **`stop <name>` の対象コンテナが管理ラベルを持たない** | その1件は**削除する**。管理ラベルを持たないことを表示する(規則 B) |
