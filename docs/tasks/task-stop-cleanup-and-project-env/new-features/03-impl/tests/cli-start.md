## テスト設計の判断

- 判断なし: **このモジュールについて AI が決めたテスト設計の判断は無い。** 自動テストを置かない範囲は `SR-32`(Bash 実装に自動テストランナーを設けない)と 02 のテスト戦略 `DSN-test-01` が既に決めており、**「テストを書かない」「手動テストで代替する」は 標準委任 `DS-01` の対象外**である(`.claude/directions/delegation.md` §2)。何を検証するかは受入基準が正で、確認は E2E の実機確認手順(`tests/e2e.md`)が持つ。
- [DS-01] **プロジェクト環境ファイルの確認を、1つの env ファイルに全部の型(普通の組・空行・コメント・読めない行・予約名・重複・外を指す指定)を詰めず、型ごとに手順を分ける**(手順8-23-1〜8-23-10) — 理由: 全部を1ファイルに入れると、1件でも採用の判定を誤ったときにどの型が壊れたかが出力から決まらない。**採用しなかった名前と行番号を利用者へ出すこと自体が条項である**(`FR-env-14-7`・`-8`・`-10`)ので、出力を型ごとに見分けられる形にしておく必要がある / 見直す条件: 採用しなかった件数だけを出す形に変わったとき
- [DS-01] **値が漏れていないことの確認を、端末出力と `docker logs` の両方に対して行う**(手順8-23-3) — 理由: `FR-env-14-3` は端末と起動ログの双方を対象にしており、片方だけを見ると entrypoint 側の出力を取りこぼす / 見直す条件: 起動ログに環境変数を出す経路が無くなったとき
- [DS-01] **`.gitignore` への追記の確認を `git check-ignore` で行い、ファイルの中身の grep で行わない** — 理由: 追記の書式(末尾のスラッシュの有無、既存行との重複)は実装の選択であり、条項が求めているのは**追跡から外れること**である(`FR-env-14-4`)。中身を見ると実装の書式に検証が縛られる / 見直す条件: 追跡から外す手段が `.gitignore` 以外になったとき
