### 論点 1. マウント(ボリューム)を消すとして、既定で消すか・指定したときだけ消すか

- **選択肢**:
  **A: `claude-dev stop` が既定でボリュームも消す** — 「セッションが作ったものは全部消える」に
  なり、溜まらない。取り違えて消したデータは戻らない。
  **B: 既定では消さず、`claude-dev stop --volumes` のように明示したときだけ消す** —
  誤って消えることはない。何も指定しなければ、いままでどおり溜まり続ける
  (**その代わり、残っているボリュームの名前を stop の最後に表示する**)。
  **C: 消さない。残っているボリュームの名前と、消し方だけを表示する** — いまの動作に
  「気づける表示」を足すだけ。溜まるのは変わらない。
- **AI推奨**: **B**。理由: 消したいという要望と、消えては困るデータがあるという事実の
  両方が成り立つのは B だけです。既定を安全側に置きつつ、`--volumes` を1回打てば
  A と同じ結果になります。**この選択で後から高くつくこと**: 利用者が毎回 `--volumes` を
  打つ必要があり、打ち忘れれば溜まります(ただし表示で気づけます)。
  **崩れる条件**: 「打ち忘れても溜まらないこと」自体が要望の本体だった場合。そのときは A です。
- **未回答時の既定**: AI推奨のとおりにする(決定として記録し、記録先をこのシートの末尾で開示する)
- **根拠(上流)**: `docs/00-requests/decisions/env.md` の `D0-env-05` 項2(セッションが作った
  資源を stop で削除すると決めた記録。ただし「削除しない: 名前付きボリューム — 利用者のデータで
  あり、削除は破壊的である」と明記)。**A も B も、この 00 の記述を人間が動かすことが前提です。**
- **根拠(同層)**: 同じ製品の中に**先例が2つ**あります。破壊的な操作(`claude-dev logout` /
  `claude-dev reset`)は**削除対象を列挙して同意を求め**、端末が無い環境では中止します。
  一方 `claude-dev stop` は**確認を求めない**と決められています(日常操作を重くしないため)。
  したがって「stop に確認を足す」案は先例に反し、代わりに**引数で明示させる**のが同じ考え方の
  適用になります。
- **根拠(下流)**: この判断に依存するのは **停止・初期化の2つの入口**と、
  **Docker Socket Proxy のラベル付与**です。さらに `docs/pendings.md` の `P-005`
  (compose の一意化名がハッシュ6桁なので、別ディレクトリと偶然一致しうることを受け入れた記録)
  の**重みが変わります** — いまは一致しても失われるのは作り直せるコンテナですが、
  **ボリュームを消す仕様にすると、一致した相手のデータが失われます**。
  そのため実装は**一意化名ではなく所有者ラベルで消す**ことを前提にします(ラベルは
  絶対パスをそのまま持つので偶然一致しません)。
- **間違えたときの戻し方**: A を選んで事故が起きた場合、**失われたデータは戻りません**。
  仕様は後続タスクで B へ戻せます。B を選んで「溜まって困る」と分かった場合は、
  後続タスクで既定を A に変えるだけで済みます(壊れるものはありません)。
- **過去の回答**: 2026-07-31 に「停止時に名前付きボリュームも消す」を却下した記録が
  `D0-env-05` にあります(概念1 と同じ記録)。**確認を求めるかどうかについては
  2026-08-04 に人間が「`claude-dev stop` は確認を求めない」と裁定済み**で、
  この論点はその裁定を変えずに済む形(引数での明示)を推奨しています。
