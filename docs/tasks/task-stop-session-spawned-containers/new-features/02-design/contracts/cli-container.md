## 破壊的操作の対象の識別

`D0-env-08` が「破壊的操作の対象は自分が作った資源に限る」と決め、識別方法をこの契約に委ねた。
ここが**唯一の正**である(`D0-env-10` の委任で名前と値を決めた)。

**この取り決めの当事者は次のとおりである。識別についてはこの節が唯一の正であり、
文書冒頭の箇条書き(「当事者」と「管理ラベルの読み手」)は起動経路
`MOD-cli-start` → `MOD-entrypoint` を述べたものとして読む** — 冒頭の
「発行側(MOD-cli-start)が」は `DSN-env-04` の導入前の記述であり、発行側の数は下の表が正である。

| 役割 | モジュール | 何を付ける / 読むか |
|---|---|---|
| **発行側(2つ)** | `MOD-cli-start` | Claude コンテナへ `claude-dev.managed` / `claude-dev.role=claude` / `claude-dev.project-dir` を付ける(`DSN-env-01`) |
| | **`MOD-docker-proxy`** | セッション由来のコンテナとネットワークへ `claude-dev.role=spawned` / `claude-dev.owner-project-dir` を付ける(`DSN-env-04`) |
| **読み手(3つ)** | `MOD-cli-stop` / `MOD-cli-logout` / `MOD-cli-reset` | 下の「削除対象の決め方(4つの規則)」に従って削除対象を決める |

**どちらかの発行側がラベルの付与をやめると、対応する読み手側の削除対象が空になる**
(`MOD-cli-start` が止めれば規則 A が、`MOD-docker-proxy` が止めれば規則 D が空になる)。
結合テストの責任モジュールが読み手側にあるのはこのためである
(`docs/02-design/system.md`「結合テスト対象」)。

## エラーケース

| 条件 | 期待する振る舞い |
|---|---|
| 共有ボリュームに認証が無い | 何もコピーせず起動を完了する(未ログインのまま使える) |
| ホストの git 設定 / gh 設定が無い | そのマウントを省いて起動する |
| SSH 鍵が選択されていない | agent ソケットを渡さず、指定方法を案内して起動する |
| Docker ソケットが無い(macOS) | `DOCKER_HOST` を設定せずに起動する |
| 環境変数が想定外の値 | **上表の「想定外の値のときの扱い」に倒し、起動を止めない**。既定が無効の変数(`CLAUDE_DEV_VM` / `CLAUDE_DEV_VNC`)は無効のまま、既定が有効の変数(`CLAUDE_DEV_DOOD_PORTSYNC`)は**有効のまま**になる |
| 公開ポートが競合して起動に失敗した | ブラウザ確認資産を使う場合に限り、**稼働していない作りかけのコンテナだけを削除して**別のポートを取り直して再試行する(上限 20 回)。上限に達したか、競合以外の失敗なら、エラーを表示して終了コード 1 で終わる |
| **コンテナ名が衝突して起動に失敗した**(同名のコンテナが既に存在する) | **既存のコンテナを削除しない。** 同名のコンテナが稼働中であることと、別ディレクトリの同名プロジェクトである可能性を表示し、**再試行せずに**終了コード 1 で終わる。同名の稼働中コンテナは利用者の作業中セッションでありうるため、後片付けの対象にしてはならない |
| **CPU 仮想化デバイスを渡す指定(`--kvm`)をしたが、そのデバイスが無い** | **警告を出して続行する**(渡せるデバイスだけを渡す) |
| **VM モードの指定(`--vm` / `--vm-fresh`)をしたが、CPU 仮想化デバイスが無い** | **中止して終了コード 1 で終わる。** ソフトウェアエミュレーションでは実用的な速度が出ないため、VM 無しで続行させるのではなく、利用者に通常起動を選ばせる |
| ゲスト VM の**起動**に失敗した(デバイスはあるが provision / ブートが失敗) | **VM 無しで続行する**(起動そのものは失敗させない)。調査手段を案内する |
| 常駐セッションの起動が待ち時間内に完了しない | コンテナは起動したまま残し、状況と再実行の方法を案内して**終了コード 0** で戻る(黙って接続失敗にしない) |
| macOS で SSH の TCP ブリッジのソケットが用意できない | **有限時間で諦めて**(待ち時間の値は 03 が持つ) agent 転送なしで続行する |
| **ロックを取得できない**(同じキーを別の操作が保持している) | **待たない。** 保持している操作の名前とプロセス ID、再実行の方法を stderr へ出し、**削除も作成も一切行わずに**終了コード 1 で終わる |
| **ロックが、既に存在しないプロセスに保持されたまま残っている** | その事実を表示してからロックを引き継ぎ、処理を続ける(永久に取得できない状態を作らない) |
| **集合として列挙する削除の対象に、管理ラベルを持たない Claude コンテナがある** | そのコンテナは**削除しない**。名前と「本変更より前に起動した可能性がある」ことを表示して残す(規則 A) |
| **`stop <name>` の対象コンテナが管理ラベルを持たない** | その1件は**削除する**。管理ラベルを持たないことを表示する(規則 B) |
| **`logout` / `reset` が標準入力を TTY として持たない環境で `--yes` 無しに実行された** | **何も削除せずに中止**し、`--yes` の指定方法を表示して終了コード 1 で終わる。**`stop <name>` はこの行の対象ではない**(利用者が名前で1件を明示的に指した削除であり、確認を求めない = 規則 B。**根拠は `D0-env-08` 項3 が明示する `stop` の免除**であって項1 ではない — 項1 はラベルの要否についての例外である)。`--yes` を受け付けるのも `logout` / `reset` だけである |
| **`claude-dev stop <name>` の `<name>` が `[A-Za-z0-9._-]` 以外を含む** | **何も削除せず**、受理できない文字を含むことを表示して終了コード 1 で終わる(ロックを取る前に検証する) |
| **`stop <name>` の対象コンテナが `claude-dev.project-dir` ラベルを持たない、または既に存在しない** | **compose 資源の削除を行わない。** 一意化名のハッシュ源(起動ディレクトリの絶対パス)はこのラベルにしか無く、推測して作った名前で削除すると別ディレクトリを巻き込む(`docs/issues/024` の欠陥そのもの)。compose 資源が残っている可能性と手動で片付ける方法を表示して続行する(`FR-env-01` 受入基準21)。**本体コンテナの削除・`fwd-*` の片付け・遊休判定は通常どおり行う** |
| **`stop <name>` の対象コンテナが `claude-dev.project-dir` ラベルを持たない、または既に存在しない(セッション由来の資源について)** | **セッション由来の資源の削除も行わない**(`FR-env-01` 受入基準23)。所有者ラベルの値は起動ディレクトリの絶対パスであり、その値はこのラベルにしか無い。**推測して作った値で削除すると別セッションの資源を巻き込む** — compose の一意化名と同じ理由である。片付けを行わなかったことは compose と同じ1つの案内にまとめてよい |
| **`stop` の時点で旧い名前(ハッシュ無し)の compose 資源が残っている** | **削除しない。** 旧名は別ディレクトリと衝突しうるため対象に含めてはならない。可能性があることと、確認・手動削除の方法を表示して続行する(案内に載せる具体的なコマンドは 03 が持つ) |
| **削除中に `INT` / `TERM` を受けた**(Ctrl-C など) | **進行中の1件を終えてから中断する**(1件の削除を途中で切ると中途半端な状態が残る)。**そこまでに削除した資源と、未削除のまま残った資源を1件ずつ列挙**し、**終了コード 130** で終わる(SIGINT の慣行値)。「削除しました」「完了」の文言は出さない。ロックは中断時にも必ず解放される(解放の手段は 03 が持つ) |
| **セッション由来の資源(コンテナ / ネットワーク)の削除に失敗した** | **握って続行する**(`FR-env-01` 受入基準24)。`stop` は `D0-env-08` 項5 の対象外であり、片付けの途中で止まるとより中途半端な状態が残る。**`reset` では握らない**(`logout` / `reset` は項5 の対象なので、消えなかった資源を列挙して終了コード 1 で終わる) |
| **使用中のためセッション由来のネットワークを削除できない** | 握って続行する(compose 既定ネットワークと同じ扱い。`FR-env-01` 受入基準11・24) |
| **セッション由来の資源が1件も無い** | **その旨を表示しない**(`FR-env-01` 受入基準27。対象が無いことを毎回表示しない) |
| **セッション由来の資源を引く問い合わせそのものが失敗した** | **削除の失敗とは別に扱う**。`stop` は**片付けを行わずに続行**し、引けなかったことを表示する(遊休判定と同じく安全側へ倒す。推測で削除しない)。`reset` は**失敗として記録し**、消えなかった資源としてまとめて列挙して終了コード 1 で終わる(`D0-env-08` 項5)。**列挙が空で返ったこと(0件)と、問い合わせが失敗したことを同一視してはならない** |
| **共有ボリュームの中身を消したが、削除後の列挙に何か残っていた** | 残っていたパスを列挙して終了コード 1 で終わる。**判定は「削除後の列挙結果」で行い、削除コマンドの終了コードでは行わない**(削除に使う操作の終了コードは「消えたか」を表さないため。理由の詳細は 03 が持つ) |
| **`logout` / `reset` の削除対象のうち1つ以上が削除できなかった** | 消えなかった資源を1件ずつ列挙し、終了コード 1 で終わる。**成功時の文言を出してはならない** |
| **遊休判定に使う Docker への問い合わせが失敗した**(ネットワークが存在しない / `docker` が応答しない) | **遊休でないと判定して docker-proxy を残す**(安全側へ倒す)。判定できなかったことを表示する。`FR-env-01` 受入基準9 は「稼働中なら止めるな」であり、判定不能を「遊休」と読み替えてはならない |

### DSN-env-01 所有権は「起動時に付けたラベル」で表し、名前とイメージでは表さない

- 内容: **Claude コンテナ**には作った時点で `claude-dev.managed` / `claude-dev.role` /
  `claude-dev.project-dir` を付け、破壊的操作が集合として列挙する削除はこのラベルを根拠にする。
  **固定名または固定接頭辞を持つ資源にはラベルを付けない**(名前で識別できるため。下の
  「識別の手段は資源ごとに違う」)。**名前から所有権が読み取れない資源にはラベルを付ける** —
  Claude コンテナがその1つ目で、**セッション由来の資源が2つ目である**(`DSN-env-04`)。
- 理由: 所有権の根拠になりうる候補は「名前」「イメージ」「ラベル」の3つである。Claude コンテナだけは
  名前が起動ディレクトリ名から決まるため一意でなく(`NFR-scale-01` / `docs/issues/028`)、
  イメージは `latest` が動くとそれ以前のコンテナを取りこぼす(`docs/issues/045`)。
  **逆に固定名を持つ資源にラベルを足すと、既存の資源がラベルを持たないという移行問題を、必要も
  無いのに作り込むことになる。**
- 却下した案:
  - **イメージ ID の履歴を並べて `--filter ancestor` に渡す** — 削除済みイメージから作られた
    コンテナを依然取りこぼす。取りこぼしの原因を減らすだけで、無くせない。
  - **コンテナ名の規約(命名の一意化)で表す** — 利用者に見える名前が変わり、既存コンテナの
    移行手順が必要になる(`docs/issues/028`)。本契約はそれを伴わずに成立する。
  - **`docker inspect` で起動引数を見て判定する** — 起動経路が増えるたびに判定条件が増える。
  - **すべての資源にラベルを付けて統一する** — 固定名の資源にとっては移行問題を増やすだけで、
    得られる情報が無い。
- 影響: **管理ラベルが付く前に起動された Claude コンテナはラベルを持たない。** 規則 A の対象から外れるため、
  `logout` / `reset` はそれを消さずに名前を表示して残す。利用者は `claude-dev stop <name>`(規則 B)で
  1件ずつ止めるか、`docker rm -f` で手動削除する。**遊休判定(規則 C)はラベルに依存しない**ため、
  ラベルの無い既存コンテナが稼働している間も docker-proxy は保護される。
  移行が完了する条件は「ラベルを持たない Claude コンテナが1つも残っていないこと」である。
  `logout` / `reset` が残したものを名前で列挙して表示するので、利用者はその表示が空になったことで
  移行の完了を判別できる(既存の他コマンドの表示は変えない)。
- 関連: `D0-env-08` / `D0-env-10` / `FR-env-01` 受入基準 9・14・15 / `FR-env-03` 受入基準 17 /
  `DSN-env-04`(同じ考え方をセッション由来の資源へ広げたもの)

### DSN-env-03 compose プロジェクト名にパスのハッシュを足して一意にする

- 内容: `COMPOSE_PROJECT_NAME` を `<正規化名>-<絶対パスの SHA-256 先頭6桁>` にする。
  `stop` の compose 片付けはこの一意な名前だけを対象にする。
- 理由: **`DSN-env-04` の導入により、compose 資源にも docker-proxy が所有者ラベルを付けるように
  なった。それでも一意化を残すのは、所有者ラベルが付く前に作られた compose 資源を引く手段が
  一意化名しか無いからである**(移行期の取りこぼしを減らすために両方を使う。`D0-env-08` 項7・項8)。
  一意化を導入した当初の理由は次のとおりで、それは今も成り立つ。
  従来の正規化(`[a-z0-9_-]` 以外を `-` に置換)は非可逆で、
  `~/work/My.App` と `~/other/my-app` が同じ `my-app` に落ちるため、一方の `stop` が他方の
  実行中サービスを削除しうる(`docs/issues/024`。データの破壊に至りうる)。
  絶対パスはプロジェクトを一意に決める唯一の値なので、それをハッシュ源にする。
- 却下した案:
  - **`stop` が削除前に対象名を列挙して確認を取るだけにする** — 名前の非一意性という根本が残るので、
    確認を読み飛ばした利用者は同じ被害に遭う。日常操作である `stop` に確認を足す代償も大きい。
  - **`stop` の compose 片付けをやめる** — `FR-env-01` 受入基準6 と `D0-env-05` のライフサイクルの
    決定に反し、compose コンテナが孤児として残り続ける。
  - **コンテナ名そのものを一意化する**(`docs/issues/028`) — 利用者に見える名前と 11 の呼び出し元が
    動く。compose 名の一意化はそれを伴わずに `024` を閉じられる。
  - **ハッシュだけにする**(正規化名を捨てる) — `docker ps` の出力から人がプロジェクトを見分けられない。
- 影響: **一意化名が導入される前に作られた compose 資源は古い名前を持つため `stop` の対象から外れる**
  (下の「compose 資源の識別」と上の「エラーケース」)。`docker ps` に現れる compose のコンテナ名・
  ネットワーク名が変わる(`<正規化名>_default` → `<正規化名>-<ハッシュ>_default`)。
- 関連: `D0-env-08` 項7 / `NFR-scale-01` / `FR-env-01` 受入基準6・19 / `docs/issues/024`

### DSN-env-04 セッション由来の資源は docker-proxy が付ける所有者ラベルで識別する

- 内容: Claude コンテナの中から docker-proxy を経由して作られる**コンテナ**と**ネットワーク**に、
  **docker-proxy が作成要求を中継するときに次の2つのラベルを付与する**。
  `stop` は所有者が自分と一致するものを、`reset` は所有者を問わず全部を削除対象にする
  (規則 D)。

  | ラベル名 | 値 | 付与する資源 | 誰が付与するか |
  |---|---|---|---|
  | `claude-dev.role` | `spawned`(固定) | セッション由来のコンテナとネットワーク | docker-proxy(作成要求のボディへ注入) |
  | `claude-dev.owner-project-dir` | **呼び出し元 Claude コンテナの `claude-dev.project-dir` ラベルの値をそのまま写したもの**(= 所有者セッションの起動ディレクトリの絶対パス) | 同上 | 同上 |

  - **注入する API 経路は `CTR-docker-api` が定める**(この契約が定めるのは付けるラベルの側である)。**ボリューム作成要求には注入しない**
    (名前付きボリュームは片付けの対象ではない。`D0-env-05` 項2)。
  - **`claude-dev.managed` は付けない。** `logout` / `reset` は「Claude コンテナを集合として
    列挙する」削除の対象を `claude-dev.managed=1` で引くため、付けるとセッション由来の資源が
    `logout` の削除対象に入り、`D0-env-05` 項2 が定めた「`logout` には掛けない」と正面から
    食い違う。**このラベルは所有と種別を表すだけで、`managed` の意味(本システムが**作った**)は
    持たせない。**
  - **利用者が同じキーのラベルを自分で指定していた場合は、docker-proxy の値で上書きする**
    (所有者の判定が利用者の入力で狂うと、別セッションの資源を消しうる)。
    それ以外のフィールドは変更しない(`FR-env-07` 受入基準11)。
  - **「呼び出し元を特定できた」の定義**: 呼び出し元 Claude コンテナを引き当てられ、
    **そのコンテナが `claude-dev.project-dir` ラベルを持ち、その値が空文字でないこと**。
    **値が空文字の場合は「特定できない」に倒す**(下の付与しない経路へ入る)。
    空値のラベルを写すと `claude-dev.owner-project-dir=` を持つ資源ができ、`stop` 側は
    照合値が空になるので片付けられない一方、`reset` の `claude-dev.role=spawned` では消える —
    **両側が同じ1つのラベルに依存するという `DSN-env-04` の根拠が、その1点でだけ破れる**。
    **`/workspace` のマウント元(bind の書き換えに使う値)ではなく、ラベルの値を写す。**
    理由は「値の一致を構成で保証するため」である: `stop` は削除対象を
    `claude-dev.owner-project-dir` == `claude-dev.project-dir` の**文字列一致**で選ぶので、
    2つの値が別々の経路から得られていると、経路のどちらかが正規化・解決を挟んだ瞬間に
    **一致しなくなり、片付けが黙って空振りする**(マウント元は Docker が返す値、ラベルは
    ホスト CLI が書いた値であり、同じである保証が仕様として存在しない)。
    同じラベルを写せば、一致は**構成上の帰結**になり検証を要しない。
  - **呼び出し元を特定できない(コンテナを引き当てられない、または `claude-dev.project-dir` を
    持たない)、またはボディが解釈できない場合は、ラベルを付けずに中継する**
    (`FR-env-07` 受入基準12)。作成要求を拒否してはならない。その資源は片付けの対象から外れる。
    **管理ラベルが付く前に起動された Claude コンテナがこの経路に入る**(そのセッションの中から
    作った資源は片付けられない)。これは `stop` 側の `FR-env-01` 受入基準23 と同じ限界であり、
    **両側が同じ1つのラベルに依存しているので、片方だけが成功する状態は生じない。**
  - **`DSN-env-04` の導入より前に作られた資源はラベルを持たないため対象外である。** 一意化名で引ける
    compose 資源(`DSN-env-03`)を除き、**列挙する手段が無いので表示もしない**。
- 理由: セッション由来の資源は**名前も固定接頭辞も持たない**(名前は利用者が決める)ので、
  `DSN-env-01` が挙げた3候補のうち「名前」は使えない。「イメージ」も同じ理由で使えない
  (利用者が任意のイメージを使う)。残るのは「ラベル」だけであり、**docker-proxy は作成要求が
  必ず通る位置にいて、呼び出し元の絶対パスを既に解決している**(bind の書き換えに使っている)
  ので、印を付ける主体として過不足がない。
  所有者の値に絶対パスを選ぶのは、**`stop` の入力が `NAME` だけで、絶対パスは削除前に読む
  `claude-dev.project-dir` から得られる**ため、読み取りを1回増やさずに済むからである
  (compose 一意化名のハッシュ源と同じ値を使う)。
  **さらにその値を「マウント元」ではなく「呼び出し元コンテナのラベル」から取るのは、
  照合する2つの値を同じ1つの出所に縛るためである**(上の「定義」)。
- 却下した案:
  - **docker-proxy が作成したコンテナ ID と所有者の対応をファイルに記録する** — 記録の置き場所
    (共有 docker-proxy はコンテナで、作り直すと対応表が消える)と記録漏れ(proxy が落ちている
    間に作られたもの)を新しく抱える。ラベルは Docker 側に永続する。
  - **所有者の値に Claude コンテナ名を使う** — 名前は利用者の起動ディレクトリ名から決まり
    一意でない(`NFR-scale-01` / `docs/issues/028`)ので、別ディレクトリの同名プロジェクトの
    資源を巻き込む。絶対パスにはその問題が無い。
  - **所有者の値を `/workspace` のマウント元から取る** — `stop` が照合する
    `claude-dev.project-dir` とは別の出所になり、**両者が一致する保証が仕様として存在しない**
    (Docker がマウント元を正規化・解決した瞬間に、片付けが黙って空振りする)。
    呼び出し元コンテナのラベルを写せば、その懸念自体が消える。
  - **`claude-dev.managed=1` を付けて既存の識別に相乗りさせる** — 上のとおり `logout` の
    削除対象に入ってしまう。
  - **一意化した compose プロジェクト名(`DSN-env-03`)だけで済ませる** — `docker compose` を
    経由しない `docker run` の資源に `com.docker.compose.project` は付かない。
  - **ラベルを付けず、`stop` が「そのセッションの起動以降に作られたコンテナ」を時刻で推定する** —
    別セッションが同時に作った資源を巻き込む。時刻は所有を表さない。
- 影響: **利用者が `docker inspect` したときに、身に覚えのないラベルが2つ増える。**
  所有者ラベルで利用者自身も一覧できる。
  **ホストの絶対パスがラベル値として現れる**が、これは `claude-dev.project-dir` で既に
  起きていることであり、許容範囲は `02-design/logging.md`「起動ディレクトリの絶対パスの扱い」が
  定める。
- 関連: `D0-env-05` 項2 / `D0-env-08` 項8 / `D0-env-10`(この決めの委任元)/ `CTR-docker-api`
  (注入を行う側の契約)/ `FR-env-01` 受入基準22〜27 / `FR-env-07` 受入基準11・12 /
  `DSN-env-01` / `DSN-env-03`

### 識別の手段は資源ごとに違う

**本システムが関与する Docker 資源のうち、名前から所有権が読み取れないのは Claude コンテナと
セッション由来の資源の2つだけ**である(前者は名前が利用者の起動ディレクトリ名から決まり、
後者は名前を利用者が自由に決める)。他の資源は本システムが決めた固定名または固定接頭辞を持つので、
名前で一意に識別できる。**したがって管理ラベルはこの2つに付ける。**

| 資源 | 識別の手段 |
|---|---|
| **Claude コンテナ** | **管理ラベル**(下の表)。名前は利用者のディレクトリ名由来で一意でない |
| **セッション由来の資源**(コンテナ・ネットワーク) | **所有者ラベル**(下の表。`DSN-env-04`)。名前は利用者が決めるので所有権を読み取れない。**ホスト CLI は付与できない**ので docker-proxy が作成要求へ注入する |
| `fwd-<コンテナ名>-<ポート>` 中継コンテナ | **名前の接頭辞 `fwd-`**。本システムが決めた固定接頭辞である |
| docker-proxy コンテナ | **固定名 `claude-dev-docker-proxy`** |
| 共有ボリューム | **固定名** `claude-dev-auth` / `claude-dev-history` / `claude-dev-config`、および接頭辞 `claude-dev-chrome-` / `claude-dev-vm-` |
| ネットワーク | **固定名 `claude-dev-net`** |
| イメージ | **固定名** `claude-dev-claude` / `claude-dev-claude-vnc` / `claude-dev-docker-proxy` |
| **コンテナ内 `docker compose` が作った資源** | 所有者ラベル(上のセッション由来の資源と同じ)に加えて、**ラベル `com.docker.compose.project` の一意化した値**(下の「compose 資源の識別」)。**2つ持つのは移行のためである**: 所有者ラベルが付く前に作られた compose 資源は一意化名でしか引けない |

### 管理ラベル

| ラベル名 | 値 | 付与する資源 | 誰が付与するか |
|---|---|---|---|
| `claude-dev.managed` | `1`(固定) | Claude コンテナ | ホスト CLI(`docker run` の `--label`) |
| `claude-dev.role` | `claude`(Claude コンテナ)/ `spawned`(セッション由来の資源) | Claude コンテナ / セッション由来のコンテナ・ネットワーク | ホスト CLI / **docker-proxy**(`DSN-env-04`) |
| `claude-dev.project-dir` | 起動時のホスト側カレントディレクトリの**絶対パス**(`pwd` の値をそのまま。正規化・短縮をしない) | Claude コンテナ | ホスト CLI |
| `claude-dev.owner-project-dir` | **所有者セッションの起動ディレクトリの絶対パス**(呼び出し元 Claude コンテナの `claude-dev.project-dir` と同じ値) | セッション由来のコンテナ・ネットワーク | **docker-proxy**(`DSN-env-04`) |

- 接頭辞は `claude-dev.` に固定する。`com.docker.*`(Docker / compose の予約)は使わない。
- **`claude-dev.managed` はセッション由来の資源に付けない。** `logout` / `reset` はこのラベルで
  削除対象を集合として引くので、付けると `logout` がセッション由来の資源まで消す
  (`D0-env-05` 項2 の「`logout` には掛けない」に反する)。**「本システムが作った」ことを表すのが
  `managed`、「本システムを通して作られた」ことを表すのが `role=spawned` である。**
- 値の検証は行わない。**受け側は存在するかどうかだけを見る**。ただし `claude-dev.project-dir` と
  `claude-dev.owner-project-dir` の**値そのものには用途がある**: 前者は (1) 利用者への表示、
  (2) **`stop` が compose の一意化名を再現するためのハッシュ源**、(3) **`stop` が所有者ラベルの
  値を再現するための元**。後者は **`stop` の削除対象を絞り込む条件**である。
  **削除するかどうかの判定に `claude-dev.managed` の値を使わない**
  (判定に使うと、ラベルを持たない既存コンテナを取りこぼす)。
- **ラベルを増やすことは互換の破れにならないが、名前と値を変えることは破れになる**
  (既存の稼働コンテナが古いラベルを持ったまま残るため)。変える場合は移行期の扱いを併記する。
- `claude-dev.project-dir` は「どのディレクトリで起動したか」という**事実の唯一の在り処**である。
  そのため次の2つが成立する: 同名コンテナとの衝突時(`FR-env-01` 受入基準12)に
  「別ディレクトリの同名プロジェクトである可能性」を推測ではなく事実として示せる。
  そして **`stop <name>` を別のディレクトリから実行しても compose の一意化名と所有者ラベルの値を
  再現できる**(`stop` の入力は `NAME` だけで、絶対パスは他のどこにも記録されていない)。
  **したがって本体コンテナを削除するとこの値は失われる**(読む時機の固定は 03 が持つ)。

### 削除対象の決め方(4つの規則)

| 規則 | 適用する操作 | 対象 |
|---|---|---|
| **A. 集合として列挙して消す** | `logout` / `reset` のコンテナ削除、`stop` の `fwd-<コンテナ名>-*` 一括削除 | Claude コンテナは `claude-dev.managed=1` を持つものだけ。**ラベルを持たない Claude コンテナは削除せず、名前を表示して残す**(表示対象の集合の求め方は下の「残したものをどう列挙するか」)。`fwd-*` と docker-proxy は上の表の名前規則で識別する(移行問題は起きない) |
| **B. 名前で1件を指して消す** | `claude-dev stop <name>` の本体コンテナ | ラベルの有無を問わず削除する(利用者が明示的に指したものである)。ラベルが無い場合はその旨を表示する。**ただし `<name>` は `[A-Za-z0-9._-]` だけを受理する**(下の「ロックキーとして使える文字」) |
| **C. 共有資源を止めてよいかの判定** | `stop` / `logout` / `reset` の docker-proxy の停止判定、および `reset` の `claude-dev-net` の削除判定(**`stop` と `logout` は `claude-dev-net` を削除する経路を持たない**。`FR-env-01` 受入基準9) | 下の「遊休判定」に従う。**ラベルとイメージのどちらにも依存させない**。`logout` と `reset` は Claude コンテナを削除したあとに判定する(**ラベルを持たない既存コンテナが稼働している間は docker-proxy と `claude-dev-net` を残し、残した理由を表示する**)。`reset` も例外ではない: `D0-env-08` 項2 は例外を書いていない |
| **D. 所有者ラベルで集合として消す**(`DSN-env-04`) | `stop` / `reset` のセッション由来の資源の削除 | `stop` は `claude-dev.owner-project-dir` が**自分の起動ディレクトリの絶対パスと一致する**コンテナとネットワーク。`reset` は `claude-dev.role=spawned` を持つ**すべての**コンテナとネットワーク(所有者を問わない)。**`logout` はこの規則を使わない**(`D0-env-05` 項2)。**使用中のネットワークが残らないよう、資源間の依存を解いてから削除する**(順序の固定は 03 が持つ)。`stop` は削除の失敗を握って続行し(`FR-env-01` 受入基準24)、`reset` は握らない(`D0-env-08` 項5)。**削除した資源の名前は種別つきで1行ずつ表示し、0件なら表示しない**(`FR-env-01` 受入基準26・27)。**規則 A と対象が重なる場面は無い**: 規則 A が引くのは `claude-dev.managed=1`、規則 D が引くのは `claude-dev.role=spawned` で、両方を持つ資源は存在しない |

### 残したものをどう列挙するか(ラベルを持たないコンテナの表示)

規則 A は「ラベルを持たない Claude コンテナは削除せず名前を表示する」と定める。**ラベルが無いのだから
ラベルでは引けない**ので、集合はこう求める。

**`claude-dev-net` に接続している稼働中コンテナから、名前が `claude-dev-docker-proxy` のものと
名前が `fwd-` で始まるものと `claude-dev.managed=1` を持つものと
`claude-dev.role=spawned` を持つものを除いた残り**が、
「本システムのものかもしれないがラベルを持たないコンテナ」である。これを名前で表示する。

- **`claude-dev.role=spawned` を除くのは `DSN-env-04` の帰結である。** セッション由来の資源は
  管理ラベルを持つので「ラベルを持たないコンテナ」ではなく、`FR-env-03` 受入基準17 が表示を
  求める集合に入らない。**除かないと `reset` が同じコンテナを「規則 D で削除する」と
  「ラベルを持たないので残した」の両方に表示することになる**(利用者が読める矛盾になる)。
  これらは規則 D が削除するので、表示ではなく削除の側で扱われる。
  **4つの除外はいずれも `logout` と `reset` の双方に掛かる**(表示の集合の求め方は
  この節が唯一の正であり、読み手のモジュールはこの節に従う)。`logout` はセッション由来の
  資源を削除しない(規則 D を使わない)が、**削除しないことと「ラベルを持たない」と
  表示することは別である** — 表示すると事実に反する。
- 遊休判定(下)と**同じ集合の求め方を使う**。ただし**遊休判定はラベルによる除外を一切行わない**
  (`FR-env-01` 受入基準9。ラベルに依存させると数え落とす)。**この表示の集合と遊休判定の集合は別である**(どこまでを共通に求めるかは 03 が持つ)。
- **停止中のラベル無しコンテナは列挙できない**(ネットワークへの接続からは稼働中のものしか引けない)。これは意図した限界である: 停止中のコンテナは利用者の作業を壊さないので急がず、
  `claude-dev stop <name>`(規則 B)で1件ずつ消せる。**この限界を表示にも書く**
  (「停止中のものは列挙していない」)。
- **利用者が自分で立てた無関係なコンテナも混じりうる**(`claude-dev-net` に手で繋いだ場合)。
  混じっても**削除はしない**(表示だけ)ので害はない。

### compose 資源の識別(プロジェクト名の一意化)

コンテナ内の `docker compose` が作る資源は、**所有者ラベル**(`DSN-env-04`)と
**一意化した `com.docker.compose.project` の値**の**2つで識別する**。
どちらも本システムが付けられる: 作成要求は必ず docker-proxy を通るので所有者ラベルは
docker-proxy が注入し、compose プロジェクト名はホスト CLI が `COMPOSE_PROJECT_NAME` で決める。

**2つ持つのは移行のためである**: **所有者ラベルが付く前に作られた compose 資源を引く手段は
一意化名しか無い**(`D0-env-08` 項7・項8)。逆に `docker compose` を経由しない `docker run` の
資源には `com.docker.compose.project` が付かないので、一意化名だけでは足りない。
本節が定めるのは後者、**一意化名の作り方**である。

**`COMPOSE_PROJECT_NAME` = `<正規化名>-<ハッシュ短縮値>`**

| 部分 | 定義 |
|---|---|
| 正規化名 | 起動ディレクトリ名を小文字化し、`[a-z0-9_-]` 以外の1文字を `-` に置換した値(**人が読める部分をコンテナ名に残すため**、ハッシュだけにはしない) |
| ハッシュ短縮値 | **起動ディレクトリの絶対パス**(`pwd` の値)の **SHA-256 の先頭6桁**(16進小文字) |

- ハッシュの入力は**絶対パス**である(ディレクトリ名ではない)。これにより
  `~/work/My.App` と `~/other/my-app` は正規化名が同じ `my-app` でも別の値になる。
- 6桁(24ビット)にした理由: 同時に扱うプロジェクト数は数十のオーダーで、衝突確率が実用上無視できる
  一方、コンテナ名として読める長さに収まる。**桁数を変えると既存の compose 資源が対象から外れる**
  ので、変える場合は移行期の扱いを併記する。
- **衝突は検出しない**(2026-08-04 に人間が受容。`docs/pendings.md` **P-005**)。
  異なる絶対パスが同じ先頭6桁になった場合、その2ディレクトリでは一方の `stop` が他方の
  compose 資源を削除しうる(`docs/issues/024` と同じ事象が、確率は桁違いに低い形で残る)。
  **この一意化が保証するのは「衝突の確率が実用上無視できる水準であること」までであり、
  衝突がゼロであることは保証しない**(絶対パスをハッシュ源にしているため、正規化名が同じでも
  別の値になるが、先頭6桁の一致は起こりうる)。解消が必要になる条件と選択肢は P-005 が持つ。
- 実装は Linux と macOS で**同じ値**を出さなければならない(`D0-scope-03`)。
  コマンド名が OS で違う点は 03 の実装上の判断が扱う。
- **`stop` はハッシュ源(起動ディレクトリの絶対パス)を `claude-dev.project-dir` ラベルから読む。**
  `stop` の入力は `NAME` だけで絶対パスを持たないため、**本体コンテナを削除するとこの値は失われる**
  (読む時機の固定は 03 が持つ)。**ラベルが無い/対象コンテナが存在しない場合は compose の片付けを
  行わず、手動手順を案内する**(推測でハッシュを作ると別ディレクトリを巻き込む)。
- **`stop` の compose 片付けはこの一意な名前だけを使う**。これで別ディレクトリの compose 資源を
  巻き込む経路が閉じる(`docs/issues/024`)。
- **ハッシュ短縮値を持たない古い名前(`<正規化名>` だけ)の compose 資源が既存環境に残っている場合、
  それは `stop` の片付け対象から外れる**(その名前を作った時点の実装が一意化していなかった)。
  `stop` はその可能性と、確認・手動削除の方法を案内する(`D0-env-08` 項7。案内の具体的な
  コマンドは 03 が持つ)。
  **古い名前を対象に含めてはならない**: それをすると衝突する別ディレクトリを巻き込む今の欠陥が
  そのまま残る。
